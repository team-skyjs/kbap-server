# Feature Specification: member 스키마 재편 — 소셜 신원 통합·정지 상태 분리·탈퇴 시 신원 더미 치환

**Feature Branch**: `kb-117-member-schema-consolidation`

**Created**: 2026-07-10

**Status**: Draft

**Input**: User description: "kb-117 작업" (Jira KB-117 — [BE] member 스키마 재편 — 소셜 신원 테이블 통합, 정지 상태 컬럼 분리, 탈퇴 시 신원 더미 치환)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 탈퇴 후 같은 소셜 계정으로 재가입 (Priority: P1)

탈퇴한 사용자가 나중에 같은 소셜 계정(구글·애플 등)으로 다시 로그인하면, 아무 장애 없이 신규 회원으로 가입된다. 회원 신원 정보를 회원 레코드에 통합하면 탈퇴(소프트 삭제)된 레코드에 소셜 식별자가 남아 재가입이 막히는 문제가 생기므로, 탈퇴 시점에 소셜 식별자를 회원마다 유일한 더미값으로 치환해 재가입 경로를 열어 둔다.

**Why this priority**: 재가입이 막히면 사용자는 서비스에 영구히 복귀할 수 없다 — 신원 통합 재편의 성립 조건이자 가장 치명적인 회귀 지점.

**Independent Test**: 가입 → 탈퇴 → 같은 소셜 계정으로 재로그인 흐름을 영속 계층 통합 테스트로 검증할 수 있다. 재가입 성공 시 새 회원이 생성되면 가치가 전달된다.

**Acceptance Scenarios**:

1. **Given** 소셜 계정으로 가입한 회원이 있을 때, **When** 그 회원이 탈퇴한 뒤 같은 소셜 계정으로 다시 로그인하면, **Then** 신규 회원으로 정상 가입된다.
2. **Given** 탈퇴한 회원 레코드가 남아 있을 때, **When** 그 레코드를 조회하면, **Then** 원본 소셜 식별자와 이메일이 남아 있지 않다(식별자는 회원별 유일 더미값, 이메일은 비어 있음).

---

### User Story 2 - 회원 정지 상태 관리 (Priority: P2)

운영자가 회원을 정지시키면 그 회원은 서비스 이용(서비스 측 조회)에서 제외된다. 다만 정지는 삭제가 아니므로 관리자 조회에서는 정지 회원이 그대로 보여야 한다 — 소프트 삭제 상태와 정지 상태는 서로 다른 축으로 분리해 관리한다.

**Why this priority**: 현재 정지 상태를 표현할 자리가 없다. 소프트 삭제 상태에 정지를 끼워 넣으면 정지 회원이 관리자 조회에서도 사라져 운영이 불가능해진다.

**Independent Test**: 정지 상태 회원을 만들어 서비스 조회 경로와 관리자 조회 경로의 노출 여부를 영속 계층 통합 테스트로 각각 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 정지 상태의 회원이 있을 때, **When** 서비스 조회 경로로 회원을 조회하면, **Then** 정지 회원은 결과에서 제외된다.
2. **Given** 정지 상태의 회원이 있을 때, **When** 관리자 조회 경로로 회원을 조회하면, **Then** 정지 회원이 결과에 포함된다.
3. **Given** 신규 가입한 회원이 있을 때, **When** 상태를 확인하면, **Then** 기본값은 활성(ACTIVE)이다.

---

### User Story 3 - 회원 신원·스키마 단일화 (Priority: P3)

회원의 소셜 플랫폼 구분, 플랫폼 고유 식별자, 이메일은 회원당 하나뿐이므로 별도 신원 테이블 없이 회원 레코드 한 행에서 통합 관리한다. 테이블 이름도 프로젝트 명명 규칙(단수형)에 맞춘다. 기피성분·맵기 선호·국가코드·언어코드는 프로필 항목 묶음(단일 유연 구조)으로 이관해 스키마 변경 없이 항목을 늘릴 수 있게 한다.

**Why this priority**: 내부 구조 개선 — 사용자 눈에 직접 보이진 않지만 US1·US2 의 전제이며, 로그인 로직을 "조회해서 없으면 가입, 있으면 로그인" 단일 분기로 유지하는 기반이다.

**Independent Test**: 신원 조회가 항상 0건 또는 1건을 반환하는지, 프로필 항목이 저장·복원되는지 영속 계층 통합 테스트로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** (소셜 플랫폼, 플랫폼 고유 식별자) 조합에 유일 제약이 있을 때, **When** 신원으로 회원을 조회하면, **Then** 결과는 항상 0건 또는 1건이다.
2. **Given** 회원이 기피성분·맵기 선호·국가코드·언어코드를 설정했을 때, **When** 회원을 저장 후 다시 조회하면, **Then** 프로필 항목이 그대로 복원된다.

---

### Edge Cases

- 동일 소셜 계정의 첫 로그인이 동시에 두 건 들어오면? → 고려하지 않는다(발생 가능성이 희박해 무시 — 범위 밖). 유일 제약은 데이터 정합용으로만 유지한다.
- 같은 소셜 계정으로 가입·탈퇴를 여러 번 반복하면? → 탈퇴마다 회원별 유일 더미값으로 치환되므로 탈퇴 레코드끼리도 충돌하지 않고 매번 재가입이 가능하다.
- 탈퇴한 회원과 정지된 회원이 섞여 있을 때 관리자 조회는? → 정지 회원은 보이고, 탈퇴(소프트 삭제) 회원은 소프트 삭제 규칙을 따른다(정지 ≠ 삭제).
- 계정 연결(한 회원이 구글·애플 동시 연결)은? → 이번 재편으로 회원당 신원 1개로 축소되어 지원하지 않는다(범위 밖 — 필요 시 별도 재분리 작업).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 회원의 소셜 플랫폼 구분·플랫폼 고유 식별자·이메일은 별도 신원 테이블 없이 회원 레코드에서 단일 관리되어야 한다(회원당 신원 1개).
- **FR-002**: (소셜 플랫폼, 플랫폼 고유 식별자) 조합의 유일 제약은 재편 후에도 그대로 유지되어야 하며, 신원 기반 회원 조회는 항상 0건 또는 1건을 반환해야 한다.
- **FR-003**: 회원 테이블 이름은 프로젝트 명명 규칙(단수형)을 따라야 한다(members → member, 신원 테이블은 제거).
- **FR-004**: 탈퇴 시 회원 레코드는 소프트 삭제로 남기되, 소셜 식별자는 회원마다 유일한 더미값으로 치환하고 이메일은 비워야 한다 — 원본 소셜 식별자·이메일이 저장소에 남지 않아야 한다.
- **FR-005**: 탈퇴한 사용자는 같은 소셜 계정으로 즉시 재가입할 수 있어야 한다.
- **FR-006**: 회원 정지 상태는 소프트 삭제 상태와 별도의 상태 축(활성/정지, 기본 활성)으로 관리되어야 하며, 소프트 삭제 상태 값에 정지를 추가해서는 안 된다.
- **FR-007**: 서비스 조회 경로는 정지 회원을 제외해야 하고, 관리자 조회 경로는 정지 회원을 포함해야 한다.
- **FR-008**: 기피성분·맵기 선호·국가코드·언어코드는 단일 프로필 항목 묶음으로 저장되어야 하며, 항목 추가 시 저장 구조 변경이 필요 없어야 한다.
- **FR-009**: 기존 저장 구조에서 새 구조로의 전환은 기존 회원 데이터(신원·프로필 항목)를 손실 없이 이관해야 한다.

### Key Entities

- **회원(Member)**: 서비스 이용 주체. 소셜 신원(플랫폼 구분·플랫폼 고유 식별자·이메일)을 자신의 속성으로 직접 보유하고, 소프트 삭제 상태와 별개로 활성/정지 상태를 가진다. 프로필 항목 묶음(기피성분·맵기 선호·국가코드·언어코드)을 포함한다.
- **소셜 신원(Social Identity)**: 회원을 외부 소셜 플랫폼과 잇는 식별 정보 — (플랫폼, 플랫폼 고유 식별자) 조합은 전체 회원에서 유일하다. 재편 후 독립 엔터티가 아니라 회원의 단일 속성이 된다.
- **회원 프로필(Member Profile)**: 기피성분·맵기 선호·국가코드·언어코드 등 개인화 설정 묶음. 항목 확장이 자유로운 유연 구조로 저장된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 탈퇴한 사용자가 같은 소셜 계정으로 재로그인하면 100% 신규 가입에 성공한다(가입·탈퇴 반복 횟수와 무관).
- **SC-002**: 탈퇴 처리 직후 저장소 어디에도 해당 회원의 원본 소셜 식별자·이메일이 남지 않는다(잔존 0건).
- **SC-003**: 신원 기반 회원 조회는 어떤 데이터 상태에서도 0건 또는 1건만 반환한다(중복 반환 0회).
- **SC-004**: 정지 회원은 서비스 조회 결과에 0건 노출되고, 관리자 조회에서는 100% 노출된다.
- **SC-005**: 재편 전 존재하던 회원의 신원·프로필 항목이 재편 후 조회에서 동일하게 복원된다(데이터 손실 0건).

## Assumptions

- 회원당 소셜 신원은 정확히 1개다 — 한 회원이 여러 소셜 계정을 연결하는 기능(계정 연결)은 이번 범위에서 제외하며, 필요 시 별도 작업으로 재분리한다.
- 탈퇴 시 더미 치환 값은 회원 식별자 기반으로 회원마다 유일하게 만든다(예: `withdrawn:{회원ID}` 형태).
- 프로필 항목(기피성분·맵기 선호·국가코드·언어코드)은 유연 구조로 묶이므로 이 값들에 대한 색인·저장소 수준 필터링은 지원하지 않는다 — 언어별 집계·타깃팅이 필요해지면 해당 항목만 다시 독립 항목으로 승격한다.
- 관리자 조회 경로는 현재 별도 관리자 화면/API 가 없으므로 저장소(영속) 계층의 조회 능력으로 제공·검증한다(관리자용 화면/API 는 범위 밖).
- 정지 처리를 수행하는 운영 도구(정지시키는 API·화면)는 이번 범위 밖이다 — 이번 작업은 정지 상태의 표현과 조회 규칙까지만 다룬다.
- 아직 프로덕션 이전 단계이므로 기존 데이터 이관은 개발 환경 데이터 기준으로 수행한다.
- 동일 소셜 계정의 동시 첫 로그인 경합은 발생 가능성이 희박해 요구사항·검증 대상에서 제외한다(사용자 결정).
