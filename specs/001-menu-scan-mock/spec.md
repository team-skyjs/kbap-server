# Feature Specification: 메뉴 스캔 제출·판정 & 음식 상세 조회 (mock 슬라이스)

**Feature Branch**: `001-menu-scan-mock`

**Created**: 2026-06-27

**Status**: Draft

**Input**: User description: "메뉴 스캔 제출·판정과 음식 상세 조회 (mock 판정 기반 첫 수직 슬라이스). 클라이언트가 메뉴명 목록과 바운딩 박스를 보내면 서버가 각 메뉴에 4단계 위험도(SAFE/CAUTION/DANGER/UNKNOWN)를 mock으로 돌려준다. 회원·알러지·인증·실제 판정·LLM 로직은 이번 범위에서 제외. 두 번째 API는 메뉴명으로 음식 상세 정보를 조회한다."

## 개요 / 의도

이 기능은 Meogo의 **메뉴 스캔 흐름을 처음부터 끝까지(end-to-end) 연결하는 최소 수직 슬라이스**다. 실제 위험도 판정·음식 데이터 생성·회원 개인화 없이, **API 계약과 데이터 흐름의 골격**을 먼저 세운다. 위험도는 mock(4단계 순환)으로 내려주어 프론트엔드가 결과 화면 UI를 즉시 통합·검증할 수 있게 한다. 이후 반복(iteration)에서 mock을 실제 판정 로직으로 교체한다.

### Session 2026-06-27

- Q: "최소 저장"의 저장소를 무엇으로 할까? → A: MySQL + JPA (scan 도메인에 JPA Entity·Repository, `api` 모듈에 Flyway 마이그레이션 추가; 정식 영속 경로)
- Q: itemId의 타입과 유일성 범위는? → A: 정수 인덱스(0..n), 한 스캔 요청 내에서만 유일, 클라이언트가 요청 바디에 포함해 전달
- Q: 음식 상세 조회(API 2)의 메뉴명 매칭 방식은? → A: 정확 일치(trim 후 exact match) — 보낸 메뉴명이 저장된 음식명과 완전히 같아야 조회 (정규화·별칭 매칭은 후속)
- Q: 바운딩 박스 좌표의 표현 방식은? → A: **정규화 좌표(normalized ratio)로 확정**. (기존 "opaque Double, 단위 미규정" 결정을 대체.) 좌표는 픽셀이 아니라 **클라이언트가 OCR을 수행한 기준 이미지** 대비 비율값이다. 좌상단 (0,0), 우하단 (1,1). 필드 범위: `x∈[0,1)`, `y∈[0,1)`, `width∈(0,1]`, `height∈(0,1]`. 검증: `x≥0, y≥0, width>0, height>0, x+width≤1, y+height≤1`. 해상도 독립적이라 표시 이미지 크기가 달라도 클라이언트가 비율을 실제 크기에 곱해 오버레이를 안정적으로 복원할 수 있다.
- Q: 바운딩 박스는 필수인가 선택인가? → A: **필수**. 각 scan item은 반드시 boundingBox를 포함해야 하며, 누락/검증 위반 좌표는 요청 거부(400). 위험도 판정엔 사용하지 않고 UI 오버레이/재현용으로 저장만.
- 이미지 처리 전제(이번 범위): Lambda 이미지 압축은 **aspect ratio를 유지**해야 정규화 좌표가 그대로 유효하다. **crop/padding/rotation/orientation 보정처럼 좌표 기준을 바꾸는 처리는 이번 범위에서 하지 않는다.** 후속에 도입하면 이미지 변환 메타데이터 또는 좌표 재계산 정책을 별도로 정의해야 한다.
- Q: mock 위험도 순환의 기준은? → A: **요청 `items` 배열 순서**(0-based index). index 0→SAFE, 1→CAUTION, 2→DANGER, 3→UNKNOWN, 이후 동일 순서 반복. `displayOrder` 같은 별도 필드는 이번 범위에서 필수로 두지 않고 서버가 배열 순서를 판정 순서로 사용.
- Q: 음식 상세 조회에서 메뉴명이 없을 때 응답은? → A: **HTTP 400 + `BaseResponse.fail("해당 음식 정보 없음")`** (2026-06-28 갱신: 이전 404에서 변경 — 미수록 메뉴 상세 요청을 잘못된 요청으로 취급). menuName 누락/blank도 **HTTP 400 + `BaseResponse.fail("menuName은 필수입니다")`**.
- Q: 한 스캔 요청의 최대 items 수는? → A: **100개**로 확정. 초과 시 HTTP 400 거부.
- Q: 이번 mock slice의 FoodDetail 응답 언어 범위는? → A(2026-06-27 갱신, 이전 "ko/en 두 필드" 결정 대체): **`ko` 원문 + 9개 대상 언어 전체 지원**(헌법 V v2.0.0·ADR-0003). API 2는 **쿼리 파라미터 `lang`** 으로 대상 언어를 받아 해당 번역본을 반환하고, 미지정/미지원은 `ko` 폴백(B-2 방식). seed가 9개 번역을 직접 포함하며, 실제 번역 생성(배치)·회원 기반 언어 해석은 후속. → 이를 위해 **헌법 원칙 V를 v2.0.0으로 개정**(한·영만 → 9개국어).
- Q: (향후 9개국어 시) 응답 언어를 무엇으로 결정하나 — 헤더 vs 회원 설정? → A: **인증된 회원의 `MemberProfile.사용 언어` 설정이 권위 출처**(member.md). `Accept-Language` 헤더는 익명/온보딩 전 폴백으로만. api/application이 하나의 target language로 해석해 유스케이스에 주입(food 도메인은 출처 모름). **인증/회원 + 9개국어 구현 이후 적용 — 이번 슬라이스 무변화.**
- Q: 클라이언트가 OCR 신뢰도(ocrConfidence)를 보내나? → A: **아니오.** 클라이언트가 전송하지 않으므로 요청 스키마에서 제거(받지 않음).
- Q: scanId 식별자를 UUID vs auto-increment 중 무엇으로? → A: **auto-increment `BIGINT` PK**. 이번 범위엔 스캔 재조회 API·민감정보·인증이 없어 순차 ID 노출의 enumeration 위험이 발휘될 데가 없고, auto-increment가 더 단순·성능 유리. 남용 추적은 scanId 불투명화가 아니라 요청자 연결로 수행(아래).
- Q: 스캔에 "누가 찍었는지(요청자)"를 기록하나? → A: **전면 후속 이관.** 이상 사진 추적·제한 목적의 요청자 식별은 신뢰 가능한 신원(인증)이 필요하므로, **요청자 컬럼·연결은 auth/member 기능에서 일괄 추가**한다. 이번 mock 슬라이스는 **완전 익명** 유지(스키마에 requester 컬럼 두지 않음).
- Q: 스캔 응답에 음식 상세를 모두 담을지(eager), 탭 시 별도 조회할지(lazy)? → A: **lazy 유지(2 API)**. 스캔 응답은 항목별 위험도만(가볍게), 음식 상세는 사용자가 탭할 때 API 2로 별도 호출.
- Q: 음식 상세 응답에 무엇을 담나? → A: 대표 이미지 + **재료 목록**(재료별 `재료명`(ko/en)·`아이콘`·`포함 비율(%)`·`riskStatus`). UI의 재료 카드(예: "바지락 조개 ~50% / 문의 필요")를 구성할 구조화 값.
- Q: 사장님 안내 설명 문장("된장찌개에는 보통 바지락 조개이(가) 들어가요 (약 50%)…")을 DB에 저장하나? → A: **저장하지 않는다.** 동적 값(음식명·재료명·포함%)은 이미 DB에 저장돼 응답에 실리고, **고정 뼈대 문구는 언어별 UI 템플릿(정적 리소스)**으로 두며, 완성 문장은 **클라이언트가 런타임에 조합**한다.
- 재료 포함 비율(`inclusionPercent`)은 **연속 퍼센티지(0~100%)**로 모델링한다 — **여러 레시피를 조회했을 때 해당 재료가 포함되는 정도(확률)**를 뜻하며, UI가 `~50%`·`~100%`로 표시하는 저장·표시값이다. `food.md`의 `0/1/2`는 이와 **별개 개념**으로, 후속에 LLM이 레시피를 찾아 매기는 **per-recipe 스코어링 입력값**이며 위 퍼센티지를 산출하는 데 쓰인다(이번 범위 밖). 둘은 충돌이 아니므로 `food.md`는 `0/1/2`를 '퍼센티지 산출용 스코어'로 위치시키도록 정리한다.
- 재료별 `riskStatus`는 **4단계 `RiskLevel`(SAFE/CAUTION/DANGER/UNKNOWN)** 값으로(재료 전용 enum 없이 항목 판정과 동일 enum 재사용), 본래 **사용자 식이 제한 의존(assessment)** 값이다. 이번 mock 슬라이스에선 사용자 프로필이 없으므로 **mock 값**으로 내려준다(UI의 '안전/문의 필요' 표시는 클라이언트가 매핑). 실제 개인화 판정은 후속.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 메뉴 스캔 제출 후 항목별 위험도 받기 (Priority: P1)

앱 사용자가 식당 메뉴판을 촬영하면, 클라이언트가 메뉴명들을 추출하고 **각 메뉴명의 화면 위치(바운딩 박스)를 반드시 함께** 서버로 보낸다. 서버는 각 메뉴 항목에 대해 4단계 위험도 결과를 돌려주고, 클라이언트는 그 결과를 자신이 보낸 항목과 매칭해 메뉴판 위에 색·아이콘 오버레이로 표시한다.

**Why this priority**: 이 서비스의 핵심 사용자 가치("이 메뉴가 나에게 안전한가")가 작동하는 첫 경로다. 이것만 있어도 프론트엔드가 결과 화면을 만들고 4가지 UI 상태를 시연할 수 있는 독립적 MVP가 된다.

**Independent Test**: 메뉴명·itemId·바운딩 박스가 담긴 항목 목록을 제출하고, 응답이 (1) 모든 itemId에 대해 빠짐없이 결과를 포함하는지, (2) 결과가 항상 4단계 중 하나인지, (3) 같은 itemId로 요청-응답이 매칭되는지, (4) boundingBox 누락/잘못된 좌표 요청이 거부되는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 클라이언트가 서로 다른 메뉴명 4개(각각 고유 itemId·**boundingBox 포함**)를 담은 스캔 요청을 보냈을 때, **When** 서버가 처리하면, **Then** 응답에는 scanId와 4개 항목 결과가 포함되고 각 결과는 요청의 itemId와 1:1로 매칭되며 각각 4단계 위험도 중 하나를 가진다.
2. **Given** 메뉴판에 동일한 메뉴명("공기밥")이 서로 다른 위치에 2번 등장(itemId는 서로 다름)했을 때, **When** 스캔을 제출하면, **Then** 두 항목은 각자의 itemId로 구분된 별도 결과를 받는다(메뉴명이 같아도 혼동되지 않는다).
3. **Given** `items` 배열이 순서대로 나열된 요청일 때, **When** mock 판정이 적용되면, **Then** 위험도는 **요청 배열의 0-based index**를 기준으로 `index 0→SAFE, 1→CAUTION, 2→DANGER, 3→UNKNOWN`을 부여하고, 4번째 이후 항목은 동일 순서로 반복한다(예: index 4→SAFE).
4. **Given** itemId 또는 rawMenuName 또는 boundingBox가 빠졌거나 boundingBox 정규화 좌표 검증을 위반한(예: `x+width>1`, `width≤0`, `x<0`) 요청일 때, **When** 서버가 검증하면, **Then** 요청을 거부(400)하고 무엇이 잘못됐는지 알 수 있게 응답한다.
5. **Given** 유효한 스캔이 제출되어 scanId가 발급됐을 때, **When** 처리가 끝나면, **Then** 스캔 요청과 항목(원문 메뉴명·boundingBox·mock 판정 결과)이 영속 저장소에 최소한으로 보존되어 동일 scanId로 식별 가능하다(별도 재열람 API는 이번 범위 밖이며, 저장은 repository/service 테스트로 검증).

### User Story 2 - 메뉴명으로 음식 상세 정보 조회 (Priority: P2)

외국인 사용자가 스캔 결과에서 특정 메뉴(음식)를 **탭하면**, 클라이언트는 **메뉴명 + 대상 언어**로 음식 상세 정보를 **사용자 언어로** 조회한다. 상세 화면은 대표 이미지와 함께 **들어가는 재료 목록**을 보여주며, 각 재료에는 **포함 비율(예: ~50%)**과 **안전/문의 필요 상태**가 표시된다. 사용자가 "문의 필요" 재료를 탭하면 사장님께 보여줄 안내 문구가 노출된다.

> FoodDetail 음식명·재료명은 **한국어(`ko`) 원문 + 9개 대상 언어**로 사전 번역돼 저장되며(헌법 V·ADR-0003), API는 요청 대상 언어의 번역본을 반환한다(미지정/미지원 → `ko` 폴백). 이번 슬라이스에선 **seed가 9개 번역을 직접 포함**하고, 대상 언어는 **쿼리 파라미터로** 받는다 — 실제 번역 생성(배치)·회원 기반 언어 해석은 후속.

**Why this priority**: 스캔 결과에서 개별 음식의 이해를 돕는 보조 흐름이다. P1(스캔)과 독립적으로 동작하며(탭 시에만 lazy 호출), 음식 상세 화면을 단독으로 개발·시연할 수 있다.

**Independent Test**: 시드(seed)된 메뉴명을 여러 `lang`(예: `en`·`ja`)으로 조회해 해당 언어 음식명·재료명이 반환되는지, 미지원/미지정 언어는 `ko` 폴백, 없는 메뉴명은 400, menuName 누락/blank는 400으로 응답되는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 시드 데이터에 존재하는 메뉴명("된장찌개")과 `lang=en`으로, **When** 음식 상세 조회를 요청하면, **Then** HTTP 200 + `BaseResponse.ok(FoodDetail)`로 **영어** 음식명·대표 이미지 참조와 **재료 목록**이 반환되고, 각 재료는 영어 재료명·아이콘 참조·포함 비율(%)·riskStatus(4단계 `RiskLevel`)를 포함한다.
2. **Given** 동일 메뉴명을 다른 `lang`(`ja`·`vi` 등)으로, **When** 조회하면, **Then** 음식명·재료명이 각 언어 번역본으로 반환된다.
3. **Given** `lang` 미지정 또는 지원하지 않는 코드(예: `lang=xx`)로, **When** 조회하면, **Then** `ko` 원문으로 폴백해 반환한다(오류 아님).
4. **Given** 시드 데이터에 없는 메뉴명으로, **When** 조회를 요청하면, **Then** HTTP 400 + `BaseResponse.fail("해당 음식 정보 없음")`으로 응답한다(미수록 메뉴 상세 요청은 잘못된 요청으로 취급).
5. **Given** menuName이 누락되었거나 빈 값일 때, **When** 조회를 요청하면, **Then** HTTP 400 + `BaseResponse.fail("menuName은 필수입니다")`로 응답한다.
6. **Given** 응답의 재료별 구조화 값(음식명·재료명·포함%)이 주어졌을 때, **When** 클라이언트가 "문의 필요" 재료의 안내 문구를 만들면, **Then** 서버가 완성 문장을 저장/전송하지 않고도 클라이언트가 템플릿 뼈대에 값을 끼워 문장을 조합할 수 있다.

---

### Edge Cases

- **빈 항목 목록**: `items`가 비어 있는 스캔 요청은 거부한다(최소 1개 항목 필요, 400).
- **항목 수 초과**: `items`가 **100개를 초과**하면 거부한다(400).
- **필수 필드 누락**: itemId 또는 rawMenuName이 없는 항목이 포함되면 요청을 거부하고(400) 어떤 항목이 잘못됐는지 알 수 있게 한다.
- **itemId 중복**: 한 요청 안에서 itemId가 중복되면 응답 매칭이 모호해지므로 거부한다(400).
- **boundingBox 누락**: boundingBox는 **필수**이므로 항목에 없으면 요청을 거부한다(400).
- **boundingBox 좌표 오류**: 정규화 좌표 검증을 위반하는 값은 거부한다(400) — `x < 0`, `y < 0`, `width ≤ 0`, `height ≤ 0`, `x + width > 1`, `y + height > 1`. boundingBox는 판정에 쓰이지 않고 저장만 하지만, 유효성은 검증한다.
- **음식 상세 - 메뉴명 미존재**: HTTP 400 + `BaseResponse.fail("해당 음식 정보 없음")` (미수록 메뉴 상세 요청을 잘못된 요청으로 취급).
- **음식 상세 - menuName 누락/blank**: HTTP 400 + `BaseResponse.fail("menuName은 필수입니다")`.
- **음식 상세 - lang 미지정/미지원**: 오류 없이 `ko` 원문으로 폴백 반환.
- **음식 상세 - 특정 언어 번역 누락**: 특정 음식/재료의 요청 언어 번역이 비어 있으면 그 항목만 `ko`로 폴백(전체 응답은 정상 200).
- **재료가 없는 음식**: 재료 목록이 빈 배열로 내려갈 수 있어야 한다(오류 아님).

## Requirements *(mandatory)*

### Functional Requirements

#### 메뉴 스캔 제출 + 판정 (API 1)

- **FR-001**: 시스템은 한 번의 스캔 요청으로 **여러 개의 메뉴 항목**을 받을 수 있어야 한다. 각 항목은 클라이언트가 **요청 바디에 부여한 itemId(정수 인덱스, 한 스캔 내 유일)**, **원문 메뉴명(rawMenuName)**, **바운딩 박스(boundingBox, 필수)**를 포함한다. (OCR 신뢰도는 클라이언트가 전송하지 않으므로 받지 않는다.)
- **FR-002**: 시스템은 같은 메뉴명이 여러 번 등장하더라도 **itemId(정수 인덱스)로 각 항목을 구분**하고, 응답 결과를 동일 itemId로 요청과 매칭할 수 있어야 한다. itemId는 한 스캔 요청 안에서만 유일하면 되고, 서버는 전역 유일성을 기대하지 않는다.
- **FR-003**: 시스템은 각 메뉴 항목에 대해 **4단계 위험도(`SAFE`/`CAUTION`/`DANGER`/`UNKNOWN`) 중 정확히 하나**를 결과로 부여해야 한다.
- **FR-004**: 이번 범위에서 위험도는 **mock**으로 산출하며, **요청 `items` 배열의 0-based index를 판정 순서로 사용**해 `index % 4`에 따라 `0→SAFE, 1→CAUTION, 2→DANGER, 3→UNKNOWN`을 순환 배정한다. `displayOrder` 같은 별도 필드는 이번 범위에서 요구하지 않는다(배열 순서가 판정 순서).
- **FR-005**: 시스템은 유효한 스캔 요청을 처리할 때 **scanId를 발급**하고, **스캔과 그 항목(원문 메뉴명·boundingBox·mock 판정 결과 포함)을 관계형 영속 저장소(MySQL/JPA)에 최소한으로 보존**해야 한다. 스키마는 Flyway 마이그레이션으로 관리한다. 별도 재열람 API는 이번 범위에 없으나 **저장 요구는 유지**하며, 저장 여부는 repository/service 테스트로 검증한다.
- **FR-006**: 응답은 **scanId**와 **항목별 결과 목록(results)**을 포함해야 하며, 각 결과는 **itemId·riskLevel·reason(mock 사유 문구)**을 가진다.
- **FR-007**: 시스템은 **boundingBox를 위험도 판정에 사용하지 않아야** 한다. 박스는 UI 오버레이/재현용 메타데이터로만 저장한다. 좌표 4개 값(x, y, width, height)은 **정규화 비율값(Double)** 이다 — 클라이언트가 OCR을 수행한 **기준 이미지** 대비 비율로, 좌상단 (0,0)·우하단 (1,1). 서버는 **유효성을 검증한다**: `x≥0, y≥0, width>0, height>0, x+width≤1, y+height≤1`. 클라이언트는 이 정규화 좌표를 실제 표시 이미지 크기에 곱해 버튼/오버레이를 배치한다(해상도 독립).
- **FR-007a**: 이미지 처리는 정규화 좌표 기준이 유지되도록 **aspect ratio를 보존**해야 한다(Lambda 압축 등). **crop/padding/rotation/orientation 보정처럼 좌표 기준을 바꾸는 처리는 이번 범위에서 수행하지 않는다.** 후속 도입 시 이미지 변환 메타데이터 또는 좌표 재계산 정책을 별도 정의한다.
- **FR-008**: 이번 범위에서 시스템은 **회원·알러지·인증·식이 제한 정보를 받지 않아야** 한다. 판정에 사용자 개인화가 들어가지 않는다.
- **FR-009**: 시스템은 잘못된 스캔 요청을 **HTTP 400**으로 거부하고 무엇이 잘못됐는지 식별 가능한 형태로 응답해야 한다. 거부 대상: 빈 항목 목록, 항목 수 100개 초과, itemId 누락, itemId 중복, rawMenuName 누락/blank, boundingBox 누락, boundingBox 좌표 검증 위반(`x<0`·`y<0`·`width≤0`·`height≤0`·`x+width>1`·`y+height>1`).
- **FR-009a**: 한 스캔 요청의 **최대 항목 수는 100개**다. 초과 시 거부한다(400).

#### 음식 상세 조회 (API 2)

- **FR-010**: 시스템은 **메뉴명 + 대상 언어(target language)를 입력받아 해당 음식의 상세 정보**를 **요청 언어로** 조회·반환할 수 있어야 한다. 응답은 **음식명**, **대표 이미지 참조**, **들어가는 재료 목록**을 포함한다. 메뉴명 매칭은 **trim 후 정확 일치**(매칭 키는 `ko` 원문 음식명)로 한다(정규화·별칭·유사도 매칭은 후속). 매칭 키와 응답 콘텐츠 언어는 분리된다.
- **FR-010a**: 지원 언어는 **한국어(`ko`) 원문 + 9개 대상 언어**(`zh-Hans`·`en`·`ja`·`zh-Hant`·`vi`·`id`·`th`·`ru`·`es`)다(헌법 V·ADR-0003). 음식명·재료명은 이들 언어로 사전 번역돼 저장된 값에서 요청 언어를 선택해 반환한다.
- **FR-010b**: 대상 언어는 **쿼리 파라미터(`lang`)로 받는다.** **미지정이거나 지원 목록에 없으면 `ko` 원문으로 폴백**해 반환한다(서버 오류 아님). (이 파라미터는 향후 회원 기반 언어 해석의 자리표시자 — 후속에 출처만 교체.)
- **FR-010c**: 재료 목록의 각 항목은 **재료명(요청 언어)·아이콘 참조·포함 비율(0~100% 연속값)·riskStatus(4단계 `RiskLevel`)**를 포함한다. 포함 비율은 음식 데이터로 **저장된 값**이며, 재료별 `riskStatus`는 **4단계 `RiskLevel`(SAFE/CAUTION/DANGER/UNKNOWN)** 값으로 이번 범위에서 **mock 값**으로 부여한다(실제로는 사용자 식이 제한 의존 = 후속 assessment). UI의 '안전/문의 필요' 2상태 표시는 클라이언트가 매핑한다.
- **FR-010d**: 시스템은 **사장님 안내 설명 문장의 완성본을 저장·전송하지 않는다.** 응답은 문장 조합에 필요한 **동적 값(음식명·재료명·포함%·riskStatus)** 만 구조화 형태로 제공하고, 고정 뼈대 문구는 **언어별 UI 템플릿(정적 리소스)** 으로 분리하며, 완성 문장은 **클라이언트가 런타임에 조합**한다.
- **FR-011**: 이번 범위에서 음식 상세는 **seed 데이터**에 기반하며(seed가 `ko` + 9개 언어 번역본을 직접 포함), **실제 번역 생성(LLM·`meogo-batch` 배치)·외부 데이터 수집은 수행하지 않는다**(후속).
- **FR-012**: 조회한 메뉴명이 데이터에 없으면 시스템은 **HTTP 400 + `BaseResponse.fail("해당 음식 정보 없음")`**으로 응답한다(미수록 메뉴 상세 요청을 잘못된 요청으로 취급 — 제품 정책). menuName 누락/blank는 **HTTP 400 + `BaseResponse.fail("menuName은 필수입니다")`**로 응답한다(메시지로 구분).

#### 경계 / 교체 용이성

- **FR-013**: mock 판정 로직은 이후 실제 판정 로직으로 **국소적으로 교체 가능**하도록, 스캔 흐름의 다른 부분(요청 수신·항목 저장·결과 응답)과 분리되어 있어야 한다.
- **FR-014**: 스캔 도메인(요청·항목·결과)과 음식 상세 도메인(음식 정보)은 **서로의 내부 구조에 직접 의존하지 않아야** 한다.

#### 공통 응답 형식

- **FR-015**: 모든 API 응답은 프로젝트 공통 응답 봉투 `BaseResponse<T>`(필드: `success`, `payload`, `message`)로 감싸 반환해야 한다. 성공은 `BaseResponse.ok(payload)`(`success=true`+`payload`), 실패는 `BaseResponse.fail(message)`(`success=false`+`message`). HTTP 상태코드는 `ResponseEntity`로 표현한다(성공 200, 잘못된 요청 400). (코드 규약은 CLAUDE.md "API 응답 규약" 참조.)

### Key Entities *(데이터 관련)*

- **MenuScan (스캔 요청)**: 한 번의 메뉴판 스캔 사건. 식별자(scanId), 제출된 항목들, 처리 상태/시각을 가진다. 이번 범위에서는 요청자(회원) 개념 없이 익명으로 둔다.
- **ScannedMenuItem (스캔 항목)**: 클라이언트가 보낸 개별 메뉴 항목. itemId(정수 인덱스), 원문 메뉴명, boundingBox(필수, **정규화 비율** x/y/width/height: Double). **수신 배열 순서**가 판정 순서이며, 서버는 이 순서를 저장/재현용으로 보존할 수 있다(별도 displayOrder 클라이언트 필드는 요구하지 않음).
- **MenuItemAssessment (항목 판정 결과, mock)**: 한 항목에 대한 위험도 결과. itemId 참조, riskLevel(4단계 중 하나), reason(mock 사유). 이번 범위에서는 mock 값.
- **RiskLevel (위험도 단계)**: `SAFE` / `CAUTION` / `DANGER` / `UNKNOWN` 4단계 고정 값.
- **FoodDetail (음식 상세)**: 메뉴명으로 조회되는 음식 정보. 음식명을 **`ko` 원문 + 9개 대상 언어 번역본**으로 보유하고, 대표 이미지 참조(언어 무관)와 재료 목록을 가진다. 조회 시 대상 언어 값을 반환(미지원 → `ko`). 이번 범위에서는 seed 데이터(번역본 포함).
- **Ingredient (재료)**: 재료명을 **`ko` 원문 + 9개 대상 언어 번역본**으로 보유하고, 표시용 아이콘 참조를 가진다. 여러 음식에서 공유된다(음식이 재료 전체를 소유하지 않음).
- **LanguageCode (지원 언어)**: `ko`(원문) + 9개 대상 언어(`zh-Hans`·`en`·`ja`·`zh-Hant`·`vi`·`id`·`th`·`ru`·`es`). 지원 목록 밖/미지정은 `ko`로 폴백.
- **FoodIngredient (음식–재료 관계)**: 특정 음식에 특정 재료가 들어가는 관계. **포함 비율(`inclusionPercent`, 0~100% 연속값)**을 저장한다 — 여러 레시피 기준 포함 확률이며 UI의 `~50%`·`~100%` 표시 원천. ※ `food.md`의 `0/1/2`는 동일 필드가 아니라 이 퍼센티지를 **산출하는 후속 LLM per-recipe 스코어링 입력값**(별개 개념, 이번 범위 밖).
- **재료 riskStatus (재료 위험 상태, mock)**: 재료별 위험도. **항목 판정과 동일한 4단계 `RiskLevel`(`SAFE`/`CAUTION`/`DANGER`/`UNKNOWN`)을 재사용**한다(재료 전용 별도 enum 없음). 본래 사용자 식이 제한 의존(assessment) 값이나 이번 범위에선 mock. UI의 '안전/문의 필요' 2상태 표시는 클라이언트가 매핑.

## API Contract *(이번 슬라이스 한정)*

> 모든 응답은 `BaseResponse<T>`로 감싼다. 경로·필드명은 plan에서 확정할 수 있으나 의미·검증 규칙은 본 계약을 따른다.

### API 1 — 메뉴 스캔 제출 + mock 판정

`POST /api/v1/menu-scans`

**Request body**:
- `items`: 필수, **1개 이상, 최대 100개**
  - `items[].itemId`: 필수, 정수, **요청 내 중복 불가**
  - `items[].rawMenuName`: 필수, **blank 불가**
  - `items[].boundingBox`: **필수** `{ x, y, width, height }` — 정규화 비율(Double, OCR 기준 이미지 대비). 검증: `x≥0, y≥0, width>0, height>0, x+width≤1, y+height≤1`

**Response (200)** — `BaseResponse.ok(...)`:
- `scanId`
- `results[]`
  - `itemId`
  - `riskLevel` (`SAFE`/`CAUTION`/`DANGER`/`UNKNOWN`)
  - `reason` (mock 사유 문구)

**Validation (모두 400, `BaseResponse.fail(...)`)**:
- `items` 빈 배열 → 400
- `items` 100개 초과 → 400
- itemId 누락 → 400
- itemId 중복 → 400
- rawMenuName 누락/blank → 400
- boundingBox 누락/잘못된 좌표 → 400

### API 2 — 음식 상세 조회

`GET /api/v1/foods/detail?menuName={menuName}&lang={lang}`

**Request**:
- `menuName`: 필수, blank 불가. 매칭: **trim 후** seed의 `ko` 원문 음식명과 **exact match**
- `lang`: 선택. 지원 = `ko`+9개(`zh-Hans`·`en`·`ja`·`zh-Hant`·`vi`·`id`·`th`·`ru`·`es`). **미지정/미지원 → `ko` 폴백**

**Response**:
- 존재 → **200** + `BaseResponse.ok(FoodDetail)` (음식명·재료명은 `lang` 언어, 미지원 시 `ko`)
  - `FoodDetail`: `name`(요청 언어), `imageRef`, `ingredients[]`
    - `ingredients[]`: `name`(요청 언어), `iconRef`, `inclusionPercent`(0~100), `riskStatus`(4단계 `RiskLevel`)
- 없음 → **400** + `BaseResponse.fail("해당 음식 정보 없음")`
- menuName 누락/blank → **400** + `BaseResponse.fail("menuName은 필수입니다")`

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 클라이언트가 N개 메뉴 항목을 한 번에 제출하면, **N개 모두에 대해 결과가 빠짐없이(누락 0건)** 반환되고, 각 결과는 4단계 위험도 중 하나를 가진다.
- **SC-002**: 동일 메뉴명이 중복된 요청에서도 **결과가 itemId 기준으로 100% 정확히 매칭**되어, 클라이언트가 각 항목 위에 올바른 위험도를 표시할 수 있다.
- **SC-003**: `items` 배열 순서를 기준으로 위험도가 `SAFE→CAUTION→DANGER→UNKNOWN` 순환 배정되므로, **항목이 4개 이상이면 응답이 4단계를 모두 포함**하여 프론트엔드가 네 가지 UI 상태를 한 번의 스캔으로 시연할 수 있다.
- **SC-004**: 사용자는 스캔 제출 후 **체감상 즉시(수 초 이내)** 결과 화면을 볼 수 있다.
- **SC-005**: 잘못된 스캔 요청(빈 목록·100개 초과·필수 필드 누락·itemId 중복·boundingBox 누락/좌표 오류)은 **100% HTTP 400으로 거부**되며, 무엇이 잘못됐는지 알 수 있다.
- **SC-006**: 유효한 스캔은 **scanId·항목·boundingBox·mock 판정 결과가 저장**되며, 이는 repository/service 테스트로 검증된다.
- **SC-007**: 시드 메뉴명을 지원 언어 중 어느 `lang`으로 조회해도 **200 + 해당 언어 음식명·재료 목록(재료명·포함%·riskStatus)**이 반환되고, 미지원/미지정 `lang`은 `ko` 폴백, 없는 메뉴명은 **400**, menuName 누락/blank는 **400**으로 일관 응답한다.
- **SC-008**: 음식 상세 응답만으로 클라이언트가 상세 화면(대표 이미지 + 재료별 이름·아이콘·포함%·안전/문의 상태)을 **추가 호출 없이** 구성할 수 있고, "문의 필요" 안내 문구도 **응답의 구조화 값 + 로컬 템플릿**으로 조합 가능하다(서버가 완성 문장을 저장/전송하지 않음).

## Assumptions

- **요청자 익명 처리**: 회원·인증이 이번 범위에서 제외되므로, 스캔 요청은 요청자(회원) 식별 없이 **완전 익명**으로 저장한다(스키마에 requester 컬럼 없음). 추후 **이상 사진 추적·이용 제한**을 위해 요청자를 기록해야 하는데, 이는 신뢰 가능한 신원(인증)이 전제이므로 **요청자 식별자 컬럼·연결은 auth/member 기능에서 일괄 추가**한다(나중에 nullable 컬럼 추가 마이그레이션은 trivial).
- **mock 순환 기준**: mock 위험도는 요청 `items` 배열의 0-based index 기준으로 `index % 4`에 따라 `SAFE/CAUTION/DANGER/UNKNOWN`을 순환 배정한다. 별도 displayOrder 필드는 요구하지 않는다.
- **boundingBox 필수 + 정규화 좌표**: 각 항목은 boundingBox를 반드시 포함한다. 좌표 4개 값(x, y, width, height)은 **클라이언트 OCR 기준 이미지 대비 정규화 비율(Double)** — 좌상단 (0,0)·우하단 (1,1). 판정엔 사용하지 않고 UI 오버레이/재현용으로만 저장하되 유효성(`x≥0, y≥0, width>0, height>0, x+width≤1, y+height≤1`)은 검증한다. 클라이언트는 표시 이미지 크기에 비율을 곱해 오버레이를 배치(해상도 독립).
- **이미지 변환 전제**: Lambda 등 이미지 압축은 **aspect ratio 보존**(정규화 좌표 유효성 유지). crop/padding/rotation/orientation 보정은 이번 범위에서 하지 않으며, 후속 도입 시 변환 메타데이터·좌표 재계산 정책을 별도 정의한다.
- **항목 수 상한**: 한 스캔당 항목 수 상한은 **100개**로 확정한다(초과 시 400).
- **음식 상세 데이터 출처**: API 2의 음식 상세는 미리 준비한 소수의 seed 데이터로 응답한다(실데이터 적재·LLM 생성은 후속).
- **음식 상세 언어**: FoodDetail 음식명·재료명은 `ko` 원문 + 9개 대상 언어로 사전 번역해 저장한다(헌법 V·ADR-0003). API 2는 **쿼리 파라미터 `lang`** 의 번역본을 반환하고, 미지정/미지원 언어는 `ko`로 폴백한다. 이번 슬라이스에선 **seed가 9개 번역을 직접 포함**한다(실제 번역 생성=배치는 후속). 매칭 키(메뉴명)는 `ko` 원문 기준.
- **대상 언어 출처(향후)**: 쿼리 `lang`은 이번 슬라이스의 언어 선택 수단이며, 향후 **회원 `MemberProfile.사용 언어`가 권위 출처**가 되고 헤더/파라미터는 폴백으로 강등된다(R7). 응답 계약은 그대로 두고 **언어 출처만 교체**된다.
- **저장 검증 방식**: 스캔 결과 재열람 API는 이번 범위에 없으나, 저장 요구는 유지한다. scanId 발급과 항목·boundingBox·mock 결과의 저장 여부는 repository/service 테스트로 검증한다.
- **OCR는 클라이언트 책임**: 서버는 OCR을 수행하지 않으며, 클라이언트가 추출한 메뉴명과 박스를 신뢰해 받는다.

## 비범위 (Out of Scope) — 후속 반복에서 추가

- 실제 위험도 판정 로직(사용자 식이 제한 × 음식 재료 비교, assessment 정책 도메인)
- 실제 음식 데이터 생성·번역 파이프라인(LLM 호출·종합·9개국어 번역, `meogo-batch` 배치, food 캐시 미스 생성) — 이번엔 seed가 번역본 직접 보유
- **스캔 미수록 메뉴 → `UNKNOWN` 응답**(메뉴명 DB 조회 기반 real 동작) 및 **research 미스 메뉴 대기열 적재**(메뉴명 정규화 dedup, 배치 트리거) — 다음 사이클(ADR-0003/0004). 이번 슬라이스의 US1은 mock 순환을 유지하고, US2는 미수록 메뉴를 400으로 응답하며 대기열을 두지 않는다.
- 회원 기반 언어 해석(`MemberProfile.사용 언어`) — 이번엔 쿼리 `lang` 파라미터로 대체
- 회원·인증·이메일 인증·식이 제한 프로필(member 도메인)
- 스캔 결과 재열람/히스토리 조회 API
- 사장님용 한국어 질문 생성, 매운맛·관심음식 등 보조 개인화
