# Feature Specification: API 요청 흐름 로깅 (API 모니터링)

**Feature Branch**: `kb-130-api-request-logging`

**Created**: 2026-07-14

**Status**: Draft

**Input**: User description: "kb-130 API 모니터링을 위해 로그 코드를 심을거야. 어떤 회원이 요청을 했고 그 요청이 처리되고 응답으로 나가는 과정 까지의 흐름을 로그로 관리할것임. 요청에 대해 랜덤한 키 값을 부여해서 나중에 로그를 필터링할 수 있어야 해. MDC가 고려될 상황이 있는지 검토가 필요하기도 함."

## Clarifications

### Session 2026-07-14

- Q: '요청이 처리되는 과정'의 로그 범위는 어디까지인가? → A: 진입/응답 요약 로그 + 에러 상세 표준화. 계층별(컨트롤러·서비스·리포지토리) 진입/종료 로그는 범위 밖. 예외 발생 시 예외 타입·애플리케이션 에러 코드·HTTP 상태·요청 URI 를 표준 형식으로 기록. 외부 API 호출 등 운영상 추적이 필요한 주요 지점에만 별도 로그를 선별 추가.
- Q: 로그 출력 형식은? → A: 환경별 이원화 — local/dev 는 사람이 읽는 텍스트 한 줄(tail/grep 용), staging/prod 는 JSON 구조화 로그(수집기에서 상관 키·회원 식별자·상태·소요 시간 필드 단위 검색).
- Q: 진입 로그에 쿼리 파라미터를 포함하는가? → A: 포함하되 민감 파라미터명 목록 기반 값 마스킹. 목록에 오른 파라미터는 값을 마스킹해 기록하고 나머지는 원문 기록(현재 민감 쿼리 파라미터는 없어 목록은 비어 있는 상태로 시작).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 요청 단위 상관 키로 로그 필터링 (Priority: P1)

운영자(개발자)가 특정 API 호출에 문제가 생겼을 때, 그 요청에 부여된 고유 키 하나로 로그를 필터링하면 해당 요청의 수신부터 응답까지 전 과정에서 남은 모든 로그를 시간순으로 볼 수 있다. 키는 요청마다 서버가 무작위로 새로 부여하며, 동시에 들어온 다른 요청의 로그와 절대 섞이지 않는다.

**Why this priority**: 상관 키가 없으면 동시 트래픽에서 한 요청의 흐름을 재구성할 수 없다 — 이 기능의 존재 이유이자 나머지 스토리의 전제.

**Independent Test**: API 하나를 호출한 뒤 응답(또는 로그)에서 확인한 키로 로그를 검색하면 그 요청의 로그만 전부 조회되는지 확인.

**Acceptance Scenarios**:

1. **Given** 서비스가 기동된 상태, **When** 임의의 비즈니스 API 를 호출하면, **Then** 그 요청 처리 중 남는 모든 로그 라인에 동일한 상관 키가 포함된다.
2. **Given** 서로 다른 두 요청이 동시에 처리 중일 때, **When** 각 요청의 로그를 상관 키로 필터링하면, **Then** 두 요청의 로그가 서로 섞이지 않고 각자의 키로만 조회된다.
3. **Given** 요청 처리 중 예외가 발생한 경우, **When** 에러 로그를 확인하면, **Then** 에러 로그에도 동일한 상관 키가 붙어 있어 어느 요청에서 난 에러인지 즉시 식별된다.

---

### User Story 2 - 요청자(회원) 식별 (Priority: P2)

운영자가 로그만 보고 "어떤 회원이 이 요청을 보냈는지"를 알 수 있다. 인증된 요청의 로그에는 회원 식별자가 함께 남고, 특정 회원의 식별자로 필터링하면 그 회원이 남긴 요청 이력을 추적할 수 있다.

**Why this priority**: 문의·장애 대응 시 "그 회원의 그 요청"을 찾는 것이 모니터링의 핵심 시나리오. 상관 키(P1) 위에 얹는 두 번째 필터 축.

**Independent Test**: 로그인한 회원으로 API 를 호출한 뒤 로그에서 회원 식별자를 확인하고, 그 식별자로 필터링해 해당 회원의 요청만 조회되는지 확인.

**Acceptance Scenarios**:

1. **Given** 인증된 회원의 요청, **When** 요청이 처리되면, **Then** 그 요청의 흐름 로그에 회원 식별자가 포함된다.
2. **Given** 인증이 필요 없는(비로그인) 요청, **When** 요청이 처리되면, **Then** 회원 식별자 없이(익명 표기) 상관 키만으로 로그가 남고 처리에 오류가 없다.

---

### User Story 3 - 요청 수신·응답 요약 로그 (Priority: P3)

운영자가 로그 스트림만 훑어도 "어떤 요청이 들어와서(메서드·경로) 어떤 결과로(상태) 얼마 만에(소요 시간) 나갔는지"를 요청당 정해진 형태의 진입/응답 로그로 파악할 수 있다.

**Why this priority**: 상관 키·회원 식별이 갖춰진 뒤 흐름의 시작점과 끝점을 표준화하는 마감 작업. 이것까지 있어야 "요청→처리→응답" 흐름이 로그로 완결된다.

**Independent Test**: API 를 호출하고 로그에서 진입 로그(메서드·경로)와 응답 로그(상태·소요 시간)가 같은 상관 키로 한 쌍 남는지 확인.

**Acceptance Scenarios**:

1. **Given** 정상 처리되는 요청, **When** 응답이 나가면, **Then** 요청 메서드·경로가 담긴 진입 로그와 응답 상태·소요 시간이 담긴 응답 로그가 같은 상관 키로 남는다.
2. **Given** 처리 중 예외로 에러 응답이 나가는 요청, **When** 응답이 나가면, **Then** 에러 응답이라도 응답 로그(상태·소요 시간)가 누락 없이 남는다.

---

### Edge Cases

- 인증 정보가 없거나 유효하지 않은 요청 → 회원 식별자 없이 상관 키만으로 로그가 남아야 하며 로깅이 요청 처리를 방해하지 않는다.
- 요청 처리 중 예외가 발생해 공통 에러 응답으로 전환되는 경우 → 진입·에러·응답 로그가 모두 같은 상관 키를 유지한다.
- 헬스체크·API 문서 등 프레임워크 경로로 들어오는 요청 → 비즈니스 API 모니터링 대상에서 제외해 로그 노이즈를 만들지 않는다.
- 로깅 자체가 실패하는 경우(예: 예상 못 한 값) → 로깅 실패가 요청 처리 실패로 번지지 않는다.
- 하나의 요청 처리가 끝난 뒤 같은 실행 자원이 다음 요청에 재사용되는 경우 → 이전 요청의 키·회원 식별자가 다음 요청 로그에 오염되지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 비즈니스 API 요청마다 전역적으로 유일한 무작위 상관 키를 부여해야 한다.
- **FR-002**: 하나의 요청을 처리하는 동안 남는 모든 로그(진입·처리·에러·응답)에는 그 요청의 상관 키가 자동으로 포함되어야 한다 — 각 로그 지점이 키를 수동으로 전달하지 않아도 된다.
- **FR-003**: 인증된 요청의 로그에는 요청 회원의 식별자가 포함되어야 하며, 미인증 요청은 회원 식별자 없이 처리된다.
- **FR-004**: 시스템은 요청 수신 시 메서드·경로가 담긴 진입 로그를, 응답 시 응답 상태·소요 시간이 담긴 응답 로그를 남겨야 한다. 에러 응답도 예외 없이 응답 로그를 남긴다.
- **FR-005**: 상관 키와 회원 식별자는 각각 독립적인 필터 축으로 로그에서 검색 가능해야 한다. 로그 출력 형식은 환경별 이원화 — local/dev 는 사람이 읽는 텍스트 한 줄, staging/prod 는 필드 단위 검색이 가능한 JSON 구조화 로그.
- **FR-006**: 요청 처리가 끝나면 그 요청의 상관 컨텍스트(키·회원 식별자)는 정리되어 이후 요청의 로그를 오염시키지 않아야 한다.
- **FR-007**: 모니터링 대상은 비즈니스 API(`/api/v*`) 로 한정하며 헬스체크·API 문서 등 프레임워크 경로는 제외한다.
- **FR-008**: 로그에는 인증 토큰·요청/응답 본문 등 민감할 수 있는 데이터를 기록하지 않는다 — 요청 메타데이터(키·회원 식별자·메서드·경로·상태·소요 시간)만 기록한다. 요청 경로에는 쿼리 파라미터를 포함하되, 민감 파라미터명 목록에 오른 값은 마스킹한다(목록은 현재 비어 있으며 민감 파라미터 도입 시 등록).
- **FR-009**: 로깅 실패는 요청 처리 결과에 영향을 주지 않아야 한다.
- **FR-010**: 요청 처리 중 예외가 발생하면 예외 타입·애플리케이션 에러 코드(`ErrorCode`)·HTTP 상태·요청 URI 가 담긴 표준 형식의 에러 상세 로그를 남겨야 한다.
- **FR-011**: 계층별(컨트롤러·서비스·리포지토리) 진입/종료 로그는 심지 않는다. 외부 시스템 호출 등 운영상 추적이 필요한 주요 지점에만 로그를 선별 추가하며, 그 로그에도 상관 키가 자동 포함된다.

### Key Entities

- **요청 흐름 로그(로그 레코드)**: 저장소 엔티티가 아닌 로그 스트림상의 레코드. 속성 — 상관 키(요청당 유일), 회원 식별자(인증 시), 요청 메서드·경로, 응답 상태, 소요 시간, 시각.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 임의의 API 요청 1건에 대해 상관 키 하나로 필터링하면 그 요청의 수신~응답 로그가 100% 조회되고 다른 요청의 로그는 0건 섞인다.
- **SC-002**: 동시에 처리되는 요청들이 서로 다른 상관 키를 부여받는다 — 키 충돌·컨텍스트 오염 0건.
- **SC-003**: 인증된 요청의 흐름 로그에서 요청 회원을 100% 식별할 수 있다.
- **SC-004**: 에러 응답을 포함한 모든 비즈니스 API 응답이 상태·소요 시간 응답 로그를 남긴다(누락 0건).
- **SC-005**: 로깅 도입 전후 API 응답 시간에 사용자가 체감할 수 있는 차이가 없다.

## Assumptions

- 상관 키는 서버가 생성한다 — 클라이언트(모바일 앱)가 자체 요청 ID 를 전달·전파하는 분산 추적은 이번 범위 밖(서버 단일 서비스). 필요해지면 클라이언트 헤더 수용을 후속으로 추가한다.
- 요청/응답 본문 로깅은 하지 않는다(개인정보·민감정보 리스크, 로그 볼륨). 메타데이터 로깅으로 모니터링 목적을 충족한다.
- 로그 저장·조회는 기존 로그 파이프라인(콘솔/파일 + 운영 환경 수집기)을 그대로 사용한다 — 별도 로그 저장소·대시보드 구축은 범위 밖.
- 대상은 web 앱(`:app:api`)의 비즈니스 API 로 한정한다. 배치(`:app:batch`)의 잡 로깅은 이번 범위 밖.
- 상관 키를 응답 헤더로 클라이언트에 돌려주는 것은 기본 포함으로 가정한다(문의 대응 시 클라이언트가 키를 제시할 수 있게) — 구현 부담이 거의 없고 가치가 큼.
- 상관 컨텍스트 전파 방식(MDC 등)은 구현 결정으로 `/speckit-plan` 단계에서 확정한다.
