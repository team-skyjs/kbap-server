# Feature Specification: 기피성분 81종 포함 신뢰도 LLM 스코어링 (3모델 병렬 → Consensus Ensemble 집계)

**Feature Branch**: `kb-53-llm-avoidance-scoring`

**Created**: 2026-07-06

**Status**: Draft

**Input**: User description: "jira kb-53 llm모듈에 만들어둔 스케폴딩의 세부 구현을 시작할 차례야. llm에게 프롬프트를 어떻게 전달할지, 응답은 어떻게 받을 것인지 구체적인 구현을 고민하고 개발한다."

## 개요

KB-49 에서 세운 `:infra:llm` 토대는 **원시 문자열 in / 원시 문자열 out** 이다 — 3개 모델로 병렬 fan-out 하고 개별 실패를 격리하지만, "무엇을 물어보는지"(프롬프트)와 "응답을 어떻게 구조화해 받는지"(파싱)는 비어 있다. 이 기능은 그 스캐폴딩을 **실제 스코어링 계약**으로 채운다.

**조사 대기열**(DB 에 없거나 재조사 대상인 음식)에서 음식을 **10개씩 청크**로 묶어, 각 청크를 3개 LLM 모델에 **동시(병렬)** 호출한다. 프롬프트는 청크의 음식들과 기피성분 81종 후보를 함께 제시하고, 모델은 **대표 레시피 기준 포함된다고 판단한 성분만** 골라 `score`(0/1/2)·`probability`(1~100)를 붙여 응답한다(응답에 없는 성분 = 미포함). 3개 모델 응답은 **Consensus Ensemble 공식**으로 성분별 하나의 최종 **포함 신뢰도(`inclusionConfidence`, 정수 1~100)** 로 종합된다. **3개 모델 결과가 모두 취합돼야 최종 결과로 확정**하며, 일부 모델(API 다운 등)이 실패하면 그 실패를 **별도 로깅**하고 해당 청크는 확정하지 않는다(재조사 대상으로 남김).

또한 같은 호출에서 **음식명(한국어 원문)의 9개 언어 번역**과 **음식 설명**(한국어 생성문 + 9개 언어 번역, **공백 포함 200자 목표·최대 230자**)을 함께 JSON 으로 받는다 — 기존 `food.name_translations`·`food.description`/`description_translations` 칼럼(KB-48)·`LocalizedText` 와 **동형**. 번역·설명 텍스트는 수치가 아니라 앙상블 대상이 아니며, 우선순위상 한 모델의 결과를 채택한다(선정 규칙 하단). 이 결과도 저장 직전 산출물로 반환하며 저장은 KB-54 다.

이 값은 "LLM 3개 결과를 종합판단한 신뢰도"이며, 이후(KB-54) `food ↔ avoidance` 매핑 데이터로 저장될 값이다. **위험도(SAFE/CAUTION/DANGER) 판정은 KB-53 의 책임이 아니다** — 저장된 신뢰도를 소비하는 KB-9 위험도 정책(`RiskLevel.fromInclusionProbability`)의 별개 몫이다. KB-53 은 KB-9 이 그대로 받을 수 있는 값(정수 1~100)을 산출하는 데까지만 책임진다.

## Clarifications

### Session 2026-07-06

- Q: 위험도 판정(SAFE/CAUTION/DANGER)을 KB-53 에서 수행하나? → A: 아니오. KB-53 은 Consensus Ensemble 로 **신뢰도 값만 산출**한다. 위험도 판정은 KB-9 `fromInclusionProbability`(임계 10/60)의 **별개 책임**이며, 참고 문서 §6 자체 판정표(70/40 + avg_score 게이트)는 **채택하지 않는다**.
- Q: 산출값을 DB(food·avoidance 매핑 테이블)에 저장하는 것까지 이번 범위인가? → A: 아니오. 영속(스키마·적재)은 **KB-54(T5)** 로 유지한다. KB-53 은 저장 직전의 **산출 결과(집계된 신뢰도)** 까지 책임진다.
- Q: 최종 산출값의 이름과 범위는? → A: 이름은 **`inclusionConfidence`**("포함 가능성 신뢰도" — LLM 추정값이지 통계적 확률이 아님), 범위는 **정수 1~100**. 각 모델의 `probability` 는 **프롬프트로 1~100 을 강제**하고, 집계 결과도 **1~100 으로 clamp**(공식상 0 산출 시 하한 1)해 KB-9 입력과 값범위·의미를 호환시킨다.
- Q: 프롬프트/응답 형태는? → A: 프롬프트에 기피성분 **81종 전부를 후보로 제시**하되, 모델은 **포함된다고 판단한 성분만** `score`·`probability` 로 응답한다. 응답에 없는 성분은 **미포함**(= 사실상 SAFE)으로 해석한다 — 따라서 "81종보다 적은 응답"은 오류가 아니라 정상이다.
- Q: 청크 단위와 처리 흐름은? → A: 조사 대기열에서 **음식 10개 단위로 청크**를 만들어 청크 1개를 3개 모델에 1회씩(모델당 1회) 병렬 호출한다.
- Q: 3개 모델 결과 종합 공식은? → A: 참고 문서(`llm_consensus_ensemble_review.md`) §4 **Consensus Ensemble**: `base_confidence = α·(avg_score/2) + (1-α)·(avg_probability/100)` (α=0.6), `final = base_confidence · agreement_factor`(3개 동일=1.0 / 2개 동일=0.9 / 모두 상이=0.75), `inclusionConfidence = round(final·100)`.
- Q: 성분 스코어링 외에 음식명 번역도 받나? → A: 예. **같은 LLM 호출에서 음식명(한국어 원문)의 대상 9개 언어 번역**을 JSON 으로 함께 받는다 — 기존 `food.name_translations` 칼럼·`LocalizedText.translations` 와 동형(`{lang_code: 번역명}`, `ko` 키 없음, 대상 언어 = 헌법 V 9종 `zh-Hans·en·ja·zh-Hant·vi·id·th·ru·es`). 번역은 앙상블 대상이 아니며 **우선순위상 한 모델의 번역을 채택**. 저장은 KB-54.
- Q: 부분 실패 시 최종 확정? → A: **3개 모델 결과가 모두 취합돼야 최종 결과로 확정**한다(변경 — 기존 "≥1 성공이면 완결" 및 KB-53 Jira DoD 의 "일부 실패해도 남은 결과로 완결" 을 **대체**). 일부 모델(API 다운·예외·파싱 불가)이 실패하면 **그 실패를 별도 로깅**하고 해당 청크는 확정하지 않는다(재조사로 남김). ⚠️ Jira DoD 갱신 필요.
- Q: 음식 설명도? → A: 예. **음식 설명(한국어 생성문 + 9개 언어 번역)** 도 산출·저장 대상이며 **공백 포함 200자 이내**여야 한다(기존 "description 범위 밖" 정정). 음식명과 달리 설명은 **한국어 원문도 LLM 이 생성**한다(대기열 음식엔 설명이 없을 수 있음). `food.description`·`food.description_translations`·`LocalizedText` 와 동형.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 음식 청크를 81종 후보에 대해 단일 모델로 구조화 스코어링 (Priority: P1)

음식 10개(청크)와 기피성분 81종 후보를 입력하면, 시스템은 이를 하나의 프롬프트로 구성해 한 개 LLM 모델에 전달하고, 모델이 **포함된다고 판단한 (음식, 성분) 조합만** `score`(0/1/2)·`probability`(1~100)로, **음식별로 9개 언어 이름 번역과 설명(한국어 + 9개 언어 번역, 공백 포함 200자 목표·최대 230자)** 을 응답하도록 지시한다. 시스템은 그 응답을 (음식 → 성분 → {score, probability}) + (음식 → 이름 번역·설명) 구조로 파싱한다.

**Why this priority**: 이 기능의 핵심(사용자가 명시한 "프롬프트를 어떻게 전달할지, 응답을 어떻게 받을지")이다. 단일 모델만으로도 청크에 대한 구조화된 성분 판단을 산출하므로 그 자체로 가치 있는 MVP 슬라이스다. 병렬·집계·배치는 모두 이 계약 위에 얹힌다.

**Independent Test**: 대표 음식 청크에 대해 페이크/스텁 모델 응답을 넣고, 파서가 (포함으로 응답된) 조합을 유효 범위로 파싱하며, 응답에 없는 성분을 미포함으로 처리하고, 범위이탈·형식오류·미지 코드 응답을 규칙대로 처리하는지 검증한다(실 네트워크 불요).

**Acceptance Scenarios**:

1. **Given** 음식 10개 청크와 81종 후보가 주어지고, **When** 시스템이 프롬프트를 구성하면, **Then** 프롬프트는 대상 음식 목록·81종 후보 성분(식별 가능하게)·기대 응답 형식(포함된 것만, score/probability, probability 1~100 강제)을 포함한다.
2. **Given** 모델이 일부 (음식, 성분) 조합만 포함으로 응답하고, **When** 응답을 파싱하면, **Then** 응답된 조합은 각각 score(0/1/2)·probability(1~100)로 구조화되고, 응답에 없는 성분은 미포함으로 처리된다.
3. **Given** 모델이 범위를 벗어난 probability·형식 오류·미지 성분코드를 반환하고, **When** 파싱하면, **Then** 정의된 규칙(부분 채택 또는 해당 모델 실패 처리)이 일관되게 적용된다.

### User Story 2 - 3모델 병렬 스코어링 + Consensus Ensemble 최종 신뢰도 (Priority: P2)

같은 청크를 3개 모델에 **동시(병렬)로** 채점시키고, **3개 모델 응답이 모두 취합됐을 때만** (음식, 성분) 조합별로 `score`·`probability` 를 **Consensus Ensemble 공식**으로 하나의 최종 `inclusionConfidence`(정수 1~100)로 종합해 **확정**한다. 일부 모델이 실패하면 그 실패를 **별도 로깅**하고 해당 청크는 확정하지 않는다.

**Why this priority**: "믿고 저장·판단"할 최종 신뢰도를 만드는 단계다. US1(단일 모델 계약) 위에서 3개 모델을 모두 취합해 편차를 줄이고 모델 간 일치도(agreement)를 반영한다. 안전 직결 데이터라 **부분 결과는 신뢰하지 않는다**(3개 모두 필요).

**Independent Test**: 3개 페이크 모델에 서로 다른 score/probability(일치·불일치·이상치 포함)를 주고, 집계가 문서 §4 공식대로 조합별 단일 `inclusionConfidence`(1~100)를 내는지, agreement_factor 가 일치 수준에 따라 적용되는지, **일부 모델 실패 시 확정하지 않고 실패가 로깅되는지** 검증한다.

**Acceptance Scenarios**:

1. **Given** 3개 모델이 (음식, 성분)에 대해 score/probability 를 반환하고, **When** 집계하면, **Then** `base_confidence = 0.6·(avg_score/2) + 0.4·(avg_probability/100)`, `final = base_confidence · agreement_factor`, `inclusionConfidence = round(final·100)` 이 문서 예시(`비빔밥-계란` → 74)와 일치하게 산출된다.
2. **Given** score 가 3개 동일/2개 동일/모두 상이한 각 경우, **When** 집계하면, **Then** agreement_factor 가 각각 1.0 / 0.9 / 0.75 로 반영된다.
3. **Given** 3개 중 1개 이상 모델이 실패(예외·타임아웃·무응답·파싱 불가)하고, **When** 잡이 처리하면, **Then** 해당 청크는 **확정되지 않고**(부분 집계 금지) 실패한 모델별로 **별도 로깅**(modelId + 사유)되며 음식은 미확정(재조사)으로 남는다.
4. **Given** 3개 모델이 모두 성공·취합되고, **When** 확정하면, **Then** (음식, 성분)별 `inclusionConfidence` 와 음식별 번역·설명이 함께 산출돼 하류(KB-54)로 넘어간다.

### User Story 3 - 배치 잡으로 조사 대기열을 청크 단위 종단 스코어링 (Priority: P3)

`:app:batch` 스코어링 잡이 **조사 대기열**의 음식을 10개 청크로 끊어 종단(end-to-end)으로 채점한다 — avoidance 카탈로그 81종을 **단일 출처**로 프롬프트를 구성하고, 3모델 병렬 → Consensus Ensemble 집계까지 수행해, 하류(KB-54 영속)가 받을 수 있는 **(음식, 성분)별 최종 신뢰도** 결과를 산출한다. 저장은 이 범위 밖이다.

**Why this priority**: 운영상 구동 경로(잡 배선)다. 스코어링 계약(US1)과 집계(US2)가 완성된 뒤 이를 배치에서 호출해 대기열 데이터에 적용한다. 잡은 결과 산출까지만 책임진다(영속은 KB-54).

**Independent Test**: 배치 잡을 대표 대기열(10개 이상)에 대해 (페이크 모델 caller 로) 실행해, 10개 청크로 분할·처리되고 카탈로그 81종을 출처로 (음식, 성분)별 최종 신뢰도 결과가 산출·반환되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 조사 대기열에 음식 N개와 avoidance 카탈로그(81종)가 있고, **When** 스코어링 잡을 실행하면, **Then** 잡은 대기열을 10개 청크로 나눠 각 청크를 종단 스코어링하고 (음식, 성분)별 최종 신뢰도를 산출한다.
2. **Given** 카탈로그가 향후 81종에서 늘거나 줄고, **When** 잡을 실행하면, **Then** 프롬프트·파싱·집계 대상 후보 성분 집합은 카탈로그를 따라가며 고정 개수(81)에 하드코딩되지 않는다.

### Edge Cases

- **정상: 부분 응답** — 모델이 81종 중 일부만 "포함"으로 응답하는 것은 정상이며, 응답에 없는 성분은 미포함(SAFE 등가)으로 처리한다(오류 아님).
- 모델이 **카탈로그에 없는 성분코드·중복 성분·청크에 없는 음식**을 응답에 포함하는 경우 → 그 항목을 무시할지 해당 모델 실패로 볼지의 처리 규칙.
- 모델이 **범위 이탈**(probability < 1, > 100, 비수치)이나 **형식 오류**(구조가 깨진 텍스트) 응답을 반환하는 경우.
- 모델이 **빈 문자열/무응답**을 반환하는 경우(스캐폴딩은 빈 content 를 반환할 수 있음) → 해당 모델 실패로 격리 → 청크 미확정 + 로깅.
- **3개 중 일부(1~2개) 모델만 성공** — 부분 집계 금지, 청크 미확정, 실패 모델별 별도 로깅(재조사로 남김).
- 개별 모델 **타임아웃/예외/API 다운**(KB-49 fan-out 이 이미 격리) → 실패로 간주, 청크 미확정 + 로깅.
- **집계 결과가 0 으로 라운딩**되는 극단 경우(예: score·probability 가 모두 하한) → 최종 `inclusionConfidence` 를 하한 1 로 clamp(KB-9 계약 1~100 보장).
- score 는 있는데 3개 모델이 크게 불일치할 때 agreement_factor(0.75)가 신뢰도를 낮추는지.
- **청크 크기 미달/초과** — 대기열 잔여가 10개 미만인 마지막 청크, 대기열이 비어 있는 경우.
- **번역 누락/미지 언어코드** — 채택 모델이 일부 언어를 빠뜨리거나(→ 키 생략, ko 폴백) 지원 목록 밖 언어코드·빈 문자열을 반환(→ 무시)하는 경우.
- **번역·설명만 실패/스코어링만 성공(또는 반대)** — 한 응답에서 성분은 유효한데 번역·설명 JSON 이 깨진 경우의 부분 처리(텍스트 산출물은 빈 값, 성분은 유지 — 단 청크 확정은 3개 모델 성공 기준).
- **설명 길이 초과/한국어 생성 실패** — 설명이 공백 포함 230자(하드캡)를 넘거나(→ 앞 230자 잘라내기) 한국어 설명을 못 만든 경우의 처리.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 조사 대기열의 음식을 **10개 단위 청크**로 묶어야 한다. 마지막 청크는 10개 미만일 수 있고, 대기열이 비면 호출하지 않는다.
- **FR-002**: 시스템은 (음식 청크 + 기피성분 81종 후보)를 담은 **스코어링 프롬프트**를 구성해야 한다. 프롬프트는 대상 음식 목록, 81종 후보(식별 가능하게), 기대 응답 형식을 명시하고, **모델이 포함된다고 판단한 (음식, 성분)만** `score`(0/1/2)·`probability`(정수 1~100)로 응답하도록 지시한다(probability 범위는 프롬프트로 강제).
- **FR-003**: 시스템은 모델 응답을 **(음식 → 성분 → {score, probability})** 구조로 파싱해야 한다. **응답에 없는 (음식, 성분)은 미포함**으로 해석한다.
- **FR-004**: 시스템은 같은 청크를 **3개 모델에 동시(병렬) 호출**해야 하며(모델당 1회 호출), 총 소요는 순차 합이 아니라 가장 느린 단일 모델에 수렴해야 한다(KB-49 fan-out 재사용).
- **FR-005**: 시스템은 (음식, 성분) 조합별로 다수 모델의 `score`·`probability` 를 **Consensus Ensemble 공식**으로 하나의 최종 `inclusionConfidence` 로 종합해야 한다: `base_confidence = 0.6·(mean(score)/2) + 0.4·(mean(probability)/100)`; `agreement_factor` = 3개 동일 1.0 / 2개 동일 0.9 / 모두 상이 0.75; `final = base_confidence · agreement_factor`; `inclusionConfidence = round(final·100)`. 규칙은 결정적이고 문서화된다.
- **FR-006**: 최종 `inclusionConfidence` 는 **정수 1~100** 이어야 한다. 공식 결과가 0 이하로 라운딩되면 **하한 1 로 clamp** 해, KB-9 `fromInclusionProbability` 입력과 값범위·의미가 호환되게 한다.
- **FR-007**: 시스템은 **3개 모델 결과가 모두 취합됐을 때만** 해당 청크를 최종 확정(집계)해야 한다. **부분 집계(1~2개 결과)로 확정하지 않는다** — 안전 직결 데이터라 3개 모두 필요(기존 "≥1 성공 완결" 및 Jira DoD 부분완결을 대체).
- **FR-008**: 개별 모델 실패(예외·타임아웃·API 다운·무응답·파싱 불가)는 격리되고, **실패한 모델별로 별도 로깅**(modelId + 사유)돼야 한다. 하나라도 실패하면 그 청크는 **미확정**으로 남겨(잘못된/부분 값이 하류로 유입되지 않게) 재조사 대상으로 둔다.
- **FR-009**: 시스템은 응답이 **미지 성분코드·청크 외 음식·중복·범위 이탈·형식 오류**인 경우의 처리 규칙(부분 채택 또는 해당 모델 실패 처리)을 정의하고 일관되게 적용해야 한다.
- **FR-010**: 후보 성분 집합은 **avoidance 카탈로그(`AvoidanceSubstanceCode`)를 단일 출처**로 참조해야 하며, 카탈로그의 증감에 따라 후보가 따라가야 한다(고정 개수 81 하드코딩 금지).
- **FR-011**: 스코어링은 **`:app:batch` 잡**으로 구동 가능해야 하며, 조사 대기열을 10개 청크로 종단(프롬프트 → 병렬 호출 → 파싱 → 집계) 처리해 (음식, 성분)별 최종 신뢰도 결과를 산출해야 한다.
- **FR-012**: KB-53 은 산출까지만 책임진다 — **위험도 판정(SAFE/CAUTION/DANGER)과 DB 영속은 범위 밖**이다(각각 KB-9 정책 / KB-54 영속의 몫). 산출 결과는 저장 직전의 결과 표현으로 반환한다.
- **FR-013**: LLM 호출 계약(프롬프트 구성·응답 파싱·집계)은 실 네트워크 없이 **페이크 단일모델 seam(`LlmModelCaller`)** 으로 단위 검증 가능해야 한다(헌법 원칙 I, Test-First).
- **FR-014**: 프롬프트는 성분 스코어링과 **함께 음식명(한국어 원문)의 대상 9개 언어 번역**(헌법 V — `zh-Hans·en·ja·zh-Hant·vi·id·th·ru·es`)을 요청해야 하며, 응답은 음식별 `{lang_code: 번역명}` JSON(`ko` 키 없음, 빈/미제공 언어는 키 생략)으로 파싱돼야 한다 — 기존 `food.name_translations`·`LocalizedText.translations` 와 동형.
- **FR-015**: 텍스트 산출물(음식명 번역·음식 설명)은 앙상블(수치 종합) 대상이 **아니다**. 3개 모델 중 **우선순위에 따라 한 모델의 텍스트를 채택**한다(선정 규칙은 결정적). 채택 모델이 특정 언어를 빠뜨리면 그 언어 키는 생략(조회 시 ko 폴백 — 헌법 V).
- **FR-016**: 시스템은 프롬프트에서 **음식 설명**을 함께 요청해야 한다 — 음식별 **한국어 설명(LLM 생성) + 9개 언어 번역**, 각 **공백 포함 200자를 목표**로 한다. 응답은 `food.description`(ko)·`food.description_translations`·`LocalizedText`(korean + translations) 와 동형으로 파싱된다. **200~230자는 여유로 허용**하고, **230자를 초과하면 앞 230자로 잘라낸다**(공백 포함, 하드캡 230).
- **FR-017**: 개별 모델 실패 로깅(FR-008)은 **어느 모델이 왜 실패했는지**(modelId + 사유) 운영이 식별 가능하게 남겨야 한다(KB-49 `LlmModelFailure` 재사용).

### Key Entities *(include if feature involves data)*

- **조사 대기열 항목(Queue item)**: 스코어링이 필요한 음식(식별/명칭) — DB 미존재 또는 재조사 대상.
- **음식 청크(Food chunk)**: 대기열에서 10개 단위로 묶인 음식 목록 — 1회 LLM 호출 단위.
- **후보 성분(Candidate substance)**: avoidance 카탈로그의 기피성분(81종 코드) — 프롬프트에 후보로 제시.
- **단일 모델 판단(Per-model judgement)**: 한 모델이 포함으로 응답한 (음식, 성분)별 `{score(0/1/2), probability(1~100)}` (모델 식별 포함). 응답에 없는 조합 = 미포함.
- **최종 집계 결과(Aggregated result)**: (음식, 성분)별 최종 `inclusionConfidence`(정수 1~100) — 하류(KB-54 영속 → KB-9 위험도)가 소비할 신뢰값. 참고용 avg_score·avg_probability·agreement_factor 도 함께 노출 가능.
- **음식명 번역(Food name translations)**: 음식별 `Map<LanguageCode, String>`(대상 9개 언어, `ko` 제외) — `LocalizedText.translations`·`food.name_translations` 와 동형. 앙상블 아님(우선순위 단일 모델 채택). 하류 KB-54 가 `food.name_translations` 로 저장.
- **음식 설명(Food description)**: 음식별 `LocalizedText`(한국어 생성문 + 9개 언어 번역), 각 **공백 포함 200자 목표·최대 230자** — `food.description`·`food.description_translations` 와 동형. 앙상블 아님(우선순위 단일 모델 채택). 하류 KB-54 저장.
- **모델 실패(Model failure)**: 격리된 개별 모델의 실패(모델 식별 + 사유) — KB-49 `LlmModelFailure` 재사용. **별도 로깅** 대상(FR-008/017). 하나라도 있으면 청크 미확정.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 조사 대기열은 항상 **10개 단위 청크**로 분할되어 호출된다(마지막 청크 잔여 허용, 빈 대기열은 무호출).
- **SC-002**: (음식, 성분)별 최종 `inclusionConfidence` 는 **정수 1~100** 범위를 벗어나지 않는다(범위 이탈 0건, 0 산출 시 1 로 clamp).
- **SC-003**: 문서 §5 예시(`비빔밥-계란`, score [2,1,2]·probability [90,70,80])를 공식에 넣으면 `inclusionConfidence = 74` 가 재현된다(집계 결정성).
- **SC-004**: 청크는 **3개 모델 결과가 모두 취합됐을 때만** 확정된다 — 1~2개만 성공한 경우 확정 0건(부분 집계 금지), 실패 모델은 100% 로깅되고 음식은 미확정으로 남는다.
- **SC-005**: 산출된 `inclusionConfidence` 를 KB-9 `fromInclusionProbability` 입력에 넣었을 때 **범위/형식 오류로 인한 거부가 0건**이다(값 범위·의미 정합).
- **SC-006**: 3모델 병렬 스코어링의 청크당 벽시계 소요가 순차 합이 아니라 **가장 느린 단일 모델 호출에 수렴**한다.
- **SC-007**: 모델 간 score 일치 수준(3개 동일/2개 동일/모두 상이)에 따라 agreement_factor(1.0/0.9/0.75)가 최종값에 반영된다(일치도 반영 검증).
- **SC-008**: 음식별 번역 산출물은 `LocalizedText.translations`·`food.name_translations` 와 동형(키가 대상 9개 언어 부분집합, `ko` 키 없음)이라 KB-54 가 변환 없이 저장 가능하다(형식 정합 검증).
- **SC-009**: 음식 설명 산출물은 한국어 + 9개 언어 번역을 담고 **각 값이 공백 포함 230자를 넘지 않으며**(목표 200, 초과분 230 잘라내기) `food.description`/`description_translations`·`LocalizedText` 와 동형이다(길이·형식 정합 검증).
- **SC-010**: 일부 모델 실패 시 실패 모델별 로그(modelId + 사유)가 남고, 부분 결과가 확정·산출물로 유입되지 않는다(부분 유입 0건).

## Assumptions

- **범위 경계**: 이번 기능은 조사 대기열의 음식을 10개 청크로 3모델 **동시** 스코어링하고 Consensus Ensemble 로 (음식, 성분)별 신뢰도를 산출하며, **같은 호출에서 음식명 9개 언어 번역 + 음식 설명(한국어 생성 + 9개 언어 번역, 공백 포함 200자 이내)** 을 함께 산출하는 데까지다. **범위 밖**: DB 영속(스키마·적재 = KB-54/T5), 위험도 판정(KB-9), 참고 문서 §6 자체 판정표, 메뉴 수집(T2), 대기열 적재(상류 로직)는 "주어진 대기열 소비"로 가정. (음식명 번역·설명은 원래 T3 였으나 스코어링 호출에 통합해 이번 범위로 흡수.)
- **모델 완결성(변경 — Jira DoD 갱신 필요)**: 청크 확정에 **3개 모델 결과 모두 필요**(부분 집계 금지). 사용자 지시(2026-07-06)가 기존 clarify "≥1 성공 완결" 및 KB-53 Jira DoD "일부 실패해도 남은 결과로 완결"을 **대체**한다. 일부 실패는 별도 로깅 + 청크 미확정(재조사). ⚠️ Jira 티켓 DoD 를 이 정책으로 갱신 요망.
- **텍스트 선정 규칙(확정)**: 음식명 번역·설명은 앙상블 아님 — 3개 모델 중 **우선순위 `OPENAI→UPSTAGE→GEMINI` 로 한 모델의 텍스트**를 채택(결정적, 이름·설명 같은 모델로 일관). 우선순위는 구현자 재량 상수(2026-07-06 사용자 위임).
- **번역 언어 수(주의)**: 사용자 표현 "한국어 외 10개국"은 헌법 V 의 **대상 9개 언어**(+ ko 원문 = 총 10)로 해석. 정본은 9개 대상 언어.
- **설명 길이(확정)**: 음식 설명 각 언어 값은 **공백 포함 200자 목표, 하드캡 230자**(200~230 허용, 230 초과분 잘라내기). 기존 도메인 `FoodContent.MAX_DESCRIPTION_LENGTH=255` 이내라 저장 호환.
- **집계 공식(확정)**: 참고 문서 §4 Consensus Ensemble(α=0.6, agreement_factor 1.0/0.9/0.75). MVP 휴리스틱 — 향후 검수 데이터로 calibration 대체 가능(문서 §7-3).
- **산출값 이름·범위(확정)**: `inclusionConfidence`(포함 가능성 신뢰도, LLM 추정값), 정수 **1~100**. 각 모델 probability 는 프롬프트로 1~100 강제, 최종값은 1~100 clamp. KB-9 `fromInclusionProbability` 계약과 호환.
- **응답 형태(확정)**: 프롬프트에 81종 후보 제시 → 모델은 **포함으로 판단한 것만** score/probability 응답. 미응답 = 미포함(SAFE 등가).
- **소비자·배선**: 단일 소비자는 `:app:batch` 이며 `:infra:llm` 을 `implementation` 으로 직접 의존한다(KB-49/ADR-0010). 프롬프트/파싱/집계 계약을 어느 모듈에 둘지(벤더 중립 `:infra:llm` vs 도메인성 배치)와 카탈로그 참조 배선은 plan 단계에서 모듈 경계(원칙 II/III)에 맞춰 결정한다.
- **DoD "81종 전 성분" 해석**: 81종 각각은 "포함(신뢰도 산출) 또는 미포함(SAFE 등가)"으로 **전부 회계처리**된다 — 모든 성분에 대해 명시적 숫자를 강제하지 않고, 응답된 것만 신뢰도를 갖고 나머지는 미포함으로 정의한다.
- **테스트**: 실 네트워크 없이 페이크 `LlmModelCaller` 로 프롬프트/파싱/집계/부분실패/공식 재현(문서 예시)을 단위 검증하며, 실키 3모델 스모크는 `@Disabled`+수동 절차로 둔다(헌법 I).
