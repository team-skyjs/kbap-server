# Feature Specification: 관리자 대시보드 확장 — 가입자·스캔·신규 음식·LLM 비용 주간 지표 시각화

**Feature Branch**: `kb-264-admin-dashboard-metrics`

**Created**: 2026-07-30

**Status**: Draft

**Input**: User description: "관리자 페이지에 대시보드를 만들어서 현재 음식 적재 정보 외에 총 가입자 수, 요일별 스캔 횟수, 신규 등록 음식 개수, llm 호출 비용 일주일 단위로 그래프 시각화 정도를 추가 (KB-264)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 총 가입자 수 확인 (Priority: P1)

운영자가 관리자 대시보드에 접속하면 기존 음식 적재 현황과 함께 현재 서비스의 총 가입자 수(활성 회원 기준)를 한눈에 확인한다. 지금은 가입자 규모를 알려면 DB 를 직접 조회해야 한다.

**Why this priority**: 가입자 규모는 서비스 성장의 가장 기본이 되는 지표이고, 단일 숫자 표시라 가장 작은 단위로 먼저 검증·배포할 수 있다.

**Independent Test**: 활성 회원·탈퇴 회원이 섞여 있는 상태로 대시보드에 접속해, 활성 회원 수만 정확히 표시되는 것으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 활성 회원 3명과 탈퇴 회원 1명이 있을 때, **When** 운영자가 대시보드에 접속하면, **Then** 총 가입자 수가 3으로 표시된다.
2. **Given** 회원이 한 명도 없을 때, **When** 운영자가 대시보드에 접속하면, **Then** 총 가입자 수가 0으로 표시된다.

---

### User Story 2 - 최근 일주일 요일별 스캔 횟수 그래프 (Priority: P2)

운영자가 대시보드에서 최근 일주일의 스캔 횟수를 요일별 그래프로 확인해, 사용량 추이와 요일별 이용 패턴을 파악한다.

**Why this priority**: 스캔은 서비스의 핵심 사용 행위라 사용량 추이가 두 번째로 중요한 운영 지표다.

**Independent Test**: 날짜별로 스캔 이력을 쌓아 둔 상태로 대시보드에 접속해, 최근 7일 각 요일의 스캔 횟수가 그래프에 정확히 표시되는 것으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 최근 7일 중 특정 요일에만 스캔 이력이 있을 때, **When** 운영자가 대시보드에 접속하면, **Then** 해당 요일에 스캔 횟수가, 나머지 요일에 0이 표시된다.
2. **Given** 7일보다 오래된 스캔 이력이 있을 때, **When** 운영자가 대시보드에 접속하면, **Then** 그 이력은 그래프 집계에 포함되지 않는다.

---

### User Story 3 - 최근 일주일 신규 등록 음식 개수 그래프 (Priority: P3)

운영자가 대시보드에서 최근 일주일 동안 새로 등록된 음식 개수를 일자별 그래프로 확인해, 콘텐츠가 얼마나 빠르게 늘고 있는지 파악한다.

**Why this priority**: 콘텐츠 증가 추이는 적재 파이프라인이 건강하게 도는지 보여주는 지표로, 사용량 지표 다음으로 필요하다.

**Independent Test**: 등록 시점이 다른 음식들을 준비한 상태로 대시보드에 접속해, 최근 7일 일자별 신규 음식 개수가 그래프에 정확히 표시되는 것으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 최근 7일 안에 등록된 음식과 그 이전에 등록된 음식이 섞여 있을 때, **When** 운영자가 대시보드에 접속하면, **Then** 최근 7일에 등록된 음식만 일자별로 집계되어 표시된다.

---

### User Story 4 - 최근 일주일 LLM 호출 비용 그래프 (Priority: P4)

운영자가 대시보드에서 최근 일주일의 LLM 호출 비용을 일자별 그래프로 확인해, 비용이 비정상적으로 튀는 날을 즉시 알아챈다.

**Why this priority**: 비용 관제는 중요하지만 발생 빈도가 배치 실행에 좌우되므로, 상시 사용 지표들 다음 순서로 둔다.

**Independent Test**: 일자별 LLM 호출 비용 기록을 쌓아 둔 상태로 대시보드에 접속해, 최근 7일 일자별 비용 합계가 그래프에 정확히 표시되는 것으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 최근 7일 중 일부 날짜에만 LLM 호출 비용이 기록돼 있을 때, **When** 운영자가 대시보드에 접속하면, **Then** 기록이 있는 날짜는 비용 합계가, 없는 날짜는 0이 표시된다.

---

### Edge Cases

- 최근 7일 전체에 데이터가 하나도 없으면 그래프는 모든 값을 0으로 표시하고 화면이 깨지지 않아야 한다.
- 날짜 경계(자정 직전·직후)에 생성된 데이터는 생성된 날짜 하루에만 집계되어야 한다(중복·누락 금지).
- 관리자 인증 없이 대시보드에 접근하면 기존 관리자 페이지와 동일하게 차단되어야 한다.
- 비용이 소수(1달러 미만)인 날도 0으로 뭉개지지 않고 실제 값으로 표시되어야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 대시보드는 기존 음식 적재 현황(상태별 카운트·READY 비율)을 유지한 채 신규 지표를 추가로 표시해야 한다.
- **FR-002**: 대시보드는 총 가입자 수를 활성 회원 기준으로 표시해야 한다(탈퇴 회원 제외).
- **FR-003**: 대시보드는 최근 7일(오늘 포함)의 스캔 횟수를 요일 라벨과 함께 일자별 그래프로 표시해야 한다.
- **FR-004**: 대시보드는 최근 7일(오늘 포함)의 신규 등록 음식 개수를 일자별 그래프로 표시해야 한다.
- **FR-005**: 대시보드는 최근 7일(오늘 포함)의 LLM 호출 비용 합계를 일자별 그래프로 표시해야 한다.
- **FR-006**: 데이터가 없는 날짜는 그래프에서 0으로 표시해야 한다(날짜 축 누락 금지).
- **FR-007**: 대시보드 지표는 인증된 관리자만 조회할 수 있어야 한다.
- **FR-008**: 지표는 대시보드 접속(조회) 시점의 데이터를 반영해야 한다.

### Key Entities

- **회원**: 서비스 가입자. 활성/탈퇴 상태를 가지며 총 가입자 수 집계의 원천.
- **스캔 이력**: 사용자가 메뉴판을 스캔한 기록. 발생 시각을 가지며 요일별 스캔 횟수 집계의 원천.
- **음식**: 서비스에 적재된 음식 콘텐츠. 등록 시각을 가지며 신규 등록 개수 집계의 원천이자 기존 적재 현황 지표의 대상.
- **LLM 호출 비용 기록**: LLM 호출 1건마다 남는 비용 원장. 발생 시각과 비용 금액을 가지며 일자별 비용 집계의 원천.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영자가 DB 를 직접 조회하지 않고 대시보드 한 화면에서 4개 신규 지표(가입자·스캔·신규 음식·LLM 비용)를 모두 확인할 수 있다.
- **SC-002**: 대시보드에 표시된 각 지표 값이 같은 시점의 원천 데이터 집계 결과와 100% 일치한다.
- **SC-003**: 기존 음식 적재 현황 지표가 변경 전과 동일하게 동작한다(회귀 없음).
- **SC-004**: 운영자가 대시보드 접속 후 추가 조작 없이 최근 일주일의 사용량·비용 추이를 파악할 수 있다.

## Assumptions

- "일주일 단위"는 조회 시점 기준 오늘을 포함한 최근 7일로 해석한다(고정 주차 단위가 아님).
- "요일별 스캔 횟수"는 최근 7일의 일자별 집계에 요일 라벨을 붙여 표시하는 것으로 해석한다(여러 주에 걸친 요일 합산이 아님).
- 총 가입자 수는 활성 회원만 센다 — 기존 회원 조회 규약(활성 회원만 노출)과 일치시킨다.
- LLM 호출 비용은 이미 적재되고 있는 비용 원장 기록을 그대로 집계한다(새로운 비용 수집 체계는 만들지 않는다).
- 대시보드는 기존 관리자 페이지와 동일한 인증 체계를 재사용한다.
- 지표는 조회 시점 계산으로 충분하며 실시간 자동 갱신·별도 사전 집계 저장은 범위 밖이다.
- 날짜 집계 기준 시간대는 한국 시간(서비스 운영 시간대)이다.
