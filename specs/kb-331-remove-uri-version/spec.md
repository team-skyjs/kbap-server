# Feature Specification: 전 API URI 버전 제거 + 버전 헤더 필수화

**Feature Branch**: `kb-331-remove-uri-version`

**Created**: 2026-08-13

**Status**: Draft

**Input**: User description: "모든 API 에서 URI 의 v1 세그먼트를 제거하고, X-API-Version 헤더를 1.0 필수로 입력받도록 개정한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 단일 경로 체계 (Priority: P1)

클라이언트 개발자는 모든 API 를 버전 세그먼트 없는 단일 경로(`/api/<리소스>`)로 호출한다. 레거시 `/api/v1/...` 경로는 더 이상 제공되지 않는다.

**Why this priority**: 현재 신규 리소스(`/api/scans`·`/api/reviews`)와 레거시(`/api/v1/members` 등)가 혼재해 클라이언트·문서·보안 설정(보호 경로 목록)이 두 체계를 함께 관리한다. 이 이중 체계가 신규 엔드포인트마다 실수 지점(보호 경로 누락 등)을 만들어 왔다.

**Independent Test**: 기존 `/api/v1/...` 로 제공되던 모든 기능이 `/api/...` 경로에서 동일하게 동작하고, `/api/v1/...` 호출은 실패하는 것으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 버전 헤더를 보내는 클라이언트가, **When** `/api/members/...` 등 새 경로로 기존 기능을 호출하면, **Then** 종전 `/api/v1/...` 과 동일한 응답을 받는다.
2. **Given** 구 경로를 호출하는 클라이언트가, **When** `/api/v1/...` 로 요청하면, **Then** 요청이 실패한다(경로 없음).

---

### User Story 2 - 버전 명시 강제 (Priority: P2)

모든 API 요청은 `X-API-Version` 헤더를 반드시 포함해야 한다. 헤더가 없는 요청은 에러로 거절된다 — 암묵 기본값(1.0)이 사라져 클라이언트가 어떤 계약을 쓰는지 항상 명시된다.

**Why this priority**: 기본값이 있으면 헤더를 빠뜨린 신규 클라이언트가 조용히 1.0 계약으로 동작해 버그가 늦게 드러난다. 필수화하면 계약 불명 요청이 시끄럽게 실패한다.

**Independent Test**: 헤더 없이 보낸 요청이 에러로 거절되고, `X-API-Version: 1.0` 을 붙이면 정상 동작하는 것으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 헤더 없는 요청이, **When** 임의 비즈니스 API 를 호출하면, **Then** 에러로 거절된다.
2. **Given** `X-API-Version: 1.0` 헤더를 포함한 요청이, **When** 같은 API 를 호출하면, **Then** 정상 처리된다.
3. **Given** 헤더 없는 요청이, **When** 앱 버전 조회(`/api/app-version`)를 호출하면, **Then** 정상 처리된다(예외 — 강제 업데이트 안내의 복구 경로).

---

### Edge Cases

- 앱 버전 조회는 헤더 필수화의 유일한 예외다 — 구버전·오동작 클라이언트도 강제 업데이트 안내를 받아야 하므로 가장 관대하게 유지한다.
- 지원하지 않는 버전 값(예: `9.9`)의 기존 처리(에러)는 그대로 유지한다.
- 관리자 API(`/api/admin/**`)·프레임워크 경로(actuator·swagger)는 이미 URI 무버전이며, 관리자 API 도 헤더 필수 대상에 포함된다.
- 기존 배포 앱은 `/api/v1` + 무헤더로 호출하므로 이 개정으로 완전히 차단된다 — KB-329 강제 업데이트(minSupportedVersion 상향) 후 배포가 전제다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 모든 비즈니스 API 는 버전 세그먼트 없는 `/api/<리소스>` 경로로만 제공되어야 한다 — 레거시 `/api/v1` 경로는 제거된다.
- **FR-002**: `X-API-Version` 헤더가 없는 비즈니스 API 요청은 에러로 거절되어야 한다(암묵 기본 버전 폐지).
- **FR-003**: 앱 버전 조회는 헤더 없이도 정상 동작해야 한다(유일 예외).
- **FR-004**: 경로 이동 후에도 각 API 의 기능·응답·인증 요구(보호/공개/게스트 예외)는 변경 전과 동등해야 한다.
- **FR-005**: 버전 헤더를 포함한 신규 클라이언트(1.0.2+)의 동작에는 회귀가 없어야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 레거시 `/api/v1` 경로가 0개가 된다 — 전 기능이 단일 경로 체계로 제공된다.
- **SC-002**: 헤더 없는 비즈니스 API 요청의 100% 가 에러로 거절된다(앱 버전 조회 제외).
- **SC-003**: 헤더를 보내는 클라이언트 기준 전 기능의 동작이 변경 전과 동등하다(전체 테스트 통과).
- **SC-004**: 신규 엔드포인트 추가 시 관리할 경로 체계가 하나로 준다(레거시 베이스 관리 소멸).

## Assumptions

- 배포 전 KB-329 로 minSupportedVersion 을 상향해 구 앱(무헤더·/api/v1)을 강제 업데이트로 차단한다 — 과도기 이중 매핑·리다이렉트는 두지 않는다(사용자 결정, 2026-08-13).
- 새 iOS 릴리스는 모든 요청에 `X-API-Version` 을 첨부한다(클라이언트 팀 합의 전제).
- 버전 값 자체의 해석(1.0/1.1 분기)은 기존 체계 그대로 유지하며, 이 개정은 경로와 필수 여부만 다룬다.
