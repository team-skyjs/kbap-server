# Feature Specification: 호스트마다 수집기를 두어 앱·호스트 메트릭을 홈서버로 보낸다 — 카나리 버전까지 구분해서

**Feature Branch**: `kb-381-alloy-daemon-remote-write`

**Created**: 2026-08-28

**Status**: Draft

**Input**: User description: "381" — Jira KB-381: ECS 에 Grafana Alloy DAEMON 서비스 추가 — actuator·호스트 메트릭 수집 → 홈 Prometheus remote_write 연동 (에픽 KB-379 모니터링, KB-380 의 후속)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 운영자가 홈서버 Grafana 에서 dev·prod 앱의 내부 상태를 본다 (Priority: P1)

KB-380 으로 api·batch 는 자기 내부 상태(JVM·커넥션 풀·엔드포인트별 요청·배치 잡)를 각 호스트 안에서 내놓게 됐지만, 그걸 읽는 것은 아직 아무도 없다. 이 기능이 끝나면 각 서버 호스트에 상주하는 수집기가 그 호스트의 앱 컨테이너를 찾아 주기적으로 읽고, 홈서버의 시계열 저장소로 밀어 넣는다. 운영자는 홈서버 Grafana 에서 `env=dev|prod` 와 앱 이름만 골라 두 환경의 앱 상태를 한 화면에서 본다.

**Why this priority**: 에픽의 핵심 경로다. 이게 없으면 KB-380 의 노출은 아무 가치가 없고, 뒤의 대시보드·알림(KB-383)도 볼 데이터가 없다.

**Independent Test**: dev 에 적용한 뒤 홈서버 Grafana 탐색기에서 `up{env="dev", job="prometheus.scrape.ecs_apps"}` 를 조회해 실행 중인 api·batch 태스크 수만큼 값 1 의 시계열(`instance=dev-api-…`/`dev-batch-…`)이 보이고, 그중 하나의 JVM 힙 사용량이 시간에 따라 그려지면 통과.

**Acceptance Scenarios**:

1. **Given** dev 에 api 태스크 2개·batch 태스크 1개가 실행 중이다, **When** 홈서버 Grafana 에서 `up{env="dev"}` 를 조회하면, **Then** 시계열 3개가 값 1 로 보이고 각각 `application` 이 `kbap-api`/`kbap-batch` 로 구분된다.
2. **Given** 수집이 동작 중이다, **When** api 의 JVM 힙 사용량·HikariCP 활성 커넥션·엔드포인트별 요청 수를 조회하면, **Then** 15초 간격의 값이 끊김 없이 그려진다.
3. **Given** 수집이 동작 중이다, **When** batch 잡을 한 번 트리거해 완료시키면, **Then** 1분 안에 그 잡의 실행 횟수·소요 시간이 홈서버에서 조회된다.
4. **Given** dev·prod 모두 적용됐다, **When** 같은 메트릭을 `env` 만 바꿔 조회하면, **Then** 두 환경이 섞이지 않고 각각 나온다.

### User Story 2 - 배포·스케일아웃이 일어나도 수집이 스스로 따라간다 (Priority: P1)

api 는 카나리 배포로 컨테이너가 계속 교체되고(한 호스트에 구·신 버전이 잠깐 공존), 부하에 따라 호스트가 늘어날 수 있다. 수집기는 호스트마다 하나씩 고정으로 살아 있으면서 그 호스트의 앱 컨테이너를 **스스로 찾아** 읽어야 한다 — 컨테이너가 바뀌거나 호스트가 늘 때 누가 설정을 고치러 들어가면 안 된다.

**Why this priority**: 수집이 배포 한 번에 끊기면 대시보드가 거짓 공백을 보인다. P1 과 같은 배포에 함께 나가야 한다.

**Independent Test**: dev 에서 (a) api 를 한 번 배포해 컨테이너가 교체된 뒤 `up` 이 잠깐의 공백 후 새 컨테이너로 다시 1 이 되고, (b) 호스트를 교체(instance refresh)한 뒤 새 호스트의 타깃이 아무 조작 없이 나타나면 통과.

**Acceptance Scenarios**:

1. **Given** 수집이 동작 중이다, **When** api 를 카나리로 배포하면, **Then** 카나리 창 동안 구버전·신버전 컨테이너 **둘 다** 수집되고, 구버전이 내려가면 그 타깃만 사라진다.
2. **Given** 수집이 동작 중이다, **When** 호스트 하나를 교체하면, **Then** 새 호스트가 클러스터에 합류한 뒤 5분 안에 그 호스트의 수집기가 뜨고 앱 타깃이 홈서버에 나타난다.
3. **Given** 수집이 동작 중이다, **When** 홈서버 접속이 30분 끊겼다가 복구되면, **Then** 끊긴 구간의 메트릭이 사후에 채워진다(수집기가 버퍼링).
4. **Given** 홈서버 접속이 3시간 이상 끊겼다, **When** 복구되면, **Then** 버퍼 용량을 넘긴 구간은 유실되지만 수집기는 정상 재개하고 앱 서비스에는 아무 영향이 없다.

### User Story 3 - 카나리 배포 중 구버전과 신버전을 나눠 비교한다 (Priority: P2)

배포 직후 가장 알고 싶은 것은 "신버전이 구버전보다 나쁜가" 다. 수집기가 각 컨테이너에 **배포 버전 라벨**과 **태스크 단위 식별 라벨**을 붙여 주면, Grafana 에서 5xx 비율·p95·JVM 메모리를 버전별로 나란히 놓고 볼 수 있다. 앱 코드나 배포 절차는 바꾸지 않는다.

**Why this priority**: 카나리를 하면서 버전 비교를 못 하면 카나리의 의미가 없다. 다만 P1·P2 가 되고 나서 라벨만 얹으면 되므로 뒤에 둔다.

**Independent Test**: dev 에서 api 를 한 번 배포한 뒤 카나리 창 안에 `http_server_requests_seconds_count` 를 `version` 으로 group by 하면 서로 다른 두 값이 나오고, 각각의 `instance` 가 태스크 단위로 구분되면 통과.

**Acceptance Scenarios**:

1. **Given** 카나리 창에 구·신 컨테이너가 공존한다, **When** 요청 수를 `version` 별로 조회하면, **Then** 두 버전이 별개 시계열로 나온다.
2. **Given** 같은 상황, **When** `instance` 라벨을 보면, **Then** 같은 호스트의 두 컨테이너가 서로 다른 값(태스크 단위)으로 구분된다.
3. **Given** 배포가 끝나 신버전만 남았다, **When** 이전 버전의 시계열을 보면, **Then** 종료 시점 이후 값이 없다(오염 없음).

---

### User Story 4 - 호스트 자원(메모리·디스크)도 같은 경로로 본다 (Priority: P2)

클라우드 콘솔은 호스트 CPU·네트워크만 알려 주고 메모리·디스크 사용률은 모른다. 호스트마다 이미 뜨는 수집기가 호스트 자원도 함께 읽어 보내면, 별도 에이전트 없이 "디스크가 차고 있다"를 홈서버 Grafana 에서 본다.

**Why this priority**: 앱 메트릭 경로가 자리 잡으면 블록 하나 추가로 얻는 값이라 뒤에 둔다. 디스크 만차는 실제 장애 원인이라 빼지는 않는다.

**Independent Test**: dev 홈서버에서 호스트 메모리 가용량·루트 파일시스템 가용량·CPU 사용률이 인스턴스 수만큼 조회되면 통과.

**Acceptance Scenarios**:

1. **Given** dev 인스턴스 3대(api 2·batch 1), **When** 호스트 메모리 가용량을 조회하면, **Then** 3개 시계열이 각각 다른 `instance` 로 보인다.
2. **Given** 같은 상황, **When** 루트 파일시스템 사용률을 조회하면, **Then** 실제 값(0~100%)이 15초 간격으로 그려진다.

---

### User Story 5 - 홈서버로 들어오는 경로는 인증되고, 앱은 홈서버를 모른다 (Priority: P1)

수집기는 밖으로만 연결한다(인바운드 개방 없음). 홈서버 쪽 수신 지점은 기존 터널을 통해 공개되되 **서비스 토큰이 없는 요청은 거부**한다. 앱은 홈서버 주소나 토큰을 갖지 않는다 — 저장소를 옮기거나 팀원 저장소로 복사본을 보낼 때 수집기 설정만 바꾼다.

**Why this priority**: 보안 경계라 P1 과 함께 나가야 한다. 토큰 없는 수신 지점을 잠깐이라도 공개하면 안 된다.

**Independent Test**: 토큰 없이 홈서버 수신 주소로 요청 → 거부(4xx). 수집기 설정에 담긴 토큰으로 요청 → 수락. api·batch 컨테이너의 환경변수·설정에 홈서버 주소·토큰이 없음.

**Acceptance Scenarios**:

1. **Given** 홈서버 수신 지점이 공개돼 있다, **When** 토큰 없이 접근하면, **Then** 거부된다.
2. **Given** 수집기가 토큰을 가진다, **When** 토큰이 폐기되면, **Then** 수집이 멈추고(홈서버에 새 데이터 없음) 앱 서비스는 영향이 없다.
3. **Given** 인스턴스 방화벽·앱 컨테이너 정의를 적용 전후로 비교한다, **When** diff 를 보면, **Then** 인바운드 규칙 변경 0, 앱 컨테이너 환경변수 변경 0 이다.

---

### Edge Cases

- 한 호스트에서 수집기가 죽으면? → 오케스트레이터가 재기동한다. 그 사이 그 호스트 타깃만 `up=0`(KB-383 알림 대상). 앱은 영향 없음.
- 수집기가 앱 메트릭을 읽는 데 실패하면(앱 기동 중·응답 지연)? → 해당 타깃 `up=0` 으로 기록되고 다음 주기에 재시도. 앱 기동 유예 동안의 0 은 정상.
- 호스트에 앱 컨테이너가 없으면(batch 풀에 api 없음)? → 그 호스트에서는 있는 것만 수집한다. 없는 컨테이너 때문에 오류를 내지 않는다.
- prod 배치는 현재 0대인데? → prod batch 호스트의 수집기는 호스트 자원만 보낸다. 배치를 켜면 자동으로 앱 타깃이 추가된다.
- 수집기 설정을 바꾸고 싶으면(홈서버 이전·복사본 추가)? → 설정 저장소의 값만 바꾸고 수집기를 재기동한다. 앱 재배포 없음.
- 홈서버 저장소 디스크가 차면? → 홈서버 쪽 보존 기간 설정의 문제이며 이 기능 범위 밖(전제: 기본 보존 15일, 월 1GB 안팎).
- 카나리 두 컨테이너가 같은 배포 버전이면(재시작)? → `version` 이 같고 `instance` 만 다르다. 비교는 안 되지만 오염도 없다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 각 서버 호스트(api 풀·batch 풀 모두)에 수집기가 정확히 하나씩 상주해야 하며, 호스트가 추가·교체되면 사람의 개입 없이 새 호스트에도 뜬다.
- **FR-002**: 수집기는 자기 호스트에서 실행 중인 api·batch 앱 컨테이너를 스스로 찾아 15초 주기로 메트릭을 읽어야 한다. 컨테이너가 교체·추가·제거되면 다음 주기부터 반영된다.
- **FR-003**: 수집기는 읽은 메트릭을 홈서버의 시계열 저장소로 **밖으로만** 보내야 한다(인스턴스 인바운드 개방 없음). 홈서버 접속 단절 시 최소 2시간분을 버퍼했다가 복구 후 전송한다.
- **FR-004**: 모든 메트릭에 다음 라벨이 붙어야 한다 — `env`(dev|prod), `application`(앱이 붙인 값 그대로), `instance`(태스크 단위로 고유), `version`(배포 버전 — 배포마다 달라지는 값). `service` 처럼 `application` 과 중복되는 라벨은 만들지 않는다.
- **FR-005**: 수집기는 호스트 자원 메트릭(CPU·메모리·디스크·load)도 같은 경로로 보내야 한다. 호스트마다 `instance` 로 구분된다.
- **FR-006**: 홈서버 수신 지점은 기존 터널을 통해 공개하되 서비스 토큰 인증을 통과한 요청만 받아야 한다. 저장소의 조회 UI 는 공개하지 않는다.
- **FR-007**: 앱(api·batch)의 코드·설정·컨테이너 정의를 이 기능을 위해 바꾸지 않는다. 홈서버 주소·토큰은 수집기만 가진다.
- **FR-008**: 수집기 설정(대상·라벨·전송처)은 인프라 코드가 관리하는 설정 저장소에 두고, 변경 시 앱 재배포 없이 수집기만 재기동해 반영한다.
- **FR-009**: 수집기의 토큰은 다른 시크릿과 같은 방식으로 저장·주입되어야 하며 코드·설정 파일에 평문으로 남지 않는다.
- **FR-010**: 인프라 문서에 수집기 구성·필요 시크릿·라벨 규약·홈서버 측 전제 조건이 기록되어야 한다.

### Key Entities *(include if feature involves data)*

- **수집기(호스트당 1)**: 호스트 수명과 같이 간다. 자기 호스트의 앱 컨테이너 목록·호스트 자원을 읽고 홈서버로 보낸다. 상태는 전송 버퍼(WAL)뿐.
- **메트릭 시계열**: 홈서버 저장소에 쌓인다(보존은 홈서버 설정). 라벨 = `env`·`application`·`instance`·`version` + 앱/호스트가 붙인 라벨.
- **서비스 토큰**: 홈서버 수신 지점 인증용 한 쌍. 환경별로 하나(dev·prod 분리 — 한쪽 폐기가 다른 쪽에 영향 없게).
- **수집기 설정**: 환경별 하나. 대상 선택 규칙·라벨·전송처·토큰 참조를 담는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: dev·prod 적용 후 홈서버에서 `up{env=...}` 가 실행 중인 앱 태스크 수와 100% 일치한다.
- **SC-002**: api 카나리 배포 1회 동안 신·구 버전 시계열이 `version` 으로 분리돼 보이고, 배포 완료 후 5분 안에 구버전 타깃이 사라진다.
- **SC-003**: 호스트 교체(instance refresh) 후 5분 안에 새 호스트의 앱·호스트 메트릭이 홈서버에 나타난다(사람 개입 0회).
- **SC-004**: 홈서버 30분 단절 후 복구 시 단절 구간 메트릭의 95% 이상이 사후 채워진다.
- **SC-005**: 토큰 없는 요청은 100% 거부되고, 인스턴스 방화벽 인바운드·앱 컨테이너 정의 변경은 0 이다.
- **SC-006**: 앱 서비스 응답 시간(로드밸런서 p95)이 적용 전후 ±5% 이내(수집이 서비스에 부담을 주지 않는다).
- **SC-007**: 월 추가 인프라 비용은 수집기 컨테이너의 CPU/메모리 예약분뿐이다(신규 EC2·로드밸런서·고정 IP 0).

## Assumptions

- 앱 측 노출은 KB-380 으로 끝나 있다 — api·batch 가 서비스 포트(8080)의 `/actuator/prometheus` 로 메트릭을 내놓고 `application` 태그를 붙인다. 이 기능은 그걸 읽는 쪽만 만든다.
- 수집기가 호스트의 컨테이너를 찾는 근거는 컨테이너 런타임의 메타데이터(오케스트레이터가 붙이는 컨테이너 이름·태스크 식별자·태스크 정의 리비전 라벨)다. `version` 은 **태스크 정의 리비전 번호**로 삼는다 — CI 가 배포마다 새 리비전을 만들므로 리비전 = 배포 버전이며 앱 변경이 필요 없다. `instance` 는 `<env>-<컨테이너 이름>-<태스크 식별자 앞부분>` 으로 만든다(카나리 중 한 호스트에 태스크 2개가 공존하므로 호스트 단위가 아니라 태스크 단위). 호스트(EC2) 식별자는 붙이지 않는다 — 컨테이너에서 인스턴스 메타데이터를 읽으려면 네트워크 설정 변경이 필요해 값 대비 비용이 크다.
- 홈서버는 이미 시계열 저장소(Prometheus 계열)와 Grafana 를 컨테이너로 운영 중이고, 외부 접속용 터널(Cloudflare Tunnel)이 구성돼 있다. 이 기능은 저장소에 원격 쓰기 수신을 켜고 터널에 수신 호스트 하나와 서비스 토큰 정책을 추가한다. Tailscale 등 새 VPN 은 등록하지 않는다(사용자 결정).
- 수신 호스트명과 서비스 토큰(환경별 1쌍)은 사용자가 발급해 제공한다. 토큰은 기존 시크릿 규칙(`/kbap/<env>/<NAME>` SecureString)으로 저장하고 수집기 컨테이너에만 주입한다.
- 수집기 설정 파일은 별도 이미지 빌드 없이 설정 저장소(SSM Parameter)에 두고 컨테이너 기동 시 주입한다.
- 호스트 자원 메트릭은 이 수집기가 담당한다(KB-383 에서 이관, 2026-08-28 결정 — CloudWatch Agent 미설치). 클라우드 관리형 지표(로드밸런서·DB·캐시·컨테이너 CPU/메모리)는 CloudWatch 그대로이며 Grafana 가 데이터소스로 읽는다(KB-383).
- 홈서버 저장소 보존 기간·디스크는 홈서버 운영 범위(기본 15일, 예상 월 1GB 안팎). 백업하지 않는다.
- 자동화 테스트는 작성하지 않는다(KB-380 과 같은 결정 — 인프라·설정 작업). 검증은 dev 적용 후 홈서버 Grafana 조회와 배포·호스트 교체 시나리오 실행으로 한다.
- prod 배치는 0대라 prod 의 batch 앱 타깃 검증은 배치를 켜는 시점으로 미룬다. 호스트 자원은 prod batch 풀이 0대면 대상 없음.
- 대시보드·알림은 KB-383 범위. 이 기능은 "홈서버에서 조회 가능" 까지다.
