# Feature Specification: HELPFUL 발송 — 리뷰 좋아요 시 작성자에게 알림

**Feature Branch**: `kb-470-helpful-push`

**Created**: 2026-09-16

**Status**: Draft

Android channelId 는 activity, data 는 type=HELPFUL·notificationId(reviewId 함께 실음). 알림은 기기 단위, 같은 리뷰에 반응이 몰릴 때 묶음(Jira DoD), 좋아요 취소 후 재등록 시 중복 발송 처리 정책을 명문화한다. 발송 실패는 로깅·카운터만, 재시도 등 추가 방어는 넣지 않는다. 자세한 배경은 Jira KB-470." — Jira KB-470(에픽 KB-463 푸시 알림). + 2차 입력(2026-09-16): "리뷰 좋아요는 실시간으로 보내는 구현으로 단순하게 먼저 끝낸다. 고도화(같은 리뷰 반복 반응 묶음)는 나중에." — Jira DoD 의 묶음 항목은 후속으로 보류.

## 배경

푸시 발송 파이프라인(KB-468)은 "어떤 회원들에게 어떤 유형을" 넣어 주면 기기별 설정·토큰 유효성을 판정해 기기마다 알림함 행을 만들고 Expo 로 보낸 뒤 결과를 발송 이력에 남기는 공용 부품이다. 지금까지 이 부품을 부르는 곳은 관리자 테스트 발송과 스캔 제안 배치(KB-471)뿐이다. 이 기능은 첫 **사용자 행동 트리거 발송자**다 — 다른 회원이 내 리뷰에 '도움돼요'(좋아요)를 누르면 나에게 활동 알림 `HELPFUL` 이 온다.

## Jira 결정과의 차이 (명시)

Jira KB-470 본문은 "반응 발생 시 알림 row(또는 아웃박스)를 남기고 **batch 가 주기적으로** 미발송 row 를 집어 Expo 로 보내는" 방식을 적었다. **이 스펙은 그 방식을 채택하지 않는다.**

| 항목 | Jira KB-470 | 이 스펙 |
|------|-------------|---------|
| 발송 주체 | batch 앱의 주기 잡 | api 앱 — 좋아요 요청이 커밋된 뒤 **백그라운드에서 즉시** |
| 중간 저장 | 미발송 아웃박스 row | 없음 — 파이프라인이 만드는 알림함 행·발송 이력이 전부 |
| 지연 | 잡 주기(수 분) | 수 초 이내 |
| 묶음 | 잡 주기 안에 쌓인 반응을 묶어 1건 | **묶지 않는다** — 새 좋아요 1건당 알림 1건. 묶음은 후속 고도화(2026-09-16 결정) |
| 프로세스 중단 시 | 아웃박스가 남아 다음 주기에 발송 | 커밋 직후 앱이 죽으면 그 알림은 유실된다(감수 — 활동 알림은 놓쳐도 데이터 정합에 영향 없음) |

바꾸는 이유: (1) api 에 백그라운드 실행 기반과 커밋 이후 이벤트 처리 선례가 이미 있어 새 테이블·새 잡 없이 구현된다, (2) 활동 알림은 즉시성이 가치다, (3) 아웃박스·잡은 유실 방지 대가로 테이블·스케줄·중복 실행 방어를 더 요구하는데 이 알림은 유실을 감수해도 되는 종류다. Jira DoD 의 "batch 발송 잡" 항목은 이 스펙의 "커밋 이후 백그라운드 발송" 으로 대체하고, "같은 리뷰 반복 반응 묶음 정책" 항목은 이번 범위에서 뺀다(단순 실시간 발송 먼저, 고도화는 별도 이슈).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 내 리뷰에 좋아요가 달리면 알림을 받는다 (Priority: P1)

리뷰 작성자 A 가 활동 알림을 켜 둔 상태에서, 다른 회원 B 가 A 의 리뷰에 좋아요(liked=true)를 누른다. A 의 기기에 "리뷰가 도움이 됐어요 / {음식} 리뷰에 누군가 '도움돼요'를 눌렀어요." 푸시가 도착하고, A 의 알림함에도 같은 내용이 남는다. 푸시를 누르면 앱이 내 리뷰 화면으로 이동한다.

**Why this priority**: 기능의 본체. 이것만 있어도 활동 알림이 성립한다.

**Independent Test**: A 의 기기 토큰과 활동 알림 on 설정을 준비하고 B 로 좋아요 API 를 호출하면, 잠시 뒤 A 앞으로 HELPFUL 알림함 행 1개와 발송 이력(전송 성공) 1개가 생기고 Expo 로 보낸 메시지의 채널·데이터가 규격과 일치한다.

**Acceptance Scenarios**:

1. **Given** A 의 리뷰와 활동 알림이 켜진 A 의 기기, **When** B 가 좋아요를 등록하면, **Then** 좋아요 API 는 즉시 성공 응답하고, 그 뒤 A 의 기기 앞으로 HELPFUL 알림함 행과 발송 이력이 생기며 Expo 로 메시지가 1건 전송된다.
2. **Given** 위 상황, **When** 전송된 메시지를 보면, **Then** 문구는 A 기기의 언어로 렌더링되고 음식 이름이 들어 있으며, Android 채널은 `activity`, 데이터에는 `type=HELPFUL`·`notificationId`(알림함 행 id)·`reviewId` 가 있다.
3. **Given** A 가 활동 알림이 켜진 기기 두 대를 쓴다, **When** B 가 좋아요를 등록하면, **Then** 두 기기 각각에 알림함 행·발송 이력·메시지가 1건씩 생긴다(기기 단위).
4. **Given** 좋아요 요청이 실패(리뷰 없음 등)해 트랜잭션이 롤백된다, **When** 요청이 끝나면, **Then** 어떤 알림도 만들어지지 않는다.

---

### User Story 2 - 받지 않아야 할 경우엔 받지 않는다 (Priority: P1)

작성자가 활동 알림을 껐거나, 본인이 자기 리뷰에 좋아요를 눌렀거나, 좋아요를 취소하는 경우에는 알림이 가지 않는다.

**Why this priority**: 잘못 보낸 알림은 설정 무시·자기 알림이라는 신뢰 문제라 P1 과 같은 릴리스에 있어야 한다.

**Independent Test**: 각 조건을 만든 뒤 좋아요 API 를 호출하고, HELPFUL 알림함 행·발송 이력·Expo 전송이 0건임을 확인한다.

**Acceptance Scenarios**:

1. **Given** A 의 활동 알림이 꺼진 기기만 있다, **When** B 가 좋아요를 등록하면, **Then** 알림함 행·발송 이력·전송이 0건이다.
2. **Given** A 가 자기 리뷰에 좋아요를 누른다, **When** 요청이 성공하면, **Then** 알림은 만들어지지 않는다.
3. **Given** B 가 A 의 리뷰 좋아요를 취소한다(liked=false), **When** 요청이 성공하면, **Then** 알림은 만들어지지 않는다.
4. **Given** A 에게 유효한 푸시 토큰의 기기가 없다, **When** B 가 좋아요를 등록하면, **Then** 알림함 행도 만들어지지 않는다(파이프라인의 기존 대상 판정 그대로).
5. **Given** B 가 이미 좋아요 상태인 리뷰에 다시 liked=true 를 보낸다(멱등 재호출), **When** 요청이 성공하면, **Then** 알림은 만들어지지 않는다.

---

### Edge Cases

- Expo 전송이 실패하면(일시·영구 불문) 파이프라인의 기존 규칙대로 발송 이력에 실패 사유가 남고 알림함 행은 지워진다. 재시도는 없다 — 다음 좋아요가 새 알림을 만든다.
- 발송 준비·전송 중 예외가 나도 좋아요 API 응답은 영향받지 않는다(이미 성공으로 끝났다). 예외는 로그로만 관측하고, 건별 결과는 발송 이력이 남긴다.
- 좋아요 직후 리뷰가 삭제되거나 작성자가 탈퇴한 경우: 발송 시점에 작성자가 활성 회원이 아니거나 리뷰가 없으면 조용히 건너뛴다.
- 작성자의 기기 언어에 음식 이름 번역이 없으면 파이프라인·음식 도메인의 기존 표시 이름 폴백을 따른다.
- api 인스턴스가 여러 대여도 좋아요 요청은 한 인스턴스가 처리하므로 같은 반응이 두 번 발송되지 않는다.
- 같은 리뷰에 짧은 시간 안에 여러 회원이 좋아요를 누르면 그 수만큼 알림이 간다. 취소 후 재등록도 새 좋아요라 다시 간다. 묶음·도배 방어는 이번 범위 밖(후속 고도화).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 회원 B 가 회원 A 의 리뷰에 좋아요를 **새로 등록**(liked=true, 직전 상태가 좋아요 아님)해 요청이 성공하면 시스템은 A 를 수신자로 하는 `HELPFUL` 알림 발송을 시작해야 한다.
- **FR-002**: 발송은 좋아요 요청의 저장이 확정(커밋)된 **뒤** 백그라운드에서 이루어져야 하며, 요청 응답을 지연시키거나 요청 실패를 유발해서는 안 된다. 요청이 롤백되면 발송은 시작되지 않는다.
- **FR-003**: 다음 경우에는 알림을 만들지 않는다: (a) 좋아요를 누른 회원이 리뷰 작성자 본인, (b) 좋아요 취소(liked=false), (c) 이미 좋아요 상태인 리뷰에 대한 liked=true 재호출.
- **FR-004**: 수신 기기 판정은 기존 발송 파이프라인 규칙을 그대로 쓴다 — 작성자에 연결된 유효 토큰 기기 중 그 (회원, 기기) 설정의 **활동(activity) 토글이 켜진** 기기에만, 기기마다 알림함 행 1개·발송 이력 1개·메시지 1건. 조건을 만족하는 기기가 없으면 아무것도 만들지 않는다.
- **FR-005**: 새 좋아요마다 알림을 만든다 — 같은 리뷰의 이전 알림 여부를 보지 않는다(묶음 없음). 취소 후 재등록은 새 좋아요로 취급한다.
- **FR-006**: 메시지 문구는 기존 HELPFUL 템플릿을 수신 기기 언어로 렌더링하고, 음식 이름 자리에 리뷰 대상 음식의 표시 이름을 채운다.
- **FR-007**: 메시지 데이터에는 `type=HELPFUL`, `notificationId`(알림함 행 id), `reviewId` 를 싣는다.
- **FR-008**: Android 알림 채널은 `activity` 다. 활동 알림 유형(HELPFUL·REVIEW_REMINDER)→`activity`, 광고성 유형→`news` 매핑은 발송 파이프라인의 유형 정의 한 곳에서 관리한다(트리거는 유형만 넘긴다).
- **FR-009**: 전송 결과(성공·실패 사유)는 기존 발송 이력에 남긴다. 실패 시 재시도·아웃박스·지연 큐 같은 추가 방어는 두지 않는다.
- **FR-010**: 발송 준비·전송 중 예외는 로그로 남기고 삼킨다 — 좋아요 요청·다른 알림 발송에 전파되지 않는다.

### Key Entities

- **리뷰 좋아요(ReviewLike)**: (리뷰, 회원) 쌍당 1개. 소프트 삭제로 취소하고 재등록 시 부활한다. 이 기능의 트리거 원천.
- **알림함 행(Notification)**: 수신 회원·기기·유형·문구·데이터·읽음 시각. HELPFUL 의 데이터에 `reviewId` 가 추가된다.
- **발송 이력(NotificationDispatch)**: 알림함 행당 전송 시도 1건 — 티켓 id 또는 실패 사유.
- **알림 설정(NotificationSetting)**: (회원, 기기) 단위 토글. HELPFUL 은 활동(activity) 토글에 묶인다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 좋아요 등록 후 수신 조건을 만족하는 작성자 기기에 알림이 도착하기까지 정상 상황에서 10초 이내(파이프라인 실행 시간 기준).
- **SC-002**: 좋아요 API 의 응답 시간은 알림 기능 도입 전과 차이가 없다(발송이 응답 경로에 없다).
- **SC-003**: 활동 알림이 꺼진 기기·본인 반응·취소·멱등 재호출·롤백된 요청에서 HELPFUL 알림은 0건이다.
- **SC-004**: 서로 다른 회원의 새 좋아요 N건은 HELPFUL 알림 N건을 만든다(묶음 없음).
- **SC-005**: Expo 로 나가는 모든 HELPFUL 메시지의 채널은 `activity`, 데이터는 `type`·`notificationId`·`reviewId` 를 포함한다.

## Assumptions

- **묶음(같은 리뷰 반복 반응 1건화)은 이번 범위 밖**이다 — 2026-09-16 결정: 실시간 단순 발송을 먼저 끝내고 고도화는 별도 이슈로. Jira DoD 의 해당 항목은 보류.
- 활동 알림 토글은 KB-544 의 기기별 설정 `activity` 다(Jira 의 "helpful on" 은 이 토글을 뜻한다). 별도 helpful 전용 토글을 만들지 않는다.
- 발송 파이프라인(KB-468/KB-471)의 대상 판정·알림함·발송 이력·Expo 어댑터(청크·페이싱·일시 실패 재시도)를 그대로 쓴다. 이 기능이 새로 소유하는 것은 **트리거 조건**과 **활동 채널 매핑** 둘뿐이다.
- api 앱에 백그라운드 실행 기반과 커밋 이후 이벤트 처리 선례가 이미 있으므로 새 실행 기반을 만들지 않는다.
- 음식 표시 이름은 음식 도메인의 언어별 이름 해석(없으면 기존 폴백)을 따른다. 기기 두 대가 다른 언어일 때의 음식 이름 언어 처리는 파이프라인의 현재 능력(요청 단위 인자)을 넘지 않는다 — 필요해지면 별도 이슈.
- 영수증 조회·토큰 무효화(KB-473), 리뷰 상세 진입 화면(FE), REVIEW_REMINDER 발송은 범위 밖이다.
- 발송 실패 유실은 감수한다(활동 알림 — 데이터 정합과 무관). 운영 api 가 2대여도 요청 단위 트리거라 중복 실행 방어(잠금)는 필요 없다.
