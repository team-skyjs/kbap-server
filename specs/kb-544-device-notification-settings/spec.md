# Feature Specification: 알림 설정 기기별 분리 — (회원, 기기) 단위 토글, 광고성 동의는 회원 단위 유지

**Feature Branch**: `kb-544-device-notification-settings`

**Created**: 2026-09-11

**Status**: Draft

**Input**: User description: "544 워크트리" — Jira KB-544 「[BE] 알림 설정 기기별 분리 — notification_setting 을 (회원, 기기) 단위로 재정의, 광고성 동의 원장은 회원 단위 유지」(에픽 KB-463 푸시 알림). 결정일 2026-09-11. 선행 KB-543(비회원 경로 제거) 머지 완료, KB-468(발송 파이프라인) 머지 완료.

## 배경

알림 설정은 지금 회원 단위다. 회원당 설정 한 벌(활동 알림·식사시간 알림)이 있고, 발송은 그 한 벌을 회원의 기기 전부에 적용한다. 그런데 알림 토글은 기기에 종속되는 값이다. 한 회원이 기기 두 대를 쓰면 기기마다 다르게 두고 싶은데, 지금은 한 기기에서 끄면 다른 기기도 꺼진다. FE(KB-497)는 기기별 설정 화면을 전제로 진행 중이라 서버 계약이 맞지 않는다.

이 기능은 설정 토글을 **(회원, 기기)** 단위로 나눈다. 광고성 수신 동의 원장은 법적 동의라 사람 단위이므로 **회원 단위를 유지**한다. 회원이 어떤 기기를 갖는지는 기존 기기 대장이 그대로 답한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 기기마다 알림 설정을 따로 켜고 끈다 (Priority: P1)

회원이 기기 A 에서 활동 알림을 끄면 기기 A 만 꺼지고 기기 B 는 그대로다. 설정 화면은 "지금 이 기기" 의 토글을 보여 주고, 처음 여는 기기는 모든 토글이 꺼진 상태로 시작한다.

**Why this priority**: 이 기능의 존재 이유. FE 기기별 설정 화면이 이 계약 위에서 만들어진다.

**Independent Test**: 회원 하나로 기기 두 대를 등록하고 각 기기 헤더로 설정을 다르게 바꾼 뒤 각각 조회하면 서로 다른 값이 돌아온다.

**Acceptance Scenarios**:

1. **Given** 기기 A·B 를 가진 회원, **When** 기기 A 헤더로 활동 알림을 끄면, **Then** 기기 A 조회는 꺼짐, 기기 B 조회는 종전 값이다.
2. **Given** 설정을 한 번도 만지지 않은 기기, **When** 설정을 조회하면, **Then** 활동·식사시간·소식 토글이 전부 꺼짐이다.
3. **Given** 기기 헤더 없이(또는 빈 값·36자 초과) 설정 조회·수정을 호출하면, **Then** 400 과 공통 요청 오류 코드를 받는다.
4. **Given** 구버전 앱(이전 계약 버전 헤더), **When** 설정을 조회·수정하면, **Then** 종전 회원 단위 동작이 그대로 유지된다.

### User Story 2 - 소식 토글과 마케팅 수신 동의는 따로 켜고 끈다 (Priority: P1)

설정 화면은 당근마켓식 두 토글이다. 「K-Bap 소식」 토글은 **이 기기**가 광고성 소식(운영·이벤트·스캔 제안)을 받을지이고 그 아래 「식사 시간 알림」이 붙는다. 「마케팅 수신 동의」 토글은 **회원**의 법적 동의 자체다(캡션에 문구 버전 날짜와 전문 링크). 두 토글은 서로를 바꾸지 않는다 — 소식을 꺼도 동의는 남고, 동의를 철회해도 기기 토글값은 남는다(발송만 멈춘다). 동의가 없으면 앱이 소식·식사시간 토글을 비활성으로 보여 준다.

**Why this priority**: 법적 동의는 사람 단위, 수신 여부는 기기 단위라는 두 층을 한 필드에 묶어 두면 기기 한 대뿐인 대부분의 사용자가 「소식」을 끄는 순간 「동의」도 꺼지는 거짓 상태가 생긴다(FE KB-497 이 이 계약을 기다린다).

**Independent Test**: 동의를 켠 뒤 소식을 껐다 켜도 동의는 그대로이고, 동의를 철회해도 기기 소식 토글값은 그대로다. 소식이 꺼진 기기에서 식사시간을 켜면 거부된다.

**Acceptance Scenarios**:

1. **Given** 동의가 없는 회원, **When** 기기 A 에서 두 문구 버전을 실어 동의를 켜면, **Then** 회원 동의 두 건이 열리고(동의 받은 기기 = A) 응답에 두 동의의 버전·시각이 실린다. 기기 토글값은 바뀌지 않는다.
2. **Given** 동의가 열린 회원, **When** 기기 A 에서 소식을 켜면, **Then** 기기 A 소식만 켜지고 동의 원장은 그대로다. 기기 B 조회는 종전 값이다.
3. **Given** 기기 A 소식이 켜진 회원, **When** 기기 A 소식을 끄면, **Then** 기기 A 만 꺼지고 동의는 열린 채 남는다(기기가 한 대뿐이어도 같다).
4. **Given** 동의가 열리고 기기 A·B 소식이 켜진 회원, **When** 어느 기기에서든 동의를 철회하면, **Then** 열린 동의 두 건이 모두 닫히고(철회 시각 기록) 기기 A·B 의 소식 토글값은 그대로 켜짐으로 조회된다.
5. **Given** 소식이 꺼진 기기, **When** 식사시간 알림을 켜면, **Then** 알림 설정 선행 조건 오류로 거부된다. 소식이 켜진 기기에서는 동의 유무와 무관하게 켜진다.
6. **Given** 동의 문구 버전이 올라간 뒤, **When** 동의를 다시 켜면, **Then** 구 버전 동의는 닫히고 새 버전으로 열린다. 같은 버전으로 다시 켜면 아무것도 바뀌지 않는다.
7. **Given** 동의 켜기 요청에 두 문구 버전 중 하나라도 빠지면, **When** 요청하면, **Then** 400 공통 요청 오류로 거부되고 원장·기기값 모두 바뀌지 않는다.
8. **Given** 동의가 없는 회원, **When** 동의 철회를 보내면, **Then** 아무 변화 없이 성공한다.
9. **Given** 한 요청에 동의 켜기와 소식 켜기와 식사시간 켜기를 함께 실으면, **When** 요청하면, **Then** 동의 → 소식 → 식사시간 순으로 반영돼 셋 다 켜진다.

### User Story 3 - 발송은 기기 단위로 대상을 고른다 (Priority: P1)

발송 파이프라인이 "이 알림을 받을 기기" 를 고를 때 기기별 설정을 본다. 회원에 연결된 기기 중 해당 토글이 켜진 기기만 대상이고, 광고성 알림은 여기에 회원의 열린 동의가 요구 문구 버전 이상이어야 한다. 설정이 없는 기기는 전부 꺼진 것으로 보아 대상이 아니다.

**Why this priority**: 설정을 기기별로 나눠도 발송이 회원 단위로 보면 의미가 없다. KB-468 이 이미 머지돼 있어 대상 조회 규칙을 여기서 맞춘다.

**Independent Test**: 기기 A 만 활동 알림이 켜진 회원에게 활동 알림을 보내면 기기 A 에만 발송 이력이 생긴다. 동의 버전이 요구치보다 낮은 회원의 기기는 광고성 알림 대상에서 빠진다.

**Acceptance Scenarios**:

1. **Given** 기기 A 는 활동 켜짐·기기 B 는 꺼짐인 회원, **When** 활동 알림을 발송하면, **Then** 기기 A 에만 발송 이력이 생긴다.
2. **Given** 소식 토글은 켜졌지만 동의 버전이 요구치 미만인 회원, **When** 광고성 알림을 발송하면, **Then** 그 회원의 기기는 대상에서 빠진다.
3. **Given** 설정 행이 없는 기기, **When** 어떤 유형의 알림을 발송해도, **Then** 대상이 아니다.

---

### User Story 4 - 로그아웃·탈퇴 시 기기 설정의 운명이 정해진다 (Priority: P2)

로그아웃하면 기기 연결만 풀리고 기기별 설정은 남아 다시 로그인하면 그대로 복원된다. 탈퇴하면 기기 연결이 전부 풀리고 열린 동의가 닫히며 기기별 설정도 지워진다. 토큰 등록만으로는 설정이 생기지 않는다.

**Why this priority**: 설정이 기기에 붙으면서 새로 생기는 생명주기 규칙. 없으면 재로그인 때 설정이 사라지거나 탈퇴 회원의 설정이 남는다.

**Independent Test**: 설정을 바꾼 뒤 로그아웃·재로그인하면 값이 유지되고, 탈퇴하면 조회할 수 없다.

**Acceptance Scenarios**:

1. **Given** 기기 A 설정을 바꾼 회원, **When** 로그아웃 후 같은 기기로 재로그인하면, **Then** 설정이 그대로다.
2. **Given** 기기별 설정과 열린 동의를 가진 회원, **When** 탈퇴하면, **Then** 기기 연결이 전부 풀리고 동의가 닫히며 기기별 설정이 더 이상 조회되지 않는다.
3. **Given** 새 기기, **When** 토큰만 등록하면, **Then** 설정 행이 생기지 않는다(조회 시 전부 꺼짐).

---

### Edge Cases

- 기존 회원 단위 설정 행(기기 식별자가 없는 행)은 지우지 않고 남긴다. 새 계약은 그 행을 읽지 않으며, 구버전 앱 계약만 그 행을 계속 쓴다.
- 같은 (회원, 기기) 조합에 행이 두 개 생기는 경합은 고유 제약으로 막는다. 첫 조회·수정 시 기본값 행을 만드는 경로가 동시에 두 번 들어와도 한 행만 남아야 한다.
- 구 고유 제약(회원당 한 행)은 이번에 제거하지 않는다. 블루/그린 배포 중 구 코드가 신 스키마 위에서 돌기 때문이며, 제거는 후속 릴리스에서 한다. 따라서 이번 릴리스 동안 신 코드는 회원당 기기별 행을 여러 개 만들 수 있어야 하므로 스키마 확장 방식이 이를 허용해야 한다.
- 동의 문구 버전은 두 종류(개인정보·수신) 모두 필수다. 하나만 보내면 동의 켜기가 거부된다(현행 규칙 유지, 대상 필드만 소식 켜기 → 동의 켜기로 이동).
- 동의 없이 기기 소식 토글을 켜는 요청은 거부하지 않고 저장한다. 앱이 동의 없는 상태에서는 토글을 비활성으로 그리고, 발송은 어차피 회원 동의가 유효해야 하므로 저장값만으로는 광고가 나가지 않는다.
- 동의 철회는 회원 단위 행위라 어느 기기에서 보내든 회원의 열린 동의 전부를 닫는다. 기기 토글값은 건드리지 않는다.
- "마지막 기기가 꺼지면 동의를 닫는다" 규칙은 없다(2026-09-11 FE 검토로 폐기). 동의는 명시적 철회로만 닫힌다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 알림 설정 토글(활동·식사시간·소식)을 (회원, 기기) 단위로 저장하고 조회해야 한다.
- **FR-002**: 시스템은 설정이 없는 기기를 모든 토글 꺼짐으로 취급해야 한다.
- **FR-003**: 새 계약 버전의 설정 조회·수정은 기기 식별 헤더를 필수로 하며, 누락·공백·36자 초과는 400 공통 요청 오류로 거부해야 한다.
- **FR-004**: 새 계약의 조회 응답은 현행 형태(활동, 소식{사용 여부, 식사시간, 개인정보 동의, 수신 동의})를 유지한다. 소식 사용 여부는 **이 기기의 저장값 그대로**이고, 식사시간은 이 기기 소식이 꺼져 있으면 저장값과 무관하게 꺼짐이며, 두 동의 항목은 회원의 종류별 열린 최신 동의(없으면 없음)다. 동의 상태는 두 동의 항목의 유무로 읽는다.
- **FR-005**: 구 계약 버전의 설정 조회·수정은 종전 회원 단위 동작을 유지해야 한다. 새 계약은 같은 경로에서 상위 버전 헤더로 구분한다.
- **FR-006**: 새 계약의 수정 요청은 소식 그룹 안에서 **기기 수신(소식 사용 여부)** 과 **회원 동의(동의 켜기/끄기)** 를 별개 항목으로 받는다. 동의 켜기는 두 문구 버전이 필수이며 회원 동의 원장에 열린 동의를 보장하고(같은 버전이면 무변화, 다른 버전이면 구 버전을 닫고 새 버전을 연다), 기기 토글값은 바꾸지 않는다.
- **FR-007**: 동의 끄기는 회원의 열린 동의를 전부 닫고(철회 시각 기록) 기기 토글값은 바꾸지 않는다. 소식 사용 여부 켜기/끄기는 이 기기 저장값만 바꾸고 동의 원장을 건드리지 않는다. 처리 순서는 활동 → 동의 → 소식 사용 여부 → 식사시간이다.
- **FR-008**: 식사시간 켜기는 이 기기의 소식이 켜져 있을 때만(같은 요청에서 켜진 경우 포함) 허용하며, 아니면 알림 설정 선행 조건 오류로 거부해야 한다. 회원 동의 유무는 조건이 아니다(발송 단계가 검사한다).
- **FR-009**: 발송 대상 조회는 기기 단위로 판정해야 한다. 회원에 연결된 기기 중 해당 토글이 켜진 기기만 대상이고, 광고성 유형은 회원의 열린 동의 버전이 요구치 이상이어야 한다.
- **FR-010**: 로그아웃은 기기 연결만 풀고 기기별 설정을 보존해야 한다. 탈퇴는 기기 연결 전체 해제·열린 동의 닫기에 더해 기기별 설정을 소프트 삭제해야 한다.
- **FR-011**: 토큰 등록은 설정 행을 만들지 않아야 한다.
- **FR-012**: 저장소 변경은 확장만 한다(기기 식별자·소식 컬럼 추가, (회원, 기기) 고유 제약 추가). 구 고유 제약 제거는 하지 않고 후속 티켓으로 남긴다.
- **FR-013**: 기존 회원 단위 설정 행은 삭제·이관하지 않는다.
- **FR-014**: API 문서는 새 계약(헤더 필수·응답 계산 규칙)을 반영하고, FE(KB-497)에 계약 버전 번호를 공유해야 한다. 지식 위키의 푸시 동의 문서에 기기별 설정 절을 추가한다.

### Key Entities *(include if data involves)*

- **기기별 알림 설정(notification_setting)**: (회원, 기기) 당 한 행. 활동·식사시간·소식 세 토글, 기본값 전부 꺼짐. 기기 식별자가 없는 기존 행은 구 계약 전용.
- **광고성 수신 동의(notification_consent)**: 회원 단위 원장. 동의 1회 = 1행, 문구 버전·동의 시각·철회 시각. 기기 설정과 독립.
- **기기(notification_device)**: 회원의 기기 목록. 설정 행의 기기 식별자는 이 대장의 설치 id 와 같은 값이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 한 회원의 기기 두 대에 서로 다른 토글을 저장하고 각각 조회했을 때 100% 자기 값을 돌려준다.
- **SC-002**: 소식 토글을 아무리 껐다 켜도 동의 원장은 0건 변경이고, 동의 철회는 기기 토글값을 0건 변경한다. 동의는 명시적 철회 요청으로만 닫힌다.
- **SC-003**: 활동 알림 발송 시 토글이 켜진 기기에만 발송 이력이 생기고, 꺼진 기기·설정 없는 기기에는 0건이다.
- **SC-004**: 구 계약 버전 헤더로 호출하는 기존 설정 테스트가 변경 없이 전부 통과한다.
- **SC-005**: 마이그레이션 1건으로 배포되며 구 코드와 신 코드가 같은 스키마 위에서 공존한다.
- **SC-006**: 기존 설정·알림함·토큰·발송 회귀 테스트가 전부 통과한다.

## Assumptions

- 세 토글의 기본값은 전부 꺼짐이다(KB-466 결정 유지 — 모바일 알림 정책상 꺼짐으로 시작). FE 가 권한 허용 시 활동을 켜서 저장하는 현행 흐름과 맞는다.
- 새 계약의 버전 번호는 앱 릴리스 마커 규약대로 다음 릴리스 번호를 쓴다. 현재 가장 높은 마커가 2.0 이므로 plan 단계에서 FE 와 맞춰 확정한다.
- 기기 식별 헤더 값은 토큰 등록에 쓰는 설치 id 와 같은 값이다. 헤더 검증 규칙(비어 있지 않음·36자 이하)은 현행 토큰 등록의 규칙을 그대로 쓴다.
- 발송 파이프라인(KB-468, PR #259) 은 이미 머지돼 있다. 이 기능은 그 파이프라인의 대상 조회 규칙을 기기 단위로 바꾸며, 파이프라인의 나머지(렌더·전송·티켓)는 손대지 않는다.
- 발송 조건의 "회원 동의 유효" 는 개인정보·수신 동의가 모두 열려 있고 각 버전이 현재 요구 버전 이상임을 뜻한다(KB-468 규칙 유지). 조회 응답은 이 판정을 하지 않는다 — 앱이 두 동의 항목의 유무(필요하면 버전)로 동의 상태를 그린다.
- 새 계약의 수정 요청 형태는 소식 그룹에 동의 켜기/끄기 항목이 추가된 것 외에 구 계약과 같다. 구 계약의 요청·응답은 바뀌지 않는다.
- 광고성 알림 유형은 SCAN_SUGGESTION·NEWS·MEAL_TIME 이고, 정보성은 HELPFUL·REVIEW_REMINDER 다(KB-468 — NOTICE 는 NEWS 로 대체됨).
