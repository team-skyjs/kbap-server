# Feature Specification: 리뷰 작성 시 태그 가능한 음식 목록 조회 API

**Feature Branch**: `kb-367-review-taggable-foods`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "KB-367 — [BE] 리뷰 작성 시 태그 가능한 음식 목록 조회 API — 본인 스캔 이력 한정"

## 맥락

- 8/15 기획 멘토링 결정: **리뷰는 본인이 실제로 스캔한 메뉴에 한해서만 작성**할 수 있다(미구현). 이 결정의 첫 단계로, 리뷰 작성 화면의 음식 태그 후보를 본인 스캔 이력으로 좁혀 내려주는 조회 API 를 만든다.
- 현재 리뷰 작성 화면은 전체 음식 목록·검색 API 를 그대로 사용해 스캔 이력과 무관하게 아무 음식이나 태그할 수 있다.
- 서비스에는 이미 "회원의 최근 스캔 음식" 개념이 존재한다 — 홈 화면의 recentScans 섹션이 같은 데이터(스캔 이력 기반, 음식 중복 제거, 최신 스캔순, 조회 가능한 READY 음식만)를 노출한다. 이 API 는 그 개념을 리뷰 작성 플로우용 독립 목록으로 제공하는 것이다.
- **범위 밖**: 리뷰 작성(POST /api/reviews) 시 서버가 스캔 이력을 검증하는 강제는 별도 태스크로 다룬다 — 이 API 가 열려도 작성 자체는 종전대로 동작한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 리뷰 작성자가 자기 스캔 음식 중에서 태그를 고른다 (Priority: P1)

회원이 리뷰 작성 화면에서 음식 태그를 고를 때, 전체 음식이 아니라 **본인이 스캔했던 음식 목록**을 받는다. 같은 음식을 여러 번 스캔했어도 한 번만 나오고, 최근에 스캔한 음식이 앞에 온다.

**Why this priority**: 이 기능의 전부 — 스캔 기반 리뷰 제한(8/15 결정)의 클라이언트 전제 조건.

**Independent Test**: 음식 A·B 를 스캔한 회원으로 호출 → A·B 만, 최신 스캔순으로 반환. 스캔 이력 없는 회원 → 빈 목록.

**Acceptance Scenarios**:

1. **Given** 음식 A→B→A 순으로 스캔한 회원, **When** 태그 가능 음식 목록을 조회하면, **Then** [A, B] 순(마지막 스캔 시점 내림차순)으로 중복 없이 내려간다.
2. **Given** 스캔 이력이 없는 회원, **When** 조회하면, **Then** 빈 목록이 내려간다(오류 아님).
3. **Given** 스캔했지만 조회 불가 상태가 된 음식(삭제·비공개), **When** 조회하면, **Then** 그 음식은 목록에서 제외된다.
4. **Given** 스캔 항목이 음식 마스터에 매칭되지 않은 경우(음식 미등록 메뉴), **When** 조회하면, **Then** 해당 항목은 목록에 나타나지 않는다 — 태그는 등록된 음식만 가능하다.
5. **Given** 비회원(인증 없음), **When** 호출하면, **Then** 401 로 거절된다 — 스캔 이력은 회원 개념이다.
6. **Given** 스캔 음식이 21개 이상인 회원, **When** 조회하면, **Then** 매칭 전체가 최신 스캔순으로 한 번에 내려간다(페이징 없음, 2026-08-19 개정).
7. **Given** 음식 A(김치찌개)·B(비빔밥)를 스캔한 회원, **When** 검색어 "김치"로 조회하면, **Then** A 만 내려간다 — 스캔 안 한 음식은 검색어가 일치해도 나오지 않는다.

---

### Edge Cases

- 같은 음식을 오늘 또 스캔하면? — 정렬 기준이 "마지막 스캔 시점"이므로 목록 맨 앞으로 올라온다.
- 목록 항목 형태는? — 기존 음식 목록 API 항목과 동일한 요약 형태(음식명·이미지·평점 요약·북마크 여부)로 내려 클라이언트가 같은 UI 를 재사용한다.
- 페이징·검색은? — **페이징 없이 매칭 전체를 한 번에 반환**한다(2026-08-19 재개정 — 검색어 필수로 결과 모수가 작고, 스캔 이력 집계 특성상 커서가 DB 비용을 줄이지 못함). **검색어는 필수**다(2026-08-19 개정 — 이 기능은 검색 전용이고, 검색어 입력 전 초기 화면은 스캔 내역 조회가 담당한다). 매칭 규칙은 기존 음식 검색과 동일(한국어명 또는 요청 언어 번역명 부분 일치, 대소문자 무시).
- 표시 언어는? — 기존 음식 목록과 동일하게 요청 언어(lang) 필수, 규칙 동일(누락 400·미지원 코드 en 폴백).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 회원은 본인 스캔 이력에 매칭된 음식 목록을 조회할 수 있어야 한다. 같은 음식은 한 번만 나타나며, 마지막 스캔 시점 내림차순으로 정렬된다.
- **FR-002**: 조회 불가 음식(삭제·비공개)과 음식 마스터 미매칭 스캔 항목은 목록에서 제외된다.
- **FR-003**: 스캔 이력이 없는 회원에게는 빈 목록을 정상 응답한다.
- **FR-004**: 이 API 는 회원 전용이다 — 인증 없는 호출은 401 로 거절된다.
- **FR-005**: 목록 항목은 기존 음식 목록 조회와 동일한 요약 형태로 내려간다(클라이언트 UI 재사용).
- **FR-006**: 페이징하지 않는다 — 매칭 전체를 한 번에 반환하며 응답 봉투는 기존 목록과 동일(hasNext 항상 false·nextCursor 항상 null).
- **FR-007**: 검색어(음식명)는 필수다(누락·빈/공백 400) — 매칭 규칙은 기존 음식 검색과 동일하며, 결과는 본인 스캔 음식 범위를 벗어나지 않는다. 매칭 없음은 빈 목록이다. 검색어 없는 초기 화면은 이 기능이 아니라 스캔 내역 조회가 담당한다.
- **FR-008**: 기존 음식 목록·검색 API 와 리뷰 작성 API 의 동작은 변경하지 않는다 — 이 기능은 새 조회 경로 추가뿐이다.

### Key Entities

- **스캔 이력**: 회원이 스캔한 메뉴 항목(음식 매칭 여부 포함) — 이 목록의 원천. 이 기능은 스캔 이력을 읽기만 하고 바꾸지 않는다.
- **태그 가능 음식 목록**: 스캔 이력에서 파생된 회원별 음식 요약 목록(중복 제거·최신 스캔순).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 리뷰 작성 화면이 이 API 만으로 태그 후보를 구성할 수 있다 — 스캔한 음식 전부가 나오고, 스캔 안 한 음식은 하나도 나오지 않는다.
- **SC-002**: 스캔 이력 없는 회원·조회 불가 음식 혼재 등 경계 상황에서 오류 없이 동작한다(빈 목록·제외 처리).
- **SC-003**: 기존 화면(홈 recentScans·음식 목록·리뷰 작성)의 동작은 회귀 없이 유지된다.

## Assumptions

- 태그 후보의 원천은 스캔 이력뿐이다 — 북마크·리뷰 이력 등 다른 원천은 포함하지 않는다(8/15 결정 문언 그대로).
- 항목 형태는 기존 음식 요약(FoodSummaryResponse 상당)을 재사용한다 — 새 응답 모양을 만들지 않는다.
- 홈 recentScans 와 같은 데이터 개념을 쓰므로 정렬·제외 규칙도 동일하게 맞춘다(불일치가 사용자에게 혼란을 준다).
- 리뷰 작성 시 스캔 이력 강제 검증, 스캔 크레딧(3회+리뷰 해제) 연동은 범위 밖 — 별도 태스크.
