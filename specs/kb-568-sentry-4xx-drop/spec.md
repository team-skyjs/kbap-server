# Feature Specification: Sentry 4xx·클라이언트 끊김 이벤트 미전송

**Feature Branch**: `kb-568-sentry-4xx-drop`

**Created**: 2026-09-15

**Status**: Draft

**Input**: User description: "Sentry 에 보고되는 예외에서 4xx 와 클라이언트 연결 끊김을 걸러내고 5xx·예상 밖 예외만 보고한다. 현재 api 는 Sentry 예외 해석 순서를 최솟값으로 두어 전역 예외 핸들러가 400 으로 정상 응답한 요청까지 이벤트가 되고, 제외 목록에는 NoResourceFoundException 하나뿐이다. BusinessException 은 ErrorCode.status 가 4xx 면 미전송, 요청 검증·API 버전 헤더 누락/미지원·타입 불일치 같은 프레임워크 4xx 와 Broken pipe 류 끊김도 미전송, 5xx 는 그대로 전송. batch 는 같은 기준 적용 여부를 정한다. 착수 시 PR #257 을 닫은 사유를 확인해 범위를 맞춘다. 상세 배경·DoD 는 Jira KB-568." — Jira KB-568 「[BE] Sentry 4xx·클라이언트 끊김 이벤트 미전송」(레이블 BE).

## 배경

KB-508 은 "4xx·5xx 를 가리지 않고 전부 수집" 을 정책으로 Sentry 를 붙였다. 켜진 직후 dev 에서 잡힌 이벤트는 봇 스캔 404·정상 토큰 갱신 흐름의 401·앱 소켓 끊김(Broken pipe) 뿐이었고, 2026-09-15 에도 잘못된 API 버전 헤더 400·필수 파라미터 누락 400·api-docs 호출 중단 Broken pipe 가 Slack 알림으로 왔다. 전부 내부 테스트 요청이었고 사용자 영향은 없었다.

Sentry 무료 플랜은 에러 5,000건/월이고 초과분은 다음 주기까지 버려진다. 최근 30일 실측은 월 600건 수준이지만 prod api·batch 까지 연결되고 봇 스캔·앱 재시도가 들어오면 의미 없는 4xx 가 한도를 먼저 채워 정작 prod 5xx 가 버려진다. 알림 채널에 노이즈가 쌓이면 대응도 둔감해진다. 클라이언트 잘못으로 나는 4xx 는 서버에서 조치할 것이 없고, 4xx 급증은 Sentry 가 아니라 서버 로그·요청 지표로 본다.

**선행 PR 의 결말(DoD 1 확인 결과)**: 같은 방향의 PR #257(4xx·클라이언트 끊김 drop)은 2026-09-09 에 "KB-508 의 4xx 수집 정책을 뒤집는다" 는 이유로 닫혔고, 범위를 좁힌 PR #258(매핑되지 않은 경로의 404 한 종류만 SDK 설정으로 제외, 2026-09-10 머지)로 대체됐다. 이번 태스크는 **그 정책 자체를 "5xx·예상 밖 예외만 수집" 으로 바꾸는 결정**이며, #257 이 이미 정리한 판정 경계(앱 에러 코드 4xx·프레임워크 4xx·인바운드 끊김은 미전송, 5xx·낙관적 락 충돌은 전송, 아웃바운드 I/O 실패는 장애로 유지)를 그대로 채택한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 클라이언트 잘못으로 난 4xx 는 Sentry 에 남지 않는다 (Priority: P1)

api 가 요청을 4xx 로 정상 응답한 경우 — 앱 에러 코드가 붙은 실패(없는 리소스·권한 없음·중복 신고 같은 정상 충돌 등), 요청 검증 실패, 필수 파라미터 누락, 본문 파싱 실패, 타입 불일치, API 버전 헤더 누락·미지원, 허용되지 않은 메서드·미디어 타입 — 그 예외는 Sentry 이벤트가 되지 않는다. 서버 로그에는 종전과 같이 남아 필요하면 조사할 수 있다.

**Why this priority**: 이벤트 한도와 알림 채널을 지키는 핵심. 이게 되면 Slack 알림은 서버가 조치할 것이 있는 오류만 뜬다.

**Independent Test**: dev 에 배포한 뒤 4xx 를 내는 요청 종류별로 한 번씩 보내면 Sentry 에 새 이벤트가 0건이고, 같은 요청의 4xx 응답과 서버 로그 한 줄은 그대로 있다.

**Acceptance Scenarios**:

1. **Given** dev 의 api, **When** 앱 에러 코드가 붙는 4xx 요청(없는 음식 id·게스트의 회원 전용 호출·중복 신고)을 보내면, **Then** HTTP 응답은 종전과 같고 Sentry 이벤트는 생기지 않는다.
2. **Given** dev 의 api, **When** 프레임워크가 걸러내는 4xx 요청(잘못된 본문·필수 파라미터 누락·타입 불일치·`X-API-Version` 누락 또는 미지원·허용되지 않은 메서드)을 보내면, **Then** 응답은 400/405 등 종전과 같고 Sentry 이벤트는 생기지 않는다.
3. **Given** 위 어느 4xx 요청이든, **When** 서버 로그를 보면, **Then** 요청 id·경로·에러 코드가 담긴 실패 로그 한 줄이 종전과 같이 남아 있다.
4. **Given** 매핑되지 않은 경로 404(봇 스캔), **When** 요청을 보내면, **Then** 종전(PR #258)대로 이벤트가 생기지 않는다.

---

### User Story 2 - 5xx 와 예상 밖 예외는 종전대로 Sentry 에 남는다 (Priority: P1)

서버 원인의 오류 — 처리되지 않은 예외, 앱 에러 코드 중 5xx 상태를 가진 실패, 낙관적 락 충돌(409 로 응답하지만 서버 측 경합 신호), DB·스토리지·LLM 같은 외부 시스템과의 I/O 실패 — 는 종전과 같은 태그(환경·배포·서비스·인스턴스·요청 id·회원 id·상태·에러 코드)와 그룹핑으로 Sentry 이벤트가 된다. 4xx 를 거르느라 5xx 가 함께 사라지는 일이 없어야 한다.

**Why this priority**: 이 기능의 존재 이유가 "prod 5xx 가 한도에 밀려 버려지지 않게" 이므로, 5xx 수집 보존은 4xx 제외와 같은 무게다.

**Independent Test**: dev 에서 5xx 를 내는 요청과 낙관적 락 충돌을 유발하면 각각 종전과 동일한 태그가 붙은 이벤트가 생긴다. 외부 연결이 끊긴 아웃바운드 I/O 실패도 500 으로 이벤트가 된다.

**Acceptance Scenarios**:

1. **Given** dev 의 api, **When** 처리되지 않은 예외로 500 이 나는 요청을 보내면, **Then** status=500·requestId·environment·release·service=api 태그가 붙은 이벤트가 종전대로 생긴다.
2. **Given** 5xx 상태를 가진 앱 에러 코드의 실패, **When** 그 요청을 보내면, **Then** status·error.code 태그와 에러 코드 단위 그룹핑이 종전대로 적용된 이벤트가 생긴다.
3. **Given** 낙관적 락 충돌(직접 또는 원인 체인 안), **When** 409 로 응답하면, **Then** status=409 이벤트가 종전대로 생긴다.
4. **Given** 외부 시스템 호출 중 연결이 끊겨 "Broken pipe"·"Connection reset" 메시지의 I/O 예외가 난 요청, **When** 500 으로 응답하면, **Then** 이벤트가 생긴다(인바운드 끊김으로 오인해 버리지 않는다).
5. **Given** 예외 없이 코드가 ERROR 로그만 남긴 경로, **When** 그 경로를 타면, **Then** 종전대로 메시지 이벤트가 생긴다.

---

### User Story 3 - 클라이언트가 연결을 끊어 난 예외는 Sentry 에 남지 않는다 (Priority: P2)

응답을 쓰는 도중 요청한 쪽이 먼저 연결을 끊어(앱 크래시·브라우저 탭 닫힘·api-docs 로드 중단) 서버가 응답 스트림에 쓰지 못한 경우, 그 예외는 Sentry 이벤트가 되지 않는다. 서버가 조치할 원인이 없기 때문이다.

**Why this priority**: 실측 노이즈 4건 중 1건 유형. 4xx 보다 빈도는 낮지만 큰 응답(문서·이미지)마다 반복된다.

**Independent Test**: dev 에서 큰 응답을 요청하고 즉시 연결을 끊으면 Sentry 이벤트가 0건이다.

**Acceptance Scenarios**:

1. **Given** 응답 전송 중인 요청, **When** 클라이언트가 연결을 끊어 서버가 응답 스트림에 쓰지 못하면, **Then** Sentry 이벤트가 생기지 않는다.
2. **Given** 같은 상황, **When** 서버 로그를 보면, **Then** 종전과 같은 로그가 남는다(로그 수위는 바꾸지 않는다).

---

### User Story 4 - 수집 계약이 문서에 반영되고 batch 는 기준이 정해진다 (Priority: P3)

운영자가 관측 문서를 열면 "무엇이 수집되고 무엇이 수집되지 않는지" 가 이번 정책으로 갱신되어 있다. batch 앱에 같은 기준을 적용할지 결정이 기록된다.

**Why this priority**: 정책 변경은 문서가 없으면 다음 사람이 "왜 4xx 가 안 보이지" 로 되묻는다. 코드보다 문서가 계약이다.

**Independent Test**: 관측 문서의 수집 계약 표·"수집되지 않는 것" 절이 이번 정책과 일치하고, batch 결정이 한 줄로 적혀 있다.

**Acceptance Scenarios**:

1. **Given** 관측 문서, **When** 수집 정책 절을 읽으면, **Then** "5xx·낙관적 락 409·예상 밖 예외·ERROR 로그만 수집, 4xx·인바운드 끊김 미수집" 으로 갱신되어 있다.
2. **Given** 관측 문서, **When** batch 항목을 읽으면, **Then** batch 는 HTTP 4xx 개념이 없어 변경 없이 종전 기준(ERROR 로그·잡 실패)을 유지한다는 결정이 적혀 있다.

---

### Edge Cases

- **앱 에러 코드 409(중복 신고 등 정상 충돌) vs 낙관적 락 409**: 둘 다 409 로 응답하지만 전자는 클라이언트 잘못이라 미전송, 후자는 서버 경합 신호라 전송. 상태 코드가 아니라 원인으로 가른다.
- **인바운드 끊김 vs 아웃바운드 I/O 실패**: "Broken pipe"·"Connection reset" 메시지는 양쪽에서 같이 난다. 메시지 문자열로 판정하면 DB·S3·LLM 장애를 삼킨다 — 응답 스트림에서만 나는 예외 종류로 판정한다(PR #257 Codex P1).
- **4xx 이면서 원인 체인에 낙관적 락 충돌이 있는 경우**: 실제로는 발생하지 않는 조합(핸들러가 락 충돌을 먼저 409 로 잡는다). 발생하면 전송 쪽을 택한다(놓치는 것보다 한 건 더 받는 게 낫다).
- **필터 단계에서 예외 없이 응답을 쓰는 401(JWT)·400(`X-API-Version` 폴백)**: 종전에도 수집되지 않았고 그대로다.
- **ERROR 로그 경로로 들어온 4xx 예외**: 4xx 를 핸들러가 ERROR 로 로깅하면 로그 어펜더 경로로 이벤트가 생길 수 있다. 판정은 예외를 보고 하므로 어느 경로로 오든 같은 결과여야 한다. 현재 핸들러는 4xx 를 WARN 이하로 남기므로 해당 없음을 확인한다.
- **Sentry 서비스 불가·전송 실패**: 종전과 같이 앱 요청 처리에 영향 없음.
- **되돌리기**: 정책을 되돌려야 하면 판정 로직 한 곳만 제거하면 KB-508 원안으로 돌아간다. 4xx 를 "샘플링" 으로 일부만 받는 중간안은 이번 범위 밖.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: api 에서 앱 에러 코드가 붙은 실패 중 상태 코드가 4xx 인 것은 Sentry 이벤트로 전송하지 않는다. 5xx 상태의 앱 에러 코드는 종전대로 전송한다.
- **FR-002**: api 에서 프레임워크가 4xx 로 응답하는 예외 — 요청 검증 실패·본문 파싱 실패·파라미터 타입 불일치·필수 파라미터 누락·API 버전 헤더 누락 또는 미지원·허용되지 않은 메서드/미디어 타입 등 상태 코드 4xx 로 응답되는 모든 예외 — 를 Sentry 이벤트로 전송하지 않는다.
- **FR-003**: 클라이언트가 연결을 끊어 서버가 응답 스트림에 쓰지 못해 난 예외는(원인 체인 안에 있는 경우 포함) Sentry 이벤트로 전송하지 않는다.
- **FR-004**: FR-003 의 판정은 예외 메시지 문자열("Broken pipe"·"Connection reset")로 하지 않는다. 외부 시스템(DB·스토리지·LLM 등) 호출 중 난 I/O 실패는 종전대로 500 이벤트로 전송한다.
- **FR-005**: 5xx 로 응답되는 예외, 낙관적 락 충돌(409), 예외 없는 ERROR 로그는 종전과 같은 태그·핑거프린트로 전송한다. 이번 변경으로 태그 규약(`http.status`·`error.code`·`requestId`·`memberId`·헤더 마스킹·쿼리 마스킹)이 달라지지 않는다.
- **FR-006**: 미전송 대상이 된 요청의 HTTP 응답(상태·봉투·에러 코드)과 서버 로그는 이번 변경 전과 동일하다. 로그 수위·로그 내용을 바꾸지 않는다.
- **FR-007**: 매핑되지 않은 경로의 404 제외(PR #258)는 그대로 유지한다.
- **FR-008**: batch 앱은 변경하지 않는다 — HTTP 요청·4xx 개념이 없고 수집원이 ERROR 로그·잡 실패뿐이라 이번 기준의 대상이 없다. 이 결정을 관측 문서에 기록한다.
- **FR-009**: 관측 문서의 수집 계약(수집 대상·미수집 대상·노이즈 조정 안내)을 이번 정책으로 갱신한다.
- **FR-010**: 판정 경계의 검증은 자동 테스트가 아니라 로컬 가짜 DSN 의 SDK drop 로그와 dev 콘솔 실이벤트로 한다 — 4xx 앱 에러 코드 미전송·5xx 앱 에러 코드 전송·프레임워크 4xx 미전송·500 전송·낙관적 락 409 전송·앱 에러 코드 409 미전송·인바운드 끊김 미전송·아웃바운드 I/O 실패 전송·예외 없는 로그 이벤트 통과. (사용자 결정 2026-09-09 KB-508·2026-09-15 KB-568 재확인: Sentry 관측 부품에는 테스트 코드를 두지 않는다.)

### Key Entities

- **Sentry 이벤트**: 하나의 예외 또는 ERROR 로그에서 만들어지는 보고 단위. 전송 직전 판정을 거쳐 전송되거나 버려진다. 속성: 원인 예외, 응답 상태, 앱 에러 코드, 요청 맥락 태그.
- **수집 정책**: "서버가 조치할 것이 있는 오류만" — 5xx·낙관적 락 충돌·예상 밖 예외·ERROR 로그는 전송, 4xx·인바운드 끊김·매핑 없는 404 는 미전송.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: dev 배포 후 4xx 응답 요청 종류별(앱 에러 코드·검증 실패·파라미터 누락·타입 불일치·버전 헤더 누락/미지원·허용되지 않은 메서드) 각 1건씩 보내도 Sentry 신규 이벤트가 0건이다.
- **SC-002**: 같은 배포에서 500 요청·낙관적 락 충돌 각 1건은 이벤트가 각 1건씩 생기고, 태그 6종(environment·release·service·requestId·http.status·error.code 해당 시)이 종전과 같다.
- **SC-003**: 큰 응답 요청 중 연결을 끊는 시도 5회에 Sentry 이벤트가 0건이다.
- **SC-004**: 배포 후 7일간 dev Sentry 신규 이벤트 중 `http.status` 가 4로 시작하는 이벤트가 0건이다.
- **SC-005**: 미전송 대상 요청 각각에 대해 서버 로그의 실패 라인(요청 id·경로·에러 코드)이 변경 전과 동일하게 남는다.
- **SC-006**: 기존 api 테스트 전체가 그대로 통과한다(테스트 추가 없음).

## Assumptions

- **정책 전환은 결정 사항이다**: KB-508 의 "4xx 전부 수집" 은 Sentry 한도(5,000건/월)·알림 노이즈 근거로 KB-568 에서 "5xx·예상 밖 예외만 수집" 으로 바꾼다. PR #257 을 닫은 사유(정책 충돌)는 이번 결정으로 해소된다. 판정 경계는 #257 이 정리한 것을 그대로 쓴다.
- **api 의 예외 해석 순서 설정(최솟값)은 손대지 않는다**: 전역 예외 핸들러가 모든 예외를 삼키므로 이 설정이 있어야 5xx 가 이벤트가 된다. 4xx 를 거르는 위치는 이벤트가 만들어진 뒤 전송 직전이다.
- **앱 에러 코드 409 는 4xx 로 취급해 미전송**: Jira DoD 의 "4xx 미전송" 을 문자 그대로 적용한다. 낙관적 락 409 만 서버 경합 신호로 전송한다.
- **인바운드 끊김 판정은 예외 종류로 한다**: 서블릿 응답 스트림에서만 나는 끊김 예외(및 비동기 요청의 응답 불가 예외)를 원인 체인에서 찾는다. 메시지 매칭은 하지 않는다.
- **batch 는 변경 없음**: HTTP 경계가 없어 4xx·끊김이 존재하지 않는다. 결정만 문서에 남긴다.
- **알림 규칙(Slack)은 범위 밖**: 이벤트가 안 생기면 알림도 안 온다. 콘솔 규칙 조정은 불필요.
- **4xx 급증 감시는 Sentry 밖**: 서버 로그·요청 지표(Grafana `http.server.requests`)로 본다. 이번 변경으로 4xx 관측 수단을 새로 만들지 않는다.
- **선행 산출물 재사용**: PR #257 의 판정 로직·문서 변경은 닫힌 브랜치에 남아 있어 참고할 수 있다(테스트 파일은 가져오지 않는다). 다만 머지 기준은 현재 develop 이다.
