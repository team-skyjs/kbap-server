# Feature Specification: 리뷰 목록 조회 정렬·필터 추가

**Feature Branch**: `kb-338-review-sort-filter`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "KB-338 — 리뷰 전체 목록 조회 정렬·필터 추가 (8/15 기획). 정렬 5종(최신순·평점 높은 순·평점 낮은 순·음식 리뷰 수 많은 순·helpful 내림차순) + 별점 구간 필터. 워크트리 진행."

## 맥락 (Jira KB-338·agent-hub)

- 8/15 기획 멘토링 결정: 리뷰 목록에 정렬 5종과 별점 필터를 추가한다.
- 현재 `GET /api/reviews` 는 정렬이 최신순 하나로 고정, 필터는 음식(foodId)·작성자 국적(countryCode) 둘뿐이다.
- KB-348 로 이 목록은 비회원에게도 열렸다 — 정렬·필터도 회원·비회원 동일하게 동작해야 한다.
- Jira 본문이 지적하는 구조 제약 두 가지: (1) 커서 페이징이 최신순 전제(id 기준)라 정렬 기준이 바뀌면 커서 전략도 그 기준을 따라야 한다, (2) helpful(좋아요) 수는 목록 조회 후 별도 집계 구조라 이 값으로 정렬하려면 집계가 조회 안으로 들어가야 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 원하는 기준으로 리뷰를 정렬한다 (Priority: P1)

사용자(회원·비회원)가 리뷰 목록(전체 피드·음식별)을 볼 때 정렬 기준을 고른다: **최신순(기본)·평점 높은 순·평점 낮은 순·음식의 리뷰 수가 많은 순·helpful(좋아요) 수 내림차순**.

**Why this priority**: 이 기능의 핵심 — 기획 요구 5종 정렬.

**Independent Test**: 정렬 파라미터별로 목록을 호출해 순서가 기준과 일치하는지 확인. 파라미터 생략 시 최신순(기존 동작 불변).

**Acceptance Scenarios**:

1. **Given** 별점이 다른 리뷰 여러 건, **When** 평점 높은 순으로 조회하면, **Then** 별점 내림차순으로 내려간다(동점은 최신 우선).
2. **Given** 같은 조건, **When** 평점 낮은 순으로 조회하면, **Then** 별점 오름차순으로 내려간다(동점은 최신 우선).
3. **Given** 좋아요 수가 다른 리뷰들, **When** helpful 내림차순으로 조회하면, **Then** 좋아요 수 내림차순으로 내려간다(동점은 최신 우선).
4. **Given** 리뷰 수가 다른 음식들의 리뷰, **When** 음식 리뷰 수 많은 순으로 조회하면, **Then** 소속 음식의 리뷰 수 내림차순으로 내려간다(동점은 최신 우선).
5. **Given** 정렬 파라미터 생략, **When** 조회하면, **Then** 기존과 동일한 최신순이다.
6. **Given** 허용값 밖의 정렬 파라미터, **When** 조회하면, **Then** 400 으로 거절된다.

---

### User Story 2 - 별점 구간으로 거른다 (Priority: P1)

사용자가 별점 구간(예: 1~3점, 3점만)으로 리뷰를 거른다. 기존 필터(음식·작성자 국적)와 조합해 함께 동작한다.

**Why this priority**: 기획 요구의 나머지 절반 — 낮은 평점만 모아보기 등.

**Independent Test**: 별점 구간을 지정해 호출 → 구간 밖 리뷰가 결과에 없다. 구간 + 국적 + 음식 동시 지정 → 전부 만족하는 리뷰만.

**Acceptance Scenarios**:

1. **Given** 별점 1~5 리뷰가 섞인 목록, **When** 1~3점 구간으로 조회하면, **Then** 1·2·3점 리뷰만 내려간다.
2. **Given** 같은 목록, **When** 3점만(하한=상한=3)으로 조회하면, **Then** 3점 리뷰만 내려간다.
3. **Given** 별점 구간 + countryCode + foodId 동시 지정, **When** 조회하면, **Then** 세 조건을 모두 만족하는 리뷰만 내려간다.
4. **Given** 하한이 상한보다 큰 구간(예: 4~2), **When** 조회하면, **Then** 400 으로 거절된다.
5. **Given** 별점 구간 필터 + 임의 정렬, **When** 조회하면, **Then** 필터와 정렬이 함께 적용된다.

---

### User Story 3 - 어떤 정렬에서도 페이지가 이어진다 (Priority: P1)

어떤 정렬 기준을 골라도 커서로 다음 페이지를 요청하면 **중복·누락 없이** 이어진다.

**Why this priority**: 정렬 추가의 구조적 난점 — 커서가 정렬 기준을 따라가지 않으면 페이지 경계에서 중복/누락이 생긴다.

**Independent Test**: 각 정렬에서 전 페이지를 끝까지 순회해 전체 집합과 일치(중복·누락 0)함을 확인 — 특히 동점 값이 페이지 경계에 걸린 경우.

**Acceptance Scenarios**:

1. **Given** 페이지 크기보다 많은 리뷰, **When** 각 정렬 기준으로 끝까지 페이징하면, **Then** 모든 리뷰가 정확히 한 번씩 나온다.
2. **Given** 같은 별점(동점) 리뷰가 페이지 경계에 걸친 상황, **When** 다음 페이지를 요청하면, **Then** 중복·누락 없이 이어진다.
3. **Given** 첫 페이지의 커서, **When** 정렬 기준을 바꿔 그 커서로 요청하면, **Then** 400 으로 거절되거나 정의된 규칙대로 동작한다(커서는 발급된 정렬 기준에 종속).

---

### Edge Cases

- 정렬 파라미터 생략 = 최신순 — 기존 클라이언트(파라미터를 모름)와의 하위 호환이 자동 성립. 계약상 새 X-API-Version 불필요(추가 optional 파라미터).
- helpful 0건 리뷰들만 있는 목록에서 helpful 정렬 — 전부 동점이므로 최신순과 동일 결과.
- 비회원 조회 — KB-348 규칙 그대로(likedByMe false·조회자별 제외 미적용), 정렬·필터는 동일 동작.
- 내 리뷰(`GET /api/reviews/me`)는 범위 밖 — 기존 최신순 유지.
- 좋아요 수·리뷰 수는 조회 시점 값 — 페이징 중 값이 바뀌면 keyset 특성상 항목이 이동할 수 있다(실시간 정합까지는 요구하지 않음, 중복·누락 없음만 보장).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `GET /api/reviews` 는 정렬 파라미터로 5종(최신순·평점 높은 순·평점 낮은 순·음식 리뷰 수 많은 순·helpful 내림차순)을 선택할 수 있어야 하며, 생략 시 최신순이다. 허용값 밖은 400.
- **FR-002**: 모든 정렬의 동점은 최신 리뷰 우선(2차 기준)으로 순서가 결정적이어야 한다.
- **FR-003**: 별점 구간 필터(하한·상한, 각 1~5)를 지원해야 한다 — 단일 점수는 하한=상한. 하한>상한·범위 밖 값은 400.
- **FR-004**: 별점 필터는 기존 필터(foodId·countryCode)·모든 정렬과 조합 가능해야 한다.
- **FR-005**: 커서 페이징은 선택한 정렬 기준을 따라 중복·누락 없이 이어져야 한다.
- **FR-006**: 정렬·필터는 회원·비회원 동일하게 동작한다(KB-348 접근 규칙 불변). 응답 항목 형태는 불변.
- **FR-007**: swagger 문서에 정렬·필터 파라미터의 허용값이 노출되어야 한다(DoD).

### Key Entities

- **정렬 기준**: 5종 고정 열거 — LATEST(기본)·RATING_DESC·RATING_ASC·FOOD_REVIEW_COUNT_DESC·HELPFUL_DESC (표기명은 구현 재량, 계약 확정은 plan 단계).
- **별점 구간**: 하한·상한(1~5 정수) 쌍 — 생략 시 전체.
- **커서**: 발급된 정렬 기준에 종속된 불투명 값 — 클라이언트는 해석하지 않고 그대로 되돌려준다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 5개 정렬 기준 각각으로 목록을 조회해 기대 순서를 얻는다 — 기준별 순서 검증 시나리오 전부 통과.
- **SC-002**: 별점 구간 필터 지정 시 구간 밖 리뷰 노출 0건, 기존 필터와의 조합도 정확히 교집합.
- **SC-003**: 모든 정렬 기준에서 끝까지 페이징 시 중복·누락 0건(동점 경계 포함).
- **SC-004**: 정렬 파라미터를 모르는 기존 클라이언트의 동작(최신순·기존 필터)은 완전히 불변 — 기존 시나리오 회귀 0건.

## Assumptions

- 별점 필터는 **구간(하한~상한)** 형태로 충분하다 — 기획 예시(1~3점, 3점만) 모두 표현 가능. 다중 선택(1,3,5점) 요구는 확인된 바 없어 범위 밖.
- "음식의 리뷰 수가 많은 순"은 리뷰가 속한 음식의 (활성) 리뷰 총수를 기준으로 하며, 전체 피드에서 의미를 갖는다(음식별 조회에서는 모든 항목이 동점 → 최신순과 동일).
- helpful 수는 좋아요 등록·취소로 변하는 현재 값 기준 — 스냅샷 저장을 새로 만들지 않는다.
- 커뮤니티 목록의 국가·음식·별점 필터(8/15 기획의 커뮤니티 항목)는 별개 태스크 — 이 기능은 리뷰 목록(`GET /api/reviews`)만 다룬다.
- 새 X-API-Version 은 만들지 않는다 — optional 파라미터 추가라 기존 계약과 하위 호환.
