# Feature Specification: 음식 이미지 회수 주기 단축

**Feature Branch**: `kb-241-image-collect-interval`

**Created**: 2026-07-25

**Status**: Draft

**Input**: User description: "kb-241 음식 이미지 회수 스케줄러 주기 15분으로 단축"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 생성된 음식 이미지가 빠르게 서비스에 반영된다 (Priority: P1)

관리자가 이미지 없는 음식들을 이미지 생성에 일괄 제출하면, 외부 생성이 끝나는 즉시에 가까운 시점에 이미지가 저장되고 음식 정보에 연결된다. 현재는 생성이 끝난 뒤에도 최대 3시간을 더 기다려야 반영되어, 관리자가 검수를 시작할 수 있는 시점이 그만큼 늦어진다.

**Why this priority**: 이 스토리 하나만 구현해도 기능의 목적(반영 지연 단축)이 달성된다. 나머지는 이를 안전하게 만드는 보완이다.

**Independent Test**: 이미지 없는 음식을 제출한 뒤, 외부 생성이 완료된 시점부터 이미지가 저장되고 음식에 연결될 때까지 걸린 시간을 측정해 검증한다.

**Acceptance Scenarios**:

1. **Given** 제출된 이미지 생성 요청이 외부에서 완료된 상태, **When** 다음 회수 시점이 도래하면, **Then** 15분 이내에 이미지가 저장되고 해당 음식에 연결된다
2. **Given** 제출된 요청이 외부에서 아직 처리 중인 상태, **When** 회수 시점이 도래하면, **Then** 아무것도 변경하지 않고 종료하며 다음 시점에 다시 확인한다
3. **Given** 회수 대상 요청이 하나도 없는 상태, **When** 회수 시점이 도래하면, **Then** 오류 없이 즉시 종료한다

---

### User Story 2 - 회수가 여러 서버에서 중복 실행되지 않는다 (Priority: P2)

운영 환경은 서버가 2대 이상이므로 같은 시각에 여러 서버가 회수를 시도할 수 있다. 주기가 짧아질수록 시도 횟수가 늘어 중복 가능성도 커진다. 같은 요청 결과를 두 서버가 동시에 회수해 이미지가 중복 저장되거나 비용이 이중 기록되면 안 된다.

**Why this priority**: 데이터 정합성과 비용에 직결되지만, 기존 중복 방지 장치가 이미 존재하므로 주기 변경에 맞춰 유효성을 재확인하는 성격이다.

**Independent Test**: 서버 2대 이상을 띄운 상태에서 회수 시점을 여러 번 지나 보내고, 회수 실행 기록과 이미지·비용 기록이 각각 한 번씩만 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 서버 2대가 동시에 회수 시점을 맞은 상태, **When** 두 서버가 회수를 시도하면, **Then** 한 서버만 실제로 수행하고 다른 서버는 건너뛴다
2. **Given** 회수를 수행하던 서버가 도중에 종료된 상태, **When** 이후 회수 시점이 도래하면, **Then** 남은 서버가 정해진 대기 시간 안에 회수를 이어받는다

---

### User Story 3 - 회수 주기를 배포 없이 환경별로 조정할 수 있다 (Priority: P3)

개발 환경에서는 더 자주, 운영 환경에서는 기본값으로 두는 식의 조정이 필요하다. 주기를 바꾸려고 코드를 고치고 다시 배포해야 한다면 검증이 느려진다.

**Why this priority**: 기본값만 바꿔도 목적은 달성되므로 필수는 아니지만, 이미 설정으로 분리돼 있어 유지하는 것만으로 충족된다.

**Independent Test**: 설정값만 바꿔 앱을 기동한 뒤, 변경한 주기대로 회수가 수행되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 환경별 설정으로 회수 주기를 지정한 상태, **When** 앱을 기동하면, **Then** 코드 변경 없이 지정한 주기로 회수가 수행된다

---

### Edge Cases

- 회수 1회가 새 주기(15분)보다 오래 걸리면 어떻게 되는가? — 이전 회수가 끝나기 전 다음 시점이 도래해도 중복 실행되지 않아야 하며, 이전 회수 완료 후 다음 회차가 정상 수행되어야 한다.
- 중복 방지 장치의 점유 시간이 새 주기보다 길면 어떻게 되는가? — 비정상 종료 등으로 점유가 남았을 때 건너뛰는 회차 수가 늘어난다. 새 주기에 맞는 점유 시간으로 조정한다.
- 회수 도중 특정 음식이 삭제되었으면 어떻게 되는가? — 해당 항목만 실패로 기록하고 나머지 회수는 계속되어야 한다.
- 외부 생성 요청이 실패·만료 상태로 돌아오면 어떻게 되는가? — 해당 요청을 실패로 마감하고 다음 회차가 같은 요청을 다시 조회하지 않아야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 제출된 이미지 생성 요청의 완료 여부를 **15분마다** 확인해야 한다
- **FR-002**: 회수 주기는 코드 변경·재빌드 없이 **환경별 설정으로 조정**할 수 있어야 한다
- **FR-003**: 요청이 완료된 경우 시스템은 생성된 이미지를 저장하고 해당 음식에 연결해야 한다
- **FR-004**: 요청이 아직 처리 중인 경우 시스템은 아무것도 변경하지 않고 다음 주기에 다시 확인해야 한다
- **FR-005**: 서버가 여러 대인 환경에서 같은 시각의 회수는 **한 번만** 수행되어야 한다
- **FR-006**: 중복 방지를 위한 점유 시간은 새 주기 기준으로 정해져야 하며, 비정상 종료 시 건너뛰는 회차가 최소화되어야 한다
- **FR-007**: 개별 항목의 실패는 같은 회차의 다른 항목 처리를 중단시키지 않아야 한다
- **FR-008**: 회수 주기 단축이 외부 이미지 생성 비용을 증가시키지 않아야 한다

### Key Entities

- **이미지 생성 요청 묶음**: 한 번에 제출된 음식들의 생성 요청 단위. 제출·완료·실패 상태와 제출 시각을 가진다
- **이미지 생성 항목**: 묶음에 속한 음식 1건의 생성 요청. 대기·완료·실패 상태와 실패 사유를 가진다
- **음식**: 이미지 연결 대상. 이미지 경로를 가지며, 경로가 비어 있는 음식이 생성 대상이 된다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 외부 이미지 생성이 완료된 시점부터 서비스에 반영되기까지의 대기 시간이 **최대 3시간에서 최대 15분으로** 줄어든다
- **SC-002**: 주기 단축 후에도 이미지 1건당 외부 생성 비용 기록이 **정확히 1회**만 남는다
- **SC-003**: 서버 2대 환경에서 회수 중복 실행이 **0건**이다
- **SC-004**: 관리자가 일괄 제출한 뒤 이미지 준비 상태를 확인하려고 반복 조회할 필요가 없어진다

## Assumptions

- 외부 이미지 생성 서비스는 완료 여부 조회 자체에 비용을 부과하지 않으므로, 조회 빈도를 높여도 비용이 늘지 않는다
- 회수 1회 처리 시간은 통상 새 주기(15분)보다 짧다. 그렇지 않은 경우는 중복 방지 장치가 처리한다
- 운영 환경 서버는 2대이며, 향후 늘어나도 중복 방지 방식은 그대로 유효하다
- 이미지 제출 자체(관리자 일괄 제출)의 동작·범위는 이번 변경 대상이 아니다
- 이미지 저장소와 외부 생성 서비스 연동은 이미 동작 중이며 재구성이 필요하지 않다
