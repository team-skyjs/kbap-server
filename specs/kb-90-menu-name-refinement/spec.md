# Feature Specification: 메뉴 스캔 메뉴명 정제 · 매칭 · 위험도 판정

**Feature Branch**: `kb-90-menu-name-refinement`

**Created**: 2026-07-08 · **Updated**: 2026-07-09

**Status**: Implemented (PR #41)

**Input**: 메뉴판 OCR 텍스트에서 한국어 메뉴명을 정제해 저장 음식과 매칭하고, 항목별 위험도를 돌려준다. 처음 보는 음식은 조사 대기 상태로 등록해 두되 일반 조회에는 노출하지 않는다. 스캔 내역은 기록하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔한 메뉴의 위험도를 바로 확인한다 (Priority: P1)

사용자가 메뉴판을 촬영하면, 로마자 음역·가격·기호·오탈자가 섞인 텍스트가 서버에서 표준 한국어 메뉴명으로 정제된다. 저장된 음식과 매칭되면 사용자의 회피 성분 기준으로 산출한 위험도를 즉시 받는다. 처음 보는 음식은 "확인 중"으로, 메뉴가 아닌 텍스트(원산지·가격·UI 문구)는 결과에서 아예 빠진다.

**Why this priority**: 스캔의 존재 이유 그 자체. 이 경로가 없으면 기능이 성립하지 않는다.

**Independent Test**: 저장된 `김치찌개`·`된장찌개`에 대해 `"김치찌개 kimchi jjigae"`·`"된장찌게 8,000"`(오탈자·가격)·`"원산지 : 중국"`·`"MacBook Air F9"`·`"우주라면"`(미등록)을 함께 스캔해, 앞 둘은 위험도와 함께 매칭되고 가운데 둘은 결과에서 빠지며 마지막은 "확인 중"으로 오는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** `김치찌개`가 저장돼 있고, **When** `"김치찌개 kimchi jjigae"`를 스캔하면, **Then** 그 음식으로 매칭(`MATCHED`)되고 회피 성분 기준 위험도를 받는다.
2. **Given** `된장찌개`가 저장돼 있고, **When** 오탈자·가격이 섞인 `"된장찌게 8,000"`을 스캔하면, **Then** 표준명으로 교정돼 매칭된다.
3. **Given** 항목이 `"원산지 : 중국"`·`"MacBook Air F9"`처럼 메뉴가 아니면, **When** 스캔하면, **Then** 결과에서 제외된다(응답 개수 < 요청 개수).
4. **Given** 저장에 없는 메뉴명이면, **When** 스캔하면, **Then** 조사 대기 음식으로 등록되고 `UNMATCHED`·위험도 `UNKNOWN`으로 응답한다.
5. **Given** 같은 미등록 메뉴를 다시 스캔하면, **When** 처리하면, **Then** 중복 등록 없이 같은 음식 식별자를 돌려준다.

---

### User Story 2 - 조사 대기 음식은 사용자에게 노출되지 않는다 (Priority: P1)

스캔으로 새로 등록된 음식은 레시피·설명·번역이 아직 없다. 이런 미완성 음식은 메뉴 목록·상세 조회에 나타나지 않아야 하고, 위험도도 "알 수 없음"이어야 한다. 데이터가 채워져 완성 상태가 된 뒤에야 일반 조회에 등장한다.

**Why this priority**: 미완성 음식이 노출되면 빈 설명·잘못된 "안전" 판정이 사용자에게 보인다. 안전 직결이라 P1이다.

**Independent Test**: 스캔으로 미완성 음식을 만든 뒤 메뉴 목록·상세를 조회해 그 음식이 나오지 않는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 스캔으로 등록된 미완성 음식이 있고, **When** 메뉴 목록을 조회하면, **Then** 그 음식은 포함되지 않는다.
2. **Given** 미완성 음식의 식별자로, **When** 상세를 조회하면, **Then** 조회되지 않는다.
3. **Given** 미완성 음식이 스캔에서 다시 매칭되면, **When** 위험도를 산출하면, **Then** 성분 정보가 없으므로 `UNKNOWN`이다(성분이 비었다고 "안전"으로 판정하지 않는다).

---

### User Story 3 - 정제 서비스 장애에도 스캔은 성공한다 (Priority: P2)

정제(외부 언어 이해) 서비스가 없거나 실패해도 스캔 요청은 성공한다. 이름이 정확한 아는 메뉴는 정규화만으로 매칭되고, 나머지는 "확인 중"으로 내려간다. 다만 음식 여부를 판정할 수 없으므로 메뉴가 아닌 텍스트가 결과에 섞일 수 있고, 응답은 이 상태를 명시적으로 알린다.

**Why this priority**: 외부 의존은 반드시 장애가 난다. 부분 강등으로 최악을 "판정 품질 저하"에 가둔다.

**Independent Test**: 정제 서비스를 끈 채 아는 메뉴 + 잡음을 스캔해, 아는 메뉴는 매칭되고 응답에 강등 표시가 오는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 정제 서비스가 미구성·불통이고, **When** 스캔하면, **Then** 요청은 성공하고 응답에 강등 표시(`degraded=true`)가 담긴다.
2. **Given** 강등 상태에서 이름이 정확한 아는 메뉴가 들어오면, **When** 처리하면, **Then** 정규화 매칭으로 `MATCHED`된다.
3. **Given** 강등 상태에서는 음식 여부를 판정할 수 없으므로, **When** 처리하면, **Then** 조사 대기 음식을 새로 등록하지 않는다(데이터 오염 방지).

---

### Edge Cases

- 한글이 하나도 없는 항목(숫자·라틴 전용) → 정제 서비스 호출 없이 결과에서 제외한다.
- 서로 다른 원문이 같은 정규화 키가 되면(`돼지 국밥`/`돼지국밥`) 같은 음식으로 매칭한다.
- 같은 정규화 키를 가진 음식이 둘 이상이면 결정적으로 하나(식별자 최소값)를 고르고 기록을 남긴다.
- 한 스캔에 같은 표준명이 여러 항목으로 나오면 조사 대기 음식은 한 번만 등록한다.
- 정제 결과 개수가 요청 개수와 다르면 결과를 신뢰하지 않고 강등 처리한다(항목 정렬이 깨졌다는 신호).
- `itemId`가 요청 안에서 중복이거나 `rawMenuName`이 비면 잘못된 요청(400)으로 거절한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 각 스캔 항목의 원문을 결정적 규칙으로 정규화(한글 외 문자 제거)해 매칭 키를 만든다. 정규화 결과가 비면 그 항목은 메뉴가 아니므로 정제 서비스에 보내지 않고 결과에서 제외한다.
- **FR-002**: 정규화 결과가 비지 않은 전 항목을 정제 서비스로 **동기 호출 1회**(스캔당) 보내, 각 항목을 표준 한국어 메뉴명 또는 "음식 아님"으로 판정한다. 응답은 요청과 같은 길이·순서여야 하며, 다르면 신뢰하지 않는다.
- **FR-003**: "음식 아님"으로 판정된 항목은 응답 결과에서 제외한다. 따라서 결과 개수는 요청 항목 수보다 적을 수 있고, 클라이언트는 `itemId`로 짝을 맞춘다.
- **FR-004**: 표준 메뉴명의 정규화 키로 저장된 활성 음식을 일괄 조회한다(스캔당 1회). 미완성 음식도 조회 대상이다.
- **FR-005**: 조회되지 않은 표준명은 미완성 음식으로 등록한다(같은 이름이면 중복 생성하지 않는다). 미완성 음식은 레시피·설명·번역이 채워져 완성 상태가 되기 전까지 일반 조회(목록·상세)에 노출되지 않는다.
- **FR-006**: 항목별 위험도는 매칭된 음식과 사용자 회피 성분으로 산출한다. **미완성 음식의 위험도는 항상 `UNKNOWN`**이며, 성분 목록이 비었다는 이유로 "안전"으로 판정하지 않는다.
- **FR-007**: 정제 서비스가 미구성·실패·타임아웃·응답 개수 불일치이면 정규화 키만으로 exact 매치하는 폴백으로 강등한다. 이때 음식 여부를 판정할 수 없으므로 **미완성 음식을 새로 등록하지 않으며**, 응답에 강등 상태를 표시한다. 스캔 요청 자체는 성공한다.
- **FR-008**: 스캔 내역(스캔·항목)은 저장하지 않는다. 응답은 요청당 판정 결과만 담는다.
- **FR-009**: 요청은 `itemId`와 원문 메뉴명만 받는다(바운딩 박스 미수신). `itemId`는 요청 안에서 유일해야 하며 중복 시 400으로 거절한다.
- **FR-010**: 응답은 공통 응답 봉투(BaseResponse)와 `/api/v1` 경로 규약을 따르고, 정규화 규칙은 단일 출처로 관리한다.

### Key Entities *(include if feature involves data)*

- **음식(Food)**: 한국어 이름·설명·번역·맵기·포함 회피 성분을 가진다. **콘텐츠 완성 상태**(미완성/완성)를 가지며, 완성 상태만 일반 조회에 노출된다. 활성(소프트삭제 제외) 음식만 매칭된다.
- **매칭 결과(Menu Item Match)**: 스캔 항목의 판정 결과. `MATCHED`(완성 음식과 매칭, 위험도 산출) 또는 `UNMATCHED`(조사 대기 — 위험도 `UNKNOWN`). 메뉴가 아닌 항목은 결과 자체가 생기지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 실측 로그의 진짜 메뉴 6종이 정제 후 100% 매칭되고, `메뉴판`·가격·원산지 문구는 매칭되지 않는다.
- **SC-002**: 로마자 혼합(`김치찌개 kimchi jjigae`)·오탈자+가격(`된장찌게 8,000`)이 각각 저장된 표준 음식으로 매칭된다.
- **SC-003**: 메뉴가 아닌 텍스트가 응답 결과에 포함되는 비율이 0%다(정제 서비스 정상 시).
- **SC-004**: 스캔으로 등록된 미완성 음식이 메뉴 목록·상세 조회에 노출되는 비율이 0%이며, 위험도는 항상 `UNKNOWN`이다.
- **SC-005**: 같은 미등록 음식이 여러 항목·여러 스캔으로 들어와도 음식 행은 1건만 생성된다.
- **SC-006**: 정제 서비스가 완전 불통이어도 스캔 요청은 성공하고, 이름이 정확한 아는 메뉴는 매칭되며, 응답이 강등 상태를 알린다.

## Assumptions

- 한국어 메뉴판 스캔이 주 시나리오다. 한글이 없는 항목은 메뉴로 보지 않는다.
- 프론트는 OCR 바운딩박스로 1차 분류를 마친 텍스트를 보낸다. 서버는 박스 좌표를 쓰지 않으므로 요청에서 받지 않는다.
- 정제는 외부 언어 이해 서비스(LLM)를 **동기 호출**한다. 정제 결과 캐시는 두지 않는다(잡음 문자열은 반복성이 낮다).
- 사용자 회피 성분은 회원 기능 도입 전까지 더미 제공자를 사용한다.
- 미완성 음식의 레시피·설명·번역을 채우는 조사 배치는 별도 작업이다. 이 작업은 미완성 음식의 **등록·노출 차단·위험도 UNKNOWN**까지 책임진다.
