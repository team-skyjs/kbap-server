# Feature Specification: 메뉴 스캔 수신 메뉴명 정제 (LLM 추출 + 매칭)

**Feature Branch**: `kb-90-menu-name-refinement`

**Created**: 2026-07-08

**Status**: Draft

**Input**: User description: "KB-90 — 메뉴 스캔 API의 수신 메뉴명 정제. 넘어온 텍스트를 정규화기에 거친 뒤 전부 LLM 에 보내 음식명만 추출하고, 그 응답으로 DB 에서 hit/miss 를 구분해 결과를 반환한다. miss 는 대기열에 등록한다. LLM 장애 시에는 정규화 exact 매치로 폴백해 아는 메뉴는 계속 매칭한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔 메뉴명을 정제해 아는 메뉴로 매칭하고 미상은 대기열로 (Priority: P1)

사용자가 메뉴판을 촬영해 스캔하면, 각 항목 텍스트(로마자 음역·기호·오탈자 등 잡음 포함)가 정제 과정을 거쳐 표준 한국어 메뉴명으로 정리되고 저장된 음식과 대조된다. 아는 메뉴는 그 음식으로 매칭돼 결과를 받고, 처음 보는 음식은 "확인 중"으로 응답되며 후속 조사 대기열에 등록된다. 원산지·가격·UI 문구 같은 비음식은 결과에서 걸러진다.

**Why this priority**: 스캔의 핵심 가치 — "찍으면 잡음이 정리돼 아는 메뉴가 잡히고, 모르는 건 조사 대기로 넘어간다". 이 경로 하나로 스캔이 유의미해지는 MVP다.

**Independent Test**: 저장된 `김치찌개` 에 대해 혼합 로마자 `"김치찌개 kimchi jjigae"`·오탈자 `"김치찌게"` 를 스캔하면 둘 다 `김치찌개` 로 매칭되고, 미등록 `"우주라면"` 은 "확인 중"+대기열, `"원산지 중국"` 은 비음식으로 걸러지는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** `김치찌개` 가 저장돼 있고, **When** `"김치찌개 kimchi jjigae"`(혼합)·`"김치찌게"`(오탈자)를 스캔하면, **Then** 두 항목 모두 `김치찌개` 로 매칭된 결과(MATCHED+foodId)를 받는다.
2. **Given** 저장에 없는 메뉴가 표준명으로 정제되면, **When** DB 매칭이 miss 이면, **Then** 그 항목은 "확인 중"(PENDING)으로 응답되고 표준명이 대기열에 등록된다.
3. **Given** 항목이 비음식 텍스트(`"원산지 중국"`·가격·UI 문구)이면, **When** 정제가 음식 아님으로 판정하면, **Then** 결과에서 비음식(NOT_FOOD)으로 처리되고 대기열에 등록되지 않는다.
4. **Given** 한글이 전혀 없는 항목(`"MacBook Air F9"`·숫자만)이면, **When** 정규화 결과가 비면, **Then** 정제 서비스 호출 없이 비음식으로 처리한다.
5. **Given** 같은 미등록 음식이 여러 항목·여러 스캔으로 들어오면, **When** 표준명이 동일하면, **Then** 대기열에는 그 표준명이 한 번만 등록된다.

---

### User Story 2 - 정제 서비스 장애에도 아는 메뉴는 계속 매칭 (Priority: P2)

정제(외부 언어 이해) 서비스가 장애이거나 응답이 지연되거나 아예 구성되지 않은 환경에서도, 스캔은 정규화된 텍스트로 저장 음식과 직접 대조해 **정확히 이름이 맞는 아는 메뉴는 그대로 매칭**한다. 정규화만으로 못 맞춘 나머지는 원문 그대로 "확인 중"으로 응답되고 대기열에 남아 서비스 복구 후 처리된다. 스캔 요청 자체는 성공한다.

**Why this priority**: 정제를 전량 외부 서비스에 태우면 장애 시 스캔이 멈춰 고객 불만으로 직결된다. 정규화 exact 매치 폴백으로 최악의 경우를 "수식어 붙은/처음 보는 항목만 즉시→나중으로 미뤄짐"에 가둔다. P1(정상 경로) 위에 얹는 견고성이다.

**Independent Test**: 정제 서비스를 강제 실패시킨 채 아는 메뉴 `"김치찌개"` + 미상 항목이 섞인 스캔을 보내, 아는 메뉴는 MATCHED 로 매칭되고 미상만 "확인 중"으로 응답되며 스캔은 200 으로 성공하는 것으로 검증한다.

**Acceptance Scenarios**:

1. **Given** 정제 서비스가 불통이고 스캔에 이름이 정확한 아는 메뉴와 잡음 항목이 섞여 있으면, **When** 스캔을 처리하면, **Then** 아는 메뉴는 정규화 exact 매치로 MATCHED 되고 나머지는 원문으로 "확인 중"+대기열이며 스캔 응답은 성공한다.
2. **Given** 정제 서비스가 아예 구성되지 않은 환경이어도, **When** 스캔을 처리하면, **Then** 애플리케이션은 정상 동작하고 위 폴백 규칙으로 응답한다.

---

### Edge Cases

- 정규화 결과가 서로 다른 원문에서 같은 키가 되면("돼지 국밥"/"돼지국밥") → 같은 음식으로 매칭한다.
- 정제가 표준명을 반환했지만 그 표준명이 저장 음식에 없으면 → "확인 중"(PENDING)+대기열(신규 음식).
- 정제가 표준명을 반환했고 저장 음식에도 있으면 → MATCHED.
- 저장 음식에 같은 한국어 이름이 둘 이상이면(동음이의) → 결정적으로 하나를 매칭(식별자 최소값)하고 기록을 남긴다.
- 항목 원문이 비었거나 공백뿐이면 → 잘못된 입력으로 거절한다(기존 스캔 검증 규약 유지).
- 폴백 중 정규화 exact 매치도 miss 인 항목 → 원문을 대기열에 등록(표준명 미상).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 각 스캔 항목의 수신 텍스트를 결정적 규칙으로 정규화(한글 외 문자 제거)해 매칭 키를 만든다. 정규화 결과가 비면(한글 0자) 그 항목은 정제 서비스에 보내지 않고 비음식(NOT_FOOD)으로 처리한다.
- **FR-002**: 정규화 결과가 비어있지 않은 항목은 정제(외부 언어 이해) 서비스로 보내 표준 한국어 메뉴명 또는 "음식 아님"으로 판정한다. 스캔당 호출은 대상 항목을 묶어 일괄 수행한다.
- **FR-003**: 정제가 반환한 표준 메뉴명으로 저장된 활성 음식을 exact 매치한다. 일치하면 MATCHED(음식 식별자 포함), 불일치하면 "확인 중"(PENDING)으로 응답하고 표준명을 대기열에 등록한다.
- **FR-004**: "음식 아님"으로 판정된 항목은 결과에서 비음식으로 처리하고 대기열에 등록하지 않는다.
- **FR-005**: 대기열에는 정제된 표준 메뉴명(폴백 시 원문)만 적재하며, 같은 값은 중복 등록되지 않는다.
- **FR-006**: 정제 서비스가 장애·지연·미구성이면 정규화된 텍스트로 저장 음식을 직접 exact 매치하는 폴백으로 강등한다 — 일치하면 MATCHED, 불일치하면 원문을 "확인 중"+대기열로 둔다. 이때도 스캔 요청 전체는 성공으로 완료된다.
- **FR-007**: 각 응답 항목은 대응하는 스캔 입력(itemId 상관키)과의 매핑을 유지해, 클라이언트가 어떤 항목의 결과인지 식별할 수 있다.
- **FR-008**: 응답은 공통 응답 봉투(BaseResponse)와 `/api/v1` 경로 규약을 따르고, 정규화 규칙은 단일 출처로 관리한다. 요청 스키마는 변경하지 않는다(기존 itemId·rawMenuName·boundingBox).
- **FR-009**: 외부 정제 호출은 DB 트랜잭션 안에서 길게 잡지 않는다(저장 → 외부 호출 → 결과 저장).

### Key Entities *(include if feature involves data)*

- **스캔 항목(Scanned Item)**: 클라이언트 상관키(itemId)·원문 텍스트·바운딩박스를 가진다. 정제 결과로 매칭 상태(MATCHED+음식 식별자 / PENDING / NOT_FOOD)를 갖는다.
- **음식(Food)**: 한국어 이름을 가진 저장 항목으로, 정규화 매칭 키의 대조 대상이다. 활성(소프트삭제 제외) 음식만 매칭된다.
- **정제 대기열 항목(Refinement Queue Entry)**: 정제된 표준 메뉴명(또는 폴백 원문)과 중복 방지 키·상태를 가진다. 후속 배치가 소비해 레시피를 조사·등록한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 실측 로그의 진짜 메뉴 6종(김치찌개·된장찌개·순두부찌개·부대찌개·고추장찌개·닭볶음탕)이 정제 후 100% 매칭 대상으로 추출되고, "메뉴판"·잡음은 하나도 매칭되지 않는다.
- **SC-002**: 혼합 로마자(`"김치찌개 kimchi jjigae"`)·오탈자(`"김치찌게"`)가 저장된 `김치찌개` 로 동일하게 매칭된다.
- **SC-003**: 원산지 값·가격·UI 텍스트 등 비음식 잡음이 신규 음식으로 대기열에 등록되는 비율이 0%다.
- **SC-004**: 정제 서비스가 완전 불통(또는 미구성)인 상태에서도 이름이 정확한 아는 메뉴가 포함된 스캔은 성공 응답을 받고 그 메뉴는 MATCHED 로 매칭된다.
- **SC-005**: 같은 미등록 음식이 여러 항목·여러 스캔으로 들어와도 대기열에는 그 값당 1건만 등록된다.

## Assumptions

- 한국어 메뉴판 스캔이 주 시나리오다. 한글이 전혀 없는(영문 전용) 박스는 이번 범위의 매칭 대상이 아니다(비음식 처리, 사용자 결정).
- 프론트는 이미 바운딩박스 기하 분류로 가격·원산지 라벨·긴 설명 등을 1차로 걸러 보낸다. 백엔드는 그 뒤에도 남는 텍스트 잡음(혼합 로마자, 원산지 값, UI 문구, 오탈자 등)을 처리한다.
- 정제는 외부 언어 이해 서비스(LLM)로 수행한다. 정규화 결과의 "음식 여부"는 형태로 판정할 수 없으므로 판정자는 DB exact 매치(hit=아는 음식) 또는 LLM(의미)이다. 정제 결과 캐시는 두지 않는다 — 잡음 문자열은 반복성이 낮아 캐시 이득이 적다(사용자 결정).
- 정제 결과 캐시가 없으므로, 반복되는 비음식·미등록 항목도 매 스캔 정제 서비스로 가지만, 비한글 pre-filter(FR-001)가 명백한 잡음의 호출을 줄인다.
- 현재 스캔의 위험도 판정은 mock 단계이며, 이 작업은 "수신 메뉴명 정제·매칭 및 대기열 라우팅" 슬라이스에 한정한다. 위험도 산출과 레시피 조사 배치는 별도 작업이다.
