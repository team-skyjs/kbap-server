# Feature Specification: 음식 번역결과 JSON 칼럼 통합 (KB-48)

**Feature Branch**: `kb-48-food-translation-json-column`

**Created**: 2026-07-04

**Status**: Draft

**Input**: User description: "jira kb-48 태스크를 시작할거야. 현재 음식의 번역결과를 별도 테이블에 저장하고 있는데, 이것을 기피성분 테이블처럼 json 칼럼 하나로 관리하도록 변경할것임"

## 개요

음식(food)의 다국어 번역결과는 현재 두 개의 **정규화된 별도 테이블**(음식명 번역 `food_name_translation`, 설명 번역 `food_description_translation`)에 언어당 한 행씩 저장된다. 이를 기피성분(`avoidance_substance.translations`, #25에서 도입)과 **동일한 방식** — 부모 음식 행에 언어→문자열 맵을 담는 **단일 JSON 칼럼** — 으로 통합한다. 한국어 원문은 지금처럼 번역 저장소 밖(`food.korean_name`·`food.description`)에 둔다.

이 작업은 **저장 방식(내부 표현)만 교체**하는 리팩터링이다. 상세조회 API(`GET /api/v1/foods/detail`)의 **응답 계약과 언어 폴백 동작은 동결**한다 — 외부에서 관찰되는 결과는 변하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 상세조회 응답이 저장 방식 교체 후에도 동일 (Priority: P1)

앱 사용자가 특정 언어로 음식 상세를 조회하면, 저장소가 별도 테이블이든 JSON 칼럼이든 **동일한 번역 음식명·설명**을 받는다. 요청 언어의 번역이 없으면 지금과 똑같이 한국어 원문으로 폴백된다.

**Why this priority**: 이 기능의 존재 이유는 "겉보기 동작 불변, 내부 저장만 단순화"다. 응답이 조금이라도 달라지면 리팩터링 자체가 실패다. 계약 동결이 최우선 안전망이다.

**Independent Test**: 마이그레이션 전/후로 같은 음식·같은 언어(9개 대상 언어 + 한국어 + 미지원 언어)에 대해 `GET /api/v1/foods/detail`을 호출해 응답 JSON(번역 음식명·`description`·폴백 결과)이 완전히 동일함을 검증한다.

**Acceptance Scenarios**:

1. **Given** 어떤 음식에 특정 대상 언어(예: `en`)의 음식명·설명 번역이 존재하고, **When** 그 언어로 상세를 조회하면, **Then** 응답의 음식명·설명이 해당 언어 번역값으로 반환된다(이전 저장 방식과 동일한 값).
2. **Given** 어떤 음식에 요청 언어의 번역이 없고, **When** 그 언어로 상세를 조회하면, **Then** 음식명은 `food.korean_name`, 설명은 `food.description`(한국어 원문)으로 폴백된다.
3. **Given** 요청 언어가 한국어(`ko`)이거나 언어 파라미터가 비어 있고, **When** 상세를 조회하면, **Then** 번역 저장소를 조회하지 않고 한국어 원문을 반환한다(기존 동작 유지).

---

### User Story 2 - 기존 번역 데이터가 무손실 이행 (Priority: P2)

운영 데이터에 이미 쌓인 모든 음식명·설명 번역이 새 JSON 칼럼으로 **한 건도 빠짐없이** 옮겨진다. 이행 후 이전 테이블의 모든 `(음식, 언어)` 쌍이 JSON 맵에서 동일 값으로 조회된다.

**Why this priority**: 계약이 동결돼 있어도(P1) 원천 데이터가 유실되면 응답이 폴백으로 바뀌어 사용자에게 노출된다. 이행 정확성이 계약 보존의 전제다.

**Independent Test**: 이행 스크립트 실행 전 `food_name_translation`·`food_description_translation`의 전체 `(food_id, lang_code, 값)` 집합을 캡처하고, 실행 후 각 음식의 JSON 맵을 펼쳐 동일 집합인지(누락·변형·중복 없음) 대조한다.

**Acceptance Scenarios**:

1. **Given** 두 번역 테이블에 N개 음식 × 최대 9개 언어의 행이 있고, **When** 이행을 수행하면, **Then** 각 음식의 음식명/설명 JSON 맵이 정확히 그 언어들만 키로 갖고 값이 원본과 일치한다.
2. **Given** 어떤 음식에 특정 언어 번역이 없었고(행 없음), **When** 이행 후 그 음식의 JSON 맵을 보면, **Then** 해당 언어 키가 **존재하지 않는다**(빈 문자열·null 키를 만들지 않는다).
3. **Given** 어떤 음식에 번역이 하나도 없었고, **When** 이행 후 조회하면, **Then** 해당 음식의 번역 맵은 빈 객체이며 모든 언어에서 한국어 원문으로 폴백된다.

---

### User Story 3 - 레거시 번역 테이블 제거로 단일 출처화 (Priority: P3)

이행이 검증된 뒤 `food_name_translation`·`food_description_translation` 테이블과 이를 조회하던 별도 경로가 제거되어, 음식 번역의 **단일 출처가 음식 행의 JSON 칼럼**이 된다.

**Why this priority**: 중복 저장·언어당 추가 조회를 없애 스키마와 읽기 경로를 단순화한다. 다만 P1·P2가 보장돼야 안전하게 제거할 수 있으므로 마지막이다.

**Independent Test**: 스키마에 두 번역 테이블이 더 이상 없고, 상세조회가 음식 로드 외 **언어별 추가 조회 없이** 번역을 해석함을 확인한다.

**Acceptance Scenarios**:

1. **Given** 이행이 완료됐고, **When** 스키마를 점검하면, **Then** `food_name_translation`·`food_description_translation` 테이블이 존재하지 않는다.
2. **Given** 상세조회 한 건을 처리할 때, **When** 번역을 해석하면, **Then** 음식 애그리거트 로드에 이미 포함된 번역 맵을 사용하며 언어별 별도 조회를 발생시키지 않는다.

---

### Edge Cases

- **미지원/미지의 언어 코드**: 기존과 동일하게 처리한다 — 지원 목록에 없는 언어 코드로 조회 시 기존 에러 동작(미지원 언어 strict 검증, #23)을 그대로 유지하고, JSON 맵에 우연히 들어간 미지의 키는 도메인 복원 시 무시한다(기피성분 패턴과 동일).
- **부분 번역**: 음식명 번역만 있고 설명 번역은 없는(또는 그 반대) 경우, 각 필드가 독립적으로 번역값/한국어 폴백을 따른다.
- **빈 문자열 값**: 원본에 빈 값이 있었다면 이행 시 키를 만들지 않는다(폴백 대상). 참고: 현행 스키마는 번역값을 `NOT NULL`로 두므로 빈 값은 예외적 케이스다.
- **길이 한계**: 번역 값은 현행 컬럼 상한(255자)을 넘지 않는다고 가정한다. JSON 저장은 개별 컬럼 길이 제약을 강제하지 않으므로 이행 데이터가 이 상한 안에 있음을 전제한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 각 음식의 **음식명 번역**을 `언어코드 → 문자열` 맵으로, **설명 번역**을 별도의 `언어코드 → 문자열` 맵으로, 해당 음식 행에 붙은 단일 JSON 저장 단위로 보관해야 한다(기피성분 `translations` 패턴과 동형).
- **FR-002**: 번역 맵의 언어 키는 한국어(`ko`)를 **포함하지 않는다**. 한국어 음식명·설명은 음식 행의 기존 필드(`korean_name`·`description`)에 남는다.
- **FR-003**: 번역이 없는 언어는 맵에 **키를 두지 않는다**(빈 문자열·null 값을 저장하지 않는다).
- **FR-004**: 상세조회는 요청 언어의 번역이 맵에 있으면 그 값을, 없으면 한국어 원문을 반환해야 한다 — 음식명·설명 각각 독립적으로. 이 폴백 결과는 기존 동작과 동일해야 한다.
- **FR-005**: 상세조회 API(`GET /api/v1/foods/detail`)의 **응답 필드 구조와 값은 동결**한다. 저장 방식 교체가 응답 스키마·필드명·값에 어떤 변화도 일으키면 안 된다.
- **FR-006**: 기존 `food_name_translation`·`food_description_translation`의 모든 `(음식, 언어, 값)` 데이터를 새 JSON 저장 단위로 **무손실 이행**해야 한다.
- **FR-007**: 이행이 검증된 뒤 레거시 번역 테이블과 이를 위한 언어별 별도 조회 경로를 제거해, 음식 번역의 단일 출처를 JSON 저장 단위로 만든다.
- **FR-008**: 지원하지 않거나 알 수 없는 언어 코드에 대한 조회 동작(에러 처리·폴백)은 현행 정책을 그대로 유지한다.

### Key Entities *(include if feature involves data)*

- **음식(Food)**: 조회의 애그리거트 루트. 한국어 음식명·설명·맵기·기피성분을 갖는다. 본 기능으로 **음식명 번역 맵·설명 번역 맵**이 이 애그리거트에 포함된다(기피성분에서 번역 맵이 애그리거트 안에 있는 것과 동일한 모양).
- **음식명 번역 맵 / 설명 번역 맵**: `언어코드 → 번역 문자열`. 한국어 제외, 최대 9개 대상 언어(`zh-Hans, en, ja, zh-Hant, vi, id, th, ru, es`). 미존재 언어는 키 없음.
- **언어코드(LanguageCode)**: 한국어 + 9개 대상 언어. 맵 키 문자열과 이 코드가 매칭된다. 미지의 키는 도메인 복원 시 무시.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 마이그레이션 전/후 동일 음식·언어 조합(9개 대상 언어 + 한국어 + 미지원 언어 표본)에 대한 상세조회 응답이 **100% 동일**하다(번역 음식명·설명·폴백·에러 동작 포함).
- **SC-002**: 이행 전 두 번역 테이블에 존재하던 `(음식, 언어)` 번역 쌍이 이행 후 JSON 맵에서 **100% 동일 값으로 조회**된다(누락·변형 0건).
- **SC-003**: 이행 완료 후 스키마에 `food_name_translation`·`food_description_translation` 테이블이 **존재하지 않는다**.
- **SC-004**: 상세조회 한 건 처리 시 번역 해석을 위한 **언어별 추가 조회가 0회**다(번역이 음식 로드에 포함).

## Assumptions

- **범위**: "번역결과"는 현존하는 **음식명 번역과 설명 번역 둘 다**를 가리킨다고 본다(둘 다 별도 테이블에 저장돼 있으므로 함께 JSON화).
- **참조 패턴**: 기피성분 `avoidance_substance.translations`(#25)와 동일한 저장·복원·폴백 방식을 채택한다 — 도메인 애그리거트 안의 `언어→문자열` 맵 + 언어 미존재 시 한국어 폴백.
- **한국어 원문 위치**: 한국어는 번역 저장소 밖(`food.korean_name`·`food.description`)에 유지한다(현행 정책 불변).
- **이행 방식**: #25가 기피성분에서 쓴 방식(백필 후 레거시 컬럼/테이블 DROP)을 답습해, 신규 마이그레이션에서 기존 두 테이블 데이터를 JSON으로 채운 뒤 테이블을 제거한다. 롤백 불가한 파괴적 이행이므로 백필 검증 후 DROP한다.
- **데이터 전제**: 이행 대상 번역 값은 현행 255자 상한 안에 있다.
- **환경**: 마이그레이션은 로컬 도커 MySQL(테스트는 H2·flyway off)에서 DROP+CREATE 부팅으로 검증한다(기존 관행).
- **의존**: 본 작업은 KB-40(음식-기피성분 매핑, #26)이 머지된 최신 develop 스키마 위에서 시작한다.
