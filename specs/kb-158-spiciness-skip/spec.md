# Feature Specification: 맵기 선호 미설정(스킵) 허용 — -1 센티널

**Feature Branch**: `kb-158-spiciness-skip`

**Created**: 2026-07-16

**Status**: Draft

**Input**: User description: "kb-158 워크트리로 시작" (Jira KB-158 — [BE] 맵기 선호 미설정(스킵) 허용 — 온보딩·프로필에서 -1 센티널로 저장)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 온보딩에서 맵기 선호 건너뛰기 (Priority: P1)

신규 회원이 온보딩 중 맵기 선호 화면을 건너뛴다. 맵기 선호는 온보딩의 **필수 항목**이며, 건너뛰기는 클라이언트가 -1(미설정)을 명시 전송하는 것으로 표현한다. 서버는 -1을 "미설정"으로 저장하고, 이후 프로필 조회에서 -1이 그대로 보인다. 값 자체를 보내지 않으면 필수 항목 누락으로 거절한다.

**Why this priority**: 정책 변경의 핵심 — 현재는 사용자가 고르지 않은 기본값 5가 강제로 저장돼, "설정 안 함"이라는 사용자 의사를 표현할 방법이 없다.

**Independent Test**: -1로 온보딩을 완료한 뒤 프로필을 조회해 -1이 반환되는지, 생략 시 거절되는지 확인하는 것만으로 검증 가능.

**Acceptance Scenarios**:

1. **Given** 온보딩 전 회원, **When** 맵기 선호로 -1을 명시해 온보딩을 완료하면, **Then** 맵기 선호가 미설정(-1)으로 저장된다
2. **Given** 온보딩 전 회원, **When** 맵기 선호로 0~10 중 한 값을 보내 온보딩을 완료하면, **Then** 그 값이 그대로 저장된다
3. **Given** 온보딩 전 회원, **When** 맵기 선호를 생략(미전송)하고 온보딩을 요청하면, **Then** 필수 항목 누락으로 거절되고 온보딩은 완료되지 않는다
4. **Given** 맵기 선호 미설정(-1)으로 온보딩을 마친 회원, **When** 내 프로필을 조회하면, **Then** 맵기 선호가 -1로 반환된다

---

### User Story 2 - 프로필 수정에서 맵기 선호를 "설정 안 함"으로 되돌리기 (Priority: P2)

맵기 선호를 설정했던 회원이 프로필 수정 화면에서 "설정 안 함"을 선택한다. 클라이언트는 -1을 명시 전송하고, 서버는 맵기 선호를 미설정으로 되돌린다. 미전송 시에는 기존 부분 수정 규약대로 기존 값이 유지된다.

**Why this priority**: 온보딩 이후에도 미설정으로 되돌릴 수 있어야 정책이 완결된다. 다만 P1(신규 유입 경로)이 먼저다.

**Independent Test**: 맵기 5로 설정된 회원이 -1을 보내 수정한 뒤 조회해 -1이 반환되는지, 맵기를 생략한 수정에서 기존 값이 유지되는지로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 맵기 선호가 5인 회원, **When** 프로필 수정에서 -1을 명시 전송하면, **Then** 맵기 선호가 미설정(-1)으로 저장된다
2. **Given** 맵기 선호가 7인 회원, **When** 맵기 선호를 생략하고 다른 필드만 수정하면, **Then** 맵기 선호는 7로 유지된다 (부분 수정 규약 불변)
3. **Given** 맵기 선호가 미설정(-1)인 회원, **When** 프로필 수정에서 0~10 중 한 값을 보내면, **Then** 그 값으로 교체된다

---

### User Story 3 - 잘못된 맵기 값 거절 (Priority: P3)

온보딩·프로필 수정에서 -1도 0~10도 아닌 값(-2, 11 등)이 오면 요청 전체를 MEMBER-009로 거절하고, 오류 메시지는 -1(미설정)이 허용된다는 사실을 반영한다.

**Why this priority**: 검증 규칙의 경계 정의 — 기능 자체는 P1·P2로 완성되고, 이 스토리는 그 경계를 지킨다.

**Independent Test**: -2와 11을 각각 보내 400 + MEMBER-009가 반환되고 프로필이 바뀌지 않았는지로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 임의 회원, **When** 온보딩 또는 프로필 수정에서 맵기 선호로 -2를 보내면, **Then** MEMBER-009로 거절되고 저장 상태는 변하지 않는다
2. **Given** 임의 회원, **When** 맵기 선호로 11을 보내면, **Then** MEMBER-009로 거절된다
3. **Given** MEMBER-009 오류 응답, **When** 메시지를 확인하면, **Then** -1(미설정)이 허용된다는 내용이 반영돼 있다

---

### Edge Cases

- 경계값: -1(허용) / -2(거절), 0·10(허용) / 11(거절).
- 이미 기본값 5로 저장된 기존 회원은 그대로 5를 유지한다 — 소급 변환(마이그레이션) 없음. 5가 "사용자가 고른 5"인지 "강제 기본값 5"인지 서버는 구분하지 않는다.
- 프로필 수정에서 맵기 선호 검증 실패 시 요청 전체가 거절되고 다른 필드도 저장되지 않는다(기존 부분 저장 없음 규약 유지).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 맵기 선호 값으로 -1(미설정)과 0~10을 허용하고, 그 외 값은 MEMBER-009로 거절해야 한다.
- **FR-002**: 온보딩에서 맵기 선호는 필수 항목이다 — -1(스킵) 또는 0~10을 반드시 보내야 하고, 생략(미전송)하면 필수 누락으로 요청을 거절한다. 온보딩 전 기본 상태(빈 프로필)의 맵기 선호는 미설정(-1)이다.
- **FR-003**: 프로필 수정에서 -1을 명시 전송하면 맵기 선호를 미설정(-1)으로 되돌려야 한다. 미전송(null) 시에는 기존 값을 유지한다(부분 수정 규약 불변 — 이 API 는 여러 화면이 공용으로 쓴다).
- **FR-004**: 프로필 조회 응답은 미설정 상태일 때 맵기 선호를 -1로 반환해야 한다.
- **FR-005**: MEMBER-009 오류 메시지는 -1(미설정) 허용을 반영해야 한다.
- **FR-006**: 기존 회원의 저장된 맵기 선호 값은 변경하지 않는다(소급 변환 없음).

### Key Entities

- **회원 프로필(MemberProfile)**: 회원의 취향·설정 묶음. 맵기 선호가 "미설정" 상태를 가질 수 있게 되며, 미설정은 -1 센티널로 표현한다(0~10 범위 밖). 현재 맵기 선호를 소비하는 다운스트림 로직은 없다(음식의 매운맛 `food.spiciness`는 별개).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 맵기 선호를 설정하지 않고도 온보딩을 완료할 수 있다 — 강제 기본값(5) 저장이 0건이 된다.
- **SC-002**: 미설정 회원의 프로필 조회는 100% -1을 반환해, 클라이언트가 "미설정" UI를 값 하나로 판별할 수 있다.
- **SC-003**: 허용 범위 밖 값(-2, 11 등)의 저장 성공이 0건 — 전부 MEMBER-009로 거절된다.
- **SC-004**: 기존 회원의 저장된 맵기 값은 배포 전후 100% 동일하다(소급 변경 0건).

## Assumptions

- 스킵/"설정 안 함"은 **클라이언트가 -1을 명시 전송**하는 계약이다(사용자 확인, 2026-07-16). 프로필 수정의 미전송=기존 값 유지 규약은 그대로 유지된다.
- 온보딩에서 맵기 선호는 **필수 전송**이다 — 미전송은 400 거절(사용자 확인, 2026-07-17). 초기 DoD 의 "온보딩 생략 시 -1 저장" 문구는 이 결정으로 대체됐다.
- 미설정 표현은 null 이 아닌 -1 센티널로 통일한다 — 저장·조회·요청 모두 동일 값.
- 기존 회원 데이터의 소급 변환(5 → -1 마이그레이션)은 범위 밖이다. 이슈의 영향 범위에 마이그레이션이 없고, 강제 기본값 5와 사용자가 고른 5를 구분할 수 없다.
- 맵기 선호를 소비하는 다운스트림 로직이 없으므로(-1이 흘러가도 깨질 소비자 없음) 추천·판정 로직 변경은 불필요하다.
- DB 스키마 변경 없음 — 맵기 선호는 기존 저장 구조(정수)에 -1이 들어갈 뿐이다.
