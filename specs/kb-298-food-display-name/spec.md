# Feature Specification: 음식 표시용 이름(display name) 분리

**Feature Branch**: `kb-298-food-display-name`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "중복 적재를 막는 제약으로 음식 띄어쓰기가 안되고 있고 ux를 해친다. 따라서 화면에 출력해줄 display_name 칼럼을 추가한다. 기존 api에서는 koreanName으로 한국 메뉴명 응답을 내려주고 있으므로 칼럼 추가후 기존 api에 db의 display_name으로 갈아끼워줘야 할 것이다." (Jira: KB-298)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔으로 새로 등록된 음식의 원본 표기 보존 (Priority: P1)

사용자가 메뉴판을 스캔하면, 아직 등록되지 않은 메뉴는 시스템에 새로 적재된다. 지금은 중복 적재를 막기 위한 정규화(공백·숫자·특수문자 제거) 이름이 그대로 저장·노출되어 "김치 찌개"가 "김치찌개"로 보인다. 앞으로는 새로 적재되는 음식이 메뉴판에 적힌 원본 표기(띄어쓰기 포함)를 표시용 이름으로 함께 보존하고, 화면에는 그 표시용 이름이 노출된다.

**Why this priority**: 신규 적재 경로가 표기 훼손의 발생 지점이다. 이 지점을 막아야 이후 쌓이는 데이터가 전부 올바른 표기를 갖는다.

**Independent Test**: 미등록 메뉴("들깨 칼국수")가 담긴 메뉴판을 스캔하면, 스캔 결과와 이후 조회에서 해당 음식 이름이 "들깨 칼국수"로 보이는지 확인한다. 중복 판정은 여전히 정규화 이름 기준으로 동작해 "들깨칼국수" 재스캔 시 새 음식이 생기지 않는지 함께 확인한다.

**Acceptance Scenarios**:

1. **Given** "들깨 칼국수"가 미등록 상태, **When** 해당 메뉴가 담긴 메뉴판을 스캔하면, **Then** 음식이 새로 적재되고 표시용 이름은 "들깨 칼국수"(원본 표기), 매칭용 이름은 정규화 형태로 저장된다.
2. **Given** "들깨 칼국수"가 위와 같이 적재된 상태, **When** 표기만 다른 "들깨칼국수"를 다시 스캔하면, **Then** 새 음식이 생기지 않고 기존 음식으로 매칭된다.
3. **Given** 신규 적재된 음식, **When** 스캔 결과 화면에 이름이 노출되면, **Then** 원본 표기(띄어쓰기 포함)가 보인다.

---

### User Story 2 - 기존 조회 화면 전체가 표시용 이름으로 응답 (Priority: P2)

음식 이름을 노출하는 모든 기존 화면(스캔 결과, 음식 상세, 목록/검색, 북마크, 홈, 관리자 화면 등)이 한국 메뉴명으로 표시용 이름을 내려준다. 클라이언트가 받는 응답 필드 구조는 바뀌지 않고 값만 표시용 이름으로 바뀐다.

**Why this priority**: 저장만 바꾸고 노출을 안 바꾸면 사용자 체감이 없다. 다만 US1 없이 단독으로는 의미가 없어 P2.

**Independent Test**: 한국 메뉴명을 응답하는 각 조회 화면을 호출해, 표시용 이름이 존재하는 음식은 표시용 이름이 내려오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 표시용 이름이 "김치 찌개"인 음식, **When** 음식 이름을 노출하는 조회 화면을 호출하면, **Then** 한국 메뉴명 값으로 "김치 찌개"가 내려온다.
2. **Given** 기존 클라이언트, **When** 변경 후 같은 화면을 호출하면, **Then** 응답 필드 구조(필드명 포함)는 변경 전과 동일하다.

---

### User Story 3 - 기존 데이터 이관 (Priority: P3)

이미 정규화 이름으로 저장된 기존 음식들도 표시용 이름을 갖는다. 원본 표기는 복원할 수 없으므로 현재 저장된 이름을 초기값으로 삼고, 이후 관리자 음식 수정 기능으로 표기를 교정할 수 있다.

**Why this priority**: 데이터 완결성을 위한 이관 단계. 사용자 체감 개선은 US1·US2 가 만들고, 기존 데이터 교정은 운영에서 점진적으로 진행한다.

**Independent Test**: 이관 후 표시용 이름이 비어 있는 음식이 0건인지, 기존 음식 조회 시 이전과 동일한 이름이 내려오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 변경 이전에 적재된 음식, **When** 이관이 완료되면, **Then** 표시용 이름이 기존 저장 이름과 동일한 값으로 채워져 있다.
2. **Given** 이관이 완료된 상태, **When** 임의 음식을 조회하면, **Then** 표시용 이름이 빈 값인 음식은 존재하지 않는다.

---

### Edge Cases

- 같은 정규화 이름으로 매칭되는 서로 다른 원본 표기("김치 찌개" / "김치  찌개")가 순차 스캔되면? — 먼저 적재된 음식의 표시용 이름을 유지한다(후속 표기는 무시, 교정은 관리자 수정으로).
- 원본 표기가 정규화 이름과 동일한 경우(공백 없는 단일어 "비빔밥")? — 표시용 이름과 매칭용 이름이 같은 값으로 저장되며 정상 동작한다.
- 원본 표기가 과도하게 길거나 공백뿐인 경우? — 기존 이름 길이·blank 검증 규칙을 표시용 이름에도 동일하게 적용한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 음식마다 표시용 이름(원본 표기, 띄어쓰기 포함)을 매칭용 정규화 이름과 별도로 보존해야 한다.
- **FR-002**: 스캔 중 미등록 메뉴를 새로 적재할 때, 표시용 이름에는 추출된 원본 메뉴명을, 매칭용 이름에는 정규화 이름을 저장해야 한다.
- **FR-003**: 음식 중복 판정(스캔 매칭·중복 적재 방지)은 변경 전과 동일하게 매칭용 정규화 이름 기준으로 동작해야 한다.
- **FR-004**: 한국 메뉴명을 노출하는 모든 기존 조회 응답은 표시용 이름 값을 내려줘야 하며, 응답 필드 구조(필드명 포함)는 변경하지 않는다.
- **FR-005**: 변경 이전에 적재된 모든 음식은 현재 저장된 이름을 표시용 이름 초기값으로 갖도록 이관되어야 한다(표시용 이름이 빈 음식 0건).
- **FR-006**: 같은 음식으로 매칭되는 다른 원본 표기가 이후에 스캔되어도 기존 표시용 이름을 덮어쓰지 않아야 한다.
- **FR-007**: 표시용 이름에는 기존 음식 이름과 동일한 길이 제한·blank 금지 검증이 적용되어야 한다.

### Key Entities

- **음식(Food)**: 스캔으로 발견되거나 운영이 등록하는 메뉴 항목. 이번 변경으로 이름이 두 역할로 분리된다 — **매칭용 정규화 이름**(중복 방지·스캔 매칭 기준, 유일성 보장)과 **표시용 이름**(화면 노출용 원본 표기).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 변경 후 새로 적재된 음식은 100% 메뉴판 원본 표기(띄어쓰기 포함)로 화면에 노출된다.
- **SC-002**: 표기만 다른 같은 메뉴를 재스캔해도 중복 음식이 0건 생성된다(변경 전과 동일).
- **SC-003**: 한국 메뉴명을 노출하는 기존 조회 화면 전수가 표시용 이름을 내려준다(누락 0건).
- **SC-004**: 기존 클라이언트는 수정 없이 변경 후에도 모든 화면을 정상 이용할 수 있다(응답 구조 비호환 0건).
- **SC-005**: 이관 후 표시용 이름이 비어 있는 음식이 0건이다.

## Assumptions

- 응답 필드명은 기존 그대로 유지한다(클라이언트 무수정 호환) — 값만 표시용 이름으로 교체한다.
- 변경 이전 데이터의 원본 표기는 복원 불가능하므로, 이관 초기값은 현재 저장된 이름이며 표기 교정은 기존 관리자 음식 수정 기능이 담당한다(이번 범위에서 관리자 기능 신규 개발 없음).
- 스캔 이력에는 이미 원본 메뉴명이 별도 보존되고 있으며 이번 변경의 대상이 아니다.
- 중복 판정 기준(정규화 규칙)은 이번 범위에서 변경하지 않는다.
