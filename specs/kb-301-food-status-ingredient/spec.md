# Feature Specification: food 상태 enum 간소화 및 기피성분 컬럼명 ingredient 변경

**Feature Branch**: `kb-301-food-status-ingredient`

**Created**: 2026-08-08

**Status**: Draft

**Input**: User description: "food 테이블의 enum 상태값 종류 변경, 기피성분 칼럼명을 음식의 재료라는 뜻으로 ingredient 로 변경. 음식 콘텐츠 생성이 랭체인(kbap-langchain)으로 이관되어 검수 결과가 pass/fail 로 전달되는 새 파이프라인에 맞춰 상태 모델을 간소화한다. (Jira KB-301)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 랭체인 결과 기반 음식 상태 수명주기 (Priority: P1)

음식 콘텐츠(설명·번역·기피성분)는 더 이상 내부 배치가 단계별로 채우지 않고, 외부 파이프라인(랭체인)이 완성한 결과가 pass/fail 로 한 번에 도착한다. 음식은 이 결과에 따라 단순한 수명주기를 가진다: pass 음식은 이미지 생성 후보(이미지 대기)가 되고, fail 음식은 관리자 리뷰 대상이 되어 이미지 생성에서 제외된다. 이미지까지 채워진 음식은 관리자 승인 대기 상태가 되고, 승인되면 사용자에게 조회 가능해진다.

**Why this priority**: 상태 모델은 음식 도메인의 모든 후속 작업(이미지 생성 후보 선정·관리자 리뷰·승인·사용자 노출)의 기준이다. KB-302(파이프라인 전환)가 이 상태 집합 위에서 동작하므로 먼저 확정되어야 한다.

**Independent Test**: 음식을 각 상태로 만들어 놓고 상태 전이(검수 통과 → 이미지 대기, 검수 실패 → 리뷰 필요, 이미지 부착 → 승인 대기, 승인 → 조회 가능)와 각 상태에서 허용되지 않는 전이가 거부되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 검수 결과가 pass 인 음식, **When** 결과가 적재되면, **Then** 음식은 이미지 생성 후보 상태(PENDING_IMAGE)가 된다
2. **Given** 검수 결과가 fail 인 음식, **When** 결과가 적재되면, **Then** 음식은 관리자 리뷰 필요 상태가 되고 이미지 생성 후보 목록에 나타나지 않는다
3. **Given** 이미지 생성 후보 상태의 음식, **When** 이미지가 부착되면, **Then** 음식은 관리자 승인 대기 상태가 된다
4. **Given** 승인 대기 상태의 음식, **When** 관리자가 승인하면, **Then** 음식은 조회 가능 상태(READY)가 되어 사용자 조회에 노출된다
5. **Given** 조회 가능 상태가 아닌 음식, **When** 사용자가 음식을 조회하면, **Then** 해당 음식은 노출되지 않는다(기존 동작 유지)

---

### User Story 2 - 기피성분 명칭을 ingredient 로 변경 (Priority: P2)

음식의 기피성분 데이터는 실제로는 "음식의 재료(성분) 목록"을 의미한다. 저장 명칭과 응답 명칭을 avoidance(기피) 계열에서 ingredient(재료) 계열로 바꿔 데이터의 의미를 정확히 드러낸다. 기존에 저장된 데이터는 명칭 변경 후에도 그대로 유지된다.

**Why this priority**: 명칭 정합성 작업으로 상태 모델과 독립적으로 배포 가능하지만, 같은 테이블을 손대는 마이그레이션이므로 한 작업으로 묶어 진행한다.

**Independent Test**: 명칭 변경 후 기존 음식의 재료 데이터가 손실 없이 조회되고, 관리자·사용자 응답에 새 명칭으로 노출되는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 기피성분 데이터가 저장된 기존 음식, **When** 명칭 변경이 적용되면, **Then** 동일한 데이터가 ingredient 명칭으로 손실 없이 조회된다
2. **Given** 음식 상세를 조회하는 사용자/관리자, **When** 응답을 받으면, **Then** 재료 목록이 ingredient 계열 명칭으로 노출된다

---

### Edge Cases

- 기존 6개 상태 데이터의 매핑: 동일 의미 상태(READY·PENDING_IMAGE·PENDING_REVIEW)는 유지하고, REVIEWED 는 승인 대기(PENDING_REVIEW)로, REVIEW_REJECTED·INCOMPLETE 는 관리자 확인 필요 상태로 매핑한다.
- 메뉴판 스캔 표시 데이터는 랭체인 결과와 무관한 별개 프로세스다 — 결과 도착 전의 "대기" 상태는 food 상태 집합에 두지 않는다.
- 승인 대기 상태에서 관리자가 반려하면 관리자 확인 필요 상태로 이동한다(가정).
- 관리자 확인 필요 상태의 음식을 관리자가 수정 완료 처리하면 이미지 대기로 진입한다(가정).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 음식 상태 집합은 4개로 재정의한다 — 관리자 확인 필요(fail 결과, FAILED), 이미지 대기(pass 결과, PENDING_IMAGE), 승인 대기(이미지 완료, PENDING_REVIEW), 조회 가능(READY). 랭체인 결과 도착 전을 표현하는 대기 상태는 두지 않는다(스캔 표시는 별개 프로세스).
- **FR-002**: 상태 전이는 다음 규칙만 허용한다 — pass 적재 → 이미지 대기, fail 적재 → 리뷰 필요, 이미지 부착 → 승인 대기, 관리자 승인 → 조회 가능. 정의되지 않은 전이는 거부된다.
- **FR-003**: 리뷰 필요 상태의 음식은 이미지 생성 후보 목록에서 제외된다.
- **FR-004**: 사용자 조회에는 조회 가능 상태의 음식만 노출된다(기존 동작 유지).
- **FR-005**: 기존 상태 데이터는 손실 없이 새 상태로 일괄 매핑된다 — READY→READY, PENDING_IMAGE→PENDING_IMAGE, PENDING_REVIEW·REVIEWED→PENDING_REVIEW, REVIEW_REJECTED·INCOMPLETE→FAILED.
- **FR-006**: 기피성분 저장 명칭을 ingredient 계열로 변경하고, 도메인·관리자 응답·사용자 응답 전체가 새 명칭을 일관되게 사용한다.
- **FR-007**: 명칭 변경 시 기존 기피성분(재료) 데이터는 값 변경 없이 보존된다.
- **FR-009**: 성분 카탈로그 테이블(avoidance_substance, 81종)을 ingredients 로 개명한다 — 사용자 프로필에서는 기피 재료로 연결되지만 음식 관점에서는 재료 카탈로그이기 때문. 회원 기피 설정·판정(avoidance) 어휘와 데이터는 그대로 유지된다.
- **FR-008**: 구 상태 집합에만 존재하던 개념(단계별 텍스트 완성도 판정, 검수 반려 횟수 등)에 의존하는 동작은 새 모델에 맞게 제거되거나 대체된다.

### Key Entities

- **음식(Food)**: 메뉴판에서 인식된 음식 콘텐츠 단위. 상태(수명주기), 이름·설명·번역, 재료(ingredient) 목록, 이미지 참조, 매운맛 정도를 가진다.
- **음식 상태(FoodContentStatus)**: 음식의 수명주기 단계. 새 집합은 관리자 확인 필요(FAILED) / 이미지 대기(PENDING_IMAGE) / 승인 대기(PENDING_REVIEW) / 조회 가능(READY) 4개.
- **재료(ingredient, 구 기피성분)**: 음식에 포함된 성분 목록. 각 항목은 성분 코드·포함 확률을 가지며 사용자별 기피 판정의 입력이 된다.
- **재료 카탈로그(ingredients, 구 avoidance_substance)**: 81종 고정 성분 기준 목록(코드·한국어명·9개 언어 번역). 음식 관점의 재료 사전이며, 회원 프로필의 기피 재료 설정이 이 코드를 참조한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 모든 음식은 언제나 새 상태 집합 중 정확히 하나의 상태를 가진다(마이그레이션 직후 구 상태 잔존 0건).
- **SC-002**: 기존 음식 데이터 전량이 손실 없이 새 상태·새 명칭으로 조회된다(데이터 유실 0건).
- **SC-003**: 사용자에게 노출되는 음식 집합이 변경 전후 동일하다(조회 가능 상태 음식만 노출).
- **SC-004**: 관리자는 상태만으로 후속 작업 대상(이미지 생성 후보·리뷰 대상·승인 대상)을 구분할 수 있다.

## Assumptions

- 이 작업은 상태 모델·명칭 변경(스키마+도메인+응답)까지만 다룬다. 랭체인 호출·아웃박스·결과 수신 API·배치 제거는 KB-302 범위다.
- 메뉴판 스캔 표시와 음식 콘텐츠 파이프라인은 별개 프로세스다 — 랭체인은 서비스의 음식 데이터를 수집하는 파이프라인이고, 스캔은 적재 트리거일 뿐이다(추후 배치 적재로 대체될 수 있음). 따라서 스캔 응답은 food 상태에 의존하지 않는다.
- KB-302 이전에도 코드베이스는 컴파일·테스트 그린을 유지해야 하므로, 구 상태를 참조하던 기존 로직(배치 포함)은 새 상태 집합에 맞게 최소 수정한다.
- 관리자 확인 필요 상태의 명칭은 FAILED 로 확정한다(랭체인 pass/fail 어휘 직결, REVIEW 계열은 승인 축 PENDING_REVIEW 와의 혼동을 피해 배제 — 2026-08-08 사용자 확정).
- 승인 대기에서 관리자 반려 시 관리자 확인 필요 상태로 이동한다.
- 관리자 확인 필요 음식을 관리자가 수정 완료 처리하면 이미지 대기로 진입한다.
- 검수 반려 횟수·반려 사유 필드는 새 모델에서도 관리자 참고 정보로 유지한다.
- 컬럼 명칭은 사용자가 지정한 ingredient 를 기준으로 하되, 목록 의미의 단복수 표기는 구현 시 정한다.
- INCOMPLETE 매핑: 배치가 더 이상 채우지 않아 영구 미완성이 되므로, 관리자 확인 필요로 매핑해 랭체인 재수집 또는 관리자 판단 대상으로 남긴다.
