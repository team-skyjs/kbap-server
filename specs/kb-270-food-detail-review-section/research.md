# Research: 리뷰 개수 조회 전략 — COUNT 집계 vs food 비정규화 컬럼

**Feature**: kb-270-food-detail-review-section | **Date**: 2026-07-31

스펙 FR-006 이 요구하는 "성능 저하 없는 정확한 개수 제공 + 결정 근거 기록"을 두 방식 비교로 확정한다. (사용자 지시: "두 방식에 대해 비교를 해서 계획을 잘 세우자")

## Decision

**현행 COUNT 집계 유지** — `ReviewJpaRepository.aggregateRating`(avg + count 단일 쿼리)을 그대로 쓴다. food 테이블 비정규화 컬럼은 도입하지 않는다. 추가로, 비회원 조회는 집계 자체를 건너뛴다(blur 고정 요약 반환) — 집계 부하가 회원 조회로만 한정된다.

## Rationale — 두 방식 비교

### 결정적 사실: count 는 이미 공짜다

현행 집계 쿼리는 `select avg(r.rating), count(r) ... where food_id = :foodId` — **avg 와 count 가 한 쿼리에서 함께 나온다**. 그런데 평균 별점(전체·같은 국적)은 비정규화가 사실상 불가능하다:

- 전체 평균을 비정규화하려면 sum·count 두 컬럼을 유지해야 하고,
- **같은 국적 평균은 (food × country) 조합별 값이라 food 테이블 컬럼으로 둘 수 없다** — 별도 집계 테이블이 필요하다.

즉 count 만 비정규화해도 **avg 를 위한 집계 쿼리는 그대로 남는다 → 상세 조회의 쿼리 수·비용이 전혀 줄지 않는다**. 비정규화의 이득이 0인 상태에서 비용만 지불하는 구조다.

### 비교표

| 기준 | A. COUNT 집계 유지 (채택) | B. food 비정규화 컬럼 |
|------|---------------------------|----------------------|
| 상세 조회 쿼리 수 | 회원 2회(전체·같은 국적 집계), 비회원 0회 | **동일 2회** — avg 집계가 남으므로 감소 없음 |
| 조회 비용 | `idx_food_review_food_recent(food_id, id)`·`idx_food_review_food_country(food_id, author_country_code)` 인덱스가 WHERE 를 커버 — 음식당 수십~수천 건 규모에서 ms 단위 | count 부분만 무료化 — 체감 차이 없음 |
| 정합성 | **항상 정확** (원장인 food_review 를 직접 집계 — 소프트삭제 `@SQLRestriction` 자동 반영) | 리뷰 생성·삭제 경로가 food UPDATE 를 빠뜨리면 조용히 드리프트 — 검증·보정 장치 추가 필요 |
| 쓰기 경로 | 변경 없음 | 리뷰 생성/삭제마다 인기 음식 row 원자 UPDATE — **row 경합 + 데드락 표면 확대**. 이 도메인은 이미 FK S-lock 데드락 전례(KB-128 랭킹 카운트)가 있어 쓰기 경로에 잠금 접점을 늘리는 선택은 리스크가 실증됨 |
| 팀 규율 정합 | 동시성 방어 수위 원칙(2026-07-30)과 일치 — 비치명 경합을 만들지 않는 쪽이 원칙의 취지 | 원자 UPDATE·경합 방어·동시성 테스트가 따라옴 — "치명 경로에만 최소 방어" 원칙과 어긋나는 투자 |
| 구현 비용 | 0 (현행 유지) | Flyway 마이그레이션 + 기존 데이터 백필 + 생성/삭제 경로 수정 + 드리프트 방어 테스트 |
| 스케일 한계 | 음식당 리뷰 수만~수십만 건이면 집계 지연 체감 가능 | 그 시점엔 count 단독이 아니라 **평균 포함 요약 전체**를 비정규화(별도 집계 테이블 or 캐시)해야 함 — B 안은 그때도 반쪽 해법 |

### 업그레이드 경로 (미래 대비 — 지금은 안 함)

집계 지연이 실측으로 문제 되는 규모(음식당 수만 건+, 상세 조회 p95 악화)가 오면, count 컬럼이 아니라 **리뷰 요약 집계 테이블(food_id, country_code, sum, count)** 또는 캐시(TTL 수 분)로 간다 — 같은 국적 평균까지 한 번에 해결되는 형태여야 해서다. 이는 실측 근거가 생겼을 때의 별도 태스크다.

## Alternatives Considered

- **B. food.review_count 비정규화 컬럼**: 기각 — 위 비교표. 핵심 기각 사유는 "avg 집계가 남아 쿼리 감소가 0"이라는 구조적 무이득.
- **B'. (food, country) 요약 집계 테이블**: 평균까지 해결되는 온전한 비정규화지만, 현재 규모(서비스 초기·음식당 리뷰 수십 건)에서 드리프트 방어·백필·쓰기 결합 비용이 과잉. 업그레이드 경로로만 기록.
- **캐시(Redis TTL)**: "작성 직후 즉시 반영"(FR-005·SC-005) 요구와 충돌 — 무효화 로직을 붙이면 비정규화와 같은 결합이 생김. 기각.
- **비회원에게도 실수치 + 클라이언트 blur**: 응답 스니핑으로 수치 노출 — 서버측 가림 원칙(FR-003) 위반. 기각.

## 부수 결정 (Phase 1 설계 입력)

- **비회원 최적화**: 비회원(`memberId == null`)은 `getFoodRatingSummary` 를 호출하지 않고 `blur=true` + 기본값(0.0·0) 고정 요약을 반환 — 상세 조회 집계 부하가 회원 트래픽으로만 한정된다.
- **0.0 변환 위치**: `RatingSummary`(서비스 내부)는 nullable 유지 — "리뷰 없음"이라는 사실을 잃지 않는다. null→0.0 변환은 응답 경계(`ReviewSummaryResponse` 조립)가 소유한다.
- **회원인데 국적 미보유**: 같은 국적 집계를 건너뛰고(현행 `viewerCountryCode == null` 분기 유지) 응답은 0.0.
