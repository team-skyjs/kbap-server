# Phase 0 Research: 메뉴판 스캔 인식 지시 개선 (kb-239)

**Feature**: kb-239-scan-prompt-ocr-override

Technical Context 에 미해결 NEEDS CLARIFICATION 은 없다. 아래는 프롬프트를 어떻게 고칠지에 대한 결정 기록이다.

## 현재 상태 (변경 대상)

`OpenAiMenuBoardVisionExtractor` 는 시스템 프롬프트(모델 역할·출력 형식·규칙)와 유저 메시지(이미지 + OCR 목록)를 함께 보낸다.

- 시스템 프롬프트의 `name` 규칙: "사진에 표기된 그대로의 메뉴명(외국어 병기 포함)."
- 시스템 프롬프트의 `matchedIdx` 규칙: "이 메뉴에 대응하는 클라이언트 OCR 항목의 idx(정수). 사진 속 위치·텍스트로 판단한다. 대응하는 OCR 항목이 없으면 null."
- 유저 메시지: "아래는 클라이언트가 같은 사진을 OCR 한 결과다(형식 \"idx: 텍스트\")." + `idx: 텍스트` 목록.

**문제**: 어디에도 "이 텍스트는 틀릴 수 있다"는 말이 없다. OCR 목록이 사진과 나란히 제시되면 모델은 그것을 정답 목록처럼 취급해, 오타(예: "김치피개")를 그대로 `name`·`koreanName` 에 옮겨 적을 수 있다. 그 결과 저장된 음식과 매칭되지 않아 위험도가 UNKNOWN 으로 떨어진다.

## Decision 1 — 규칙 본문은 시스템 프롬프트에 둔다

- **Decision**: 오타 고지와 "사진 판독 우선" 규칙을 **시스템 프롬프트의 규칙 목록**에 추가하고, 유저 메시지의 OCR 목록 소개 문장은 표현만 "참고용 메타정보"로 맞춘다.
- **Rationale**: 이 클래스의 규칙은 이미 전부 시스템 프롬프트에 모여 있다(형식·name·koreanName·matchedIdx·비메뉴 제외·price). 규칙을 두 곳에 나누면 나중에 한쪽만 고쳐 어긋난다. 유저 메시지는 요청마다 달라지는 데이터(OCR 목록)를 나르는 자리로 유지한다.
- **Alternatives considered**:
  - 유저 메시지에만 넣기 — 요청 데이터와 정책이 섞이고, 규칙 목록을 읽어선 정책을 알 수 없다.
  - 시스템 프롬프트만 고치고 유저 메시지는 방치 — "클라이언트가 OCR 한 결과다"라는 중립 서술이 여전히 권위처럼 읽혀 규칙과 톤이 충돌한다.

## Decision 2 — `name` 의 출처를 사진으로 못 박는다

- **Decision**: `name` 정의는 그대로 두고(사진에 표기된 그대로), 프롬프트 앞에 `[진실의 출처]` 절을 세워 우선순위를 못 박는다: **사진 픽셀로 판독되는 글자가 최종 근거**, 사진에서 분명히 판독되면 OCR 오탈자를 교정, **판독이 확실치 않으면 OCR 보존**(과교정 금지), 사진에 근거 없는 OCR 항목은 제외.
- **Rationale**: "무조건 사진 우선"만 넣으면 반대 방향 오류가 생긴다 — 모델이 낯선 실재 메뉴("밀냉면"·"짜글이")를 자기가 아는 흔한 이름으로 갈아 끼운다. 교정 권한을 "사진에서 분명히 판독될 때"로 묶는 것이 오타 교정과 과교정 방지를 동시에 얻는 지점이다(최종 프롬프트는 사용자가 작성).
- **Alternatives considered**:
  - 신뢰도 가중("OCR 을 70% 신뢰")·확신도 출력 필드 추가 — 응답 스키마가 늘어나고 FR-005(계약 동결)에 걸린다. 판정 근거도 검증 불가.
  - `koreanName` 만 교정 — 표시명(`name`)에 오타가 남아 사용자에게 그대로 노출된다.

## Decision 3 — `matchedIdx` 는 위치가 아니라 텍스트 내용으로 매칭하고, 커버리지 규칙을 명시한다

- **Decision**: 응답 필드·의미는 그대로 두되(대응 없으면 null), 매칭 기준을 **텍스트 내용**으로 명확화하고 커버리지 규칙을 별도 절로 뺀다 — 사진에서 확인되는 메뉴는 반드시 하나의 result 로 커버, 쪼개진 OCR 조각(예: "삼겹"+"살")은 합쳐 하나의 result + idx 하나만, 한 idx 는 최대 하나의 result 에만(중복 금지).
- **Rationale**: OCR 목록의 순서는 사진 배치와 다를 수 있어 "사진 속 위치로 판단"이 오히려 오매칭을 유도한다. 또 조각 분할·병합 상황에서 규칙이 없으면 같은 메뉴가 여러 result 로 갈라지거나 한 idx 가 중복 사용돼 클라이언트 박스가 어긋난다.
- **Alternatives considered**: 좌표를 받아 매칭 자체를 바꾸는 안 — KB-239 범위 축소 결정으로 제외(spec Assumptions). 프롬프트 개선 효과를 먼저 측정한다.

## Decision 4 — "결과의 기준은 사진" 을 명시한다

- **Decision**: 비메뉴 제외 규칙 옆에 **OCR 항목마다 결과를 만들지 않는다**(결과 목록은 사진에서 추출한 메뉴 기준)를 명시한다.
- **Rationale**: 사진 우선을 강조하면 모델이 "OCR 목록을 사진으로 교정해 전부 되돌려주는" 방향으로 해석할 수 있다. 그러면 상호·원산지·영업시간 같은 노이즈가 결과로 새어 들어와 US2(회귀 방지)가 깨진다.
- **Alternatives considered**: 아무 말도 하지 않기 — 현재도 비메뉴 제외 규칙이 있어 대체로 동작하지만, 지시문 톤이 바뀌는 변경에서 방어 문장 없이 가는 것은 회귀 위험을 감수하는 선택이다.

## Decision 5 — 프롬프트 문구는 단위 테스트 대상이 아니다

- **Decision**: 프롬프트 문자열을 검증하는 테스트를 두지 않는다. 기존 테스트(비용 이벤트·파싱·실패 격리)는 그대로 유지한다.
- **Rationale**: 프롬프트 문자열을 assert 하는 테스트는 "내가 쓴 문장이 그 자리에 있다"를 확인할 뿐, 이 변경이 노리는 결과(모델이 오타를 교정하는가)는 전혀 보장하지 못한다. 문구를 다듬을 때마다 같이 고쳐야 하는 유지 비용만 남는다. 로직 분기가 없는 문자열 상수 변경이므로 검증은 실사진 확인이 유일하게 의미 있는 수단이다(사용자 결정).
- **Alternatives considered**:
  - 실제 모델 호출 통합 테스트 — 비용·비결정성·외부 의존으로 CI 부적합(기존 `LlmSmokeTest` 도 수동 실행 계열이다).
  - 규칙 문구 부분 문자열 assert — 위 이유로 폐기.

## 검증 방법

이 변경의 유일한 검증은 **실사진 표본 수동 확인**(SC-001~SC-005)이다. 절차는 [quickstart.md](quickstart.md) 에 둔다. 기존 자동 테스트는 회귀 가드로만 기능한다(`./gradlew build` 무수정 통과).
