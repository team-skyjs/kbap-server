# Feature Specification: 주문 1시간 후 리뷰 리마인더 푸시 배치 (REVIEW_REMINDER)

**Feature Branch**: `kb-469-review-reminder-batch`

**Created**: 2026-09-28

**Status**: Draft

**Input**: User description: "KB-469 REVIEW_REMINDER 배치 — 주문 1시간 후 리뷰 리마인더 푸시. FE 가 주문 완료 시 기기 로컬 알림으로 예약하던 '1시간 후 리뷰 리마인더' 를 서버 배치로 옮긴다. 대상은 주문 생성 후 1시간 이상 25시간 이하 경과한 회원 주문. 그 회원에게 주문 이후 REVIEW_REMINDER 알림이 이미 있거나 항목 음식 전부에 리뷰가 있으면 제외. 대표 음식을 고르지 않고 주문 자체에 대한 리뷰를 요청한다. 중복 방지는 알림 테이블 not exists. 푸시 data 는 orderId 만(foodId 없음), 알림함 응답에 orderId 필드 추가(REVIEW_REMINDER 만 non-null). 문구를 주문 맥락으로 교체. 5분 주기 cron + HTTP 트리거, 기존 스캔 제안 배치와 같은 구조, ttl 설정값. 게스트 주문 제외. 범위 밖: FE 변경(KB-500)·PushTrigger sealed 리팩터·ShedLock·orders 발송 마커 컬럼." — Jira KB-469.

## 배경

앱은 지금 주문을 완료하는 순간 **기기 안에서 로컬 알림**을 예약해 1시간 뒤 "리뷰를 남겨 달라" 고 띄운다. 이 방식은 서버가 모르는 알림이라 알림함에 남지 않고, 앱을 지우거나 기기를 바꾸면 사라지며, 이미 리뷰를 쓴 뒤에도 그대로 뜬다.

주문은 이미 서버에 저장된다(회원 주문만 — 주문 행은 항상 회원에게 속한다). 알림 유형 `REVIEW_REMINDER` 도 이미 있다 — 활동 알림(비광고)이며 활동 토글로 발송 여부를 판정하고, 별도 동의는 받지 않는다. 푸시 문구 템플릿(3변형 × 10개 언어 파일 — 현재는 `{food}` 인자를 받는 스캔 맥락 문구), 알림함의 `foodId` 노출(KB-575), 앱의 딥링크도 이미 있다.

이 기능은 그 리마인더를 **서버 배치가 보내는 푸시**로 옮긴다. 배치가 5분마다 "1시간 이상 지났고, 아직 리마인더를 받지 않았고, 리뷰를 다 쓰지 않은" 주문을 골라 **그 주문에 대한** 리뷰 리마인더를 보낸다. 음식 하나를 대표로 고르지 않는다 — 리마인더는 주문 단위이고 앱 착지도 주문 상세다. 앱의 로컬 리마인더를 끄는 일(KB-500)은 이 기능이 dev 에 배포된 뒤 앱 팀이 진행한다.

## 확정 결정

| 항목 | 결정 |
|------|------|
| 대상 주문 | 회원 주문 중 생성 시각이 지금 기준 **1시간 이상 25시간 이하** 경과한 것. 25시간 상한은 기기가 없거나 활동 토글을 끈 회원의 주문을 영원히 재스캔하지 않기 위한 창이다 |
| 제외 1 — 이미 리마인더 받음 | 그 회원에게 **주문 생성 시각 이후에 만들어진 `REVIEW_REMINDER` 알림**이 하나라도 있으면 제외. 같은 주문의 중복을 막고, 1시간 안에 여러 번 주문해도 리마인더는 1건만 간다 |
| 제외 2 — 리뷰 다 씀 | 주문 항목의 음식 **전부**에 그 회원의 리뷰가 이미 있으면 제외 |
| 대표 음식 | **고르지 않는다.** 리마인더는 주문 단위 — 문구에 음식명을 넣지 않고 푸시 data 에 `foodId` 도 담지 않는다. 어떤 음식에 리뷰를 쓸지는 회원이 주문 상세에서 고른다 |
| 중복 방지 수단 | 알림 테이블에 "없음" 조건으로 판정(소식 알림의 미발송 회원 조회와 같은 패턴). **주문 테이블에 발송 마커 컬럼을 두지 않는다** |
| 발송 실패 후 | 실패한 알림은 기존 파이프라인이 알림함 행을 소프트 삭제하므로, 다음 주기에 다시 대상이 되어 자연 재시도된다 |
| 게스트 주문 | 대상 아님(주문 자체가 회원 전용). 이 결정을 KB-469 코멘트로 남긴다 |
| 푸시 `data` | `{ type: "REVIEW_REMINDER", orderId, notificationId }`. `orderId` 는 **숫자(64비트 정수)** — `notificationId` 와 같은 타입. `foodId` 없음. 앱 착지는 주문 상세(`/profile/order/{orderId}`) — KB-500 전의 앱은 `foodId` 가 없어 폴백 라우팅이 동작하지 않으므로, 이 배치는 KB-500 배포와 발맞춰 켠다 |
| 알림함 응답 | 최근 알림 목록·읽음 처리 응답에 `orderId` 필드 추가. `REVIEW_REMINDER` 일 때만 발송 data 의 orderId, 그 외 유형은 null. `foodId` 와 같은 규칙(정수·정수 문자열 허용, 아니면 null). 기존 `foodId` 필드는 그대로 두되 이 배치의 알림에서는 null 이다. API 버전은 올리지 않는다 |
| 문구 | **본문만** "스캔한 {food}" 맥락에서 **주문 맥락**으로 교체한다 — 제목 3변형은 스캔 맥락이 없어 그대로 둔다. 3변형 × 모든 언어 파일. **`{food}` 인자를 없앤다**(문구에 음식명 없음). 대상 창이 1~25시간이라 "아까" 같은 시간 부사는 쓰지 않는다. 한국어 초안: ① "주문하신 식사, 맛있게 드셨나요? 리뷰로 알려 주세요." ② "주문하신 메뉴가 어땠는지 한 문장만 남겨 주세요." ③ "주문하신 음식 경험을 리뷰로 나눠 주세요. 다음 사람에게 도움이 돼요." — **문구는 구현을 먼저 끝낸 뒤 다듬는다** |
| 주기 | **5분 cron** + HTTP 트리거 병행. 배치 1대 전제라 분산 락 없음. 부팅 시 자동 실행 금지 |
| 구조 | 기존 스캔 제안 배치와 같은 리더/라이터 구조, 공용 발송기로 발송, 청크 100, 발송 메트릭에 `type=REVIEW_REMINDER` 로 집계 |
| 발송 단위 | **주문 1건 = 발송 요청 1건.** 발송 요청은 `data` 를 하나만 가지므로 주문마다 다른 `orderId` 를 실으려면 회원을 묶을 수 없다(스캔 제안은 회원 100명을 요청 하나로 묶는다). 청크 100 이면 외부 푸시 호출도 최대 100번 — 물량이 적어 감수한다 |
| `foodId` 정리 | 현재 `foodId` 를 푸시 data 에 넣는 발송처는 없다(도움돼요는 `reviewId`). 알림함 응답의 `foodId` 필드는 유지하되 KB-468 계약 문서와 알림함 API 문서에서 "REVIEW_REMINDER 가 채운다" 는 설명을 **미사용**으로 정정한다 |
| 만료(ttl) | 1시간 뒤 문맥 문구라 하루를 넘겨 뜨지 않도록 푸시에 만료 시간을 둔다. 설정값, 기본 수 시간 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 주문 1시간 뒤 리뷰 리마인더를 받는다 (Priority: P1)

회원이 앱에서 주문을 저장한다. 1시간쯤 뒤 "주문하신 식사, 맛있게 드셨나요? 리뷰로 알려 주세요." 푸시가 오고, 탭하면 그 주문의 상세로 간다. 알림함에도 같은 알림이 남는다.

**Why this priority**: 이 기능의 존재 이유. 로컬 알림을 서버 푸시로 옮기는 핵심 흐름이다.

**Independent Test**: 유효 기기를 가진 회원의 주문을 1시간 전 시각으로 만들고 배치를 실행하면, 그 회원의 기기로 `REVIEW_REMINDER` 푸시 1건이 나가고 알림함 행이 생긴다.

**Acceptance Scenarios**:

1. **Given** 유효 기기·활동 토글 켜진 회원의 주문이 70분 전에 저장됐고 항목 음식 어느 것에도 리뷰가 없다, **When** 배치가 돈다, **Then** 그 회원에게 `REVIEW_REMINDER` 푸시 1건이 나가고 문구는 기기 언어의 주문 맥락 문구이며, 푸시 data 에 `type`·`orderId`(숫자)·`notificationId` 가 모두 있고 `foodId` 는 없다.
2. **Given** 위와 같은 주문, **When** 배치가 돈다, **Then** 푸시 봉투의 채널은 활동 알림 채널(`activity`)이고 제목·본문에 광고 표기가 붙지 않는다.
3. **Given** 주문이 30분 전에 저장됐다, **When** 배치가 돈다, **Then** 아무것도 보내지 않는다(1시간 미경과).
4. **Given** 주문이 26시간 전에 저장됐고 리마인더를 받은 적이 없다, **When** 배치가 돈다, **Then** 아무것도 보내지 않는다(25시간 창 초과).

---

### User Story 2 - 같은 회원에게 리마인더가 두 번 가지 않는다 (Priority: P1)

배치가 5분마다 돌아도, 그리고 회원이 짧은 시간에 여러 번 주문해도, 리마인더는 한 번만 온다. 이미 리뷰를 다 쓴 주문에는 오지 않는다.

**Why this priority**: 중복 푸시는 즉시 알림 끄기·앱 삭제로 이어진다. P1 과 함께 있어야 출시 가능하다.

**Independent Test**: 같은 주문으로 배치를 두 번 실행하면 발송은 1건뿐이다.

**Acceptance Scenarios**:

1. **Given** 70분 전 주문에 대해 배치가 이미 리마인더를 보냈다, **When** 5분 뒤 배치가 다시 돈다, **Then** 같은 주문으로 다시 보내지 않는다.
2. **Given** 한 회원이 70분 전과 65분 전에 주문 두 건을 저장했다, **When** 배치가 돈다, **Then** 리마인더는 1건만 나간다. 두 번째 주문은 첫 리마인더가 주문 시각 이후에 생성됐으므로 제외된다.
3. **Given** 70분 전 주문의 항목이 음식 A·B 이고 회원이 A·B 모두에 리뷰를 썼다, **When** 배치가 돈다, **Then** 보내지 않는다.
4. **Given** 70분 전 주문의 항목이 A·B 이고 A 에만 리뷰가 있다, **When** 배치가 돈다, **Then** 리마인더 1건이 나간다(아직 리뷰 안 쓴 항목이 남아 있다).
5. **Given** 리마인더 발송이 실패해 알림함 행이 소프트 삭제됐다, **When** 다음 주기에 배치가 돈다, **Then** 그 주문이 다시 대상이 되어 재발송을 시도한다.

---

### User Story 3 - 알림함에서 주문으로 간다 (Priority: P2)

회원이 알림함에서 리뷰 리마인더 항목을 탭하면 앱이 그 주문의 상세로 이동할 수 있도록, 알림함 응답에 주문 id 가 실린다.

**Why this priority**: 푸시를 놓친 회원의 재진입 경로. 푸시 발송(P1) 없이는 의미가 없어 P2.

**Independent Test**: `REVIEW_REMINDER` 알림 행을 만들고 알림함 목록·읽음 처리 응답을 조회하면 `orderId` 가 있고, 다른 유형의 항목은 `orderId` 가 null 이다.

**Acceptance Scenarios**:

1. **Given** 발송 data 에 `orderId=12` 가 담긴 `REVIEW_REMINDER` 알림이 있다, **When** 최근 알림 목록을 조회한다, **Then** 그 항목의 `orderId` 는 12 이고 `foodId` 는 null 이다(발송 data 에 없음).
2. **Given** 같은 알림, **When** 읽음 처리한다, **Then** 응답에도 `orderId=12` 가 있다.
3. **Given** `NEWS` 유형 알림이 있다, **When** 목록을 조회한다, **Then** 그 항목의 `orderId` 는 null 이다.
4. **Given** `REVIEW_REMINDER` 알림의 data 에 `orderId` 가 없거나 정수가 아니다(방어), **When** 목록을 조회한다, **Then** `orderId` 는 null 이고 응답은 정상이다.

---

### User Story 4 - 주문 맥락의 문구를 본다 (Priority: P2)

리마인더 문구가 "스캔한 {음식}" 이 아니라 "주문하신 식사" 맥락으로, 음식명 없이 온다. 기기 언어별로 3변형 중 하나가 온다.

**Why this priority**: 스캔 맥락 문구가 주문 리마인더로 오면 어색하지만, 발송 자체는 동작한다.

**Independent Test**: 모든 언어 파일의 리뷰 리마인더 3변형 제목·본문에 "스캔" 계열 표현과 `{food}` 인자가 없다.

**Acceptance Scenarios**:

1. **Given** 기기 언어가 한국어인 회원, **When** 리마인더가 온다, **Then** 본문은 주문 맥락(예: "주문하신 식사, 맛있게 드셨나요? 리뷰로 알려 주세요.")이고 음식명·시간 부사가 들어가지 않는다. 제목은 기존 3변형 그대로다.
2. **Given** 기기 언어가 영어인 회원, **When** 리마인더가 온다, **Then** 영어 주문 맥락 문구가 온다.

---

### Edge Cases

- 주문 항목이 0건인 주문(방어): 리뷰를 쓸 항목이 없으므로 보내지 않는다("리뷰 안 쓴 항목이 하나라도 있다" 조건에 흡수).
- 항목 음식이 삭제(소프트)됐으면: 문구에 음식명을 쓰지 않으므로 발송에는 영향이 없다. 리뷰 유무 판정만 그 음식 id 로 한다.
- 회원의 유효 기기가 0대이거나 활동 토글이 꺼져 있으면: 알림함 행도 푸시도 만들지 않는다(기존 대상 판정). 이 주문은 25시간 창이 닫힐 때까지 매 주기 조회되지만 아무 일도 하지 않는다 — 창이 그 비용의 상한이다.
- 배치가 멈췄다가 복구돼 24시간 넘게 지난 주문이 남아 있으면: 25시간 창 안의 것만 보내고, 창을 넘긴 주문은 영구 제외된다.
- 푸시 만료 시간이 지나도록 기기가 오프라인이면: 푸시는 도착하지 않지만 알림함 행은 남는다. 재발송은 하지 않는다(발송 자체는 성공이었다).
- 같은 주기에 배치가 겹쳐 실행되면(HTTP 트리거 + cron): 배치 1대 전제라 잡 인스턴스가 이미 실행 중이면 두 번째 기동은 거부된다(기존 런처 동작). 분산 락은 두지 않는다.
- 회원이 탈퇴(비활성)했으면: 대상 판정에서 빠진다(기존 규칙).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 5분마다 리뷰 리마인더 배치를 실행해야 하며, 같은 배치를 HTTP 트리거로도 실행할 수 있어야 한다. 앱 부팅 시 자동 실행하지 않는다.
- **FR-002**: 배치는 생성 시각이 실행 시점 기준 1시간 이상 25시간 이하 경과한 회원 주문만 대상으로 삼아야 한다.
- **FR-003**: 배치는 그 회원에게 주문 생성 시각 이후에 만들어진 `REVIEW_REMINDER` 알림이 하나라도 있는 주문을 제외해야 한다.
- **FR-004**: 배치는 주문 항목의 음식 전부에 그 회원의 리뷰가 있는 주문을 제외해야 한다.
- **FR-005**: 배치는 대상 주문마다 `REVIEW_REMINDER` 유형으로 회원의 유효 기기 각각에 기기 언어 문구를 렌더해 발송해야 하며, 문구에 음식명을 넣지 않는다(대표 음식 선택 없음).
- **FR-006**: 푸시 data 는 `type="REVIEW_REMINDER"`, `orderId`(주문 id, 숫자), `notificationId`(알림함 행 id) 를 담아야 하며 `foodId` 는 담지 않는다. 배치는 주문 1건마다 발송 요청 1건을 만든다.
- **FR-007**: 리마인더 푸시는 활동 알림 채널(`activity`)로 나가야 하며 광고 표기·수신거부 안내를 붙이지 않아야 한다.
- **FR-008**: 시스템은 주문 테이블에 발송 여부 컬럼을 추가하지 않고, 알림 테이블의 존재 여부만으로 중복을 막아야 한다.
- **FR-009**: 발송 실패로 알림함 행이 소프트 삭제된 주문은 다음 주기에 다시 대상이 되어야 한다.
- **FR-010**: 리마인더 푸시에는 만료 시간을 설정값으로 둬야 하며 기본값은 수 시간이고 24시간 미만이어야 한다.
- **FR-011**: 배치는 청크 100 단위로 조회·발송해야 하며, 발송 결과를 기존 푸시 발송 메트릭에 `type=REVIEW_REMINDER` 로 집계해야 한다.
- **FR-012**: 알림함 최근 목록·읽음 처리 응답의 각 항목에 `orderId` 필드가 있어야 하며, `REVIEW_REMINDER` 유형이고 발송 data 의 `orderId` 가 정수 또는 정수 문자열일 때만 값을 채우고 그 외에는 null 이어야 한다. API 버전은 올리지 않는다.
- **FR-013**: 알림함 API 문서(스키마·예시)에 `orderId` 를 반영하고, `foodId` 설명을 "REVIEW_REMINDER 가 채운다" 에서 미사용(항상 null)으로 정정해야 한다.
- **FR-014**: 리뷰 리마인더 **본문** 3변형을 모든 언어 파일에서 주문 맥락으로 교체하고 `{food}` 인자를 제거해야 한다. 제목은 유지한다. 최종 문구 다듬기는 구현 완료 후 별도로 한다.
- **FR-015**: KB-468 의 푸시 data 계약 문서에 `orderId`(숫자) 를 추가하고 `foodId` 행을 미사용으로 정정하며, 그 변경과 "게스트 주문은 대상이 아니다" 결정을 KB-469 코멘트로 남겨야 한다.
- **FR-016**: 배치는 단일 인스턴스 전제이며 분산 락을 두지 않는다.

### Key Entities

- **주문(Order)**: 회원이 저장한 식사 주문. 회원 id·생성 시각을 가진다. 리마인더 대상 판정의 기준 시각은 생성 시각이다.
- **주문 항목(OrderItem)**: 주문에 속한 음식 한 줄. 음식 id 를 가진다. "리뷰 안 쓴 항목이 남아 있는가" 판정의 대상이다.
- **리뷰(Review)**: 회원이 음식에 남긴 평가. 회원 id + 음식 id 로 "이 항목에 리뷰가 있는가" 를 판정한다.
- **알림(Notification)**: 알림함 행. 유형·회원·기기·생성 시각·발송 data 를 가진다. `REVIEW_REMINDER` 행의 존재가 중복 판정의 근거이고, data 의 `orderId` 가 알림함 응답으로 노출된다.
- **발송 요청(PushRequest)**: 트리거가 발송기에 넘기는 유형·문구 인자·data 묶음. 이 기능은 `orderId` 를 data 에 추가한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 리마인더 대상 조건을 만족하는 주문은 조건 충족 후 5분 이내(배치 주기 1회)에 리마인더가 발송된다.
- **SC-002**: 같은 주문에 대해 배치를 여러 번 실행해도 발송되는 리마인더는 정확히 1건이다.
- **SC-003**: 한 회원이 1시간 안에 여러 번 주문해도 리마인더는 1건이다.
- **SC-004**: 주문 항목 전부에 리뷰가 있는 주문·1시간 미경과 주문·25시간 초과 주문에는 0건 발송된다.
- **SC-005**: 발송된 모든 리마인더의 data 에 `orderId` 가 있고, 알림함 응답에서 `REVIEW_REMINDER` 항목만 `orderId` 가 non-null 이다.
- **SC-006**: 모든 언어 파일의 리뷰 리마인더 제목·본문에 "스캔" 맥락 표현과 `{food}` 인자가 남지 않는다. 렌더러는 인자 없는 자리표시자를 빈 문자열로 채워 조용히 깨지므로 이 조건은 테스트로 강제한다.
- **SC-007**: 앱 팀이 로컬 리마인더를 끈 뒤(KB-500) 회원이 받는 리뷰 리마인더 수는 주문당 최대 1건으로 유지된다.

## Assumptions

- 주문 항목의 음식은 저장 시점에 확정된 음식 id 이며, 리뷰 유무는 "그 회원 + 그 음식" 의 활성 리뷰 존재로 판정한다.
- 문구 파일은 현재 10개 언어(ko·en·es·ru·id·ja·th·vi·zh_Hans·zh_Hant)에 리뷰 리마인더 키가 있다. 사용자 입력의 "5개 언어" 는 기존 키가 있는 모든 언어 파일을 뜻하는 것으로 본다 — 전부 교체한다.
- 푸시 만료 기본값은 6시간으로 둔다(설정으로 변경 가능, 24시간 미만).
- "주문 생성 시각 이후" 의 비교는 알림 행의 생성 시각 기준이며, 기기별 알림 행 중 하나라도 있으면 "이미 받음" 이다.
- 25시간 창 안의 미발송 주문(기기 없음·토글 off)이 매 주기 조회되는 비용은 감수한다.
- 배치 앱은 항상 떠 있고 잡은 스케줄러·HTTP 트리거로만 기동한다(기존 운영 규칙). 배치는 1대다.
- 알림함 `orderId` 추출은 `foodId` 와 같은 규칙(정수·정수 문자열 허용, 아니면 null)이며 API 버전 헤더 값은 바뀌지 않는다. 보내는 쪽은 항상 숫자로 넣는다.
- 중복 판정과 재시도(FR-009)는 실패 알림 행이 소프트 삭제(status=DELETED)된다는 사실에 기댄다 — 판정 쿼리는 활성 알림 행만 봐야 한다.
- "리뷰 안 쓴 항목이 남은 주문" 을 창 안에서 한 번에 뽑는 조회는 현재 없어 새로 만든다(리뷰 유무는 회원 id + 음식 id 로 판정).
- FE 착지 변경·로컬 리마인더 폐기는 KB-500 이 담당하며, 이 기능이 dev 에 배포된 뒤 진행한다. 푸시 data 에 `foodId` 가 없으므로 KB-500 전의 앱은 리마인더를 탭해도 음식 상세로 가지 못한다 — prod 에서 배치를 켜는 시점은 KB-500 릴리스에 맞춘다.

## 범위 밖

- 앱(FE) 변경 — KB-500.
- 발송 요청 페이로드를 유형별 sealed 타입으로 바꾸는 리팩터 — 별도 티켓.
- 분산 락(ShedLock).
- 주문 테이블의 발송 마커 컬럼.
- 게스트 주문 리마인더.
