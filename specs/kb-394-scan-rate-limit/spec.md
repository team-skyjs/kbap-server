# Feature Specification: 스캔 rate-limit 을 "인식 실패"와 분리 — OpenAI 429 전용 에러코드·로그·재시도 방침

## 배경

메뉴판 스캔은 사진을 외부 비전 모델(OpenAI)에 보내 메뉴를 읽는다. KB-393 부하 테스트에서 벤더의 **요청 한도 초과(429 rate-limit)** 를 일으켜 보니, 사용자에게는 "메뉴판 인식에 실패했습니다"(SCAN-002)가 나가고 서버 로그에도 "메뉴판 비전 인식 실패" WARN 만 남았다. 원인은 비전 어댑터가 일시 장애(`TransientAiException`·네트워크)만 "서버 장애"(SCAN-006)로 구분하고, 그 밖의 모든 예외 — 벤더 429 포함 — 를 "인식 실패"로 뭉개기 때문이다.

결과로 두 가지 오해가 생긴다:
- **사용자**: 사진을 다시 찍어도 소용없는데 "인식 실패" 문구 때문에 사진 품질 문제로 여긴다.
- **운영자**: WARN 로그가 사진 품질 문제와 구분되지 않아 벤더 한도 초과를 인지하지 못한다.

429 에는 두 갈래가 있다:
- **비일시적(non-transient)** — 한 요청의 토큰이 분당 토큰 한도(TPM)를 넘는 경우. 재시도해도 같은 결과라 벤더 클라이언트가 즉시 실패시킨다. 사용자 체감은 "1초 만에 인식 실패".
- **일시적(transient)** — 분당 요청 수(RPM) 초과. 재시도로 회복되므로 현재는 프레임워크 기본 재시도(백오프)가 돌아 스캔이 수 초~수 분 늦어진 뒤 "서버 장애"(SCAN-006)로 끝난다.

이 기능은 rate-limit 을 인식 실패·서버 장애와 **구분해 사용자·운영자에게 드러내고**, 두 갈래의 처리 방침을 정한다. 벤더 한도 자체를 올리는 것은 범위 밖이다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 사용자는 rate-limit 을 "인식 실패"가 아니라 "잠시 후 재시도"로 안내받는다 (Priority: P1)

스캔이 벤더 한도 초과로 실패하면 앱은 "일시적으로 요청이 많습니다. 잠시 후 다시 시도해 주세요" 류의 안내를 받고, 사진을 다시 찍을 필요가 없음을 안다. 무료 스캔 횟수는 차감되지 않는다.

**Why this priority**: 잘못된 안내("사진을 다시 찍어라")가 사용자에게 헛수고를 시키는 것이 이 기능의 존재 이유.

**Independent Test**: 비전 어댑터가 벤더 429 를 받도록 만든 통합 테스트에서 응답 코드가 **rate-limit 전용 코드**이고 SCAN-002·SCAN-006 이 아니며, 스캔 횟수가 그대로다.

**Acceptance Scenarios**:

1. **Given** 벤더가 요청 한도 초과(429)로 즉시 거절하는 상태, **When** 사용자가 스캔하면, **Then** 응답은 rate-limit 전용 에러코드와 "요청이 많아 잠시 후 다시 시도" 취지의 메시지이며 SCAN-002("인식 실패")·SCAN-006("서버 장애")이 아니다.
2. **Given** 같은 상황, **When** 스캔이 실패하면, **Then** 사용자의 스캔 횟수는 차감되지 않는다(스캔 티켓 예약이 해제된다).
3. **Given** 벤더가 정상 응답하거나 다른 종류의 오류(일시 장애·인식 불가)를 내는 상태, **When** 스캔하면, **Then** 기존 코드(성공·SCAN-006·SCAN-002·SCAN-003)가 그대로 나간다 — 회귀 없음.

---

### User Story 2 - 운영자는 로그에서 rate-limit 을 한눈에 구분한다 (Priority: P1)

운영자가 로그 수집기에서 스캔 실패를 볼 때 rate-limit 건은 "메뉴판 비전 인식 실패"와 다른 메시지·마커로 나타나고, 벤더가 준 정보(남은 한도·재시도 권고 시각)가 있으면 함께 남는다.

**Why this priority**: 한도 초과는 벤더 플랜·트래픽 대응이 필요한 운영 신호인데 지금은 완전히 묻힌다. US1 과 같은 코드 경로에서 나오므로 함께 P1.

**Independent Test**: 429 시나리오에서 남는 로그 한 줄에 rate-limit 을 뜻하는 고정 문구/키가 있고, "메뉴판 비전 인식 실패" 문구는 없다.

**Acceptance Scenarios**:

1. **Given** 벤더 429, **When** 스캔이 실패하면, **Then** 로그에 rate-limit 임을 뜻하는 고정 마커(예: `vision rate-limit`)와 갈래(즉시 거절/재시도 소진), 벤더가 준 `Retry-After`·남은 한도 값(있을 때)이 구조화 필드로 남는다.
2. **Given** 사진 품질 문제로 벤더가 응답은 했으나 메뉴를 못 읽은 경우, **When** 스캔이 실패하면, **Then** 로그는 기존 "메뉴판 비전 인식 실패" 그대로이고 rate-limit 마커가 붙지 않는다.

---

### User Story 3 - 일시적 429 는 짧게 재시도하고, 그래도 안 되면 같은 안내로 끝난다 (Priority: P2)

분당 요청 수 초과처럼 잠깐 기다리면 풀리는 429 는 서버가 짧게 재시도해 사용자가 모르게 성공시키되, 상한(총 대기 시간)을 넘기면 수 분을 붙들지 않고 rate-limit 안내로 끝낸다.

**Why this priority**: 지금은 프레임워크 기본 재시도가 수 분까지 늘어져 "1초 실패"의 반대 극단이 된다. 비일시적 갈래(US1)를 먼저 고친 뒤 상한을 정한다.

**Independent Test**: 벤더가 처음 N번 429 를 내고 그 뒤 성공하는 페이크로 (a) 상한 안에서 성공, (b) 상한을 넘기면 rate-limit 코드로 실패하며 총 소요가 상한 이하임을 확인.

**Acceptance Scenarios**:

1. **Given** 벤더가 첫 시도에 일시적 429, 두 번째에 성공, **When** 스캔하면, **Then** 사용자는 성공 응답을 받고 총 소요는 재시도 상한 안이다.
2. **Given** 벤더가 상한 동안 계속 일시적 429, **When** 스캔하면, **Then** 총 대기가 상한(가정: 10초)을 넘기지 않고 rate-limit 전용 코드로 실패한다 — SCAN-006 이 아니다.
3. **Given** 벤더가 비일시적 429(요청 > TPM), **When** 스캔하면, **Then** 재시도 없이 즉시 rate-limit 코드로 실패한다.

---

### User Story 4 - (선택) 벤더 재시도 권고를 사용자 안내에 반영한다 (Priority: P3)

벤더가 `Retry-After` 를 주면 응답에 "N초 후 재시도" 값을 실어 앱이 버튼 비활성화·카운트다운에 쓸 수 있게 한다.

**Why this priority**: 있으면 좋지만 벤더가 항상 주지 않고, 앱 변경이 따른다. 서버는 값이 있을 때만 싣는다.

**Independent Test**: `Retry-After: 20` 을 낸 429 시나리오에서 응답 payload 에 `retryAfterSeconds: 20` 이 있고, 헤더가 없으면 payload 가 비어 있다.

**Acceptance Scenarios**:

1. **Given** 벤더 429 응답에 `Retry-After` 가 있음, **When** 스캔이 실패하면, **Then** 에러 응답 payload 에 재시도 권고 초가 들어간다.
2. **Given** 헤더가 없음, **When** 실패하면, **Then** payload 없이 코드·메시지만 나간다.

---

### Edge Cases

- 벤더가 429 이외의 비일시적 오류(인증 실패 401·요청 형식 400·모델 없음 404)를 내면: 이 기능의 범위 밖 — 오늘처럼 "인식 실패"(SCAN-002)로 나간다. 단, 로그의 예외 원인은 그대로 남아 운영자가 구분할 수 있다.
- 재시도 중 사용자가 앱을 닫아도 서버 재시도는 상한까지 돌 수 있다 — 상한이 짧아(가정 10초) 자원 낭비가 제한된다.
- 여러 사용자가 동시에 한도에 걸리면 모두 같은 안내를 받는다 — 서버 측 사전 스로틀·큐잉은 범위 밖(로그 마커로 빈도를 관측한 뒤 별도 판단).
- 스캔 v1(무버전, 티켓 없음)과 v2(티켓·예약) 모두 같은 서비스 경로를 타므로 코드 매핑은 동일하며, 횟수 미차감은 v2 의 예약 해제로 보장된다.
- 벤더 클라이언트가 429 를 프레임워크의 "비일시적 예외"로 감싸서 던질 수도, 원 예외를 그대로 던질 수도 있다 — 어느 형태든 rate-limit 으로 식별해야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 벤더 요청 한도 초과(429)로 스캔이 실패하면 **전용 에러코드**(SCAN 계열 신규, 번호는 채번 규칙대로)로 응답하고, 메시지는 "일시적으로 요청이 많습니다. 잠시 후 다시 시도해 주세요" 취지여야 한다. SCAN-002·SCAN-006 을 재사용하지 않는다.
- **FR-002**: rate-limit 실패는 스캔 횟수를 차감하지 않아야 한다(v2: 예약 해제, v1: 증가 없음).
- **FR-003**: 서버 로그에 rate-limit 건은 "메뉴판 비전 인식 실패"와 다른 고정 마커·메시지로 남기고, 갈래(즉시 거절 / 재시도 소진)와 벤더 제공 정보(`Retry-After`·남은 한도, 있을 때)를 함께 남겨야 한다.
- **FR-004**: 비일시적 429(요청 > 분당 토큰 한도)는 재시도 없이 즉시 FR-001 로 응답해야 한다.
- **FR-005**: 일시적 429(분당 요청 수 초과)는 총 대기 상한 안에서 재시도하고, 상한을 넘기면 FR-001 로 응답해야 한다. 상한은 설정값이며 기본 10초로 가정한다.
- **FR-006**: 429 를 벤더 클라이언트가 어떤 예외 형태로 던지든(원 예외·프레임워크 래핑) rate-limit 으로 식별해야 한다.
- **FR-007**: 벤더가 재시도 권고 시각(`Retry-After`)을 주면 에러 응답 payload 에 초 단위로 실어야 하고, 없으면 payload 를 비운다. (US4, 선택)
- **FR-008**: 다른 실패 경로(SCAN-002 인식 실패·SCAN-003 미검출·SCAN-006 서버 장애)의 응답·로그는 바뀌지 않아야 한다.
- **FR-009**: 스캔 API 문서(v1·v2)의 응답 코드 목록에 신규 코드를 추가하고, 앱이 "재시도 유도" 분기를 태울 수 있게 코드 의미를 명시해야 한다.

### Key Entities

- **rate-limit 실패**: 벤더 429 로 끝난 스캔 시도. 속성 — 갈래(즉시 거절/재시도 소진), 재시도 권고 초(선택), 남은 한도(선택), 소요 시간.
- **전용 에러코드**: 클라이언트 분기 식별자. 기존 SCAN-002(인식 실패)·SCAN-006(서버 장애)과 배타.
- **재시도 상한**: 일시적 429 에 대해 서버가 붙드는 총 시간의 설정값(기본 10초).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 벤더 429 로 끝난 스캔 중 사용자에게 SCAN-002 로 나가는 비율 0%.
- **SC-002**: 비일시적 429 응답까지 걸리는 시간이 벤더 응답 시간 + 1초 이내(재시도 없음).
- **SC-003**: 일시적 429 가 지속될 때 사용자가 기다리는 총 시간이 상한(10초) + 벤더 1회 응답 시간 이내(현재 수 분).
- **SC-004**: 운영자가 로그 검색 한 번(rate-limit 마커)으로 한도 초과 건수·갈래를 집계할 수 있다.
- **SC-005**: 기존 스캔 테스트 전부 그린(회귀 0).

## Assumptions

- HTTP 상태는 SCAN-002·SCAN-006 과 같은 **503** 으로 둔다 — 앱은 `code` 로만 분기하고, 503 계열이 이미 "재시도 유도 모달" 로 처리되므로 신규 코드도 그 분기에 얹는다. 클라이언트가 HTTP 429 를 요구하면 plan 에서 바꾼다.
- 재시도 상한 기본 10초: 스캔 UX 가 이미 수 초 대기(비전 호출 자체)를 전제로 하므로, 그 두 배 안쪽에서 끝낸다.
- 일시적/비일시적 판별은 벤더 클라이언트·프레임워크가 주는 예외 종류로 한다(비일시적은 즉시 던져지고, 일시적은 재시도 대상으로 분류됨).
- 벤더 한도 상향·사전 스로틀·큐잉·서킷브레이커는 범위 밖(로그 마커로 관측 후 별도 태스크).
- 429 이외의 비일시적 벤더 오류는 현행(SCAN-002) 유지.
- 앱(클라이언트) 변경은 이 스펙 범위 밖 — 신규 코드는 문서화만 하고, 앱 팀이 분기를 추가한다. US4 의 `retryAfterSeconds` 도 서버가 실을 뿐 소비는 앱 몫.
