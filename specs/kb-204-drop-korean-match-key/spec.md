# Feature Specification: food.korean_match_key 생성 컬럼 제거 — 메뉴명 매칭 앱 레벨 일원화

**Feature Branch**: `kb-204-drop-korean-match-key`

**Created**: 2026-07-21

**Status**: Draft

**Input**: User description: "kb-204 작업하던걸 브랜치 파서 해야지 — food.korean_match_key 생성 컬럼 제거, 메뉴명 매칭 앱 레벨 일원화 (Jira KB-204)"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔 메뉴명 매칭 동작 보존 (Priority: P1)

회원이 메뉴판 사진을 스캔하면, 인식된 메뉴명이 표기 변형(공백·특수문자·숫자·괄호 등)이 있어도 등록된 음식과 기존과 동일하게 매칭된다. 저장소의 파생 컬럼을 제거해도 회원이 체감하는 매칭 결과는 변하지 않아야 한다.

**Why this priority**: 매칭은 스캔 기능의 핵심 경로다. 내부 구조 변경이 회원 기능을 깨뜨리면 이 작업은 실패다.

**Independent Test**: 표기 변형이 섞인 메뉴명 집합으로 매칭 조회를 수행해, 변경 전과 동일한 음식이 반환되는지 기존 매칭 테스트로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** "김치찌개"가 등록된 상태, **When** "김치 찌개 (2인)"이 스캔되면, **Then** 해당 음식으로 매칭된다
2. **Given** 같은 정규화 결과를 갖는 음식이 둘 이상인 상태, **When** 그 이름이 스캔되면, **Then** 가장 먼저 등록된(최소 식별자) 음식으로 매칭되고 경고가 기록된다
3. **Given** 콘텐츠 미완성(INCOMPLETE) 음식이 있는 상태, **When** 그 이름이 스캔되면, **Then** 매칭 대상에 포함된다
4. **Given** 소프트 삭제된 음식만 이름이 일치하는 상태, **When** 그 이름이 스캔되면, **Then** 매칭되지 않는다

---

### User Story 2 - 운영 데이터 임의 조작 가능 (Priority: P2)

운영자가 food 테이블의 행을 GUI 도구(row 편집)나 전체 컬럼을 지정하는 수동 INSERT/UPDATE 로 자유롭게 조작할 수 있다. 현재는 저장소가 자동 계산하는 파생 컬럼이 이런 조작을 거부해 운영이 불편하다.

**Why this priority**: 이 작업의 직접적 동기다. 다만 회원 기능 보존(P1)이 전제돼야 한다.

**Independent Test**: 전체 컬럼을 지정한 INSERT/UPDATE 문과 GUI row 편집이 오류 없이 수행되는지 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 파생 컬럼이 제거된 상태, **When** 운영자가 전체 컬럼을 지정해 행을 INSERT/UPDATE 하면, **Then** 오류 없이 반영된다
2. **Given** 운영자가 음식 이름을 수동으로 수정한 상태, **When** 그 이름이 스캔되면, **Then** 별도 후속 조치 없이 새 이름 기준으로 매칭된다

---

### User Story 3 - 정규화 규칙 단일 출처화 (Priority: P3)

메뉴명 정규화(한글 외 문자 제거) 규칙이 애플리케이션 한 곳에만 존재한다. 지금은 앱과 저장소 양쪽에 같은 규칙이 중복돼 어긋날 위험이 있고, 이를 감시하는 동기화 테스트를 별도로 유지해야 한다.

**Why this priority**: 유지보수 비용 절감 효과다. P1·P2 가 달성되면 자연히 따라온다.

**Independent Test**: 코드베이스에서 정규화 규칙 정의가 한 곳뿐이고, 저장소-앱 동기화 검증 테스트가 더 이상 필요 없음을 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 파생 컬럼이 제거된 상태, **When** 정규화 규칙을 변경하면, **Then** 앱 코드 한 곳만 수정하면 되고 저장소 스키마 변경은 불필요하다

---

### Edge Cases

- 한글이 전혀 없는 메뉴명(정규화 결과가 빈 문자열)은 매칭 시도 대상에서 제외된다 — 기존 동작 유지.
- 기존 데이터 중 정규화 시 다른 음식과 이름이 충돌하거나 빈 문자열이 되는 행은 자동 정리 대상에서 제외된다 — 매칭에서 빠지며 수동 정리 대상이다.
- 이미 적용된 환경의 저장소에서 파생 컬럼 제거는 데이터 손실이 없다 — 값이 원본 이름에서 전량 재계산 가능하다.
- 블루/그린 배포의 공존 구간에서 이전 버전은 여전히 파생 컬럼을 조회한다 — 컬럼 제거를 같은 배포에 넣으면 이전 버전의 음식 조회가 전부 실패하므로, 제거는 이전 버전 소멸 후 별도 배포로 미룬다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 스캔된 메뉴명과 등록 음식의 매칭을 저장소의 파생 컬럼 없이 수행해야 한다
- **FR-002**: 메뉴명 정규화 규칙은 애플리케이션에 단일 출처로 존재해야 한다
- **FR-003**: 기존 매칭 계약을 유지해야 한다 — 표기 변형 흡수, 동음이의 시 최소 식별자 매칭과 경고 기록, 미완성 음식 포함, 소프트 삭제 음식 제외, 빈 정규화 키 제외
- **FR-004**: food 저장소의 korean_match_key 파생 컬럼과 그 색인은 두 단계로 제거한다 — 이번 단계는 코드가 컬럼을 더 이상 읽지 않게 하고, 실제 컬럼 제거는 이전 버전 프로세스가 완전히 중단된 뒤 후속 배포에서 수행한다(블루/그린 공존 구간에 이전 버전이 깨지지 않아야 한다)
- **FR-005**: 파생 컬럼 제거 후 전체 컬럼을 지정하는 수동 INSERT/UPDATE 와 GUI row 편집이 가능해야 한다
- **FR-006**: 저장소-앱 정규화 규칙 동기화를 검증하던 테스트는 제거하고, 매칭 계약은 기존 행위 테스트로 계속 보장해야 한다

### Key Entities

- **Food(음식)**: 한국어 정식 명칭을 갖는 등록 음식. 명칭 자체를 항상 정규화된 상태로 저장·유지해 별도 매칭 키가 필요 없다
- **정규화 키**: 음식 명칭에서 한글 외 문자를 제거한 값. 별도 저장 없이 명칭 그 자체가 정규화 키다 — 스캔 입력은 조회 전에, 신규 등록 이름은 저장 전에 정규화한다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 기존 매칭 행위 테스트(표기 변형·동음이의·미완성·소프트 삭제 시나리오)가 전부 통과한다 — 매칭 결과 변경 0건
- **SC-002**: 전체 컬럼을 지정한 수동 INSERT/UPDATE 및 GUI row 편집 시 파생 컬럼 관련 오류 0건
- **SC-003**: 메뉴명 정규화 규칙 정의가 코드베이스에 정확히 1곳만 존재한다
- **SC-004**: 현재 데이터 규모에서 스캔 응답 시간이 체감 저하 없이 유지된다

## Assumptions

- 파생 컬럼 값은 원본 명칭에서 전량 재계산 가능하므로 제거 시 백업이 불필요하다
- 매칭 키를 사용하는 기능은 스캔 매칭뿐이다 — 다른 기능은 이 컬럼을 참조하지 않는다
- 운영자가 명칭을 수동 수정·등록하는 경우는 허용된 운영 행위이며, 운영자는 정규화된(한글만 있는) 이름만 입력한다 — 시스템은 운영자 입력을 별도 검증하지 않는다
- 음식 명칭은 한글로만 구성된다 — 한글 외 문자가 필요한 명칭(예: 영문 포함)은 취급하지 않는다
