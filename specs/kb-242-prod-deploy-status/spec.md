# Feature Specification: prod 배포 성공이 워크플로우 실패로 표시되는 문제 해소

**Feature Branch**: `kb-242-prod-deploy-status`

**Created**: 2026-07-29

**Status**: Draft

**Input**: User description: "KB-242 — 배포가 성공해도 prod 배포 워크플로우가 실패로 끝나는 문제. 카나리 15분+bake 30분(최소 45분)인데 폴링 타임아웃 기본 30분이라 배포 완료 전에 워크플로우가 실패로 종료된다. 임시로 DEPLOY_TIMEOUT_SECONDS=4200 을 설정했으나 bake 시간이 바뀔 때마다 조정해야 한다. 45분 이상 러너를 점유하는 폴링 방식의 타당성도 검토한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 워크플로우 결과가 배포 성패를 정직하게 말한다 (Priority: P1)

배포 담당자가 prod 배포를 트리거하면, 실제로 성공한 배포는 워크플로우도 성공으로 끝난다. 카나리·bake 에 시간이 얼마나 걸리든, 담당자는 워크플로우 상태 배지만 보고 배포 성패를 판단할 수 있다.

**Why this priority**: 지금은 성공 배포가 실패로 표시돼 "실패 = 진짜 실패"라는 신뢰가 깨져 있다. 알람 무감각(alert fatigue)으로 이어져 진짜 실패를 놓치게 만드는 것이 이 이슈의 핵심 피해다.

**Independent Test**: prod 배포를 1회 트리거하고 카나리+bake 가 끝까지 진행되게 둔 뒤, 워크플로우가 성공 상태로 종료되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정상 동작하는 새 리비전, **When** prod 배포를 트리거하고 카나리+bake(45분 이상)가 완료되면, **Then** 워크플로우는 성공으로 종료된다
2. **Given** 새 리비전이 기동에 실패하거나 롤백되는 상황, **When** prod 배포를 트리거하면, **Then** 워크플로우는 실패로 종료되고 실패 사유가 로그에 드러난다

---

### User Story 2 - 판정 불가와 배포 실패가 구분된다 (Priority: P2)

배포 결과를 제한 시간 안에 확인하지 못한 경우(판정 불가), 담당자는 이것이 "배포가 실패했다"가 아니라 "확인을 못 했다"임을 워크플로우 표시에서 즉시 구분할 수 있다.

**Why this priority**: 오인의 두 번째 원인. 타임아웃과 실패가 같은 빨간불이면 담당자가 매번 AWS 콘솔에 들어가 실상을 확인해야 한다.

**Independent Test**: 확인 제한 시간을 인위적으로 짧게 설정해 판정 불가 상황을 만들고, 워크플로우 표시가 배포 실패와 다른 형태(상태/문구)로 나타나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 제한 시간 내 배포 완료 확인이 불가한 상황, **When** 제한 시간이 지나면, **Then** 워크플로우는 "배포 실패"가 아닌 "판정 불가(확인 필요)"로 식별 가능한 상태·메시지를 남긴다

---

### User Story 3 - 운영 설정 변경에 따라다니는 수동 조정 제거 (Priority: P3)

인프라 담당자가 카나리·bake 시간을 조정해도, 배포 워크플로우의 별도 설정값을 함께 손보지 않아도 배포 성패 판정은 계속 올바르게 동작한다.

**Why this priority**: 현행 임시 조치(고정 타임아웃 상향)는 bake 시간과 설정값이 어긋나는 순간 다시 오탐을 만든다. 어긋남의 근원을 없애야 재발하지 않는다.

**Independent Test**: bake 시간을 변경한 뒤 워크플로우 설정을 손대지 않고 배포를 1회 수행해 성패 판정이 올바른지 확인한다.

**Acceptance Scenarios**:

1. **Given** bake 시간이 변경된 서비스, **When** 워크플로우 설정 변경 없이 배포를 트리거하면, **Then** 성공 배포는 성공으로 판정된다

---

### Edge Cases

- 배포 완료 직전(예: bake 종료 수 초 전)에 확인 제한 시간이 끝나면? → 판정 불가로 표시되어야 하며 실패로 단정하지 않는다
- 배포 도중 서킷브레이커가 롤백을 시작하면? → 실패로 표시되고 롤백 사실이 로그에 드러난다
- 동일 서비스에 배포가 연달아 트리거되면(이전 배포가 아직 bake 중)? → 최소한 판정이 서로 뒤섞이지 않아야 한다
- 배포 상태 조회 자체가 일시적으로 실패하면(API 오류)? → 일시 오류로 배포를 실패로 단정하지 않는다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 정상 완료되는 prod 배포는 카나리·bake 소요 시간과 무관하게 워크플로우 성공으로 끝나야 한다
- **FR-002**: 실제 배포 실패(기동 실패·롤백)는 워크플로우 실패로 끝나고 사유가 로그에 남아야 한다
- **FR-003**: 제한 시간 내 판정 불가 상황은 배포 실패와 구분되는 상태·메시지로 표시되어야 한다
- **FR-004**: 카나리·bake 시간이 변경되어도 워크플로우 쪽 설정을 수동으로 함께 조정할 필요가 없어야 한다
- **FR-005**: 결과 확인 방식은 배포 소요 시간(45분 이상) 동안 실행 자원(러너) 점유가 타당한지 검토를 거쳐 결정되어야 한다 — 검토 대안: (1) 완료까지 대기하되 제한 시간을 서비스 설정에서 자동 산출 (2) 새 리비전 기동·헬시 확인 시점에 성공 처리 (3) 트리거만 하고 결과는 별도 통지

### Key Entities

- **배포 판정 상태**: 성공 / 실패(사유 포함) / 판정 불가(확인 필요) 3분류 — 워크플로우가 남기는 최종 표식

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 정상 카나리 배포(45분 이상 소요) 1회에서 워크플로우가 성공으로 종료된다 — 현행은 100% 실패 표시
- **SC-002**: bake 시간 변경 후 워크플로우 설정 무수정으로 배포 1회를 수행해도 판정이 올바르다
- **SC-003**: 판정 불가와 배포 실패가 워크플로우 로그·상태에서 서로 다른 문구로 식별된다
- **SC-004**: 배포 성패 확인을 위해 AWS 콘솔에 별도로 들어가야 하는 경우가 정상 경로에서 0회가 된다

## Assumptions

- 현행 prod api 배포는 ECS 네이티브 블루/그린(카나리 15분 + bake 30분, 최소 45분)이며 이 시간은 인프라 소유 설정으로 향후 변경될 수 있다
- 임시 조치로 `DEPLOY_TIMEOUT_SECONDS=4200` 환경 변수가 설정되어 있다 — 본 작업 완료 시 이 임시값 의존은 제거 대상이다
- 검증은 실제 prod 배포 1회로 수행한다 (스테이징에 동일 카나리 구성이 없다는 전제)
- dev 배포 경로(EC2+SSM)는 이 문제의 영향 밖이며 범위에 포함하지 않는다
- DoD 의 대안 3안 중 선택은 계획(plan) 단계의 검토·결정 사항이다 — 본 명세는 어느 안을 택하든 만족해야 할 결과만 규정한다
