# Feature Specification: prod 배포 성공이 워크플로우 실패로 표시되는 문제 해소

**Feature Branch**: `kb-242-prod-deploy-status`

**Created**: 2026-07-29

**Status**: Draft

**Input**: User description: "KB-242 — 배포가 성공해도 prod 배포 워크플로우가 실패로 끝나는 문제. 카나리 15분+bake 30분(최소 45분)인데 폴링 타임아웃 기본 30분이라 배포 완료 전에 워크플로우가 실패로 종료된다. 임시로 DEPLOY_TIMEOUT_SECONDS=4200 을 설정했으나 bake 시간이 바뀔 때마다 조정해야 한다. 45분 이상 러너를 점유하는 폴링 방식의 타당성도 검토한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 워크플로우 결과가 배포 성패를 정직하게 말한다 (Priority: P1)

배포 담당자가 prod 배포를 트리거하면, 실제로 성공한 배포는 워크플로우도 성공으로 끝난다. 카나리·bake 에 시간이 얼마나 걸리든, 담당자는 워크플로우 상태 배지만 보고 배포 성패를 판단할 수 있다.

**Why this priority**: 지금은 성공 배포가 실패로 표시돼 "실패 = 진짜 실패"라는 신뢰가 깨져 있다. 알람 무감각(alert fatigue)으로 이어져 진짜 실패를 놓치게 만드는 것이 이 이슈의 핵심 피해다.

**Independent Test**: prod 배포를 1회 트리거하고 카나리+bake 가 끝까지 진행되게 둔 뒤, 워크플로우가 성공 상태로 종료되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정상 동작하는 새 리비전, **When** prod 배포를 트리거하면, **Then** 카나리·bake 소요 시간과 무관하게 워크플로우는 성공으로 종료된다
2. **Given** 배포 자체가 시작되지 못하는 상황(트리거 거부·새 리비전 미교체), **When** prod 배포를 트리거하면, **Then** 워크플로우는 실패로 종료되고 사유가 로그에 드러난다

---

### User Story 2 - 워크플로우 실패는 "시작조차 안 됨"만 뜻한다 (Priority: P2)

배포 결정(대안 3) 이후 워크플로우의 실패는 "배포가 시작되지 못했다"는 하나의 의미만 갖는다. 시작된 뒤의 성패(기동 실패·헬스체크 탈락·롤백)는 운영 관찰 체계가 판정하며, 워크플로우 성공 로그에 그 책임 경계가 명시된다.

**Why this priority**: 파이프라인이 중간 신호(RUNNING 수·rolloutState)로 성패를 추정하면 반드시 오판이 생긴다 — RUNNING 은 헬스체크 통과가 아니고, 카나리(신규 20% 트래픽) 진행 중에는 완료 전까지 어떤 신호도 확정적이지 않다. 판정 책임을 명시적으로 나누는 것이 오판보다 낫다.

**Independent Test**: 배포 시작이 확인되지 않는 상황(태스크정의 미교체)을 만들면 워크플로우가 실패로 끝나고, 정상 시작이면 성공 로그에 "이후 판정은 운영 체계 소관" 문구가 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 배포 트리거가 접수되지 않거나 새 리비전으로 교체가 시작되지 않는 상황, **When** 시작 확인 제한 시간이 지나면, **Then** 워크플로우는 실패로 끝나고 "시작 확인 실패"가 사유로 남는다
2. **Given** 배포가 정상 시작된 상황, **When** 워크플로우가 성공으로 끝나면, **Then** 이후 카나리·bake·롤백 판정이 운영 관찰 체계 소관임이 요약에 명시된다

---

### User Story 3 - 운영 설정 변경에 따라다니는 수동 조정 제거 (Priority: P3)

인프라 담당자가 카나리·bake 시간을 조정해도, 배포 워크플로우의 별도 설정값을 함께 손보지 않아도 배포 성패 판정은 계속 올바르게 동작한다.

**Why this priority**: 현행 임시 조치(고정 타임아웃 상향)는 bake 시간과 설정값이 어긋나는 순간 다시 오탐을 만든다. 어긋남의 근원을 없애야 재발하지 않는다.

**Independent Test**: bake 시간을 변경한 뒤 워크플로우 설정을 손대지 않고 배포를 1회 수행해 성패 판정이 올바른지 확인한다.

**Acceptance Scenarios**:

1. **Given** bake 시간이 변경된 서비스, **When** 워크플로우 설정 변경 없이 배포를 트리거하면, **Then** 성공 배포는 성공으로 판정된다

---

### Edge Cases

- 배포 시작 확인 중 상태 조회가 일시 실패하면(API 오류)? → 제한 시간 내 재시도하며, 일시 오류로 실패를 단정하지 않는다
- 배포 시작 뒤 기동 실패·헬스체크 탈락·bake 중 롤백이 일어나면? → 워크플로우는 이미 성공으로 끝나 있다 — 운영 관찰 체계(서킷브레이커·알람·콘솔)가 감지하며, 이 경계는 성공 요약에 명시된다
- 동일 서비스에 배포가 연달아 트리거되면(이전 배포가 아직 bake 중)? → 시작 확인은 자기 태스크정의 기준이라 판정이 뒤섞이지 않는다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 정상 prod 배포는 카나리·bake 소요 시간과 무관하게 워크플로우 성공으로 끝나야 한다
- **FR-002**: 배포가 시작되지 못한 경우(트리거 거부·새 리비전으로 교체 미시작)는 워크플로우 실패로 끝나고 사유가 로그에 남아야 한다
- **FR-003**: 배포 시작 이후의 성패(기동 실패·헬스체크 탈락·롤백)는 운영 관찰 체계(서킷브레이커·알람) 소관이며, 워크플로우 성공 요약에 이 책임 경계가 명시되어야 한다
- **FR-004**: 카나리·bake 시간이 변경되어도 워크플로우 쪽 설정을 수동으로 함께 조정할 필요가 없어야 한다
- **FR-005**: [결정됨 — 대안 (3) 채택] 워크플로우는 배포 시작까지만 확인하고 결과 관찰은 운영 체계에 위임한다. 근거: RUNNING 태스크 수는 헬스체크 통과를 뜻하지 않고, 카나리 진행 중 어떤 중간 신호도 성패의 확정 근거가 못 되며, 45분+ 러너 점유는 낭비다

### Key Entities

- **배포 판정 상태**: 성공(배포 시작 확인) / 실패(시작 미확인, 사유 포함) 2분류 — 워크플로우가 남기는 최종 표식. 시작 이후의 성패는 운영 관찰 체계 소관

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 정상 카나리 배포 1회에서 워크플로우가 성공으로 종료된다 — 현행은 100% 실패 표시
- **SC-002**: bake 시간 변경 후 워크플로우 설정 무수정으로 배포 1회를 수행해도 판정이 올바르다
- **SC-003**: 워크플로우의 배포 단계 소요 시간이 45분+에서 수 분 이내로 줄어든다(러너 점유 제거)
- **SC-004**: 워크플로우 실패가 "시작 실패" 단일 의미가 되어, 성공 배포가 실패로 표시되는 오탐이 0건이 된다

## Assumptions

- 현행 prod api 배포는 ECS 네이티브 블루/그린(카나리 15분 + bake 30분, 최소 45분)이며 이 시간은 인프라 소유 설정으로 향후 변경될 수 있다
- 임시 조치로 `DEPLOY_TIMEOUT_SECONDS=4200` 환경 변수가 설정되어 있다 — 본 작업 완료 시 이 임시값 의존은 제거 대상이다
- 검증은 실제 prod 배포 1회로 수행한다 (스테이징에 동일 카나리 구성이 없다는 전제)
- dev 배포 경로(EC2+SSM)는 이 문제의 영향 밖이며 범위에 포함하지 않는다
- DoD 대안 (3) 채택이 확정됐다 — 배포 시작 이후의 실패를 능동 통지하는 알람(예: 배포 실패 이벤트 → 알림 채널)은 후속 과제로 분리한다. 알람이 갖춰지기 전까지는 bake 중 롤백을 ECS 콘솔에서 확인해야 한다
