# Feature Specification: 검색어에 맞는 메뉴 조회 API (다국어 부분 일치, no-offset 커서 페이지네이션)

**Feature Branch**: `kb-62-menu-search`

**Created**: 2026-07-09

**Status**: Draft

**Input**: User description: "kb-62 검색 기능에서 한국어와 9개국 언어만으로 검색을 할 거야. 이때 검색 키워드가 포함되는 데이터를 페이지네이션으로 찾아서 내려주면돼" — KB-62 [BE] 검색어에 맞는 메뉴 조회 API

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 검색어로 먹고 싶은 메뉴를 찾는다 (Priority: P1)

사용자가 먹고 싶은 메뉴 이름 일부를 검색창에 입력하면, 그 검색어가 **이름 어딘가에 포함되는** 메뉴들이 한 페이지(20개)씩 내려온다. 검색어는 **한국어 메뉴명과 요청 언어(`lang`)의 번역명** 두 이름을 대상으로 매칭되므로, 사용자가 자기 언어로 검색하든 한국어로 검색하든 해당 메뉴를 찾을 수 있다. 지원 언어는 한국어 + 9개국 언어(영어·중국어 간체/번체·일본어·베트남어·인도네시아어·태국어·러시아어·스페인어)이며, 한 번의 검색은 그 중 요청한 한 언어의 번역명과 한국어명만 본다. 결과가 많으면 계속 스크롤해 다음 20개를 이어서 받는다.

**Why this priority**: 검색어로 원하는 메뉴를 찾아내는 것이 이 기능의 존재 이유 그 자체다. 부분 일치 매칭과 첫 페이지 반환만 동작하면 "이름으로 메뉴를 찾는다"는 사용자 여정이 완결된다(MVP).

**Independent Test**: 특정 메뉴명(한국어명 또는 요청 언어 번역명)의 일부를 검색어로 넣어, 그 조각을 한국어명 또는 요청 언어 번역명에 포함하는 메뉴만 결과에 담기고 포함하지 않는 메뉴는 빠지는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 이름에 "김치"가 들어간 메뉴가 여러 개 있고, **When** "김치"로 검색하면, **Then** 한국어명에 "김치"가 포함된 메뉴들이 최신 등록순 20개까지 반환된다.
2. **Given** 한국어명은 "비빔밥"이고 영어 번역명이 "Bibimbap"인 메뉴가 있을 때, **When** `lang=en`으로 "bibim"을 검색하면, **Then** 요청 언어(en) 번역명 매칭으로 그 메뉴가 결과에 포함된다.
3. **Given** 어떤 메뉴 이름에도 포함되지 않는 문자열로, **When** 검색하면, **Then** 오류가 아니라 200과 빈 목록을 반환한다.

### User Story 2 - 검색 결과를 무한 스크롤로 끝까지 넘겨본다 (Priority: P2)

검색 결과가 20개를 넘어도 목록 조회와 똑같이 no-offset 커서로 다음 페이지가 이어진다. 아무리 뒤 페이지로 가도 느려지지 않고, 스크롤 도중 메뉴가 추가·삭제돼도 이미 본 항목이 중복되거나 건너뛰어지지 않는다.

**Why this priority**: 인기 검색어는 결과가 수십~수백 개일 수 있어 페이지네이션이 없으면 실사용이 안 된다. 다만 P1(매칭 자체)이 없으면 성립하지 않으므로 그다음이다.

**Independent Test**: 결과가 20개를 넘는 검색어로 첫 페이지와 `nextCursor`·`hasNext`를 받고, 같은 검색어에 그 커서를 실어 다음 페이지를 요청해 이전 페이지와 겹치지 않는 다음 항목을 받는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 검색 결과가 20개보다 많고, **When** 커서 없이 검색하면, **Then** 상위 20개와 다음 커서, `hasNext=true`를 받는다.
2. **Given** 첫 페이지에서 받은 다음 커서를 **같은 검색어와 함께** 실어, **When** 다음 페이지를 요청하면, **Then** 첫 페이지 마지막 항목보다 오래된 다음 결과 20개를 받고 두 페이지 사이에 중복·누락이 없다.
3. **Given** 남은 결과가 20개 이하인 마지막 페이지에서, **When** 조회하면, **Then** 남은 항목과 `hasNext=false`, 다음 커서 부재(null)를 받는다.

---

### User Story 3 - 항목에서 바로 상세로 이어지고 목록과 같은 카드를 본다 (Priority: P3)

검색 결과의 각 항목은 목록 조회와 동일한 'food summary' 형태로, 상세 조회로 곧장 이어질 안정적 식별자(foodId)와 요청 언어 표시명·대표 이미지·맵기·회피 기준 종합 위험도를 함께 담는다. 사용자는 검색 결과 카드에서 이미 위험도를 훑고 탭 한 번으로 상세로 진입한다.

**Why this priority**: 검색과 목록이 같은 항목 스키마를 공유해야 클라이언트가 두 화면을 한 컴포넌트로 다룰 수 있고 상세 진입이 자연스럽다. 매칭·페이지네이션이 선행돼야 하므로 P3.

**Independent Test**: 검색 결과 한 페이지의 임의 항목 식별자로 상세 조회가 성공하고, 각 항목에 요청 언어 표시명·이미지·맵기·종합 위험도가 목록 API와 동일하게 담기는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 검색 결과 한 페이지를 받고, **When** 임의 항목의 식별자로 상세 조회를 요청하면, **Then** 그 항목의 메뉴 상세가 정상 반환된다.
2. **Given** `lang`을 지정해 검색하면, **When** 해당 언어 번역이 있으면 그 언어로, 없으면 한국어로, **Then** 각 항목 표시명이 목록·상세 API와 동일한 폴백 규칙으로 지역화된다.
3. **Given** 사용자의 회피 성분이 주어졌을 때, **When** 검색하면, **Then** 각 항목의 종합 위험도가 SAFE/CAUTION/DANGER/UNKNOWN 중 하나로 표시된다.

---

### Edge Cases

- **빈/공백 검색어**: 검색어가 없거나 공백뿐이면 검색을 수행하지 않고 사유가 담긴 실패 응답을 반환한다(검색어 없는 전체 탐색은 목록 조회 API의 몫 — 두 엔드포인트를 분리한다).
- **검색 대상 언어 범위**: 매칭 대상은 **한국어명 + 요청 언어(`lang`) 번역명** 두 이름이다. `lang`은 매칭 대상 번역명 선택과 결과 표시명 지역화 양쪽에 함께 쓰인다(예: `lang=en`이면 한국어명·영어 번역명만 보고, 일본어 번역명은 매칭하지 않는다).
- **`lang` 미지정**: `lang`이 없으면 한국어로 폴백하므로 매칭 대상은 한국어명뿐이다(상세·목록 API와 동일한 폴백 규칙).
- **대소문자/부분 위치**: 매칭은 대소문자를 구분하지 않고, 검색어가 이름의 앞·중간·끝 어디에 포함돼도 매칭된다(부분 일치).
- **결과 없음**: 매칭이 하나도 없으면 오류가 아니라 200과 빈 목록·`hasNext=false`를 반환한다.
- **정확히 20의 배수**: 결과 총 개수가 20의 배수라 마지막 페이지가 꽉 찬 경우, 다음 요청은 빈 목록 + `hasNext=false`를 반환한다.
- **스크롤 중 삽입/삭제**: keyset 커서라 이미 지나온 경계 밖의 삽입/삭제는 현재 검색 페이지 연속성에 영향을 주지 않는다.
- **잘못된 커서**: 형식이 잘못됐거나 해석 불가한 커서는 사유가 담긴 실패 응답으로 처리한다.
- **한국어명·번역명 동시 매칭**: 한 메뉴가 한국어명과 요청 언어 번역명 양쪽에서 검색어를 포함해도 결과에는 **한 번만** 나온다(중복 제거).
- **미지원 `lang`**: `lang`이 지원 목록에 없는 코드면(대소문자·지역 변형 포함, 예: `fr`·`EN`·`ko-KR`) 조용히 폴백하지 않고 **400 으로 거절**하며 지원 언어 목록을 안내한다(원칙 V fail-fast, 상세·목록 API와 동일).
- **검색어의 패턴 특수문자**: 검색어에 `%`·`_` 가 들어와도 와일드카드가 아니라 **리터럴**로 매칭한다. 즉 `keyword=%` 는 전체 메뉴가 아니라 이름에 `%` 를 포함하는 메뉴만 반환한다(FR-003a).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 검색어를 받아 이름에 검색어를 **부분 일치(포함)** 하는 메뉴를 페이지당 20개씩 조회하는 GET 검색 엔드포인트를 제공해야 한다.
- **FR-002**: 매칭 대상은 각 메뉴의 **한국어 메뉴명과 요청 언어(`lang`)의 번역명** 두 이름이어야 하며, 둘 중 하나라도 검색어를 포함하면 매칭으로 간주해야 한다.
- **FR-003**: 매칭은 **대소문자 비구분** 부분 일치여야 하며, 검색어가 이름의 어느 위치에 포함되든 매칭해야 한다. 이는 **한국어명·번역명 두 경로 모두**에 동일하게 적용된다.
- **FR-003a**: 검색어에 포함된 패턴 특수문자(`%`·`_` 등)는 **리터럴 문자로 취급**해야 하며 와일드카드로 해석되어서는 안 된다 — 검색어 `%` 는 전체 메뉴가 아니라 이름에 `%` 를 포함하는 메뉴만 매칭해야 한다(검색어 없는 전체 탐색은 목록 API 의 몫이므로 우회 경로가 생겨선 안 된다).
- **FR-004**: `lang` 파라미터는 **매칭 대상 번역명 선택**과 **결과 표시명 지역화**에 함께 쓰여야 한다. 원칙 V 에 따라 (1) **미지정**(null·빈·공백)이면 `ko` 로 해석하고, (2) **지원 언어이나 번역 부재**면 표시명을 `ko` 로 폴백하며, (3) **지원 목록에 없는 코드**는 조용히 폴백하지 않고 **실패 응답(400)으로 거절**하고 지원 언어 목록을 안내해야 한다(목록·상세 API 와 동일 규칙). (1)·(2)로 `ko` 가 확정된 경우 매칭 대상은 한국어명뿐이다.
- **FR-005**: 결과 정렬은 **최신 등록순(내부 식별자 foodId 내림차순)** 으로 결정적·안정적이어야 한다.
- **FR-006**: 페이지네이션은 offset 이 아니라 **no-offset(cursor/keyset)** 방식이어야 한다 — 요청은 검색어와 선택적 커서를 받고(커서 없으면 첫 페이지), 응답은 **다음 커서**와 **다음 페이지 존재 여부(hasNext)** 를 포함해야 한다.
- **FR-007**: 커서 이후 페이지는 이전 페이지와 항목이 중복·누락되지 않아야 하며, 스크롤 도중 삽입·삭제가 일어나도 동일하게 보장해야 한다.
- **FR-008**: 한 메뉴가 한국어명과 요청 언어 번역명 양쪽에서 검색어를 포함하더라도 결과에 **중복 없이 한 번만** 나와야 한다.
- **FR-009**: 검색 결과의 각 항목은 **목록 조회(KB-63)와 동일한 'food summary' 스키마**를 재사용해야 한다 — 상세 조회로 이어질 **안정적 식별자(숫자 foodId)**, 요청 언어 표시명, 대표 이미지 참조, 맵기(0~10), 사용자 회피 기준 **종합 위험도(SAFE/CAUTION/DANGER/UNKNOWN)** 를 포함해야 한다.
- **FR-010**: 검색 결과 각 항목의 표시명은 `lang`으로 지역화하며(FR-004 의 미지정/번역부재 → `ko` 폴백, 미지원 코드 → 400 규칙과 동일), 목록·상세 API와 동일하게 처리해야 한다.
- **FR-011**: 빈/공백 검색어는 검색을 수행하지 않고 사유가 담긴 실패 응답으로 처리해야 한다.
- **FR-012**: 매칭 결과가 0건이어도 오류가 아니라 200과 빈 목록·`hasNext=false`를 반환해야 한다.
- **FR-013**: 마지막 페이지에서는 `hasNext=false`이고 다음 커서는 비어 있어야(null) 한다.
- **FR-014**: 형식이 잘못됐거나 해석 불가한 커서는 사유가 담긴 실패 응답으로 처리해야 한다.
- **FR-015**: 삭제(소프트 삭제)된 메뉴는 검색 결과·커서 계산에서 제외되어야 한다.
- **FR-016**: 모든 응답은 공통 봉투 `BaseResponse`로 감싸고, 경로는 `/api/v1` 규약을 따라야 한다.
- **FR-017**: 부분 일치 매칭·빈 검색어·결과 없음·커서 경계(마지막 페이지)·잘못된 커서 케이스가 BehaviorSpec 통합 테스트로 검증되어야 한다.

### Key Entities *(include if data involved)*

- **메뉴 요약(Food Summary)**: 목록·검색이 공유하는 항목 표현(KB-63과 동일). 속성 — 안정 식별자(foodId), 요청 언어 표시명, 대표 이미지 참조, 맵기, 사용자 회피 기준 종합 위험도.
- **검색어(Search Keyword)**: 사용자가 입력한 조회 문자열. 공백 제거 후 비어 있지 않아야 하며, 한국어명 + 요청 언어 번역명에 대한 부분 일치 매칭의 대상.
- **커서 페이지(Cursor Page)**: 한 번의 검색 응답 단위. 속성 — 메뉴 요약 목록(≤20), 다음 커서(nullable), 다음 페이지 존재 여부(hasNext).
- **커서(Cursor)**: 다음 페이지의 시작 위치. 마지막으로 반환된 항목의 정렬 키(내부 식별자)에서 파생되며, 첫 요청에서는 부재. 같은 검색어와 함께 전달돼야 유효하다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 한국어명 조각 또는 요청 언어(`lang`) 번역명 조각으로 검색하면, 그 조각을 해당 이름에 포함하는 메뉴를 결과로 받는다.
- **SC-002**: 검색 결과가 20개를 넘어도 20개 단위로 끊김 없이 계속 스크롤할 수 있고, 연속한 두 페이지 사이의 중복·누락 항목이 **0건**이다(스크롤 중 삽입/삭제 동시 발생 시에도 동일).
- **SC-003**: 검색 응답 성능이 데이터 양·페이지 깊이에 따라 저하되지 않는다 — 첫 페이지와 아주 뒤쪽 페이지의 응답 시간이 유의하게 차이 나지 않는다(OFFSET 스캔 비용 제거 확인).
- **SC-004**: 검색 결과 각 항목의 식별자로 상세 조회를 한 번 요청하면 100% 해당 상세로 진입한다.
- **SC-005**: 부분 일치, 빈 검색어(실패 응답), 결과 없음(빈 목록 200), 마지막 페이지(`hasNext=false`), 잘못된 커서 경계가 모두 BehaviorSpec 통합 테스트로 커버된다.

## Assumptions

- **검색 대상 = 한국어명 + 요청 언어 번역명**: 매칭 대상은 각 메뉴의 한국어명과 요청 언어(`lang`) 번역명 두 이름이다(원 Jira 설명과 동일). 지원 언어는 한국어 + 9개국이지만 한 번의 검색은 요청한 한 언어 번역명과 한국어명만 본다. 메뉴명 외 다른 필드(설명·성분 등)는 검색 대상이 아니다.
- **검색어 필수 / 목록과 분리**: 검색어 없는 전체 탐색은 이미 KB-63 목록 조회 API가 담당하므로, 이 엔드포인트는 검색어를 필수로 요구하고 빈 검색어는 실패로 처리한다.
- **항목 스키마 재사용**: KB-63이 정의한 'food summary' 항목 스키마·언어 폴백·회피 성분 종합 위험도 산출 방식을 그대로 재사용한다(현재 회피 성분은 Mock 제공자). 검색은 매칭·페이지 소스만 다르고 항목 표현은 목록과 동일하다.
- **페이지 크기 20 고정**: 클라이언트가 페이지 크기를 지정하지 않으며 서버가 20으로 고정한다.
- **정렬·커서 = 목록과 동일**: 결과 정렬은 relevance 랭킹이 아니라 최신 등록순(foodId 내림차순)이며, 커서는 마지막 항목의 정렬 키(내부 식별자)에서 파생된다(목록 API와 동일). relevance/가중치 랭킹은 범위 밖.
- **익명 검색**: 검색은 로그인 없이 가능한 공개 조회다. 항목 위험도 산출에 쓰는 회피 성분 컨텍스트는 상세·목록 API가 쓰는 동일한 제공 방식을 재사용한다.
- **상세 식별자 정합 의존**: 상세 조회가 foodId 기반(KB-98)으로 이미 정합되어 있음을 전제한다.
- **키워드 정규화**: 검색어는 앞뒤 공백을 제거해 처리하고, 패턴 특수문자(`%`·`_`)는 이스케이프해 리터럴로 매칭한다(FR-003a). 그 밖의 형태소 분석·동의어·오타 교정은 범위 밖(순수 부분 일치).
