# Feature Specification: 음식 사진 WebP 변환본 서빙

**Feature Branch**: `kb-285-food-image-webp`

**Created**: 2026-08-03

**Status**: Draft

**Input**: KB-285 [BE] 음식 사진 로딩 개선 — PNG 원본의 WebP 변환본 서빙

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 신규 음식 사진이 가벼운 포맷으로 내려온다 (Priority: P1)

앱 사용자가 음식 목록·상세 화면을 열면 음식 사진이 즉시 뜬다. 지금은 장당 약 2MB 무손실 원본을 받아 목록에서 6장을 동시에 받을 때 장당 1.0~1.7초가 걸리고, 첫 진입에서 빈 자리가 눈에 띈다. 배치가 새로 만든 음식 사진부터는 화질 차이 없이 10분의 1 용량의 변환본이 내려와 체감 대기가 사라진다.

**Why this priority**: 사용자가 실제로 겪는 지연이며, 이 스토리만 배포해도 신규 음식부터 즉시 개선된다.

**Independent Test**: dev 환경에서 이미지 배치를 한 번 회수시킨 뒤, 새로 생성된 음식의 상세/목록 API 응답 이미지 URL이 변환본 경로를 가리키는지, 앱에서 정상 렌더링되는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 이미지 배치가 완료돼 회수 대상 결과가 있을 때, **When** 회수가 실행되면, **Then** 경량 포맷 이미지가 저장되고 음식 레코드에 그 저장 경로가 기록된다.
2. **Given** 변환본 경로가 기록된 음식일 때, **When** 클라이언트가 음식 조회 API를 호출하면, **Then** 응답의 이미지 URL이 변환본을 가리킨다.
3. **Given** 생성 요청에 출력 포맷이 지정됐을 때, **When** 배치가 제출되면, **Then** 요청 본문에 포맷·압축 수준이 포함된다.
4. **Given** 회수가 중간에 실패해 재시도될 때, **When** 같은 항목을 다시 회수하면, **Then** 예약된 파일명이 유지돼 저장 경로가 바뀌지 않는다.

---

### User Story 2 - 이미 쌓인 음식 사진도 가벼워진다 (Priority: P2)

기존에 적재된 음식들도 목록에서 같은 지연을 만든다. 축적된 음식 레코드의 이미지 참조를 변환본 경로로 일괄 갱신하면 전체 카탈로그가 개선된다.

**Why this priority**: P1 없이는 신규 건이 계속 무거운 포맷으로 쌓이므로 순서상 뒤지만, 사용자 체감 범위는 P1보다 넓다.

**Independent Test**: 갱신 작업 전후로 기존 음식 표본의 응답 이미지 URL이 변환본을 가리키고 해당 이미지가 실제로 내려받아지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 원본 경로가 기록된 기존 음식이 있을 때, **When** 일괄 갱신을 수행하면, **Then** 해당 음식의 이미지 참조가 같은 파일명의 변환본 경로로 바뀐다.
2. **Given** 갱신된 음식일 때, **When** 클라이언트가 조회하면, **Then** 이미지가 깨지지 않고 정상 표시된다.

---

### Edge Cases

- 생성 API 가 출력 포맷 지정을 거부하면 배치 전량이 실패한다 — 배포 전 단건 호출 검증으로 차단한다.
- 회수 중 음식이 삭제된 경우 기존과 동일하게 항목을 실패 처리하고 이미지 참조를 기록하지 않는다.
- 이미 변환본 경로가 기록된 음식에 일괄 갱신을 다시 수행해도 경로가 중복 변형되지 않는다(멱등).
- 절대 URL(외부 이미지)로 기록된 이미지 참조는 일괄 갱신 대상에서 제외한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 이미지 생성 요청은 경량 포맷(webp)과 압축 수준을 지정해, 생성 결과를 그 포맷으로 받아야 한다.
- **FR-002**: 이미지 배치 회수는 받은 경량 포맷 이미지를 저장하고, 음식 레코드의 이미지 참조로 그 저장 경로를 기록해야 한다(저장 키와 기록 값이 같다).
- **FR-003**: 회수 항목의 파일명 예약은 기존 원본 키 기준을 유지해야 하며, 재시도 시 예약된 파일명이 변경되지 않아야 한다.
- **FR-004**: 이미지 저장 시 콘텐츠 타입이 실제 포맷과 일치해야 한다.
- **FR-005**: 출력 포맷·압축 수준은 설정으로 조정 가능해야 하며, 미설정 시 생성 API 의 기본 동작을 따라야 한다.
- **FR-007**: 기존에 적재된 음식의 이미지 참조는 스키마 변경 없이 변환본 경로로 일괄 갱신돼야 하며, 반복 수행해도 결과가 같아야 한다.
- **FR-008**: 이미지 크기(픽셀 해상도)는 변환 전후로 동일해야 한다 — 리사이즈하지 않는다.
- **FR-009**: 이미지 URL 조립 규칙(기준 URL + 참조 경로)은 변경 없이 그대로 동작해야 한다.

### Key Entities

- **음식(Food)**: 사용자에게 노출되는 음식 정보. 이미지 참조 값 하나를 가지며, 이 값이 원본 경로 대신 변환본 경로를 가리키게 바뀐다.
- **이미지 배치 항목(ImageBatchItem)**: 음식 1건에 대한 이미지 생성 요청의 처리 단위. 재시도 안정성을 위해 예약된 파일명을 보유하며, 이 값은 원본 키 기준을 유지한다.
- **저장 객체**: 경량 포맷 한 벌만 저장한다. (전환 이전에 적재된 무손실 원본은 삭제하지 않고 남겨 둔다.)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 음식 사진 1장의 전송 용량이 기존 대비 80% 이상 줄어든다.
- **SC-002**: 캐시되지 않은 목록 화면에서 사진 6장이 모두 표시되기까지 걸리는 시간이 기존 대비 절반 이하가 된다.
- **SC-003**: 신규 생성 음식의 100%가 변환본 경로로 조회된다.
- **SC-004**: 일괄 갱신 후 이미지가 있는 기존 음식의 100%가 변환본 경로로 조회되며, 이미지 깨짐 신고가 발생하지 않는다.
- **SC-005**: 사진 화질에 대한 육안 열화가 없다(동일 해상도 유지).

## Assumptions

- 이미지 생성 API 가 출력 포맷 지정을 지원한다(배포 전 단건 호출로 검증한다 — 미지원이면 별도 변환 파이프라인으로 복귀).
- 무손실 원본을 보존하지 않는다 — 실측상 화질 열화가 없고, 필요 시 재생성 비용이 낮다.
- 파일명 생성 규칙(해시 + 임의 문자열)은 유지하고 확장자만 바뀐다.
- 이미 적재된 자산은 별도 일괄 변환으로 같은 경로 규칙에 맞춰 두었으므로, 기존 데이터 갱신은 문자열 규칙 변환으로 처리 가능하다.
- 기존 이미지 참조 갱신은 마이그레이션 이력에 남기지 않고 직접 수행한다(운영 DB 대상 1회성 작업).
- 이미지 서빙 앞단(CDN)의 캐시 동작은 이미 정상이며 이번 변경으로 조정하지 않는다.
- 클라이언트는 변환 포맷을 지원한다(현행 앱 이미지 컴포넌트 기준).
