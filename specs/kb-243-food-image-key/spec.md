# Feature Specification: 음식 이미지·스캔 이미지 저장 키 규약 정비

**Feature Branch**: `kb-243-food-image-key`

**Created**: 2026-07-29 (개정: /speckit-plan 사용자 결정 반영)

**Status**: Draft

**Input**: User description: "243. 실제 음식 사진의 path가 원하는대로 설정되어있지 않음. 그리고 사용자가 메뉴판 스캔했을 때 이미지도 저장경로가 현재 어떻게 되어있는지 확인후 작업이 필요하면 같이 진행하려고함." + 플랜 단계 결정: "음식 사진은 images/food/{음식이름 해싱}_{uuid}.{ext}, 메뉴판 스캔은 images/scans/{yyyy}/{mm}/{member_id}_{uuid}.{ext} 구조로 수정."

**Jira**: [KB-243](https://simhani1.atlassian.net/browse/KB-243) — 단, 저장 폴더는 이슈 본문의 `images/menus/` 가 아니라 **`images/food/`** 로 확정(플랜 단계 사용자 결정, Jira DoD 문구보다 우선).

## 배경 조사 결과

- **음식 이미지(배치 생성)**: 배치 회수 단계가 `images/food/{음식ID}.png` 키로 저장 중. 파일명에 uuid 가 없어 재생성 시 같은 키를 덮어써 CDN/브라우저 캐시가 갱신되지 않고, 파일명이 기존 시딩 규약(`{sha256(음식명) 앞 12자리}_{uuid 16자리}.png`)과 다르다. → **파일명을 규약에 일치**: `images/food/{sha256(음식명)[:12]}_{uuid16}.png`.
- **메뉴판 스캔 이미지(사용자 업로드)**: 업로드 URL 발급 키가 `{환경접두}/images/scan/{yyyy}/{MM}/{회원ID}/{uuid}.{확장자}`. 덮어쓰기·캐시 문제는 없으나 폴더명 단수(`scan`)·회원ID 가 폴더 계층인 구조를 개편한다. → **`{환경접두}/images/scans/{yyyy}/{mm}/{회원ID}_{uuid}.{확장자}`** (회원ID 를 파일명으로 이동, 폴더는 연/월까지만).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 배치 생성 음식 이미지의 파일명 규약 일치 (Priority: P1)

운영자가 이미지 배치를 제출하고 회수가 완료되면, 생성된 음식 사진이 `images/food/{sha256(음식명) 앞 12자리}_{uuid 16자리}.{확장자}` 키로 저장되어, 재생성할 때마다 새 파일명이 만들어지고 음식의 이미지 참조가 새 키로 갱신된다.

**Why this priority**: 이슈의 핵심 결함 — uuid 없는 고정 키는 재생성 시 덮어쓰기로 CDN 캐시가 갱신되지 않아 사용자에게 옛 이미지가 계속 보인다.

**Independent Test**: 배치 회수 성공 경로를 실행해 저장 키가 형식(폴더 `images/food/`, 해시 12자리, uuid 16자리, 확장자)과 일치하고, 두 번 회수하면 서로 다른 키가 나오는지 확인.

**Acceptance Scenarios**:

1. **Given** 완료된 이미지 배치의 결과에 음식 이미지가 있을 때, **When** 회수가 실행되면, **Then** 이미지는 `images/food/{sha256(음식명)[:12]}_{uuid16}.png` 키로 저장되고 음식의 이미지 참조가 이 키로 갱신된다.
2. **Given** 음식 이미지 저장 키를 생성할 때, **When** 키가 만들어지면, **Then** 환경별 접두가 붙지 않는다(음식 사진은 환경 공용 — KB-171).
3. **Given** 이미 이미지가 있는 음식을 재생성·회수할 때, **When** 저장되면, **Then** 이전과 다른 새 uuid 키가 만들어져 기존 객체를 덮어쓰지 않고, 이미지 참조가 새 키로 바뀐다.
4. **Given** 저장 키를 여러 번 생성할 때, **When** 같은 음식명이 입력되어도, **Then** uuid 가 매번 달라 키가 충돌하지 않는다. (동명 음식 2건은 `korean_name` unique 제약으로 도메인상 존재 불가 — 키 생성 규칙 검증으로 갈음.)

---

### User Story 2 - 메뉴판 스캔 업로드 키 구조 개편 (Priority: P2)

사용자가 메뉴판 스캔용 업로드 URL 을 발급받으면, 객체 키가 `{환경접두}/images/scans/{연도}/{월}/{회원ID}_{uuid}.{확장자}` 구조로 발급되어, 버킷의 스캔 이미지가 연/월 폴더 아래 회원ID 를 파일명에 담은 단일 규약으로 쌓인다.

**Why this priority**: 기능 결함은 아니고 구조 정비 — 기존 키도 동작하지만 규약을 하나로 통일해 운영·조회를 단순화한다.

**Independent Test**: 스캔 목적의 업로드 URL 발급을 실행해 발급 키가 새 형식과 일치하는지 확인.

**Acceptance Scenarios**:

1. **Given** 스캔 목적의 업로드 요청이 유효할 때, **When** 업로드 URL 이 발급되면, **Then** 객체 키는 `{환경접두}/images/scans/{yyyy}/{mm}/{회원ID}_{uuid}.{확장자}` 형식이다.
2. **Given** 규약 변경 이전에 구 키(`images/scan/.../{회원ID}/{uuid}.jpg`)로 업로드된 이미지가 있을 때, **When** 그 경로로 스캔·조회를 진행하면, **Then** 저장된 경로 문자열 그대로 동작한다(소급 이관 없음).

---

### Edge Cases

- 회수 시점에 음식이 삭제된 경우: 기존 동작(해당 건 실패 처리 후 건너뜀)을 유지한다.
- 음식명에 한글·공백·특수문자가 있는 경우: 해시 입력은 음식명 그대로, 키에는 16진수만 남아 파일명 안전성은 형식이 보장한다.
- 규약 변경 이전에 저장된 객체(`images/food/{id}.png`, `images/scan/...`): 이미지 참조/경로가 가리키는 한 계속 서빙된다. 일괄 이관은 범위 밖.
- 스캔 외 업로드 목적(프로필 등): 동일한 키 형태(`{회원ID}_{uuid}` 파일명)를 공유하되 폴더명은 기존 값을 유지한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 배치 회수가 저장하는 음식 이미지 키는 `images/food/{sha256(음식명) 소문자 16진수 앞 12자리}_{uuid 소문자 16진수 16자리}.{확장자}` 형식이어야 한다(배치 산출물의 확장자는 png).
- **FR-002**: 음식 이미지 저장 키에는 환경별 접두를 붙이지 않는다(환경 공용 — KB-171 결정과 일관).
- **FR-003**: 같은 음식을 다시 생성·회수할 때마다 새 uuid 로 새 키가 만들어져야 하며, 기존 키를 덮어쓰지 않아야 한다.
- **FR-004**: 이미지 저장이 성공하면 해당 음식의 이미지 참조가 새 키로 갱신되어야 한다(회수 항목의 완료 기록도 동일 키를 남긴다).
- **FR-005**: 음식 이미지 파일명 생성 규칙(해시 12자리·uuid 16자리·구분자 `_`·png 확장자)은 자동화된 테스트로 고정되어야 한다.
- **FR-006**: 메뉴판 스캔 업로드 URL 발급 키는 `{환경접두}/images/scans/{yyyy}/{mm}/{회원ID}_{uuid}.{확장자}` 형식이어야 한다(환경접두는 KB-171 대로 업로드 키에만 적용).
- **FR-007**: 규약 변경 이전에 저장된 이미지 경로(음식·스캔 모두)는 저장된 문자열 그대로 계속 유효해야 한다 — 소급 이관·리네임을 하지 않는다.

### Key Entities

- **음식(Food)**: 이미지 참조(저장 키)를 보유. 회수 성공 시 참조가 새 규약 키로 갱신된다.
- **이미지 배치 항목(ImageBatchItem)**: 배치 내 음식 1건의 생성 요청/결과 상태. 완료 시 저장된 키를 기록한다.
- **업로드 이미지(UploadedImage)**: 사용자가 업로드한 객체의 경로·소유자 기록. 경로 문자열을 그대로 저장하므로 키 규약 변경의 영향을 받지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 본 변경 이후 배치로 생성·저장되는 음식 이미지의 100%가 `images/food/{해시12}_{uuid16}` 파일명 규약을 따른다.
- **SC-002**: 이미지를 재생성한 음식은 캐시 삭제 등 별도 조치 없이 다음 조회부터 새 이미지가 노출된다(재생성 후 옛 이미지가 보이는 사례 0건).
- **SC-003**: 본 변경 이후 발급되는 스캔 업로드 키의 100%가 `images/scans/{yyyy}/{mm}/{회원ID}_{uuid}` 규약을 따르고, 구 키로 저장된 이미지의 조회 실패 0건.

## Assumptions

- 해시·uuid 자릿수는 기존 시딩 도구(kbap-image-maker) 규약(해시 12자리·uuid 16자리, 예: `7eb8f793d0c9_bee76f920e204f64.png`)을 따른다 — 사용자 결정은 폴더(`images/food/`)와 구조만 지정했고 자릿수는 기존 규약 유지로 해석한다.
- 저장 폴더는 Jira DoD 의 `images/menus/` 가 아니라 `images/food/` 다(플랜 단계 사용자 결정이 우선). Jira 이슈 본문은 별도 갱신 대상.
- 기존 객체(`images/food/{id}.png`·`images/menus/...`·`images/scan/...`)의 일괄 이관·삭제는 범위 밖이다.
- 스캔 외 업로드 목적(프로필)은 같은 발급 로직을 공유하므로 파일명 형태(`{회원ID}_{uuid}`)는 함께 바뀌되 폴더명은 기존 유지한다 — 별도 요구 시 후속.
- 배치 제출 측(요청 생성)은 변경하지 않는다 — 저장 키는 회수(저장) 시점에 결정된다.
