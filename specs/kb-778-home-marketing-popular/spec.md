## User Scenarios & Testing *(mandatory)*

### User Story 1 - 새 버전 앱은 홈 인기 음식 자리에 외국인 선호 음식을 본다 (Priority: P1)

`X-API-Version` 2.1 이상으로 홈을 여는 사용자(회원·비회원)는 인기 음식 자리에서 운영자가 정해 둔 "외국인 선호 음식" 풀에서 뽑은 최대 10개를 본다. 실제 조회 수와 무관하며, 홈의 다른 섹션(기피 성분·리뷰 인기·최근 스캔)과 응답 구조는 지금과 같다. 호출마다 무작위로 뽑아 풀이 10개보다 크면 사용자마다·호출마다 다른 조합을 본다.

**Why this priority**: 기능의 본체다.

**Independent Test**: 풀을 설정하고 2.1 로 홈을 조회하면 인기 음식이 풀의 READY 음식 중 최대 10개다.

**Acceptance Scenarios**:

1. **Given** 풀이 `[A, B, C]` 이고 셋 다 READY 일 때, **When** 2.1 로 홈을 조회하면, **Then** 인기 음식은 `{A, B, C}` 전부(순서 무관)다.
2. **Given** 풀에 READY 음식이 12개일 때, **When** 2.1 로 홈을 조회하면, **Then** 인기 음식은 그중 서로 다른 10개다.
3. **Given** 풀이 적용 중일 때, **When** 회원이 2.1 로 조회하면, **Then** 각 음식의 안전 여부·북마크·평점·표시 언어는 기존과 같이 그 회원 기준으로 계산된다.
4. **Given** 풀이 적용 중일 때, **When** 같은 회원이 1.0 과 2.1 로 조회하면, **Then** 인기 음식 섹션을 제외한 응답은 같다.

---

### User Story 2 - 구 버전 앱은 아무 영향을 받지 않는다 (Priority: P1)

2.1 미만 헤더(1.0·1.1·2.0)를 보내는 앱은 지금과 똑같이 최근 30일 조회 수 집계 기반 인기 음식을 본다. 경로·응답 구조·필드는 바뀌지 않는다.

**Why this priority**: 이미 배포된 앱의 동작을 바꾸지 않는 것이 릴리스 안전의 전제다.

**Independent Test**: 같은 설정에서 1.0·2.0 으로 홈을 조회하면 인기 음식이 조회 수 집계 순서다.

**Acceptance Scenarios**:

1. **Given** 풀이 설정돼 있을 때, **When** 1.0 으로 홈을 조회하면, **Then** 인기 음식은 조회 수 집계 결과이고 풀은 반영되지 않는다.
2. **Given** 풀이 설정돼 있을 때, **When** 2.0 으로 홈을 조회하면, **Then** 인기 음식은 조회 수 집계 결과다.

---

### User Story 3 - 보여줄 수 없는 음식은 풀에서 조용히 빠진다 (Priority: P2)

풀에 콘텐츠가 준비되지 않은(READY 가 아닌) 음식이나 존재하지 않는·삭제된 id 가 섞여 있으면 그 항목만 제외하고 나머지에서 뽑는다. 빠진 자리는 조회 수 집계로 채우지 않는다.

**Why this priority**: 설정 실수나 콘텐츠 상태 변화로 준비 안 된 음식이 노출되는 것을 막는다.

**Independent Test**: 풀 `[A, B(비READY), C]` 로 설정하면 2.1 인기 음식은 `{A, C}` 두 건이다.

**Acceptance Scenarios**:

1. **Given** 풀 `[A, B, C]` 중 B 가 READY 가 아닐 때, **When** 2.1 로 조회하면, **Then** 인기 음식은 `{A, C}` 이고 길이는 2 다.
2. **Given** 풀에 존재하지 않거나 삭제된 음식 id 가 있을 때, **When** 2.1 로 조회하면, **Then** 그 id 는 제외된다.
3. **Given** 풀의 모든 음식이 READY 가 아닐 때, **When** 2.1 로 조회하면, **Then** 인기 음식은 빈 목록이다(조회 수 집계로 폴백하지 않는다).

---

### Edge Cases

- 풀에 같은 음식 id 가 중복으로 들어 있으면 한 번만 센다.
- 풀이 10건 이하이면 READY 인 것을 전부 내려준다(순서는 매 호출 무작위).
- 풀 설정이 비어 있으면 2.1 인기 음식은 빈 목록이다 — 운영상 비어 있을 일이 없다고 가정하고 폴백을 두지 않는다.
- 설정 형식이 잘못돼(숫자가 아닌 id) 읽을 수 없으면 앱 기동 시 실패해 배포 전에 드러난다.
- 2.1 은 서버가 아는 버전 집합에 등록돼야 한다 — 등록이 없으면 2.1 요청 전체가 400 이다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 홈 조회는 기존 경로·매핑 하나를 유지하고, 요청의 `X-API-Version` 이 2.1 이상일 때만 인기 음식을 풀에서 뽑는다. 2.1 미만의 응답 내용·구조는 바뀌지 않는다.
- **FR-002**: 풀(음식 id 목록)은 배포 환경 설정값으로 관리한다. 변경에 코드 수정이 필요하지 않다.
- **FR-003**: 2.1 이상 응답의 인기 음식은 풀 중 READY 인 음식에서 호출마다 무작위로 최대 10개를 뽑는다.
- **FR-004**: 풀 중 콘텐츠 상태가 READY 가 아니거나 존재하지 않는(삭제 포함) 음식은 제외한다. 제외로 생긴 빈자리는 채우지 않는다. 모두 제외되면 빈 목록이다.
- **FR-005**: 풀의 중복 id 는 한 번만 센다.
- **FR-006**: 버전과 무관하게 각 음식의 안전 여부·북마크·평점·표시 언어는 요청자 기준으로 기존과 동일하게 계산되고, 나머지 섹션(기피 성분·리뷰 인기·최근 스캔)은 동일하다.
- **FR-007**: 테스트로 (a) 2.1 에서 풀 노출·10개 상한, (b) 2.1 미만의 집계 유지, (c) 비READY·미존재 제외·전부 제외를 검증한다.

### Key Entities

- **마케팅 인기 풀 설정**: 음식 id 목록. 배포 환경 설정값이며 DB 에 저장하지 않는다.
- **음식(Food)**: 기존 엔티티. 콘텐츠 상태(READY 여부)와 소프트 삭제 상태가 노출 가능 여부를 결정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 2.1 이상 앱의 인기 음식은 항상 풀의 READY 음식 부분집합이며 길이는 min(풀 READY 수, 10) 이다.
- **SC-002**: 2.1 미만 앱의 홈 응답은 이 기능 도입 전과 동일한 구조·값을 유지한다.
- **SC-003**: 풀 변경은 설정값 수정 + 배포만으로 반영된다.
- **SC-004**: 2.1 홈 응답 시간은 기존 대비 체감 차이가 없다(id 목록 PK 조회 1회, 집계 없음).

## Assumptions

- 풀은 설정값 한 종류(전 사용자 공통)다. 회원 국적·언어별로 다른 풀은 범위 밖이다.
- 풀은 비어 있지 않게 운영한다(사용자 결정 — 폴백 없음).
- 기간 설정은 없다 — 끄려면 2.1 을 보내는 앱이 없어지거나 설정을 바꿔 배포한다.
- 설정 변경의 반영 시점은 앱 재기동(배포)이다.
- 관리자 화면·API 로 풀을 편집하는 기능은 범위 밖이다.
- 기존 조회 수 집계 캐시(KB-725)의 동작·TTL 은 변경하지 않는다.
