# Feature Specification: dev 로그 출력을 prod 와 동일하게

**Feature Branch**: `kb-652-dev-log-prod-parity`

**Created**: 2026-09-30

**Status**: Draft

**Jira**: [KB-652](https://simhani1.atlassian.net/browse/KB-652)

**Input**: User description: "develop 쪽 로그 출력 포맷을 prod 환경과 동일하게 맞추고 부하 테스트를 진행하면서 1만명 동접자를 목표로 램프업 테스트를 진행할 것이다. 따라서 로그 출력을 동일하게 맞추는 작업이 필요하다."

## 배경

dev 환경에서 1만 동접을 목표로 램프업 부하 테스트를 진행할 예정이다. 부하 테스트의 목적은 prod 가 그 부하를 견디는지 미리 아는 것이므로, dev 의 측정치가 prod 를 대표해야 한다. 그런데 지금 dev 와 prod 는 로그를 다르게 낸다.

- prod·staging 의 api 는 수집기가 필드 단위로 검색할 수 있는 **JSON 구조화 형식**으로 로그를 내고, SQL 문은 로그에 찍지 않는다.
- dev 의 api 는 사람이 읽는 **텍스트 형식**으로 로그를 내고, 실행되는 **모든 SQL 문을 표준 출력에 찍는다**. 배치도 dev 만 SQL 문을 찍는다.

로그 형식과 SQL 출력은 요청마다 CPU(직렬화)와 출력 I/O 를 소비한다. 이 비용이 prod 와 다르면 부하 테스트에서 얻은 응답 시간·처리량·자원 사용량이 prod 의 것과 다르고, 특히 SQL 전량 출력은 높은 부하에서 병목 자체가 될 수 있다. 또한 dev 로그가 텍스트라 수집기에서 요청 상관 키·회원 식별자로 검색할 수 없어, 부하 중 발생한 오류를 추적하기 어렵다.

이 작업은 dev 의 로그 출력 설정을 prod 와 같게 맞춘다. 로컬 개발 환경은 개발 편의를 위해 그대로 둔다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 부하 테스트 측정치가 prod 를 대표한다 (Priority: P1)

부하 테스트 수행자가 dev 에 램프업 부하를 걸면, 애플리케이션이 로그를 내는 비용(형식·양)이 prod 와 같아서 측정한 응답 시간·처리량·자원 사용량을 prod 예측치로 쓸 수 있다.

**Why this priority**: 이 작업의 존재 이유다. 로그 비용이 다르면 부하 테스트 결과 전체가 prod 에 대해 무의미하다.

**Independent Test**: dev 에 배포된 api 의 로그 한 줄과 prod 의 로그 한 줄을 나란히 놓고 형식·필드 집합이 같은지 확인한다. 같은 요청을 보내고 SQL 문이 로그에 나오지 않음을 확인한다.

**Acceptance Scenarios**:

1. **Given** dev 에 배포된 api, **When** 홈 조회 같은 임의 요청을 보내면, **Then** 그 요청의 로그 줄이 prod 와 같은 JSON 구조화 형식이고 같은 필드 집합(요청 상관 키·회원 식별자 포함)을 가진다.
2. **Given** dev 에 배포된 api, **When** DB 를 읽는 요청을 보내면, **Then** 실행된 SQL 문이 로그에 나오지 않는다.
3. **Given** dev 에 배포된 배치, **When** DB 를 읽는 작업이 돌면, **Then** 실행된 SQL 문이 로그에 나오지 않는다.

---

### User Story 2 - 부하 중 오류를 필드로 추적한다 (Priority: P2)

부하 테스트 중 오류가 나면, 수행자가 수집기에서 요청 상관 키나 회원 식별자로 해당 요청의 로그만 골라 볼 수 있다.

**Why this priority**: 1만 동접 램프업에서 오류는 반드시 나오고, 텍스트 로그 수천만 줄에서 grep 으로 찾는 것은 현실적이지 않다. P1 의 형식 통일이 이 능력을 함께 가져온다.

**Independent Test**: dev 로그 수집기에서 특정 요청 상관 키로 조회했을 때 그 요청의 로그 줄만 나온다.

**Acceptance Scenarios**:

1. **Given** dev 에서 처리된 요청의 상관 키, **When** 수집기에서 그 키로 검색하면, **Then** 그 요청의 로그 줄만 반환된다.

---

### User Story 3 - 로컬 개발 경험은 변하지 않는다 (Priority: P3)

로컬에서 앱을 띄우는 개발자는 이전과 같은 텍스트 로그와 SQL 출력을 본다.

**Why this priority**: 로컬은 부하 테스트 대상이 아니고, SQL 을 눈으로 보는 것이 개발 중 유용하다. dev 를 맞추면서 로컬까지 바꾸면 불필요한 불편이 생긴다.

**Independent Test**: 로컬 프로필 설정 파일에 변경이 없다.

**Acceptance Scenarios**:

1. **Given** 로컬 프로필로 띄운 api, **When** 요청을 보내면, **Then** 이전과 같은 텍스트 로그와 SQL 출력이 나온다.

---

### Edge Cases

- dev 배포 후 로그 수집기가 JSON 을 그대로 한 필드에 넣고 파싱하지 않으면 필드 검색이 안 된다. prod 가 이미 같은 형식으로 수집되고 있으므로 dev 도 같은 수집 경로를 타는지 배포 후 확인한다.
- 구조화 로그로 바꾸면 사람이 dev 콘솔을 직접 읽기 불편해진다. 이는 prod 와 같은 조건이며 수집기 조회로 대체한다.
- 배치는 prod 도 구조화 형식이 아니다. 배치 dev 는 SQL 출력만 끄고 형식은 prod 와 같게(텍스트) 둔다 — "prod 와 동일" 이 기준이지 "JSON" 이 기준이 아니다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: dev 프로필의 api 는 prod 프로필과 **같은 로그 출력 형식**(JSON 구조화, 같은 필드 집합)으로 로그를 내야 한다.
- **FR-002**: dev 프로필의 api 는 실행된 SQL 문을 로그에 **출력하지 않아야** 한다(prod 와 동일).
- **FR-003**: dev 프로필의 배치는 실행된 SQL 문을 로그에 **출력하지 않아야** 한다(배치 prod 와 동일). 배치의 로그 형식은 prod 와 같게 유지한다.
- **FR-004**: 로컬 프로필의 로그 형식·SQL 출력은 **변경하지 않아야** 한다.
- **FR-005**: staging·prod 프로필의 로그 설정은 **변경하지 않아야** 한다.
- **FR-006**: 로그 형식 설정이 프로필별로 의도대로 잡혀 있는지 검사하는 기존 자동 검증이 있다면, dev 프로필을 그 검사 대상에 포함해야 한다. 별도의 도메인 테스트는 만들지 않는다(설정만 켜는 변경).
- **FR-007**: 변경은 설정 파일 범위로 한정하며, 로그를 남기는 코드·로그 메시지 내용은 바꾸지 않는다.

### Key Entities

- **로그 줄**: 한 요청 또는 한 작업 단위에서 나오는 기록. prod 에서는 시각·수준·메시지·요청 상관 키·회원 식별자 등이 필드로 분리된 JSON 한 줄이다.
- **프로필**: 실행 환경 구분(local·dev·staging·prod). 로그 설정은 프로필별 설정 파일이 결정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: dev 와 prod 의 api 로그 한 줄을 비교했을 때 형식과 필드 집합이 **일치**한다(차이 0개 필드).
- **SC-002**: dev api·배치에서 DB 를 읽는 요청·작업을 실행했을 때 로그에 나오는 SQL 문이 **0건**이다.
- **SC-003**: 로컬 프로필 설정 파일과 staging·prod 프로필 설정 파일의 변경이 **0줄**이다.
- **SC-004**: dev 수집기에서 요청 상관 키로 검색하면 해당 요청의 로그만 반환된다(다른 요청 로그 혼입 0건).
- **SC-005**: 기존 자동 테스트가 전부 통과한다.

## Assumptions

- "prod 와 동일" 의 기준은 **각 앱의 prod 프로필**이다. api 는 JSON 구조화 + SQL 미출력, 배치는 텍스트 + SQL 미출력이 된다. 배치를 JSON 으로 바꾸는 것은 이 작업의 범위가 아니다.
- dev 로그 수집 경로(수집기·대시보드)는 이미 prod 와 같은 방식으로 구성돼 있어 형식만 맞추면 필드 검색이 된다고 본다. 아니면 배포 후 확인 단계에서 드러나며, 수집 경로 정비는 별도 작업으로 뺀다.
- 로그 수준(level) 설정은 dev 와 prod 가 이미 같으므로 손대지 않는다. 다르다는 것이 확인되면 같은 작업에서 맞춘다.
- 이 작업은 부하 테스트의 전제이며, 부하 테스트 자체(시나리오·램프업 계획·목표치)는 별도 작업이다.
- 검증은 설정 변경 후 dev 배포와 실제 로그 확인으로 한다. 프레임워크 기본 기능을 설정으로 켜는 것이라 도메인 테스트를 추가하지 않는다.
