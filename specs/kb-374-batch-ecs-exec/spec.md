# Feature Specification: 배치 잡 원격 트리거 — 클러스터 밖 운영 도구가 dev/prod 배치 잡을 실행

**Feature Branch**: `kb-374-batch-ecs-exec`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: "374 워크트리" — Jira KB-374: 배치 잡 원격 트리거를 위한 ECS Exec 활성화 — 홈서버 젠킨스가 인바운드 개방 없이 dev/prod 잡 실행

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 운영자가 클러스터 밖에서 배치 잡을 실행한다 (Priority: P1)

운영자(또는 운영자가 홈서버에 둔 자동화 도구)가 사무실·집 등 클라우드 밖 어디에서든, 클라우드 계정의 자격증명만으로 dev 또는 prod 배치 앱에 "이 잡을 지금 실행하라"고 지시하고, 실행이 접수되었는지·완료/실패했는지 확인할 수 있다. 이를 위해 배치 앱의 잡 실행 포트를 인터넷이나 특정 IP 에 개방하지 않는다.

**Why this priority**: 현재 배치 잡은 클러스터 내부에서만 실행할 수 있어, 정기 스케줄 외의 수동·임시 실행(재처리, 장애 복구, 신규 잡 시운전)을 하려면 서버에 직접 들어가야 한다. 이 경로를 여는 것이 기능의 존재 이유다.

**Independent Test**: dev 환경에 적용한 뒤, 클라우드 밖 PC 에서 dev 자격증명으로 잡 하나를 실행 지시 → 접수 응답(실행 ID)을 받고 → 같은 경로로 그 실행 ID 의 상태를 조회해 완료가 확인되면 통과. 같은 시도를 배치 포트에 직접 접속하는 방식으로 하면 여전히 거부되어야 한다.

**Acceptance Scenarios**:

1. **Given** dev 배치 앱이 기동 중이고 운영자에게 dev 실행 권한이 있다, **When** 클러스터 밖에서 잡 이름을 지정해 실행을 지시하면, **Then** 실행이 접수되고 실행 ID 가 반환된다.
2. **Given** 실행 ID 를 받았다, **When** 클러스터 밖에서 그 실행의 상태를 조회하면, **Then** 진행 중/완료/실패 상태와 시각을 확인할 수 있다.
3. **Given** 같은 잡이 이미 실행 중이다, **When** 다시 실행을 지시하면, **Then** 중복 실행이 거부되고 진행 중인 실행 ID 를 알려준다(기존 배치 앱의 중복 방지 동작이 원격에서도 동일).
4. **Given** 운영자가 클라우드 자격증명 없이 배치 앱의 잡 실행 주소로 직접 접속을 시도한다, **When** 인터넷 어디에서 접속하든, **Then** 연결 자체가 거부된다(포트 미개방 유지).

---

### User Story 2 - dev 와 prod 실행 권한이 분리된다 (Priority: P2)

운영자는 dev 용 자격증명과 prod 용 자격증명을 따로 가진다. dev 자격증명으로는 prod 잡을 실행할 수 없고 그 반대도 마찬가지라서, 자동화 도구 설정 실수로 잘못된 환경의 잡이 실행되는 사고를 구조적으로 막는다.

**Why this priority**: 한 도구가 두 환경을 다루는 순간 가장 흔한 사고가 "환경 착각"이다. P1 이 열어주는 경로에 붙는 안전장치라 P1 다음이다.

**Independent Test**: dev 자격증명으로 prod 클러스터의 배치에 실행 지시 → 권한 거부. prod 자격증명으로 dev 에 지시 → 권한 거부. 각 자격증명으로 자기 환경은 성공.

**Acceptance Scenarios**:

1. **Given** dev 자격증명만 가진 운영자, **When** prod 배치 잡 실행을 지시하면, **Then** 권한 없음으로 거부되고 prod 에서 아무 실행도 시작되지 않는다.
2. **Given** dev 자격증명, **When** 배치가 아닌 다른 컨테이너(api 등)에 명령 실행을 시도하면, **Then** 거부된다 — 원격 명령 실행은 배치 컨테이너로만 한정된다.

---

### User Story 3 - 원격 실행 절차가 문서로 남는다 (Priority: P3)

팀원 누구나 문서만 보고 동일한 절차로 잡을 원격 실행할 수 있다(어떤 자격증명·어떤 명령·상태 조회 방법).

**Why this priority**: 절차가 특정인의 셸 히스토리에만 있으면 기능이 없는 것과 같다. 구현 후 마무리 작업.

**Independent Test**: 문서를 처음 보는 팀원이 문서만으로 dev 잡 하나를 실행하고 상태를 조회할 수 있으면 통과.

**Acceptance Scenarios**:

1. **Given** 인프라 문서에 원격 실행 절차가 있다, **When** 팀원이 절차대로 따라 하면, **Then** 추가 질문 없이 잡 실행·상태 조회에 성공한다.

---

### Edge Cases

- 배치 앱이 내려가 있거나(desired 0) 기동 중이라 아직 준비되지 않았을 때 실행을 지시하면? → 접수 불가가 명확한 오류로 드러나야 하며, 조용히 성공한 것처럼 보이면 안 된다.
- 잡 이름을 잘못 지정하면? → 배치 앱이 알려주는 "알 수 없는 잡 + 실행 가능한 잡 목록" 응답이 원격에서도 그대로 전달된다.
- 원격 명령 실행 도중 운영자 쪽 연결이 끊기면? → 잡 실행은 접수 즉시 배치 앱 안에서 독립적으로 진행되므로 영향이 없고, 실행 ID 로 나중에 상태를 확인할 수 있다.
- 새 배치 버전을 배포한 직후에도 원격 실행이 계속 되나? → 배포로 컨테이너가 교체되어도 원격 실행 능력은 유지되어야 한다(설정이 배포마다 사라지면 안 됨).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 운영자는 클라우드 자격증명만으로, 클러스터 밖에서 dev·prod 각 배치 앱의 잡을 이름으로 지정해 실행 지시할 수 있어야 한다.
- **FR-002**: 운영자는 같은 경로로 특정 실행의 상태(진행/완료/실패, 시각)를 조회할 수 있어야 한다.
- **FR-003**: 배치 앱의 잡 실행 포트는 계속해서 클러스터 내부에서만 접근 가능해야 하며, 이 기능을 위해 인터넷·특정 IP 대역에 개방해서는 안 된다.
- **FR-004**: 원격 실행 권한은 환경별로 분리되어야 한다 — dev 자격증명은 dev 배치에만, prod 자격증명은 prod 배치에만 유효하다.
- **FR-005**: 원격 명령 실행 대상은 배치 컨테이너로 한정되어야 한다 — 같은 자격증명으로 api 등 다른 컨테이너에 명령을 실행할 수 없다.
- **FR-006**: 원격 실행 능력은 배치 앱 재배포·컨테이너 교체 후에도 유지되어야 한다(인프라 정의의 일부로 관리).
- **FR-007**: 배치 앱의 기존 실행 의미(접수 즉시 반환, 실행 ID 로 상태 조회, 동일 잡 중복 실행 거부, 알 수 없는 잡 오류)는 원격 경로에서도 동일하게 전달되어야 한다.
- **FR-008**: 원격 실행 절차(필요 자격증명, 실행 지시·상태 조회 방법)가 인프라 문서에 기록되어야 한다.

### Key Entities *(include if feature involves data)*

- **배치 잡 실행(Job Execution)**: 잡 이름·실행 ID·상태·시작/종료 시각. 배치 앱이 이미 영속화하는 실행 이력이며 이 기능은 새 데이터를 만들지 않는다.
- **환경별 운영 자격증명**: dev 용·prod 용 각 1개. 해당 환경의 배치 컨테이너에 대한 원격 명령 실행 권한만 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영자가 클라우드 밖에서 dev 잡 실행 지시 → 실행 ID 수신까지 1분 이내에 완료된다(서버 접속·터널 설정 없이).
- **SC-002**: 이 기능 적용 전후로 배치 앱에 인터넷에서 접근 가능한 포트가 0개로 동일하다.
- **SC-003**: 환경 교차 실행 시도(dev 자격증명→prod, prod→dev)는 100% 거부된다.
- **SC-004**: 이 기능으로 인한 월 추가 인프라 비용이 0이다(새 서버·부하분산기·고정 IP 없음).
- **SC-005**: 문서를 처음 보는 팀원이 문서만으로 dev 잡 원격 실행에 첫 시도에 성공한다.

## Assumptions

- 배치 앱은 각 환경에 상시 기동 컨테이너 1개로 존재하고, 잡 실행은 컨테이너 내부의 HTTP 트리거(접수 즉시 반환 + 실행 ID 상태 조회)로만 이뤄진다는 현재 구조를 그대로 둔다 — 이 기능은 그 트리거를 "클러스터 밖에서 안전하게 부르는 통로"만 추가한다.
- 통로는 클라우드 제공자의 관리형 원격 명령 실행 기능(컨테이너가 바깥으로 제어 채널을 열고 대기하는 방식)을 사용한다 — 인바운드 개방 없음·추가 비용 없음이 이 선택의 근거다.
- 홈서버 자동화 도구(젠킨스)의 설치·파이프라인 작성은 범위 밖이다. 이 기능은 그 도구가 사용할 "자격증명 + 명령 절차"까지만 제공한다.
- 배치 앱의 정기 스케줄(인앱 cron)은 그대로 유지되며, 원격 실행은 수동·임시 실행 용도다.
- 배치 컨테이너 이미지에 HTTP 호출 도구(curl)가 이미 포함되어 있다(런타임 베이스 이미지 특성) — 없을 경우에만 이미지에 추가한다.
- dev·prod 인프라는 코드(Terraform)로 관리되므로 필요한 설정은 그 코드에 반영하고 dev 에 먼저 적용해 검증한다. prod 적용은 별도 판단(배포 창)으로 한다.
- 환경별 자격증명 생성 자체(계정 콘솔 작업)는 사용자가 수행하며, 이 기능은 부여할 권한의 정확한 범위를 정의한다.
