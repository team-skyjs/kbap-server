# Feature Specification: 리뷰 평가 항목 3종 추가 — 제공 속도·직원 친절도·매장 찾기 쉬움

**Feature Branch**: `kb-347-review-extra-ratings`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "KB-347 — [BE] 리뷰 평가 항목 3종 추가 — 제공 속도·직원 친절도·매장 찾기 쉬움"

## 맥락

- 현재 리뷰는 단일 별점(1~5)·본문·사진·식당 위치만 담는다. 음식 맛 외에 **매장 경험**(음식이 얼마나 빨리 나왔는지·직원이 친절했는지·매장을 찾기 쉬웠는지)을 표현할 수단이 없다.
- 외국인 사용자 대상 서비스 특성상 "찾기 쉬움"·"친절도"는 식당 선택에 큰 영향을 주는 신호다 — 리뷰에 세부 평가 3종을 추가해 열람자가 매장 경험까지 참고할 수 있게 한다.
- 기존 리뷰(항목 도입 전 작성)는 세 항목 값이 없다 — 미기입으로 노출하며 소급 입력을 강제하지 않는다.
- 명확화 확정(2026-08-18): 척도는 별점과 동일한 1~5, 입력은 0~5 로 받되 **0 = 미기입**과 동일 취급, 음식 단위 집계(요약)는 이번 범위에서 제외(후속 이슈).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 리뷰 작성 시 세부 평가 3종을 남긴다 (Priority: P1)

리뷰 작성자가 별점·본문과 함께 제공 속도·직원 친절도·매장 찾기 쉬움을 항목별 1~5 로 평가해 저장한다. 평가하지 않을 항목은 0(미기입)으로 두거나 생략한다. 리뷰 수정 시에도 세 항목을 함께 고칠 수 있다.

**Why this priority**: 데이터가 쌓여야 노출·활용이 성립한다 — 이 기능의 시작점.

**Independent Test**: 리뷰 작성 요청에 세 항목 값을 포함해 저장 → 단건 응답과 목록 조회에서 저장한 값이 그대로 보인다.

**Acceptance Scenarios**:

1. **Given** 회원이 리뷰를 작성할 때, **When** 별점과 함께 세 항목 값을 1~5 로 제출하면, **Then** 리뷰가 저장되고 응답에 세 항목 값이 포함된다.
2. **Given** 회원이 리뷰를 작성할 때, **When** 일부 항목만 1~5 로 제출하고 나머지는 0 또는 누락으로 두면, **Then** 제출한 항목만 값이 저장되고 나머지는 미기입으로 저장된다.
3. **Given** 세 항목이 저장된 리뷰, **When** 작성자가 리뷰를 수정하며 항목 값을 바꾸면(1~5 변경·0 으로 지움 포함), **Then** 바뀐 상태가 그대로 저장·노출된다.
4. **Given** 리뷰 작성·수정 요청, **When** 세 항목 값이 0~5 범위를 벗어나면, **Then** 400 으로 거절된다.

---

### User Story 2 - 리뷰 열람자가 세부 평가를 본다 (Priority: P1)

리뷰 열람자(회원·비회원)가 리뷰 목록·음식 상세 동봉 리뷰·내 리뷰에서 각 리뷰의 세부 평가 3종을 확인한다.

**Why this priority**: 저장만 되고 보이지 않으면 가치가 없다 — US1 과 함께 이 기능의 최소 완결.

**Independent Test**: 세 항목이 저장된 리뷰를 목록·상세 동봉·내 리뷰로 조회해 값 노출을 확인하고, 항목 없는 기존 리뷰는 미기입으로 내려오는지 확인.

**Acceptance Scenarios**:

1. **Given** 세 항목이 저장된 리뷰, **When** 리뷰 목록(전체·음식별)·음식 상세 recentReviews·내 리뷰를 조회하면, **Then** 각 리뷰 항목에 세부 평가 3종 값이 포함된다.
2. **Given** 세 항목 도입 전에 작성된 기존 리뷰 또는 미기입 항목, **When** 어떤 경로로든 조회하면, **Then** 해당 항목은 미기입으로 내려간다 — 1~5 값과 명확히 구분된다.
3. **Given** 비회원 열람, **When** 리뷰 목록·상세 동봉 리뷰를 조회하면, **Then** 회원과 동일하게 세 항목이 보인다 (비회원 리뷰 공개 정책 불변).

---

### Edge Cases

- 세 항목 중 일부만 제출하면? — 항목별 독립 저장: 1~5 만 값으로 저장, 0·누락은 미기입.
- 기존 리뷰를 수정할 때 세 항목을 안 보내면? — 누락 = 0 = 미기입으로 저장한다(리뷰 수정은 전체 교체 계약 — 기존 rating·content 와 일관).
- 리뷰 신고·차단·삭제 음식 제외 규칙은? — 기존 노출 규칙 그대로 — 세 항목은 리뷰의 속성일 뿐 노출 규칙을 바꾸지 않는다.
- 기존 별점 평균(averageRating) 집계에 섞이나? — 섞지 않는다. 세 항목은 별점과 독립이며 이번 범위에서 집계 자체가 없다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 리뷰 작성·수정 시 제공 속도·직원 친절도·매장 찾기 쉬움 3개 항목을 항목별 정수로 함께 제출할 수 있어야 한다. 허용 입력은 0~5 — 1~5 는 평가값, **0 과 누락은 미기입**으로 동일 취급한다.
- **FR-002**: 0~5 범위를 벗어난 항목 값은 400 으로 거절한다.
- **FR-003**: 모든 리뷰 열람 경로(리뷰 목록·음식 상세 동봉·내 리뷰·작성/수정 응답)에서 각 리뷰의 세 항목 값이 동일한 형태로 내려간다. 미기입 항목은 평가값(1~5)과 구분되는 형태로 내려간다.
- **FR-004**: 세 항목 도입 전 작성된 기존 리뷰는 전 항목 미기입으로 조회되며, 별점·본문 등 기존 데이터는 영향받지 않는다.
- **FR-005**: 기존 응답 필드(별점 rating·averageRating 등) 계약은 변경하지 않는다 — 세 항목은 추가 필드로만 들어간다(무버전 즉시 적용).
- **FR-006**: 비회원 열람 정책(리뷰 전부 공개)·차단/신고 제외·삭제 음식 제외 등 기존 노출 규칙은 변경하지 않는다.
- **FR-007**: 음식 단위 집계(항목별 요약)는 이번 범위에 포함하지 않는다 — 후속 이슈로 분리한다.

### Key Entities

- **리뷰**: 기존 리뷰에 세부 평가 3종(제공 속도·직원 친절도·매장 찾기 쉬움)이 항목별 독립 값(1~5 또는 미기입)으로 추가된다. 미기입이 유효 상태다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 리뷰 작성자가 세 항목을 포함해 리뷰를 저장하면, 모든 열람 경로에서 저장한 값이 즉시 일관되게 보인다.
- **SC-002**: 세 항목 도입 이후에도 기존 리뷰·기존 클라이언트의 리뷰 작성/조회가 회귀 없이 동작한다 — 기존 시나리오 회귀 0건.
- **SC-003**: 미기입 항목이 섞여 있어도 열람이 오표시(미기입을 평가값처럼 표시) 없이 동작한다.

## Assumptions

- 세 항목은 리뷰(음식×식당 경험)의 속성이다 — 별도 평가 객체나 식당 단위 독립 평가로 분리하지 않는다.
- 기존 단일 별점(rating)의 의미·집계(averageRating)는 불변이다 — 세 항목은 별점 평균에 섞이지 않는다.
- 입력 계약은 0~5(0=미기입)이고, 조회 응답에서 미기입의 표현(null 또는 0)은 클라이언트와 조율해 plan 단계에서 확정한다 — 어느 쪽이든 평가값과 구분된다는 계약(FR-003)은 불변.
- 응답 계약은 추가 필드만으로 확장한다 — 클라이언트 조율된 additive 변경이므로 API 버전을 올리지 않는다(KB-334 선례).
- 소급 입력(기존 리뷰에 항목 채우기 유도)은 범위 밖이다.
