# Feature Specification: 톰캣 스레드 풀을 버추얼 스레드로 전환

**Feature Branch**: `kb-653-virtual-threads`

**Created**: 2026-09-30

**Status**: Draft

**Jira**: [KB-653](https://simhani1.atlassian.net/browse/KB-653)

**Input**: User description: "tomcat 스레드 풀을 버츄얼 스레드로 대체해보려고 한다. 그럼 동접자가 늘어날 것을 기대하고 있음. 액츄에이터에서 tomcat 스레드 풀이 아니라 버츄얼 스레드 중 활성화된 스레드 지표를 따로 노출시켜서 그라파나 연동이 필요한가?"

## 배경

dev 에서 홈 조회에 2천 동시 부하를 걸었을 때 웹 서버의 요청 처리 스레드 풀이 기본 상한(200)에 도달했다. 요청이 스레드를 기다리며 줄을 서 홈 조회가 평균 4.5초 걸렸고, DB 커넥션 풀(기본 10개)에서는 30초 대기를 넘긴 요청이 오류로 떨어졌다. 1만 동접 램프업 부하 테스트를 앞두고 이 상한을 걷어내야 한다.

버추얼 스레드로 전환하면 요청마다 가벼운 스레드를 새로 만들어 웹 서버 쪽 스레드 수 상한이 사라진다. 그러면 병목은 DB 커넥션 풀로 옮겨가므로 풀 크기를 함께 올려야 하고, 그 상한은 공유 RDS(dev·staging 공용)의 최대 연결 수다. 관측 쪽에서는 풀이 없어지므로 "스레드 풀 사용률" 패널이 의미를 잃고, 대신 "지금 처리 중인 요청 수" 와 "DB 커넥션 대기 수" 가 포화 지표가 된다. 이 둘은 이미 애플리케이션이 노출하고 있어 새 지표를 만들 필요는 없고 대시보드 패널만 바꾸면 된다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 웹 서버 스레드 상한이 사라져 동시 처리량이 늘어난다 (Priority: P1)

부하 테스트 수행자가 같은 홈 조회 스파이크(2천 동시 × 5회)를 걸면, 요청이 웹 서버 스레드를 기다리지 않고 곧바로 처리에 들어간다. 이전에 4.5초였던 홈 조회 시간이 줄고, 동시에 처리 중인 요청 수가 200 을 넘어선다.

**Why this priority**: 이 작업의 목적이다. 스레드 상한이 그대로면 나머지는 의미가 없다.

**Independent Test**: dev 에 배포 후 같은 k6 스크립트를 돌려 "처리 중 요청 수" 지표가 200 을 넘고, 홈 조회 p95 가 이전 측정(4.5초)보다 짧은지 비교한다.

**Acceptance Scenarios**:

1. **Given** 버추얼 스레드로 전환된 dev api, **When** 2천 동시 홈 조회 스파이크를 걸면, **Then** 처리 중 요청 수 지표의 최대값이 200 을 초과한다.
2. **Given** 같은 조건, **When** 결과를 이전 측정과 비교하면, **Then** 홈 조회 p95 가 4.5초보다 짧다.
3. **Given** 버추얼 스레드로 전환된 api, **When** 기존 자동 테스트를 돌리면, **Then** 전부 통과한다(동작 변경 없음).

---

### User Story 2 - DB 커넥션 풀이 새 병목이 되지 않는다 (Priority: P1)

스레드 상한이 사라져도 DB 커넥션 대기로 요청이 오류가 나면 안 된다. 풀 크기를 RDS 가 허용하는 범위 안에서 올려, 같은 스파이크에서 커넥션 대기 초과 오류가 나지 않는다.

**Why this priority**: 스레드만 풀면 2천 요청이 커넥션 10개 앞에서 줄을 서 오류가 폭증한다. US1 과 같은 우선순위다.

**Independent Test**: 같은 스파이크에서 커넥션 대기 초과 오류(30초 타임아웃)가 0건이고, RDS 의 실제 연결 수가 최대 연결 수를 넘지 않는다.

**Acceptance Scenarios**:

1. **Given** 풀 크기가 상향된 dev api, **When** 2천 동시 스파이크를 걸면, **Then** DB 커넥션 대기 초과 오류가 0건이다.
2. **Given** 풀 크기 결정, **When** api 인스턴스 수 × 풀 크기를 계산하면, **Then** RDS 최대 연결 수에 여유(다른 소비자·배치 포함)를 남긴다.

---

### User Story 3 - 포화를 대시보드에서 계속 볼 수 있다 (Priority: P2)

운영자가 그라파나 앱 대시보드를 열면, 스레드 풀 패널 대신 "처리 중 요청 수" 와 "DB 커넥션 대기" 로 서버 포화를 판단할 수 있다. 스레드 풀 패널이 빈 채로 남아 오해를 주지 않는다.

**Why this priority**: 지표가 없으면 다음 부하 테스트에서 어디가 막히는지 볼 수 없다. 다만 P1 이 배포된 뒤에야 확인 가능하다.

**Independent Test**: 대시보드 정의 파일에 처리 중 요청 수 패널이 있고, 스레드 풀 패널은 제거되거나 "버추얼 스레드 모드에서는 무의미" 설명이 붙어 있다. 대시보드 문서도 같은 내용으로 갱신된다.

**Acceptance Scenarios**:

1. **Given** 갱신된 대시보드 정의, **When** 그라파나에 import 하면, **Then** 처리 중 요청 수 패널이 부하 중 값을 그린다.
2. **Given** 갱신된 대시보드 문서, **When** 패널 표를 읽으면, **Then** 스레드 풀 패널의 의미 변화가 적혀 있다.

---

### User Story 4 - 버추얼 스레드가 캐리어에 고정되지 않는다 (Priority: P2)

JDK 21 에서는 특정 동기화 블록 안에서 블로킹하면 버추얼 스레드가 실제 스레드에 고정(핀닝)돼 이점이 사라진다. 부하 중 핀닝이 발생하는지 확인해 결과를 기록한다.

**Why this priority**: 핀닝이 있으면 US1 의 효과가 나지 않는다. 실측으로만 알 수 있다.

**Independent Test**: dev 에 핀닝 추적 옵션을 켜고 스파이크를 건 뒤 로그에서 핀닝 보고를 센다.

**Acceptance Scenarios**:

1. **Given** 핀닝 추적이 켜진 dev api, **When** 스파이크를 걸면, **Then** 핀닝 보고 건수와 발생 지점을 기록한다. 0건이면 통과, 있으면 원인(드라이버·라이브러리)을 적고 후속 작업으로 분리한다.

---

### Edge Cases

- 배치 앱은 요청 기반이 아니므로 대상이 아니다. api 만 전환한다.
- 스레드 수 상한이 사라지면 동시 처리 요청이 폭증해 힙 사용량·GC 가 늘 수 있다. 부하 중 GC 패널을 함께 본다.
- 웹 서버의 연결 수 상한(기본 8,192)과 로드밸런서 쪽 제한은 그대로다. 1만 동접은 이 상한에 걸릴 수 있으며, 이 작업의 범위는 스레드·DB 풀이다.
- 풀 크기를 올려도 RDS 최대 연결 수는 dev·staging·배치가 공유한다. staging 이 같은 RDS 를 쓰므로 dev 풀 크기 계산에 staging 몫을 남긴다.
- 로컬 프로필은 개발 편의를 위해 전환 여부를 강제하지 않는다. 전 프로필 공통 설정으로 켜되, 로컬에서 문제가 생기면 로컬만 끌 수 있다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: api 는 요청 처리에 버추얼 스레드를 사용해야 한다. 웹 서버 스레드 풀 상한(200)이 동시 처리 요청 수를 제한하지 않아야 한다.
- **FR-002**: DB 커넥션 풀 최대 크기를 상향해야 하며, 값은 RDS 최대 연결 수 실측값과 api 인스턴스 수·다른 소비자(staging·배치) 몫을 근거로 정하고 그 근거를 기록해야 한다.
- **FR-003**: 그라파나 앱 대시보드 정의에 "처리 중 요청 수" 패널을 추가하고, 스레드 풀 패널은 제거하거나 버추얼 스레드 모드에서 무의미함을 표시해야 한다. 대시보드 문서를 같은 내용으로 갱신해야 한다.
- **FR-004**: dev 에서 핀닝 추적을 켠 상태로 부하를 걸어 핀닝 발생 여부를 확인하고 결과를 기록해야 한다.
- **FR-005**: 전환 후 같은 k6 스크립트로 재측정해 처리 중 요청 수 최대값과 홈 조회 p95 를 이전(200 스레드·4.5초)과 비교해 기록해야 한다.
- **FR-006**: 기존 자동 테스트가 전부 통과해야 한다. 비즈니스 로직·API 계약은 바꾸지 않는다.
- **FR-007**: 배치 앱은 변경하지 않는다.

### Key Entities

- **처리 중 요청 수**: 지금 서버가 응답을 만들고 있는 HTTP 요청의 개수. 버추얼 스레드 모드에서 "활성 요청 스레드 수" 와 같다. 이미 노출되는 지표.
- **DB 커넥션 풀**: 애플리케이션이 RDS 와 유지하는 연결 묶음. 활성·유휴·대기 수와 최대 크기.
- **핀닝**: 버추얼 스레드가 블로킹 중 실제 스레드를 놓지 못하는 상태. 발생하면 동시성 이점이 사라진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 스파이크(2천 동시 × 5회)에서 처리 중 요청 수 최대값이 **200 을 초과**한다.
- **SC-002**: 같은 스파이크에서 홈 조회 p95 가 **4.5초 미만**이다(이전 측정 대비 단축).
- **SC-003**: 같은 스파이크에서 DB 커넥션 대기 초과 오류가 **0건**이다.
- **SC-004**: RDS 실제 연결 수 최대치가 최대 연결 수의 **80% 이하**다.
- **SC-005**: 대시보드에 처리 중 요청 수 패널이 있고 부하 중 값이 그려진다.
- **SC-006**: 핀닝 확인 결과(건수·지점)가 기록된다.
- **SC-007**: 기존 자동 테스트 전부 통과.

## Assumptions

- 측정 기준은 이전과 같은 k6 스크립트(홈 조회, 2천 VU × 5회, 회원 1명)다. 측정은 사용자가 직접 수행하며, 집 네트워크가 아니라 AWS 안에서 쏘는 것이 결과 신뢰도에 필요하다(이전 측정에서 집 네트워크가 연결을 끊었다).
- DB 커넥션 풀 크기의 구체 값은 플랜 단계에서 RDS 실측값을 보고 정한다. 이 스펙은 "근거 있는 상향" 만 요구한다.
- 새 지표를 만들지 않는다. 처리 중 요청 수·커넥션 풀 지표는 이미 프로메테우스 엔드포인트로 나간다.
- 핀닝이 발견되면 원인 해결(드라이버 교체·JDK 상향)은 이 작업이 아니라 후속 작업이다.
- 웹 서버 연결 수 상한·로드밸런서 제한·RDS 인스턴스 크기 조정은 범위 밖이다.
