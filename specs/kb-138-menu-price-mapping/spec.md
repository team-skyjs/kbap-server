# Feature Specification: 메뉴판 사진 → 메뉴명·가격 추출 퀄리티 실험 (스파이크)

**Feature Branch**: `kb-138-menu-price-mapping`

**Created**: 2026-07-14

**Status**: Draft

**Input**: User description: "kb-138 작업을 실험적으로 해보려고 생각중이야. 다른 작업도 있어서 워크트리로 작업을 해보자. 메뉴판 사진을 gpt llm api로 호출해서 메뉴명과 가격을 맵핑지으려고 하는데 이미지 url을 넘겨도 될까? 이미지 파일을 서버쪽으로 넘기는 것은 희망하지 않거든. 실제 환경이 된다면 클라이언트에서 s3 presigned url로 사진을 업로드하고 링크를 백엔드로 넘겨주는 꼴이 될거야."

## 배경

현재 메뉴 스캔 파이프라인은 클라이언트가 OCR 한 텍스트 라인을 서버로 보내는 구조라, 이미지 인식 품질이 전적으로 클라이언트 OCR 에 달려 있고 가격 정보는 파이프라인 어디에도 없다. 이 작업은 메뉴판 **사진(이미지 URL)** 을 비전 인식 서비스에 직접 넣어 메뉴명과 가격을 한 번에 뽑았을 때의 결과 퀄리티를 측정하는 **실험(스파이크)** 이다. 프로덕션 코드는 건드리지 않으며, 채택 여부는 실험 결과를 바탕으로 후속 이슈에서 결정한다. 실제 환경 전제는 "클라이언트가 사진을 스토리지에 직접 업로드하고 그 링크만 백엔드에 전달"하는 흐름이므로, 실험도 **이미지 파일이 아니라 이미지 URL 을 입력**으로 삼는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이미지 URL 로 메뉴명·가격 구조화 추출 (Priority: P1)

실험 실행자(백엔드 개발자)가 메뉴판 사진의 **URL** 을 실험 하네스에 입력하면, 비전 인식 결과로 "메뉴명–가격" 쌍 목록이 구조화된 형태(JSON)로 출력된다. 이미지 파일 자체는 서버(실험 하네스)를 거치지 않는다.

**Why this priority**: 이 실험의 존재 이유 — URL 입력만으로 추출이 되는지, 결과가 어떤 모양인지 확인하지 못하면 나머지(측정·비교)는 시작조차 못 한다.

**Independent Test**: 메뉴판 사진 1장을 접근 가능한 URL 로 준비해 하네스를 1회 실행하고, 메뉴명·가격 쌍 목록이 구조화 형태로 출력되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 접근 가능한 메뉴판 사진 URL, **When** 하네스를 실행하면, **Then** 메뉴명·가격 쌍 목록이 구조화 JSON 으로 출력된다.
2. **Given** 가격이 표기되지 않은 메뉴가 포함된 사진, **When** 추출을 실행하면, **Then** 해당 메뉴는 가격 없음(null 등)으로 구분되어 출력된다.
3. **Given** 만료되었거나 접근 불가한 이미지 URL, **When** 추출을 실행하면, **Then** 실패 원인이 식별 가능한 형태로 보고된다(조용한 빈 결과 금지).

---

### User Story 2 - 정답 라벨 대비 지표 측정 (Priority: P2)

실험 실행자가 조건이 다양한 메뉴판 사진 샘플셋과 수기 정답 라벨(메뉴명·가격)을 준비하고, 샘플 전체에 대해 추출을 실행해 지표 — 메뉴명 정확도(누락·오검출·오타), 가격 정확도, 응답 지연, 사진 1장당 토큰·비용 — 를 얻는다.

**Why this priority**: 채택/미채택 판단은 인상이 아니라 수치로 해야 한다. P1 이 동작해야 의미가 있으므로 P2.

**Independent Test**: 라벨이 있는 샘플 3장만으로도 지표 4종이 산출되는지 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 정답 라벨이 있는 샘플셋, **When** 전체 샘플에 대해 실험을 실행하면, **Then** 샘플별·전체 지표(메뉴명 정확도, 가격 정확도, 지연, 토큰·비용)가 산출된다.
2. **Given** 산출된 지표, **When** 결과를 검토하면, **Then** 어떤 샘플의 어떤 항목이 틀렸는지(누락/오검출/오타) 추적할 수 있다.

---

### User Story 3 - 현행 방식 대비 비교와 결론 문서 (Priority: P3)

실험 실행자가 현행 방식(클라이언트 OCR + 텍스트 정제) 대비 비교표를 작성하고, 채택/미채택 판단 근거와 후속 이슈 목록(이미지 입력 확장, 가격 스키마·응답 필드, 해석 경계 재설계)을 결론 문서로 남긴다.

**Why this priority**: 실험의 산출물은 코드가 아니라 의사결정 근거다. 다만 P1·P2 의 데이터가 있어야 쓸 수 있으므로 마지막.

**Independent Test**: P2 지표가 주어졌을 때 비교표와 결론 섹션이 채워진 문서가 존재하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** P2 의 지표 산출 결과, **When** 결론을 정리하면, **Then** 현행 방식 대비 비교표와 채택/미채택 근거, 후속 이슈 목록이 담긴 문서가 남는다.

---

### Edge Cases

- 손글씨 메뉴판, 저조도·기울어진 각도·저해상도 사진에서 추출 품질이 어떻게 달라지는가? (샘플셋 조건에 포함해 측정)
- 한 메뉴에 여러 가격(사이즈별 가격)이 붙은 경우 어떻게 표현되는가?
- 영문 병기 메뉴명은 어느 쪽 이름으로 추출되는가?
- 메뉴가 아닌 텍스트(가게 이름, 전화번호, "포장 가능")가 메뉴로 오검출되는가?
- 이미지 URL 이 만료(presigned URL TTL 초과)되었거나 외부에서 접근 불가하면 어떤 실패가 나는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 실험 하네스는 이미지 **URL** 을 입력으로 받아야 하며, 이미지 파일 바이트를 하네스/서버로 업로드받는 방식을 쓰지 않아야 한다(실환경 전제: 클라이언트 → 스토리지 직접 업로드 후 링크 전달).
- **FR-002**: 추출 결과는 "메뉴명–가격" 쌍의 구조화 목록이어야 하며, 가격이 없는 메뉴는 가격 없음으로 구분되어야 한다.
- **FR-003**: 샘플셋은 인쇄/손글씨, 조명·각도·해상도 편차, 영문 병기 등 조건이 섞이도록 구성되어야 한다.
- **FR-004**: 샘플별 수기 정답 라벨(메뉴명·가격)이 존재해야 한다.
- **FR-005**: 실험은 샘플별로 메뉴명 정확도(누락·오검출·오타 구분), 가격 정확도, 응답 지연, 사진 1장당 토큰·비용을 산출해야 한다.
- **FR-006**: 현행 방식(클라이언트 OCR + 텍스트 정제) 대비 비교표가 작성되어야 한다.
- **FR-007**: 채택/미채택 판단 근거와 후속 이슈 목록이 결론 문서로 남아야 한다.
- **FR-008**: 프로덕션 코드(기존 스캔 파이프라인·API·스키마)는 변경하지 않아야 한다 — 실험 하네스(스크립트/테스트) 수준에서만 검증한다.
- **FR-009**: 접근 불가/만료 URL 등 실패 케이스는 원인이 식별 가능한 형태로 보고되어야 한다.

### Key Entities

- **실험 샘플**: 메뉴판 사진 1장 — 접근 가능한 이미지 URL, 촬영 조건 태그(인쇄/손글씨, 조명, 각도, 해상도, 병기 여부).
- **정답 라벨**: 샘플별 수기 작성한 메뉴명·가격 쌍 목록(실측 기준값).
- **추출 결과**: 비전 인식이 반환한 메뉴명·가격 쌍 목록 + 호출 메타(지연, 토큰, 비용).
- **실험 리포트**: 지표 집계, 현행 방식 비교표, 채택/미채택 결론, 후속 이슈 목록.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 조건이 섞인 샘플 10장 이상에 대해 정답 라벨과 추출 결과가 모두 존재한다.
- **SC-002**: 지표 4종(메뉴명 정확도, 가격 정확도, 응답 지연, 장당 토큰·비용)이 샘플별·전체 집계로 산출된다.
- **SC-003**: 실험 실행자는 이미지 파일을 서버로 옮기지 않고 URL 만으로 전체 실험을 재현할 수 있다.
- **SC-004**: 결론 문서만 읽고도 제3자가 채택/미채택 판단 근거와 후속 이슈 범위를 이해할 수 있다(비교표·근거·후속 목록 포함).
- **SC-005**: 프로덕션 코드 diff 가 0 이다(실험 하네스·문서·샘플 자산만 추가).

## Assumptions

- 실험용 이미지 URL 은 호출 시점에 외부(비전 인식 서비스)에서 접근 가능하다. 실환경에서는 클라이언트가 스토리지에 직접 업로드한 뒤 발급받는 서명 URL(presigned URL)이 이 역할을 하며, **서명 URL 의 유효기간은 인식 호출이 끝날 때까지 유지된다**고 가정한다.
- 샘플셋 규모는 10~20장 수준이면 판단에 충분하다(조건 커버리지가 장수보다 중요).
- 실험 비용(비전 인식 호출)은 소액이며 별도 예산 승인이 필요 없다.
- 현행 방식과의 비교 기준 데이터는 동일 샘플에 대한 기존 파이프라인 결과 또는 그에 준하는 수기 평가로 갈음할 수 있다.
- 채택 시의 프로덕션 반영(이미지 입력 확장, 가격 스키마, 응답 필드, 해석 경계 재설계)은 전부 후속 이슈 범위이며 이 실험의 범위가 아니다.
