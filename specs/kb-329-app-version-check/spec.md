# Feature Specification: 앱 버전 정보 조회 (최소 지원·최신 버전과 스토어 링크)

**Feature Branch**: `kb-329-app-version-check`

**Created**: 2026-08-13

**Status**: Draft

**Input**: User description: "지원되는 앱의 최소 버전과 최신 버전을 보여주고, 과거 버전의 앱 사용자는 강제 업데이트가 가능하도록 스토어 링크로 연결하는 GET API. 현재는 앱스토어만 배포되어 있어 aos 링크는 null 로 내려준다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 구버전 사용자 강제 업데이트 유도 (Priority: P1)

앱 사용자가 앱을 실행하면, 앱은 서버에서 최소 지원 버전·최신 버전·스토어 링크를 조회한다. 사용자의 앱 버전이 최소 지원 버전보다 낮으면 앱은 강제 업데이트 안내를 띄우고, 제공된 스토어 링크로 사용자를 이동시킨다.

**Why this priority**: 이 기능의 존재 이유다. 하위 호환이 깨지는 릴리스를 배포할 때 구버전 앱이 오동작하는 것을 막을 유일한 수단이며, 이 정보가 없으면 클라이언트는 강제 업데이트를 판단할 수 없다.

**Independent Test**: 버전 정보 조회 요청 하나를 보내 최소 지원 버전·최신 버전·스토어 링크가 응답에 포함되는지 확인하는 것으로 완결 검증된다.

**Acceptance Scenarios**:

1. **Given** 서버에 최소 지원 버전 1.0.0·최신 버전 1.0.1 이 설정되어 있을 때, **When** 버전 정보를 조회하면, **Then** 응답에 minSupportedVersion=1.0.0, latestVersion=1.0.1, storeUrls(ios 링크 포함)가 담긴다.
2. **Given** iOS 앱스토어에만 배포된 현재 상태에서, **When** 버전 정보를 조회하면, **Then** storeUrls.ios 는 유효한 링크이고 storeUrls.aos 는 null 이다.

---

### User Story 2 - 로그인 전 접근 보장 (Priority: P2)

앱 최초 실행 시점(로그인·회원가입 전)에도 버전 확인이 이루어져야 하므로, 인증 정보가 전혀 없는 사용자도 버전 정보를 조회할 수 있다.

**Why this priority**: 강제 업데이트 판단은 로그인보다 먼저 일어난다. 인증이 요구되면 신규 설치·로그아웃 상태의 구버전 사용자가 업데이트 안내를 받지 못해 P1 의 가치가 무너진다.

**Independent Test**: 인증 토큰 없이 조회 요청을 보내 정상 응답(거부 아님)을 받는 것으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 인증 토큰이 없는 상태에서, **When** 버전 정보를 조회하면, **Then** 인증 오류 없이 버전 정보가 정상 반환된다.

---

### User Story 3 - 관리자의 버전 정보 갱신 (Priority: P3)

새 버전을 릴리스하거나 최소 지원 버전을 올릴 때, 관리자는 코드 배포 없이 최소 지원 버전·최신 버전·스토어 링크를 직접 변경할 수 있다. 변경 즉시 모든 사용자 조회에 반영된다.

**Why this priority**: 강제 업데이트는 릴리스 운영 도구다. 값 변경에 배포가 필요하면 긴급 차단(치명 버그 버전 차단)이 배포 파이프라인에 묶인다. 다만 초기 값만으로도 P1·P2 는 성립하므로 P3 다.

**Independent Test**: 관리자 권한으로 값을 변경한 뒤 공개 조회에서 변경된 값이 반환되는 것으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 관리자 권한이 있는 상태에서, **When** 최신 버전을 1.0.2 로 변경하면, **Then** 이후 공개 조회 응답의 latestVersion 이 1.0.2 다.
2. **Given** 관리자 권한이 없는 일반 사용자가, **When** 버전 정보 변경을 시도하면, **Then** 요청이 거부된다.

---

### Edge Cases

- 미배포 플랫폼(현재 aos)의 스토어 링크는 값이 없다는 사실을 명시적으로 표현한다(null) — 빈 문자열이나 항목 누락으로 얼버무리지 않는다.
- 버전 비교·강제 업데이트 판단은 클라이언트 책임이다. 서버는 판단 재료(버전 값·링크)만 제공하며 클라이언트의 현재 버전을 받지 않는다.
- 버전 정보가 존재하지 않는 상태로 서비스되는 상황은 허용하지 않는다 — 초기 값은 배포 시점에 반드시 함께 준비된다.
- 관리자가 아닌 사용자의 변경 시도는 거부된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 단일 조회 요청으로 최소 지원 버전(minSupportedVersion)과 최신 버전(latestVersion)을 함께 제공해야 한다.
- **FR-002**: 시스템은 플랫폼별 스토어 링크(storeUrls)를 같은 응답에 포함해야 하며, iOS 는 앱스토어 링크를, 미배포 플랫폼(aos)은 null 을 반환해야 한다.
- **FR-003**: 버전 정보 조회는 인증 없이 접근 가능해야 한다.
- **FR-004**: 응답은 서비스의 다른 API 와 동일한 공통 응답 형식을 따라야 한다.
- **FR-005**: 버전 값과 스토어 링크는 코드 배포 없이 관리자가 갱신할 수 있어야 하며, 변경은 즉시 조회에 반영되어야 한다.
- **FR-006**: 버전 정보 갱신은 관리자 권한이 있는 사용자만 수행할 수 있어야 한다.

### Key Entities

- **버전 정보**: 최소 지원 버전, 최신 버전, 플랫폼별 스토어 링크(ios·aos)로 구성된 단일 정보. 사용자·요청 조건과 무관하게 모든 호출자에게 동일한 값이 제공되며, 관리자만 변경할 수 있다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 클라이언트는 요청 1회로 강제 업데이트 판단에 필요한 모든 정보(두 버전 값 + 스토어 링크)를 얻는다.
- **SC-002**: 인증 없이 보낸 조회 요청의 100% 가 인증 오류 없이 성공한다.
- **SC-003**: 하위 호환이 깨지는 릴리스 시, 관리자는 코드 배포 없이 값 변경만으로 구버전 사용자 전원에게 강제 업데이트를 유도할 수 있다.
- **SC-004**: 안드로이드 스토어 배포 시 관리자가 aos 링크 값 하나를 채우는 것만으로 aos 링크 제공이 시작된다.

## Assumptions

- 버전 문자열은 semantic versioning 형식(`major.minor.patch`, 예: 1.0.1)이며, 비교 로직은 클라이언트가 소유한다.
- 버전 값·스토어 링크의 변경 빈도는 낮다(릴리스 시점에만 변경). 관리자 변경은 API 로 수행하며, 관리자 콘솔 화면(UI)은 이 기능의 범위 밖이다(필요 시 별도 작업).
- 플랫폼 구분은 iOS·AOS 두 가지뿐이며, 클라이언트가 자기 플랫폼의 링크를 골라 쓴다(플랫폼별 별도 요청 없음).
- 강제 업데이트 여부의 판단·차단 UI 는 클라이언트 책임이고, 서버는 데이터 제공만 담당한다.
