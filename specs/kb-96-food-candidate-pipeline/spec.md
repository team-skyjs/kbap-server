# Feature Specification: 음식 candidate 스테이징 파이프라인 골격 + 승격 배치

**Feature Branch**: `kb-96-food-candidate-pipeline`

**Created**: 2026-07-07

**Status**: Draft

**Input**: User description: "KB-96 — 음식 candidate 스테이징 파이프라인 골격 + 승격 배치 (미완성 음식 → 완성 시 food 적재). 근거: ADR-0012·ADR-0013"

## 배경 (Context)

음식 콘텐츠는 서로 다른 배치·시점에서 **부분적으로** 완성된다 — 기피성분 스코어링이 성분 매핑을, 설명 배치가 9개 언어 설명 번역을 채운다. 두 조각은 독립적으로, 순서 없이 완성된다. `food` 테이블은 API 음식 상세 서빙 테이블인데, 미완성 음식(성분만·설명만)이 여기 섞이면 사용자에게 불완전한 데이터가 노출된다. 특히 성분 매핑이 없는 음식은 회피 성분 정보가 공백이 되어 안전 직결로 치명적이다.

이 기능은 **미완성 음식을 별도 candidate 스테이징에 쌓고, 완성된 것만 승격 배치가 `food` 로 적재하는 파이프라인 골격**이다. 성분·설명을 실제로 채우는 enrichment 잡(KB-54·KB-94)은 이 골격 위의 후속이며, 여기서는 스테이징·완성 판정·승격을 픽스처로 end-to-end 완결한다. 설계 근거·기술 결정은 [ADR-0012](../../docs/adr/0012-food-candidate-staging-promotion-pipeline.md)(스테이징→승격)·[ADR-0013](../../docs/adr/0013-batch-bulk-persistence-io-exposed.md)(대량 영속·IO 전략).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 완성된 음식만 사용자에게 서빙 (Priority: P1)

미완성 음식은 candidate 스테이징에 격리되고, 성분·설명이 모두 갖춰진 음식만 `food` 로 승격되어 사용자에게 노출된다. 사용자는 음식 상세에서 항상 완전한 정보(설명 + 회피 성분)를 본다.

**Why this priority**: 이 파이프라인의 존재 이유다. 서빙 테이블을 "완성본만"으로 유지해 불완전 데이터(특히 회피 성분 공백)의 사용자 노출을 구조적으로 차단한다. 이 슬라이스만으로도 "스테이징 → 완성 판정 → food 적재"가 픽스처로 end-to-end 완결된다(MVP).

**Independent Test**: candidate 를 만들고 성분·설명을 픽스처로 채운 뒤 승격을 실행하면, 완성 candidate 만 `food` 에 적재되고 미완성은 적재되지 않는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 성분 매핑·ko 설명·9개 언어 번역이 모두 갖춰진 candidate 가 있을 때, **When** 승격 배치를 실행하면, **Then** 그 음식이 `food`(+회피 성분)로 적재되고 candidate 는 승격됨으로 표시된다.
2. **Given** 성분 매핑만 있고 설명 번역이 없는 candidate 가 있을 때, **When** 승격 배치를 실행하면, **Then** 그 candidate 는 `food` 로 적재되지 않고 다음 실행 대상으로 남는다.
3. **Given** 승격이 끝난 뒤, **When** 사용자가 음식 상세를 조회하면, **Then** 설명과 회피 성분이 모두 채워진 완전한 음식만 조회된다.

---

### User Story 2 - enrichment 잡의 안전한 부분 채움 (Priority: P2)

서로 다른 enrichment(성분 매핑·설명 번역)가 candidate 의 서로 다른 부분을 독립적으로 채운다. 두 잡이 같은 음식을 동시에 갱신해도 어느 쪽 데이터도 유실되지 않는다.

**Why this priority**: 이 골격은 스코어링(KB-54)·설명(KB-94) 잡이 위에서 **독립·병렬**로 돌 수 있게 하는 토대다. 잡 스케줄이 겹쳐도(대량 처리로 실행이 길어져 오버런) 안전해야 파이프라인이 신뢰된다.

**Independent Test**: 한 candidate 에 대해 성분 채움과 설명 채움을 (동시 포함) 임의 순서로 적용해도, 최종 candidate 가 두 조각을 모두 보존하는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 성분 매핑이 채워진 candidate 가 있을 때, **When** 설명 번역을 채우면, **Then** 성분 매핑은 그대로 보존되고 설명이 추가된다(반대 순서도 동일).
2. **Given** 두 enrichment 가 같은 candidate 를 동시에 갱신할 때, **When** 둘 다 완료되면, **Then** 성분·설명 어느 쪽도 상대에게 덮여 유실되지 않는다.

---

### User Story 3 - 멱등 재실행·부분 실패 복원·대량 효율 (Priority: P3)

승격 배치는 이미 승격된 음식을 다시 적재하지 않고, 일부 음식의 적재가 실패해도 나머지는 적재되며, 대량이어도 효율적으로 처리한다.

**Why this priority**: 대량 음식을 여러 번에 나눠 안전하게 흘려보내고, 일시적 실패에서 회복하며, 처리량이 커져도 감당하기 위한 운영 특성이다. P1/P2 성립 뒤의 견고성·성능이다.

**Independent Test**: 일부는 완성, 일부는 미완성, 일부는 이미 승격된 혼합 candidate 집합에서 승격을 두 번 실행해, 중복 적재가 없고 완성분만 흘러가는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 이미 승격된 candidate 가 있을 때, **When** 승격을 다시 실행하면, **Then** 해당 음식의 `food` row 가 중복 생성되지 않는다.
2. **Given** 한 음식의 적재가 실패했을 때, **When** 승격이 끝나면, **Then** 나머지 완성 음식은 적재되고 실패 음식은 다음 실행 대상으로 남는다.
3. **Given** 대량의 완성 candidate 가 있을 때, **When** 승격을 실행하면, **Then** 처리에 드는 데이터베이스 왕복이 음식 수에 선형 비례하지 않고 청크 단위로 억제된다.

---

### Edge Cases

- 완성 조건 미달 candidate(성분·설명 중 하나라도 결여, 또는 번역 언어 불완전)는 승격되지 않고 다음 실행까지 스테이징에 남는다.
- 승격할 완성 candidate 가 하나도 없으면 승격 배치는 아무 것도 적재하지 않고 정상 종료한다.
- 승격 대상 음식과 같은 이름(korean_name)이 `food` 에 이미 있으면(시드 또는 이전 승격), 중복 생성하지 않고 갱신(업서트)한다.
- enrichment 잡과 승격 배치가 시간상 겹쳐 실행돼도 데이터가 유실·손상되지 않는다.
- 한 candidate 의 설명 번역이 9개 언어 중 일부만 있으면 "번역 미완비"로 간주해 완성으로 보지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 미완성 음식을 서빙 테이블과 분리된 candidate 스테이징에 보관해야 한다(성분 매핑·설명 번역이 부분적으로만 채워질 수 있음).
- **FR-002**: enrichment 는 candidate 의 자기 담당 부분만 갱신해야 하며, 동시에 실행되는 다른 enrichment 가 채운 부분을 덮어써서는 안 된다.
- **FR-003**: 시스템은 candidate 의 완성 여부(성분 매핑 있음 · ko 설명 있음 · 9개 대상 언어 번역 완비 · 아직 미승격)를 판정할 수 있어야 한다.
- **FR-004**: 승격은 완성 조건을 만족한 candidate 만 `food`(및 회피 성분 매핑)로 적재해야 하며, 미완성은 적재하지 않아야 한다.
- **FR-005**: 승격 적재는 멱등이어야 한다 — 재실행해도 이미 승격된 음식의 중복 생성 없이, 자연 키(음식명) 기준 업서트와 승격 표시로 안전해야 한다.
- **FR-006**: 승격은 음식 1건 단위로 원자적이어야 한다 — 일부 음식의 적재가 실패해도 나머지 음식의 적재는 진행되고, 실패·미처리 음식은 다음 실행 대상으로 남아야 한다.
- **FR-007**: 대량 처리 시 데이터베이스 왕복 횟수는 음식 수에 선형 비례하지 않고 청크 단위로 억제되어야 한다(단건 반복 처리 금지).
- **FR-008**: 시스템은 candidate 를 생성하는 경로(음식명과 ko 설명 확보)를 제공해, enrichment 와 승격의 입력을 마련해야 한다.
- **FR-009**: 파이프라인 골격은 성분·설명을 픽스처로 채운 상태에서 candidate 생성 → 완성 판정 → 승격 → `food` 적재를 end-to-end 로 검증해야 한다(테스트 우선).
- **FR-010**: 승격 시 스테이징과 서빙 도메인 사이는 스냅샷 값(음식명·설명·성분 코드+확률)으로만 옮기고, 두 도메인 객체를 직접 공유하지 않아야 한다.

### Key Entities *(include if feature involves data)*

- **candidate(제작 중 음식)**: 완성 전 음식의 스테이징 레코드. 음식명(ko)·ko 설명·언어별 설명 번역·성분 매핑 스냅샷(성분 코드 + 최종 포함확률)·승격 여부/링크를 갖는다. 완성 여부가 승격 대상 판정 기준이다.
- **승격 실행(Promotion Run)**: 완성된 candidate 집합을 `food` 로 옮기는 1회 실행. 대상 수·성공·실패 집계를 산출하고, 승격된 candidate 를 표시한다.
- **food(완성 음식)**: API 서빙 대상. 승격을 통해서만 채워지며 완성본만 존재한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 승격 후 `food` 에 적재된 음식은 성분 매핑·ko 설명·9개 언어 번역을 **모두** 갖는다(불완전 적재 0건).
- **SC-002**: 완성 조건 미달 candidate 는 `food` 에 적재되지 않는다(미완성 음식의 서빙 노출 0건).
- **SC-003**: 승격을 재실행해도 이미 승격된 음식의 `food` row 가 중복 생성되지 않는다(중복 0건).
- **SC-004**: 두 enrichment 가 같은 candidate 를 동시에 갱신해도 성분·설명 어느 쪽도 유실되지 않는다(유실 0건).
- **SC-005**: 승격 중 일부 음식이 실패해도 성공 음식은 적재되고 실패 음식은 다음 실행에서 다시 대상이 된다(성공분 유실 0건).
- **SC-006**: 대량(N건) 승격 시 데이터베이스 왕복 횟수가 N 에 선형 비례하지 않고 청크 단위 상수로 유지된다.
- **SC-007**: candidate 생성 → (픽스처) enrichment → 승격 → `food` 적재 전 과정이 자동화 테스트로 검증된다.

## Assumptions

- **ko 설명은 입력 전제**: candidate 는 생성 시 음식명과 ko 설명을 갖는다. 설명 번역(KB-94)은 이 ko 설명을 입력으로 9개 언어를 채우므로, ko 설명은 candidate 생성 단계에서 확보된다.
- **enrichment 는 후속**: 성분 매핑을 채우는 스코어링(KB-54)·설명 번역을 채우는 설명 배치(KB-94)는 이 골격 위의 후속 티켓이다. 본 기능은 그 부분을 **픽스처로 대체해** 골격을 end-to-end 검증한다(범위 밖).
- **서빙 회피 성분 저장소 존재**: `food` 의 회피 성분 매핑 저장소는 이미 존재하며, 승격이 이를 채운다(새 서빙 스키마를 만들지 않는다).
- **완성 조건**: 성분 매핑 있음 · ko 설명 있음 · 9개 대상 언어 번역 완비 · 미승격을 모두 만족할 때 완성으로 본다.
- **스케줄 비의존**: enrichment·승격의 실행 시각(스케줄)은 운영 결정이며, 파이프라인 정합성은 실행 타이밍에 의존하지 않는다(동시 실행에도 안전).
- **서빙 읽기 불변**: `food` 음식 상세 조회(서빙) 경로는 기존 방식을 유지하며 이 기능의 범위가 아니다.
- **범위 밖**: 스코어링 알고리즘·집계, 설명 생성·번역 로직, 위험도 판정(KB-9)은 이 기능의 범위가 아니다.

## 설계 근거 (범위 밖 상세 — plan 에서 구체화)
