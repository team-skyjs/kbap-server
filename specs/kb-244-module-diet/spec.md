# Feature Specification: 스프링 모듈 구조 다이어트 — api·batch·common 3모듈로 통합

**Feature Branch**: `kb-244-module-diet`

**Created**: 2026-07-28

**Status**: Draft

**Input**: User description: "스프링 모듈 api, batch, common 3개로 다이어트하는 업무. 현재 도메인 별 모듈이 쪼개져있는데 무의미함. 따라서 api 모듈에 디렉토리 구분으로 합침. 단 batch와 공통으로 사용하는 코드를 common 모듈로 공통화 하는 작업을 진행하여 구조를 더 단순히 바꿈" (Jira KB-244)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 3모듈 구조에서 동일 기능 유지 (Priority: P1)

개발자가 모듈 통합 후에도 기존과 완전히 동일하게 빌드·실행·테스트할 수 있다. web 앱과 배치 앱은 그대로 기동되고, 기존 전체 테스트가 그대로 통과한다. 이 작업은 순수 구조 변경이며 기능·API·DB 스키마는 어떤 것도 달라지지 않는다.

**Why this priority**: 구조 변경의 전제 조건 — 동작 동일성이 깨지면 다이어트가 아니라 장애다. 이것만 완성돼도(모듈이 3개로 줄고 모든 것이 그대로 동작) 이 작업의 핵심 가치가 전달된다.

**Independent Test**: 전체 빌드(`build`)와 두 앱 기동만으로 독립 검증 가능 — 기존 테스트 슈트가 회귀 안전망이다.

**Acceptance Scenarios**:

1. **Given** 통합이 완료된 저장소, **When** 전체 빌드·테스트를 실행하면, **Then** 기존과 동일하게 전부 통과한다.
2. **Given** 통합이 완료된 저장소, **When** web 앱과 배치 앱을 각각 기동하면, **Then** 두 앱 모두 기존과 동일하게 정상 기동한다.
3. **Given** 통합이 완료된 저장소, **When** 모듈 목록을 확인하면, **Then** 실행 모듈 구성이 api·batch·common 3개로 정리되어 있다.

---

### User Story 2 - 공유 코드의 common 단일화 (Priority: P2)

개발자가 web 과 배치 양쪽에서 쓰는 코드(엔티티·리포지토리·도메인 서비스·LLM 어댑터 등)를 찾을 때 항상 common 한 곳에서 찾는다. api 전용 코드(컨트롤러·인증·조합 계층)는 api 에, 배치 전용 코드는 batch 에 있으며, 의존 방향은 api→common, batch→common 단방향이다.

**Why this priority**: 3모듈 구조의 존재 이유 — 공유 코드가 한 곳에 모여야 "batch 가 어떤 코드를 쓰는지"가 모듈 경계로 즉시 드러난다. P1(동작 동일성) 위에서만 의미가 있다.

**Independent Test**: api 와 batch 가 서로를 의존하지 않고 common 만 의존하는지 빌드 의존 그래프로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 통합이 완료된 저장소, **When** 모듈 의존을 확인하면, **Then** api→common, batch→common 만 존재하고 api↔batch 상호 의존은 없다.
2. **Given** web 과 배치가 함께 쓰는 코드, **When** 그 코드의 위치를 찾으면, **Then** common 모듈에만 존재한다(api·batch 에 사본 없음).
3. **Given** api 전용 코드(컨트롤러 등), **When** 그 코드의 위치를 찾으면, **Then** api 모듈 안에 디렉터리(패키지) 구분으로 존재한다.

---

### User Story 3 - 경계 규칙·문서의 새 구조 반영 (Priority: P3)

개발자가 새 구조에서도 아키텍처 경계(도메인 로직 위치·계층 의존 방향)를 자동 검증으로 보장받고, 프로젝트 문서만 읽어도 새 모듈 구조를 정확히 이해한다.

**Why this priority**: 모듈이 줄면 Gradle 이 막아주던 경계가 사라진다 — 그 몫을 자동 검증이 넘겨받아야 규율이 유지된다. 동작(P1)·구조(P2)가 완성된 뒤의 마무리다.

**Independent Test**: 경계 검증 테스트 실행과 문서 대조만으로 독립 검증 가능.

**Acceptance Scenarios**:

1. **Given** 통합이 완료된 저장소, **When** 경계 검증 테스트를 실행하면, **Then** 패키지 기준의 새 경계 규칙으로 통과한다.
2. **Given** 통합이 완료된 저장소, **When** 프로젝트 안내 문서(CLAUDE.md·아키텍처 문서)를 읽으면, **Then** 3모듈 구조·의존 방향·코드 배치 기준이 실제와 일치하게 설명되어 있다.

---

### Edge Cases

- 기존에 Gradle 모듈 경계가 컴파일 차단하던 도메인 간 순환 의존이, 통합 후 패키지 경계에서는 어떻게 막히는가? → 경계 검증 테스트(패키지 기준)가 넘겨받는다.
- 배치 앱이 현재 컴포넌트 스캔을 좁혀(도메인 서비스 미탑재) 부팅하는 구조는 통합 후에도 유지되는가? → 유지 — batch 는 common 의 필요한 빈만 조립한다.
- api 전용 인프라(인증·Redis)까지 common 으로 끌려가면 batch 가 불필요한 의존을 얻는다 → 공유 여부 기준으로만 common 에 배치한다.
- 빈 placeholder 모듈(review)은 어디로 가는가? → 대응 코드가 없으므로 제거한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 저장소의 실행 모듈 구성은 api(web 실행 앱)·batch(배치 실행 앱)·common(공유 코드) 3개로 정리되어야 한다(공통 빌드 설정 유틸리티는 예외).
- **FR-002**: 기존 도메인·인프라 코드는 삭제 없이 3모듈 중 한 곳으로 전부 이동하고, 도메인 구분은 모듈 대신 디렉터리(패키지) 구분으로 유지되어야 한다.
- **FR-003**: web 과 배치가 함께 사용하는 코드는 common 에만 존재해야 하며, 어떤 코드도 두 모듈에 중복으로 존재해서는 안 된다.
- **FR-004**: 모듈 의존 방향은 api→common, batch→common 단방향이어야 하고 api 와 batch 는 서로 의존하지 않아야 한다.
- **FR-005**: 통합 후 두 실행 앱은 기존과 동일하게 정상 기동하고, 기존 전체 테스트는 수정 전과 동일한 의미로 전부 통과해야 한다(기능·API·DB 스키마 변경 없음).
- **FR-006**: 기존에 모듈 경계가 강제하던 아키텍처 규칙(도메인 간 의존 방향·계층 격리)은 패키지 기준의 자동 경계 검증으로 대체되어야 한다.
- **FR-007**: DB 마이그레이션 소유권(web 앱이 스키마 owner, 배치는 마이그레이션 미실행) 구조는 통합 후에도 유지되어야 한다.
- **FR-008**: 프로젝트 안내 문서(CLAUDE.md·아키텍처 문서)의 모듈 구조 설명은 새 구조와 일치하게 갱신되어야 한다.

### Key Entities

데이터 모델 변경 없음 — 이 작업은 코드 배치(모듈 구조)만 바꾸며 엔티티·스키마는 건드리지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 실행 모듈 수가 12개 안팎에서 3개로 줄어든다.
- **SC-002**: 기존 전체 테스트가 100% 통과한다(테스트 의미 변경 없이).
- **SC-003**: 두 실행 앱이 통합 전과 동일하게 기동된다.
- **SC-004**: 새 코드를 추가할 때 "어느 모듈에 두는가" 판단이 공유 여부 하나로 끝난다 — 모듈별 빌드 설정 파일 수가 3개로 줄어 빌드 설정 관리 지점이 최소화된다.

## Assumptions

- 패키지 이름(`com.kbap.*` 계층 구조)은 유지하고 코드의 소속 모듈만 바꾼다 — 패키지 대개편은 이 작업 범위 밖이다.
- common 배치 기준은 "web 과 배치가 함께 쓰는가" 하나다: 공통 커널·엔티티·리포지토리·도메인 서비스·LLM 어댑터는 common, 컨트롤러·인증·Redis·조합 계층 등 api 전용 코드는 api, 배치 잡 코드는 batch.
- 대응 코드가 없는 빈 placeholder 모듈(review)은 제거한다.
- 공통 빌드 설정(buildSrc 컨벤션 플러그인)은 모듈 수에 맞춰 축소·정리하되 존치 여부 자체는 구현 단계에서 결정한다.
- 배치 앱의 부팅 방식(컴포넌트 스캔 좁힘·필요 빈 직접 조립)은 현행 유지가 기본이며, 변경이 필요하면 구현 계획 단계에서 결정한다.
