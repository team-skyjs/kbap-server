# Feature Specification: 홈 인기 음식을 조회수 순으로

**Feature Branch**: `kb-714-popular-by-views`

**Created**: 2026-10-04

**Status**: Draft

**Jira**: [KB-714](https://simhani1.atlassian.net/browse/KB-714)

**Input**: User description: "홈 인기 음식을 무작위(ORDER BY RAND()) 대신 음식 상세 조회 로그(food_view_log) 기반 조회수 순으로 바꾼다. 최근 30일 조회수 내림차순, 조회수가 없는 READY 음식은 뒤에서 레일 크기(10)를 채우고, 동률은 id 순서로 고정한다. 리포지토리 네이티브 쿼리 findRandom 을 findPopular(since, size) 로 교체하고 서비스는 호출 한 줄만 바꾼다. 기존 홈 통합 테스트는 무수정 통과해야 하며, 리포지토리 테스트(순서·동률·기간 밖 제외·보충)를 먼저 Red 로 작성한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 실제로 많이 본 음식이 인기 음식에 먼저 나온다 (Priority: P1)

홈 화면을 여는 사용자(회원·비회원)는 인기 음식 레일에서 최근 사람들이 실제로 많이 조회한 음식을 조회수가 많은 순서로 본다. 지금은 공개 음식 중 무작위로 뽑혀 "인기"라는 이름이 사실과 다르고, 열 때마다 목록이 바뀐다.

**Why this priority**: 기능의 본체다. 인기 레일이 사용자 행동을 반영해야 이름이 참이 되고, 같은 조건에서 같은 결과가 나와야 화면이 안정된다.

**Independent Test**: 음식 A·B·C 에 최근 30일 내 상세 조회 기록을 각각 3·2·1건 남기고 인기 음식을 조회하면 A, B, C 순으로 나온다. 다시 조회해도 순서가 같다.

**Acceptance Scenarios**:

1. **Given** 공개 음식 A(조회 3건)·B(2건)·C(1건)의 최근 30일 조회 기록이 있을 때, **When** 인기 음식을 조회하면, **Then** A, B, C 순서로 나온다.
2. **Given** 조회수가 같은 공개 음식 두 개가 있을 때, **When** 인기 음식을 조회하면, **Then** 나중에 등록된 음식(id 가 큰 쪽)이 먼저 나오고, 반복 조회해도 순서가 바뀌지 않는다.
3. **Given** 어떤 음식의 조회 기록이 전부 30일보다 오래됐을 때, **When** 인기 음식을 조회하면, **Then** 그 기록은 조회수에 세지 않는다(기간 내 기록이 없으면 그 음식은 나오지 않는다).
4. **Given** 회원 조회와 비회원 조회 기록이 섞여 있을 때, **When** 인기 음식을 조회하면, **Then** 둘 다 조회수에 포함된다.

---

### User Story 2 - 조회 기록이 적으면 있는 만큼만 보여준다 (Priority: P2)

조회 기록이 있는 음식이 레일 크기(10)보다 적으면, 인기 레일은 조회 기록이 있는 음식만 그 수만큼 보여준다. 조회되지 않은 음식으로 자리를 채우지 않는다 — "인기"가 아닌 음식을 인기로 내보이지 않는다.

**Why this priority**: 로그가 적은 초기에 레일이 짧아지는 것을 받아들이는 결정(2026-10-04 사용자 지시)이다. 정렬 규칙(US1)의 경계 조건이다.

**Independent Test**: 공개 음식 12개 중 2개에만 조회 기록을 남기고 인기 음식을 조회하면 그 2개만 조회수 순으로 나온다.

**Acceptance Scenarios**:

1. **Given** 조회 기록 있는 공개 음식이 2개, 없는 공개 음식이 10개일 때, **When** 크기 10으로 인기 음식을 조회하면, **Then** 조회 기록 있는 2개만 조회수 순으로 나온다.
2. **Given** 최근 30일 조회 기록이 하나도 없을 때, **When** 인기 음식을 조회하면, **Then** 빈 목록이 나온다(오류 아님).

---

### Edge Cases

- 조회 기록은 있지만 공개 상태(READY)가 아니거나 삭제된 음식은 조회수가 아무리 많아도 나오지 않는다.
- 공개 음식이 하나도 없으면 빈 목록을 돌려준다(오류 아님).
- 조회수 있는 음식이 레일 크기보다 많으면 상위 레일 크기만큼만 나온다.
- 30일 경계: 기준 시각(조회 시점 − 30일) 이후의 기록만 센다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 인기 음식은 공개(READY)·미삭제 음식만 대상으로 한다.
- **FR-002**: 인기 음식은 조회 시점 기준 최근 30일의 음식 상세 조회 기록 수(조회수) 내림차순으로 정렬한다. 회원·비회원 기록을 모두 센다.
- **FR-003**: 조회수가 같은 음식은 id 내림차순(나중 등록 우선)으로 순서를 고정한다 — 같은 데이터에서는 항상 같은 결과가 나온다.
- **FR-004**: 최근 30일 조회 기록이 없는 음식은 인기 음식에 넣지 않는다. 조회 기록 있는 음식이 요청 크기보다 적으면 있는 만큼만 돌려준다(보충 없음).
- **FR-005**: 결과는 요청 크기(홈 레일 10) 이하이며 음식이 중복되지 않는다.
- **FR-006**: 홈 응답 구조(필드·레일 최대 크기·리뷰 평점 포함)는 바뀌지 않는다 — 기존 홈 통합 테스트의 검증 본문은 수정 없이 통과한다(테스트 시드에 조회 기록을 더하는 것만 허용).
- **FR-007**: 무작위 선정은 사용처가 사라지면 제거한다.
- **FR-008**: 정렬·동률·기간 밖 제외·무조회 음식 제외 규칙은 구현보다 먼저 실패하는 테스트로 고정한다(Test-First).

### Key Entities

- **음식(Food)**: 인기 레일의 대상. 공개 상태(READY)·삭제 여부가 노출 조건이다.
- **음식 조회 기록(food_view_log)**: 음식 상세를 볼 때마다 쌓이는 기록(음식, 회원 또는 비회원, 발생 시각). 최근 30일 건수가 곧 조회수다. 이 기능은 읽기만 하며 기록 방식은 바꾸지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 데이터에서 인기 음식을 연속 조회하면 100% 동일한 목록·순서가 나온다.
- **SC-002**: 최근 30일 조회수가 더 많은 공개 음식이 더 적은 음식보다 항상 앞에 나온다.
- **SC-003**: 인기 레일에 나오는 모든 음식은 최근 30일 안에 한 번 이상 조회된 음식이다(최대 10개).
- **SC-004**: 기존 홈 검증(레일 크기·공개 음식만·중복 없음·리뷰 평점 포함)이 변경 없이 전부 통과한다.
- **SC-005**: 로컬에서 음식 상세를 몇 번 조회한 뒤 홈을 열면 그 음식이 인기 레일 앞쪽으로 올라온다.

## Assumptions

- 동률 순서는 Jira KB-714 원문("동률은 id 역순")을 따랐다.
- Jira 원문의 "조회수 없는 음식으로 레일 채움"은 2026-10-04 사용자 지시로 철회했다 — 로그가 부족해 레일 크기만큼 못 채워도 된다. 그 결과 조회 기록이 없는 환경에서는 인기 레일이 비며, 클라이언트는 빈 배열을 이미 처리한다고 본다.
- 집계 기간 30일과 레일 크기 10은 고정값이다(로그가 아직 적어 7일 대신 30일). 설정화하지 않는다.
- 조회수는 기록 건수 그대로다 — 같은 사람의 반복 조회 중복 제거는 하지 않는다.
- 조회수는 조회 시점에 바로 집계한다. 캐시·사전 집계 테이블은 범위 밖이다(기간+음식 인덱스가 이미 있다).
- 조회수 값 자체는 응답에 싣지 않는다. API 계약·DB 스키마 변경이 없다.
- 리뷰 많은 음식 등 홈의 다른 레일은 범위 밖이다.
