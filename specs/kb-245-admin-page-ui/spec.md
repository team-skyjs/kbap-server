## Clarifications

- Q: 관리자 자격 증명 저장 방식(운영 설정 vs 계정 저장소)? → A: 관리자 계정 테이블을 만들어 자체 로그인으로 구현한다(운영 설정 방식 폐기). 로그인 성공 시 JWT 를 쿠키로 받아 관리자 권한으로 호출한다.
- Q: 브라우저(관리자 화면)의 서버 기능 호출 방식? → A: 타임리프 폼 POST(서버 렌더링) — 뷰 컨트롤러가 서비스 빈을 직접 호출하고 쿠키 JWT 는 페이지 접근 인증에 사용. 기존 REST·인증 필터 무변경.
- Q: 최초 관리자 계정 프로비저닝 방식? → A: 운영자가 DB 에 직접 INSERT(1회성, bcrypt 해시). 계정 등록/비밀번호 변경 화면은 이번 범위 밖.
- Q: 로그인 실패 잠금·rate limit? → A: 하지 않는다 — 간단한 최소 구현으로 동작하는 것에 집중(사용자 결정).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자 페이지 베이스와 내비게이션 (Priority: P1)

관리자는 관리자 페이지에 로그인해 사이드바의 카테고리(음식 데이터, 회원 관리)를 통해 각 관리 화면으로 이동한다. 관리자 권한이 없는 사용자는 어떤 관리 화면에도 접근할 수 없다.

**Why this priority**: 모든 관리 화면이 이 레이아웃·인증 위에 올라간다. 이것 없이는 다른 스토리를 배포할 수 없다.

**Independent Test**: 관리자 자격 증명으로 로그인 → 사이드바에 카테고리가 보이고 클릭으로 화면 전환 확인. 비관리자/미로그인 접근 시 차단 확인. 이것만으로 "인증된 관리자 전용 공간"이라는 가치가 성립한다.

**Acceptance Scenarios**:

1. **Given** 관리자 자격 증명이 있는 사용자, **When** 로그인에 성공하면, **Then** 사이드바(음식 데이터·회원 관리 카테고리)가 있는 관리자 페이지가 표시된다
2. **Given** 로그인한 관리자, **When** 사이드바 카테고리를 클릭하면, **Then** 해당 관리 화면으로 이동하고 현재 위치가 사이드바에 표시된다
3. **Given** 로그인하지 않은 사용자, **When** 관리자 페이지 주소로 직접 접근하면, **Then** 로그인 화면으로 안내되고 관리 화면 내용은 노출되지 않는다
4. **Given** 잘못된 자격 증명, **When** 로그인을 시도하면, **Then** 실패 사유가 표시되고 접근이 거부된다
5. **Given** 로그인한 관리자, **When** 화면 간 이동을 반복하면, **Then** 재인증 없이 로그인 상태가 유지된다

---

### User Story 2 - 음식 데이터 적재 현황 대시보드 (Priority: P1)

관리자는 전체 음식 데이터의 적재 진행 상황 — 콘텐츠 준비 단계별(미완료, 이미지 대기, 검수 대기, 준비 완료) 분포와 준비 완료(READY) 비율 — 을 DB를 직접 조회하지 않고 한 화면에서 확인한다.

**Why this priority**: KB-245의 핵심 동기. 현재 적재 현황 확인 수단이 DB 직접 조회뿐이라 운영 부담이 가장 큰 지점이다.

**Independent Test**: 상태가 서로 다른 음식 데이터를 준비한 뒤 대시보드 진입 → 단계별 건수·비율이 실제 데이터와 일치하는지 확인.

**Acceptance Scenarios**:

1. **Given** 여러 준비 단계의 음식 데이터가 존재할 때, **When** 관리자가 음식 데이터 화면에 진입하면, **Then** 전체 건수와 단계별(미완료·이미지 대기·검수 대기·준비 완료) 건수가 표시된다
2. **Given** 음식 데이터가 존재할 때, **When** 현황을 조회하면, **Then** 전체 대비 준비 완료(READY) 비율이 시각적으로(비율 표시) 확인된다
3. **Given** 음식 데이터가 0건일 때, **When** 현황을 조회하면, **Then** 오류 없이 "데이터 없음" 상태가 표시된다

---

### User Story 3 - 화면에서 관리자 작업 실행 (Priority: P2)

관리자는 기존에 API 직접 호출(Swagger·curl)로만 가능했던 두 작업 — 음식 시드 등록, 음식 이미지 배치 제출 — 을 화면의 버튼/폼으로 실행하고 결과를 즉시 확인한다.

**Why this priority**: 현황 가시화(US2) 다음으로 운영 편의를 높이는 작업. US2 없이도 동작하지만 대시보드와 같은 화면 맥락에 있을 때 가치가 크다.

**Independent Test**: 화면에서 음식 시드 등록 폼 제출 → 등록 결과(성공 건수) 표시 확인. 이미지 배치 제출 버튼 클릭 → 제출 결과 표시 확인.

**Acceptance Scenarios**:

1. **Given** 음식 데이터 화면, **When** 관리자가 시드 등록 입력을 제출하면, **Then** 등록 처리 결과(성공/실패와 건수)가 화면에 표시된다
2. **Given** 이미지 생성 대상 음식이 존재할 때, **When** 관리자가 이미지 배치 제출을 실행하면, **Then** 제출 결과(대상 건수 등)가 화면에 표시된다
3. **Given** 이미지 생성 대상이 0건일 때, **When** 이미지 배치 제출을 실행하면, **Then** 오류가 아닌 "대상 없음" 결과가 표시된다
4. **Given** 잘못된 형식의 시드 입력, **When** 제출하면, **Then** 실패 사유가 표시되고 데이터는 변경되지 않는다

---

### User Story 4 - 회원 목록·상세 조회 (Priority: P2)

관리자는 회원 관리 화면에서 회원 목록을 페이지 단위로 조회하고, 특정 회원을 선택해 프로필과 상태(활성·정지 등)를 상세 확인한다.

**Why this priority**: KB-246 범위. 음식 데이터 운영(P1·US3)보다 빈도는 낮지만 회원 현황 확인의 DB 직접 조회를 제거한다.

**Independent Test**: 회원 데이터가 있는 상태에서 목록 화면 진입 → 페이징 동작 확인, 회원 클릭 → 상세 화면에서 프로필·상태 확인.

**Acceptance Scenarios**:

1. **Given** 회원이 존재할 때, **When** 회원 관리 화면에 진입하면, **Then** 회원 목록이 페이지 단위로 표시되고 페이지 이동이 가능하다
2. **Given** 회원 목록, **When** 특정 회원을 선택하면, **Then** 해당 회원의 프로필 정보와 상태가 상세 화면에 표시된다
3. **Given** 회원이 0명일 때, **When** 목록을 조회하면, **Then** 오류 없이 빈 목록 상태가 표시된다
4. **Given** 존재하지 않는 회원 식별자, **When** 상세 화면에 직접 접근하면, **Then** 오류 안내가 표시되고 다른 화면으로 이동할 수 있다

---

### Edge Cases

- 마지막 페이지를 넘는 페이지 번호로 회원 목록에 접근하면 빈 목록 또는 마지막 페이지가 표시된다(오류 미노출).
- 로그인 세션이 만료된 상태에서 화면을 조작하면 로그인 화면으로 안내된다.
- 관리자 권한이 없는 로그인 사용자가 관리 화면 주소로 직접 접근하면 접근 거부가 표시된다.
- 시드 등록·배치 제출 처리 중 화면 이탈/재시도 시 중복 실행에 대한 결과가 명확히 표시된다.
- 아이패드 미니 크기(가로 약 768px)에서 사이드바·본문 레이아웃이 깨지지 않고 조작 가능하다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 관리자 전용 페이지를 제공하며, 관리자 인증을 통과한 사용자만 접근을 허용해야 한다.
- **FR-002**: 시스템은 관리자 계정 저장소(테이블)에 보관된 자격 증명으로 로그인·로그아웃을 제공하고, 로그인 상태를 화면 이동 간 유지해야 한다. 최초 계정은 운영자가 저장소에 직접 등록하며(1회성), 계정 등록·비밀번호 변경 화면은 범위 밖이다.
- **FR-003**: 관리자 페이지는 사이드바 카테고리(음식 데이터, 회원 관리)를 상시 노출하고, 카테고리 선택으로 화면을 전환하며 현재 위치를 표시해야 한다.
- **FR-004**: 음식 데이터 화면은 전체 음식 건수와 콘텐츠 준비 단계별(미완료·이미지 대기·검수 대기·준비 완료) 건수를 표시해야 한다.
- **FR-005**: 음식 데이터 화면은 전체 대비 준비 완료(READY) 비율을 시각적으로 표시해야 한다.
- **FR-006**: 관리자는 음식 데이터 화면에서 음식 시드 등록을 실행하고 처리 결과(성공/실패·건수)를 확인할 수 있어야 한다.
- **FR-007**: 관리자는 음식 데이터 화면에서 음식 이미지 배치 제출을 실행하고 처리 결과를 확인할 수 있어야 한다.
- **FR-008**: 회원 관리 화면은 회원 목록을 페이지 단위로 제공하고 페이지 이동을 지원해야 한다.
- **FR-009**: 회원 상세 화면은 선택한 회원의 프로필 정보와 계정 상태를 표시해야 한다.
- **FR-010**: 관리자 권한이 없는 요청(미로그인·비관리자)은 모든 관리 화면·관리 기능에서 차단되어야 한다.
- **FR-011**: 모든 관리 화면은 데스크톱 브라우저 기준으로 동작하며, 화면 폭 768px(아이패드 미니 세로 기준)까지 레이아웃이 유지되어야 한다. 그 미만 폭(모바일)의 반응형 대응은 범위 밖이다.
- **FR-012**: 화면 디자인은 일관된 스타일(색상·타이포그래피·간격 체계)을 갖춘 깔끔한 관리자 도구 스타일로 제작한다.

### Key Entities

- **음식(Food)**: 적재 파이프라인의 대상. 콘텐츠 준비 단계(미완료 → 이미지 대기 → 검수 대기 → 준비 완료)를 가지며 대시보드 집계의 기준이 된다.
- **회원(Member)**: 서비스 가입자. 프로필 정보와 계정 상태(활성·정지)를 가지며 목록·상세 조회의 대상이다.
- **관리자 계정**: 관리자 페이지에 로그인할 수 있는 자격 증명의 주체. 서비스 회원과 구분되는 **별도 저장소(관리자 계정 테이블)** 에 보관되며, 로그인 식별자와 비밀번호(해시)를 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자가 DB 조회 도구 없이 관리자 페이지 접속 후 10초 이내에 음식 데이터 적재 현황(단계별 건수·READY 비율)을 확인할 수 있다.
- **SC-002**: 음식 시드 등록·이미지 배치 제출을 API 도구(Swagger·curl) 없이 화면 조작만으로 완료할 수 있다.
- **SC-003**: 관리자가 특정 회원의 프로필·상태를 화면 조작 3회 이내(로그인 제외)로 확인할 수 있다.
- **SC-004**: 비관리자 접근 시도는 100% 차단되며 관리 데이터가 노출되지 않는다.
- **SC-005**: 화면 폭 768px 환경에서 모든 화면의 핵심 기능(내비게이션·현황 확인·작업 실행·목록/상세 조회)이 정상 동작한다.

## Assumptions

- 관리자는 소수(현재 1~2명)이며, 관리자 계정은 서비스 회원과 분리된 관리자 계정 테이블에 저장한다(소셜 로그인 미사용, 자체 로그인 — 사용자 결정 2026-07-29). 로그인 상태는 JWT 를 쿠키로 보관해 유지한다.
- 관리 기능의 권한 검증은 기존 관리자 권한 검증 체계(관리자 역할 기반)를 재사용한다.
- 회원 목록·상세는 서비스에 노출되는 활성 데이터 기준으로 조회한다(삭제 처리된 데이터는 시스템 전역 규칙에 따라 조회 대상에서 제외됨).
- 화면은 사내 관리자만 사용하는 내부 도구로, 대규모 동시 접속·모바일 지원·다국어는 범위 밖이다.
- 음식 시드 등록·이미지 배치 제출은 기존에 제공되던 관리 기능을 화면으로 노출하는 것이며, 처리 규칙 자체는 변경하지 않는다.
- 기존 관리 기능의 API 직접 호출(Swagger·curl)은 화면 도입 후에도 **그대로 유지**한다(2026-07-29 확정 — plan·contracts 와 일치).
