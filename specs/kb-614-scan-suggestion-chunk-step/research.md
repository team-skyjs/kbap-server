# Research: KB-614

미해결 NEEDS CLARIFICATION 없음. 설계 선택의 근거를 남긴다.

## R1. 발송 잡 리더

- **Decision**: 직접 만든 `ItemStreamReader<Long>` — `member_id` 커서 + 한 페이지 버퍼. `FoodVectorOutboxItemReader` 와 같은 구조.
- **Rationale**: 배치 안에 같은 모양의 선례가 있다. keyset 방식이라 실행 중 대상이 바뀌어도 누락·중복이 없다.
- **Alternatives considered**: `JpaPagingItemReader`·`RepositoryItemReader`(offset — 행이 바뀌면 페이지가 밀린다), `JpaCursorItemReader`(DB 커서를 스텝 내내 열어 둔다), `JdbcPagingItemReader`(keyset + 재시작 상태 저장을 기본 제공하지만 SQL 직접 작성·소프트 삭제 조건 수동·선례와 다른 패턴. 재시작을 쓰지 않으므로 이득이 없다 — R4).

## R2. 슬롯 중복 방지 위치

- **Decision (2026-09-22 개정)**: 리더 쿼리의 `NOT EXISTS` 로 거른다. 프로세서·`existsBy…` 파생 쿼리는 삭제했다. 사용자 지적 — 발송 대상의 정의가 곧 "이번 슬롯에 아직 안 받은 회원" 이므로 조회 조건이 맞다. 회원당 1회이던 존재 여부 쿼리(청크당 100회)가 사라지고 클래스가 하나 준다. 대가: 걸러진 수(`filterCount`)가 실행 기록에 남지 않는다. 아래는 처음 결정의 기록이다.
- **처음 결정**: 프로세서가 회원 1명당 파생 쿼리 `existsBy…` 1회.
- **Rationale**: `null` 반환이 곧 필터라 `filterCount` 가 공짜로 남는다. `idx_notification_member_id (member_id, id)` 가 회원별로 좁힌다. 청크당 100회의 인덱스 조회.
- **Alternatives considered**: 리더 쿼리에 `NOT EXISTS` 합치기(세 역할 구분이 사라지고 걸러진 수가 안 남는다), 라이터에서 `IN` 1회(거르기가 라이터로 샌다), 슬롯 시작을 스텝 시작 시 1회 계산(상태·리스너가 는다).

## R3. 발송 잡 트랜잭션 매니저

- **Decision**: 실제 `PlatformTransactionManager`. 사용자 결정.
- **달라지는 점**: 지금은 `ResourcelessTransactionManager` 라 `prepare`·`record` 가 각자 커밋된다. 바꾸면 둘의 `@Transactional`(REQUIRED)이 청크 트랜잭션에 합류해 읽기·거르기·준비·Expo 호출·결과 기록이 한 트랜잭션이 된다.
- **감수하는 위험**: (1) Expo 호출(재시도 대기 최대 약 7초, 읽기 타임아웃 10초) 동안 DB 연결 1개 점유 — 배치는 단일 스레드라 동시 1개. (2) Expo 발송 뒤 같은 청크가 롤백되면 푸시는 나갔는데 기록이 사라져 같은 슬롯 재실행에서 그 청크 회원이 다시 받는다. 발송기는 예외를 던지지 않으므로 경로는 `record` 의 DB 오류 정도. (3) 롤백 시 메트릭 카운터는 되돌아가지 않는다.
- **영수증 잡도 같다(2026-09-21 추가 결정)**: 처음엔 영수증 잡만 `ResourcelessTransactionManager` + 3단 패턴으로 설계했으나, 사용자 지시로 실제 트랜잭션 매니저로 통일했다. `Resourceless` 에서도 메타 테이블 기록 자체는 된다(`JobRepository` 가 자기 트랜잭션으로 쓴다) — 다만 청크의 업무 데이터 커밋과 메타 기록이 다른 트랜잭션이라 원자적이지 않다. 통일 후에는 한 청크의 영수증 확정·재전송 이력·스텝 실행 기록이 함께 커밋된다. 추가로 감수하는 위험: 외부 호출이 청크당 두 번(영수증 조회·재전송)이라 연결 점유가 더 길고, 재전송 발송 뒤 청크가 롤백되면 확정·재전송 기록이 사라져 다음 회차에 같은 영수증으로 다시 재전송될 수 있다(그 기기에 중복 1건).
- **Alternatives considered**: 발송 잡도 `Resourceless` 유지 — 위험 (1)(2)가 없으나 사용자 결정과 다르다. 설정 한 줄로 되돌릴 수 있다.

## R4. 실패한 발송 잡의 재시작(restart)을 쓰지 않는 이유

- Spring Batch 는 재시작을 **제공**하지만 자동으로 하지 않는다. 확인한 사실: 잡에 `RunIdIncrementer` 가 있으면 `JobOperator.start` 는 다음 인스턴스로 실행한다(Spring Batch 6.0.4 `SimpleJobOperator.start` 소스). `BatchJobLauncher` 가 이 경로만 쓰므로 재실행은 항상 새 인스턴스·처음부터다. `restart` 를 부르는 경로는 없다.
- 재시작 방식으로 가려면 런처·트리거에 재시작 경로, 리더 상태 저장, "점심 실행이 저녁에 재시작되는 경우" 의 처리가 필요하고, 그래도 수동 중복 트리거는 못 막는다.
- **Decision**: 재시작을 도입하지 않고 프로세서 필터로 재실행을 멱등하게 만든다. 클래스 한 줄 + 파생 쿼리 하나.

## R5. 발송기 순차화

- **Decision**: 스레드 풀·요청 간격 슬롯 제거. 사용자 결정.
- **Rationale**: 호출부가 100 단위로 끊어 부르므로 발송기 안 병렬은 의미가 거의 없다. 순차 발송이 초당 600건을 넘으려면 요청 왕복이 167ms 미만이어야 하고, 넘어도 429 → 기존 백오프가 받는다.
- **부수 효과**: 자원을 소유하지 않으므로 `AutoCloseable`·`destroyMethod` 제거.

## R6. 영수증 확인 시점과 재전송 시간표

Expo 문서(2026-09-21 확인): 영수증은 발송 15분 뒤 조회 권고, 24시간 보관, 조회당 최대 1000 id. `ok` 는 FCM·APNs 수신이지 기기 수신이 아니다. 재시도 권고는 `MessageRateExceeded` 하나뿐이고 나머지 오류 코드는 재시도 금지.

| | 광고성(10분 주기) | 활동(15분 주기) |
|---|---|---|
| 최초 발송 | 11:00 | 14:00 |
| 확인 1 → 재전송 1 | 11:20 | 14:15 |
| 확인 2 → 재전송 2 | 11:40 | 14:30 |
| 확인 3 → 최종 판정 | 12:00 | 14:45 |

- 10분 주기에서는 15분 대기 때문에 한 알림의 실제 간격이 20분이다. 최악에도 12:00 에 끝나 13:00 마감까지 1시간 여유 — 회차 지연·영수증 지연을 흡수한다.
- **재전송 상한 2회**(사용자 결정). 시간으로만 자르면 `MessageRateExceeded` 기기에 최대 5번 보내게 돼 상황이 나빠진다.
- 재전송 대기 15분이 `MessageRateExceeded` 의 백오프 역할을 한다. 별도 백오프 로직이 없다.

## R7. 재전송 단위 — 회원이 아니라 발송 이력

- **Decision**: 같은 알림함 행에 새 `NotificationDispatch` 를 붙여 그 기기에만 보낸다.
- **Rationale**: `PushHandler.send` 는 회원 단위라 다시 부르면 이미 성공한 다른 기기에도 나가고 알림함 행이 새로 생긴다. 발송 이력은 이미 알림 1 : 이력 N 구조다(`findByNotificationId` 가 `List`). 따라오는 이점 — 시도 횟수 = 이력 개수(컬럼 불필요), 알림함 중복 없음, 알림함 행이 활성인 동안 발송 잡의 슬롯 필터가 그 회원을 걸러 재전송과 재실행이 겹치지 않는다, 알림함 행 `createdAt` 이 2시간 창의 기준이 된다.
- **재전송 직전 자격 재확인**: `PushTargetResolver.resolve` 를 그대로 쓴다. 광고성 동의 철회 뒤 재전송은 법적 문제라 생략할 수 없다. 토큰도 판정기가 돌려준 현재 값을 쓴다(그 사이 재등록됐을 수 있다).
- **재전송 ttl**: 메시지 ttl 은 어디에도 저장돼 있지 않다. 광고성은 "재전송 마감까지 남은 시간" 으로 계산해 창 밖에서 뜨지 않게 하고, 활동 알림은 원 발송처럼 두지 않는다. 유형별 ttl 설정을 새로 만들지 않는다.

## R8. 유형 구분 — 컬럼 vs 조인

- **Decision**: `notification_dispatch.notification_type` 컬럼. 사용자 결정.
- **Alternatives considered**: 알림함 테이블 조인(PK 조회라 비용 없음, 마이그레이션 없음) — 제안했으나 기각됨.
- **배포 안전**: api 가 2대 블루/그린이라 구 코드가 새 스키마 위에서 컬럼 없이 INSERT 한다. `NOT NULL` 이면 그 구간의 도움돼요 발송이 실패하므로 NULL 허용으로 넣는다. NULL 행은 두 잡 모두 집지 않고 24시간 뒤 미확인 종결된다(수 분치). `NOT NULL` 전환은 다음 릴리스.
- **인덱스**: 새로 만들지 않는다. 조회는 `(dispatch_status, created_at)` 범위를 타고, `SENT` + 최근 24시간 집합은 작다.
- **배포 순서**: 배치의 새 코드는 컬럼에 쓴다. 스키마 owner 가 api 이므로 api 가 먼저 배포돼야 한다.

## R9. 24시간 지난 SENT

- **Decision (2026-09-22 개정)**: 영수증 잡의 조회 조건(`created_at >= now - 24h`)은 그대로 두고, 자정 종결 잡을 추가한다 — 접수 후 이틀 지난 `SENT` 를 벌크 UPDATE 한 번으로 `FAILED`(`ReceiptUnconfirmed`) 처리. 사용자 결정. `SENT` 가 영구히 두 뜻을 갖는 문제가 사라지고 성공률 집계가 `DELIVERED`/`FAILED` 둘로 닫힌다. 이틀 기준은 영수증 보관 24시간 + 마지막 영수증 잡 회차까지의 여유다. 태스크릿 한 개라 두 영수증 잡의 대칭은 깨지지 않는다. 알림함 행은 지우지 않는다(실제로는 전달됐을 수 있다). 벌크 UPDATE 는 엔티티의 `markFailed` 와 `@UpdateTimestamp` 를 거치지 않는다 — 기존 `markAllReadByMemberId` 와 같은 선례이고, 종결 시각은 배치 메타 테이블의 실행 기록으로 남는다.
- **처음 결정**: 상태를 바꾸는 정리 작업 없음. 조회 조건 `created_at >= now - 24h` 로 제외.
- **Rationale**: 두 잡이 완전히 대칭이 된다. 실제로는 전달됐을 수 있는 건을 실패로 적지 않는다. 인덱스 범위 스캔이라 미확인 행이 쌓여도 비용이 일정하다.
- **대가**: `SENT` 가 두 뜻을 가진다 — spec 의 상태 정의 표에 못 박았다. 성공률 집계는 24시간 지난 `SENT` 를 미확인으로 센다.

## R10. 영수증 포트를 따로 둔 이유

`PushClient` 가 `fun interface` 라(테스트·`ExpoPushHandlerTest` 가 람다로 구현) 메서드를 더하면 깨진다. api 는 영수증을 조회하지 않으므로 포트를 나누면 api 의 페이크·조립을 건드리지 않아도 된다.

## R11. 영수증 조회 실패 처리

- **Decision**: 어댑터는 재시도하지 않고 예외를 올린다. 라이터가 그 청크만 건너뛴다.
- **Rationale**: 10~15분 뒤 다음 회차가 같은 행을 다시 집는다 — 잡 주기가 곧 재시도다. 발송기의 `RetryTemplate` 을 복제하지 않는다.
