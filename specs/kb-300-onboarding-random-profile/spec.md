# Feature Specification: 온보딩 시 닉네임·프로필 사진 랜덤 지정

**Feature Branch**: `kb-300-onboarding-random-profile`

**Created**: 2026-08-10

**Status**: Draft

**Input**: User description: "300. 그런데 기존 회원 등록 api에도 정상 동작할 수 있도록 해야 해. 즉 아직 1.0.0 앱에서 사용하는 api는 닉네임, 프로필 사진을 직접 입력받고 있어. 현재 작업하는 api는 그렇지 않게 되는 것이고. 따라서 기존 api 동작에 영향이 없도록 개발해야 하는데 아직 강제 업데이트나 버저닝 헤더를 받지 않도록 개발한 상황이라 이부분 고민임." (Jira KB-300, 에픽 KB-193 프로필)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 신규 앱 사용자의 무입력 온보딩 (Priority: P1)

신규 가입자가 온보딩 화면에서 닉네임을 짓거나 프로필 사진을 고르지 않아도 온보딩을 마칠 수 있다. 온보딩을 마치는 순간 서버가 닉네임을 자동 생성하고 프로필 사진을 준비된 후보 중에서 골라 붙여 준다. 사용자는 온보딩 직후 프로필 화면에서 자신의 닉네임과 사진이 이미 채워져 있는 것을 본다.

**Why this priority**: 이 기능의 본질이다. 온보딩 이탈의 주요 원인인 "이름 짓기·사진 고르기" 단계를 제거하는 것이 목표이며, 이것만 구현해도 신규 사용자 가치가 완결된다.

**Independent Test**: 닉네임·프로필 사진을 전혀 전달하지 않는 온보딩 요청을 신규 회원으로 보낸 뒤, 프로필 조회에서 닉네임이 정해진 형식을 만족하고 프로필 사진이 후보 목록 안의 값인지로 독립 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 소셜 로그인은 마쳤지만 온보딩을 하지 않은 신규 회원, **When** 닉네임·프로필 사진 없이 회피 성분·국가·맵기 선호만 담아 온보딩을 완료하면, **Then** 온보딩이 성공하고 닉네임은 생성 형식을 만족하는 값으로, 프로필 사진은 후보 중 하나로 채워진다
2. **Given** 온보딩을 방금 마친 회원, **When** 자신의 프로필을 조회하면, **Then** 자동 지정된 닉네임과 프로필 사진이 반환되며 프로필 사진은 다른 프로필 이미지와 동일한 형태(전체 URL)로 내려온다
3. **Given** 자동 지정된 닉네임·사진이 마음에 들지 않는 회원, **When** 프로필 수정으로 닉네임·사진을 바꾸면, **Then** 변경한 값이 저장되고 이후 조회에 반영된다
4. **Given** 이미 온보딩을 마친 회원, **When** 다시 온보딩을 시도하면, **Then** 기존과 동일하게 "이미 온보딩을 완료함" 오류가 반환되고 닉네임·사진이 다시 뽑히지 않는다

---

### User Story 2 - 구버전 앱(1.0.0) 사용자의 온보딩 무중단 (Priority: P1)

이미 배포된 1.0.0 앱 사용자는 앱을 업데이트하지 않아도 기존과 똑같이 닉네임과 프로필 사진을 직접 입력해 온보딩을 마칠 수 있다. 서버 배포 후에도 구버전 앱의 온보딩 화면·요청·응답·검증 오류가 한 가지도 달라지지 않는다.

**Why this priority**: 강제 업데이트 장치도 앱 버전 식별 수단도 없는 상태이므로, 구버전 온보딩이 깨지면 신규 가입 자체가 막히는 서비스 장애가 된다. P1 두 개가 동시에 성립해야만 이 기능을 배포할 수 있다.

**Independent Test**: 1.0.0 앱이 보내는 것과 동일한 온보딩 요청(닉네임·프로필 사진 포함)을 보내 성공하는지, 그리고 잘못된 값(빈 닉네임·전체 URL 형태의 사진 경로 등)에 대해 변경 전과 동일한 오류 코드가 나오는지로 독립 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 1.0.0 앱을 쓰는 신규 회원, **When** 닉네임·프로필 사진을 포함한 기존 형식으로 온보딩을 완료하면, **Then** 입력한 닉네임·사진 그대로 저장되고 랜덤 값으로 덮어써지지 않는다
2. **Given** 1.0.0 앱 사용자, **When** 온보딩에 유효하지 않은 값(빈 닉네임, 절대 URL 형태의 프로필 이미지 경로, 잘못된 국가 코드 등)을 보내면, **Then** 변경 전과 동일한 오류 코드·상태로 거부된다
3. **Given** 1.0.0 앱 사용자, **When** 온보딩 이후 프로필 조회·프로필 수정을 하면, **Then** 변경 전과 완전히 동일한 응답 형식과 동작을 얻는다
4. **Given** 서버에 신·구 온보딩 경로가 함께 열려 있는 상태, **When** 어느 한쪽으로 온보딩한 회원을 조회하면, **Then** 온보딩 경로와 무관하게 동일한 프로필 응답 형식이 반환된다

---

### User Story 3 - 자동 지정 값의 품질 (Priority: P2)

자동으로 붙는 닉네임과 프로필 사진이 서비스에 어울리고, 사용자마다 충분히 다양해서 "모두가 같은 이름"처럼 보이지 않는다. 자동 지정된 사진은 항상 실제로 표시되는 이미지다(깨진 이미지가 나오지 않는다).

**Why this priority**: 기능은 P1 만으로 동작하지만, 후보가 빈약하거나 이미지가 깨지면 자동 지정이 오히려 나쁜 첫인상을 만든다.

**Independent Test**: 다수의 신규 회원을 연속 온보딩시켜 지정된 닉네임·사진의 분포가 한 값에 쏠리지 않는지, 그리고 지정된 모든 사진 후보가 실제 조회 가능한 이미지인지로 독립 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 닉네임 생성 규칙과 이미지 후보 목록, **When** 신규 회원 다수를 연속으로 온보딩시키면, **Then** 닉네임은 거의 매번 다른 값이 나오고 이미지는 특정 하나에 고정되지 않고 후보 전반에 분포한다
2. **Given** 자동 지정된 프로필 사진, **When** 프로필 조회 응답의 사진 주소로 이미지를 요청하면, **Then** 실제 이미지가 조회된다
3. **Given** 자동 지정된 닉네임, **When** 그 회원이 커뮤니티(리뷰·댓글 등)에 노출되면, **Then** 기존 닉네임 표기 규칙(길이 제한 등)을 위반하지 않는다

---

### Edge Cases

- 신규 온보딩 경로로 닉네임·프로필 사진을 굳이 함께 보내면? → 무시하고 서버가 뽑은 값을 쓴다(요청 항목으로 취급하지 않는다).
- 자동으로 뽑힌 닉네임이 이미 다른 회원이 쓰고 있으면? → 닉네임은 고유값이 아니므로 그대로 허용한다(현행 정책 유지).
- 이미지 후보 목록이 비어 있거나 잘못된 값을 담고 있으면? 생성 닉네임이 저장 제약을 위반하면? → 온보딩 요청 시점이 아니라 배포 전에 드러나야 한다(유효성은 자동 검증 대상).
- 구버전 앱이 신규 온보딩 경로를 알 수 없는 상태에서 서버만 먼저 배포되면? → 구버전 경로가 그대로 살아 있어 아무 영향이 없다.
- 온보딩을 마친 회원이 프로필 수정으로 닉네임을 비우려 하면? → 기존 프로필 수정 정책을 그대로 따른다(이 기능의 범위 밖).
- 온보딩 요청이 **순차로** 두 번 들어오면? → 두 번째는 "이미 온보딩을 완료함"으로 거부된다.
- 온보딩 요청이 **동시에** 두 번 들어오면? → 두 요청이 모두 성공할 수 있다(락·버전 검사 없음). 같은 회원이 두 값 중 하나를 갖게 될 뿐 데이터가 깨지지 않고, 이는 기존 v1 온보딩과 **동일한 수준**이다. 비치명 경합으로 감수한다(CLAUDE.md "동시성 방어 수위", 2026-07-30).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 닉네임 생성 규칙과 프로필 이미지 후보 목록을 코드 수준의 상수로 보유해야 한다(운영 중 데이터 변경 없이 배포로만 바뀐다).
- **FR-002**: 신규 온보딩 경로는 닉네임과 프로필 사진을 요청 항목으로 받지 않아야 한다. 회피 성분 코드·국가 코드·맵기 선호는 기존과 동일하게 받는다.
- **FR-003**: 시스템은 신규 온보딩 완료 시 닉네임을 생성 규칙으로 만들고 프로필 이미지를 후보에서 무작위 선택해 회원 프로필에 지정해야 한다.
- **FR-004**: 자동 지정은 온보딩 완료 1회에만 일어나야 하며, 이후 로그인·프로필 조회·순차 재요청으로 값이 다시 바뀌지 않아야 한다. (동시 요청은 예외 — Edge Cases 참조.)
- **FR-005**: 자동 지정된 닉네임·프로필 사진은 기존 프로필 수정 기능으로 사용자가 변경할 수 있어야 한다.
- **FR-006**: 기존(구버전) 온보딩 경로는 요청 형식·검증 규칙·성공 응답·오류 코드가 하나도 변경되지 않은 채 계속 동작해야 한다.
- **FR-007**: 구버전 온보딩 경로로 전달된 닉네임·프로필 사진은 그대로 저장되어야 하며, 자동 지정 값으로 덮어써지지 않아야 한다.
- **FR-008**: 신·구 온보딩 경로는 앱 버전 식별 수단(강제 업데이트·버전 헤더 등) 없이도 공존해야 한다 — 클라이언트가 호출하는 주소만으로 구분된다.
- **FR-009**: 두 경로 중 어느 쪽으로 온보딩했든 이후의 프로필 조회·프로필 수정·커뮤니티 노출 동작은 동일해야 한다.
- **FR-010**: 자동 지정된 프로필 사진은 기존에 사용자가 직접 지정한 사진과 동일한 형태로 저장·응답되어야 한다(저장 형태·응답 형태가 갈라지지 않는다).
- **FR-011**: 생성된 닉네임은 기존 닉네임 제약(공백 아님, 저장 가능한 최대 길이 이내)을 모두 만족해야 하며, 이미지 후보는 기존 프로필 이미지 경로 제약을 모두 만족해야 한다. 위반은 자동 검증으로 배포 전에 드러나야 한다.
- **FR-012**: 자동 지정된 값은 반복 온보딩 시 하나의 값에 고정되지 않아야 한다 — 닉네임은 사실상 매번 다른 값이, 이미지는 후보 전반에 걸친 분포가 나와야 한다.
- **FR-013**: 닉네임은 고정 문구 후보에서 고르지 않고 **영숫자 6자 무작위 코드**(예: `K7M2XB`)로 생성한다. 시각적으로 혼동되는 문자(`0`·`O`·`1`·`I`)는 쓰지 않는다.
- **FR-014**: 프로필 이미지 후보는 **이미 스토리지에 준비된 아바타 6종**(`images/webp/default_profile/avatar-{amber,navy,olive,orange,plum,teal}.png`)을 가리킨다. 이 작업에서 이미지 파일을 새로 제작·업로드하지 않는다.

### Key Entities

- **회원 프로필**: 회원의 닉네임·프로필 이미지 경로·회피 성분 코드 목록·국가 코드·맵기 선호를 담는다. 이 기능은 이 중 닉네임·프로필 이미지 경로의 **채워지는 방법**만 바꾸며 저장 구조는 바꾸지 않는다.
- **닉네임 생성 규칙**: 온보딩 시 닉네임을 만드는 고정 규칙(영문 접두 + 무작위 코드). 배포 산출물의 일부이며 운영 데이터가 아니다.
- **프로필 이미지 후보 목록**: 온보딩 시 무작위 선택에 쓰이는 고정 이미지 경로 집합. 각 경로는 실제 조회 가능한 이미지를 가리켜야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 신규 앱 사용자는 닉네임 입력·사진 선택 단계 없이 온보딩을 마칠 수 있고, 온보딩 완료 회원 100% 가 비어 있지 않은 닉네임과 프로필 사진을 갖는다.
- **SC-002**: 서버 배포 전후로 구버전 앱의 온보딩 성공률과 오류 응답이 변하지 않는다(구버전 경로 회귀 0건).
- **SC-003**: 구버전 앱 사용자는 앱 업데이트 없이 계속 가입·온보딩할 수 있다 — 강제 업데이트 안내가 필요 없다.
- **SC-004**: 신규 회원 100명을 연속 온보딩했을 때 닉네임이 거의 전부 서로 다르고(중복 5% 미만), 프로필 사진은 한 후보 점유율이 30% 미만이다.
- **SC-005**: 자동 지정된 프로필 사진 요청 시 이미지 조회 실패율 0%.
- **SC-006**: 온보딩 완료 후 사용자가 닉네임·사진을 원하는 값으로 변경하는 데 실패하는 경우가 없다.

## Assumptions

- 앱 버전 식별 수단(강제 업데이트·버전 헤더)이 없으므로, 신·구 동작 분기는 **요청의 닉네임·사진 필드 유무(null 여부)로** 구분한다 — 구버전 앱은 항상 두 필드를 보내고, 신버전 앱은 보내지 않는다(2026-08-10 개정 — 초안의 v2 경로 분리안 철회).
- 온보딩 엔드포인트는 v1 하나만 유지한다. 필드 완화가 하위 호환이므로 별도 정리 작업이 없다.
- 닉네임은 회원 간 **고유값이 아니다**(현행 정책). 생성 규칙상 충돌 확률이 극히 낮으므로 중복 확인·재생성 로직을 두지 않는다.
- 자동 생성 닉네임이 짧은 영문 코드 형태라는 점은 **의도된 신호**다 — "아직 직접 정하지 않았다"가 드러나 사용자가 프로필 수정으로 자기 닉네임을 짓도록 유도한다. 커뮤니티 작성자란에서 다소 무기질적으로 보이는 점은 짧은 표기를 얻는 대가로 감수한다.
- 프로필 이미지 후보는 이미 프로필 이미지에 쓰이는 것과 **동일한 저장 규칙**(스토리지 경로, 절대 URL 금지)을 따른다. 응답 시 공개 베이스 URL 이 붙는 방식도 동일하다.
- 온보딩에서 받는 나머지 항목(회피 성분 코드·국가 코드·맵기 선호)의 필수 여부·검증 규칙은 이번 작업에서 바꾸지 않는다.
- 프로필 수정(닉네임·사진 변경) 기능은 이미 존재하므로 이번 작업 범위 밖이다.
- 무작위 선택은 회원별 독립 추첨이며, 후보 소진·순환 보장 같은 제약은 두지 않는다.
- 프로필 이미지 후보 자산 6종은 스토리지에 이미 존재하며 경로가 확정됐다(FR-014). 후보 추가·교체는 상수 변경만으로 이뤄진다.
- 기존 기본 이미지(`images/default/profile/profile-default-512.png`)는 랜덤 후보에 포함하지 않는다 — 구버전 클라이언트가 명시 전송하는 값이지 아바타가 아니다.
- 생성 닉네임은 저장 가능한 길이(현행 닉네임 컬럼 상한) 안이며 ASCII 문자만 쓰므로 커뮤니티 노출 시 표기 문제가 없다.
