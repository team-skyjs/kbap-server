# 계약: SQS 수집 요청 메시지 (kbap → kbap-langchain)

> **이번 범위 밖 — 합의 문서**. 발행 구현은 후속 티켓(`:batch` 잡)이 소유한다. 여기 적힌 형태는 랭체인 쪽과 맞춰 둔 계약이며, KB-302 는 이 메시지를 만들 재료(`food_content_outbox` 행)를 준비하는 데까지만 한다.

## 큐

단일 표준 큐. URL·리전은 `kbap.mq.food-content-queue-url` / AWS 기본 리전 체인으로 주입한다. 발행 주체는 **kbap api 스케줄러 하나뿐**이다.

## 메시지 본문

```json
{ "foodId": 1234, "displayName": "들깨 칼국수" }
```

| 필드 | 타입 | 설명 |
|---|---|---|
| `foodId` | number | 대상 음식 식별자. 람다는 **결과 호출에 이 값을 그대로 실어 보낸다** |
| `displayName` | string | 콘텐츠 생성 입력이 되는 표시명(띄어쓰기 포함 원본) |

배치 엔트리 id 로는 아웃박스 행 id 를 쓴다(본문에는 없음 — 발행 성공/실패를 행에 되짚기 위한 용도).

## 발행 규칙

- `SendMessageBatch` 로 **10건씩** 보낸다(AWS 상한). 부분 실패는 정상 응답이며, 성공한 엔트리만 `SENT` 로 표시하고 나머지는 다음 주기에 재시도한다.
- 같은 음식에 대기 중인 요청이 있으면 새 메시지를 만들지 않는다. 단, 재시도·SQS at-least-once 특성상 **같은 메시지가 두 번 도착할 수 있다** — 적재가 멱등이므로 문제되지 않는다.
- 중복 소비 방지를 위한 FIFO 큐·중복 제거 ID 는 쓰지 않는다(멱등 적재로 충분).

## 실패 처리

람다 쪽 런타임 실패는 SQS 재시도 후 DLQ 로 간다. 그 경우 kbap 적재 API 는 호출되지 않고, 아웃박스 행은 `SENT` 인 채 남는다 — **발행은 성공했고 처리가 실패한 상태**이므로 서버가 자동 재발행하지 않는다. 재시도는 관리자가 재수집으로 명시 요청한다.
