# Feature Specification: 음식 콘텐츠 파이프라인 랭체인 전환 — 아웃박스 적재·결과 수신·재수집

**Feature Branch**: `kb-302-langchain-food-ingest`

**Created**: 2026-08-11

**Status**: Draft

**Input**: KB-302 음식 콘텐츠 파이프라인 랭체인 전환 — 아웃박스 발행(스캔 miss·관리자 일괄 재수집), foodId 기반 결과 수신 API, 기존 사진 재활용(재수집 시 이미지 재생성 금지), READY 유지 즉시 덮어쓰기

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 서비스 중인 음식의 오타·설명 일괄 재수집 (Priority: P1)

관리자가 음식 목록에서 검색어·상태로 대상을 좁힌 뒤 "재수집"을 실행하면, 해당 음식들의 설명·번역·재료가 외부 콘텐츠 생성 파이프라인에서 다시 만들어져 자동으로 반영된다. 이미 서비스 중인 음식은 재수집 도중에도 사용자에게 계속 보이고, **이미 확보한 음식 사진은 그대로 유지된다**(재생성하지 않는다).

**Why this priority**: 지금 당장 필요한 요구. 기존 데이터에 오타·부실한 설명이 섞여 있어 사람이 일일이 고칠 수 없다. 사진을 재활용하지 못하면 이미지 생성 비용이 데이터 전체에 다시 든다.

**Independent Test**: READY 상태 음식 몇 건을 조건으로 골라 재수집을 요청하고, (1) 결과 도착 후 설명·번역이 갱신되는지, (2) 사진 경로가 변하지 않는지, (3) 그 사이에도 앱 목록·검색에 계속 노출되는지 확인하면 단독으로 검증된다.

**Acceptance Scenarios**:

1. **Given** READY 상태이고 사진이 있는 음식, **When** 관리자가 재수집을 요청하고 성공 결과가 도착하면, **Then** 설명·번역·재료·맵기가 갱신되고 상태는 READY 그대로이며 사진은 바뀌지 않는다
2. **Given** 재수집을 요청한 음식, **When** 결과가 아직 도착하지 않았을 때, **Then** 사용자에게는 기존 콘텐츠가 계속 정상 노출된다
3. **Given** READY 상태 음식, **When** 실패 결과(passed=false)가 도착하면, **Then** 기존 콘텐츠·상태·사진은 보존되고 실패 원인·사유만 기록된다
4. **Given** 사진이 없는 음식, **When** 성공 결과가 도착하면, **Then** 이미지 생성 대기 상태가 되어 기존 이미지 파이프라인이 사진을 만든다
5. **Given** 조건에 걸린 대상이 상한(캡)을 넘는 경우, **When** 관리자가 재수집을 실행하면, **Then** 실행이 거부되고 대상 건수와 상한이 안내된다
6. **Given** 이미 재수집 요청이 대기 중인 음식, **When** 같은 음식이 다시 요청되면, **Then** 중복 요청은 새로 쌓이지 않는다

---

### User Story 2 - 메뉴판 스캔에서 처음 본 음식 자동 수집 (Priority: P2)

사용자가 메뉴판을 스캔했을 때 보유 데이터에 없던 음식은 관리자 개입 없이 콘텐츠 수집 대상으로 등록되고, 완성되면 관리자 승인 흐름(사진 → 승인)을 거쳐 서비스에 편입된다.

**Why this priority**: 데이터가 자라는 유일한 자동 경로. 다만 US1 없이도 서비스는 굴러가므로 P2.

**Independent Test**: 미보유 음식명이 포함된 스캔을 처리한 뒤, 그 음식이 수집 요청 대기 목록에 남고 결과 도착 시 이미지 생성 대기 상태가 되는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 보유 데이터에 없는 음식명이 스캔에 등장, **When** 스캔이 처리되면, **Then** 해당 음식이 관리자 확인 상태로 등록되고 콘텐츠 수집 요청이 함께 남는다
2. **Given** 수집 요청이 남은 음식, **When** 수집 성공 결과가 도착하면, **Then** 콘텐츠가 채워지고 이미지 생성 대기 상태가 된다
3. **Given** 음식 등록 트랜잭션이 롤백되는 상황, **When** 스캔이 실패하면, **Then** 음식도 수집 요청도 남지 않는다(반쪽 상태 금지)
4. **Given** 스캔 응답, **When** 미보유 음식이 포함되어 있어도, **Then** 스캔 결과 응답은 콘텐츠 수집 진행 상태에 의존하지 않고 즉시 반환된다

---

### User Story 3 - 실패한 음식의 원인 확인 (Priority: P3)

관리자가 음식 화면에서 실패 상태 음식의 **실패 유형**(비음식·판정 탈락·재료 가드)과 사유 문구를 확인하고, 삭제할지 이름을 고쳐 재수집할지 판단한다.

**Why this priority**: 수집 결과를 사람이 트리아지하는 마지막 고리. 없으면 실패 음식이 왜 실패했는지 DB를 봐야 한다.

**Independent Test**: 실패 결과가 기록된 음식을 관리자 화면에서 열어 유형·사유가 보이는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 실패 결과가 기록된 음식, **When** 관리자가 음식 상세를 열면, **Then** 실패 유형과 사유 문구가 함께 보인다
2. **Given** 실패 유형이 "재료 가드"인 음식, **When** 관리자가 목록에서 보면, **Then** 안전 직결 항목임을 구분할 수 있다

---

### Edge Cases

- **결과가 도착했는데 그 음식이 이미 삭제됨**: 적재를 거부하고 호출자가 사람 판단으로 넘길 수 있는 실패 응답을 준다(조용한 유실 금지).
- **계약 위반 요청**(번역 9개 언어 미충족, 재료 누락, 맵기 범위 밖, 실패 유형이 정의된 3값 밖): 경계에서 거절하고 저장하지 않는다.
- **같은 음식 결과가 두 번 도착**: 두 번째도 정상 처리(갱신 후 성공 응답) — 재시도가 오류로 보이지 않아야 한다.
- **외부 파이프라인 런타임 장애**(모델 다운·타임아웃): 실패 결과로 도착하지 않는다 — 재시도 후 사람이 보는 경로로 빠진다. 서버는 실패 상태를 자동 재시도하지 않는다.
- **재수집 대상 0건**: 아무 요청도 쌓이지 않고 그 사실이 관리자에게 그대로 표시된다.

## Requirements *(mandatory)*

### Functional Requirements

**수집 요청(아웃박스)**

> **범위 주의**: 쌓인 요청을 실제로 외부 큐에 **발행하는 일은 이번 범위 밖**이다(후속 티켓의 배치가 소유). 여기서는 요청이 유실 없이 쌓이고, 발행 주체가 집어 갈 수 있는 형태로 남는 데까지만 다룬다.

- **FR-001**: 시스템은 콘텐츠 수집 요청을 음식 등록과 같은 트랜잭션에서 영속화해야 한다(요청 유실 금지).
- **FR-002**: 수집 요청은 대상 음식의 **식별자(foodId)** 와 발행에 쓸 표시명을 보관해야 한다 — 결과 수신 시 이름이 아닌 식별자로 대상을 특정하기 위함이다.
- **FR-003**: 수집 요청은 대기/발행 완료 상태와 발행 시도 횟수·발행 시각을 가져야 한다 — 발행 주체(후속)가 대기 요청만 골라 집고 결과를 되짚을 수 있어야 한다.
- **FR-004**: 같은 음식에 대기 중인 요청이 이미 있으면 새 요청을 쌓지 않는다.

**결과 수신·적재**

- **FR-005**: 시스템은 외부 파이프라인이 호출하는 음식 단건 적재 창구를 제공해야 하며, 머신 인증(관리자 자격)을 요구한다.
- **FR-006**: 적재 대상은 요청에 담긴 **foodId 로만 특정**한다. 해당 음식이 없거나 삭제된 경우 실패 응답으로 거절한다.
- **FR-007**: 성공 결과는 설명·맵기·이름 번역·설명 번역·재료를 갱신한다. 번역은 정의된 9개 언어 전수·빈 값 불가, 재료는 필수이며 빈 목록을 허용한다(빈 목록 = "조사했고 해당 없음", 미조사와 구분).
- **FR-008**: 성공 결과 적용 시 상태는 다음 규칙을 따른다 — 이미 서비스 중(READY)이면 **상태를 바꾸지 않는다**; 그 외에는 **사진이 이미 있으면 승인 대기**로, **사진이 없으면 이미지 생성 대기**로 둔다.
- **FR-009**: 시스템은 어떤 경우에도 적재 과정에서 기존 사진을 지우거나 교체하지 않는다. 사진이 있는 음식은 이미지 생성 후보로 다시 선정되지 않는다.
- **FR-010**: 실패 결과는 실패 유형(3값 중 하나)과 사유 문구를 저장한다. 대상이 서비스 중(READY)이면 상태·콘텐츠를 유지하고 실패 기록만 남긴다. 그 외에는 관리자 확인 상태로 둔다.
- **FR-011**: 실패 유형이 정의된 3값 밖이면 요청을 거절한다. 사유 문구는 표시 전용이며 어떤 분기에도 쓰지 않는다.
- **FR-012**: 같은 결과가 중복 도착해도 정상 처리(갱신 + 성공 응답)한다.
- **FR-013**: 시스템은 실패 상태 음식을 자동으로 재수집하지 않는다.

**관리자 조작**

- **FR-014**: 관리자는 음식 목록의 검색어·상태 조건에 걸린 음식 전체에 대해 재수집을 한 번에 요청할 수 있어야 한다.
- **FR-015**: 일괄 재수집은 실행 전 대상 건수를 보여주고 확인을 받아야 하며, 1회 요청 대상 건수에 상한을 둔다. 상한을 넘으면 실행을 거부하고 조건을 좁히도록 안내한다.
- **FR-016**: 관리자 화면은 실패 상태 음식의 실패 유형과 사유를 표시해야 한다.

### Key Entities

- **음식(Food)**: 표시명·매칭 키·설명·번역·재료·맵기·사진 참조·콘텐츠 상태를 가진다. 콘텐츠 상태는 기존 4값(관리자 확인 필요 / 이미지 생성 대기 / 승인 대기 / 서비스 중)을 그대로 쓴다. 실패 유형이 새 속성으로 추가된다.
- **콘텐츠 수집 요청(아웃박스 항목)**: 대상 음식 식별자, 발행에 쓸 표시명, 요청 상태(대기/발행 완료), 시도 횟수, 발행 시각. 요청 출처(스캔 / 관리자 재수집)는 구분하지 않는다 — 처리 방식이 같다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사진이 있는 음식을 재수집할 때 이미지 재생성 발생 건수는 **0** 이다.
- **SC-002**: 서비스 중인 음식을 재수집하는 동안 그 음식이 앱 목록·검색·상세에서 사라지는 시간은 **0초**다.
- **SC-003**: 수집 대상이 된 음식 중 대기 요청이 남지 않은 음식은 **0건**이다(등록과 요청이 한 트랜잭션이라 반쪽 상태가 없다).
- **SC-004**: 관리자는 조건 지정부터 재수집 요청 완료까지 **1분 이내**에 마칠 수 있으며, 요청 응답을 위해 외부 파이프라인 완료를 기다리지 않는다.
- **SC-005**: 실패한 음식은 관리자 화면에서 **화면 이동 없이** 실패 유형과 사유를 확인할 수 있다.
- **SC-006**: 계약을 위반한 결과 요청(번역 누락·재료 누락·범위 밖 값)은 **100%** 저장 전에 거절된다.

## Assumptions

- 외부 콘텐츠 생성 파이프라인(kbap-langchain, 람다)은 요청 메시지에 담긴 **foodId 를 결과 호출에 그대로 실어 보낸다**. 이 한 가지가 계약 변경의 전부다.
- 큐에 메시지를 넣는 주체는 우리 서버뿐이다. 따라서 결과 호출과 재수집 요청을 짝짓는 별도 상관관계 식별자는 두지 않는다.
- 기존 계약의 "이미 서비스 중인 음식은 덮지 않고 건너뛴다" 규칙은 **폐기**한다 — 재수집이 이 규칙과 정면으로 충돌하며, 발행 주체가 우리뿐이라 의도치 않은 덮어쓰기가 발생하지 않는다.
- 수집 대상 음식 행은 요청 시점에 **항상 이미 존재**한다(스캔 미보유 음식도 등록 후 요청을 쌓는다). 따라서 결과 적재는 신규 생성 경로를 갖지 않는다.
- 스캔 응답은 콘텐츠 수집 진행 상태에 의존하지 않는다(별개 프로세스 — 2026-08-08 확정).
- 일괄 재수집 1회 상한은 **500건**으로 시작한다(운영하며 조정 가능한 값).
- 승인·반려 전이, 이미지 생성·회수 파이프라인, 관리자 인증은 이미 존재하며 그대로 재사용한다.
- **범위 밖**: 대기 요청을 외부 큐로 **발행하는 일**. 후속 티켓의 배치 잡이 소유한다. 이번 작업 완료 후에는 요청이 쌓이기만 하고 실제 수집은 그 티켓이 붙어야 시작된다 — 결과 적재 API 는 그때까지 수동 호출·테스트로만 검증된다.
- **범위 밖**: 기존 내부 배치(`:batch`) 모듈의 콘텐츠 채움 코드 정리와 모듈 존치 결정(KB-302 DoD 항목). 이번 작업은 배치 모듈을 건드리지 않는다.
