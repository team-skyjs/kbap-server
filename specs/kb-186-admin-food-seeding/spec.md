# Feature Specification: 신규 음식 적재 관리자 API (Admin Food Seeding)

**Feature Branch**: `kb-186-admin-food-seeding`

**Created**: 2026-07-21

**Status**: Draft

**Input**: User description: "kb-186 — [BE] 신규 음식 적재 관리자 API. 관리자가 외국인 인기 한국 음식 메뉴를 선정한 뒤, 기존 food(korean_name)와 대조해 중복을 제외한 신규 메뉴만 INCOMPLETE 상태로 적재한다. 관리자만 호출 가능(ADMIN 인가), 재실행해도 중복 행이 생기지 않는 멱등 적재."

## Clarifications

### Session 2026-07-21

- Q: 관리자 요청을 '진짜 관리자'로 인가하는 메커니즘을? → A: 기존 HS256 서명 JWT 를 재사용하고 MemberRole 에 ADMIN 값을 추가해 엔드포인트에서 role==ADMIN 을 검사한다. 토큰 서명이 위조를 막으므로 role 클레임 하나로 인가가 안전하며, 별도 API 키·인프라를 새로 만들지 않는다. ("인증 없음" = 관리자 로그인 흐름 없이 서명된 ADMIN 토큰을 발급해 두고 인가만 수행.)
- Q: ADMIN 토큰의 시크릿 격리와 수명 정책은? → A: 유저 JWT 와 **동일한 시크릿(kbap.auth.jwt.secret)** 으로 서명하고 표준 access TTL 을 적용한다. 별도 관리자 전용 시크릿은 두지 않는다. 잔여 위험(bearer 토큰 유출)은 공용 시크릿 회전으로 폐기하는 것으로 수용한다.
- 결정(타 세션 조율): 적재되는 신규 음식의 초기값은 **맵기 = -1(미조사 센티널)**, **회피·주의 성분 = null(미조사)** 로 둔다. 배치가 "조사 결과 없음(0·빈 목록)"과 "아직 미조사"를 구분하지 못하던 문제(맵기 0 이 안 매운 건지 미조사인지, 회피 성분 빈 목록이 없는 건지 미조사인지) 때문이다. 이 초기값은 스캔·관리자 두 입구가 공유하는 미완성 음식 생성 경로(`Food.incomplete()` + `upsertIncomplete`)가 책임지며, 해당 변경은 **`kb-182-batch-pipeline-skeleton` 세션이 소유**한다. kb-186 은 그 경로를 재사용할 뿐 초기값 로직을 다시 구현하지 않는다([[batch-food-unit-pipeline]] 관련).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 신규 메뉴를 INCOMPLETE 로 일괄 적재 (Priority: P1)

관리자가 외국인이 많이 찾는 한국 음식 메뉴 후보 목록을 선정해 시스템에 제출한다. 시스템은 각 이름을 기존 음식과 대조하고, 아직 없는 이름만 새 음식으로 INCOMPLETE 상태로 저장한다. 이렇게 적재된 음식은 이후 콘텐츠 채움 파이프라인(KB-182~184)이 집어 완성해 READY 로 전이시킨다.

**Why this priority**: 지금까지 새 음식이 DB 에 들어오는 입구는 "메뉴판 스캔 중 미등록 음식 발견" 하나뿐이라 시드를 능동적으로 늘릴 수단이 없었다. 이 스토리가 없으면 기능 자체가 존재하지 않는다 — 이것이 곧 MVP 다.

**Independent Test**: 신규 이름 목록을 제출하면 그 이름들이 INCOMPLETE 음식으로 생성되고, 이미 존재하는 이름은 건너뛰며, 생성/건너뜀 결과가 응답으로 확인되는지로 단독 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 목록의 모든 이름이 기존 food 에 없을 때, **When** 관리자가 목록을 제출하면, **Then** 각 이름이 INCOMPLETE 음식으로 정확히 하나씩 생성된다.
2. **Given** 목록 중 일부는 이미 존재하고 일부는 신규일 때, **When** 관리자가 목록을 제출하면, **Then** 신규 이름만 생성되고 기존 이름은 건너뛰며 응답이 생성/건너뜀 수를 알려준다.
3. **Given** 목록의 모든 이름이 이미 존재할 때, **When** 관리자가 목록을 제출하면, **Then** 새로 생성되는 음식은 없고 요청은 성공으로 처리된다(0건 생성).

---

### User Story 2 - 관리자만 적재 가능 (ADMIN 인가) (Priority: P2)

이 적재 작업은 DB 에 직접 데이터를 쌓으므로 관리자 권한을 가진 호출자만 수행할 수 있어야 한다. 관리자 권한이 없는 호출은 거절되고 데이터가 전혀 생성되지 않는다.

**Why this priority**: DB 를 능동적으로 채우는 통로를 아무나 열면 데이터 오염 위험이 크다. 접근 통제는 이 기능을 안전하게 노출하기 위한 전제 조건이라 P2 다.

**Independent Test**: 관리자 권한이 없는(또는 권한 증표가 없는) 호출이 거절되고 어떤 음식도 생성되지 않는지, 반대로 관리자 권한을 가진 호출은 통과하는지로 단독 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 관리자 권한 증표가 없는 호출자가, **When** 적재를 시도하면, **Then** 요청은 거절되고 어떤 음식도 생성되지 않는다.
2. **Given** 관리자 권한이 없는 일반 사용자 증표를 가진 호출자가, **When** 적재를 시도하면, **Then** 요청은 거절된다.
3. **Given** 관리자 권한을 가진 호출자가, **When** 적재를 시도하면, **Then** 요청이 통과해 적재가 수행된다.

---

### User Story 3 - 재실행·경합에도 중복 없는 멱등 적재 (Priority: P3)

같은(또는 겹치는) 목록으로 적재를 여러 번 실행하거나 동시에 실행해도, 같은 이름의 음식 행이 중복 생성되지 않고 실패도 나지 않아야 한다.

**Why this priority**: 관리자가 목록을 다듬어 재제출하거나 재시도하는 것은 일상적이다. 멱등성이 없으면 unique 제약 위반으로 요청이 깨지거나 유령 중복이 쌓인다. 정확성의 핵심이라 명시적 스토리로 둔다.

**Independent Test**: 동일 목록을 두 번(그리고 동시에 두 번) 제출한 뒤, 각 신규 이름이 정확히 한 행만 존재하고 두 번째 요청이 실패 없이 성공하는지로 단독 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 어떤 목록으로 이미 한 번 적재했을 때, **When** 같은 목록을 다시 제출하면, **Then** 새로 생성되는 행은 0건이고 요청은 성공한다.
2. **Given** 동일한 목록을 담은 두 요청이 동시에 도착할 때, **When** 둘 다 처리되면, **Then** 각 신규 이름은 정확히 한 행만 저장되고 어느 요청도 오류로 실패하지 않는다.

---

### Edge Cases

- 한 요청 안에 같은 이름이 중복으로 들어오면 → 그 이름은 한 번만 반영된다(요청 내 중복 제거).
- 빈 목록 또는 공백/빈 문자열 이름이 섞여 있으면 → 유효하지 않은 항목은 무시하고, 유효 항목이 없으면 0건 생성으로 성공 처리한다.
- 같은 korean_name 의 소프트 삭제된 행이 이미 있으면 → 유령 중복이 생기거나 unique 제약으로 요청이 깨지지 않도록 안전하게 처리한다.
- 이미 READY(완성) 상태인 동명 음식이 있으면 → 신규 생성 없이 건너뛴다(상태와 무관하게 korean_name 존재만으로 중복 판정).
- 매우 큰 목록이 한 번에 들어와도 부분 실패로 멀쩡한 항목까지 롤백되지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 관리자가 한국 음식 메뉴 이름 집합을 제출해 신규 음식으로 적재를 요청할 수 있는 작업을 제공해야 한다.
- **FR-002**: 시스템은 이 적재 작업을 **ADMIN 역할을 가진 호출자로만** 제한해야 한다. 호출자의 역할은 **서명 검증에 통과한 JWT 의 role 클레임**에서 판정하며, ADMIN 이 아니거나 토큰이 없거나 서명이 유효하지 않은 호출은 거절해야 한다. (서명 검증이 위조를 막으므로 role 클레임만으로 인가가 성립한다.)
- **FR-003**: 시스템은 제출된 각 이름을 기존 food 의 korean_name 과 대조해, **이미 존재하지 않는 이름만** 새로 생성해야 한다.
- **FR-004**: 새로 생성되는 음식은 **INCOMPLETE 콘텐츠 상태**로 저장되어, 기존 콘텐츠 채움 파이프라인이 이후 완성할 수 있어야 한다.
- **FR-005**: 적재 작업은 **멱등**해야 한다 — 같은/겹치는 입력으로 재실행해도 중복 음식 행을 만들지 않고, korean_name unique 제약 위반으로 실패하지 않아야 한다.
- **FR-006**: 시스템은 적재 결과(예: 신규 생성 건수와 기존으로 건너뛴 건수)를 호출자에게 알려야 한다.
- **FR-007**: 시스템은 한 요청 안의 중복 이름과 빈/공백 이름을 안전하게 처리(중복 제거·무시)해야 한다.
- **FR-008**: 동일 입력의 동시 요청이 있어도 중복 행을 만들거나 오류로 실패하지 않아야 한다.
- **FR-009**: 적재된 신규 음식은 "아직 조사되지 않음"을 나타내는 초기값을 가져야 한다 — **맵기 = -1(미조사 센티널)**, **회피·주의 성분 = null(미조사)**. 배치가 이 미조사 상태를 "조사 결과 없음(맵기 0·회피 성분 빈 목록)"과 구분할 수 있어야 한다. (이 초기값은 미완성 음식 생성 경로가 제공하며 kb-186 은 재사용한다 — Clarifications 결정 참조.)

### Key Entities *(include if feature involves data)*

- **Food(음식)**: 시스템이 관리하는 음식. korean_name 이 유일(uq_food_korean_name)하며 중복 판정 기준이 된다. 콘텐츠 상태는 INCOMPLETE(미완성) → READY(완성)로 전이한다. 이 기능으로 적재되는 신규 음식은 INCOMPLETE 로 들어온다.
- **관리자(Admin caller)**: role 클레임이 ADMIN 인 서명된 JWT 를 지닌 호출자. 이 적재 작업을 수행할 수 있는 유일한 주체다. 관리자용 로그인/신원 행은 없고, 토큰은 사전 발급되는 bearer 증표다.
- **적재 요청(Seed request)**: 관리자가 선정한 한국 음식 메뉴 이름들의 집합. 시스템은 이 집합을 기존 음식과 대조해 신규분만 적재한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: N개 이름(그중 M개가 신규)을 제출하면 정확히 M개의 INCOMPLETE 음식이 새로 생기고 나머지 N−M개는 기존으로 건너뛴다.
- **SC-002**: 같은 목록을 두 번째로 제출하면 신규 생성은 0건이고 요청은 성공한다.
- **SC-003**: 관리자 권한이 없는 호출은 거절되며 음식이 하나도 생성되지 않는다.
- **SC-004**: 동일 목록을 동시에 두 번 제출해도 각 신규 이름은 정확히 한 번만 저장되고 어느 요청도 실패하지 않는다.
- **SC-005**: 새로 적재된 음식은 콘텐츠 채움 파이프라인의 대상(INCOMPLETE)으로 즉시 편입된다.

## Assumptions

- 콘텐츠 채움 파이프라인(KB-182~184)이 INCOMPLETE 음식을 소비해 완성한다. 이 기능은 음식을 **INCOMPLETE 로 만들기만** 하면 되고 콘텐츠 완성(번역·회피 점수 등)은 책임지지 않는다.
- 관리자 신원은 **미리 발급된, role=ADMIN 인 서명 JWT** 로 전달된다. 별도의 로그인/인증 흐름은 만들지 않는다(DoD: "인증은 필요없음" — 인가 정책만 적용). ADMIN 은 기존 MemberRole 에 추가하는 값이며, 토큰은 **유저 JWT 와 같은 시크릿(kbap.auth.jwt.secret)** 으로 서명하고 표준 access TTL 을 쓴다(관리자 전용 시크릿 없음).
- 잔여 보안 위험은 **bearer 토큰 유출** 하나다(관리자 신원 행이 없어 개별 폐기 불가). 유출 시 공용 시크릿을 회전해 폐기하는 것으로 수용하며, 전용 시크릿·토큰 폐기 목록은 이번 범위 밖이다.
- "외국인 인기 메뉴" 선정은 사람이 수동/오프라인으로 큐레이션하는 단계다. API 는 확정된 이름 목록을 받을 뿐, 어떤 메뉴가 인기인지 발굴하는 로직은 포함하지 않는다.
- 신규 음식 적재에는 korean_name 만 있으면 충분하다. 나머지 속성은 이후 파이프라인이 채운다.
- 중복 판정 키는 korean_name 이며, 기존 메뉴판 스캔 입구와 동일한 기준을 쓴다.
- **의존(타 세션)**: 미완성 음식의 초기 센티널(맵기 -1·회피 성분 null)은 공유 생성 경로(`Food.incomplete()`·`upsertIncomplete` SQL·해당 컬럼 nullable 스키마)에서 나온다. 이 변경은 배치 파이프라인 세션이 소유하며, kb-186 의 센티널 검증(FR-009)은 그 변경이 develop 에 반영된 뒤에 그린이 된다. kb-186 자체는 이 경로를 수정하지 않는다.

## Out of Scope

- 어떤 메뉴를 추가할지 선정·발굴하는 큐레이션 로직.
- 적재된 음식의 콘텐츠 완성(번역, 회피 물질 점수 등) — KB-182~184 가 담당.
- 관리자용 로그인/인증 시스템 구축(인가 정책만 적용, 인증은 범위 밖).
