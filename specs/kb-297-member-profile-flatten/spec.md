# Feature Specification: 회원 프로필 JSON 컬럼 평탄화

**Feature Branch**: `kb-297-member-profile-flatten`

**Created**: 2026-08-05

**Status**: Draft

**Input**: User description: "회원 테이블의 json 포맷으로 프로필 정보를 저장하고 있는데 개별 칼럼으로 평탄화하는 작업 진행한다" (Jira KB-297, 에픽 KB-208 데이터베이스)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 기존 회원 데이터 무손실 이전 (Priority: P1)

기존 회원의 프로필 정보(회피 성분 코드 목록·맵기 선호도·국가 코드·프로필 이미지 경로)가 저장 구조 변경 후에도 한 건도 유실·변형 없이 그대로 유지된다. 회원이 앱을 다시 열었을 때 자신의 프로필이 변경 전과 동일하게 보인다.

**Why this priority**: 데이터 유실은 되돌릴 수 없는 사고이며, 이 작업의 유일한 실패 조건이다. 저장 구조가 어떻게 바뀌든 기존 회원 경험이 흔들리면 안 된다.

**Independent Test**: 구조 변경 전 저장된 회원 데이터를 기준으로, 변경 적용 후 프로필 조회 결과가 변경 전과 완전히 일치하는지 비교하여 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 프로필(회피 성분·맵기 선호·국가·이미지 경로)이 채워진 기존 회원, **When** 저장 구조 변경이 적용된 후 프로필을 조회하면, **Then** 변경 전과 동일한 프로필 정보가 반환된다
2. **Given** 프로필 일부 항목만 설정된 회원(예: 국가 미설정), **When** 구조 변경 후 조회하면, **Then** 설정된 항목은 유지되고 미설정 항목은 여전히 미설정 상태다
3. **Given** 회피 성분 코드를 여러 개 선택한 회원, **When** 구조 변경 후 조회하면, **Then** 선택한 코드 전체가 누락 없이 반환된다

---

### User Story 2 - 프로필 기능 동작 불변 (Priority: P2)

온보딩 완료, 프로필 수정, 프로필 조회 등 회원이 사용하는 모든 프로필 관련 기능이 저장 구조 변경 후에도 동일하게 동작한다. 응답 형식·검증 규칙·에러 동작이 변하지 않는다.

**Why this priority**: 저장 구조는 내부 구현이므로 사용자·클라이언트 앱 관점에서 어떤 변화도 감지되어서는 안 된다. 데이터 이전(P1) 다음으로 중요한 무결성 조건이다.

**Independent Test**: 온보딩·프로필 수정·조회의 기존 자동화 테스트 전체를 재실행하여 전부 통과하는지로 독립 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 신규 가입 회원, **When** 온보딩(닉네임·회피 성분·맵기 선호·국가·프로필 이미지 입력)을 완료하면, **Then** 변경 전과 동일하게 프로필이 저장되고 온보딩 완료 상태가 된다
2. **Given** 온보딩을 마친 회원, **When** 프로필 일부 항목만 수정하면, **Then** 수정한 항목만 바뀌고 나머지는 유지된다
3. **Given** 유효하지 않은 입력(잘못된 회피 성분 코드·잘못된 국가 코드 등), **When** 프로필을 수정하면, **Then** 변경 전과 동일한 검증 에러가 반환된다

---

### User Story 3 - 프로필 항목별 데이터 정합성 강제 (Priority: P3)

프로필의 단일 값 항목들이 개별 저장 항목으로 분리되어, 저장소 수준에서 항목별 형식·정합성이 강제되고 항목 단위 조회·집계가 가능해진다. 목록형인 회피 성분 코드는 다른 프로필 항목과 섞이지 않는 독립된 목록 항목으로 분리된다.

**Why this priority**: 이 작업의 본래 목적(운영·분석 개선)이지만, P1·P2 가 지켜진 뒤에 의미가 있는 이득이다.

**Independent Test**: 저장소에서 프로필 각 항목을 개별 항목으로 직접 조회·필터링할 수 있는지, 형식에 어긋난 값 저장이 저장소 수준에서 거부되는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 구조 변경이 적용된 저장소, **When** 특정 프로필 항목(예: 국가 코드)으로 회원을 필터링 조회하면, **Then** 문서 파싱 없이 항목 값으로 직접 조회된다
2. **Given** 구조 변경이 적용된 저장소, **When** 회원의 회피 성분 코드 목록을 조회하면, **Then** 다른 프로필 항목과 분리된 독립 목록 항목에서 코드 목록이 반환된다

---

### Edge Cases

- 프로필이 완전히 비어 있는 회원(가입 직후 온보딩 미완료)은 구조 변경 후에도 기본값 상태로 조회되어야 한다.
- 과거 형식의 잔재가 있는 데이터(예: 선행 슬래시가 붙은 이미지 경로, 폐기된 항목이 남은 데이터)는 이전 시 현행 규칙으로 정규화되어야 한다.
- 탈퇴(소프트 삭제)한 회원의 데이터도 이전 대상에 포함되어, 이전 과정에서 오류를 일으키지 않아야 한다.
- 이전 도중 실패 시 데이터가 반쯤 이전된 상태로 서비스되지 않아야 한다(이전 단계 분리로 안전하게 재시도 가능해야 한다).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 회원 프로필의 맵기 선호도·국가 코드·프로필 이미지 경로를 각각 독립된 저장 항목으로 보관해야 한다
- **FR-002**: 시스템은 회원의 회피 성분 코드 목록을 다른 프로필 항목과 분리된 독립 목록 항목으로 보관해야 한다
- **FR-003**: 시스템은 기존 JSON 형식으로 저장된 모든 회원 프로필 데이터를 신규 구조로 손실 없이 이전해야 한다
- **FR-004**: 이전 완료 후 기존 JSON 저장 항목은 제거되어야 한다
- **FR-005**: 프로필 조회·수정·온보딩의 외부 동작(입력·응답·검증 규칙·에러)은 변경 전과 동일해야 한다
- **FR-006**: 프로필 항목별 형식 제약(길이·허용 값)은 저장소 수준에서 강제되어야 한다
- **FR-007**: 이전 작업은 실패 시 재시도 가능해야 하며, 부분 적용 상태로 서비스에 노출되지 않아야 한다

### Key Entities

- **회원(Member)**: 서비스 이용자. 계정 식별 정보와 프로필을 보유하며, 프로필의 단일 항목들(맵기 선호도·국가 코드·프로필 이미지 경로)을 개별 항목으로 직접 보유하게 된다
- **회원 회피 성분(Member Avoidance Substance)**: 회원이 기피하는 성분 코드. 회원 1명이 0개 이상 보유하는 목록형 데이터로, 다른 프로필 항목과 분리된 독립 목록 항목으로 보관된다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 구조 변경 전후 전체 회원의 프로필 조회 결과가 100% 일치한다(데이터 유실·변형 0건)
- **SC-002**: 온보딩·프로필 수정·조회 관련 기존 자동화 테스트가 전부 통과한다
- **SC-003**: 클라이언트 앱 수정 없이 배포 가능하다(외부 응답·요청 형식 변경 0건)
- **SC-004**: 프로필 각 항목을 저장소에서 항목 단위로 직접 조회·필터링할 수 있다

## Assumptions

- 프로필 저장 구조는 내부 구현이므로 외부(클라이언트 앱) 대응 작업은 없다 — API 계약 불변이 전제다.
- 닉네임은 이미 개별 저장 항목으로 분리되어 있어 이번 작업 범위가 아니다.
- 회피 성분 코드 목록은 목록형 데이터이므로 단일 항목 평탄화 대상이 아니라 독립 목록 항목으로 분리한다(2026-08-05 결정 — 별도 테이블이 아닌 목록 컬럼 유지, 코드 단위 역방향 조회 요구 없음).
- 이전은 서비스 중단 없이 적용 가능해야 하며, 기존 데이터 정규화 규칙(이미지 경로 선행 슬래시 제거, 폐기 항목 무시)은 현행 로직과 동일하게 적용한다.
- 프로필 관련 기존 검증 규칙(닉네임 공백 금지, 성분 코드 카탈로그 검증, 국가 코드 검증, 이미지 경로 길이·형식 검증)은 그대로 유지된다.
