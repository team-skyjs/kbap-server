## Clarifications

### Session 2026-08-30

- Q: 재사용할 테스트 이미지를 S3에 어떻게 올려둘까(시드 방식)? → A: 실제 업로드 체인(presign→PUT→complete)을 시드 스크립트로 1회 실행해 objectKey를 확보한다(공개 URL·경로 포맷 보장).
- Q: 부하 루프가 측정할 범위는? → A: 루프 = 스캔 티켓 발급 + 스캔만. presign·PUT·complete는 1회 시드로 빠진다(스캔 LLM 엔드포인트에 집중, 반복성↑).
- Q: objectKey(시드 키)를 어떻게 관리해 반복 구조를 만들까? → A: 시드 스크립트가 objectKey를 출력하고, k6에 `-e SCAN_IMAGE_PATH`로 주입한다(키는 커밋하지 않음).
- 근거(코드 확인): `scanMenuBoardImageV2`는 imagePath의 업로드 완료·소유 여부를 검증하지 않는다(티켓 검증 → 예약 → 비전 추출기에 imagePath 전달). 따라서 한 번 시드한 이미지 키를 전체 회차에서 반복 재사용해도 스캔이 거부하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔 체인 동시 부하 실측 (Priority: P1)

운영자는 dev 환경에서 테스트 이미지를 **사전에 1회 시드**(실제 업로드 체인으로 objectKey 확보)해 두고, 부하 루프는 **스캔 티켓 발급 + 스캔** 두 단계만 동시 사용자 수 5 → 50 → 145 로 늘려 가며 반복 실행해 스캔 응답 시간 분포(p95)·실패율을 얻는다. 이미지는 매 요청 재업로드하지 않고 시드한 키를 재사용한다. 스캔 1건마다 외부 비용(약 10원)이 발생하므로 스캔 요청 총량이 200건을 넘지 않아야 한다.

**Why this priority**: 이 기능의 존재 이유다 — 비용 상한 안에서 동시성 증가에 따른 성능 곡선을 얻는 것. 이것만 되면 나머지 없이도 가치가 있다.

**Independent Test**: 소량(동시 5) 리허설만 단독 실행해 체인 5단계가 전부 성공하고 요약 결과가 나오는 것으로 검증 가능.

**Acceptance Scenarios**:

1. **Given** 무제한 스캔 계정·유효 토큰·시드된 이미지 키(SCAN_IMAGE_PATH)가 준비된 상태, **When** 동시 5 리허설을 실행하면, **Then** 5건 모두 티켓 발급+스캔이 성공(HTTP 200)하고 스캔 응답 시간 요약이 출력된다.
2. **Given** 리허설이 성공한 상태, **When** 동시 50, 이어서 동시 145 를 실행하면, **Then** 각 회차의 p95·실패율이 기록되고 스캔 요청 누적이 200건을 넘지 않는다.
3. **Given** 티켓 발급에 실패한 가상 사용자가 있는 상태, **When** 그 사용자의 차례가 되면, **Then** 스캔 요청을 보내지 않아 비용이 발생하지 않는다.

---

### User Story 2 - 동시 스캔 중 타 API 영향 관찰 (Priority: P2)

운영자는 동시 스캔이 몰리는 동안 다른 API 의 응답 시간이 함께 밀리는지, 그리고 서버 자원(커넥션 풀·힙·호스트 CPU)이 어디까지 차는지를 모니터링 대시보드에서 관찰하고 병목 지점을 판정한다.

**Why this priority**: 스캔은 외부 LLM 응답까지 서버 자원을 점유하는 가장 무거운 경로다 — 스캔 폭주가 일반 사용자 경험을 해치는지가 이 테스트의 두 번째 질문이다.

**Independent Test**: 동시 50 실행 창에서 대시보드의 타 API p95·자원 그래프를 캡처하는 것으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 동시 50/145 실행 중, **When** 대시보드를 보면, **Then** 스캔 p95·타 API p95·커넥션 풀 사용량·힙·호스트 CPU 가 실행 창 구간에서 판독 가능하게 기록돼 있다.
2. **Given** 실행이 끝난 상태, **When** 결과를 해석하면, **Then** 병목이 앱 자원인지·DB 인지·외부 LLM 호출 한도인지 구분해 판정할 수 있다(외부 한도 초과 응답은 앱 결함과 분리 집계).

---

### User Story 3 - 결과 기록과 정리 (Priority: P3)

운영자는 회차별 결과 수치(p95 곡선·실패율·병목 판정)를 지식 위키에 남기고, 테스트 스크립트를 저장소에 커밋하며, 테스트용으로 만든 더미 계정이 있으면 비활성화한다.

**Why this priority**: 한계 수치는 코드로 알 수 없는 지식이라 기록해야 재사용된다. 다만 측정 자체가 끝난 뒤의 뒷정리다.

**Independent Test**: 위키 문서와 저장소 커밋, 더미 계정 상태 확인으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 3회차 실행이 끝난 상태, **When** 기록을 마치면, **Then** 위키에서 회차별 수치와 병목 판정을 확인할 수 있고 스크립트가 저장소에 있다.
2. **Given** 더미 계정을 만들었던 경우, **When** 정리를 마치면, **Then** 그 계정은 더 이상 서비스 조회에 노출되지 않는다.

---

### Edge Cases

- 인증 토큰이 만료·오서명이면: 체인 1단계에서 전원 실패 → 스캔 0건, 비용 0원. 리허설(동시 5)이 이 사고를 50원 이내로 잡는 안전망이다.
- 외부 LLM 호출 한도(429)가 동시 145 에서 걸리면: 실패로 집계하되 앱 결함과 분리해 기록한다 — 재실행하지 않는다(비용 상한).
- 스캔 응답이 매우 느려도(수십 초) 실행이 끊기지 않아야 한다 — 회차당 최대 대기 시간을 두고 넘으면 실패로 마감한다.
- 실행 대상은 dev 환경뿐이다. prod 호스트로는 어떤 회차도 실행하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 테스트 이미지는 부하 실행 전에 실제 업로드 체인(presign→PUT→complete)으로 **1회 시드**해 objectKey를 확보하고, 부하 루프는 각 가상 사용자마다 **스캔 티켓 발급 + 스캔 요청** 두 단계만 수행하며 시드한 이미지 키를 재사용해야 한다.
- **FR-002**: 전체 테스트에서 스캔 요청(비용 발생 단계) 총량은 200건을 넘지 않아야 하며, 회차 구성은 5(리허설) → 50 → 145 로 한다.
- **FR-003**: 가상 사용자 수만큼만 스캔이 나가야 한다 — 반복·재시도로 건수가 늘어나서는 안 된다.
- **FR-004**: 티켓 발급에 실패한 가상 사용자는 스캔 요청을 보내지 않아야 한다.
- **FR-011**: 시드 objectKey는 스크립트가 산출해 실행 파라미터(SCAN_IMAGE_PATH)로 주입하며, 저장소에 커밋하지 않는다. 같은 키로 회차를 반복 실행할 수 있어야 한다(반복 가능 구조).
- **FR-005**: 테스트 계정은 스캔 횟수 제한이 없는 상태여야 하며, 소셜 로그인 없이 인증할 수 있어야 한다(dev 한정 수단, 운영 환경 금지).
- **FR-006**: 각 회차 결과로 스캔 응답 시간 분포(최소 p95)와 실패율이 산출돼야 한다.
- **FR-007**: 실행 창 동안 스캔 외 API 응답 시간과 서버 자원(커넥션 풀·힙·호스트 CPU)이 모니터링에서 판독 가능해야 한다.
- **FR-008**: 외부 LLM 한도 초과(429)로 인한 실패는 앱 오류와 분리해 집계해야 한다.
- **FR-009**: 결과 수치·병목 판정은 지식 위키에, 테스트 스크립트는 저장소에 남겨야 한다.
- **FR-010**: 테스트용 더미 계정을 만들었다면 종료 후 비활성화해야 한다.

### Key Entities

- **테스트 계정**: 스캔 무제한 상태의 dev 회원. 기존 계정 재사용이 우선, 없으면 식별 가능한 더미 1건.
- **회차(run)**: 동시 사용자 수(5/50/145)·시각·p95·실패율·비고(429 여부)를 갖는 실행 단위.
- **시드 이미지**: 스캔 대상 실제 메뉴판 사진 1장을 1회 업로드해 얻은 objectKey. 전 회차·전 가상 사용자가 이 **하나의 키를 재사용**한다(재업로드 없음).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 스캔 요청 총량 ≤ 200건, 외부 비용 ≤ 약 2,000원으로 테스트가 완료된다.
- **SC-002**: 동시 5 리허설에서 체인 성공률 100% 를 확인한 뒤에만 본 회차가 실행된다.
- **SC-003**: 동시 50 과 145 두 지점의 스캔 p95·실패율이 산출돼 동시성 증가에 따른 변화를 비교할 수 있다.
- **SC-004**: 동시 스캔 실행 창에서 타 API p95 변화(영향 유무)가 판정된다.
- **SC-005**: 병목 지점(앱 자원/DB/외부 LLM 한도)이 하나 이상의 근거 지표와 함께 기록된다.
- **SC-006**: prod 환경으로 나간 테스트 요청이 0건이다.

## Assumptions

- 비용 단가(스캔 1건 ≈ 10원)는 개략치다 — 상한 관리 목적이며 정산 목적이 아니다.
- 429(외부 한도)가 대량 발생해도 예산을 남겨 재실행하지 않는다 — 그 자체가 "현 동시성에서 외부 한도가 병목" 이라는 결과다.
- 리허설 5건도 200건 예산에 포함된다(5+50+145=200).
- 모니터링(KB-379~381)이 dev 에 이미 동작 중이다.
- 스캔은 imagePath의 소유/완료를 검증하지 않으므로(코드 확인) 시드 키 재사용이 안전하다. 이 전제가 깨지면(향후 검증 추가) 시드 방식을 재설계한다.
- 시드 이미지는 공개 URL로 비전 추출기(외부 LLM)가 fetch 가능해야 한다 — 실제 업로드 체인 시드가 이를 보장한다.
