# Feature Specification: 앱 내부 메트릭 노출 — api·batch 가 컨테이너 안 상태를 수집기에 제공하고 배치도 헬스체크로 관리된다

**Feature Branch**: `kb-380-prometheus-metrics-endpoint`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "380" — Jira KB-380: api·batch 에 Prometheus 메트릭 엔드포인트 노출 + batch ECS 헬스체크 추가 (에픽 KB-379 모니터링 — Grafana·CloudWatch 관측 체계의 첫 태스크)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 운영자가 api 앱의 "컨테이너 안" 상태를 수집 가능한 형태로 얻는다 (Priority: P1)

운영자는 지금 클라우드 콘솔에서 컨테이너의 CPU·메모리 사용률(컨테이너 밖)까지는 볼 수 있지만, 그 안에서 앱이 어떤 상태인지 — 메모리가 힙 압박인지 GC 가 못 따라오는지, DB 커넥션 풀이 고갈됐는지, 어느 엔드포인트가 느려지고 에러를 내는지 — 는 알 수 없다. 이 기능이 끝나면 api 앱이 그 내부 상태(JVM 메모리·GC·스레드, DB 커넥션 풀, 엔드포인트별 요청 수·지연·상태코드)를 표준 메트릭 형식으로 같은 호스트의 수집기에 제공한다.

**Why this priority**: 에픽 전체(홈서버 Grafana 에서 dev·prod 총괄)의 출발점이다. 앱이 내놓지 않으면 뒤의 수집기(Alloy)·대시보드가 볼 게 없다.

**Independent Test**: dev 에 배포한 뒤 해당 인스턴스 안에서 api 컨테이너의 메트릭 제공 지점을 직접 읽어, JVM 메모리·DB 커넥션 풀·HTTP 요청 메트릭이 앱 식별 태그(`kbap-api`)와 함께 나오면 통과. 수집기 없이도 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** api 앱이 기동 중이다, **When** 같은 호스트에서 메트릭 제공 지점을 읽으면, **Then** JVM 메모리·GC·스레드, DB 커넥션 풀(활성/대기), HTTP 요청(엔드포인트·상태코드별 횟수와 지연 분포) 메트릭이 표준 텍스트 형식으로 응답된다.
2. **Given** 메트릭 응답을 받았다, **When** 어느 앱의 것인지 확인하면, **Then** 모든 메트릭에 앱 식별 태그(`application=kbap-api`)가 붙어 있어 batch 와 구분된다.
3. **Given** api 앱에 요청이 몇 건 들어갔다, **When** 다시 메트릭을 읽으면, **Then** 해당 엔드포인트의 요청 횟수가 그만큼 증가해 있다.

---

### User Story 2 - batch 앱도 같은 메트릭을 내놓고, 죽으면 자동으로 교체된다 (Priority: P2)

batch 앱은 상시 기동 + HTTP 잡 트리거 구조라 진짜 장애는 "죽었다"가 아니라 "조용히 안 돌았다 / 오래 걸렸다 / 반쯤 실패했다"다. 이건 로그로는 못 잡고 잡 실행 메트릭(잡·스텝별 성공/실패 횟수·소요 시간)으로만 잡힌다. 또 현재 batch 컨테이너에는 헬스체크가 없어 프로세스만 살아 있으면 앱이 응답 불능이어도 오케스트레이터가 교체하지 않는다.

**Why this priority**: api 와 같은 작업이라 같은 PR 에 담기지만, prod 배치는 현재 0대라 dev 에서만 즉시 효과가 있다. api(P1) 다음.

**Independent Test**: dev batch 컨테이너의 메트릭 제공 지점을 읽어 JVM 메트릭과 배치 잡 메트릭이 `application=kbap-batch` 태그로 나오고, 오케스트레이터 콘솔에서 batch 태스크의 헬스 상태가 HEALTHY 로 표시되면 통과.

**Acceptance Scenarios**:

1. **Given** batch 앱이 기동 중이다, **When** 같은 호스트에서 메트릭 제공 지점을 읽으면, **Then** JVM 메트릭과 함께 배치 잡 실행 메트릭(잡 이름·상태별 횟수와 소요 시간)이 `application=kbap-batch` 태그로 응답된다.
2. **Given** batch 잡을 하나 트리거해 완료됐다, **When** 메트릭을 읽으면, **Then** 그 잡 이름으로 완료 1건과 소요 시간이 기록돼 있다.
3. **Given** batch 태스크가 기동됐다, **When** 오케스트레이터가 헬스 상태를 판정하면, **Then** 기동 완료 후 HEALTHY 로 표시된다.
4. **Given** batch 앱이 응답 불능 상태가 됐다(프로세스는 살아 있음), **When** 헬스체크가 연속 실패하면, **Then** 오케스트레이터가 컨테이너를 교체한다.

---

### User Story 3 - 새 버전을 배포해도 batch 헬스체크 설정이 유지된다 (Priority: P2)

이미지 태그만 바꾸는 일상 배포(CI)가 컨테이너 정의를 복제해 새 리비전을 만드는 구조다. 이번에 추가하는 batch 헬스체크가 그 복제에 포함되지 않으면 첫 배포 직후 사라진다.

**Why this priority**: 한 번 켜지고 다음 배포에 꺼지는 헬스체크는 없는 것보다 나쁘다(있다고 믿게 만든다).

**Independent Test**: 이 기능 적용 후 CI 로 batch 를 한 번 더 배포(이미지 태그만 변경)하고, 새 리비전에도 헬스체크가 그대로 있으며 태스크가 HEALTHY 면 통과.

**Acceptance Scenarios**:

1. **Given** 이 기능이 적용된 상태, **When** CI 로 이미지 태그만 바꿔 batch 를 배포하면, **Then** 새 컨테이너 정의 리비전에 헬스체크가 그대로 포함되고 배포 후 태스크가 HEALTHY 다.

---

### Edge Cases

- 메트릭 제공 지점이 느리거나 실패하면 서비스 트래픽에 영향이 있나? → 메트릭 응답 실패는 수집 공백일 뿐 장애가 아니다. 응답 생성은 요청 시점 스냅샷이라 서비스 요청 처리와 락을 공유하지 않는다.
- 배치 잡이 실행 중일 때 헬스체크가 실패하면? → 헬스체크는 앱 응답성만 보므로 잡 실행 자체가 헬스를 떨어뜨리지 않아야 한다. 진짜 응답 불능이면 교체되는 게 맞고, 실행 중이던 잡은 배치 앱의 기존 실행 이력에 실패로 남는다.
- 기동 직후 헬스체크가 너무 일찍 시작해 정상 기동 중인 컨테이너를 죽이면? → 기동 유예 시간을 두어 앱이 뜨는 동안은 판정하지 않는다(api 는 이미 150초 유예 — batch 도 같은 원칙).
- 로컬 개발(docker-compose·bootRun)에서는? → `localhost:8080/actuator/prometheus` 가 그대로 열린다. 추가 설정 없음.
- 오토스케일로 태스크가 늘면? → 새 태스크도 같은 컨테이너 정의라 자동으로 메트릭을 제공한다(수집기가 찾는 건 다음 태스크 KB-381 의 몫).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: api·batch 앱은 각각 자기 내부 상태를 표준 메트릭 텍스트 형식으로 제공하는 지점을 가져야 한다. 최소 포함: JVM 메모리(힙/논힙)·GC·스레드, DB 커넥션 풀(활성/대기/최대), HTTP 요청(엔드포인트·메서드·상태코드별 횟수와 지연 분포). batch 는 추가로 배치 잡·스텝 실행(잡 이름·상태별 횟수와 소요 시간).
- **FR-002**: 모든 메트릭에는 앱 식별 태그가 붙어야 한다 — api 는 `application=kbap-api`, batch 는 `application=kbap-batch`.
- **FR-003**: 관리 경로(메트릭·헬스)는 기존 서비스 포트(8080)와 기본 경로(`/actuator`)를 그대로 쓰고, 앱은 접근 제어를 하지 않는다. 공개 진입점(로드밸런서)에서의 차단은 별도 후속 작업(로드밸런서 규칙 — 이 기능 범위 밖)이다.
- **FR-004**: 서비스 포트·컨테이너 정의의 포트·인스턴스 방화벽·로드밸런서 규칙을 이 기능을 위해 추가·변경해서는 안 된다.
- **FR-005**: batch 컨테이너에 헬스체크가 정의되어야 한다 — 앱이 준비되면 HEALTHY, 응답 불능이 연속되면 컨테이너 교체. 기동 유예 시간을 두어 정상 기동 중 오판을 막는다.
- **FR-006**: api 의 기존 헬스체크(로드밸런서·컨테이너)는 경로·포트 변경 없이 계속 통과해야 한다(이 기능이 헬스 응답 형식·경로를 바꾸지 않는다).
- **FR-007**: batch 헬스체크 정의는 인프라 코드에 반영되어야 하며, CI 의 이미지 태그 교체 배포 후 새 리비전에도 그대로 유지되어야 한다.
- **FR-008**: 메트릭 제공 지점의 지연·실패는 서비스 응답에 영향을 주지 않아야 한다.

### Key Entities *(include if feature involves data)*

- **메트릭 제공 지점**: 앱마다 하나. 표준 텍스트 형식으로 현재 스냅샷을 응답한다. 저장하지 않는다 — 읽는 순간의 값이며 누적은 수집기(다음 태스크)의 몫이다.
- **앱 식별 태그**: `application` 한 개, 값은 앱 이름. dev/prod 환경 구분은 이 기능이 아니라 수집기가 붙인다.
- **컨테이너 헬스 상태**: 오케스트레이터가 판정하는 HEALTHY/UNHEALTHY. 새 데이터가 아니라 기존 오케스트레이터 상태를 batch 에도 쓰기 시작하는 것.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: dev 배포 후 api·batch 각 컨테이너에서 메트릭 제공 지점을 읽으면 FR-001 의 메트릭군이 100% 포함돼 있고 `application` 태그가 붙어 있다.
- **SC-002**: 이 기능으로 인한 인스턴스 방화벽·로드밸런서·api 컨테이너 정의 변경 수 0 (배포 전후 인프라 diff 는 batch 컨테이너 헬스체크뿐).
- **SC-003**: batch 태스크가 오케스트레이터 콘솔에서 HEALTHY 로 표시되고, 응답 불능 유도 시 5분 이내 자동 교체된다.
- **SC-004**: 이 기능 적용 후 CI 배포 1회를 거쳐도 batch 헬스체크가 유지된다(리비전에 정의 존재 + HEALTHY).
- **SC-005**: 기존 서비스 응답 시간(로드밸런서 p95)과 로드밸런서 healthy 타깃 수가 적용 전후로 변하지 않는다(p95 ±5% 이내, healthy 수 동일).
- **SC-006**: 이 기능으로 인한 월 추가 인프라 비용이 0 이다(새 리소스 없음 — 앱 설정·코드와 batch 컨테이너 정의 변경뿐).

## Assumptions

- 수집기(Grafana Alloy)와 홈서버 연동은 다음 태스크(KB-381)이며, 이 기능은 "앱이 내놓는 것"까지만 책임진다. 수집기는 같은 호스트의 컨테이너 네트워크로 서비스 포트(8080)에 직접 접근한다.
- **공개 차단은 이 기능 범위 밖이다.** api 앱이 아닌 경로(관리 경로 포함)의 외부 접근은 로드밸런서 규칙으로 후속 차단한다(사용자 결정, 2026-08-27). 그 전까지 공개 도메인에서 `/actuator/prometheus`·`/actuator/health` 가 읽힌다 — 노출되는 것은 내부 지표(엔드포인트 목록·요청량·힙·커넥션 풀 상태)이며 자격증명·개인정보는 아니다. 후속 작업 시 참고: 로드밸런서는 원문 경로를 매칭하고 앱 서버는 정규화·디코딩 후 라우팅하므로 접두 패턴 하나(`/actuator/*`)로는 `//actuator/…` 류가 새어 들어갈 수 있다 — 허용 목록(`/api/*` 만 통과) 방식이 안전하다.
- 관리 경로는 기존 서비스 포트(8080)와 기본 경로(`/actuator`)를 그대로 쓴다 — 포트 분리·경로 변경을 하지 않는다.
- 메트릭 형식은 Prometheus 텍스트 노출 형식이다. 앱 프레임워크가 기본 제공하는 메트릭군(JVM·커넥션풀·HTTP·Spring Batch)만 쓰고 커스텀 메트릭은 만들지 않는다.
- 헬스·메트릭 외의 관리 기능(환경 정보·설정 덤프·스레드 덤프 등)은 노출하지 않는다.
- 컨테이너 정의는 인프라 코드가 초기 리비전을 만들고 CI 가 이미지만 교체해 복제하므로, batch 헬스체크를 실제 리비전으로 반영하는 절차(인프라 코드가 컨테이너 정의 변경을 무시하도록 설정돼 있음)를 구현 계획에서 정한다. api 컨테이너 정의는 변경하지 않는다.
- prod 배치는 현재 0대라 batch 관련 항목은 dev 에서 검증한다. prod 적용은 별도 판단(배포 창).
- **자동화 테스트를 작성하지 않는다**(사용자 결정, 2026-08-27 — 프레임워크 기본 기능의 설정 노출이라 불필요). 검증은 로컬 `bootRun` + curl 과 dev 배포 확인으로 한다.
