# Feature Specification: 리뷰 작성 자격 검증(스캔 이력) + 음식 상세 리뷰 자격 표시

**Feature Branch**: `kb-369-review-eligibility`

**Created**: 2026-08-21

**Status**: Draft

**Input**: User description: "리뷰 작성·수정 시 자격 검증 — 요청 회원의 스캔 이력에 없는 foodId 면 전용 에러 코드로 거절, 수정은 재검증 안 함. 음식 상세 응답에 리뷰 작성 자격 boolean(reviewEligible) 추가 — 비회원은 false."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔하지 않은 음식의 리뷰 작성 거절 (Priority: P1)

회원이 리뷰를 작성하려는 음식이 본인의 스캔 이력에 없으면, 작성 요청이 전용 오류로 거절된다. 앱은 이 오류를 받아 "이 음식을 스캔하면 리뷰를 쓸 수 있어요" 안내로 분기한다. 직접 먹어 본(= 메뉴판을 스캔한) 음식만 리뷰할 수 있게 하여 리뷰 신뢰도를 지키는 것이 목적이다.

**Why this priority**: 자격 없는 리뷰가 쌓이면 리뷰 데이터 전체의 신뢰가 무너진다. 이 기능의 존재 이유.

**Independent Test**: 스캔 이력이 없는 회원으로 리뷰 작성을 호출해 전용 오류를 받고, 같은 음식을 스캔한 회원으로는 작성이 성공하는 것으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 회원이 음식 A 를 스캔한 적이 없다, **When** 음식 A 에 리뷰 작성을 요청하면, **Then** 전용 오류 코드(신규 1개)로 거절되고 리뷰는 저장되지 않는다.
2. **Given** 회원이 음식 A 를 스캔해 매칭에 성공한 이력이 있다, **When** 음식 A 에 리뷰 작성을 요청하면, **Then** 기존과 동일하게 작성이 성공한다.
3. **Given** 다른 회원 B 만 음식 A 를 스캔했다, **When** 회원 C 가 음식 A 에 리뷰 작성을 요청하면, **Then** 거절된다 — 자격은 요청 회원 본인의 이력 기준이다.
4. **Given** 회원이 음식 A 리뷰를 이미 작성했다, **When** 그 리뷰를 수정하면, **Then** 스캔 이력과 무관하게 수정이 성공한다 — 수정은 자격을 재검증하지 않는다.

---

### User Story 2 - 음식 상세에서 리뷰 작성 가능 여부 표시 (Priority: P1)

회원이 음식 상세 화면에 진입하면, 응답에 "이 음식에 리뷰를 쓸 수 있는가" 를 나타내는 값(reviewEligible)이 함께 내려온다. 앱은 이 값으로 리뷰 작성 버튼을 게이트해, 글을 다 쓰고 나서야 거절당하는 UX 를 막는다. 비회원 조회에서는 이 값이 항상 false 다(작성 자체가 불가하므로).

**Why this priority**: 사후 거절(US1)만 있으면 사용자가 작성 노력을 낭비한다. 진입 시점 안내가 있어야 US1 이 완결된 UX 가 된다.

**Independent Test**: 스캔 이력이 있는 회원·없는 회원·비회원 세 갈래로 음식 상세를 조회해 각각 true / false / false 를 받는 것으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 회원이 음식 A 를 스캔한 이력이 있다, **When** 음식 A 상세를 조회하면, **Then** reviewEligible 이 true 다.
2. **Given** 회원이 음식 A 를 스캔한 적이 없다, **When** 음식 A 상세를 조회하면, **Then** reviewEligible 이 false 다.
3. **Given** 비회원이다, **When** 음식 A 상세를 조회하면, **Then** reviewEligible 이 false 다 — bookmarked 와 같은 축(비회원 판별은 overallRiskStatus 가 담당).

---

### Edge Cases

- **매칭 실패 스캔**: 스캔했지만 음식 매칭에 실패한 이력(음식 미확정)은 자격으로 인정하지 않는다. 미등록이었다가 나중에 등록된 음식은 재스캔 전까지 자격이 없다 — 이 경계를 앱 안내 문구와 맞춘다.
- **음식 자체의 오류가 우선**: 존재하지 않거나 공개 전 상태의 음식이면 기존의 음식 오류로 응답한다 — 자격 오류는 음식이 유효할 때만 판정한다.
- **삭제된 스캔 이력**: 삭제 처리된 스캔 이력은 자격으로 인정하지 않는다(활성 이력만).
- **스캔 크레딧 해금 루프와의 상호작용**: "리뷰 작성 시 스캔 무제한 해금"(KB-345) 흐름에서, 크레딧을 소진한 회원도 이미 스캔했던 음식에는 리뷰를 쓸 수 있으므로 해금 경로는 막히지 않는다.
- **리뷰 삭제 후 재작성**: 자격(스캔 이력)이 있는 한 기존 재작성 규칙을 그대로 따른다 — 이 기능이 새 제약을 더하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 리뷰 작성 요청은 요청 회원의 활성 스캔 이력에 해당 음식이 존재할 때만 성공해야 한다(매칭 성공 이력 기준).
- **FR-002**: 자격이 없는 작성 요청은 이 사유 전용의 신규 오류 코드 1개로 거절되어야 하며, 앱이 이 코드만으로 "스캔 유도" 안내를 분기할 수 있어야 한다.
- **FR-003**: 리뷰 수정 요청은 스캔 이력 자격을 재검증하지 않아야 한다(본인 리뷰 여부 검증은 기존대로 유지).
- **FR-004**: 음식 상세 응답에 리뷰 작성 자격 값(reviewEligible)이 포함되어야 한다 — 회원: true/false, 비회원: 항상 false.
- **FR-005**: 상세 응답의 자격 값과 작성 요청의 자격 판정은 같은 기준을 사용해야 한다 — 상세에서 true 를 받은 회원의 작성이 자격 사유로 거절되는 불일치가 없어야 한다.
- **FR-006**: 음식이 존재하지 않거나 공개 전 상태인 경우 기존 음식 오류 응답이 자격 오류보다 우선해야 한다.

### Key Entities

- **스캔 이력**: 회원이 메뉴판을 스캔한 기록. 매칭에 성공한 이력만 특정 음식과 연결되며, 이 연결이 리뷰 작성 자격의 근거다.
- **리뷰**: 회원이 음식에 남기는 평가. 이번 기능으로 "작성 시점에 스캔 이력 필요" 제약이 추가된다(수정·삭제는 불변).
- **음식 상세 응답**: 음식 정보 + 조회자 맥락 값(북마크 여부·위험도 등). 여기에 리뷰 작성 자격 값이 추가된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 스캔 이력이 없는 회원의 리뷰 작성 시도는 100% 거절되고, 거절 응답만으로 앱이 스캔 유도 안내를 표시할 수 있다.
- **SC-002**: 회원은 음식 상세 진입 시점에 리뷰 작성 가능 여부를 즉시 알 수 있다 — 글을 작성한 뒤 자격 사유로 거절당하는 경우가 0 이 된다(상세 true ↔ 작성 성공 정합).
- **SC-003**: 기존 리뷰 수정·삭제 흐름은 이 기능 배포 전후로 동작 변화가 없다.
- **SC-004**: 비회원의 음식 상세 조회는 기존과 동일하게 성공하며, 새 필드는 false 로만 나타난다.

## Assumptions

- 자격 기준은 "본인의 활성 스캔 이력 중 매칭에 성공해 음식과 연결된 기록의 존재"다. 주문 이력·북마크 등 다른 행위는 자격으로 인정하지 않는다(향후 확장 여지는 필드명을 자격 의미(reviewEligible)로 지어 흡수).
- 기존에 이미 작성된 리뷰(자격 검증 도입 전)는 소급 검증하지 않는다 — 조회·수정·삭제 모두 기존대로 동작한다.
- 필드명 reviewEligible 은 서버 응답 컨벤션(is 접두 없는 Boolean)에 맞춘 제안으로, 클라이언트 확인 후 확정한다.
- 관리자 흐름은 범위 밖이다.
