## 배경

푸시 발송 파이프라인(KB-468)은 "어떤 회원들에게 어떤 유형을" 넣어 주면 기기별 설정·동의·토큰 유효성을 판정해 기기마다 알림함 행을 만들고 Expo 로 보내는 공용 부품이다. 지금 이 파이프라인을 부르는 곳은 관리자 테스트 발송뿐이다. 이 기능은 첫 **스케줄 발송자**다 — 매일 점심 시간대에 스캔 제안(광고성 유형 `SCAN_SUGGESTION`)을 광고성 동의자에게 보낸다.

Jira 본문의 대상 조건은 작성 당시(비회원 발송 가능·회원 단위 설정) 기준이라 낡았다. 그 뒤 머지된 두 변경으로 조건이 바뀌었다:

- **#260 (KB-543, 2026-09-10)**: 알림은 회원만 받는다. 게스트 동의·게스트 기기 발송 경로가 사라졌다 → Jira 의 "게스트 쿼리" 는 폐기.
- **#261 (KB-544, 2026-09-11)**: 알림 설정이 (회원, 기기) 단위가 됐고 소식 토글 `news` 가 생겼다. 스캔 제안은 이 기기 토글이 켜진 기기에만 간다. 광고성 수신 동의는 회원 단위 원장 그대로다.

따라서 **이 기능은 대상 규칙을 새로 정의하지 않는다.** 파이프라인의 대상 판정(기기 소식 토글 + 회원 동의 두 종류 v≥2 + 유효 토큰)을 그대로 쓰고, 배치가 새로 소유하는 것은 세 가지뿐이다 — **후보 회원 수집**, **발송 허용 시간대 하드 가드**, **하루 1회 상한**.

## 대상 규칙 (확정 — #260·#261 반영)

한 기기가 스캔 제안을 받으려면 아래를 **모두** 만족해야 한다. 앞 세 줄은 파이프라인이 이미 판정하고, 마지막 줄만 이 기능이 더한다.


| 조건                                                   | 판정 주체 | 근거                       |
| ---------------------------------------------------- | ----- | ------------------------ |
| 기기가 활성 회원에 연결돼 있고 푸시 토큰이 무효화되지 않았다                   | 파이프라인 | #260 — 회원 전용, 무효 토큰 제외   |
| 그 (회원, 기기) 설정 행이 있고 **소식(`news`) 토글이 켜져 있다**         | 파이프라인 | #261 — 설정 행 없는 기기는 대상 아님 |
| 회원의 광고성 동의 두 종류(개인정보·수신)가 **모두 열려 있고 문구 버전 ≥ 요구 버전** | 파이프라인 | KB-466·KB-468            |
| 같은 기기에 **이번 슬롯(12:00~18:00 / 18:00~다음 날 12:00 KST)에 이미 스캔 제안이 만들어지지 않았다** | 이 기능 | 슬롯당 1회 상한 |


- 회원 한 명이 기기 두 대를 쓰고 둘 다 소식이 켜져 있으면 두 기기 모두 받는다(기기당 1건, 회원당 1건이 아니다 — #261 의 기기 단위 설계와 일치).
- 게스트(회원 미연결 기기)는 어떤 조건에서도 대상이 아니다.

## 잡 구조와 Expo 발송 제약 (2차 입력 반영)

잡은 **두 단계**로 나뉜다. 단계 경계는 "대상을 확정하는 일" 과 "외부로 내보내는 일" 을 분리해, 외부 발송이 DB 트랜잭션 밖에서 일어나고 실행 결과를 단계별로 셀 수 있게 하기 위함이다.

| 단계 | 하는 일 | 결과 |
|------|---------|------|
| 1. 대상 확정 | 후보 회원 수집(한 번의 조회) → 이번 슬롯에 이미 받은 회원 제외 → 회원 id 목록을 버퍼에 적재 | 후보 수, 회원 id 목록 |
| 2. 청크 발송 | 후보 회원을 묶음 단위로 **공용 발송 부품**에 넘긴다. 부품이 기기별 알림함·발송 이력을 만들고, Expo 제약에 맞는 청크로 잘라 **동시에 여러 요청**을 보내되 초당 상한을 지키고, 결과를 발송 이력에 반영 | 성공·실패 건수 |

**Expo 발송 제약 (공식 문서 2026-09-15 확인)** — 발송 단계가 지켜야 하는 수치:

| 항목 | 값 | 이 기능의 적용 |
|------|-----|---------------|
| 요청 1건당 메시지 수 | 최대 **100** | 청크 크기 100 |
| 동시 연결 | 공식 SDK 는 **최대 6개 연결**을 동시에 열고 요청을 자동 throttle | 청크 요청을 최대 6개까지 동시에 보낸다(설정값). 동시성은 지연을 줄일 뿐 초당 600건 상한을 넘기지 않는다 |
| 처리량 상한 | 프로젝트당 **초당 600건** | 청크 요청의 **시작 시각**을 초당 6개 이하로 배분한다(동시 요청이 있어도 같은 상한) |
| 알림 1건 페이로드 | 최대 **4096 바이트** | 현재 데이터(`type`·`notificationId`)는 100 바이트 미만 — 초과 불가 |
| 네트워크 오류·429(Too Many Requests)·5xx | **일시 실패** — 지수 백오프 후 재시도 권고 | 그 청크 요청을 지수 백오프(1s → 2s → 4s)로 최대 3회 재시도한다. 끝내 실패하면 그 청크를 실패로 기록하고 다음 청크로 넘어간다 |
| 400(페이로드 오류)·자격 증명 오류 | **영구 실패** — 재시도해도 해결되지 않음 | 재시도 없이 그 청크를 즉시 실패로 기록한다 |
| 200 응답 안의 건별 error 티켓(`DeviceNotRegistered` 등) | 메시지 단위 실패 | 재시도 대상이 아니다 — 사유만 기록 |
| `DeviceNotRegistered` 티켓 | 재등록 전까지 그 토큰으로 보내지 말 것 | 이 기능은 실패 사유만 기록한다. 토큰 무효화는 영수증 정리(KB-473) 몫 |
| 영수증(receipt) | 티켓 id 최대 1000개씩, 발송 약 15분 뒤 조회, 24시간 뒤 소멸 | 범위 밖(KB-473) |
| `channelId` | 기기에 존재하는 채널이어야 표시됨 | 광고성 유형 → `news`(FE 가 만든 채널) |
| `priority` | `default`·`normal`·`high` | 기존 `high` 유지 |
| `ttl` | 생략 시 4주 | 스캔 제안은 당일 점심에만 의미 있으므로 짧은 만료를 둔다(Assumptions 참조) |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 점심 시간대에 동의한 기기로 스캔 제안이 온다 (Priority: P1)

소식 알림을 켜고 마케팅 수신에 동의한 회원은 매일 12:00 에 "점심 먹을 때 스캔해보세요", 18:00 에 "저녁 메뉴, 스캔해보세요" 스캔 제안 푸시를 그 기기 언어로 받는다. 제목 앞에는 `(광고)`, 본문 끝에는 수신거부 안내가 붙어 있고, 알림을 누르면 스캔 화면으로 간다. 같은 알림이 알림함에도 남는다.

**Why this priority**: 이 기능의 존재 이유. 첫 스케줄 발송이며 스캔 유입을 만드는 프로모션 채널이다.

**Independent Test**: 조건을 만족하는 기기와 만족하지 않는 기기를 섞어 시드한 뒤 잡을 한 번 실행하면, 만족하는 기기에만 알림함 행과 발송 이력이 생기고 나머지엔 아무것도 생기지 않는다.

**Acceptance Scenarios**:

1. **Given** 소식 토글이 켜진 기기와 두 종류 동의(v≥2)가 열린 회원, **When** 점심 스케줄 잡이 실행되면, **Then** 그 기기에 `SCAN_SUGGESTION` 알림함 행 1건과 발송 이력 1건이 생기고 푸시 데이터에는 `type=SCAN_SUGGESTION` 과 그 알림함 행의 `notificationId` 가 실린다.
2. **Given** 회원 한 명이 기기 A·B 를 쓰고 둘 다 소식이 켜진 상태, **When** 잡이 실행되면, **Then** A·B 각각 1건씩 받는다.
3. **Given** 소식 토글이 꺼진 기기 / 설정 행이 없는 기기 / 동의가 철회됐거나 버전이 낮은 회원의 기기 / 토큰이 무효화된 기기 / 회원 미연결(게스트) 기기, **When** 잡이 실행되면, **Then** 이들에게는 알림함 행도 발송 이력도 생기지 않는다.
4. **Given** 한국어 기기와 영어 기기, **When** 잡이 실행되면, **Then** 각 기기 언어의 문구로 렌더되고 광고 표기·수신거부 안내가 붙는다.

### User Story 2 - 같은 기기에는 슬롯당 한 번만 온다 (Priority: P1)

하루 두 슬롯(12:00·18:00 KST)에 각각 한 번씩 받는다. 같은 슬롯 안에서 잡이 두 번 돌아도(수동 트리거, 실패 후 재실행) 이미 이번 슬롯에 스캔 제안이 만들어진 기기에는 다시 보내지 않는다.

**Why this priority**: 광고성 푸시의 과다 발송은 수신거부·앱 삭제로 직결된다. 재실행이 안전해야 운영이 잡을 자유롭게 다시 돌릴 수 있다.

**Independent Test**: 같은 슬롯에서 잡을 두 번 실행하면 두 번째는 발송 0건이다. 18:00 슬롯과 다음 날 12:00 슬롯에는 다시 1건씩 보낸다.

**Acceptance Scenarios**:

1. **Given** 이번 슬롯에 이미 스캔 제안 알림함 행이 있는 기기, **When** 잡이 다시 실행되면, **Then** 그 기기는 대상에서 빠진다.
2. **Given** 12:00 슬롯에 받은 기기, **When** 18:00 슬롯·다음 날 12:00 슬롯에 잡이 실행되면, **Then** 각각 다시 받는다.
3. **Given** 이번 슬롯 발송이 Expo 오류로 실패한 기기, **When** 결과가 기록되면, **Then** 그 기기의 알림함 행은 소프트 삭제되고 발송 이력만 FAILED 로 남는다(받지 못한 알림이 알림함에 보이지 않는다). 그 회원의 다른 기기가 성공했으면 회원은 같은 슬롯에 다시 대상이 되지 않고, 전 기기가 실패했으면 같은 슬롯 재실행에서 다시 시도된다.

### User Story 3 - Android 에서 광고성 알림이 소식 채널로 헤드업된다 (Priority: P2)

FE(KB-498, PR #149) 는 Android 알림 채널을 "K-Bap 소식"(`news`, 높은 중요도)으로 만들고 `default` 채널은 만들지 않는다. 광고성 유형(`SCAN_SUGGESTION`·`NEWS`·`MEAL_TIME`)의 Expo 메시지는 `channelId=news` 로 나가야 헤드업되고, 사용자가 기기 설정에서 광고성만 따로 끌 수 있다.

**Why this priority**: 채널이 틀리면 Android 에서 알림이 조용히 폴백 채널로 떨어져 사실상 안 보인다. 발송 자체는 되므로 P1 은 아니다.

**Independent Test**: 스캔 제안 발송 시 Expo 로 나가는 메시지의 `channelId` 가 `news` 다.

**Acceptance Scenarios**:

1. **Given** 스캔 제안 발송, **When** Expo 메시지가 만들어지면, **Then** `channelId` 는 `news` 다.
2. **Given** 유형→채널 매핑은 발송 파이프라인 한 곳에 있다, **When** 다른 광고성 유형(`NEWS`·`MEAL_TIME`)을 보내도, **Then** 같은 규칙으로 `news` 채널이다(트리거는 유형만 넘긴다).

---

### User Story 4 - 운영이 스케줄을 조정하고 실행 결과를 본다 (Priority: P2)

발송 시각은 12:00·18:00 KST 로 코드에 고정한다(환경변수 없음 — 2026-09-15 결정). 잡은 상시 기동된 배치 앱의 스케줄로만 돌고(부팅 시 자동 실행 없음), 기존 수동 트리거 경로로도 같은 잡을 돌릴 수 있다. 실행이 끝나면 후보 수·발송 성공·실패 건수와 시간대 밖 건너뜀 여부를 로그와 메트릭으로 남긴다.

**Why this priority**: 운영 가시성과 조정 가능성. 없으면 "안 왔어요" 문의에 답할 수 없다.

**Independent Test**: 잡 실행 후 로그에 후보·성공·실패 건수가 남고, 수동 트리거로 같은 잡을 이름으로 부를 수 있다.

**Acceptance Scenarios**:

1. **Given** 배치 앱이 떠 있으면, **When** 12:00 과 18:00 KST 가 되면, **Then** 잡이 기동한다.
2. **Given** 배치 앱 부팅, **When** 부팅이 끝나도, **Then** 잡은 실행되지 않는다.
3. **Given** 잡 실행 완료, **When** 로그·메트릭을 보면, **Then** 후보 회원 수·발송 성공·실패 건수가 남는다.
4. **Given** 같은 잡이 이미 실행 중이면, **When** 스케줄 시각이 되면, **Then** 중복 실행하지 않고 건너뛴다.

### User Story 5 - 대상이 많아져도 Expo 제약 안에서 전부 보낸다 (Priority: P2)

대상이 수천 기기로 늘어도 잡은 Expo 가 허용하는 요청 크기(100건)와 처리량(초당 600건)을 넘기지 않고 순서대로 전부 보낸다. 한 청크가 실패해도 나머지 청크는 계속 나가고, 실행이 끝나면 청크 수·성공·실패가 남는다.

**Why this priority**: 지금 회원 수백 규모에서는 한두 청크로 끝나지만, 제약을 넘기는 순간 429 로 청크 전체가 실패한다. 첫 스케줄 발송자이므로 제약을 여기서 못 박는다.

**Independent Test**: 250개 대상 기기를 시드하면 Expo 로 3회(100·100·50) 요청이 나가고, 중간 청크의 응답을 오류로 꾸며도 나머지 두 청크의 기기는 SENT, 실패 청크의 기기만 FAILED 다.

**Acceptance Scenarios**:

1. **Given** 대상 250기기, **When** 발송 단계가 돌면, **Then** 요청은 100·100·50 세 번이고 각 기기의 발송 이력이 요청 순서대로 결과를 받는다.
2. **Given** 대상 1,200기기, **When** 발송 단계가 돌면, **Then** 어느 1초 구간에서도 600건을 넘겨 보내지 않는다.
3. **Given** 두 번째 청크가 429 또는 5xx 로 실패, **When** 발송 단계가 돌면, **Then** 그 청크의 기기만 FAILED(사유 기록)이고 첫·세 번째 청크는 SENT 이며 잡은 정상 종료한다.
4. **Given** 대상 0기기, **When** 발송 단계가 돌면, **Then** Expo 를 한 번도 부르지 않는다.
5. **Given** Expo 응답이 청크당 일정 지연을 갖는 상황에서 대상 1,200기기(청크 12개), **When** 발송 단계가 돌면, **Then** 청크 요청이 최대 6개까지 동시에 나가 총 소요가 청크 수 × 응답 지연보다 짧고, 요청 시작 시각은 여전히 초당 6개를 넘지 않는다.

### User Story 6 - Expo 가 잠깐 흔들려도 발송이 유실되지 않는다 (Priority: P2)

Expo 서비스가 일시적으로 응답하지 않거나(네트워크 오류·5xx) 요청을 너무 많이 받았다고 답하면(429), 그 청크 요청을 잠시 기다렸다가 다시 보낸다. 기다리는 시간은 회차마다 두 배로 늘어나고, 정해진 횟수 안에 성공하면 정상 발송으로 기록된다. 반대로 페이로드 오류(400)나 자격 증명 오류처럼 다시 보내도 같은 결과인 실패는 즉시 실패로 기록하고 재시도하지 않는다.

**Why this priority**: Expo 문서가 명시한 운영 규칙. 점심 1회 발송은 다시 돌릴 기회가 없어(하루 1회 상한) 수 초짜리 흔들림으로 하루치 발송을 잃으면 안 된다.

**Independent Test**: 어느 청크의 Expo 응답을 두 번 5xx 로 꾸민 뒤 세 번째에 정상 응답하면 그 청크의 기기가 전부 SENT 이고 요청은 세 번 나간다. 400 응답이면 요청은 한 번뿐이고 청크 전체가 FAILED 다.

**Acceptance Scenarios**:

1. **Given** 어느 청크의 첫 두 응답이 5xx(또는 429·네트워크 오류)이고 세 번째가 정상, **When** 발송 단계가 돌면, **Then** 그 청크의 기기는 전부 SENT 이고 그 청크 요청은 3회 나간다.
2. **Given** 어느 청크가 재시도 한도까지 계속 5xx, **When** 발송 단계가 돌면, **Then** 그 청크의 기기는 전부 FAILED(사유에 마지막 오류)이고 나머지 청크는 정상 발송된다.
3. **Given** 어느 청크가 400 으로 거부됨, **When** 발송 단계가 돌면, **Then** 재시도 없이 요청 1회로 그 청크가 FAILED 다.
4. **Given** 재시도 대기는 회차마다 두 배(1초 → 2초 → 4초), **When** 세 번 재시도하면, **Then** 총 대기는 약 7초이며 다음 청크 발송은 재시도가 끝난 뒤 이어진다.

---

### Edge Cases

- 후보가 0명(배포 직후 기기 설정 행이 없는 과도기 — #261 의 알려진 상태)이면 Expo 를 부르지 않고 정상 종료한다.
- Expo 가 일부 청크에서 실패하면(재시도 소진 또는 영구 실패) 그 기기들의 발송 이력만 FAILED 로 남고 나머지는 계속 간다. FAILED 로 남은 건은 같은 날 다시 보내지 않는다(하루 1회 상한).
- KST 날짜 경계: "오늘" 은 KST 달력일이다. 23:59 KST 에 만들어진 알림은 다음 날 00:00 KST 부터 상한에서 풀린다(어차피 시간대 밖이라 실발송은 08:00 이후).
- 같은 회원의 열린 동의 행이 종류당 두 개 이상이어도 기기당 1건이다.
- 탈퇴·로그아웃으로 회원 연결이 풀린 기기는 대상이 아니다(#260·#261 생명주기 그대로).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 매일 12:00 KST 에 점심 스캔 제안 잡을, 18:00 KST 에 저녁 스캔 제안 잡을 기동해야 한다(잡 2개, 스케줄 메서드 2개). 두 시각은 코드 상수이며 환경변수·설정으로 바꾸지 않는다(2026-09-15 결정).
- **FR-002**: 잡은 대상 규칙 표의 네 조건을 모두 만족하는 기기에만 `SCAN_SUGGESTION` 알림을 보내야 한다. 앞 세 조건의 판정은 기존 발송 파이프라인의 규칙을 그대로 써야 하며 이 기능이 별도 판정 로직을 복제하지 않는다.
- **FR-003**: 잡은 후보 회원을 한 번의 조회로 모아야 하며, 후보 조회는 "소식 토글이 켜진 기기 설정을 가진 회원" 을 넘지 않는 범위여야 한다(전 회원 순회 금지). 탈퇴 회원은 기기 연결 해제·설정 삭제로 자동 제외되며, 회원 상태를 따로 조인하지 않는다.
- **FR-004**: (삭제 — 2026-09-15 결정) 별도 발송 시간대 가드를 두지 않는다. 발송 시각은 cron(12:00·18:00 KST)이 정하고, 수동 트리거는 시각과 무관하게 보낸다.
- **FR-005**: 잡은 같은 (회원, 기기)에 같은 슬롯(12:00~18:00, 18:00~다음 날 12:00 KST) 안에 스캔 제안 알림을 두 번 만들지 않아야 한다. 판정 기준은 "이번 슬롯 시작 이후 만들어진 활성 `SCAN_SUGGESTION` 알림함 행의 존재" 다. 발송 실패로 소프트 삭제된 행은 세지 않으므로 전 기기가 실패한 회원은 재실행에서 다시 시도된다.
- **FR-006**: 발송되는 푸시 데이터에는 `type=SCAN_SUGGESTION` 과 알림함 행의 `notificationId` 가 실려야 한다(기존 FE 데이터 계약 그대로, 추가 필드 없음).
- **FR-007**: 광고성 유형(`SCAN_SUGGESTION`·`NEWS`·`MEAL_TIME`)의 Expo 메시지는 `channelId=news` 로 나가야 하며, 유형→채널 매핑은 발송 경로 한 곳에서만 한다. 비광고성 유형의 채널 값은 이 기능에서 바꾸지 않는다.
- **FR-008**: 외부 발송(Expo 호출)은 DB 트랜잭션 밖에서 해야 한다 — 준비(알림함·발송 이력 저장) → 발송 → 결과 기록의 기존 3단 구조를 따른다.
- **FR-009**: 잡은 배치 앱 부팅 시 자동 실행되지 않아야 하며, 기존 수동 트리거 경로로 이름을 불러 실행할 수 있어야 한다.
- **FR-010**: 잡은 같은 인스턴스에서 앞선 실행이 끝나지 않았으면 이번 스케줄을 건너뛴다. 배치 앱은 1대만 돌므로 인스턴스 간 분산 잠금은 두지 않는다.
- **FR-011**: 잡 실행마다 후보 회원 수·이번 슬롯 제외 회원 수·발송 성공 건수·실패 건수를 로그와 메트릭으로 남겨야 한다.
- **FR-012**: 잡의 문구는 점심·저녁 슬롯별 스캔 제안 템플릿(기기 언어별 10종 × 2슬롯)을 쓰며, 문구는 발송 템플릿 한 곳에서만 정의해 교체가 한 파일 수정으로 끝나야 한다. 광고 표기·수신거부 안내("프로필 > 알림 설정" 경로)는 기존 렌더 규칙이 붙인다. 슬롯 문구가 없는 유형은 기본 템플릿으로 떨어진다.
- **FR-013**: 잡은 「대상 확정」과 「청크 발송」 두 단계로 구성돼야 한다. 대상 확정 단계는 후보 회원을 **한 번의 조회 흐름**으로 확정해 발송 대기 목록을 만들고, 청크 발송 단계는 그 목록을 묶음 단위로 공용 발송 부품에 넘긴다.
- **FR-014**: 청크 발송은 요청 1건당 최대 100 메시지, 프로젝트당 초당 600 메시지를 넘기지 않아야 한다. 청크 요청은 설정된 동시성(기본 6)까지 병렬로 보내되, 요청 시작 시각을 초당 6개 이하로 배분해 처리량 상한을 지킨다. 동시성·초당 상한은 실행 환경 설정으로 바꿀 수 있다.
- **FR-015**: 청크 하나의 최종 실패(재시도 소진·영구 실패·응답 파싱 실패)는 그 청크의 발송 이력을 FAILED 로 남기고 해당 알림함 행을 소프트 삭제한 뒤 다음 청크로 이어져야 하며, 잡은 실패 청크가 있어도 정상 종료하고 성공·실패 건수를 기록한다.
- **FR-016**: 스캔 제안 푸시는 당일 점심에만 의미가 있으므로 만료(ttl)를 두어, 기기가 오프라인이었다가 저녁이나 다음 날 켜졌을 때 뒤늦게 표시되지 않아야 한다.
- **FR-017**: 청크 요청의 일시 실패(네트워크 오류·429·5xx)는 지수 백오프(초기 1초, 회차마다 2배)로 최대 3회 재시도한 뒤에만 실패로 확정해야 한다. 영구 실패(400 등 그 밖의 4xx)는 재시도 없이 즉시 실패로 확정한다. 200 응답 안의 건별 error 티켓은 재시도하지 않는다. 재시도 횟수·초기 대기·배수는 실행 환경 설정으로 바꿀 수 있다.
- **FR-018**: 푸시 발송의 실제 수행(기기별 알림함·발송 이력 생성, 청크 분할, 동시 발송, 초당 상한, 재시도, 결과 기록)은 **공용 발송 부품 하나**가 소유해야 한다. 스캔 제안 배치·관리자 테스트 발송·앞으로의 식사시간/리뷰 리마인더/활동 알림은 모두 이 부품에 **알림 유형과 대상 회원(및 유형별 인자)** 만 넘기고, 발송 방식을 각자 구현하지 않는다.

### Key Entities *(include if data involves)*

- **알림(Notification)**: 발송 시점에 (회원, 기기)마다 기기 언어로 하나씩 저장되는 알림함 행. 이 기능에서는 `SCAN_SUGGESTION` 유형이며 생성일(KST)이 하루 1회 상한의 기준이다.
- **발송 이력(NotificationDispatch)**: 알림 1건의 Expo 발송 결과(SENT/FAILED·티켓·오류). 이 기능은 읽지 않고 파이프라인이 쓴다.
- **기기(NotificationDevice)**: 설치 id·푸시 토큰·언어·회원 연결·토큰 무효 시각. 후보 판정의 단위.
- **기기별 알림 설정(NotificationSetting)**: (회원, 기기) 행의 `news` 토글이 스캔 제안 수신 여부다.
- **광고성 수신 동의(NotificationConsent)**: 회원 단위 원장. 개인정보·수신 두 종류가 모두 열려 있고 버전 ≥ 2 여야 광고성 대상이다.

스키마 변경은 없다.

## Assumptions

- **발송 시각은 12:00·18:00 KST 하드코딩**이다(2026-09-15 결정 — 환경변수 없음). 둘 다 주간이라 야간 광고 동의 이슈가 없다.
- **후보 범위는 대상 규칙 표의 조건을 만족하는 기기 전부**이며 매일 보낸다(2026-09-15 결정). 활동 기반 제외(오늘 스캔한 회원 제외·미접속 회원만 등)는 두지 않는다 — 수신 조절은 소식 토글과 동의 철회로 한다.
- **상한은 슬롯당 1회, 단위는 기기**다(회원이 아니다). 슬롯은 12:00~18:00 과 18:00~다음 날 12:00 KST. 알림함 행이 기기 단위이고(#261) 파이프라인이 기기마다 1건을 만들므로, 기기 두 대인 회원은 기기마다 1건씩 받는다. 판정은 "이번 슬롯 시작 이후 스캔 제안 알림이 있는 회원" 을 후보에서 빼는 회원 단위 차집합으로 하며, 이는 기기 단위 규칙의 상위 집합이다(한 실행에서 한 회원의 기기들은 함께 만들어진다).
- **하드 가드의 시각 기준**은 실행 시작 시각이며 시간대는 KST 고정이다(기기에 timezone 이 없다 — Jira). 국가별 시간대 스케줄은 범위 밖.
- **야간 별도 동의는 보류**(위키 결정). **08~21 KST 코드 가드는 두지 않는다**(2026-09-15 결정) — 발송 시각은 cron 상수(12:00·18:00)가 정하므로 조건절이 중복이고, 수동 트리거는 운영자 책임으로 언제든 보낸다.
- **비광고성 유형의 Android 채널**은 이 기능에서 정하지 않는다. FE 가 `default` 채널을 만들지 않는다는 결정은 광고성 유형 매핑만 요구하며, 활동 알림 채널명은 FE 확인 후 별도 태스크다.
- **분산 잠금(ShedLock)은 두지 않는다**(2026-09-15 결정). 배치 앱은 1대만 돌아 스케줄러 동시성 문제가 없고, 같은 인스턴스 안의 중복은 기존 실행 중 가드가 막는다. Jira DoD 의 ShedLock 문구는 이 결정으로 대체한다.
- **재시도는 청크 요청 단위·일시 실패에만**(2026-09-15 결정 — KB-468 의 "필요해지면 어댑터 안에서만" 을 실행). 기본값 최대 3회 재시도(총 4회 시도), 대기 1초 → 2초 → 4초. 재시도는 발송 어댑터 한 곳에서 하므로 관리자 테스트 발송 등 다른 호출자도 같은 규칙을 탄다. **건별 재전송·토큰 무효화는 없다** — 200 응답 안의 error 티켓은 사유만 기록하고 토큰 정리는 영수증(KB-473) 몫. FAILED 건은 하루 1회 상한 때문에 같은 날 다시 보내지 않는다.
- **Expo 제약 수치의 출처**는 공식 문서(https://docs.expo.dev/push-notifications/sending-notifications/, 2026-09-15 확인)다 — 요청당 100건, 초당 600건, 페이로드 4096 바이트, 영수증 1000개·15분·24시간. 기존 어댑터는 100건 청크만 지키고 처리량 간격은 없어 이 기능이 발송 단계에서 간격을 둔다.
- **동시 발송은 청크 요청 단위, 기본 동시성 6**(Expo 공식 SDK 의 최대 연결 수와 같다). 동시성은 Expo 왕복 지연을 겹쳐 전체 소요를 줄일 뿐 초당 600건 상한을 넘기지 않는다 — 대상이 아주 많으면 소요 시간의 하한은 `기기 수 ÷ 600` 초다(10만 기기 ≈ 3분). 그 이상 빨라야 한다면 Expo 에 상한 상향을 요청하거나 대상을 시간대로 나눈다(범위 밖).
- **초당 상한은 앱 인스턴스별로 지킨다.** api 2대와 batch 1대가 동시에 대량 발송하면 합이 600 을 넘을 수 있으나, api 발송은 건별 이벤트(수 건)이고 대량 발송은 배치뿐이라 감수한다.
- **제네릭은 쓰지 않는다.** 세 전송(스캔 제안·식사시간·활동/리뷰)이 다른 것은 알림 유형·인자·data 값뿐이고 발송 절차는 같다. 알림 유형은 열거형 매개변수로 넘기며, 유형별 문구·채널·광고 표기는 유형에서 파생된다. 타입 매개변수로 얻을 컴파일타임 이득이 없다(호출자마다 다른 페이로드 클래스와 그 등록소가 추가로 필요해 코드만 늘어난다). 유형별 인자의 컴파일타임 검증이 필요해지면 그때 sealed 요청 타입을 검토한다.
- **만료(ttl)** 는 스캔 제안이 점심 맥락이므로 발송 시각으로부터 3시간으로 둔다(Expo 기본 4주 대신). 다른 유형의 ttl 은 바꾸지 않는다.
- **단계 구성**은 사용자 지시(2차 입력)대로 "대상 확정(한 번의 조회) → 청크 발송" 두 단계다. 대상 확정 단계는 회원 id 만 확정하고, 발송 단계가 회원 묶음마다 공용 발송 부품을 불러 알림함 저장·청크·동시 발송·기록을 맡긴다 — KB-468 의 준비 → 발송 → 기록 3단은 부품 안에 그대로 있다.
- **배포 직후 과도기**: #261 로 기기 설정 행이 없는 기기는 대상이 아니므로, FE 기기 단위 설정 릴리스가 나가기 전에는 후보 0건으로 정상 종료한다. 스케줄을 운영에서 켜는 시점은 FE 릴리스 이후다.
- **의존**: KB-468 발송 파이프라인(머지)·KB-466/KB-544 기기별 알림 설정(머지)·KB-543 회원 전용화(머지). 모두 develop 에 있다.
- **발송 실패 건은 알림함에서 지운다**(2026-09-16 결정). `record` 가 FAILED 로 판정한 건의 `notification` 행을 소프트 삭제한다 — 서버 알림함으로 전환됐을 때 "받은 적 없는 알림"이 보이지 않게. 발송 이력(`notification_dispatch`)은 사유와 함께 남는다.
- **범위 밖**: 스키마 변경, 문구 신규 작성, 국가별 시간대, 활동 기반 타깃팅, 건별(메시지) 재전송, 영수증 조회·토큰 무효화(KB-473), 관리자 화면.
