# Feature Specification: 스캔 2.0 응답 구조 통일 — similarFood 제거·항목 imageRef 신설

**Feature Branch**: `kb-343-remove-similar-food`

**Created**: 2026-08-19

**Status**: Draft

**Input**: User description: "KB-343 — 스캔 2.0 에서 DB miss 음식을 유사 음식으로 대체하지 않고 1.0 처럼 스캔 결과를 그대로 반환. similarFood 응답 필드 제거." (당초의 "디폴트 이미지 대체"는 스캔 응답에 이미지 필드가 원래 없음이 확인되어 폐기 — 2026-08-19)

## 맥락

- 스캔 2.0 은 등록 음식과 매칭되지 않은(DB miss) 메뉴에 **유사 음식 대체 결과(similarFood)** 를 동봉한다 — 이름·설명·이미지를 벡터 검색으로 찾은 비슷한 음식으로 채워 "정확 매칭 아님" 주의 표시와 함께 보여주는 UX 였다.
- 이 대체 UX 를 폐기한다: 비매칭 메뉴는 **1.0 과 동일하게 스캔 추출 결과 그대로**(정제된 메뉴명·가격·위험도 UNKNOWN) 내려준다. 다른 음식을 대신 보여주지 않는다.
- **(재개정 2026-08-19)** v2 항목에 음식 사진 URL(`imageRef`)을 신설한다 — 스캔 카드에 사진을 바로 노출하기 위함. 매칭 음식은 대표 이미지, 비매칭·대표 이미지 없는 음식은 **디폴트 음식 이미지**(`images/webp/default_miss_food/food_not_found.png`, S3 업로드 완료)로 항상 값이 내려간다. v1 은 동결 계약이라 제외.
- 유사 음식 검색을 지탱하던 벡터 인프라(READY 음식 임베딩 적재·문서 DB 검색)는 **존치**한다 — 이번엔 스캔의 검색 호출·응답 조립만 걷어낸다(명확화 확정, 2026-08-19).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 비매칭 메뉴가 유사 음식 없이 그대로 내려온다 (Priority: P1)

스캔 2.0 사용자가 등록되지 않은 메뉴를 스캔하면, 비슷한 다른 음식이 아니라 스캔에서 읽어낸 그 메뉴 자체(이름·가격)가 그대로 보인다.

**Why this priority**: 이 기능의 전부 — 응답 구조 통일과 오인 유발 UX(다른 음식 표시) 제거.

**Independent Test**: 등록/미등록 메뉴가 섞인 메뉴판 스캔 → 미등록 항목에 similarFood 없음, 등록 항목은 종전과 동일.

**Acceptance Scenarios**:

1. **Given** 등록 음식과 매칭되지 않는 메뉴, **When** 스캔 2.0 을 실행하면, **Then** 응답 항목에 similarFood 필드가 존재하지 않고, 메뉴명·가격·riskLevel(UNKNOWN)은 종전 그대로다.
2. **Given** 등록 음식과 매칭된 메뉴, **When** 스캔 2.0 을 실행하면, **Then** 매칭 판정·위험도·기피성분 겹침 등 기존 동작이 변하지 않고, imageRef 에 음식 대표 이미지 URL 이 담긴다.
4. **Given** 비매칭 메뉴(또는 대표 이미지 없는 매칭 음식), **When** 스캔 2.0 을 실행하면, **Then** imageRef 에 디폴트 음식 이미지 URL 이 담긴다 — 항상 값이 있다.
3. **Given** 벡터 검색이 가능한 환경, **When** 비매칭 메뉴를 스캔해도, **Then** 유사 음식 검색을 시도하지 않는다(응답 지연·비용 제거).

---

### Edge Cases

- 스캔 1.0 은? — 무변경(원래 similarFood 가 없다).
- degraded(LLM 미가동) 응답은? — 종전 규칙 그대로.
- 벡터 인프라는? — 존치. 스캔의 검색 호출이 사라져 검색 경로는 미사용 상태가 되지만, 적재 파이프라인(KB-328)은 향후 재사용을 위해 유지한다. 운영 정리(DocumentDB 축소 등)는 별도 이슈.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 스캔 2.0 응답 항목에서 similarFood 필드를 제거한다 — 비매칭 메뉴에 다른 음식 정보를 대체 표시하지 않는다.
- **FR-002**: 비매칭 메뉴는 1.0 과 동일한 원칙(스캔 추출 결과 그대로 — 정제 메뉴명·가격·위험도 UNKNOWN)으로 내려간다.
- **FR-003**: 비매칭 메뉴에 대해 유사 음식 검색(임베딩·벡터 조회)을 수행하지 않는다.
- **FR-004**: 매칭 메뉴의 판정·표시(위험도·기피성분 겹침·이름 규칙)와 스캔 1.0 계약은 변경하지 않는다.
- **FR-007**: v2 항목에 음식 사진 URL(imageRef)을 신설한다 — 매칭은 대표 이미지, 비매칭·이미지 부재는 디폴트 음식 이미지로 항상 값 제공(재개정 2026-08-19).
- **FR-005**: 벡터 적재 파이프라인(READY 음식 임베딩 동기화)은 변경하지 않는다 — 스캔 쪽 검색 소비 코드만 제거한다.
- **FR-006**: 이 변경은 스캔 2.0 클라이언트와 조율된 계약 변경으로, 기존 2.0 매핑에서 즉시 적용한다(버전 증가 없음).

### Key Entities

- **스캔 2.0 응답 항목**: similarFood 필드가 사라지고 imageRef(항상 값)가 생긴다. 나머지 필드 불변.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 비매칭 메뉴 응답에 다른 음식 정보가 일절 나타나지 않는다 — similarFood 잔존 0건.
- **SC-002**: 유사 음식 검색 제거로 비매칭 항목 처리에서 외부 검색 호출이 0건이 된다.
- **SC-003**: 매칭 메뉴·스캔 1.0 의 기존 시나리오 회귀 0건.

## Assumptions

- similarFood 필드 제거는 스캔 2.0 클라이언트와 조율된 파괴적 계약 변경이다 — 2.0 매핑 안에서 즉시 적용(무버전).
- 디폴트 음식 이미지 자산은 S3 에 업로드 완료(`images/webp/default_miss_food/food_not_found.png`) — 경로는 서버 상수로 고정.
- 스캔 이력 저장·크레딧 등 스캔의 다른 동작은 무관·불변이다.
