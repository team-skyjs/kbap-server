# Feature Specification: 푸시 토큰 등록 API 와 로그인·로그아웃·탈퇴 시 기기-회원 연결

**Feature Branch**: `kb-465-push-token-api`

**Created**: 2026-09-07

**Status**: Draft

**Input**: User description: "465 워크트리ㄱ" — Jira KB-465 「[BE] 푸시 토큰 API PUT/DELETE /api/notifications/tokens + 로그인·로그아웃·탈퇴 시 토큰-회원 연결」. 에픽 KB-463 푸시 알림의 두 번째 태스크, KB-464(저장 기반, PR #246) 위에 쌓인다.

## 배경

KB-464 로 서버는 기기 토큰·광고성 동의 원장을 저장할 자리를 갖췄지만, 앱이 그 자리에 값을 넣을 통로가 없다. 앱의 토큰 전송 함수는 지금 아무것도 하지 않는 빈 함수다. 이 기능은 그 통로 하나(토큰 등록)를 열고, 이미 있는 로그인·로그아웃·탈퇴 흐름에 "이 기기가 누구 것인지" 를 갱신하는 처리를 끼워 넣는다.

이 API 가 개발 서버에 올라가는 순간부터 두 가지가 가능해진다. 실기기 토큰이 서버에 쌓여 후속 발송 배치(KB-468 이후)를 진짜 기기로 검증할 수 있고, 앱 팀은 API 문서를 보고 병렬로 연동을 시작한다. 에픽에서 1순위인 이유다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 기기가 자기 푸시 토큰을 서버에 등록·갱신한다 (Priority: P1)

앱은 알림 권한을 얻고 토큰을 발급받을 때마다, 그리고 앱을 켤 때마다 토큰을 서버에 보낸다. 서버는 기기 설치 식별자(모든 요청에 실리는 헤더) 기준으로 기기당 기록 하나를 유지한다. 처음 보는 기기면 새로 만들고, 이미 있는 기기면 토큰·플랫폼·언어를 덮어쓴다. 예전에 "이 토큰은 더 이상 유효하지 않다" 고 표시됐던 기기라도 새 토큰이 들어오면 다시 유효한 기기가 된다. 게스트도 회원도 같은 요청을 보내며, 회원이 보내면 그 기기가 그 회원에게 연결된다.

**Why this priority**: 토큰이 서버에 없으면 이 에픽의 어떤 것도 동작하지 않는다. 앱 팀의 병렬 작업 시작점이기도 하다.

**Independent Test**: 게스트로 토큰을 등록 → 같은 기기 식별자로 다른 토큰을 등록 → 기록이 하나뿐이고 토큰만 바뀜 → 같은 기기 식별자로 회원 인증을 붙여 등록 → 그 기록에 회원이 연결됨. 이 API 하나로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 서버가 모르는 기기, **When** 게스트가 토큰·플랫폼·언어를 보내면, **Then** 그 기기 식별자로 기록 하나가 생기고 회원 연결은 비어 있으며 응답은 성공이다.
2. **Given** 이미 등록된 기기, **When** 같은 기기 식별자로 다른 토큰을 보내면, **Then** 기록 수는 그대로이고 토큰·플랫폼·언어가 새 값으로 바뀐다.
3. **Given** 토큰이 무효로 표시된 기기, **When** 새 토큰을 보내면, **Then** 무효 표시가 사라지고 발송 대상으로 다시 잡힌다.
4. **Given** 게스트로 등록된 기기, **When** 로그인한 회원이 같은 기기 식별자로 토큰을 보내면, **Then** 그 기록에 회원이 연결되고 기록 수는 늘지 않는다.
5. **Given** 어떤 요청이든, **When** 기기 식별자 헤더가 없으면, **Then** 요청은 거절되고(클라이언트 오류) 아무 기록도 바뀌지 않는다.
6. **Given** 어떤 요청이든, **When** 토큰이 비어 있거나 플랫폼이 허용 값(iOS·Android)이 아니면, **Then** 요청은 거절된다.

### User Story 2 - 게스트가 토큰 등록과 함께 광고성 수신 동의를 켜고 끈다 (Priority: P2)

게스트는 설정 화면이 없어(설정 API 는 회원 전용, KB-466) 광고성 알림 동의를 토큰 등록 요청에 실어 보낸다. 동의를 켜면 "이 기기가 이 문구 버전에 이 시각에 동의했다" 는 기록이 원장에 남고, 끄면 그 기기의 열린 동의가 철회 시각과 함께 닫힌다. 같은 버전으로 다시 켜는 요청은 아무것도 바꾸지 않고, 문구 버전이 올라간 뒤 켜면 이전 동의를 닫고 새 동의를 남긴다. 회원이 보낸 요청의 동의 값은 무시한다 — 회원 동의는 설정 화면(KB-466)이 정본이다.

**Why this priority**: 게스트에게 점심 스캔 제안 같은 광고성 알림을 보내려면 법적 동의 기록이 있어야 한다. 토큰 등록 없이는 의미가 없어 P1 뒤에 온다.

**Independent Test**: 게스트가 동의 on 으로 등록 → 원장에 열린 기록 하나 → 같은 버전으로 다시 on → 변화 없음 → 다른 버전으로 on → 이전 기록 닫히고 새 기록 → off → 열린 기록 없음. 회원 요청에 동의 값을 실어도 원장 무변화.

**Acceptance Scenarios**:

1. **Given** 동의 기록이 없는 게스트 기기, **When** 동의 on 과 문구 버전을 실어 등록하면, **Then** 그 기기의 열린 동의 기록이 하나 생기고 버전·동의 시각이 남는다.
2. **Given** 같은 버전의 열린 동의가 있는 게스트 기기, **When** 같은 버전으로 다시 on 을 보내면, **Then** 기록 수·시각이 바뀌지 않는다.
3. **Given** 버전 1 의 열린 동의가 있는 게스트 기기, **When** 버전 2 로 on 을 보내면, **Then** 버전 1 기록은 철회 시각이 찍혀 닫히고 버전 2 의 열린 기록이 새로 생긴다.
4. **Given** 열린 동의가 있는 게스트 기기, **When** off 를 보내면, **Then** 열린 기록은 철회 시각이 찍혀 닫히고 기록 자체는 남는다.
5. **Given** 열린 동의가 없는 게스트 기기, **When** off 를 보내면, **Then** 아무 변화 없이 성공한다.
6. **Given** 회원 인증이 붙은 요청, **When** 동의 값을 실어 보내면, **Then** 원장은 바뀌지 않고 토큰 등록만 처리된다.
7. **Given** 게스트 요청, **When** 동의 on 인데 문구 버전이 없거나 정수가 아니면, **Then** 요청은 거절된다.

### User Story 3 - 로그인·로그아웃·탈퇴가 기기 연결과 동의를 이어받거나 정리한다 (Priority: P2)

게스트로 쓰던 기기에서 로그인하면 그 기기는 그 회원의 것이 되고, 게스트로 남긴 광고성 동의는 회원에게 이어진다 — 단, 회원에게 이미 유효한 동의가 있으면 게스트 동의는 닫는다(정본은 하나). 로그아웃하면 기기와 회원의 연결만 끊고 동의 원장은 건드리지 않는다. 탈퇴하면 기기 연결을 끊고 그 회원의 열린 동의를 전부 닫되 기록은 보존한다.

**Why this priority**: 이 처리가 없으면 로그아웃한 기기에 회원 알림이 계속 가고, 탈퇴한 회원에게 광고성 알림이 나간다. 토큰 등록(P1)과 독립적으로 기존 인증 흐름에서 검증할 수 있다.

**Independent Test**: 게스트 기기에 토큰·동의를 심어 두고 로그인 → 기기에 회원 연결, 게스트 동의가 회원 동의로 바뀌되 최초 동의 시각 유지 → 로그아웃 → 연결만 해제, 동의 그대로 → 탈퇴 → 연결 해제 + 열린 동의 전부 닫힘.

**Acceptance Scenarios**:

1. **Given** 게스트 기기(토큰 등록됨, 열린 게스트 동의 있음)와 유효한 동의가 없는 회원, **When** 그 기기에서 로그인하면, **Then** 기기는 회원에 연결되고 게스트 동의는 회원 동의로 바뀌며 동의 시각은 원래 값이 유지된다.
2. **Given** 게스트 기기(열린 게스트 동의 있음)와 이미 유효한 동의가 있는 회원, **When** 그 기기에서 로그인하면, **Then** 기기는 회원에 연결되고 게스트 동의는 철회 시각이 찍혀 닫히며 회원의 기존 동의는 그대로다.
3. **Given** 서버가 모르는 기기, **When** 로그인하면, **Then** 로그인은 정상 성공하고 기기·동의 기록은 생기지 않는다(토큰 등록은 별도 요청).
4. **Given** 회원에 연결된 기기, **When** 그 기기에서 로그아웃하면, **Then** 기기의 회원 연결만 비워지고 동의 원장은 한 행도 바뀌지 않는다.
5. **Given** 회원에 연결된 기기가 두 대이고 열린 회원 동의가 있음, **When** 회원이 탈퇴하면, **Then** 두 기기 모두 회원 연결이 비워지고 열린 동의는 전부 철회 시각이 찍혀 닫히며 기록은 남는다.
6. **Given** 로그인·로그아웃 요청에 기기 식별자 헤더가 없음, **When** 요청하면, **Then** 인증 처리는 기존과 동일하게 성공하고 기기 연결 처리만 생략된다.

---

### Edge Cases

- 게스트 동의가 재시도 등으로 한 기기에 두 건 이상 열려 있을 때 로그인하면 전부 회원에게 이어지거나(회원 동의 없음) 전부 닫힌다(회원 동의 있음). 한 건만 처리하고 남기지 않는다.
- 회원 A 가 연결된 기기에서 회원 B 가 로그인하면 기기 연결은 B 로 바뀐다. 기기의 게스트 동의는 이미 없으므로(A 로그인 때 처리됨) 동의 이어받기는 발생하지 않는다.
- 같은 기기 식별자로 최초 등록 요청이 동시에 두 번 오면 한쪽은 유일성 제약으로 실패할 수 있다. 앱은 다음 실행에서 다시 보내므로 감수한다(KB-464 R2 결정).
- 회원 인증이 붙은 요청이 다른 기기 식별자로 여러 번 오면 기기마다 기록이 생기고 전부 그 회원에 연결된다(회원 1 : 기기 N).
- 탈퇴 후 같은 기기에서 게스트로 토큰을 보내면 기존 기기 기록이 게스트 상태로 갱신된다(기록 삭제 없음).
- 언어 코드는 검증하지 않고 받은 그대로 보관한다(KB-464 결정).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 기기가 토큰·플랫폼·언어를 보내 자신을 등록하는 단일 진입점을 제공해야 하며, 인증 없이도(게스트) 인증이 있어도(회원) 같은 진입점으로 받는다.
- **FR-002**: 시스템은 요청의 기기 설치 식별자 헤더를 기기 기록의 유일 키로 사용해야 하며, 헤더가 없으면 클라이언트 오류로 거절하고 아무 기록도 바꾸지 않는다.
- **FR-003**: 시스템은 같은 기기 식별자의 재등록을 새 기록 생성이 아니라 기존 기록 갱신으로 처리해야 하며, 갱신 시 토큰 무효 표시를 해제한다.
- **FR-004**: 시스템은 기기 기록을 어떤 사건에서도 삭제하지 않아야 한다(로그아웃·탈퇴·토큰 무효 포함). 상태 변경만 허용한다.
- **FR-005**: 시스템은 회원 인증이 붙은 등록 요청에서 그 기기를 요청 회원에 연결해야 한다.
- **FR-006**: 시스템은 게스트 등록 요청의 광고성 동의 값(on/off + 문구 버전)을 동의 원장에 반영해야 한다: on 이면 같은 버전의 열린 동의가 없을 때만 새 동의를 남기고(다른 버전의 열린 동의는 닫는다), off 면 그 기기의 열린 게스트 동의를 전부 닫는다.
- **FR-007**: 시스템은 회원 인증이 붙은 등록 요청의 동의 값을 무시해야 한다.
- **FR-008**: 시스템은 동의 on 요청에 문구 버전(양의 정수)이 없으면 거절해야 한다.
- **FR-009**: 시스템은 로그인 시 요청 기기(헤더 기기 식별자로 등록된 기록이 있을 때)를 로그인 회원에 연결해야 한다.
- **FR-010**: 시스템은 로그인 시 회원에게 열린 동의가 없으면 그 기기의 열린 게스트 동의 전부를 회원 동의로 바꾸되 원래 동의 시각을 보존해야 하고, 회원에게 열린 동의가 있으면 그 기기의 열린 게스트 동의 전부를 닫아야 한다.
- **FR-011**: 시스템은 로그아웃 시 요청 기기의 회원 연결만 해제해야 하며 동의 원장은 변경하지 않는다.
- **FR-012**: 시스템은 탈퇴 시 그 회원에 연결된 모든 기기의 회원 연결을 해제하고, 그 회원의 열린 동의를 전부 닫되 기록은 보존해야 한다.
- **FR-013**: 로그인·로그아웃·탈퇴에서 기기 처리가 불가능한 경우(헤더 없음·미등록 기기)에도 인증 처리 자체는 기존과 동일하게 성공해야 한다.
- **FR-014**: 시스템은 이 API 를 기존 API 규약(공통 응답 봉투·버전 헤더 필수·보호 경로 등록)에 맞춰 노출하고 API 문서에 실어야 한다.
- **FR-015**: 시스템은 동의 원장의 어떤 행도 삭제하지 않아야 한다(탈퇴 포함).
- **FR-016**: 푸시 토큰 관리(토큰 등록 API, 로그인·로그아웃·탈퇴의 기기-회원 연결 처리)는 **API 버전 1.1 이상에서만** 동작해야 한다. 버전 1.0 의 로그인·회원가입·로그아웃·탈퇴 동작은 어떤 변화도 없어야 하고, 1.0 으로 토큰 등록을 요청하면 클라이언트 오류(404 — 이 버전에 존재하지 않는 API)로 거절한다. (2026-09-07 추가)

### Key Entities *(include if data involves)*

- **기기 기록(NotificationDevice)**: 설치 식별자로 유일한 기기 한 대. 토큰·플랫폼·언어·연결 회원(선택)·토큰 무효 시각. KB-464 에서 정의됨, 이 기능은 읽고 갱신만 한다.
- **광고성 동의 기록(NotificationConsent)**: 동의 1회의 생애. 주체(회원 또는 기기)·문구 버전·동의 시각·철회 시각(비어 있으면 유효). KB-464 정의. 이 기능은 게스트 동의 생성·철회·회원 인수·탈퇴 일괄 철회를 수행한다.
- **회원(Member)**: 기존 엔티티. 이 기능은 id 로만 참조한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 앱 팀이 개발 서버의 API 문서만 보고 토큰 전송 연동을 시작할 수 있다(추가 질의 없이 요청·응답 형식이 문서에 완결).
- **SC-002**: 실기기 한 대로 앱 설치 → 토큰 등록 → 로그인 → 로그아웃 → 재로그인을 수행했을 때 서버의 기기 기록은 시종 1건이고 연결 회원이 각 단계에 맞게 바뀐다.
- **SC-003**: 게스트 동의 on → 로그인 → 탈퇴 시나리오 후 동의 원장에는 삭제된 행 없이 동의·인수·철회 이력이 시각과 함께 남아 있어, 특정 회원이 언제 무엇에 동의했는지 원장만으로 답할 수 있다.
- **SC-004**: 로그아웃한 기기와 탈퇴한 회원은 이후 발송 대상 조회(KB-464 정의 질의)에서 회원 알림 대상으로 잡히지 않는다.
- **SC-005**: 위 시나리오 전부가 자동화 통합 테스트로 재현되어 회귀 시 실패한다.

## Assumptions

- 기기 설치 식별자는 앱이 모든 요청에 `X-Installation-Id` 헤더로 보내는 재설치 후에도 유지되는 UUID 다(KB-464 가정 계승). 현재 서버는 이 헤더를 어디서도 읽지 않으므로 이 기능이 첫 소비자다.
- 토큰 삭제 API(DELETE)는 만들지 않는다. 로그아웃·탈퇴의 서버 처리가 그 역할을 대신한다(Jira 결정). 앱이 명시적으로 "이 기기 알림 끄기" 를 원하면 후속 태스크에서 다룬다.
- 등록 요청의 동의 값은 선택 항목이다. 없으면 동의 원장을 건드리지 않는다.
- 광고성 동의 문구 버전은 앱이 정수로 보낸다. 서버는 "현재 최신 버전" 을 검증하지 않고 받은 값을 기록한다(버전 정책은 KB-466 이후).
- 로그인·로그아웃 요청의 기기 식별자 헤더는 선택이다. 현재 앱은 모든 요청에 보내지만, 없어도 인증이 깨지면 안 된다.
- 로그아웃은 회원 식별 없이 refresh 토큰만 받는 기존 계약을 유지하며, 기기 연결 해제는 헤더의 기기 식별자만으로 수행한다(그 기기의 연결 회원이 누구든 해제).
- 회원 광고성 동의의 켜기·끄기는 이 기능 범위 밖이다(KB-466 설정 API).
- 외부 푸시 서비스 호출은 없다. 이 기능은 저장·연결만 다룬다.
- 이 기능의 계약은 전부 `X-API-Version: 1.1` 이상이다(온보딩·프로필 1.1 과 같은 릴리스 마커). 1.0 앱은 토큰을 보내지 않으므로 1.0 탈퇴가 기기를 정리하지 않아도 정리할 기기가 없다.
- 서버 구현의 클래스 접두·패키지·URL 은 전부 `notification`(도메인 컨텍스트명)이다 — `PUT /api/notifications/tokens`. Jira 초안의 `/api/push/tokens` 는 이 경로로 대체한다(2026-09-07 결정, Jira 본문·FE 공유 갱신 필요).
