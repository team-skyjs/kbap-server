## User Scenarios & Testing *(mandatory)*

### User Story 1 - 텍스트 묶음을 임베딩 벡터로 변환 (Priority: P1)

배치·서비스 개발자는 음식 이름·설명 같은 한국어 텍스트 묶음을 넘기면, 각 텍스트에 대응하는 고정 차원의 임베딩 벡터 목록을 입력 순서 그대로 돌려받는다. 호출하는 쪽은 어떤 외부 임베딩 제공자가 쓰이는지 알 필요가 없다.

**Why this priority**: KB-299 유사도 검색 파이프라인 전체(적재 배치·유사 음식 API)가 이 변환 능력 위에 서므로, 이것이 없으면 후속 작업을 시작할 수 없다.

**Independent Test**: 외부 시스템 없이 페이크 구현으로 계약(순서 보존·개수 일치·차원)을 검증할 수 있고, 실제 제공자 구현은 자격증명이 있는 환경에서 소량 텍스트로 단독 스모크 확인이 가능하다.

**Acceptance Scenarios**:

1. **Given** 텍스트 N건의 목록, **When** 임베딩 변환을 요청하면, **Then** N건의 벡터가 입력과 같은 순서로 반환되고 각 벡터는 약속된 고정 차원이다
2. **Given** 빈 목록, **When** 임베딩 변환을 요청하면, **Then** 외부 호출 없이 빈 목록이 반환된다
3. **Given** 외부 제공자 호출이 실패하는 상황(권한·네트워크 등), **When** 임베딩 변환을 요청하면, **Then** 실패가 호출자에게 예외로 전파된다(부분 성공 결과를 조용히 돌려주지 않는다)

---

### User Story 2 - 미설정 환경에서 부팅 안전 (Priority: P2)

임베딩 관련 설정(자격증명·활성 플래그)이 없는 환경(로컬 개발·CI·기존 프로필)에서도 web·batch 애플리케이션은 아무 영향 없이 정상 구동된다.

**Why this priority**: 이 저장소의 기존 외부 연동(LLM 3종)과 동일한 운영 원칙 — 설정이 없다고 앱이 못 뜨면 전 팀원의 로컬·CI 가 깨진다.

**Independent Test**: 임베딩 설정 없이 애플리케이션 컨텍스트를 구동해 부팅 성공을 확인한다.

**Acceptance Scenarios**:

1. **Given** 임베딩 설정이 전혀 없는 프로필, **When** web/batch 앱을 구동하면, **Then** 정상 부팅되고 임베딩 기능만 비활성 상태가 된다

---

### Edge Cases

- 빈 문자열이 목록에 섞여 있으면? — 그대로 제공자에 전달하고 제공자 응답/오류를 따른다(사전 필터링·보정은 이 구간의 책임이 아니다).
- 목록 중간 건에서 제공자 호출이 실패하면? — 전체 요청이 예외로 실패한다. 부분 결과 반환 없음(재시도·재개·격리 정책은 호출자 — 적재 배치든 동기 스캔 흐름이든 — 의 소관).
- 제공자가 약속과 다른 차원의 벡터를 반환하면? — 계약 위반으로 오류 처리한다(잘못된 벡터가 조용히 하류로 흘러가지 않는다).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 텍스트 목록을 받아 같은 개수·같은 순서의 임베딩 벡터 목록을 반환하는 계약(포트)을 공용 모듈에 제공해야 한다. 계약은 특정 외부 제공자·프레임워크 타입을 노출하지 않는다.
- **FR-002**: 계약의 실제 구현은 인프라 어댑터 모듈에 두고, 도메인·배치 코드는 계약만 알아야 한다(기존 외부 시스템 seam 격리 원칙과 동일).
- **FR-003**: 반환 벡터의 차원은 고정값(1024)이어야 하며, 코사인 유사도 계산에 적합한 형태여야 한다(KB-299 확정 사항).
- **FR-004**: 임베딩 설정(자격증명·모델 식별자·활성 플래그)이 없으면 구현 빈이 생성되지 않아야 하고, 그 상태로 web·batch 앱이 정상 부팅되어야 한다.
- **FR-005**: 외부 호출 실패는 호출자에게 예외로 전파되어야 하며, 부분 성공을 정상 결과처럼 반환해서는 안 된다.
- **FR-006**: 빈 입력 목록에는 외부 호출 없이 빈 목록을 반환해야 한다.
- **FR-007**: 계약 동작(순서 보존·개수 일치·실패 전파)은 외부 시스템 없이 페이크 구현으로 단위 검증되어야 한다(헌법 원칙 I).

### Key Entities

- **임베딩 벡터**: 텍스트 한 건의 의미를 담은 고정 차원(1024) 실수 배열. 원본 텍스트와 1:1 대응하며 순서로 대응 관계를 식별한다.
- **임베딩 계약(포트)**: 텍스트 목록 → 벡터 목록 변환을 약속하는 공용 모듈의 인터페이스. 외부 제공자 교체 시에도 불변.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 개발자는 텍스트 N건(1≤N≤소량 묶음)을 넘겨 N건의 1024차원 벡터를 입력 순서 그대로 받을 수 있다.
- **SC-002**: 임베딩 설정이 없는 기존 전 프로필에서 web·batch 앱 부팅 성공률 100% (기존 테스트 스위트 전부 통과).
- **SC-003**: 자격증명이 있는 환경에서 한국어 음식명 텍스트로 실 스모크 호출 시 유효한 벡터를 받는다(1회 이상 실측 기록).
- **SC-004**: 계약 동작 검증 테스트가 외부 네트워크 없이 통과한다.

## Assumptions

- 임베딩 제공자는 KB-299 에서 확정된 AWS Bedrock Titan Text Embeddings V2(차원 1024, cosine)를 1차 대상으로 한다. 호출 권한(`bedrock:InvokeModel`)은 실측 확인·EC2 역할 부착 완료 상태다.
- 벡터 DB(Qdrant) 연동·적재 배치·유사 음식 조회 API 는 이 기능의 범위가 아니다 — 벡터 DB 도입이 확정되면 별도 작업으로 이어진다(KB-299 잔여 범위).
- 임베딩 대상 텍스트 조립 규칙("이름 | 설명")은 호출자의 소관이며, 이 구간은 받은 텍스트를 그대로 변환만 한다.
- 호출 경로는 경로 중립이다 — 배치 묶음 적재(수백~수천 건, 비실시간)와 동기 단건/소량 호출(예: 메뉴판 스캔 직후) 모두 수용한다. 계약은 특정 호출 경로를 전제하지 않으며, 스캔·배치와의 실제 통합은 이 기능 범위 밖이다(KB-299 잔여).
