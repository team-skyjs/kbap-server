# Feature Specification: 메뉴판 사진 스캔 — 업로드 완료 검증 + 메뉴명·가격 추출

**Feature Branch**: `kb-138-menu-photo-scan`

**Created**: 2026-07-15

**Status**: Draft

**Input**: User description: "kb-138" (Jira KB-138 — [BE] 메뉴판 사진 스캔 — presigned URL 업로드 검증 + gpt-4o-mini 메뉴명·가격 추출)

## 배경

현재 메뉴 스캔은 클라이언트가 OCR 한 텍스트 라인을 서버에 보내는 구조라, 인식 품질이 클라이언트 OCR 에 좌우되고 가격 정보는 파이프라인 어디에도 없다. KB-138 스파이크에서 메뉴판 **사진**을 비전 인식에 직접 넣어 메뉴명·가격을 한 번에 추출하는 방식의 품질을 검증했고, 그 결과를 실제 스캔 파이프라인으로 구현한다.

사진은 서버를 거치지 않는다 — 클라이언트가 발급받은 서명 URL(KB-145, 별도 태스크)로 스토리지에 직접 업로드한 뒤, (1) **업로드 완료를 신고**해 서버가 실제 올라간 파일이 허용된 사진인지 검증하고, (2) 검증된 이미지의 **경로(path)만으로 스캔을 요청**한다. 스캔은 사진에서 메뉴명·가격을 추출해 기존 음식 매칭·회피성분 위험도 판정으로 연결하고, 스캔 내역(누가 어떤 이미지에서 어떤 메뉴를 얼마로 스캔했는지)을 히스토리로 남긴다. 기존 OCR 텍스트 입력 방식은 이미지 스캔으로 **대체**한다(공존하지 않음).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 업로드 완료 신고와 파일 검증 (Priority: P1)

사용자가 서명 URL 로 사진 업로드를 마친 뒤 앱이 업로드 완료를 신고하면, 서버는 스토리지에 실제 올라간 오브젝트의 형식과 크기를 확인한다. 스마트폰 촬영 사진(이미지 형식)이고 신고한 값과 일치하면 업로드 이미지로 기록되고, 영상 등 비이미지이거나 신고값과 다르면 그 오브젝트는 스토리지에서 삭제되고 실패로 응답한다.

**Why this priority**: 검증되지 않은 파일이 버킷에 남으면 이후 모든 소비(스캔·표시)가 오염된다. 허용된 사진만 시스템에 들어온다는 보장이 스캔 기능 전체의 전제다.

**Independent Test**: 오브젝트가 실제 존재하는 상태에서 완료 신고를 호출해, 이미지면 기록 성공·비이미지면 오브젝트 삭제와 실패 응답이 오는지로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 서명 URL 로 이미지(사진) 업로드가 완료된 오브젝트, **When** 업로드 완료를 신고하면, **Then** 서버가 실제 형식·크기를 확인하고 업로드 이미지로 기록하며 성공을 응답한다.
2. **Given** 이미지가 아닌 파일(예: 영상)이 업로드된 오브젝트, **When** 업로드 완료를 신고하면, **Then** 오브젝트가 스토리지에서 삭제되고 안정 에러 코드와 함께 거절된다.
3. **Given** 신고한 크기·형식이 실제 오브젝트와 다른 경우, **When** 업로드 완료를 신고하면, **Then** 오브젝트가 삭제되고 거절된다.
4. **Given** 존재하지 않는 경로, **When** 업로드 완료를 신고하면, **Then** 원인이 식별 가능한 실패로 응답한다.

### User Story 2 - 사진으로 메뉴 스캔: 메뉴명·가격 추출과 위험도 판정 (Priority: P1)

사용자가 검증된 메뉴판 사진의 경로로 스캔을 요청하면, 시스템이 사진에서 메뉴명(사진 표기 그대로 + 표준 한국어 이름)과 가격을 추출하고, 표준 한국어 이름으로 기존 음식 데이터와 매칭해 회피성분 위험도를 판정한다. 사용자는 메뉴별로 위험도와 가격이 담긴 결과를 받는다.

**Why this priority**: 이 기능의 존재 이유 — 사용자가 사진 한 장으로 "이 메뉴판에서 내가 피해야 할 음식과 가격"을 확인하는 핵심 가치. US1 과 함께 있어야 end-to-end 가 성립한다.

**Independent Test**: 검증된 이미지 경로 하나로 스캔을 요청해, 메뉴별 위험도·가격이 담긴 구조화 응답이 반환되는지로 검증 가능(비전 인식은 페이크로 대체 가능).

**Acceptance Scenarios**:

1. **Given** 검증된 메뉴판 사진 경로, **When** 스캔을 요청하면, **Then** 메뉴별 항목(표기 이름·표준 한국어 이름·가격·위험도·매칭 여부)이 담긴 결과가 반환된다.
2. **Given** 가격이 "1.6"·"9.0" 처럼 축약 표기된 메뉴판, **When** 스캔하면, **Then** 가격이 원(KRW) 단위 정수(16000·9000)로 복원되어 반환된다.
3. **Given** 가격이 표기되지 않은 메뉴가 섞인 메뉴판, **When** 스캔하면, **Then** 해당 메뉴는 가격 없음으로 구분되어 반환된다.
4. **Given** 상호·전화번호·원산지 표기가 섞인 메뉴판, **When** 스캔하면, **Then** 메뉴가 아닌 텍스트는 결과에서 제외된다.
5. **Given** 한 메뉴에 사이즈별 가격이 여러 개인 메뉴판, **When** 스캔하면, **Then** 항목이 분리되어 반환된다(예: 김치찌개(소)/김치찌개(대)).
6. **Given** 비전 인식 호출이 실패하거나 응답을 해석할 수 없는 경우, **When** 스캔하면, **Then** 원인이 식별 가능한 실패로 응답한다(조용한 빈 결과 금지).

### User Story 3 - 스캔 내역 히스토리 (Priority: P2)

스캔이 완료되면 누가(회원) 어떤 이미지(경로)에서 어떤 메뉴(표기 이름·표준 한국어 이름)를 얼마(가격)로 스캔했는지가 히스토리로 남는다. 가격 데이터는 이 히스토리에만 존재하며, 음식 마스터 데이터에는 저장되지 않는다.

**Why this priority**: 당장 사용자에게 노출되는 기능은 아니지만, 향후 분석·환율 계산 기능의 원천 데이터다. US2 가 있어야 기록할 내용이 생기므로 P2.

**Independent Test**: 스캔 1회 후 히스토리 조회로 회원·이미지 경로·메뉴·가격이 기록됐는지 확인 가능.

**Acceptance Scenarios**:

1. **Given** 스캔이 성공한 요청, **When** 히스토리를 조회하면, **Then** 회원·이미지 경로·추출 메뉴(표기/표준 이름)·가격이 기록되어 있다.
2. **Given** 스캔 히스토리가 쌓인 상태, **When** 음식 마스터 데이터를 조회하면, **Then** 어떤 가격 정보도 존재하지 않는다.

---

### Edge Cases

- 완료 신고 없이(검증되지 않은 경로로) 스캔을 요청하면? → 거절된다.
- 다른 회원이 업로드한 이미지 경로로 스캔을 요청하면? → 본인 소유 이미지가 아니면 거절된다.
- 경로 대신 전체 URL(도메인 포함)을 넘기면? → 경로만 허용, 거절된다.
- 메뉴판이 아닌 사진(풍경 등)을 스캔하면? → 추출 항목이 0개인 정상 응답(실패 아님)으로 구분된다.
- 추출된 메뉴가 음식 데이터에 없으면? → 기존 스캔과 동일하게 미매칭(위험도 미상)으로 표시되고, 가격은 그대로 반환·기록된다.
- 저장소 도메인(CDN)이 바뀌면? → 저장된 데이터는 경로뿐이므로 영향이 없다(도메인은 서버 설정).
- 완료 신고가 같은 경로로 중복 호출되면? → 중복 기록 없이 동일 결과(멱등)로 응답한다.

## Requirements *(mandatory)*

### Functional Requirements

**업로드 완료 검증**

- **FR-001**: 시스템은 업로드 완료 신고(이미지 경로·클라이언트가 신고한 형식·크기)를 받아, 스토리지에 실제 존재하는 오브젝트의 형식·크기와 대조 검증해야 한다.
- **FR-002**: 허용 판정은 "사진인지"만 본다 — 이미지 형식(스마트폰 촬영 사진 포맷)이면 허용하고, 영상 등 비이미지는 거절한다. 별도 크기 상한 정책은 두지 않으며 크기는 신고값–실제값 대조용으로만 쓴다.
- **FR-003**: 검증 실패(비이미지·신고값 불일치) 시 해당 오브젝트를 스토리지에서 삭제하고 안정 에러 코드로 거절해야 한다.
- **FR-004**: 검증 성공 시 업로드 이미지가 기록되어, 이후 스캔 요청이 그 경로의 유효성(존재·소유)을 확인할 수 있어야 한다.

**사진 스캔·추출**

- **FR-005**: 스캔 요청은 이미지의 **경로(path)** (전체 URL 금지)와 **클라이언트 자체 OCR 항목 목록**(항목별 `idx` + 원문 텍스트, 1~100개·idx 유일)을 함께 받아야 한다. idx 는 클라이언트 UI 박스와 결과를 잇는 키다.
- **FR-005a**: 시스템은 각 추출 메뉴를 클라이언트 OCR 항목의 `idx` 에 매칭해 응답 항목의 `idx` 로 돌려줘야 한다(비전 인식이 사진 위치·텍스트로 판단). 대응하는 OCR 항목이 없는 추출 메뉴는 `idx=null` 로 포함한다. 요청 목록에 없는 idx 가 반환되면 서버가 null 로 방어한다.
- **FR-006**: 스캔은 검증된 본인 소유 이미지에 대해서만 수행되어야 한다(미검증·타인 소유·미존재 경로는 거절).
- **FR-007**: 시스템은 사진에서 메뉴 항목을 추출해야 한다 — 항목별로 사진 표기 그대로의 이름, 표준 한국어 이름, 가격(원 단위 정수, 미표기 시 없음)을 구조화한다.
- **FR-008**: 가격 추출은 축약 표기를 복원해야 한다 — "1.6"·"1.6만" → 16000, "9.0"·"9,0" → 9000 처럼 메뉴판 전체 가격대 문맥으로 단위를 판단하고, 통화기호·콤마·"원"을 제거해 정수만 남긴다.
- **FR-009**: 메뉴가 아닌 텍스트(상호·전화번호·원산지 표기·영업 안내)는 결과에서 제외하고, 한 메뉴에 사이즈별 가격이 여러 개면 항목을 분리해야 한다.
- **FR-010**: 추출된 표준 한국어 이름은 기존 음식 매칭·회피성분 위험도 판정으로 연결되어, 스캔 응답에 메뉴별 위험도·매칭 여부·가격이 함께 담겨야 한다.
- **FR-010a**: 스캔 응답은 **기존 스캔 API 응답 구조를 유지한 채 신규 필드를 얹는(additive) 형태**여야 한다 — 기존 항목 필드(항목 식별 순번·매칭 여부·음식 식별자·위험도·표시명·한국어명)와 응답 구조는 제거·개명하지 않고, 가격 등 신규 정보만 필드로 추가한다(클라이언트가 기존 파싱 코드를 재사용). 항목 식별 순번은 요청 항목이 사라지므로 서버가 메뉴판 내 추출 순서로 부여하는 것으로 의미만 재정의한다.
- **FR-011**: 비전 인식 실패·응답 해석 불가 시 원인이 식별 가능한 실패로 보고되어야 한다(조용한 빈 결과 금지). 추출 항목 0개는 실패가 아니라 빈 결과로 구분한다.
- **FR-012**: 이미지의 전체 접근 주소가 필요한 내부 처리(비전 인식 호출 등)에서는 서버가 설정된 저장소 도메인과 경로를 조합해야 하며, 클라이언트·저장 데이터에는 경로만 존재해야 한다.

**저장·히스토리**

- **FR-013**: 스캔 성공 시 히스토리에 회원·이미지 경로·추출 메뉴(표기/표준 이름)·가격이 저장되어야 한다.
- **FR-014**: 가격은 스캔 히스토리 외 어떤 곳(음식 마스터 데이터 등)에도 저장되지 않아야 한다.
- **FR-015**: 기존 스캔의 부가 동작(회원 스캔 횟수 증가, 최근 스캔 음식 기반 홈 노출)은 이미지 스캔에서도 유지되어야 한다.

**규약**

- **FR-016**: 완료 신고·스캔 API 는 인증된 사용자 전용이며, 프로젝트 공통 응답 봉투·경로 규약·안정 에러 코드 체계를 준수해야 한다.
- **FR-017**: 실 스토리지·실 비전 인식 접근 없이 전 시나리오를 검증할 수 있어야 한다(외부 시스템은 대체 가능한 경계 뒤에 격리 — 헌법 I Test-First).

### Key Entities

- **업로드 이미지**: 완료 검증을 통과한 이미지 기록 — 소유 회원, 오브젝트 경로, 형식, 크기, 검증 시각. 스캔 요청의 유효성(존재·소유) 판단 근거.
- **스캔 히스토리(확장)**: 스캔 1회의 기록 — 회원, 이미지 경로, 추출 항목들(표기 이름, 표준 한국어 이름, 가격, 매칭된 음식). 가격이 존재하는 유일한 저장소.
- **추출 항목**: 비전 인식이 반환한 메뉴 1건 — 순번, 표기 이름, 표준 한국어 이름, 가격(원 단위 정수 또는 없음).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 메뉴판 사진 촬영 → 업로드 → 스캔 한 번의 흐름으로 메뉴별 위험도와 가격을 확인할 수 있다(end-to-end 성립).
- **SC-002**: 이미지가 아닌 파일은 완료 검증 단계에서 100% 거절되고 스토리지에 남지 않는다.
- **SC-003**: 스캔 성공 후 누가·어떤 이미지에서·어떤 메뉴를·얼마로 스캔했는지 히스토리로 추적할 수 있다.
- **SC-004**: 천원 축약 표기("1.6", "9.0") 메뉴판도 가격이 원 단위 정수로 복원되어 반환된다.
- **SC-005**: 저장소 도메인을 변경해도 저장된 데이터 수정이 0건이다(경로만 저장).
- **SC-006**: 가격 데이터는 스캔 히스토리에서만 발견된다(그 외 저장 위치 0곳).

## Assumptions

- **서명 URL 발급은 KB-145 가 담당**: 발급 API(용도·형식 검증, 키 생성, 만료)는 별도 태스크 KB-145 의 범위이며, 본 태스크는 "발급받아 업로드가 끝난 뒤"부터를 담당한다. KB-145 의 객체 키 설계(용도 prefix + 회원 식별 포함)를 소유 검증의 근거로 활용한다.
- **기존 텍스트 스캔 대체 가능**: 앱이 미출시 상태라 기존 OCR 텍스트 입력 계약을 유지할 클라이언트가 없다 — 스캔 입력을 이미지 경로로 전환하고 텍스트 입력은 제거한다(사용자 확정).
- **추출 모델·프롬프트는 스파이크 산출물 재사용**: 모델과 시스템 프롬프트·구조화 응답 형식·가격 복원 지침은 KB-138 스파이크(`kb-138-menu-price-mapping`)에서 검증된 것을 이식한다.
- **텍스트 정제 단계 생략**: 비전 인식이 표준 한국어 이름을 함께 반환하므로, 기존 파이프라인의 별도 텍스트 정제(해석) 호출은 이미지 스캔 경로에서 불필요하다.
- **완료 검증과 스캔은 별도 요청**: 업로드 완료 신고(검증·기록)와 스캔 요청은 분리된 두 단계다(사용자 확정) — 완료 검증은 향후 다른 이미지 용도(리뷰 사진 등)에도 재사용될 수 있다.
- **사진 후처리(픽셀 압축 등)는 범위 밖**: 업로드 후 이미지 압축·리사이즈 자동화는 향후 인프라 확장(파생 키 방식)으로 붙일 수 있으며 본 태스크는 고려만 하고 구현하지 않는다.
