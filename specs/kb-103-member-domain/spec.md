# Feature Specification: 회원 도메인 — 소셜 신원·프로필·온보딩 상태·탈퇴

**Feature Branch**: `kb-103-member-domain`

**Created**: 2026-07-08

**Status**: Draft

**Input**: User description: "kb-103 진행하자. 워크트리로 ㄱㄱ"

## 배경 / 문제

회원 컨텍스트가 빈 스켈레톤이라 회원·소셜 신원·프로필 모델이 없다. 소셜 로그인(KB-102)은 검증된 소셜 신원(제공자·제공자 사용자 ID·이메일)을 들고 "이 신원이 어느 회원인가"를 물어야 하는데, 그 답을 주는 **신원 해소**가 존재하지 않는다. 로그인이 신원 해소를 호출하므로 이 작업이 선행이다.

당초 "같은 검증 이메일이면 구글·애플을 한 회원으로 자동 통합"할 계획이었으나 **철회했다(사용자 결정, 2026-07-08)**: 같은 사람이라도 제공자별 이메일이 다르면 묶을 근거가 없고, 애플 Hide My Email 릴레이 주소는 같은 이메일 사용자조차 매칭을 깨뜨린다 — 자동 통합은 신뢰할 수 없다. 따라서 **신원 해소 키는 (제공자, 제공자 사용자 ID) 단독**이며, 소셜 계정마다 별도 회원이 생성된다. 계정 통합이 필요해지면 로그인된 상태에서 다른 제공자 로그인을 한 번 더 수행해 본인임을 증명하는 **명시적 소셜 계정 연동** 기능을 후속 이슈로 다룬다(회원 1—N 신원 구조는 그때를 대비해 유지).

최초 가입 회원은 온보딩 미완료 상태로 시작해 온보딩(KB-104)에서 프로필 값을 채우고 완료로 전이해야 하며, 탈퇴는 데이터를 즉시 파기하지 않되 조회·인증에서 확실히 제외되어야 한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 소셜 신원 해소로 가입·재로그인 (Priority: P1)

사용자가 소셜 계정(구글 또는 애플)으로 처음 로그인하면 회원이 새로 만들어지고, 같은 소셜 계정으로 다시 로그인하면 매번 **같은 회원**으로 인식된다. 시스템은 해소 결과에 회원의 **온보딩 상태**(PENDING/COMPLETED)와 신규 가입 여부를 함께 실어, 클라이언트가 온보딩 화면으로 보낼지 판단할 수 있게 한다.

**Why this priority**: 로그인(KB-102)이 이 신원 해소를 호출해야 완결되는, 회원 컨텍스트의 존재 이유다. 이 슬라이스만으로 "가입·재로그인" 가치를 단독 전달한다.

**Independent Test**: 동일 (제공자, 제공자 사용자 ID)로 두 번 해소를 요청했을 때 첫 번째는 신규 회원 생성, 두 번째는 동일 회원 반환·신규 아님 표시를 검증.

**Acceptance Scenarios**:

1. **Given** 어떤 회원도 없는 상태, **When** 구글 신원(제공자 사용자 ID·이메일)으로 해소 요청, **Then** 새 회원이 생성되고 신규 가입으로 표시되며 온보딩 상태는 미완료(PENDING)다.
2. **Given** 위에서 생성된 회원, **When** 같은 구글 신원으로 다시 해소 요청, **Then** 같은 회원이 반환되고 신규 가입이 아니라고 표시된다.
3. **Given** 가입만 하고 온보딩을 마치지 않은(PENDING) 기존 회원, **When** 같은 소셜 계정으로 재로그인, **Then** 신규 가입이 아니라고 표시되지만 **온보딩 상태는 여전히 PENDING** 으로 반환되어 클라이언트가 온보딩을 다시 유도할 수 있다(라우팅 신호는 신규 여부가 아니라 온보딩 상태다).
4. **Given** 온보딩을 완료한(COMPLETED) 기존 회원, **When** 재로그인, **Then** 온보딩 상태 COMPLETED 로 반환되어 온보딩을 건너뛴다.
5. **Given** 구글 신원(이메일 A)으로 가입한 회원, **When** **같은 이메일 A** 의 애플 신원으로 해소 요청, **Then** 자동 통합 없이 **별도 신규 회원**이 생성된다(신원 해소 키는 제공자·제공자 사용자 ID 뿐).
6. **Given** 이메일이 제공되지 않은 소셜 신원(애플 재로그인 등), **When** 해소 요청, **Then** 이메일 없이도 정상적으로 해소·가입된다.
7. **Given** 동일 소셜 계정으로 거의 동시에 두 번 해소 요청, **Then** 회원은 한 명만 생성된다(중복 가입 불가).

---

### User Story 2 - 프로필·온보딩 상태 보유와 전이 (Priority: P2)

회원은 닉네임·기피성분 코드 집합·맵기 선호(0~10)·국가·앱 언어를 담는 프로필과 온보딩 상태(PENDING/COMPLETED)를 가진다. 프로필을 저장·조회할 수 있고, 온보딩 상태는 미완료에서 완료로 전이할 수 있다.

**Why this priority**: 값을 채우는 온보딩 플로우는 KB-104 지만, 담을 그릇(모델·저장·조회·전이)이 먼저 있어야 한다.

**Independent Test**: 회원의 프로필을 저장한 뒤 다시 조회해 값이 유지되고, 온보딩 상태가 PENDING→COMPLETED 로 전이되는지 검증.

**Acceptance Scenarios**:

1. **Given** 신규 가입 회원, **When** 프로필(닉네임·기피성분 집합·맵기·국가·언어) 저장, **Then** 재조회 시 저장한 값이 그대로 반환된다.
2. **Given** 온보딩 미완료(PENDING) 회원, **When** 온보딩 완료 처리, **Then** 상태가 COMPLETED 로 전이되고 재조회에도 유지된다.
3. **Given** 신규 가입 직후 회원, **When** 프로필 조회, **Then** 온보딩 상태는 PENDING 이고 프로필 값은 아직 비어 있다.

---

### User Story 3 - 회원 탈퇴 (Priority: P3)

회원이 탈퇴하면 데이터가 즉시 파기되는 대신 탈퇴 상태로 전환되고, 이후 모든 조회·인증에서 그 회원은 존재하지 않는 것처럼 취급된다.

**Why this priority**: 가입·프로필이 있어야 의미 있는 마무리 기능이다.

**Independent Test**: 회원 탈퇴 후 해당 회원 조회가 실패(부재)하는지 검증.

**Acceptance Scenarios**:

1. **Given** 활성 회원, **When** 탈퇴 처리, **Then** 이후 그 회원 ID 조회는 부재로 처리된다.
2. **Given** 탈퇴한 회원의 소셜 신원, **When** 같은 소셜 계정으로 다시 해소 요청, **Then** 탈퇴 회원이 반환되지 않고 새 회원으로 가입된다(과거 프로필은 복구되지 않는다).

---

### Edge Cases

- 같은 소셜 계정인데 제공자 측 이메일이 바뀐 뒤 재로그인: 이메일은 매칭 키가 아니므로 (제공자, 제공자 사용자 ID)로 같은 회원으로 인식된다.
- 애플 이메일 최초-only: 애플은 이메일을 최초 로그인에만 줄 수 있다 — 재로그인에 이메일이 없어도 해소에 지장 없다(이메일은 참고 정보).
- 애플 Hide My Email(릴레이 주소): 릴레이 이메일도 그대로 참고 정보로 저장한다 — 매칭 키가 아니므로 오동작 여지가 없다.
- 같은 이메일의 타 제공자 로그인: 자동 통합하지 않고 별도 회원이 생성된다. 하나로 묶는 것은 후속 명시적 계정 연동 기능의 몫이다.
- 거의 동시에 도착한 동일 신원 최초 로그인 2건: 중복 가입 방지 규칙에 의해 한 명만 생성되고 나머지는 기존 회원 반환으로 수렴한다.
- 탈퇴 회원과 같은 이메일·같은 소셜 계정의 재가입: 탈퇴 회원은 모든 조회에서 제외되므로 새 회원이 생성된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 회원은 여러 소셜 신원(제공자·제공자 사용자 ID·이메일)을 가질 수 있는 구조여야 한다 — 이번 범위에서 신원은 회원당 1개만 생성되지만, 후속 명시적 계정 연동을 위해 1—N 관계를 유지한다.
- **FR-002**: 동일한 (제공자, 제공자 사용자 ID) 조합은 시스템 전체에서 유일해야 하며, 같은 소셜 계정의 중복 가입은 동시 요청에서도 불가능해야 한다.
- **FR-003**: 신원 해소는 (제공자, 제공자 사용자 ID)로 기존 신원을 조회하고, 없으면 신규 회원을 생성해야 한다. **이메일은 신원 매칭 키로 사용하지 않는다**(자동 통합 없음).
- **FR-004**: 신원 해소 결과는 해당 회원, 회원의 온보딩 상태(PENDING/COMPLETED), 신규 가입 여부를 함께 제공해야 한다 — 재방문 시 온보딩 유도 판단의 근거는 신규 여부가 아니라 온보딩 상태다.
- **FR-005**: 이메일은 신원의 참고 정보로 저장하며 부재(애플 재로그인·Hide My Email 해지 등)를 허용해야 한다.
- **FR-006**: 신규 회원은 온보딩 미완료(PENDING) 상태로 시작해야 한다.
- **FR-007**: 회원 프로필은 닉네임·기피성분 코드 집합(회피 카탈로그 내 코드)·맵기 선호(0~10)·국가·앱 언어를 저장·조회할 수 있어야 한다.
- **FR-008**: 온보딩 상태는 PENDING 에서 COMPLETED 로 전이할 수 있어야 한다. 온보딩을 마치지 않고 이탈한 회원은 재방문·재로그인 후에도 PENDING 을 유지해 온보딩을 이어서 유도할 수 있어야 한다.
- **FR-009**: 회원 탈퇴는 데이터 파기가 아닌 상태 전환으로 처리하고, 탈퇴 회원은 모든 조회(ID 조회·신원 해소)에서 제외해야 한다.
- **FR-010**: 회원 도메인 모델은 불변 규약(상태 변경은 새 인스턴스 반환)과 애그리거트 규약을 따라야 한다.

### Key Entities

- **회원(Member)**: 서비스 사용자. 프로필(닉네임·기피성분 집합·맵기 선호·국가·앱 언어)과 온보딩 상태(PENDING/COMPLETED)를 보유한다. 소셜 신원을 1개 이상 가진다(이번 범위에선 1개, 구조는 1—N).
- **소셜 신원(SocialIdentity)**: 외부 제공자 계정과 회원의 연결. 제공자(GOOGLE/APPLE)·제공자 사용자 ID·이메일(참고 정보, 부재 허용)을 담고, (제공자, 제공자 사용자 ID)가 유일하다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 동일 소셜 계정으로 몇 번을 로그인해도 회원은 정확히 1명이다(중복 가입 0건 — 동시 요청 포함).
- **SC-002**: 서로 다른 소셜 계정은 이메일이 같더라도 항상 서로 다른 회원이 된다(자동 통합 0건 — 해소 결과가 이메일 값에 영향받지 않음).
- **SC-003**: 신규 가입·기존 로그인 두 경우 모두 신규 가입 여부가 올바르게 표시된다(가입 시에만 신규).
- **SC-004**: 탈퇴한 회원은 탈퇴 직후부터 조회·신원 해소 어디에도 나타나지 않는다(노출 0건).
- **SC-005**: 신원 해소(신규·기존·이메일 무관)·프로필 저장 조회·온보딩 전이·탈퇴가 단위·통합 테스트로 검증된다.
- **SC-006**: 가입 후 온보딩 미완료(PENDING) 회원이 재로그인하면 해소 결과의 온보딩 상태가 PENDING 으로 반환된다(온보딩 유도 신호가 신규 여부와 독립적으로 유지됨).

## Assumptions

- 소셜 토큰의 서명·만료 검증은 로그인(KB-102) 책임이다 — 이 기능은 이미 검증된 신원(제공자·제공자 사용자 ID·이메일)을 입력으로 받는다.
- 제공자는 당장 GOOGLE·APPLE 두 종이며, 추후 추가될 수 있는 구조로 둔다.
- **이메일 기반 자동 계정 통합은 하지 않는다(사용자 결정, 2026-07-08)** — 제공자별 이메일 상이·애플 릴레이 주소로 신뢰 불가. 계정 통합은 후속 "명시적 소셜 계정 연동" 기능(로그인 상태에서 타 제공자 재인증)으로 다룬다.
- 자체 발급 JWT 에는 이메일을 넣지 않는다(사용자 결정) — 토큰 클레임은 회원 식별자 등 최소 정보만 담고, 이메일은 서버 측 소셜 신원 저장소에서만 관리한다(KB-102 구현 시 준수).
- 탈퇴 후 같은 소셜 계정으로 재로그인하면 **신규 회원으로 재가입**한다(과거 데이터 복구 없음 — 복구/유예 기간은 범위 밖, 필요 시 후속 이슈).
- 프로필 값 입력·검증(닉네임·카탈로그 81종·국가 코드·10개국어)과 온보딩 API 는 KB-104 범위다 — 여기서는 담는 그릇(모델·저장·조회·전이)까지만 제공한다.
- 닉네임은 사용자 표시용이며 **회원 간 유일성을 강제하지 않는다**(중복 허용, 표시 전용). 형식·길이 상세 검증은 KB-104 입력 검증에서 다루고, 도메인은 형식 불변만 지킨다.
- 온보딩 미완료(PENDING) 회원의 재방문 유도는 클라이언트 라우팅 책임이며, 서버는 해소 결과에 온보딩 상태를 실어 신호만 제공한다(온보딩 화면 자체는 KB-104).
- 앱 언어는 음식 번역과 같은 지원 언어 집합(한국어 + 9개 대상 언어)을 사용한다.
- 기피성분은 회피 카탈로그가 소유한 코드로만 참조한다(컨텍스트 간 코드 참조 원칙).
