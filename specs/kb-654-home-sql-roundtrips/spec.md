# Feature Specification: 홈 조회 SQL 왕복 12회→5회

**Feature Branch**: `kb-654-home-sql-roundtrips`

**Created**: 2026-09-30

**Status**: Draft

**Jira**: [KB-654](https://simhani1.atlassian.net/browse/KB-654)

**Input**: User description: "member를 1차 캐시 사용할 수 있는 구조로 변경하면서 인기음식, 리뷰 많은 음식은 id 조회후 엔티티 조회가 아니라 native 쿼리로 한번에 엔티티를 가져오도록 수정. 메서드 뒤에 ready 안붙여도 됨."

## 배경

버추얼 스레드 전환(KB-653) 후 dev 부하 측정에서 병목이 DB 커넥션 풀로 옮겨갔다. 처리량은 커넥션 수 ÷ 한 요청의 커넥션 보유 시간이다. 홈 조회 한 건은 읽기 트랜잭션 하나에서 커넥션을 쥔 채 SQL 을 12번 왕복한다. 회원 행을 5번 읽고, 세 음식 섹션은 id 조회 뒤 재조회로 각 2번이다. 개별 쿼리는 가볍지만 왕복 수가 곧 보유 시간이다. 왕복을 5번으로 줄이면 풀·RDS 를 건드리지 않고 처리량이 두 배 이상 난다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 홈 응답은 그대로이고 SQL 왕복만 줄어든다 (Priority: P1)

앱 사용자는 이전과 같은 홈 응답(같은 섹션·같은 내용·같은 순서)을 받는다. 서버는 회원 홈 조회 한 건에 SQL 을 5번만 보낸다.

**Why this priority**: 이 작업의 목적이자 수용 기준이다.

**Independent Test**: 기존 홈 통합 테스트(회원·비회원·순서·언어·위험도)가 무수정으로 통과하고, 로컬 dev 프로필에서 `show-sql` 을 켜고 회원 홈을 한 번 호출했을 때 SQL 문이 5개다.

**Acceptance Scenarios**:

1. **Given** 기존 홈 통합 테스트, **When** 변경 후 실행하면, **Then** 한 줄도 고치지 않고 전부 통과한다.
2. **Given** 로컬에서 `show-sql` 을 켠 api, **When** 회원 토큰으로 홈을 한 번 호출하면, **Then** 로그의 SQL 문이 5개다(회원 1·기피 성분 1·인기 1·리뷰 많은 1·최근 스캔 1).
3. **Given** 같은 조건, **When** 비회원으로 호출하면, **Then** SQL 문이 2개다(인기 1·리뷰 많은 1).

---

### User Story 2 - 세 음식 섹션의 정렬 의미가 유지된다 (Priority: P1)

리뷰 많은 음식은 활성 리뷰 수 내림차순, 동률이면 최신 리뷰 우선, READY 음식만. 최근 스캔은 최신 스캔순, 같은 음식은 한 번만, READY 음식만. 인기 음식은 READY 중 무작위.

**Independent Test**: 리포지토리 테스트가 새 조회 메서드로 옮겨져 통과하고, 홈 통합 테스트의 순서 시나리오가 통과한다.

**Acceptance Scenarios**:

1. **Given** 리뷰 수가 다른 READY·비READY 음식, **When** 리뷰 많은 음식을 조회하면, **Then** READY 만 리뷰 수 내림차순으로, 리뷰 0건은 제외된다.
2. **Given** 같은 음식을 여러 번 스캔한 회원, **When** 최근 스캔을 조회하면, **Then** 음식당 한 번, 최신순이다.

---

### Edge Cases

- 소프트 삭제된 음식·리뷰·스캔 이력은 결과에서 빠져야 한다. 네이티브 조회는 자동 필터가 없으므로 조건을 직접 건다.
- 탈퇴·정지 회원의 활성 여부 판정은 그대로다(활성이 아니면 회원 없음 오류).
- 회원 조회를 다른 곳(트랜잭션 밖)에서 부르는 경로는 지금처럼 매번 조회된다. 퇴행 없음.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 회원 홈 조회 한 건의 SQL 왕복은 5회, 비회원은 2회여야 한다.
- **FR-002**: 홈 응답 구조·내용·정렬은 변경 전과 같아야 한다. 기존 홈 통합 테스트는 무수정 통과.
- **FR-003**: 회원 단건 조회는 같은 트랜잭션 안에서 반복 호출 시 첫 호출만 DB 에 가야 한다. 활성 회원만 노출하는 계약은 유지한다.
- **FR-004**: 인기·리뷰 많은·최근 스캔 음식은 각각 SQL 한 번으로 음식 엔티티 목록을 정렬된 채로 받아야 한다. 소프트 삭제·READY 조건을 쿼리에 직접 포함한다.
- **FR-005**: 더 이상 쓰이지 않는 조회 메서드는 제거하고, 그 메서드의 리포지토리 테스트는 새 메서드로 옮긴다.
- **FR-006**: 기존 자동 테스트 전부 통과.

## Success Criteria *(mandatory)*

- **SC-001**: 로컬 `show-sql` 기준 회원 홈 조회 SQL 5개, 비회원 2개.
- **SC-002**: 홈 통합 테스트 3파일 diff 0, 전부 통과.
- **SC-003**: api·common 테스트 그린.
- **SC-004**: 머지 후 dev 재측정(같은 k6 스크립트)에서 200 비율·p50·Hikari 타임아웃 500 건수가 KB-653 결과(40%·26초·2,888건)보다 개선된다.

## Assumptions

- 새 리포지토리 메서드 이름은 `findRandom`·`findMostReviewed`·`findRecentScanned`(사용자 지시: `Ready` 접미 생략).
- 리뷰 많은 음식 결과 캐시는 이 작업이 아니다(별도 결정).
- 측정은 사용자가 AWS 안에서 수행한다.
