# Feature Specification: Flyway 마이그레이션 스쿼시 — 스키마·시드 분리 및 프로필별 적용

**Feature Branch**: `kb-163-flyway-squash`

**Created**: 2026-07-16

**Status**: Draft

**Input**: User description: "kb-163 워크트리로 시작. 스키마 생성부터 현재 데이터베이스의 테이블 최종 상태를 기준으로 파일 하나로 압축. 단 81종 기피성분과 국가 코드 등 기본으로 저장되어야 하는 데이터는 insert하도록 남겨둘 것. 이미 저장된 다른 회원, 음식 데이터 등은 날라가지 않는지 확인 후 판단해줄것."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 신규 환경(프로덕션 포함)은 스키마 + 마스터 데이터만으로 초기화된다 (Priority: P1)

프로덕션(또는 스테이징)에 처음 배포할 때, 빈 데이터베이스가 최종 테이블 구조와 서비스 운영에 필수인 마스터 데이터(기피물질 카탈로그 81종)만으로 초기화된다. 개발·데모용으로 넣어 두었던 음식 10건 등 데모 데이터는 프로덕션에 들어가지 않는다.

**Why this priority**: 이 작업의 존재 이유다. 현재 구조로는 프로덕션 첫 배포 시 데모 시드가 그대로 insert 되며, 이를 막을 방법이 없다. 프로덕션 배포 이전인 지금이 마이그레이션 이력을 재작성할 수 있는 마지막 시점이다.

**Independent Test**: 빈 데이터베이스에 프로덕션 프로필로 애플리케이션을 기동해, 테이블 7종이 생성되고 기피물질 카탈로그 81종만 존재하며 음식 데이터가 0건임을 확인한다.

**Acceptance Scenarios**:

1. **Given** 빈 데이터베이스, **When** 프로덕션 프로필로 애플리케이션을 기동하면, **Then** 최종 스키마(테이블 7종)가 생성되고 엔티티-스키마 정합 검증을 통과한다
2. **Given** 프로덕션 프로필로 초기화된 데이터베이스, **When** 기피물질 카탈로그를 조회하면, **Then** 81종이 전부 존재한다
3. **Given** 프로덕션 프로필로 초기화된 데이터베이스, **When** 음식 데이터를 조회하면, **Then** 데모 음식 데이터가 0건이다

---

### User Story 2 - 기존 운영 중인 DB의 저장 데이터는 유실되지 않는다 (Priority: P2)

이미 운영 중인 홈서버(dev) 데이터베이스에는 실제 가입한 회원, 축적된 음식 데이터, 북마크, 스캔 이력 등이 저장되어 있다. 마이그레이션 이력을 새 구조로 전환한 뒤에도 이 데이터는 한 건도 사라지지 않고, 애플리케이션이 정상 기동·동작한다.

**Why this priority**: 사용자가 명시적으로 요구한 안전 조건이다. 원래 계획(DB drop 후 재생성)을 그대로 따르면 홈서버의 회원·음식 데이터가 전부 유실된다. 기존 DB의 스키마는 이미 최종 상태와 동일하므로, 데이터를 지우지 않고 마이그레이션 **이력 장부만 새 기준선으로 교체**하는 방식으로 전환한다.

**Independent Test**: 기존 데이터가 있는 데이터베이스에서 전환 절차를 수행한 뒤, 전환 전후 각 테이블의 행 수가 100% 일치하고 애플리케이션이 정상 기동함을 확인한다.

**Acceptance Scenarios**:

1. **Given** 기존 마이그레이션 22개가 모두 적용되고 회원·음식 데이터가 저장된 데이터베이스, **When** 새 마이그레이션 이력으로 전환하면, **Then** 회원·음식·북마크·스캔 이력·업로드 이미지 데이터의 행 수가 전환 전과 동일하다
2. **Given** 전환이 완료된 기존 데이터베이스, **When** 애플리케이션을 기동하면, **Then** 마이그레이션 검증을 통과하고 정상 부팅한다
3. **Given** 전환이 완료된 기존 데이터베이스(데모 시드가 이미 존재), **When** 애플리케이션을 기동하면, **Then** 데모 시드가 중복 insert 되지 않는다

---

### User Story 3 - 로컬 개발 환경은 파일 하나로 즉시 재구성된다 (Priority: P3)

개발자가 로컬 데이터베이스를 새로 만들면, 22개 파일을 순차 적용하던 기존 방식 대신 스키마 전용 초기화 파일 하나(+ 시드)로 최종 상태가 곧바로 만들어지고, 데모 데이터까지 포함되어 바로 개발·데모에 쓸 수 있다.

**Why this priority**: 개발 편의 개선 효과다. P1·P2 가 충족되면 자연히 따라오는 결과이며, 단독으로도 온보딩·환경 재구성 시간을 줄인다.

**Independent Test**: 빈 로컬 데이터베이스에 로컬 프로필로 기동해, 최종 스키마 + 마스터 데이터 + 데모 데이터가 모두 준비됨을 확인한다.

**Acceptance Scenarios**:

1. **Given** 빈 로컬 데이터베이스, **When** 로컬(또는 dev) 프로필로 기동하면, **Then** 최종 스키마와 기피물질 카탈로그 81종, 데모 음식 데이터(음식·설명·음식-기피물질 매핑)가 모두 생성된다
2. **Given** 새 구조의 마이그레이션 디렉터리, **When** 파일 목록을 확인하면, **Then** 기존 22개 파일은 삭제되고 스키마 초기화 1개 + 마스터 시드 + (별도 위치의) 데모 시드만 남는다

---

### Edge Cases

- 기존 DB의 실제 스키마가 새 초기화 파일이 만드는 스키마와 다르면(수동 변경 등) 전환 후 엔티티 검증이 실패한다 — 전환 절차에 스키마 일치 확인이 선행되어야 한다.
- 기피물질 카탈로그 시드 파일명이 바뀌므로, 시드 SQL 을 리소스 경로로 하드코딩해 읽는 동기화 테스트가 빈 문자열을 읽어 "파일 없음"이 아닌 **데이터 불일치로 오진**하며 깨진다 — 경로를 반드시 함께 갱신한다.
- 데모 시드가 이미 들어 있는 기존 DB(홈서버·로컬)에 전환 후 데모 시드가 다시 적용되면 중복/충돌이 난다 — 기존 DB 는 시드 재적용 대상에서 제외되어야 한다.
- 통합 테스트는 매번 빈 컨테이너 DB 에 마이그레이션을 적용하므로, 테스트 환경의 적용 범위(데모 시드 포함 여부)가 기존 테스트의 전제(시드 음식 존재 여부)와 어긋나면 무관한 테스트가 깨질 수 있다.
- 배치 애플리케이션은 마이그레이션을 직접 실행하지 않으므로(스키마 소유자는 API 앱) 이번 변경의 직접 영향은 없으나, 전환 후 스키마로 정상 동작해야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 기존 마이그레이션 22개가 만들던 **최종 스키마(테이블 7종: 음식, 기피물질, 음식-기피물질 매핑, 회원, 스캔 이력, 북마크, 업로드 이미지)** 를 스키마 전용 초기화 파일 **하나**로 동일하게 재현해야 한다.
- **FR-002**: **마스터 데이터 — 기피물질 카탈로그 81종(다국어 명칭 포함)** 은 모든 환경(프로덕션 포함)에 공통 적용되는 시드로 유지되어야 한다.
- **FR-003**: **데모 데이터 — 음식 10건·음식 설명·음식-기피물질 매핑** 은 마스터와 분리된 별도 시드로 옮기고, 프로덕션·스테이징에는 적용되지 않아야 한다.
- **FR-004**: 환경 프로필별 적용 범위가 나뉘어야 한다 — 프로덕션·스테이징 = 스키마 + 마스터만, 로컬·dev(및 통합 테스트) = 스키마 + 마스터 + 데모.
- **FR-005**: 기존 데이터가 저장된 DB(홈서버 dev)는 **데이터 손실 0** 으로 새 마이그레이션 이력에 합류해야 한다 — DB 재생성(drop)이 아니라 **이력 재기준선** 방식으로 전환하며, 회원·음식·북마크·스캔 이력·업로드 이미지 데이터가 전량 보존된다. (원 계획의 "drop 후 재생성"은 데이터 유실을 확인함에 따라 홈서버에는 적용하지 않는다.)
- **FR-006**: 기존 마이그레이션 22개 파일은 삭제한다.
- **FR-007**: 기피물질 카탈로그 시드 경로를 하드코딩한 동기화 테스트(`AvoidanceCatalogSeedSyncTest`)의 리소스 경로를 새 파일로 갱신하고, 전체 테스트가 통과해야 한다.
- **FR-008**: 빈 DB·기존 DB 양쪽 모두에서 애플리케이션이 정상 기동하고 엔티티-스키마 정합 검증을 통과해야 한다.

### Key Entities

- **스키마 초기화 파일**: 최종 테이블 7종의 구조(컬럼·제약·인덱스·외래키)만 담는 단일 파일. 데이터는 포함하지 않는다.
- **마스터 시드**: 기피물질 카탈로그 81종. 서비스 운영에 필수인 기준 데이터로, 전 환경 공통. (참고: "국가 코드"는 별도 테이블이 아니라 회원 속성으로 저장되므로 시드 대상이 아니다 — Assumptions 참조.)
- **데모 시드**: 음식 10건과 그 설명·기피물질 매핑. 개발·데모 환경 전용.
- **마이그레이션 이력**: 각 DB 가 어떤 마이그레이션까지 적용했는지의 장부. 기존 DB 는 이 장부만 새 기준선으로 교체된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 빈 DB 를 최종 스키마로 만드는 데 필요한 스키마 파일 수가 22개에서 1개로 줄어든다.
- **SC-002**: 프로덕션 프로필로 초기화한 DB 의 데모 음식 데이터가 0건이고, 기피물질 카탈로그는 81종 전부 존재한다.
- **SC-003**: 기존 홈서버 DB 전환 전후로 전 테이블 행 수가 100% 일치한다(데이터 손실 0건).
- **SC-004**: 전환 후 전체 테스트 스위트 통과율 100%.
- **SC-005**: 신규 개발자가 빈 로컬 DB 를 개발 가능한 상태(스키마+마스터+데모)로 만드는 데 애플리케이션 기동 1회 외의 수작업이 필요 없다.

## Assumptions

- **프로덕션·스테이징 DB 는 아직 프로비저닝되지 않았다**(로컬·홈서버 DB 만 존재). 따라서 마이그레이션 이력 재작성이 가능한 마지막 시점이라는 이슈의 전제를 그대로 따른다.
- **"국가 코드"는 DB 시드 대상이 아니다.** 현재 스키마에 국가 코드 테이블은 없으며, 국가 코드는 회원 프로필의 속성 값으로, 언어 코드는 코드 레벨 열거형으로 관리된다. 따라서 "기본으로 저장되어야 하는 데이터"는 기피물질 카탈로그 81종이 유일하다. (Jira 이슈 본문의 "카탈로그 143건"은 이후 마이그레이션에서 폐기된 카테고리 매핑 행 수로, 최종 상태 기준은 81종이다.)
- **홈서버 DB 는 기존 마이그레이션 22개가 전부 적용된 상태**이며, 스키마가 새 초기화 파일의 결과와 동일하다(초기화 파일 자체를 이 최종 상태에서 도출하므로 구조적으로 보장). 전환 절차에서 일치 여부를 확인한다.
- **로컬 DB 는 개발자 개인 소유**로, 개발자 판단에 따라 재생성(drop)해도 무방하다. 데이터 보존 의무는 홈서버 DB 에만 적용한다.
- 데모 음식 시드는 여러 마이그레이션에 걸쳐 변형된 **최종 상태 기준**으로 재작성한다(초기 시드 원문 그대로가 아님).
- 통합 테스트는 데모 시드까지 포함한 적용 범위로 동작한다(기존 테스트가 시드 음식 존재를 전제할 수 있음).
