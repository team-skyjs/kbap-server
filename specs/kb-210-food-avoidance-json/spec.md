# Feature Specification: 음식 기피성분 매핑을 food 테이블 JSON 컬럼으로 이관

**Feature Branch**: `kb-210-food-avoidance-json`

**Created**: 2026-07-21

**Status**: Draft

**Input**: User description: "kb-210 음식 기피성분 매핑을 food 테이블 JSON 컬럼으로 이관" (Jira KB-210) + 보완 지시: 정렬·유효성 검사는 애플리케이션 레이어 담당(DB는 저장만), 배치 저장 경로는 범위 제외, 구 테이블은 삭제하지 않음

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 음식 상세 조회 동작 무변화 (Priority: P1)

앱 사용자가 음식 상세를 조회하면, 기피성분 저장 구조가 별도 매핑 테이블에서 음식 레코드 내부의 기피성분 목록으로 바뀐 뒤에도 이전과 동일하게 기피성분 목록이 포함 확률 높은 순으로 정렬되어 표시된다. 정렬은 조회 시 애플리케이션이 수행하고, 저장소는 목록을 저장·반환만 한다.

**Why this priority**: 이 작업은 내부 저장 구조 변경이며, 사용자 관점의 유일한 계약은 "기존 응답이 그대로 유지된다"이다. 이것이 깨지면 이관 자체가 실패다.

**Independent Test**: 기피성분이 여러 개 저장된 음식의 상세를 조회해, 응답의 기피성분 목록이 포함 확률 내림차순으로 이전과 동일한 내용·순서인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 기피성분 3개(확률 34%·12%·80%)가 저장된 음식, **When** 상세를 조회하면, **Then** 기피성분이 80% → 34% → 12% 순으로 응답에 포함된다.
2. **Given** 저장 순서가 확률 순이 아닌 기피성분 목록, **When** 상세를 조회하면, **Then** 애플리케이션이 조회 시점에 확률 내림차순으로 정렬해 반환한다(저장 순서 무관).
3. **Given** 기피성분이 하나도 없는 음식, **When** 상세를 조회하면, **Then** 기피성분 목록이 빈 목록으로 응답되고 오류가 없다.
4. **Given** 사용자가 기피 등록한 성분을 포함한 음식, **When** 상세·목록을 조회하면, **Then** 위험도 판정(overall risk)이 이관 전과 동일하게 계산된다.

---

### User Story 2 - 기존 데이터 백필 (Priority: P2)

기존에 별도 매핑 테이블(`food_avoidance_substance`)에 쌓인 음식별 기피성분 데이터가 손실 없이 음식 레코드의 기피성분 목록으로 복사되고, 원본 테이블과 데이터는 그대로 보존된다.

**Why this priority**: 새 구조가 기존 데이터 없이 비어 있으면 P1의 조회 계약이 성립하지 않는다. 원본은 검증·롤백 대비를 위해 삭제하지 않는다.

**Independent Test**: 백필 후, 원본 매핑 테이블의 (음식, 성분 코드, 확률) 전체 집합과 각 음식 레코드의 기피성분 목록 합집합이 일치하는지 대조한다.

**Acceptance Scenarios**:

1. **Given** 구 매핑 테이블에 N건의 (음식, 성분, 확률) 데이터, **When** 백필을 수행하면, **Then** 각 음식 레코드의 기피성분 목록에 동일한 성분 코드·확률이 모두 존재한다.
2. **Given** 백필 완료 상태, **When** 구 매핑 테이블을 확인하면, **Then** 원본 데이터가 변형·삭제 없이 그대로 남아 있다.
3. **Given** 매핑이 0건인 음식, **When** 백필을 수행하면, **Then** 해당 음식의 기피성분 목록은 빈 목록으로 취급되고 오류가 없다.

---

### Edge Cases

- 기피성분이 0건인 음식은 이관 후에도 빈 목록으로 취급되어 조회·위험도 판정이 정상 동작해야 한다.
- 저장된 목록의 순서가 어떤 순서든(입력 순서·코드 순서 등) 조회 응답의 정렬 결과는 항상 확률 내림차순이어야 한다.
- 백필 대상 데이터에 확률 경계값(0, 100)이 있어도 그대로 보존되어야 한다.
- 형식이 어긋난 저장 값(예: 수동 조작으로 생긴 비정상 목록)은 저장소가 아니라 애플리케이션이 읽기 시점에 감지·처리한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 음식 레코드는 자신의 기피성분 목록(성분 코드 + 포함 확률의 쌍)을 단일 속성으로 소유해야 한다.
- **FR-002**: 저장소(DB)는 기피성분 목록을 저장·반환만 하며, 정렬·유효성 검사 책임을 지지 않는다 — 목록 값에 대한 저장소 수준 제약(체크 제약·유일 제약 등)을 추가하지 않는다.
- **FR-003**: 음식 상세 조회는 애플리케이션 레이어에서 기피성분 목록을 포함 확률 내림차순으로 정렬해 반환해야 하며, 이관 전 응답과 내용·순서가 동일해야 한다.
- **FR-004**: 기피성분 값(코드·확률)의 유효성 판단이 필요한 경우 애플리케이션 레이어가 수행한다.
- **FR-005**: 사용자 기피 성분 기반 위험도 판정은 새 저장 구조를 기반으로 이관 전과 동일한 결과를 내야 한다.
- **FR-006**: 구 매핑 테이블의 기존 데이터는 손실·변형 없이 새 구조로 백필되어야 하며, 원본 테이블과 데이터는 삭제·변경하지 않는다.
- **FR-007**: 스키마 변경(컬럼 추가·백필)은 프로젝트의 마이그레이션 버전 규칙(timestamp 버전, 독립 실행 가능)을 따라야 한다.
- **FR-008**: 관련 자동화 테스트는 새 구조 기준으로 갱신되어 전체 테스트가 통과해야 한다.

### Key Entities

- **Food(음식)**: 스캔·검색 대상 음식. 이관 후 자신의 기피성분 목록을 내장 속성으로 직접 소유한다.
- **기피성분 항목**: 성분 코드(예: SOY, MILK)와 포함 확률(0~100 정수)의 쌍. 이관 전에는 별도 매핑 테이블의 행, 이관 후에는 음식 레코드 내 목록의 원소.
- **FoodAvoidanceSubstance(구 매핑)**: 음식-성분 다대다 매핑 행. 백필의 원본이며 이번 작업에서 테이블·데이터를 보존한다(제거는 후속 작업).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 이관 전후 음식 상세 조회 응답의 기피성분 목록(내용·정렬)이 100% 동일하다.
- **SC-002**: 구 매핑 테이블의 모든 (음식, 성분, 확률) 데이터가 손실 0건으로 새 구조에 존재하고, 원본 테이블도 그대로 남아 있다.
- **SC-003**: 조회 응답의 정렬이 저장 순서와 무관하게 항상 확률 내림차순이다(저장 순서를 뒤섞어도 결과 동일).
- **SC-004**: 새 구조 기준으로 갱신된 전체 테스트 스위트가 통과한다.

## Out of Scope

- **배치 스코어링 저장 경로 전환**: 배치(`AvoidanceScoringJob`) 쪽 코드는 이번 작업에서 건드리지 않는다 — 기존 매핑 테이블 저장 경로를 유지하며, 전환은 후속 작업이다.
- **구 매핑 테이블·관련 코드 제거**: 백필 원본 보존을 위해 `food_avoidance_substance` 테이블과 기존 저장 경로는 삭제하지 않는다.
- **특정 성분 기준 음식 역조회**: 현재 요구가 없어 범위 밖이다.

## Assumptions

- 배치가 구 매핑 테이블에 계속 기록하는 동안 새 목록 컬럼과 원본 사이에 시차가 생길 수 있다 — 이번 작업의 백필은 마이그레이션 시점 스냅샷 1회이며, 지속 동기화는 배치 전환(후속 작업)에서 해결한다.
- 음식 1건당 기피성분 개수는 소수(카탈로그 성분 수 이하)로, 단일 속성 내 목록 저장에 크기 문제가 없다.
- 백필은 서비스 중단 없이 마이그레이션 단계에서 1회 수행하며, 별도 병행 기록(dual-write) 기간은 두지 않는다.
- 상세 조회 외 화면(목록·홈)의 기피성분 노출 규칙은 기존 로직을 그대로 따르며 이 작업에서 변경하지 않는다.
