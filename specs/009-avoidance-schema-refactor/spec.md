# Feature Specification: 기피 성분 데이터 구조 정리 — 미사용 분류 제거 + 다국어 저장 단순화

**Feature Branch**: `009-avoidance-schema-refactor`

**Created**: 2026-07-03

**Status**: Draft

**Input**: User description: "기피 성분(avoidance) 데이터 구조 정리 — 미사용 분류 카테고리 제거 + 다국어 번역 저장 방식 단순화. 81종 기피 성분 카탈로그에서 (1) 조회·활용 기능이 없는 3분류 카테고리를 제거하고, (2) 언어마다 나뉘어 저장되는 다국어 번역을 언어 확장에 유연한 단일 저장 방식으로 통합한다. 대상은 기피 성분 카탈로그에 한정하며, 음식 재료·이름·설명 번역과 사용자 대상 API 동작은 바꾸지 않는다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 다국어 번역 저장 방식 단순화 (Priority: P1)

기피 성분 카탈로그를 유지하는 담당자 입장에서, 새로운 지원 언어를 추가할 때 성분마다 저장 구조 자체를 바꾸지 않고 번역만 채워 넣을 수 있어야 한다. 현재는 언어가 늘어날 때마다 저장 구조가 함께 늘어나 확장 비용이 크다. 저장 방식을 언어 확장에 유연한 단일 형태로 통합해 이 비용을 없앤다.

**Why this priority**: 앞으로의 언어 확장(현재 한국어 외 9개 언어) 비용을 직접 줄이는 변경이며, 이후 다른 다국어 데이터의 기준이 되는 구조적 결정이다.

**Independent Test**: 기존 81종 성분에 대해 각 지원 언어로 이름을 조회했을 때, 변경 전과 동일한 결과가 나오는지(요청 언어 번역이 없으면 한국어로 폴백) 확인하면 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 81종 성분과 각 성분의 기존 다국어 이름이 있는 상태에서, **When** 임의의 지원 언어로 성분 이름을 조회하면, **Then** 저장 방식 변경 전과 동일한 이름을 반환한다.
2. **Given** 특정 성분에 요청 언어의 번역이 없는 상태에서, **When** 그 언어로 이름을 조회하면, **Then** 한국어 이름으로 폴백해 반환한다.
3. **Given** 새로운 지원 언어를 도입하려는 상황에서, **When** 그 언어의 번역을 성분들에 추가하면, **Then** 저장 구조를 변경하지 않고 번역만 채워 확장이 완료된다.

---

### User Story 2 - 미사용 분류 카테고리 제거 (Priority: P2)

기피 성분 카탈로그를 유지하는 담당자 입장에서, 실제로 조회·활용되지 않는 3분류 카테고리를 데이터와 코드에서 걷어내 유지 대상을 줄인다. 이 분류는 어떤 사용자 대상 기능에도 노출되거나 사용되지 않으므로, 제거해도 관찰 가능한 동작은 달라지지 않는다.

**Why this priority**: 순수한 부채 정리로 사용자 가치에 직접 기여하지는 않지만, 카탈로그의 유지 표면을 줄여 이후 변경을 단순하게 한다.

**Independent Test**: 분류 카테고리가 데이터·코드에서 완전히 사라진 뒤에도 성분 조회·연결 등 기존 기능이 정상 동작하는지 확인하면 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 카테고리를 제거한 상태에서, **When** 성분 카탈로그를 조회하거나 재료와 성분을 연결하면, **Then** 카테고리 없이도 정상 동작한다.
2. **Given** 카테고리 제거 이후, **When** 전체 빌드·테스트를 실행하면, **Then** 카테고리에 의존하던 잔여 코드 없이 통과한다.

---

### Edge Cases

- 요청 언어가 지원 언어 목록에 없을 때 → 한국어로 폴백한다(기존 동작 유지).
- 특정 성분이 일부 언어 번역만 가진 경우 → 있는 언어는 해당 번역, 없는 언어는 한국어 폴백.
- 번역이 하나도 없는 성분 → 모든 비-한국어 조회가 한국어로 폴백한다.
- 카테고리 제거가 재료↔성분 연결 등 다른 카탈로그 관계에 영향을 주지 않아야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 기피 성분의 3분류 카테고리 개념을 데이터와 코드에서 제거해야 한다.
- **FR-002**: 카테고리 제거 후에도 성분 카탈로그 조회 및 재료↔성분 연결 등 기존 기능이 정상 동작해야 한다.
- **FR-003**: 시스템은 기피 성분의 다국어 번역을 언어 확장에 유연한 단일 저장 방식으로 통합해야 한다.
- **FR-004**: 저장 방식 통합 후에도 기존 81종 성분의 각 지원 언어 이름은 변경 전과 동일하게 조회되어야 한다.
- **FR-005**: 요청 언어의 번역이 없을 때 시스템은 한국어 이름으로 폴백해야 한다.
- **FR-006**: 새로운 지원 언어를 추가할 때 저장 구조를 변경하지 않고 번역 값만 추가해 확장할 수 있어야 한다.
- **FR-007**: 이번 변경은 기피 성분 카탈로그에 한정되며, 음식 재료·이름·설명의 번역 저장 방식은 변경하지 않아야 한다.
- **FR-008**: 사용자 대상 API 의 동작과 응답은 이번 변경으로 달라지지 않아야 한다(카테고리는 원래 노출되지 않았고, 언어별 이름 조회 결과는 동일해야 한다).

### Key Entities *(include if feature involves data)*

- **기피 성분(Avoidance Substance)**: 회피·주의 대상 성분 81종. 한국어 이름과 여러 지원 언어의 번역 이름을 가진다. 이번 변경 이후 분류 카테고리를 더 이상 갖지 않으며, 다국어 번역은 단일 유연 저장 방식으로 보관한다.
- **분류 카테고리(Classification Category)**: 성분에 부여되던 3종 분류 개념. 조회·활용되지 않아 이번 변경으로 제거된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 기존 81종 성분 전부에 대해 각 지원 언어 이름 조회 결과가 변경 전과 100% 동일하다(번역이 없는 경우 한국어 폴백).
- **SC-002**: 새로운 지원 언어 1종을 추가할 때 저장 구조 변경 없이 번역 데이터 추가만으로 확장이 완료된다.
- **SC-003**: 분류 카테고리가 데이터·코드에서 완전히 사라지며, 그로 인한 기능 회귀가 0건이다(전체 빌드·테스트 통과).
- **SC-004**: 사용자 대상 API 의 요청·응답 계약이 변경 전후로 동일하다.

## Assumptions

- 기피 성분 카탈로그(81종)와 기존 다국어 이름 데이터가 이미 존재하며, 저장 방식 변경 시 기존 값이 보존·이전되어야 한다.
- 분류 카테고리는 시딩된 데이터만 존재하고 이를 조회·활용하는 사용자 대상 기능이 없다(제거해도 관찰 가능한 동작 변화 없음).
- 지원 언어 집합(한국어 기준 + 다수 언어)은 기존 시스템의 언어 정의를 그대로 재사용한다.
- 다국어 이름 조회 시 한국어를 기본 폴백으로 사용하는 기존 정책을 유지한다.
- 데이터 저장소는 이미 배포되어 운영 중이므로, 기존 데이터를 보존하며 앞으로 나아가는 방식으로 구조를 변경한다(기존 데이터 손실 없음).
