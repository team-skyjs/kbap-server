# Feature Specification: 홈 화면 조합 서비스 퍼사드화

**Feature Branch**: `010-home-service-facade`

**Created**: 2026-09-30

**Status**: Draft

**Input**: User description: "서비스 클래스를 새롭게 추가하여 HomeService가 퍼사드 역할처럼 보이게 만들 것이다. repository랑 service가 혼합된 구조를 개선한다. reviewService의 역할은 fooodService로 이관하며 리뷰가 많은 음식 조회 메서드로 지정한다. 최대한 서비스 메서드를 호출호출호출 하는 구조로 간단히 만들고 HomeResult 구조는 변경 없이 기존과 동일하게 응답이 나갈 수 있도록 한다. 테스트 코드는 기존 getHome 메서드의 응답 결과 테스트를 유지한 채, 리팩토링 이후 통과하는지 여부를 확인해 안정성을 챙긴다."

## 배경

홈 화면 조회는 기피 성분·인기 음식·리뷰 많은 음식·최근 스캔 네 섹션을 한 응답으로 묶는다. 현재 홈 조합 서비스는 이 네 섹션을 만들기 위해 회원·음식·스캔·리뷰 서비스와 성분 저장소를 **한 메서드 안에서 섞어** 호출하고, 각 섹션의 id 목록을 음식으로 되찾아 카드로 바꾸는 조립 로직까지 직접 갖고 있다. 그 결과 홈 조합 서비스가 "무엇을 모으는가"가 아니라 "어떻게 만드는가"를 드러내고, 저장소 직접 접근과 서비스 호출이 한 층에 공존한다.

이 작업은 **동작 변경이 없는 구조 개선**이다. 홈 조합 서비스는 각 섹션을 담당 서비스에 한 번씩 요청해 결과만 모으는 퍼사드가 되고, 섹션을 만드는 세부 로직은 각 섹션의 소유 도메인으로 내려간다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 홈 응답은 리팩토링 전후로 동일하다 (Priority: P1)

앱 사용자(회원·비회원)가 홈 화면을 열면, 리팩토링 이전과 **완전히 같은 형태·같은 내용·같은 순서**의 응답을 받는다. 사용자는 구조 개선을 인지할 수 없어야 한다.

**Why this priority**: 이 작업의 존재 이유가 "동작을 바꾸지 않는 구조 개선"이다. 응답이 한 항목이라도 달라지면 실패다.

**Independent Test**: 기존 홈 조회 통합 테스트(회원 시나리오·비회원 시나리오·언어 시나리오·위험도 판정 시나리오) 를 **한 줄도 고치지 않고** 리팩토링 후 실행해 전부 통과하는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 기피 성분과 스캔 이력이 있는 회원, **When** 홈을 조회하면, **Then** 기피 성분·인기 음식·리뷰 많은 음식·최근 스캔 네 섹션이 리팩토링 전과 같은 내용·순서로 한 응답에 담긴다.
2. **Given** 인증 헤더가 없는 비회원 요청, **When** 홈을 조회하면, **Then** 개인화 섹션(기피 성분·최근 스캔)은 빈 배열이고 인기 음식·리뷰 많은 음식만 내려온다.
3. **Given** 리뷰 수가 다른 음식들, **When** 홈을 조회하면, **Then** 리뷰 많은 음식 섹션은 리뷰 수 내림차순이고 리뷰 0건 음식은 빠지며 회원·비회원의 순서가 같다.
4. **Given** 같은 메뉴를 여러 번 스캔한 회원, **When** 홈을 조회하면, **Then** 최근 스캔에 중복 없이 최신 1건만 나타난다.
5. **Given** 기피 성분을 100% 포함한 음식과 그 성분을 회피하는 회원, **When** 홈을 조회하면, **Then** 본인 프로필 기준 위험도 판정이 리팩토링 전과 같다.
6. **Given** lang 파라미터(ko·ja·en·미지원 값), **When** 홈을 조회하면, **Then** 음식명·기피 성분명의 언어 선택 규칙이 리팩토링 전과 같다.

---

### User Story 2 - 홈 조합 서비스는 섹션별 서비스 호출만 나열한다 (Priority: P2)

유지보수 개발자가 홈 조합 서비스를 열면, 네 섹션 각각이 **담당 서비스 메서드 한 번 호출**로 얻어지는 것을 즉시 읽을 수 있다. 홈 조합 서비스에는 저장소 직접 접근, id 목록을 음식으로 되찾는 재조회, 카드 변환 반복 같은 조립 세부가 남아 있지 않다.

**Why this priority**: 사용자 가치(P1)를 지키면서 얻으려는 구조적 목표다. P1 없이 P2만 있으면 위험하고, P2 없이 P1만 있으면 작업의 의미가 없다.

**Independent Test**: 홈 조합 서비스의 의존 목록에 저장소가 없고, 홈 조회 메서드 본문이 "회원 해석 → 섹션별 서비스 호출 → 결과 조립"만으로 구성돼 있는지 코드 리뷰로 확인한다.

**Acceptance Scenarios**:

1. **Given** 리팩토링된 홈 조합 서비스, **When** 의존 목록을 보면, **Then** 저장소 타입이 없고 서비스 타입만 있다.
2. **Given** 리팩토링된 홈 조합 서비스의 홈 조회 메서드, **When** 본문을 읽으면, **Then** 각 섹션이 서비스 메서드 호출 하나로 채워지며, 섹션 내부 로직(id 재조회·정렬 유지·카드 변환)은 홈 조합 서비스에 없다.

---

### User Story 3 - 리뷰 많은 음식 조회는 음식 서비스가 소유한다 (Priority: P3)

"리뷰가 많은 음식"은 결과가 **음식 목록**이므로 음식 서비스의 책임으로 옮긴다. 홈 조합 서비스는 리뷰 서비스를 더 이상 알지 않고, 음식 서비스에 "리뷰 많은 음식 N개"를 요청한다.

**Why this priority**: P2 의 구체 항목 중 사용자가 명시적으로 지목한 이관이다. 나머지 섹션(기피 성분·최근 스캔)의 이관 방식은 P2 원칙만 지키면 된다.

**Independent Test**: 홈 조합 서비스의 의존 목록에 리뷰 서비스가 없고, 음식 서비스에 리뷰 많은 음식 목록을 돌려주는 메서드가 있으며, 홈의 리뷰 많은 음식 섹션 테스트가 통과한다.

**Acceptance Scenarios**:

1. **Given** 리팩토링된 음식 서비스, **When** 리뷰 많은 음식 N개를 요청하면, **Then** 리뷰 수 내림차순으로 정렬된 준비 완료(READY) 음식 목록을 최대 N개 돌려주고, 리뷰 0건 음식은 포함하지 않는다.
2. **Given** 리팩토링된 홈 조합 서비스, **When** 의존 목록을 보면, **Then** 리뷰 서비스가 없다.

---

### Edge Cases

- 회원 id 가 있으나 활성 회원이 아니면(탈퇴·삭제) 회원 없음 오류(`MEMBER_NOT_FOUND`)로 거절한다 — 2026-09-30 구현 중 결정으로 기존의 "비회원 강등" 을 대체. 유효 토큰이 있는데 활성 회원이 아닌 상태는 정상 경로가 아니다.
- 리뷰 많은 음식 id 가 준비 완료(READY) 가 아닌 음식을 가리키면 그 음식은 섹션에서 빠지고 나머지 순서는 유지된다 — 기존 동작 유지.
- 최근 스캔 id 목록에 삭제·미준비 음식이 섞여 있으면 그 항목만 빠진다 — 기존 동작 유지.
- 기피 성분을 하나도 고르지 않은 회원은 성분 조회 없이 빈 목록을 받는다 — 기존 동작 유지.
- 회원의 언어 프로필 값과 요청 lang 이 다르면 요청 lang 이 우선한다 — 기존 동작 유지.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 홈 조회 응답의 **구조(네 섹션과 각 카드 필드)·내용·정렬 순서**는 리팩토링 전과 동일해야 한다. 응답 결과 타입은 변경하지 않는다.
- **FR-002**: 홈 조합 서비스는 **저장소를 직접 의존하지 않아야** 하며, 서비스만 의존한다.
- **FR-003**: 홈 조합 서비스의 홈 조회는 각 섹션을 **담당 서비스 메서드 한 번 호출**로 얻고, 그 결과를 응답 결과 타입으로 조립하는 역할만 가져야 한다. 섹션 내부 조립(id 목록 → 음식 재조회·원 순서 유지·카드 변환)은 홈 조합 서비스 밖에 있어야 한다.
- **FR-004**: "리뷰 많은 음식 목록" 조회는 **음식 서비스가 제공**해야 하며, 홈 조합 서비스는 리뷰 서비스를 의존하지 않아야 한다. 이름은 서비스 메서드 네이밍 규칙(목록 조회 `get~s`)을 따르며 "리뷰가 많은 음식" 을 드러낸다.
- **FR-005**: 기피 성분 섹션(회원이 고른 성분 코드 → 표시명 목록)은 **저장소가 아닌 서비스**를 통해 얻어야 한다. 이를 위해 새 서비스를 추가하거나 기존 소유 도메인 서비스에 메서드를 추가한다.
- **FR-006**: 최근 스캔 섹션(회원의 최근 스캔 음식 카드 목록)은 홈 조합 서비스가 id 재조회를 직접 수행하지 않고, 담당 서비스가 **카드 목록 또는 음식 목록**으로 돌려줘야 한다.
- **FR-007**: 기존 홈 조회 통합 테스트(회원·비회원·언어·위험도·리뷰 많은 음식·최근 스캔 중복 제거 시나리오)는 **수정 없이 그대로** 리팩토링 후 통과해야 한다. 테스트를 통과시키기 위해 테스트를 고치는 것은 허용하지 않는다.
- **FR-008**: 새로 추가되거나 이관된 서비스 메서드는 프로젝트 테스트 규약에 맞는 검증을 갖거나, 기존 홈 통합 테스트가 그 동작을 이미 커버함을 확인해야 한다.
- **FR-009**: 트랜잭션 경계·소프트 삭제 필터·읽기 전용 조회 규약 등 기존 데이터 접근 규약은 이관 후에도 유지되어야 한다.

### Key Entities

- **홈 응답 결과**: 기피 성분 목록·인기 음식 카드 목록·리뷰 많은 음식 카드 목록·최근 스캔 카드 목록의 네 섹션. 구조 불변.
- **음식 카드**: 음식 요약 표시 단위(이름·이미지·위험도·리뷰 평점/수). 구조 불변.
- **기피 성분 표시 항목**: 성분 코드와 요청 언어의 표시명. 구조 불변.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 기존 홈 조회 통합 테스트 전 시나리오가 **테스트 코드 변경 0줄**로 리팩토링 후 100% 통과한다.
- **SC-002**: 홈 조합 서비스의 의존 목록에서 **저장소 타입 0개·리뷰 서비스 0개**가 된다.
- **SC-003**: 홈 조합 서비스의 홈 조회 메서드에서 네 섹션이 **각각 서비스 호출 1개**로 채워진다(섹션당 재조회·변환 반복 없음).
- **SC-004**: api 모듈 전체 테스트(아키텍처 규칙 포함)가 리팩토링 후 통과한다.
- **SC-005**: 홈 조회의 외부 계약(경로·헤더·응답 봉투·필드명)에 변경이 없어 클라이언트 수정이 필요 없다.

## Assumptions

- "서비스 클래스를 새롭게 추가"는 **홈 조합 서비스가 저장소를 직접 만지지 않게 하기 위한 소유 도메인 서비스**를 뜻한다. 기피 성분 섹션은 성분 도메인이 소유하므로 성분 서비스(신규)가 가장 자연스러운 후보이며, 구체 위치·이름은 플랜에서 정한다.
- 리뷰 많은 음식 조회를 음식 서비스로 옮기되, **리뷰 수 집계 자체는 여전히 리뷰 도메인 저장소가 제공**한다. 음식 서비스가 리뷰 저장소(또는 리뷰 서비스)를 의존하는 것은 허용한다 — 도메인 간 허용 방향은 플랜에서 아키텍처 규칙으로 확인한다.
- 최근 스캔 섹션의 "id 목록 → 음식 카드" 조립은 스캔 서비스 또는 음식 서비스 중 한 곳으로 내려가며, 어느 쪽이 소유할지는 플랜에서 결정한다. 어느 쪽이든 홈 조합 서비스는 호출 1개만 가진다.
- 인기 음식 섹션은 이미 음식 서비스 호출 1개로 얻고 있으므로 카드 변환만 서비스 쪽으로 옮긴다.
- 섹션별 개수(인기 5·최근 스캔 10·리뷰 많은 음식 10)는 기존 값을 유지한다.
- 성능 목표는 별도로 두지 않는다. 섹션별 서비스가 각자 회원 기피 성분을 조회하면서 회원 단건 조회가 몇 회 늘어나는 것은 감수한다(기본키 조회, 한 읽기 트랜잭션 안). 음식·리뷰·스캔 쪽 조회 수는 늘어나지 않아야 한다.
- 관리자 화면 등 홈 조합 서비스 외의 소비자는 이 작업의 대상이 아니다.
