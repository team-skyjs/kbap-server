## 배경

관리자 기능은 두 층으로 나뉘어 있다. **화면 층**(`/admin/**`, 서버 렌더링 페이지, 로그인 폼 + 쿠키)이 대시보드·음식 목록/상세/편집·시드·이미지 배치·회원 목록/상세를 담당하고, **REST 층**(`/api/admin/**`, 관리자 토큰)은 시드·이미지 제출·앱 버전·랭체인 콜백 7개뿐이다. 관리자 화면을 React 로 분리하려면 화면 층이 들고 있던 데이터와 조작을 REST 로 열어야 한다.

운영자 인터뷰(2026-08-25)에서 확인된 핵심 문제:
- 파이프라인에 **개입**하는 정식 수단(승인·반려·개별 재수집·이미지 교체·배치 회수)이 없어 **상태 드롭다운이 백도어**로 쓰인다 — 재료 무검증 저장으로 앱 사용자 음식 상세가 500 이 날 수 있고, 재료·이미지 없는 음식이 READY 로 노출될 수 있다.
- 회원은 검색·탈퇴자 조회·제재·활동 이력이 없고, 정지 회원은 엉뚱한 에러 코드를 받는다.
- 어떤 관리자 조작도 **누가·언제·무엇을** 바꿨는지 기록되지 않는다.
- 신 화면(SPA)이 관리자 토큰을 얻을 경로가 없다(쿠키 로그인뿐).

이 기능은 **구 화면을 그대로 살려둔 채** 신 화면이 쓸 REST 를 만들고, 그 REST 에서 검증·전이 규칙·감사 기록을 강제한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 신 관리자 화면 로그인과 감사 기록 (Priority: P1)

운영자가 신 관리자 화면에서 아이디/비밀번호로 로그인하면 이후 모든 관리자 API 호출에 쓸 자격을 받는다. 자격이 만료되면 재로그인 없이 갱신할 수 있다. 로그인을 5회 연속 실패하면 잠시 잠긴다. 관리자가 데이터를 바꾸는 모든 조작(음식 수정·승인·삭제, 회원 제재 등)은 "누가·언제·어떤 대상을·이전값→이후값" 으로 감사 이력에 남고, 운영자는 대상별 이력을 조회할 수 있다.

**Why this priority**: 이것이 없으면 신 화면 자체가 동작할 수 없고, 이후 모든 파괴적 조작의 책임 추적이 불가능하다. 앱 버전 오설정 같은 전 사용자 잠금 사고의 롤백 근거가 된다.

**Independent Test**: 관리자 계정으로 로그인 → 자격으로 관리자 API 1개 호출 성공 → 회원 계정 자격으로 같은 API 호출 시 거부 → 어떤 쓰기 조작 후 감사 이력 조회에 그 조작이 남아 있음 → 비밀번호 5회 오류 후 정답 입력도 거부됨.

**Acceptance Scenarios**:

1. **Given** 유효한 관리자 계정, **When** 아이디/비밀번호로 로그인 요청, **Then** 관리자 자격(액세스·갱신)을 받고 관리자 API 를 호출할 수 있다.
2. **Given** 잘못된 비밀번호 5회 연속, **When** 6번째에 올바른 비밀번호로 시도, **Then** 잠금 안내와 함께 거부되며, 잠금 시간 경과 후에는 성공한다.
3. **Given** 일반 회원 자격, **When** 관리자 API 호출, **Then** "관리자 전용" 오류로 거부된다.
4. **Given** 관리자 자격, **When** 회원 전용 API(예: 내 프로필 조회) 호출, **Then** 거부된다(관리자 자격은 회원 자격으로 통하지 않는다).
5. **Given** 관리자가 음식 A 의 설명을 수정, **When** 음식 A 의 감사 이력 조회, **Then** 조작자·시각·조작 종류·이전 설명·이후 설명이 한 건으로 남아 있다.
6. **Given** 액세스 자격 만료, **When** 갱신 자격으로 갱신 요청, **Then** 새 액세스 자격을 받고 작업을 이어간다.

### User Story 2 - 음식 콘텐츠 검수와 안전한 상태 전이 (Priority: P1)

운영자가 승인 대기 음식을 보고 **승인** 또는 **반려(사유 필수)** 한다. 음식 정보를 수정할 때는 재료 코드가 카탈로그에 있고 비율이 범위 안일 때만 저장되며, 다른 사람이 먼저 바꿨으면 덮어쓰지 않고 충돌을 알린다. 상태는 수정 화면에서 바꿀 수 없고, 허용된 전이(승인·반려·재제출 등)만 별도 조작으로 한다. 실패 상태를 벗어나면 남아 있던 실패 사유가 정리된다.

**Why this priority**: 인터뷰의 사고 위험 1·2·3 번(앱 상세 500, 부적합 음식 READY 노출, 편집 불가)을 직접 막는다. 검수는 매일 반복되는 핵심 운영 업무다.

**Independent Test**: 승인 대기 음식 1건을 승인 → READY 로 바뀌고 검색 동기화가 예약됨 / 다른 1건을 사유와 함께 반려 → 반려 사유·횟수가 남음 / 카탈로그에 없는 재료 코드로 수정 → 거부 / 오래된 버전으로 수정 → 충돌 거부.

**Acceptance Scenarios**:

1. **Given** 승인 대기(PENDING_REVIEW) 음식, **When** 승인, **Then** 상태가 READY 가 되고 벡터 동기화가 예약되며 감사 이력이 남는다.
2. **Given** 승인 대기 음식, **When** 사유 없이 반려, **Then** 거부된다. **When** 사유와 함께 반려, **Then** 반려 사유와 반려 횟수가 증가해 기록된다.
3. **Given** 재료가 비어 있거나 이미지가 없는 음식, **When** 승인 시도, **Then** 이유를 명시해 거부된다.
4. **Given** 어떤 음식, **When** 카탈로그에 없는 재료 코드 또는 비율 0/101 로 수정, **Then** 어떤 항목이 왜 틀렸는지와 함께 거부되고 데이터는 바뀌지 않는다.
5. **Given** 운영자 A 가 상세를 열어 둔 사이 B 가 저장, **When** A 가 이전 버전 번호로 저장, **Then** 충돌로 거부되고 최신 버전을 다시 받으라는 안내를 받는다.
6. **Given** 수정 요청에 상태 값이 포함됨, **When** 저장, **Then** 상태는 무시되거나 거부된다(상태 전이는 전용 조작으로만).
7. **Given** FAILED 상태(실패 유형·사유 있음) 음식, **When** 허용 전이로 FAILED 를 벗어남, **Then** 실패 유형·사유가 비워진다.
8. **Given** 어떤 음식, **When** 현재 상태에서 허용되지 않는 전이 요청, **Then** 허용 전이 목록과 함께 거부된다.

### User Story 3 - 음식 탐색과 상황 파악 (Priority: P1)

운영자가 음식을 id·이름·재료 코드·번역명으로 찾고, 상태·실패 유형으로 거르고, 최근 갱신순 등으로 정렬하며, 한 페이지 크기를 고른다. 목록에는 id·상태·실패 유형·맵기·이미지 유무·갱신 시각·리뷰 수가 보인다. 상세에는 번역과 재료가 구조화된 형태로 오고, 그 음식의 콘텐츠 수집 이력·이미지 생성 이력·검색 동기화 상태·리뷰 요약·검수 횟수·긴 설명·매칭키가 함께 온다. 대시보드는 기간을 지정할 수 있고 상태 이름이 한 가지로 통일돼 있으며, 비용 지표는 집계 범위가 명시된다.

**Why this priority**: 검수·개입의 전제가 "어떤 음식을 먼저 볼지" 를 찾는 것이다. 현재는 200건 고정 카드에서 눈으로 찾고, 이력은 세 화면을 오가야 한다.

**Independent Test**: 재료 코드로 검색해 해당 음식만 나옴 / 실패 유형 필터로 NOT_FOOD 만 나옴 / 상세 응답 한 번에 수집·이미지·벡터 이력이 포함됨 / 대시보드를 30일로 조회.

**Acceptance Scenarios**:

1. **Given** 음식 200건 이상, **When** 검색어에 숫자 id 를 입력, **Then** 그 id 의 음식이 나온다. **When** 재료 코드 `PEANUT` 로 검색, **Then** 그 재료를 포함한 음식만 나온다.
2. **Given** 실패 음식이 여러 유형, **When** 실패 유형 `NOT_FOOD` 로 필터, **Then** 그 유형만 나온다.
3. **Given** 목록, **When** 갱신 시각 오름차순 정렬, **Then** 가장 오래 방치된 음식이 먼저 나온다. **When** 페이지 크기 50 지정, **Then** 50건 단위로 나온다.
4. **Given** 어떤 음식, **When** 상세 조회, **Then** 번역은 언어별 항목으로, 재료는 코드·비율 목록으로 오고, 최근 수집 요청 이력·이미지 배치 아이템(실패 사유 포함)·벡터 동기화 상태·리뷰 수/평균·검수 횟수·긴 설명·매칭키가 한 응답에 있다.
5. **Given** 대시보드, **When** 기간 30일 지정, **Then** 스캔·신규 음식·비용 지표가 30일 기준으로 온다. 비용 지표에는 "스캔 비전·이미지 성공분만 집계" 같은 범위 설명이 함께 온다.
6. **Given** 대시보드와 목록, **When** 각각의 상태 표시를 비교, **Then** 같은 상태는 같은 이름으로 온다.

### User Story 4 - 파이프라인 개입 (Priority: P2)

운영자가 특정 음식 하나만 다시 수집 요청하고, READY 인 음식의 사진을 노출 중단 없이 다시 생성하거나 직접 업로드해 교체한다. 이미지 배치의 아이템별 결과(실패 사유·외부 배치 식별자)를 보고, 완료된 배치를 정시 대기 없이 즉시 회수하며, 실패 아이템을 골라 재제출한다. 오래 발행 상태에 머문(고착) 수집 요청을 찾아 재발행하거나 취소한다. 검색 동기화 실패를 한 번에 재시도하고, 적재 요청 결과(몇 건 예약·몇 건 잔여)를 즉시 안다. 시드 등록 결과로 생성된 id·중복으로 건너뛴 이름·삭제 음식과 충돌한 이름을 받는다. 삭제한 음식을 다시 보고 복구한다. 여러 음식을 골라 일괄 승인·재수집·삭제한다. 재료 카탈로그를 조회한다.

**Why this priority**: 사고 위험 7·8 번(과포함 재수집, 고착 아웃박스)과 매일의 번거로움(3시간 대기, 200번 클릭)을 없앤다. US2·3 없이도 독립 배포 가능하지만 검수보다는 후순위다.

**Independent Test**: 음식 1건 재수집 → 그 음식만 수집 요청이 생김 / READY 음식 이미지 재생성 → 상태 READY 유지된 채 새 배치 아이템 생성 / 배치 즉시 회수 → 결과 반영 / 고착 요청 재발행 → 대기 상태로 복귀 / 삭제 음식 복구 → 목록에 재등장.

**Acceptance Scenarios**:

1. **Given** 이름이 비슷한 음식 여러 건, **When** 음식 1건 지정 재수집, **Then** 그 음식만 수집 요청이 생기고, 이미 대기 중이면 중복 생성 없이 그 사실을 알린다.
2. **Given** READY 음식, **When** 이미지 재생성 요청, **Then** 상태는 READY 로 유지된 채 이미지 생성 아이템이 생긴다. **When** 파일 업로드로 교체, **Then** 새 이미지가 즉시 반영된다.
3. **Given** 이미지 배치, **When** 배치 상세 조회, **Then** 아이템별 음식·상태·실패 사유·외부 배치 식별자·프롬프트 버전이 온다. **When** 즉시 회수 요청, **Then** 완료된 결과가 반영된다(진행 중이면 그 사실을 알린다).
4. **Given** 발행 후 N시간 넘게 완료되지 않은 수집 요청, **When** 고착 조회, **Then** 그 건들이 경과 시간과 함께 나온다. **When** 재발행, **Then** 대기 상태로 돌아가 다시 발행된다. **When** 취소, **Then** 더 이상 발행되지 않는다.
5. **Given** 벡터 동기화 실패 여러 건, **When** 일괄 재시도, **Then** 전부 대기 상태로 돌아가고 건수를 받는다. **When** 미적재 READY 적재 요청, **Then** 예약 건수와 잔여 건수를 받는다.
6. **Given** 시드 300줄 중 중복·삭제 충돌 포함, **When** 등록, **Then** 생성된 id 목록·건너뛴 이름·삭제 음식과 충돌한 이름이 분류돼 온다.
7. **Given** 삭제된 음식, **When** 삭제 포함 조회, **Then** 삭제 표시와 함께 나온다. **When** 복구, **Then** 활성으로 돌아오고 검색 동기화가 예약된다. 같은 이름의 활성 음식이 있으면 복구가 거부된다.
8. **Given** 음식 여러 건 선택, **When** 일괄 승인/재수집/삭제, **Then** 건별 성공·실패 사유가 온다. 500건 초과는 거부된다.

### User Story 5 - 회원 탐색 (Priority: P2)

운영자가 닉네임·이메일·가입 경로·상태·온보딩 여부·가입일 범위로 회원을 찾고, 탈퇴 회원도 포함해 볼 수 있으며, 페이지 크기와 정렬을 고른다. 상세에서 외부 계정 식별자와 이메일은 기본 가려져 있고, 스캔 잠금 해제 여부·식단 카테고리·통화·최근 변경 시각·랭킹 점수와 다음 등급까지 남은 점수·최근 스캔/리뷰/주문·받은/한 신고 수·차단 수·북마크 수를 본다.

**Why this priority**: CS 대응의 출발점. 현재는 20건씩 넘기며 눈으로 찾고, 문의에 답할 활동 정보가 없다.

**Independent Test**: 닉네임 일부로 검색 → 해당 회원만 / 탈퇴 포함 조회 → 탈퇴 회원이 탈퇴 표시와 함께 나옴 / 상세에 최근 스캔 5건·리뷰 5건·주문 5건 포함.

**Acceptance Scenarios**:

1. **Given** 회원 다수, **When** 닉네임 일부·가입 경로·상태로 검색, **Then** 조건에 맞는 회원만 가입일 역순으로 온다.
2. **Given** 탈퇴 회원, **When** 기본 조회, **Then** 안 나온다. **When** 탈퇴 포함 조회, **Then** 탈퇴 표시와 탈퇴 시각(근사)과 함께 나온다.
3. **Given** 회원 상세, **When** 조회, **Then** 외부 계정 식별자는 오지 않고 이메일은 마스킹돼 오며, 스캔 잠금 해제·식단·통화·랭킹 점수/다음 등급 잔여·최근 스캔/리뷰/주문 각 5건·신고/차단/북마크 수가 온다.

### User Story 6 - 회원 조치 (Priority: P3)

운영자가 회원을 사유와 함께 정지하거나 해제하고, 부적절한 닉네임을 초기화하거나 프로필 사진을 기본으로 되돌리며, 스캔 제한을 수동으로 풀고, 회원을 강제 탈퇴시키고, 랭킹 점수 변동 내역을 본다. 정지된 회원이 로그인하면 "정지됨" 을 뜻하는 오류를 받는다.

**Why this priority**: 사고 위험 6번. 빈도는 낮지만 지금은 운영 DB 직접 수정으로만 가능하다.

**Independent Test**: 회원 정지 → 그 회원 로그인 시 정지 오류 / 닉네임 초기화 → 기본 닉네임으로 / scan-unlock → 스캔 허용 / 강제 탈퇴 → 기존 탈퇴와 동일한 결과.

**Acceptance Scenarios**:

1. **Given** 활성 회원, **When** 사유와 함께 정지, **Then** 상태·사유·시각이 기록되고, 그 회원의 로그인은 "정지됨" 오류로 거부된다. **When** 해제, **Then** 다시 로그인된다.
2. **Given** 욕설 닉네임 회원, **When** 닉네임 초기화, **Then** 기본 닉네임으로 바뀌고 감사 이력이 남는다.
3. **Given** 스캔 3회 소진 회원, **When** 스캔 잠금 해제, **Then** 이후 스캔이 허용된다.
4. **Given** 회원, **When** 강제 탈퇴, **Then** 사용자 본인 탈퇴와 같은 절차(외부 계정 삭제 선행 포함)로 처리되고, 외부 계정 삭제 실패 시 탈퇴는 진행되지 않고 실패가 기록된다.
5. **Given** 회원, **When** 랭킹 변동 내역 조회, **Then** 사건별 점수 변동과 시각이 온다.

### User Story 7 - 구 관리자 화면 병행 유지 (Priority: P1, 횡단)

React 전환이 끝날 때까지 기존 서버 렌더링 관리자 화면의 모든 기능이 그대로 동작한다. 신 REST 가 추가돼도 구 화면의 로그인·목록·편집·시드·배치·회원 화면은 변경 없이 쓸 수 있고, 구 화면에서 한 조작도 감사 이력에 남는다.

**Why this priority**: 운영 공백 금지가 사용자의 명시 제약이다.

**Independent Test**: 기존 관리자 화면 회귀 테스트 전부 통과 + 구 화면에서 음식 수정 후 감사 이력 존재.

**Acceptance Scenarios**:

1. **Given** 신 REST 배포 후, **When** 구 화면 로그인·대시보드·목록·편집·시드·이미지 배치·회원 화면 사용, **Then** 이전과 동일하게 동작한다.
2. **Given** 구 화면에서 음식 수정, **When** 감사 이력 조회, **Then** 조작자(관리자 계정)와 변경 내용이 남아 있다.

---

### Edge Cases

- 관리자 갱신 자격이 탈취되면? — 갱신 시 이전 갱신 자격은 즉시 무효(회전). 로그아웃 시 갱신 자격 폐기.
- 잠금 중 올바른 비밀번호 입력 — 잠금 해제까지 거부(잠금 시간은 늘어나지 않음).
- 관리자 계정이 삭제/비활성인데 자격이 남아 있으면? — 자격 검증 시 계정 존재를 확인해 거부. *(계정 관리 자체는 Phase 3)*
- 승인 대상 음식이 요청 사이에 다른 운영자에 의해 이미 승인/삭제됨 — 현재 상태 기준 허용 전이가 아니면 거부.
- 수정 요청에 번역 언어가 일부 누락 — 누락 언어를 명시해 거부(9개 대상 언어 전부 필요).
- 재료 목록이 빈 배열 vs 누락 — 빈 배열은 "해당 없음" 으로 허용, 누락은 거부(위험도 계산이 갈린다).
- 이미지 재생성 요청 중복(이미 진행 중 아이템 존재) — 중복 생성 없이 진행 중임을 알린다.
- 이미지 업로드 파일이 허용 형식/크기를 벗어남 — 거부, 기존 이미지 유지.
- 고착 판정 기준 시간(N) — 기본 3시간, 조회 시 지정 가능.
- 고착 요청을 재발행했는데 랭체인 결과가 뒤늦게 두 번 도착 — 완료된 요청에 대한 재도착은 무시(기존 규칙 유지).
- 복구하려는 삭제 음식과 같은 이름의 활성 음식이 있음 — 복구 거부.
- 일괄 작업 중 일부 실패 — 나머지는 계속 진행하고 건별 결과 반환(전체 롤백 아님).
- 회원 검색어가 이메일 전체와 정확히 일치 — 마스킹과 무관하게 검색은 원문으로 가능(운영자 권한).
- 정지 회원의 기존 발급 자격 — 정지 즉시 회원 API 호출이 거부된다.
- 강제 탈퇴 대상이 이미 탈퇴됨 — 멱등하게 성공 처리.
- 감사 이력 대상이 이후 삭제됨 — 이력은 남는다(대상 id 로 조회 가능).
- 구 화면과 신 REST 가 같은 음식을 동시에 수정 — 버전 충돌 규칙이 양쪽에 동일 적용(구 화면도 버전을 제출).

## Requirements *(mandatory)*

### Functional Requirements

**관리자 인증·자격 (Phase 0)**

- **FR-001**: 시스템은 관리자 아이디/비밀번호로 로그인해 관리자 액세스 자격과 갱신 자격을 발급하는 조작을 제공해야 한다.
- **FR-002**: 관리자 자격은 회원 자격과 구분돼야 하며, 관리자 자격으로 회원 전용 기능을 쓸 수 없고 회원 자격으로 관리자 기능을 쓸 수 없어야 한다. 기록(로그)에서도 관리자와 회원 식별자가 혼동되지 않아야 한다.
- **FR-003**: 갱신 자격으로 액세스 자격을 재발급할 수 있어야 하며, 사용된 갱신 자격은 즉시 무효가 되어야 한다. 로그아웃 시 갱신 자격을 폐기해야 한다.
- **FR-004**: 같은 관리자 계정으로 로그인 실패가 5회 연속되면 15분간 로그인을 거부해야 한다.
- **FR-005**: 기존 서버 렌더링 화면의 쿠키 로그인은 그대로 동작해야 한다.

**감사 이력 (Phase 0)**

- **FR-006**: 관리자에 의한 모든 데이터 변경 조작(음식 수정·전이·삭제·복구·재수집·이미지 교체·일괄 작업·시드, 회원 제재·프로필 조정·스캔 해제·강제 탈퇴, 앱 버전 수정 포함)은 조작자·시각·조작 종류·대상 종류·대상 식별자·변경 전/후 값을 감사 이력으로 남겨야 한다. 신 REST 와 구 화면 양쪽에서 동일하게 남아야 한다.
- **FR-007**: 대상 종류·대상 식별자·조작자·기간으로 감사 이력을 조회할 수 있어야 한다.
- **FR-008**: 감사 이력은 삭제·수정할 수 없어야 하며 최소 1년 보존해야 한다.

**대시보드 (Phase 1)**

- **FR-009**: 대시보드 조회는 기간(일수)을 받아 스캔·신규 음식·비용 지표를 그 기간으로 집계해야 한다(기본 7일, 최대 90일).
- **FR-010**: 음식 상태는 모든 응답에서 동일한 식별자와 표시명 쌍으로 와야 한다.
- **FR-011**: 비용 지표 응답에는 집계에 포함되는 호출 범위 설명이 포함돼야 하며, 원화 환산값도 함께 와야 한다.
- **FR-012**: 대시보드는 콘텐츠 수집 요청의 상태별 건수와 함께 "발행 후 N시간 이상 미완료" 건수를 제공해야 한다.

**음식 탐색 (Phase 1)**

- **FR-013**: 음식 목록은 검색어(숫자면 id, 아니면 표시명 포함 검색), 재료 코드, 번역명, 상태, 실패 유형, 삭제 포함 여부로 걸러야 하고, 정렬 기준(id·갱신 시각·이름, 오름/내림)과 페이지 크기(기본 50, 최대 200)를 받아야 한다.
- **FR-014**: 목록 항목은 id·표시명·상태·실패 유형·맵기·이미지 유무·갱신 시각·검수 횟수·리뷰 수·검색 동기화 상태를 포함해야 한다.
- **FR-015**: 음식 상세는 번역을 언어별 구조로, 재료를 코드·비율 목록으로 제공하고, 매칭키·긴 설명·검수 횟수·반려 사유·실패 유형·버전·생성/갱신 시각을 포함해야 한다.
- **FR-016**: 음식 상세는 그 음식의 최근 콘텐츠 수집 요청 이력, 이미지 생성 아이템 이력(실패 사유 포함), 검색 동기화 상태, 리뷰 수/평균 평점, 스캔 매칭 수, 북마크 수를 함께 제공해야 한다.
- **FR-017**: 재료 카탈로그(코드·한국어명·번역·이미지) 목록을 조회할 수 있어야 한다.

**음식 수정·검수·전이 (Phase 1)**

- **FR-018**: 음식 수정은 현재 버전 번호를 필수로 받아야 하며, 저장된 버전과 다르면 변경 없이 충돌로 거부해야 한다.
- **FR-019**: 음식 수정은 이름(정규화 후 비어 있지 않고 다른 음식과 중복 아님)·설명(1~255자)·맵기(0~10)·번역(9개 대상 언어 전부 비어 있지 않음)·재료(카탈로그 코드, 비율 1~100, 빈 배열 허용·누락 불허)를 검증하고 항목별 오류를 돌려줘야 한다. 이 검증은 랭체인 적재 검증과 동일 규칙이어야 한다.
- **FR-020**: 음식 수정 조작으로는 상태를 바꿀 수 없어야 한다.
- **FR-021**: 승인 대기 음식에 대해 승인 조작과 반려(사유 필수) 조작을 제공해야 한다. 승인은 재료가 조사됐고 이미지가 있을 때만 허용하며, 승인 시 검색 동기화를 예약하고, 반려 시 사유와 반려 횟수를 기록해야 한다.
- **FR-022**: 허용된 상태 전이만 수행하는 전이 조작을 제공해야 하며, 응답에 현재 상태에서 가능한 전이 목록을 포함해야 한다. 허용되지 않는 전이는 거부한다. 실패 상태를 벗어나는 전이는 실패 유형·사유를 비워야 한다.
- **FR-023**: 음식 소프트 삭제·복구 조작을 제공해야 한다. 복구는 같은 이름의 활성 음식이 있으면 거부하고, 삭제·복구 모두 검색 동기화를 예약해야 한다.
- **FR-024**: 여러 음식을 지정해 승인·재수집·삭제를 일괄 수행하는 조작을 제공해야 하며(최대 500건), 건별 성공·실패 사유를 돌려줘야 한다.

**파이프라인 개입 (Phase 1)**

- **FR-025**: 음식 1건을 지정해 콘텐츠 재수집을 요청할 수 있어야 하며, 이미 대기 중이면 중복 생성 없이 그 사실을 알려야 한다. 조건 일괄 재수집(최대 500건)은 유지한다.
- **FR-026**: READY 음식의 상태를 유지한 채 이미지 재생성을 요청할 수 있어야 하며, 진행 중 아이템이 있으면 중복 생성하지 않아야 한다.
- **FR-027**: 음식 이미지를 파일 업로드로 교체할 수 있어야 한다(허용 형식·크기 검증, 기존 업로드 경로 재사용).
- **FR-028**: 이미지 배치 목록(페이지)과 배치 상세(아이템별 음식·상태·실패 사유·파일명, 배치의 외부 식별자·프롬프트 버전)를 조회할 수 있어야 한다.
- **FR-029**: 제출된 이미지 배치를 즉시 회수하는 조작을 제공해야 하며, 정시 회수와 동시에 실행돼도 중복 반영되지 않아야 한다.
- **FR-030**: 실패한 이미지 아이템을 골라 재제출할 수 있어야 한다. 이미지 배치 제출 응답에는 제출 대상 후보 수가 사전 조회로 제공돼야 한다.
- **FR-031**: 콘텐츠 수집 요청을 상태·고착 기준 시간·음식으로 조회할 수 있어야 하고, 고착 요청의 재발행(대기 복귀)·취소 조작을 제공해야 한다. 요청에는 마지막 실패 사유·시각이 기록·노출돼야 한다.
- **FR-032**: 검색 동기화 요청을 상태별로 페이지 조회하고, 실패 건 전체를 일괄 재시도하며, 미적재 READY 적재 요청 응답에 예약 건수와 잔여 건수를 포함해야 한다.
- **FR-033**: 시드 등록 응답에는 생성된 음식 id 목록, 중복으로 건너뛴 이름, 삭제된 음식과 충돌한 이름이 분류돼 포함돼야 한다. 기존 REST 시드 조작은 하위 호환을 유지한다.

**회원 탐색 (Phase 2)**

- **FR-034**: 회원 목록은 닉네임·이메일·가입 경로·상태·온보딩 여부·가입일 범위·탈퇴 포함 여부로 걸러야 하고, 정렬과 페이지 크기(기본 20, 최대 200)를 받아야 한다.
- **FR-035**: 회원 상세는 외부 계정 식별자를 제공하지 않고 이메일을 마스킹해 제공해야 하며, 스캔 잠금 해제 여부·스캔 허용 여부·식단 카테고리·통화·최근 변경 시각·랭킹(점수·등급·다음 등급 잔여·스캔/리뷰/고유 리뷰 음식 수)·최근 스캔/리뷰/주문 각 5건·받은/한 신고 수·차단 수·북마크 수·제재 사유/시각을 포함해야 한다.
- **FR-036**: 탈퇴 회원은 탈퇴 표시와 탈퇴 시각(근사)과 함께 조회돼야 한다.

**회원 조치 (Phase 2)**

- **FR-037**: 회원 상태를 정지/활성으로 바꾸는 조작을 제공해야 하며, 정지 시 사유(필수)와 시각을 기록해야 한다. 정지 회원의 로그인·회원 기능 사용은 "정지됨" 을 뜻하는 전용 오류로 거부돼야 한다(기존의 중복 계정 오류로 오인되지 않게).
- **FR-038**: 회원 닉네임을 기본값으로 초기화하고 프로필 사진을 기본으로 되돌리는 조작을 제공해야 한다.
- **FR-039**: 회원의 스캔 제한을 수동으로 해제하는 조작을 제공해야 한다.
- **FR-040**: 회원을 강제 탈퇴시키는 조작을 제공해야 하며, 사용자 본인 탈퇴와 동일한 절차(외부 계정 삭제 선행)를 따르고, 외부 삭제 실패 시 탈퇴를 진행하지 않고 실패를 기록·조회할 수 있어야 한다. 이미 탈퇴한 회원에는 멱등해야 한다.
- **FR-041**: 회원의 랭킹 점수 변동 내역(사건·점수·시각)을 조회할 수 있어야 한다.

**공통·호환**

- **FR-042**: 모든 신 조작은 기존 관리자 API 규약(공통 응답 봉투, 버전 헤더, 관리자 자격 필수, 안정적인 오류 코드)을 따라야 한다.
- **FR-043**: 기존 서버 렌더링 관리자 화면의 모든 기능은 변경 없이 동작해야 하며, 구 화면의 음식 수정은 신 REST 와 같은 검증·버전 충돌 규칙을 따라야 한다.
- **FR-044**: 기존 REST 7개(시드·이미지 제출·앱 버전 조회/수정·검수 대상 조회/결과·콘텐츠 적재)의 계약은 하위 호환을 유지해야 한다.

### Key Entities *(include if feature involves data)*

- **관리자 세션 자격**: 관리자 계정에 발급되는 액세스·갱신 자격. 회원 자격과 구분되는 주체 종류를 가진다. 갱신 자격은 1회용(회전).
- **로그인 잠금**: 관리자 계정별 연속 실패 횟수와 잠금 만료 시각.
- **감사 이력**: 조작자(관리자 계정)·시각·조작 종류·대상 종류·대상 식별자·변경 전 값·변경 후 값·비고. 불변, 삭제된 대상에도 남는다.
- **회원 제재 기록**: 회원의 정지 사유·정지 시각(회원에 귀속).
- **콘텐츠 수집 요청(확장)**: 기존 요청에 마지막 실패 사유·실패 시각이 추가된다. 고착 여부는 발행 시각 경과로 판정한다.
- **탈퇴 실패 기록**: 강제/본인 탈퇴 중 외부 계정 삭제 실패의 회원·시각·사유.
- **상태 전이 규칙**: 음식 상태별 허용 전이 집합과 전이 조건(승인 전제: 재료 조사됨·이미지 있음).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영자가 신 화면에서 로그인부터 승인 대기 음식 1건 승인까지 1분 이내에 완료할 수 있다(현재: 상세 편집 진입 → 상태 변경 → 저장, 반려 사유 기록 불가).
- **SC-002**: 관리자에 의한 데이터 변경 조작의 100% 가 감사 이력에서 조작자·이전값·이후값으로 확인된다.
- **SC-003**: 카탈로그에 없는 재료 코드·범위 밖 비율·누락 번역이 저장되는 경우가 0건이 된다(관리자 경로에서 앱 사용자 음식 상세 오류 유발 0건).
- **SC-004**: 재료·이미지가 없는 음식이 관리자 조작으로 READY 가 되는 경우가 0건이 된다.
- **SC-005**: 특정 음식 1건 재수집 시 수집 요청이 정확히 1건만 생성된다(현재: 이름 포함 검색으로 다수 건 발행).
- **SC-006**: READY 음식의 이미지 교체 중 앱 노출이 중단되는 시간이 0 이 된다(현재: 상태 강등으로 최대 3시간+ 미노출).
- **SC-007**: 발행 후 3시간 이상 미완료인 수집 요청을 운영자가 대시보드에서 10초 이내에 식별할 수 있다.
- **SC-008**: 회원 CS 문의 시 닉네임/이메일로 대상 회원을 30초 이내에 찾고, 상세 한 화면에서 최근 활동을 확인할 수 있다(현재: 20건씩 순차 탐색, 활동 정보 없음).
- **SC-009**: 회원 정지가 운영 DB 직접 수정 없이 화면 조작으로 완료되고, 정지 회원은 전용 오류를 받는다.
- **SC-010**: 신 REST 배포 후 기존 관리자 화면 회귀 테스트 통과율 100%.
- **SC-011**: 관리자 목록 조회(음식·회원)가 데이터 1만 건 기준 2초 이내에 응답한다.

## Assumptions

- 신 관리자 화면(React)은 별도 저장소/오리진에서 개발되며, 이 기능은 백엔드 REST 만 다룬다. 화면 자체는 범위 밖.
- 관리자 액세스 자격 수명은 1시간, 갱신 자격은 7일로 두고 갱신 자격 저장은 기존 회원 갱신 자격 저장소를 재사용한다(주체 종류로 구분).
- 감사 이력의 "변경 전/후 값" 은 변경된 필드만 담은 구조화 값이며, 대용량 필드(긴 설명·번역 전체)도 그대로 담는다. 보존 1년 후 정리는 별도 배치(범위 밖).
- 관리자 계정 관리(추가·비활성화·비밀번호 변경), 신고 큐, 리뷰/커뮤니티 관리자 삭제, 주문/스캔 이력 조회, 앱 버전 변경 이력은 Phase 3 으로 이 기능 범위 밖이다. 앱 버전 조회/수정 REST 계약은 KB-373 이 다룬다.
- 회원 상세의 "최근 활동" 은 각 5건이며 더 보기(페이지)는 Phase 3 의 도메인별 조회에서 다룬다.
- 회원 강제 탈퇴는 기존 본인 탈퇴 흐름(외부 계정 삭제 선행 → 내부 탈퇴)을 관리자 주체로 재사용한다.
- 이미지 업로드는 기존 사전 서명 업로드 경로를 재사용하고, 허용 형식은 기존 이미지 업로드 규칙과 같다.
- 고착 판정 기본 기준은 발행 후 3시간이다(랭체인 처리 상한 기준, 조회 시 변경 가능).
- 일괄 작업 상한 500건은 기존 재수집·시드 상한과 맞춘다.
- 정지 회원 전용 오류 코드는 기존 오류 코드 체계에 새 번호로 추가한다(폐기 번호 재사용 없음).
- 구 화면의 음식 수정 폼은 버전 번호를 함께 제출하도록 최소 수정한다(맵기 입력 범위 오류 정정 포함) — "변경 없이 동작" 의 예외로, 신 REST 와 규칙을 맞추기 위한 것이다.
- 신 REST 는 기존 관리자 서비스와 뷰 모델을 재사용하며, 화면 전용 계산값(막대 높이·요일 라벨)은 REST 응답에서 제외한다.

## Out of Scope

- Phase 3: 신고 처리 큐, 리뷰/게시글/댓글 관리자 삭제, 주문·스캔 이력 조회, 앱 버전 변경 이력, 관리자 계정 관리, 관리자 IP 허용 목록.
- React 관리자 화면 구현.
- 구 서버 렌더링 화면의 UX 개선(버전 제출·맵기 범위 정정 외).
- 감사 이력 보존 기간 만료 정리 배치.
