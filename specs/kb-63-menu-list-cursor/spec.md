# Feature Specification: 메뉴 목록 조회 API (무한 스크롤, no-offset 커서 페이지네이션)

**Feature Branch**: `kb-63-menu-list-cursor`

**Created**: 2026-07-07

**Status**: Draft

**Input**: User description: "kb-63 작업을 워크트리에서 진행한다" — KB-63 [BE] 메뉴 목록 조회 API (무한 스크롤, no-offset)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 검색어 없이 메뉴를 무한 스크롤로 훑어본다 (Priority: P1)

사용자가 딱히 찾는 게 없어도 메뉴 목록 화면을 열면 최신 등록순으로 메뉴가 한 페이지(20개)씩 내려오고, 계속 아래로 스크롤하면 다음 20개가 이어서 로드된다. 데이터가 아무리 많아져도 뒤로 갈수록 느려지지 않고, 스크롤하는 동안 새 메뉴가 추가되거나 삭제돼도 이미 본 항목이 중복되거나 건너뛰어지지 않는다.

**Why this priority**: 검색 없이 메뉴를 구경하는 진입 경험 그 자체가 이 기능의 핵심 가치다. 첫 페이지 조회와 커서 기반 연속 로딩이 동작하면 그것만으로 "메뉴를 둘러본다"는 사용자 여정이 완결된다(MVP).

**Independent Test**: 커서 없이 목록을 최초 요청해 최신 20개와 `nextCursor`·`hasNext`를 받고, 받은 `nextCursor`로 다음 요청을 보내 이전 페이지와 겹치지 않는 다음 20개를 받는 것으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 메뉴가 20개보다 많이 등록돼 있고, **When** 커서 없이 목록을 조회하면, **Then** 최신 등록순 상위 20개와 다음 커서, `hasNext=true`를 받는다.
2. **Given** 첫 페이지에서 받은 다음 커서를 들고, **When** 그 커서로 다음 페이지를 조회하면, **Then** 첫 페이지의 마지막 항목보다 오래된 다음 20개를 받고, 두 페이지 사이에 중복·누락 항목이 없다.
3. **Given** 사용자가 스크롤을 이어가는 도중 새 메뉴가 추가되거나 기존 메뉴가 삭제돼도, **When** 커서로 다음 페이지를 계속 요청하면, **Then** 이미 지나간 항목이 다시 나오거나 아직 안 본 항목이 사라지지 않는다.

---

### User Story 2 - 항목에서 바로 상세로 이어지고 한눈에 요약을 본다 (Priority: P2)

목록의 각 항목이 상세 조회로 곧장 이어질 안정적인 식별자를 담고 있어, 사용자가 관심 가는 메뉴를 탭하면 추가 검색 없이 상세 화면으로 진입한다. 각 항목은 요청 언어로 지역화된 메뉴명, 대표 이미지, 맵기, 그리고 사용자의 회피 성분 기준 종합 위험도를 함께 보여줘서 목록에서 이미 훑어볼 수 있다.

**Why this priority**: 목록이 단순 나열을 넘어 "상세로 이어지고 위험도를 미리 보여주는" 카드가 되어야 실제 탐색에 쓸모가 있다. 다만 P1(스크롤 자체)이 없으면 성립하지 않으므로 그다음 우선순위다.

**Independent Test**: 목록 한 페이지를 받아 각 항목에 안정적 식별자(foodId)가 있고, 그 식별자로 상세 조회가 성공하며, 항목에 요청 언어 메뉴명·이미지·맵기·종합 위험도가 담기는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 목록 한 페이지를 받고, **When** 임의 항목의 식별자로 상세 조회를 요청하면, **Then** 그 항목에 해당하는 메뉴 상세가 정상 반환된다.
2. **Given** `lang`을 지정해 목록을 조회하면, **When** 해당 언어 번역이 있으면 그 언어로, 없으면 한국어로, **Then** 각 항목의 표시명이 상세 API와 동일한 폴백 규칙으로 지역화된다.
3. **Given** 사용자의 회피 성분이 주어졌을 때, **When** 목록을 조회하면, **Then** 각 항목의 종합 위험도가 SAFE/CAUTION/DANGER/UNKNOWN 중 하나로 표시된다.

---

### User Story 3 - 경계·빈 결과에서도 예측 가능하게 동작한다 (Priority: P3)

마지막 페이지, 빈 목록, 잘못된 커서 같은 경계 상황에서도 응답이 일관되고 예측 가능해야 한다. 목록 끝에 도달하면 클라이언트가 "더 없음"을 분명히 알 수 있고, 결과가 하나도 없어도 오류가 아니라 빈 목록으로 응답한다.

**Why this priority**: 무한 스크롤 UI가 멈춰야 할 시점을 정확히 알게 해 무한 재요청·깨진 화면을 막는다. 핵심 흐름은 아니지만 견고성에 필수라 P3.

**Independent Test**: 마지막 페이지 응답의 `hasNext=false`·다음 커서 부재, 빈 테이블에서의 빈 목록 200 응답, 잘못된 커서에 대한 실패 응답을 각각 확인해 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 남은 항목이 20개 이하인 마지막 페이지에서, **When** 목록을 조회하면, **Then** 남은 항목과 함께 `hasNext=false`, 다음 커서는 비어 있다(null).
2. **Given** 조회 가능한 메뉴가 하나도 없을 때, **When** 목록을 조회하면, **Then** 200과 빈 목록·`hasNext=false`를 반환한다(오류 아님).
3. **Given** 형식이 잘못됐거나 해석할 수 없는 커서로, **When** 목록을 조회하면, **Then** 사유가 담긴 실패 응답을 반환한다.

---

### Edge Cases

- **첫 요청(커서 없음)**: 커서 파라미터가 없으면 첫 페이지(최신 20개)로 해석한다.
- **정확히 20의 배수**: 총 개수가 20의 배수라 마지막 페이지가 꽉 찬 경우, 그 다음 요청은 빈 목록 + `hasNext=false`를 반환한다.
- **스크롤 중 삽입/삭제**: keyset 커서라 이미 지나온 경계 밖의 삽입/삭제는 현재 페이지 연속성에 영향을 주지 않는다(중복·누락 없음).
- **미지원/미지정 언어**: `lang`이 없거나 지원하지 않으면 표시명은 한국어로 폴백한다(상세 API와 동일 규칙).
- **회피 컨텍스트 부재**: 회피 성분 정보가 없으면 항목 위험도는 UNKNOWN 또는 SAFE로 일관 처리한다(상세 API와 동일한 회피 성분 제공 방식 재사용).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 검색어 없이 전체 메뉴를 페이지당 20개씩 조회하는 GET 목록 엔드포인트를 제공해야 한다.
- **FR-002**: 목록 정렬은 **최신 등록순(내부 식별자 foodId 내림차순)** 으로 결정적·안정적이어야 한다.
- **FR-003**: 페이지네이션은 offset 이 아니라 **no-offset(cursor/keyset)** 방식이어야 한다 — 요청은 선택적 커서를 받고(없으면 첫 페이지), 응답은 **다음 커서**와 **다음 페이지 존재 여부(hasNext)** 를 포함해야 한다.
- **FR-004**: 커서 이후 페이지는 이전 페이지와 항목이 중복되거나 누락되지 않아야 한다 — 스크롤 도중 삽입·삭제가 일어나도 동일하게 보장한다.
- **FR-005**: 목록의 각 항목은 상세 조회로 이어질 **안정적 식별자(숫자 foodId)** 를 포함해야 한다.
- **FR-006**: 각 항목은 **요청 언어 표시명**, **대표 이미지 참조**, **맵기(0~10)**, **사용자 회피 기준 종합 위험도(SAFE/CAUTION/DANGER/UNKNOWN)** 를 포함해야 한다.
- **FR-007**: 목록은 선택적 `lang` 파라미터를 받아 표시명을 지역화하고, 미지원·미지정·번역 부재 시 한국어로 폴백해야 한다(상세 API와 동일 규칙).
- **FR-008**: 항목 스키마는 향후 **검색어 조회 응답과 일관**되게 재사용 가능한 'food summary' 형태여야 한다.
- **FR-009**: 마지막 페이지에서는 `hasNext=false`이고 다음 커서는 비어 있어야(null) 한다.
- **FR-010**: 조회 결과가 0건이어도 오류가 아니라 200과 빈 목록·`hasNext=false`를 반환해야 한다.
- **FR-011**: 형식이 잘못됐거나 해석 불가한 커서는 사유가 담긴 실패 응답으로 처리해야 한다.
- **FR-012**: 모든 응답은 공통 봉투 `BaseResponse`로 감싸고, 경로는 `/api/v1` 규약을 따라야 한다.
- **FR-013**: 상세 조회 식별자 정합을 위해 상세 조회가 **foodId로 조회**되도록 정합/보완되어야 한다(현재 상세 API는 한국어 메뉴명 조회 — 본 스펙의 전제이자 의존).
- **FR-014**: 커서 경계(마지막 페이지)·빈 결과·잘못된 커서 케이스가 BehaviorSpec 통합 테스트로 검증되어야 한다.

### Key Entities *(include if data involved)*

- **메뉴 요약(Food Summary)**: 목록/검색이 공유하는 항목 표현. 속성 — 안정 식별자(foodId), 요청 언어 표시명, 대표 이미지 참조, 맵기, 사용자 회피 기준 종합 위험도.
- **커서 페이지(Cursor Page)**: 한 번의 목록 응답 단위. 속성 — 메뉴 요약 목록(≤20), 다음 커서(nullable), 다음 페이지 존재 여부(hasNext).
- **커서(Cursor)**: 다음 페이지의 시작 위치. 마지막으로 반환된 항목의 정렬 키(내부 식별자)에서 파생되며, 첫 요청에서는 부재.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 검색어 입력 없이 메뉴 목록을 열어 20개 단위로 끊김 없이 계속 스크롤할 수 있다.
- **SC-002**: 연속한 두 페이지 사이의 중복·누락 항목이 **0건**이다 — 스크롤 중 삽입/삭제가 동시에 일어나는 상황에서도 동일하다.
- **SC-003**: 목록 응답 성능이 데이터 양·페이지 깊이에 따라 저하되지 않는다 — 첫 페이지와 아주 뒤쪽 페이지의 응답 시간이 유의하게 차이 나지 않는다(OFFSET 스캔 비용 제거 확인).
- **SC-004**: 목록 각 항목의 식별자로 상세 조회를 한 번 요청하면 100% 해당 상세로 진입한다.
- **SC-005**: 마지막 페이지(`hasNext=false`·다음 커서 부재), 빈 결과, 잘못된 커서 경계가 모두 BehaviorSpec 통합 테스트로 커버된다.

## Assumptions

- **페이지 크기 20 고정**: 클라이언트가 페이지 크기를 지정하지 않으며, 서버가 20으로 고정한다.
- **익명 브라우즈**: 목록 조회는 로그인 없이 가능한 공개 탐색이다. 항목 위험도 산출에 쓰는 회피 성분 컨텍스트는 상세 API가 쓰는 동일한 회피 성분 제공 방식을 재사용한다(현재 Mock 제공자).
- **언어 폴백 동일 규칙**: `lang` 처리와 폴백(한국어)은 상세 API와 완전히 동일하게 맞춘다.
- **커서 표현**: 커서는 마지막 항목의 정렬 키(내부 식별자)에서 파생된 값으로 클라이언트에 전달된다(불투명 문자열 여부는 구현 세부).
- **검색 태스크 선행/병행**: 검색어 조회 API는 아직 없다. 본 목록의 항목 스키마('food summary')를 검색이 그대로 재사용할 것을 전제로 설계한다.
- **상세 식별자 정합 의존**: FR-013에 따라 상세 조회가 foodId 기반 조회를 지원하도록 정합이 필요하다. 이 정합의 범위(본 태스크 포함 vs 별도 후속)는 계획 단계에서 확정한다.
- **소프트 삭제 준수**: 삭제(소프트 삭제)된 메뉴는 목록·커서 계산에서 제외된다(영속 계층의 상시 ACTIVE 필터에 따름).
