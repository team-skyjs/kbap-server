# Feature Specification: 회원 탈퇴 — DB 소프트 삭제와 Firebase user record 삭제

**Feature Branch**: `kb-119-member-withdrawal`

**Created**: 2026-07-12

**Status**: Implemented

**Input**: KB-119 — "[BE] 회원탈퇴 — DB 소프트 삭제와 Firebase user record 삭제"

> **티켓 대비 변경된 결정 2건** (구현 중 사용자 확정):
> 1. **소셜 ID 토큰 재인증 없음.** 티켓 Background 는 "탈퇴 요청 시 클라이언트가 신선한 Firebase ID 토큰을 함께 보낸다"였으나, 실제 앱은 탈퇴 직전 소셜 재로그인을 하지 않는다. 따라서 서버가 저장된 소셜 신원으로 인증 제공자에 **직접 사용자 기록을 조회해** 삭제한다. 요청 본문이 없다.
> 2. **이메일은 우리 DB 에 남긴다.** 티켓 DoD 는 "email 을 비운다"였으나 유지하기로 했다. 인증 제공자(Firebase) 쪽 이메일은 계정 삭제로 사라진다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원이 탈퇴하면 우리 DB와 인증 제공자 양쪽 기록이 지워진다 (Priority: P1)

로그인한 회원이 앱에서 탈퇴를 요청한다. 서버는 접근 토큰이 가리키는 회원의 소셜 신원(제공자 + 소셜 식별자)으로 인증 제공자에 남아 있는 사용자 기록(이메일 포함)을 찾아 지우고, 우리 DB 의 회원 행을 소프트 삭제하면서 소셜 식별자를 더미 값으로 치환한다.

**Why this priority**: 이 스토리가 태스크의 존재 이유다. 우리 DB 만 정리하면 인증 제공자 쪽에 이메일이 그대로 남아 개인정보 삭제 요구를 충족하지 못한다.

**Independent Test**: 로그인 → 탈퇴 API 호출 → (a) 인증 제공자의 사용자 기록이 사라졌는지, (b) 회원 행이 소프트 삭제되고 소셜 식별자가 더미로 바뀌었는지 확인하면 단독 검증된다.

**Acceptance Scenarios**:

1. **Given** 소셜 로그인으로 가입한 회원과 유효한 접근 토큰, **When** 탈퇴를 요청하면, **Then** 성공 응답을 받고 인증 제공자의 사용자 기록이 삭제되며 회원 행이 소프트 삭제된다.
2. **Given** 탈퇴가 완료된 회원, **When** 기존 접근 토큰으로 프로필 조회를 시도하면, **Then** "회원을 찾을 수 없음"으로 거부된다.
3. **Given** 탈퇴가 완료된 회원, **When** 탈퇴 전에 발급받은 갱신 토큰으로 토큰 재발급을 시도하면, **Then** 거부되어 새 접근 토큰을 얻을 수 없다.
4. **Given** 이미 탈퇴한 회원, **When** 같은 요청을 한 번 더 보내면, **Then** "회원을 찾을 수 없음"으로 거부된다.
5. **Given** 인증 제공자 계정 삭제가 실패하는 상황, **When** 탈퇴를 요청하면, **Then** 실패 응답을 받고 회원 행은 활성 상태 그대로 남는다.

---

### User Story 2 - 탈퇴한 사람이 같은 소셜 계정으로 다시 가입할 수 있다 (Priority: P2)

탈퇴했던 사람이 마음을 바꿔 동일한 구글/애플 계정으로 다시 로그인한다. 서버는 이 사람을 과거 회원으로 복구하지 않고 **신규 회원**으로 새로 가입시킨다(새 회원 식별자, 온보딩 미완료 상태).

**Why this priority**: 탈퇴가 "다시는 못 들어오는 문"이 되면 안 된다. 소셜 식별자에 유일 제약이 걸려 있어 더미 치환이 제대로 되지 않으면 재가입이 막히므로, 탈퇴 구현이 옳은지 되짚는 검증 역할도 한다.

**Independent Test**: 탈퇴 직후 같은 소셜 계정으로 로그인 API 를 호출해 "신규 회원" 여부와 새 회원 식별자가 반환되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 방금 탈퇴한 소셜 계정, **When** 같은 계정으로 다시 로그인하면, **Then** 신규 회원으로 가입되고 이전과 다른 회원 식별자를 받으며 온보딩 미완료 상태다.
2. **Given** 가입-탈퇴를 두 번 반복한 소셜 계정, **When** 세 번째로 로그인하면, **Then** 식별자 충돌 없이 정상 가입된다.
3. **Given** 재가입한 회원, **When** 프로필을 조회하면, **Then** 탈퇴 전 회원의 프로필(닉네임·기피 성분 등)이 딸려오지 않는다.

---

### Edge Cases

- **인증 제공자 쪽 사용자 기록이 이미 없는 경우**(관리자가 콘솔에서 먼저 지웠거나 중복 요청): 삭제를 성공으로 간주하고 DB 탈퇴를 계속 진행한다(멱등).
- **인증 제공자 삭제가 실패한 경우**(네트워크·권한·장애): 탈퇴 전체를 실패시키고 DB 는 **아무것도 바꾸지 않는다**. 소셜 식별자만 더미로 치환된 채 인증 제공자 기록이 남으면 그 기록을 찾아 지울 단서(소셜 식별자)를 잃기 때문이다. 대신 관리자가 콘솔에서 직접 지울 수 있도록 회원 식별자·소셜 제공자·소셜 식별자·실패 사유를 담은 오류 로그를 남긴다.
- **인증 제공자 삭제는 성공했으나 DB 탈퇴가 실패한 경우**: 회원은 실패 응답을 받고 재시도한다. 재시도 시 인증 제공자 삭제는 멱등하게 통과한다. 인증 제공자 기록이 지워져도 같은 소셜 계정으로 다시 로그인하면 소셜 신원(제공자 + 소셜 식별자)이 동일하므로 기존 회원으로 로그인된다.
- **여러 기기에서 로그인한 회원이 한 기기에서 탈퇴**: 다른 기기의 갱신 토큰으로도 토큰을 재발급받을 수 없어야 한다.
- **온보딩을 완료하지 않은 회원의 탈퇴**: 정상 처리된다.
- **동시에 두 번 들어온 탈퇴 요청**: 하나만 성공하고 나머지는 "회원을 찾을 수 없음"으로 거부된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 로그인한 회원이 자신의 계정을 탈퇴하는 엔드포인트 `PATCH /api/v1/members/me/withdraw` 를 제공해야 한다. 접근 토큰 인증이 필수이며 **요청 본문은 없다** — 접근 토큰이 대상 회원을 결정한다.
- **FR-002**: 시스템은 회원의 저장된 소셜 신원(제공자 + 소셜 식별자)으로 인증 제공자에서 해당 사용자 기록을 찾아 삭제해야 한다(이메일 포함). 해당 기록이 이미 없으면 삭제 성공으로 간주한다.
- **FR-003**: 인증 제공자 사용자 기록 삭제가 실패하면 시스템은 탈퇴 전체를 실패로 처리하고 회원 데이터를 **변경하지 않은 채로** 남겨야 한다. 동시에 관리자가 수동 삭제할 수 있도록 회원 식별자·소셜 제공자·소셜 식별자·실패 사유를 담은 오류 로그를 남긴다.
- **FR-004**: 인증 제공자 삭제가 성공하면 시스템은 회원 행을 소프트 삭제하고 소셜 식별자를 **회원마다 유일한 더미 값**으로 치환해야 한다. 소셜 신원의 유일성 제약이 유지되어 같은 소셜 계정으로 재가입할 수 있어야 한다.
- **FR-005**: 탈퇴 이후 해당 회원의 갱신 토큰으로는 새 접근 토큰을 재발급받을 수 없어야 한다. 탈퇴를 요청한 기기뿐 아니라 그 회원의 **모든 기기**에 대해 성립해야 한다.
- **FR-006**: 탈퇴한 회원의 접근 토큰으로 회원 전용 API 를 호출하면 "회원을 찾을 수 없음"(400)으로 거부되어야 한다.
- **FR-007**: 탈퇴 직후 동일한 소셜 계정으로 로그인하면 **신규 회원**으로 가입되어야 한다 — 새 회원 식별자, 온보딩 미완료, 이전 프로필 미승계.
- **FR-008**: 존재하지 않거나 이미 탈퇴한 회원에 대한 탈퇴 요청은 400 으로 거부되어야 한다.
- **FR-009**: 성공 응답은 프로젝트 공통 응답 봉투를 따르며 별도 페이로드를 담지 않는다.

### Key Entities

- **회원(Member)**: 소셜 신원·프로필·온보딩 여부를 가진 애그리거트. 탈퇴 시 소프트 삭제되며 소셜 식별자가 더미 값으로 바뀐다. 이메일·닉네임·프로필은 그대로 남는다.
- **소셜 신원(SocialIdentity)**: 제공자(GOOGLE/APPLE) + 소셜 식별자(구글·애플이 발급한 subject) + 이메일. 인증 제공자에서 사용자 기록을 찾는 **조회 키**로 쓰인다.
- **갱신 토큰(Refresh Token)**: 회원의 세션을 잇는 토큰. 탈퇴 후에는 어느 기기의 것이든 재발급에 쓰일 수 없어야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 탈퇴가 성공한 회원의 이메일이 인증 제공자의 사용자 목록에 100% 남지 않는다.
- **SC-002**: 탈퇴 직후 동일 소셜 계정으로 재로그인하면 100% 신규 회원으로 가입되며, 이전 회원의 프로필이 노출되지 않는다.
- **SC-003**: 탈퇴한 회원이 보유하던 갱신 토큰으로는 어느 기기에서든 새 접근 토큰을 단 한 건도 발급받을 수 없다.
- **SC-004**: 인증 제공자 삭제가 실패한 경우, "소셜 식별자가 더미로 치환됐는데 인증 제공자 기록은 살아 있는" 회원이 0건이다. 실패는 100% 관리자가 추적 가능한 오류 로그를 남긴다.
- **SC-005**: 회원은 고객 문의 없이 앱 안에서 스스로 탈퇴를 완료할 수 있다(App Store 심사지침 5.1.1(v) 요구 충족).

## Assumptions

- **탈퇴에 재인증을 요구하지 않는다.** 접근 토큰만으로 탈퇴가 확정된다. 앱이 탈퇴 직전 소셜 재로그인을 하지 않기로 했기 때문이며, 그 대가로 **접근 토큰이 탈취되면 계정이 삭제될 수 있다**(access TTL 30분 내). 되돌릴 수 없는 작업에 대한 재인증이 필요해지면 소셜 ID 토큰을 본문으로 받아 신원 대조하는 방식을 후속으로 도입한다.
- **인증 제공자의 사용자 식별자(Firebase local uid)는 저장하지 않는다.** 저장된 `(provider, providerUserId)` 로 인증 제공자에 역조회해 uid 를 얻는다(구글/애플의 subject 는 안정적이라 유효한 조회 키다).
- **이메일과 닉네임·프로필은 우리 DB 에 남는다.** 인증 제공자 쪽 이메일은 계정 삭제로 함께 사라진다. 보존 기간 정책이 정해지면 별도 태스크로 다룬다.
- **소프트 삭제의 더미 치환은 필수 장치다.** 소프트 삭제라 유니크 인덱스 `(provider, provider_uid)` 에 항목이 그대로 남으므로, 치환하지 않으면 같은 소셜 계정 재가입 INSERT 가 유니크 제약에 걸린다. 회원 PK 를 접미사로 쓰는 현행 더미 값은 회원마다 유일하고 가입-탈퇴를 반복해도 충돌하지 않는다.
- **탈퇴한 회원의 갱신 토큰 무효화는 "재발급 시 회원 유효성 확인"으로 달성한다.** 갱신 토큰 저장소는 토큰 단위 키만 가지고 회원별 색인이 없어 한 회원의 토큰을 열거해 지울 수 없다. 재발급 경로에서 회원 존재를 확인하면 모든 기기의 잔여 토큰이 한 번에 무력화되고, 저장소에 남은 항목은 만료 시간이 정리한다.
- **접근 토큰은 상태가 없어 만료 전까지 서명 검증을 통과한다.** 탈퇴 직후에도 짧은 만료 시간 동안은 토큰 자체가 유효하지만, 회원 조회가 필요한 API 는 400 으로 막힌다. 접근 토큰 블랙리스트는 도입하지 않는다.

## Out of Scope

- **Sign in with Apple 토큰 revoke**: 실제 의무 범위와 구현 방법을 조사해 결론을 별도 Jira 태스크로 남긴다.
- **관리자용 수동 삭제 도구**: 인증 제공자 삭제 실패 시 관리자가 콘솔에서 직접 지운다. 재시도 큐·관리자 API 는 만들지 않는다.
- **닉네임·이메일·프로필·스캔 이력 파기**: 소프트 삭제된 회원 행에 그대로 남는다.
- **탈퇴 철회·유예 기간(grace period)**: 탈퇴는 즉시 확정된다.
