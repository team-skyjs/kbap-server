# Feature Specification: 푸시 알림 문구를 메시지 파일로 이관

**Feature Branch**: `kb-617-push-message-source`

**Created**: 2026-09-22

**Status**: Implemented (2026-09-22 — 범위 확장: 문구 교체 + 후보 랜덤 선택)

**Jira**: [KB-617](https://simhani1.atlassian.net/browse/KB-617)

**Input**: User description: "푸시 알림 문구를 MessageSource 기반 메시지 파일로 옮긴다. 현재 문구는 코드에 박힌 맵 상수(알림 유형 5종 × 언어 10종, 스캔 제안 점심·저녁 슬롯별 문구, 수신거부 안내 10종)다. 렌더러는 유형·언어·슬롯으로 문구를 골라 {food} 를 치환하고, 광고성 유형이면 제목에 '(광고) ' 를 붙이고 본문 끝에 수신거부 안내를 덧붙이며 제목 200자·본문 1000자로 절단한다. api·batch 양쪽에서 같은 기준으로 구성돼야 한다. zh-Hans 와 zh-Hant 가 각각 올바르게 해석돼야 한다. 문구가 없으면 예외를 던지는 현재 동작 때문에 유형·슬롯 × 언어 조합 누락 검증 테스트가 필요하다. 메시지 파일은 UTF-8 로 고정하고 이모지가 깨지지 않아야 한다. 이관 후 상수는 제거한다. 기존 동작(치환·광고 접두·절단)은 그대로 유지한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 수신자는 렌더 규칙이 그대로인 푸시를 받는다 (Priority: P1)

앱 사용자는 자신의 언어로 된 푸시 알림을 받는다. 문구의 보관 위치가 코드에서 메시지 파일로 바뀌고 문구 자체가 새 후보로 교체돼도(2026-09-22 결정), 음식 이름 치환, 광고성 알림의 "(광고) " 접두와 수신거부 안내, 길이 절단 규칙은 그대로다.

**Why this priority**: 렌더 규칙(광고 표기·수신거부 안내)은 법규·계약이라 문구가 바뀌어도 깨지면 안 된다.

**Independent Test**: 알림 유형·슬롯·언어의 전 조합에 대해 접두·안내·절단·치환 규칙을 검증한다.

**Acceptance Scenarios**:

1. **Given** 한국어 사용자와 음식 이름 "비빔밥", **When** 리뷰 리마인더 알림을 렌더하면, **Then** 후보 중 하나의 제목·본문 쌍이 나오고 본문의 `{food}` 자리에 "비빔밥" 이 들어간다.
2. **Given** 광고성 유형 알림, **When** 렌더하면, **Then** 제목 앞에 "(광고) " 가 붙고 본문 끝에 줄바꿈 뒤 해당 언어의 수신거부 안내가 붙는다.
3. **Given** 광고성이 아닌 유형 알림, **When** 렌더하면, **Then** 접두도 수신거부 안내도 붙지 않는다.
4. **Given** 치환 후 제목이 200자·본문이 1000자를 넘는 입력, **When** 렌더하면, **Then** 제목은 200자·본문은 1000자로 절단되고, 광고성 유형은 수신거부 안내가 잘리지 않도록 본문 쪽을 먼저 절단한다.
5. **Given** 스캔 제안 알림에 점심 슬롯이 지정됨, **When** 렌더하면, **Then** 점심 전용 문구가 나오고, 슬롯이 없으면 유형 기본 문구가 나온다.
6. **Given** 공지(NEWS) 알림에 제목·본문 인자가 주어짐, **When** 렌더하면, **Then** 어떤 언어든 주어진 제목·본문이 그대로 나온다.

---

### User Story 2 - 문구 담당자가 코드를 열지 않고 문구를 고친다 (Priority: P2)

번역 담당자나 기획자는 언어별로 분리된 메시지 파일에서 문구 한 줄을 찾아 고친다. 알림 유형·슬롯·제목/본문이 드러나는 키 이름만 보고 어느 알림의 문구인지 알 수 있고, 언어별 파일을 나란히 놓으면 어떤 언어가 비어 있는지 보인다.

**Why this priority**: 이관의 목적 그 자체다. 다만 P1(동작 보존)이 깨지면 의미가 없으므로 두 번째다.

**Independent Test**: 메시지 파일의 문구 한 줄만 바꾸고(코드 변경 없음) 렌더 결과가 바뀐 문구로 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 언어별 메시지 파일, **When** 특정 언어의 특정 알림 제목을 수정하면, **Then** 코드 수정 없이 그 언어·그 알림의 렌더 결과만 바뀐다.
2. **Given** 이모지가 포함된 문구를 메시지 파일에 저장, **When** 렌더하면, **Then** 이모지와 비라틴 문자(한글·한자·태국어·키릴 등)가 깨지지 않고 그대로 나온다.
3. **Given** 이관 완료 상태, **When** 코드베이스를 검색하면, **Then** 문구를 담은 코드 상수는 남아 있지 않다(문구의 출처는 메시지 파일 하나).

---

### User Story 3 - 누락된 번역이 배포 전에 잡힌다 (Priority: P2)

개발자는 문구가 파일로 옮겨진 뒤에도, 어떤 유형·슬롯·언어 조합의 문구가 빠졌다면 발송 시점이 아니라 빌드(테스트) 단계에서 알게 된다. 간체(zh-Hans)와 번체(zh-Hant)가 서로 섞이거나 다른 언어로 조용히 대체되는 일도 테스트가 막는다.

**Why this priority**: 상수 맵일 때는 컴파일·코드 리뷰가 누락을 드러냈지만, 파일 기반에서는 런타임에야 드러난다. 누락 검증이 없으면 이관이 안전장치를 하나 없애는 셈이 된다.

**Independent Test**: 메시지 파일에서 임의의 키 하나를 지우고 테스트를 돌려 실패하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 알림 유형 5종·스캔 제안 슬롯 2종·수신거부 안내 × 지원 언어 10종, **When** 누락 검증 테스트를 실행하면, **Then** 전 조합에 제목·본문(수신거부 안내는 안내문)이 존재함이 확인된다.
2. **Given** 한 언어의 키 하나가 빠진 상태, **When** 테스트를 실행하면, **Then** 빠진 유형·슬롯·언어를 짚어 실패한다.
3. **Given** zh-Hans 사용자와 zh-Hant 사용자, **When** 같은 알림을 렌더하면, **Then** 각각 간체·번체 문구가 나오고 서로 바뀌거나 다른 언어로 대체되지 않는다.
4. **Given** 어떤 언어의 문구가 없는 상태, **When** 그 언어로 렌더하면, **Then** 다른 언어 문구로 조용히 대체하지 않고 오류를 낸다(현재 동작 유지).

---

### Edge Cases

- 치환 인자에 없는 자리표시자(예: 인자 없이 `{food}` 포함 문구 렌더) → 현재처럼 빈 문자열로 치환된다.
- 문구에 따옴표·작은따옴표·중괄호 외 특수문자(‘ ’ “ ” 「 」 ¿ > 등)가 있어도 원문 그대로 나온다 — 메시지 파일 포맷의 이스케이프 규칙 때문에 글자가 사라지거나 변형되면 안 된다.
- 서버 실행 환경의 기본 언어(시스템 로케일)가 무엇이든 결과가 같다 — 요청 언어의 문구가 없을 때 서버 기본 언어 문구로 새지 않는다.
- 슬롯이 지정됐지만 그 유형에 슬롯별 문구가 없는 경우 → 유형 기본 문구를 쓴다(현재 동작).
- 웹 서버와 배치 서버가 같은 알림을 렌더하면 결과가 동일하다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 모든 푸시 문구(알림 유형 5종의 제목·본문, 스캔 제안의 점심·저녁 슬롯별 제목·본문, 수신거부 안내)를 코드 밖의 언어별 메시지 파일에서 읽어야 한다.
- **FR-002**: 문구는 유형(·슬롯)마다 **후보 여러 개**를 가질 수 있고, 렌더 때마다 그중 하나를 무작위로 골라 제목·본문을 **같은 후보 번호**로 짝지어 쓴다. 후보 수는 언어마다 같아야 한다. 수신거부 안내는 후보 없이 하나다. (2026-09-22 — Codex 제안 + 윤문 검수 후보 3개씩 채택, 수신거부 안내는 기존 문구 고정.)
- **FR-003**: 시스템은 알림 유형·슬롯(선택)·언어의 조합으로 문구를 결정해야 하며, 슬롯이 지정되고 슬롯별 문구가 있으면 그것을, 없으면 유형 기본 문구를 써야 한다.
- **FR-004**: 시스템은 문구 안의 이름 있는 자리표시자(`{food}`, `{title}`, `{body}` 등)를 전달된 인자로 치환하고, 인자가 없는 자리표시자는 빈 문자열로 치환해야 한다.
- **FR-005**: 광고성 유형은 제목 앞에 "(광고) " 를 붙이고 본문 끝에 줄바꿈과 해당 언어의 수신거부 안내를 붙여야 하며, 비광고성 유형에는 붙이지 않아야 한다.
- **FR-006**: 제목은 200자, 본문은 1000자를 넘지 않도록 절단해야 하며, 광고성 유형은 수신거부 안내가 온전히 남도록 본문을 먼저 절단해야 한다.
- **FR-007**: 지원 언어 10종(ko·zh-Hans·en·ja·zh-Hant·vi·id·th·ru·es)은 각각 자기 언어의 메시지 파일로 해석돼야 하며, 특히 zh-Hans 와 zh-Hant 는 언어 태그 기준으로 서로 다른 파일로 구분돼야 한다.
- **FR-008**: 요청 언어의 문구가 없으면 시스템은 다른 언어(서버 기본 언어 포함)의 문구로 대체하지 않고 오류를 내야 한다.
- **FR-009**: 웹 서버와 배치 서버는 동일한 메시지 파일과 동일한 해석 규칙을 사용해야 한다 — 같은 입력에 같은 렌더 결과.
- **FR-010**: 메시지 파일은 UTF-8 로 읽혀야 하며, 이모지와 비라틴 문자가 손실 없이 렌더돼야 한다.
- **FR-011**: 유형·슬롯·수신거부 안내 × 언어 10종의 전 조합에 문구가 존재하는지 검증하는 자동화 테스트가 있어야 하며, 누락 시 어느 조합인지 드러내며 실패해야 한다.
- **FR-012**: 치환·광고 접두·수신거부 안내·길이 절단 동작이 이관 전과 같음을 자동화 테스트로 고정해야 한다.
- **FR-013**: 이관이 끝나면 문구를 담은 코드 상수는 제거돼야 한다 — 문구의 출처는 메시지 파일 하나다.

### Key Entities

- **푸시 문구**: 알림 유형(+선택적 식사 슬롯)과 언어로 식별되는 제목·본문 쌍. 자리표시자를 포함할 수 있다.
- **수신거부 안내**: 언어별 한 줄 안내문. 광고성 유형 본문 끝에만 붙는다.
- **지원 언어**: 서비스가 지원하는 10개 언어 코드. 각 코드는 메시지 파일 하나에 대응한다.
- **알림 유형**: HELPFUL·SCAN_SUGGESTION·REVIEW_REMINDER·NEWS·MEAL_TIME. 유형마다 광고성 여부를 가진다.
- **식사 슬롯**: 점심·저녁. 현재 스캔 제안 유형만 슬롯별 문구를 가진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 유형 5종 + 슬롯 2종 × 언어 10종의 전 조합에서 후보 수가 언어 간 같고, 광고 접두·수신거부 안내·절단·치환 규칙이 100% 적용된다.
- **SC-002**: 문구 한 줄 수정에 필요한 변경이 메시지 파일 1개·1줄로 끝난다(코드 파일 변경 0).
- **SC-003**: 임의의 문구 키 1개를 지우면 자동화 테스트가 100% 실패하며, 실패 메시지에서 누락된 유형·슬롯·언어를 식별할 수 있다.
- **SC-004**: zh-Hans·zh-Hant 렌더 결과가 각각 간체·번체 문구와 일치한다(교차·대체 0건).
- **SC-005**: 이모지를 포함한 문구가 웹 서버·배치 서버 양쪽에서 원문과 동일하게 렌더된다.
- **SC-006**: 이관 후 코드베이스에 문구 상수가 0개 남는다.

## Assumptions

- 신규 언어/유형 추가·문구의 무배포 실시간 교체(외부 저장소, 핫 리로드)는 범위 밖이다 — 문구 수정은 여전히 배포를 거치되, 코드가 아닌 메시지 파일만 고치면 된다.
- 운영 문구에 이모지가 들어간다(후보당 1개). UTF-8 검증은 운영 문구 자체로 한다.
- 후보 선택은 발송 건(기기)마다 독립 무작위다 — 같은 회원의 기기 두 대가 다른 후보를 받을 수 있고, 회원별 고정·순환·A/B 측정은 하지 않는다.
- "(광고) " 접두는 현재처럼 언어와 무관한 고정 문자열로 유지한다(번역 대상 아님 — 국내 법규 표기).
- NEWS 유형은 전 언어가 동일한 통과형 문구(`{title}`/`{body}`)다. 누락 검증의 일관성을 위해 다른 유형과 같은 방식으로 메시지 파일에 둔다.
- 길이 기준 "자"는 현재 구현과 같은 문자 단위(문자열 길이)다.
- 렌더러의 호출 계약(유형·언어·인자·슬롯 → 제목·본문)은 바뀌지 않으므로 발송 파이프라인·배치 잡 등 호출부는 수정 대상이 아니다.
- 웹 서버는 전체 구성 요소를 자동 탐색하고 배치 서버는 필요한 구성 요소만 골라 조립하므로, 메시지 파일 해석 구성은 양쪽이 공유하는 공통 모듈에 한 벌만 둔다.
