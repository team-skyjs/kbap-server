# Feature Specification: 홈 최근 스캔 조회 쿼리 DB 레벨 최적화

**Feature Branch**: `fix/kb717-recent-scans-query`

**Created**: 2026-10-05

**Status**: Draft

**Jira**: [KB-717](https://simhani1.atlassian.net/browse/KB-717)

**Input**: User description: "KB-717 홈 최근 스캔 조회 쿼리를 DB 레벨에서 최적화한다. Jira KB-717 본문을 스펙 입력으로 삼는다: ScanHistoryJpaRepository.findRecentScannedFoods 가 회원의 scan_history 전체를 food 와 조인해 food_id 로 group by + max(created_at) 정렬 후 limit 10 — 1년치 더미(회원 4,477행·853종)에서 70 rps 부하 중 DB avg 2,803 ms(p95 15.6 s), 무경합 21 ms. 테이블 추가·변경 없이 쿼리·인덱스 레벨에서 어디까지 줄일 수 있는지 확인하고, 안 되면 회원×음식 읽기 모델(member_scanned_food)을 후속 태스크로 뺀다. 홈 응답 계약 불변(READY 만, 최대 10, 마지막 스캔 시각 순), 기존 홈·리포지토리 테스트 통과, 같은 시드·70 rps 에서 avg 100 ms 미만·무경합 10 ms 미만을 RDS 슬로우 로그로 확인. 측정 근거 문서: docs/performance/recent-scans-query-analysis.md, 시드/정리 SQL: scripts/perf/seed-home-load.sql · cleanup-home-load.sql (dev 에 시드가 들어가 있음, 슬로우 로그 켜져 있음, k6 스크립트 ~/Desktop/1만명-tomcat스레드.js 70 rps)"

## 배경

홈 화면의 최근 스캔 섹션은 "이 회원이 최근에 본 음식 10개, 음식별로 한 번씩, 마지막 스캔 시각 순"을 보여 준다. 스캔 이력은 스캔할 때마다 메뉴 항목당 한 행이 쌓이는 로그라서 같은 음식이 여러 행으로 반복된다. 지금 조회는 회원의 스캔 행 전부를 읽어 음식별로 묶고 정렬한 뒤에야 10개를 자른다. 비용이 결과 크기(10)가 아니라 회원의 누적 스캔 행 수에 비례하고 상한이 없다.

dev 에 1년치 규모 더미 데이터(스캔 이력 17만 행, 측정 회원 4,477행·음식 853종)를 넣고 동시 1,000명·70 rps 부하를 걸었을 때 실측값은 다음과 같다(RDS 슬로우 로그).

| 조건 | DB 실행 시간 |
|---|---|
| 70 rps 부하 중 평균 | 2,803 ms |
| 70 rps 부하 중 p95 | 15,582 ms |
| 무경합 | 21 ms |
| 현재 실데이터(회원 477행) | 7 ms |

이 쿼리 하나가 홈 요청 DB 시간의 48% 를 차지한다. 실행 계획에는 임시 테이블과 정렬이 남는다. 정렬 기준인 "음식별 마지막 스캔 시각"이 저장된 값이 아니라 집계 결과이기 때문이다. 음식 공개 상태 확인도 회원의 모든 스캔 행마다 수행된다.

이 작업은 **테이블을 추가하거나 바꾸지 않고** 쿼리와 인덱스만으로 어디까지 줄일 수 있는지 확인한다. 검토 후보는 Jira 본문의 네 가지다.

1. 스캔 이력만으로 음식별 마지막 스캔 시각을 먼저 뽑고, 상위 N개(비공개 탈락분을 고려해 10보다 넉넉히)만 음식과 결합해 공개 상태를 거른다.
2. 최신 행부터 읽으며 음식 중복을 제거하는 형태와 그에 맞는 인덱스.
3. 음식이 먼저 훑어지는 실행 계획 차단.
4. 조회 컬럼을 홈 카드에 필요한 것으로 좁혀 적재 비용 축소.

쿼리 레벨의 한계가 확인되면 회원×음식 단위 읽기 모델(`member_scanned_food`)은 이 작업에서 만들지 않고 후속 태스크로 뺀다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔을 많이 한 회원도 홈이 빠르게 열린다 (Priority: P1)

1년 동안 꾸준히 스캔한 회원(스캔 수천 행)이 홈을 연다. 최근 스캔 섹션의 내용은 이전과 같고, 그 조회가 홈 응답을 붙잡지 않는다. 다른 회원들이 동시에 홈을 여는 부하 상황에서도 마찬가지다.

**Why this priority**: 이 작업의 유일한 목적이다. 홈은 앱의 첫 화면이고, 현재 이 조회 하나가 부하 중 평균 2.8초를 쓴다.

**Independent Test**: 시드된 dev 에서 같은 부하 스크립트(동시 1,000명, think 12~16초, 약 70 rps)를 돌리고 RDS 슬로우 로그에서 이 쿼리의 실행 시간을 집계한다. 기존 홈·리포지토리 테스트를 실행한다.

**Acceptance Scenarios**:

1. **Given** 시드된 dev(측정 회원 4,477행·853종), **When** 70 rps 부하 중 슬로우 로그를 집계하면, **Then** 최근 스캔 조회의 DB 평균 실행 시간이 100 ms 미만이다.
2. **Given** 같은 시드, **When** 부하 없이 측정 회원으로 홈을 호출하면, **Then** 최근 스캔 조회의 DB 실행 시간이 10 ms 미만이다.
3. **Given** 여러 음식을 여러 번 스캔한 회원, **When** 홈을 조회하면, **Then** 최근 스캔 섹션은 음식별로 한 번씩, 마지막 스캔 시각이 최신인 순으로, 최대 10개를 보여 준다.
4. **Given** 스캔한 음식 중 일부가 공개 상태(READY)가 아니거나 삭제됨, **When** 홈을 조회하면, **Then** 그 음식은 섹션에 나오지 않고 나머지 공개 음식으로 최대 10개가 채워진다.
5. **Given** 기존 홈 통합 테스트와 스캔 이력 리포지토리 테스트, **When** 변경 후 실행하면, **Then** 전부 통과한다.

### User Story 2 - 선택 근거와 한계가 기록으로 남는다 (Priority: P2)

이 쿼리를 다음에 손대는 개발자는 PR 본문에서 기준선, 후보별 비교, 선택 이유를 읽을 수 있다. 쿼리 레벨로 목표에 못 미쳤다면 그 한계 수치와 읽기 모델 전환 근거를 담은 후속 태스크를 찾을 수 있다.

**Why this priority**: 목표 달성 여부와 무관하게 "어디까지 되는가"를 확인하는 것이 태스크의 정의다. 기록이 없으면 같은 탐색을 다시 한다.

**Independent Test**: PR 본문에 기준선·후보 비교표·선택 근거가 있는지, 목표 미달 시 후속 Jira 태스크가 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 시드된 dev, **When** 작업을 시작하면, **Then** 현재 쿼리의 실행 계획 분석 결과와 슬로우 로그 수치(무경합 21 ms, 부하 중 평균 2,803 ms)가 기준선으로 기록된다.
2. **Given** 후보 쿼리·인덱스들, **When** 하나를 고르면, **Then** PR 본문에 후보별 실행 계획·검사 행 수·임시 테이블과 정렬 유무가 비교되어 있고 선택 근거가 적혀 있다.
3. **Given** 선택한 안이 성능 목표에 못 미침, **When** 작업을 마치면, **Then** 한계 수치와 읽기 모델 전환 근거를 적은 후속 태스크가 만들어져 있다.

---

### Edge Cases

- 스캔 이력이 없는 회원은 빈 섹션을 받는다(지금과 같다).
- 공개 음식을 10종 미만 스캔한 회원은 있는 만큼만 받는다.
- 최근에 스캔한 음식 다수가 비공개여도 공개 음식이 10개 이상 있으면 10개가 채워져야 한다. 후보를 넉넉히 뽑는 방식이라면 이 경우에 결과가 모자라지 않아야 한다.
- 같은 음식을 수백 번 반복 스캔한 회원(음식 종류는 적고 행은 많음)도 결과가 같고 성능 목표 안에 든다.
- 삭제된(소프트 삭제) 스캔 행과 삭제된 음식은 결과에 반영되지 않는다.
- 다른 회원의 스캔은 결과에 섞이지 않는다.
- 배포 중 구 버전과 신 버전이 같은 DB 를 함께 쓰는 동안 양쪽 모두 정상 동작한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 홈 최근 스캔 섹션은 요청 회원이 스캔한 음식을 음식별로 한 번씩, 마지막 스캔 시각 내림차순으로, 최대 10개 반환해야 한다.
- **FR-002**: 공개 상태(READY)이고 삭제되지 않은 음식만 반환해야 한다. 비공개·삭제 음식이 빠진 자리는 그다음으로 최근에 스캔한 공개 음식이 채운다.
- **FR-003**: 각 항목은 그 음식의 마지막 스캔 시각을 변경 전과 같은 값으로 담아야 한다.
- **FR-004**: 홈 응답의 구조·필드·값·정렬은 변경 전과 같아야 한다. 기존 홈 통합 테스트와 스캔 이력 리포지토리 테스트가 통과해야 한다.
- **FR-005**: 새 테이블을 만들지 않고 기존 테이블의 컬럼도 바꾸지 않는다. 허용되는 변경은 조회 쿼리와 인덱스다.
- **FR-006**: 인덱스를 바꾸는 경우, 같은 인덱스에 기대는 다른 조회(내 스캔 목록 페이지, 내 스캔 검색, 음식별 마지막 스캔 시각 조회)가 느려지지 않아야 한다.
- **FR-007**: 변경 전 기준선(실행 계획 분석, 무경합·부하 중 슬로우 로그 수치)을 시드된 dev 에서 기록해야 한다.
- **FR-008**: 후보 쿼리·인덱스를 실행 계획 분석으로 비교하고, 선택 근거(플랜·검사 행 수·임시 테이블과 정렬 유무)를 PR 본문에 적어야 한다.
- **FR-009**: 변경 후 같은 시드·같은 부하로 재측정해 전후 수치를 PR 본문에 적어야 한다.
- **FR-010**: 쿼리 레벨로 성능 목표에 못 미치면 한계 수치와 읽기 모델 전환 근거를 적은 후속 Jira 태스크를 만들어야 한다. 읽기 모델 자체는 이 작업에서 구현하지 않는다.

### Key Entities

- **스캔 이력**: 회원이 메뉴판을 스캔할 때 인식된 메뉴 항목마다 한 행씩 쌓이는 로그다. 회원, 음식, 가격, 스캔 시각을 담는다. 같은 음식을 다시 스캔하면 행이 추가된다.
- **음식**: 공개 상태(READY 여부)와 삭제 여부를 가진다. 홈 카드에 필요한 표시 정보의 출처다.
- **최근 스캔 항목**: 음식 하나와 그 회원의 마지막 스캔 시각의 쌍이다. 홈 섹션의 한 칸이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 1년치 규모 시드와 약 70 rps 부하에서 최근 스캔 조회의 DB 평균 실행 시간이 100 ms 미만이다(기준선 2,803 ms).
- **SC-002**: 같은 시드에서 무경합 시 최근 스캔 조회의 DB 실행 시간이 10 ms 미만이다(기준선 21 ms).
- **SC-003**: 홈 응답은 변경 전과 같고, 기존 홈·리포지토리 테스트가 100% 통과한다.
- **SC-004**: PR 본문만 읽고 기준선, 후보별 비교, 선택 근거, 전후 수치를 확인할 수 있다.
- **SC-005**: SC-001 또는 SC-002 에 못 미친 경우, 한계 수치와 전환 근거를 담은 후속 태스크가 존재한다.

## Assumptions

- 범위는 홈 최근 스캔 조회 하나다. 같은 구조를 가진 내 스캔 목록 페이지와 내 스캔 검색은 이 작업에서 고치지 않는다. 다만 인덱스 변경으로 그 둘이 나빠지면 안 된다.
- 성능 수치의 판정 근거는 RDS 슬로우 로그다. 애플리케이션 쪽 쿼리 통계 로그는 네이티브 쿼리의 DB 시간을 담지 못해 쓰지 않는다.
- 측정 환경은 dev 이며 더미 시드가 이미 들어가 있고 슬로우 로그가 켜져 있다. 시드는 `scripts/perf/seed-home-load.sql` 로 넣고 `cleanup-home-load.sql` 로 지운다.
- 측정 회원의 실제 행 수는 시드 4,000행에 기존 실데이터가 더해진 4,477행·853종이다.
- 부하는 기존 k6 스크립트(동시 1,000명, think 12~16초, 약 70 rps, 1분 15초) 그대로 쓴다. 전후 비교는 같은 데이터·같은 부하로 한다.
- 마지막 스캔 시각이 같은 음식 사이의 순서는 지금도 정해져 있지 않으므로, 동률 순서는 응답 계약에 포함하지 않는다.
- 섹션 크기 10은 홈이 요청하는 값이며 이 작업에서 바꾸지 않는다.
- 인덱스 추가·교체는 "테이블 추가·변경 없이"의 범위 안이다. 배포 중 구 버전 코드가 새 인덱스 위에서 도는 구간이 있으므로, 기존 인덱스를 지우는 경우 구 쿼리가 버틸 수 있는지 확인한다.
- 캐시 도입과 읽기 모델 구현은 범위 밖이다.
