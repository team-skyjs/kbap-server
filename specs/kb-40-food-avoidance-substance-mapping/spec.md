# Feature Specification: 음식별 81종 기피 성분 포함 여부·포함 확률 저장 (레시피/재료 모델 제거)

**Feature Branch**: `kb-40-food-avoidance-substance-mapping`

**Created**: 2026-07-03

**Status**: Draft

**Input**: User description: "메뉴마다 기존에는 레시피 정보를 저장하고 있었다. 이제부터는 db에 갖고 있는 81종 기피 성분 중에 해당 메뉴에 포함되는 것이 있는지 여부를 저장해야 하며, 포함될 때 확률을 1~100 사이의 퍼센티지로 저장할 것이다. 즉 음식 레시피 정보는 불필요하고 81종 기피 성분의 포함 여부만 관리하면 된다는 것." (Jira: KB-40)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 음식별 기피 성분 포함 여부와 포함 확률 저장 (Priority: P1)

식이 제약(알레르기·종교·기호)으로 특정 성분을 피해야 하는 사용자를 지원하려면, 각 음식이 **81종 기피 성분 카탈로그** 중 어떤 성분을 포함하는지, 그리고 그 성분이 실제로 들어 있을 가능성이 얼마나 되는지를 알아야 한다. 지금은 이 정보를 음식의 재료 구성(레시피)을 거쳐 간접적으로만 도출한다. 앞으로는 음식마다 "포함하는 기피 성분과 그 포함 확률(1~100%)"을 직접 보유해, 성분 포함 여부 판정을 한 번의 조회로 끝낼 수 있게 한다.

**Why this priority**: 이 앱의 핵심 가치(사용자가 피해야 할 성분을 정확히 알려주는 것)를 직접 실현하는 데이터다. 이후 음식 상세·메뉴 스캔 판정이 모두 이 정보를 근거로 삼으므로, 가장 먼저 확보해야 할 기반이다.

**Independent Test**: 임의의 음식에 대해 "포함하는 기피 성분 목록과 각 성분의 포함 확률"을 조회했을 때, 카탈로그 81종의 부분집합이 반환되고 각 성분의 확률이 1~100 범위인지 확인하면 독립적으로 검증된다. 재료/레시피 데이터 없이도 이 정보만으로 성립한다.

**Acceptance Scenarios**:

1. **Given** 81종 기피 성분 카탈로그와 특정 음식이 있는 상태에서, **When** 그 음식이 포함하는 기피 성분을 조회하면, **Then** 카탈로그에 속한 성분들의 부분집합과 각 성분의 포함 확률(1~100 정수 퍼센티지)이 함께 반환된다.
2. **Given** 어떤 기피 성분도 포함하지 않는 음식이 있는 상태에서, **When** 그 음식의 기피 성분을 조회하면, **Then** 빈 목록이 반환된다(포함 성분 없음).
3. **Given** 음식에 기피 성분 포함 정보를 등록하려는 상황에서, **When** 포함 확률로 1~100 범위를 벗어난 값(0, 101, 음수)을 지정하면, **Then** 저장이 거부된다.
4. **Given** 한 음식과 한 기피 성분의 조합이 이미 등록된 상태에서, **When** 동일한 (음식, 성분) 조합을 다시 등록하려 하면, **Then** 중복 저장이 허용되지 않는다(조합은 유일하다).

### User Story 2 - 음식 레시피/재료 모델 제거 (Priority: P2)

시스템을 유지·확장하는 담당자 입장에서, 더 이상 사용하지 않는 레시피/재료 구성 데이터를 걷어내 관리 대상을 단순화해야 한다. 재료 목록·재료별 포함 비율·재료명 번역·재료-성분 매핑은 기피 성분 포함 여부를 직접 저장하면 불필요해진다. 이 데이터를 유지하면 저장·시드·번역 관리 비용만 남고, 조회 경로에 불필요한 조인이 계속 낀다.

**Why this priority**: US1이 성립하면 레시피/재료는 소비자가 사라진 죽은 데이터가 된다. 제거는 US1의 가치를 실현하는 데 필수는 아니지만(그래서 P2), 정리하지 않으면 이중 표현이 남아 혼란과 유지 비용을 만든다.

**Independent Test**: 음식 관련 어떤 조회·응답 경로에서도 재료 목록·재료별 포함 비율·재료명·재료-성분 매핑이 더 이상 산출·참조되지 않는지 확인하면 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 레시피/재료 모델이 제거된 상태에서, **When** 음식 데이터를 조회하면, **Then** 재료 목록·재료별 포함 비율이 결과에 존재하지 않는다.
2. **Given** 재료-성분 매핑이 제거된 상태에서, **When** 음식의 기피 성분을 조회하면, **Then** 재료를 경유하지 않고 음식에 직접 저장된 기피 성분 정보만 사용된다.

---

### User Story 3 - 음식 상세 응답을 기피 성분 중심으로 제공 (Priority: P3)

음식 상세를 조회하는 최종 사용자 입장에서, 재료 나열 대신 "이 음식에 들어 있는(또는 들어 있을 수 있는) 기피 성분과 그 가능성"을 보고 자신이 먹어도 되는지 판단할 수 있어야 한다. 레시피가 사라지므로 상세 화면의 성분 정보도 기피 성분 중심으로 바뀐다.

**Why this priority**: 저장·모델(US1·US2)이 갖춰진 뒤라야 노출할 수 있는 표현 계층이라 마지막 순위다. 이번 범위에 포함되며(사용자 확인), 독립 슬라이스로 두어 US1·US2 완료 후 안전하게 얹는다.

**Independent Test**: 음식 상세를 요청 언어로 조회했을 때, 응답이 그 음식의 포함 기피 성분 목록(표시명·포함 확률·위험 표시)을 담고, 재료 목록 필드가 사라졌는지 확인하면 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 포함 기피 성분이 등록된 음식이 있는 상태에서, **When** 음식 상세를 조회하면, **Then** 응답에 포함 기피 성분 목록(성분 표시명·포함 확률·위험 표시)이 담기고 재료 목록은 포함되지 않는다.
2. **Given** 요청 언어가 한국어가 아닌 상태에서, **When** 음식 상세를 조회하면, **Then** 기피 성분 표시명이 요청 언어로 제공되고, 번역이 없으면 한국어로 폴백한다.
3. **Given** 포함 기피 성분이 없는 음식이 있는 상태에서, **When** 음식 상세를 조회하면, **Then** 기피 성분 목록이 빈 상태로 정상 응답한다.

---

### Edge Cases

- 포함 확률이 경계값(1, 100)일 때 정상 저장되어야 한다. 0은 "포함 안 함"을 뜻하므로 저장 대상이 아니라 거부된다.
- 카탈로그(81종)에 존재하지 않는 성분을 음식에 포함으로 등록하려 하면 거부된다.
- 같은 음식에 같은 성분을 중복 등록하려 하면 거부된다(조합 유일).
- 기피 성분을 하나도 포함하지 않는 음식은 유효하며, 빈 목록으로 취급된다.
- 기존에 재료를 통해 특정 기피 성분이 도출되던 음식은, 전환 후에도 동일한 기피 성분 집합을 직접 보유해야 한다(정보 손실 없음).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 각 음식에 대해, 81종 기피 성분 카탈로그 중 그 음식이 포함하는 성분들의 집합을 저장할 수 있어야 한다.
- **FR-002**: 시스템은 음식이 포함하는 각 기피 성분마다 포함 확률을 1~100 사이의 정수 퍼센티지로 저장해야 한다.
- **FR-003**: 시스템은 포함 확률이 1~100 범위를 벗어나면(0, 101 이상, 음수) 저장을 거부해야 한다.
- **FR-004**: 시스템은 한 음식과 한 기피 성분의 조합을 최대 한 번만 저장해야 한다(중복 금지, 조합 유일).
- **FR-005**: 시스템은 카탈로그(81종)에 존재하는 기피 성분에 한해 음식의 포함 성분으로 등록을 허용해야 한다.
- **FR-006**: 시스템은 임의의 음식에 대해, 포함하는 기피 성분 목록과 각 성분의 포함 확률을, 재료를 경유하지 않고 직접 조회할 수 있어야 한다.
- **FR-007**: 시스템은 기피 성분을 하나도 포함하지 않는 음식을 유효한 상태로 취급하고 빈 목록으로 반환해야 한다.
- **FR-008**: 시스템은 음식의 레시피/재료 구성(재료 목록, 재료별 포함 비율, 재료명·재료명 번역, 재료-성분 매핑)을 더 이상 보유하거나 조회 경로에서 산출하지 않아야 한다.
- **FR-009**: 시스템은 전환 이전에 재료를 통해 각 음식에 대해 도출되던 기피 성분 집합을, 전환 이후에도 그 음식이 직접 보유하도록 보존해야 한다(정보 손실 없음).
- **FR-010**: 기피 성분 카탈로그 자체(81종 코드·표시명·다국어 번역)는 이 변경으로 바뀌지 않고 유지되어야 한다.
- **FR-011** *(User Story 3)*: 음식 상세 조회 응답은 재료 목록 대신 포함 기피 성분 목록(성분 표시명·포함 확률·위험 표시)을 제공해야 하며, 요청 언어에 맞춰 성분 표시명을 제공하고 번역이 없으면 한국어로 폴백해야 한다.

### Key Entities *(include if feature involves data)*

- **음식(Food)**: 메뉴 한 종류. 한국어 음식명, 이미지, 간단/상세 설명(및 다국어 번역)을 가진다. 이 변경 이후 재료 구성 대신 "포함 기피 성분과 그 포함 확률"의 집합을 보유한다.
- **기피 성분(Avoidance Substance)**: 사용자가 피할 수 있는 성분. 81종 카탈로그로 관리되며 코드·한국어 표시명·다국어 번역을 가진다(본 변경으로 바뀌지 않음).
- **음식-기피성분 포함(Food Avoidance Substance)**: 특정 음식이 특정 기피 성분을 포함한다는 사실과, 그 포함 확률(1~100%)을 나타내는 연결. (음식, 성분) 조합은 유일하다.
- **[제거 대상] 재료(Ingredient) 및 음식-재료 연결**: 기존 레시피 모델. 재료 기준 정보·재료명 번역·음식별 재료 포함 비율·재료-성분 매핑을 포함하며, 이 변경으로 음식 모델에서 제거된다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 모든 음식에 대해, 포함하는 기피 성분 목록(81종의 부분집합)과 각 성분의 포함 확률(1~100)을 한 번의 조회로 얻을 수 있다.
- **SC-002**: 어떤 음식 조회·응답 경로에서도 재료 목록·재료별 포함 비율·재료-성분 매핑이 산출되지 않는다(레시피 모델 사용처 0건).
- **SC-003**: 전환 이전에 재료를 통해 각 음식에서 도출되던 기피 성분 집합이, 전환 이후 그 음식의 직접 보유 집합과 100% 일치한다(정보 손실 0).
- **SC-004**: 저장된 모든 음식-기피성분 포함 값의 포함 확률이 1~100 범위 안에 있고, 범위를 벗어난 값은 하나도 저장되지 않는다.
- **SC-005**: 음식 상세 조회 1회의 조회 횟수가 포함 기피 성분 개수에 비례해 늘어나지 않는다(성분 개수와 무관하게 상수 횟수 조회, N+1 없음).

## Assumptions

- **API 응답 재편 범위 (확정)**: 음식 상세 응답을 재료 목록에서 포함 기피 성분 목록으로 재편하는 것(US3, FR-011)을 **이번 범위에 포함**한다. 저장·도메인(US1·US2) 완료 후 노출 계층이라 우선순위는 P3이지만, 별도 후속으로 미루지 않고 이번 기능에서 함께 완결한다. (2026-07-03 사용자 확인.)
- **재료 데이터 처리 (확정)**: 재료 카탈로그(`ingredient`)·재료명 번역(`ingredient_name_translation`)·음식-재료 연결(`food_ingredient`)·재료-성분 매핑(`ingredient_avoidance_substance`)과 관련 도메인/엔티티/코드를 **전부 제거**한다. 존치하지 않는다. (2026-07-03 사용자 확인.)
- **포함 확률 의미**: 포함 확률은 "그 성분이 해당 음식에 실제로 들어 있을 가능성"을 뜻하며 1~100 정수 퍼센티지다. 조리법·가게마다 편차가 있어 확정적이지 않은 포함을 표현한다. 0은 저장하지 않으며 "포함 안 함"과 동치다.
- **기존 데이터 이행(시드)**: 전환 시 각 음식의 포함 기피 성분 집합은 기존 "음식→재료→기피성분" 연결을 접어(collapse) 도출해 보존한다. 기존 데이터에는 확률 개념이 없었으므로, 도출된 포함 성분의 초기 포함 확률 기본값은 구현 단계(plan)에서 정한다.
- **위험 표시(riskStatus)**: 음식 상세의 위험 표시는 현재 mock 판정을 유지하며, 실제 사용자 회피 조건 기반 판정은 이 기능의 범위 밖이다.
- **대상 범위**: 이 변경은 음식(메뉴) 도메인과 그 저장·조회에 한정한다. 메뉴 스캔(menu-scan) 판정 로직·기피 성분 카탈로그 자체·사용자 회피 프로필은 바꾸지 않는다.
