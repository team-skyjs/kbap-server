# Feature Specification: 푸시 알림 데이터 기반 (기기 토큰·알림 설정·알림 이력·발송 추적)

**Feature Branch**: `kb-464-push-notification-schema`

**Created**: 2026-09-07

**Status**: Draft

**Input**: User description: "464 워크트리" — Jira KB-464 「[BE] 푸시 알림 데이터 모델·Flyway 마이그레이션 (notification_device·notification_setting·notification·notification_dispatch)」. 에픽 KB-463 푸시 알림의 첫 태스크.

## 배경

앱(FE)은 OS 알림 권한 요청, 푸시 토큰 발급, 수신·탭 처리, 딥링크 라우팅, 알림함 화면, 알림 설정 화면(토글 3개), 종 아이콘 NEW 배지까지 갖추고 있다. 서버 연동만 없다. 토큰은 발급 후 서버에 전달되지 않고, 알림함·설정·미읽음 수는 전부 기기 로컬에만 있다. 그 결과 기기를 바꾸면 알림 이력과 설정이 사라지고, 서버는 누구에게 무엇을 보낼지 알 방법이 없다.

이 기능은 푸시 알림 전체(에픽 KB-463)의 **저장 기반**을 만든다. 서버가 "어느 기기에", "어떤 알림을 받기로 했는지", "무엇을 보냈고 어떻게 됐는지" 를 기억할 수 있게 한다. 이 위에 후속 태스크(토큰 API KB-465, 설정 API KB-466, 알림함 API KB-467, 발송 배치 KB-468~473)가 쌓인다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 기기 단위 푸시 토큰 보관과 회원 연결 (Priority: P1)

앱을 설치한 기기마다 푸시 토큰 하나를 서버가 보관한다. 게스트 상태에서도 토큰은 보관되며, 그 기기에서 로그인하면 토큰이 회원에게 연결되고, 로그아웃·탈퇴하면 연결이 풀린다. 한 회원이 여러 기기를 쓰면 기기 수만큼 토큰이 회원에 연결된다.

**Why this priority**: 토큰이 없으면 어떤 알림도 보낼 수 없다. 실기기 토큰이 서버에 있어야 후속 배치 발송을 검증할 수 있고, FE 가 병렬 작업을 시작할 수 있는 기준점(KB-465)도 이 저장 구조에 의존한다.

**Independent Test**: 기기 식별자(설치 UUID)와 토큰을 저장 → 같은 기기 식별자로 다시 저장하면 새 행이 생기지 않고 갱신됨 → 회원을 연결하고 다시 해제할 수 있음. 저장 계층만으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 서버에 기록이 없는 기기, **When** 기기 식별자·토큰·플랫폼·언어를 저장하면, **Then** 그 기기 식별자로 정확히 하나의 토큰 기록이 존재하고 회원 연결은 비어 있다.
2. **Given** 게스트 기기의 토큰 기록, **When** 그 기기에서 회원이 로그인하면, **Then** 같은 기록에 회원이 연결되고 기록 수는 늘지 않는다.
3. **Given** 회원에 연결된 토큰 기록, **When** 로그아웃하면, **Then** 회원 연결만 비워지고 토큰·언어·게스트 설정은 남는다.
4. **Given** 회원에 연결된 토큰 기록, **When** 회원이 탈퇴하면, **Then** 그 회원과의 연결이 남지 않는다(연결 해제 또는 기록 제거).
5. **Given** 한 회원이 기기 두 대에서 로그인, **When** 회원 기준으로 토큰을 조회하면, **Then** 두 기록이 모두 조회된다.
6. **Given** 기기의 토큰이 바뀜(앱 재설치·토큰 갱신), **When** 같은 기기 식별자로 새 토큰을 저장하면, **Then** 기존 기록의 토큰만 바뀐다.

### User Story 2 - 회원 알림 설정 보관과 광고성 수신 동의 기록 (Priority: P2)

회원은 선호 2가지(리뷰 도움됨·리뷰 리마인더)를 켜고 끌 수 있고, 서버는 그 설정을 회원 단위로 보관한다. 광고성 정보 수신은 법적 동의이므로 회원·게스트 구분 없이 "동의 행위" 로 기록한다 — 켠 시각과 그때 동의한 문구 버전을 서버가 남기고, 끄면 지우는 게 아니라 철회 시각을 남긴다. 점심 넛지·프로모션 공지 같은 광고성 알림은 유효한(철회되지 않은) 동의가 있고 문구 버전이 충분할 때만 받는다. 게스트는 선호가 없고(리뷰·주문이 회원 전용) 광고성 동의만 기기 식별자로 남긴다. 그 기기에서 가입하면 회원에게 유효한 동의가 없을 때만 게스트 동의가 회원 동의로 이어진다(같은 기록, 최초 동의 시각 보존).

**Why this priority**: 발송 대상 필터링의 근거다. 설정이 없으면 원치 않는 알림을 보내게 되고, 광고성 알림은 동의 시각 기록이 법적으로 필요하다(정보통신망법).

**Independent Test**: 회원 설정을 저장하지 않은 상태에서 조회하면 기본값(도움됨 on, 리마인더 on)이 나온다 → 광고성 수신 동의를 남기면 동의 시각과 문구 버전이 기록되고, 철회하면 기록은 남은 채 유효하지 않게 된다. 저장 계층만으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 설정 기록이 없는 회원, **When** 설정을 조회하면, **Then** 도움됨 on·리마인더 on 으로 해석되고 유효한 광고성 동의는 없다.
2. **Given** 광고성 동의가 없는 회원, **When** 문구 버전 2 로 동의하면, **Then** 동의 시각이 서버 시각으로, 문구 버전이 2 로 기록된 유효한 동의가 생긴다.
3. **Given** 유효한 광고성 동의가 있는 회원, **When** 철회하면, **Then** 유효한 동의는 없어지지만 동의·철회 시각이 기록으로 남는다.
6. **Given** 구 문구(v1)로 켠 회원, **When** 발송에 v2 이상이 필요한 광고성 알림 대상을 뽑으면, **Then** 그 회원은 제외된다.
4. **Given** 회원 설정 기록, **When** 회원 한 명 기준으로 조회하면, **Then** 정확히 하나의 설정 기록만 존재한다.
5. **Given** 게스트 기기, **When** 광고성 수신 동의를 문구 버전 v2 로 켜면, **Then** 기기 기록에 동의 on·버전·서버 시각이 남고 끄면 비워진다.

### User Story 3 - 알림 이력과 발송 추적 보관 (Priority: P3)

서버가 만든 알림(유형·제목·본문·이동 정보)을 수신자별로 기록해 알림함에서 다시 볼 수 있게 하고, 읽음 여부를 알림마다 남긴다. 알림 하나가 실제로 어느 기기 토큰으로 발송됐고 배달 결과가 무엇이었는지(접수 번호·상태·오류)도 별도로 추적한다.

**Why this priority**: 알림함(KB-467)과 영수증 정리 배치(KB-473)의 저장소다. 토큰·설정 없이는 발송 자체가 불가능하므로 우선순위는 셋째지만, 이 기록이 없으면 사용자는 알림을 다시 볼 수 없고 운영자는 실패 원인을 알 수 없다.

**Independent Test**: 회원 대상 알림 기록을 만들고 → 회원 기준 최신순으로 조회되고 → 읽음 시각을 남기면 미읽음 수가 줄고 → 발송 추적 기록에 접수 번호와 상태를 남길 수 있다. 저장 계층만으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 회원 대상 알림 기록 3건, **When** 회원 기준으로 조회하면, **Then** 최신순으로 3건이 나오고 각 건에 유형·제목·본문·이동 정보·생성 시각·읽음 시각(없음)이 있다.
2. **Given** 미읽음 알림 3건, **When** 1건에 읽음 시각을 남기면, **Then** 미읽음 수는 2가 된다.
3. **Given** 알림 1건이 회원의 기기 2대로 발송됨, **When** 발송 추적을 조회하면, **Then** 알림 1건에 발송 추적 2건이 각각 토큰·접수 번호·상태로 연결된다.
4. **Given** 발송 추적 기록, **When** 배달 결과가 "기기 미등록"으로 확인되면, **Then** 그 상태와 오류 사유를 추적 기록에 남길 수 있다.
5. **Given** 게스트 기기 대상 알림, **When** 회원 없이 기기 식별자만으로 알림 기록을 만들면, **Then** 저장이 거부되지 않는다(게스트 알림함 제공 여부는 후속 결정).

---

### Edge Cases

- 같은 기기 식별자로 동시에 두 번 저장 요청이 오면 기록은 하나만 남아야 한다(기기 식별자 유일성이 저장소에서 강제됨).
- 회원이 삭제(소프트 삭제)된 뒤 그 회원에 연결된 토큰·설정·알림 기록은 회원 조회에 노출되지 않아야 한다.
- 토큰 문자열이 같은데 기기 식별자가 다른 경우(기기 식별자 재발급)는 별개 기록으로 취급한다. 중복 발송은 발송 단계에서 걸러야 한다(이 기능 범위 밖).
- 알림 이동 정보(음식 id 등)가 없는 유형(공지)도 저장 가능해야 한다.
- 발송 추적의 접수 번호는 발송 실패 시 비어 있을 수 있다.
- 지원하지 않는 언어 코드가 저장되면 발송 시 기본 언어로 대체한다(저장은 거부하지 않음).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 기기 설치 식별자를 유일키로 하는 푸시 토큰 기록을 보관해야 한다. 기록은 토큰 문자열, 플랫폼(iOS/Android), 기기 언어, 선택적 회원 연결, 게스트 광고성 수신 동의(on/off·문구 버전·동의 시각)를 가진다.
- **FR-002**: 시스템은 하나의 회원에 여러 토큰 기록이 연결되는 것을 허용해야 하며, 회원 기준으로 연결된 토큰을 조회할 수 있어야 한다.
- **FR-003**: 시스템은 토큰 기록의 회원 연결을 붙이고 떼는 것을 기록의 다른 정보 손실 없이 수행할 수 있어야 한다.
- **FR-004**: 시스템은 회원당 정확히 하나의 선호 기록(도움됨·리마인더)을 보관해야 하며, 기록이 없을 때의 해석은 둘 다 on 이다.
- **FR-005**: 시스템은 광고성 수신 동의를 회원 또는 기기 식별자 기준의 "동의 행위" 로 기록해야 한다. 동의 시 서버 시각과 문구 버전을 남기고, 철회 시 기록을 지우지 않고 철회 시각을 남긴다. 재동의는 새 기록이며 이전 기록은 보존된다. 클라이언트가 보낸 시각은 사용하지 않는다.
- **FR-013**: 시스템은 광고성 알림의 발송 가능 여부를 "철회되지 않은 동의가 있음 AND 그 문구 버전이 요구 버전 이상" 으로 판정할 수 있어야 하고, 회원 기준·게스트 기기 기준 양쪽으로 대상을 뽑을 수 있어야 한다.
- **FR-014**: 시스템은 기기 기록을 삭제하지 않고 무효 토큰을 표시할 수 있어야 하며, 같은 기기가 다시 등록하면 그 기록이 유효하게 되살아나야 한다.
- **FR-006**: 시스템은 알림 기록을 유형·제목·본문·이동 정보·읽음 시각·생성 시각과 함께 보관해야 하며, 수신자는 회원 또는 기기 식별자 중 하나 이상으로 식별한다.
- **FR-007**: 시스템은 회원 기준으로 알림 기록을 최신순으로 페이지 조회할 수 있어야 하고, 미읽음 건수를 셀 수 있어야 한다.
- **FR-008**: 시스템은 알림 기록 1건에 대해 기기 토큰별 발송 추적 기록(토큰·접수 번호·상태·오류 사유)을 여러 건 보관할 수 있어야 한다.
- **FR-009**: 시스템은 회원·음식·주문·리뷰 등 다른 영역의 기록을 참조할 때 식별자 값으로만 참조하며, 참조 무결성은 저장소가 강제한다.
- **FR-010**: 시스템은 모든 신규 기록에 공통 생성·수정 시각과 소프트 삭제 상태를 두어 기존 기록들과 같은 방식으로 조회·삭제되게 해야 한다.
- **FR-011**: 시스템은 이 저장 구조를 기존 저장소 변경 이력에 한 단계로 추가해, 개발·운영 환경에 같은 순서로 적용되고 자동 검증(구조 정합)이 통과되어야 한다.
- **FR-012**: 시스템은 통합 테스트 정리 절차가 새 기록들을 함께 비우도록 해, 다른 테스트에 남은 기록이 영향을 주지 않게 해야 한다.

### Key Entities

- **알림 기기(NotificationDevice)**: 앱이 설치된 기기 하나를 나타낸다. 기기 설치 식별자(유일), 푸시 토큰 문자열, 플랫폼, 기기 언어, 선택적 회원 연결, 무효 토큰 표시. 회원 1 : 기기 N. 삭제되지 않는다.
- **회원 선호(NotificationSetting)**: 회원 한 명의 정보성 알림 선호. 도움됨·리뷰 리마인더 on/off. 회원 1 : 설정 1.
- **광고성 수신 동의(NotificationConsent)**: 동의 행위 한 번. 주체(회원 또는 기기 식별자), 문구 버전, 동의 시각, 철회 시각. 철회되지 않은 것이 현재 유효한 동의. 주체 1 : 동의 N(이력).
- **알림(Notification)**: 서버가 만든 알림 한 건. 유형(도움됨·넛지·리뷰 리마인더·공지), 제목, 본문, 이동 정보(음식 id·알림 id 등), 읽음 시각, 수신자(회원 또는 기기 식별자). 알림함의 단위.
- **발송 추적(NotificationDispatch)**: 알림 한 건이 기기 토큰 하나로 나간 기록. 접수 번호, 상태(대기·발송·배달·실패), 오류 사유. 알림 1 : 발송 추적 N. 영수증 정리의 단위.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 기기에서 토큰 저장을 100회 반복해도 토큰 기록은 1건만 존재한다.
- **SC-002**: 게스트 → 로그인 → 로그아웃 → 재로그인 순서를 거쳐도 기기의 토큰 기록은 1건이고, 각 단계의 회원 연결 상태가 정확히 반영된다.
- **SC-003**: 설정 기록이 없는 회원의 설정 조회 결과가 기본값과 100% 일치한다.
- **SC-004**: 광고성 동의·철회를 100회 반복해도 모든 동의·철회 시각이 기록으로 남고(소실 0건), 유효한 동의는 마지막 행위와 항상 일치한다.
- **SC-005**: 회원의 알림 1,000건을 최신순으로 20건씩 페이지 조회할 때 순서가 어긋나거나 누락·중복되는 건이 0건이다.
- **SC-006**: 알림 1건에 발송 추적 N건을 남긴 뒤 알림 기준으로 조회하면 N건이 정확히 조회된다.
- **SC-007**: 저장 구조 변경이 개발 환경 통합 테스트(구조 정합 검증 포함)를 첫 시도에 통과한다.

## Assumptions

- 기기 설치 식별자는 앱이 모든 요청에 보내는 값(X-Installation-Id)이며, 재설치 후에도 유지되는 UUID 다. 유일성은 이 값 하나로 판단한다.
- 푸시 토큰 문자열은 Expo 형식 하나로 통일되며, 플랫폼 구분은 통계·디버깅용이다.
- 알림 유형은 도움됨(HELPFUL)·넛지(NUDGE)·리뷰 리마인더(REVIEW_REMINDER)·공지(NOTICE) 4종으로 시작하고, 유형 추가는 저장 구조 변경 없이 가능해야 한다(문자열 코드 저장).
- 야간(21~08시) 광고성 전송 별도 동의는 1차 범위 밖이다. 발송 배치가 08~21 KST 밖에서는 광고성 알림을 보내지 않는 것으로 대신한다.
- 알림 제목·본문은 발송 시점의 기기 언어로 렌더된 문자열을 저장한다. 조회 시점 언어로 다시 렌더하는 방식은 후속 태스크(알림함 API)에서 결정한다.
- 게스트 알림함 제공 여부와 게스트 주문 리마인더 발송 여부는 미결이다. 저장 구조는 회원·기기 식별자 둘 다 수신자로 허용해 두 결정 어느 쪽도 막지 않는다.
- 발송 추적 상태는 대기·발송(접수 번호 있음)·배달·실패 4단계로 시작한다.
- 알림·발송 추적 기록의 보존 기간은 정하지 않는다(정리 배치 KB-473 에서 결정).
- 회원 소프트 삭제 시 기기 연결 해제·유효 동의 철회는 탈퇴 처리(KB-465)가 수행한다. 이 기능은 저장 구조만 제공한다.
- 동의 문구 버전은 정수이며 구 문구(점심 스캔 알림 한정)는 1 이다.
