# Feature Specification: 이미지 업로드용 presigned URL 발급 API

**Feature Branch**: `kb-145-presigned-url`

**Created**: 2026-07-15

**Status**: Draft

**Input**: User description: "kb-145 presigned url 발급 api 작업을 시작하자" (Jira KB-145 — [BE] 이미지 업로드용 S3 presigned URL 발급 API)

## 개요

클라이언트가 이미지를 **서버를 거치지 않고 오브젝트 스토리지에 직접 업로드**하고, 백엔드에는 업로드된 이미지의 URL만 전달하는 구조를 만든다. 이를 위해 백엔드가 **만료 시간이 있는 서명(presigned) 업로드 URL**을 발급하는 범용 API를 제공한다. 특정 기능 전용이 아니라 **용도(purpose)로 구분되는 공용 업로드 창구**이며, 첫 소비자는 메뉴판 스캔(사진 → vision LLM → 메뉴명·가격 추출)이고 이후 리뷰 사진 등 다른 기능이 같은 API를 재사용한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 인증된 사용자가 업로드용 서명 URL을 받아 이미지를 직접 업로드한다 (Priority: P1)

인증된 사용자가 "이 이미지를 어떤 용도로 어떤 형식으로 올리겠다"는 정보(용도·Content-Type)를 담아 발급을 요청하면, 서버가 해당 이미지를 **직접 스토리지에 PUT 업로드할 수 있는 서명 URL**과 업로드 후 참조할 **객체 키(경로)**를 돌려준다. 사용자는 서버를 거치지 않고 그 URL로 이미지를 올린다.

**Why this priority**: 이 발급 자체가 기능의 핵심이자 최소 가치 단위다. 이것만 있으면 클라이언트가 이미지를 스토리지에 올리고 그 위치를 백엔드에 알릴 수 있어, 후속 기능(메뉴판 스캔 등)이 이미지를 확보한다.

**Independent Test**: 인증 토큰으로 발급 요청 → 응답의 서명 URL로 실제 이미지 PUT 업로드가 성공하는지로 단독 검증 가능(발급→업로드 왕복).

**Acceptance Scenarios**:

1. **Given** 유효한 인증 토큰과 허용된 용도·Content-Type, **When** 발급을 요청하면, **Then** 업로드용 서명 URL·객체 키·만료 시각을 담은 성공 응답(`BaseResponse.ok`)을 받는다.
2. **Given** 발급받은 업로드용 서명 URL, **When** 만료 전에 지정한 Content-Type으로 이미지를 PUT 업로드하면, **Then** 스토리지에 객체가 저장된다.
3. **Given** 발급받은 업로드용 서명 URL, **When** 크기 상한을 초과하는 파일을 업로드하면, **Then** 업로드가 거부된다(정책 위반).

---

### User Story 2 - 업로드된 이미지를 안정 공개 URL로 저장·표시·소비한다 (Priority: P1)

발급 응답에는 업로드용 서명 URL과 함께, 업로드 후 이미지를 참조·표시할 **만료 없는 안정 공개 URL(CDN 경로)** 이 담긴다. 클라이언트는 이 URL을 백엔드에 전달하고 백엔드는 DB에 저장하며, 앱은 응답으로 받은 URL을 그대로 표시한다. 메뉴판 스캔의 vision LLM도 **이 공개 URL을 직접 fetch** 한다. 읽기가 공개이므로 조회용 서명·재발급이 필요 없다(만료가 없어 재서명 불필요).

**Why this priority**: 첫 소비자(메뉴판 스캔)가 실제로 동작하려면 업로드에 더해 "그 이미지를 읽는" 경로가 반드시 필요하다. P1 두 스토리가 함께 있어야 첫 소비자가 end-to-end로 성립한다.

**Independent Test**: 업로드 완료된 객체에 대해 발급 응답이 준 안정 URL로 이미지를 GET 했을 때 이미지 바이트가 반환되는지로 검증(만료·재서명 없이 반복 조회 성공).

**Acceptance Scenarios**:

1. **Given** 업로드가 완료된 이미지 객체, **When** 발급 응답에 담긴 안정 공개 URL로 GET 하면, **Then** 이미지 바이트가 반환된다.
2. **Given** 반환된 안정 공개 URL, **When** vision LLM이 그 URL을 fetch 하면, **Then** 재서명·만료 갱신 없이 이미지를 확보한다.
3. **Given** 스토리지, **When** 서명 없이 직접 쓰기(PUT)를 시도하면, **Then** 거부된다(버킷에 공개 쓰기 없음).

---

### Edge Cases

- 인증 토큰이 없거나 만료된 경우 → 발급이 거부된다(`401`, 규약상 `AUTH-*` 코드).
- 허용되지 않은 Content-Type(예: 이미지가 아닌 형식)으로 발급을 요청한 경우 → `400`으로 거부된다.
- 알 수 없는/미지원 용도(purpose) 값으로 요청한 경우 → `400`으로 거부된다.
- 같은 사용자가 짧은 시간에 다수 발급을 요청해도 객체 키가 서로 충돌하지 않아야 한다(회원·시각·랜덤 요소 조합).
- 업로드 URL 만료 후 업로드를 시도한 경우 → 스토리지가 거부한다(서버 추가 처리 없음).
- 서명 없이 스토리지에 직접 쓰기(PUT)를 시도한 경우 → 거부된다(버킷에 공개 쓰기 없음).
- 발급은 성공했으나 클라이언트가 실제 업로드를 하지 않은 경우 → 서버는 상태를 추적하지 않으며(스토리지에 객체 부재), 존재하지 않는 객체를 참조할 때의 처리는 소비 기능의 책임이다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 **인증된 사용자에게만** 이미지 업로드용 서명 URL을 발급해야 한다(JWT 인증 필수).
- **FR-002**: 발급 API는 **`/api/v1` 경로 규약**과 **`BaseResponse` 응답 봉투**를 준수해야 한다.
- **FR-003**: 발급 요청은 **용도(purpose)** 와 업로드할 이미지의 **Content-Type**을 입력으로 받아야 하며, 용도로 서로 다른 소비 기능(메뉴판 스캔·향후 리뷰 등)을 구분해야 한다.
- **FR-004**: 시스템은 요청한 Content-Type이 **허용된 이미지 타입 목록**(예: `image/jpeg`, `image/png`)에 속하는지 검증하고, 위반 시 `400`으로 거부해야 한다.
- **FR-005**: 시스템은 요청한 용도(purpose)가 **지원되는 값**인지 검증하고, 미지원 값은 `400`으로 거부해야 한다.
- **FR-006**: 발급되는 업로드 서명 URL에는 **크기 상한(content-length-range)** 정책이 포함되어, 상한을 초과하는 업로드는 스토리지 단에서 거부되어야 한다.
- **FR-007**: 시스템은 **용도별 prefix + 회원 식별 + 시각/랜덤 요소**를 조합한 객체 키를 생성해, 동시·연속 발급에도 키가 충돌하지 않도록 해야 한다.
- **FR-008**: 업로드용 서명 URL은 **만료 시간(TTL)** 을 가져야 하며, 응답에 만료 시각이 포함되어야 한다.
- **FR-009**: 발급 응답은 업로드 후 이미지를 참조·표시할 **만료 없는 안정 접근 URL(공개 읽기/CDN 경로)** 을 포함해야 한다. 클라이언트는 이 URL을 백엔드에 전달·DB 저장·표시에 사용하며, vision LLM도 이 URL로 이미지를 직접 fetch 한다(별도 조회 서명·재발급 불필요).
- **FR-010**: 업로드(쓰기)는 **서명 PUT URL로만** 허용되어야 한다(버킷에 공개 쓰기 없음). 읽기는 **추측 불가능한 객체 키 기반 공개 읽기/CDN 경로**로 제공하며, 서명 없는 쓰기는 거부되어야 한다.
- **FR-011**: 발급 응답은 클라이언트가 업로드 후 백엔드에 전달·저장할 **이미지 참조 값(안정 공개 URL 및/또는 객체 키)** 을 포함해, 소비 기능이 그 값으로 이미지를 식별·표시할 수 있어야 한다.
- **FR-012**: 발급 실패(인증·검증)는 규약상 **안정 에러 코드(`code`)** 로 구분되어야 한다(클라이언트가 `code`로 분기).
- **FR-013**: 이미지 읽기는 **FR-009의 안정 공개 URL 하나로 충족**되며, 별도의 조회(GET) 서명·재발급 엔드포인트를 두지 않는다.
- **FR-014**: 실 스토리지 접근은 **dev/prod 프로파일에서만** 이뤄지고, local·테스트는 발급 로직을 **seam 인터페이스의 페이크 구현**으로 검증한다(실 S3 없이 동작·테스트, 헌법 I Test-First).

### Key Entities *(include if feature involves data)*

- **발급 요청(Presign Request)**: 용도(purpose), 이미지 Content-Type. (선택적으로 클라이언트가 알리는 예상 크기.)
- **발급 결과(Presign Result)**: 업로드용 서명 URL, 만료 시각, 그리고 업로드 후 저장·표시에 쓸 **안정 공개 URL(및/또는 객체 키)**.
- **용도(Purpose)**: 업로드 창구를 구분하는 값. 객체 키 prefix와 향후 용도별 규격(크기·품질)을 결정. 첫 값은 메뉴판 스캔.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 인증된 사용자가 발급을 요청하면, 서버 왕복 없이 **자신의 이미지를 스토리지에 직접 업로드**하고 그 위치를 백엔드에 알릴 수 있다(발급→업로드→참조 전달 왕복 성공).
- **SC-002**: 메뉴판 스캔이 발급받은 안정 공개 URL로 이미지를 확보해 **end-to-end로 스캔을 완료**할 수 있다(첫 소비자가 실제 동작).
- **SC-003**: 크기 상한을 초과하는 업로드는 **거부**되고, 허용되지 않은 Content-Type·미지원 용도 요청은 발급 단계에서 거부된다.
- **SC-004**: 서명 없는 **쓰기(업로드)** 는 **항상 거부**된다(버킷에 공개 쓰기 없음). 읽기는 반환된 안정 URL로 만료·재서명 없이 반복 가능하다.
- **SC-005**: 동일 사용자가 연속·동시에 다수 발급을 받아도 객체 키 충돌이 발생하지 않는다.

## Assumptions

- **인증**: 기존 JWT 인증(`@AuthMemberId`)을 재사용하며, 비인증 발급은 지원하지 않는다(DoD 명시).
- **읽기 접근 모델(사용자 확정)**: 이미지(메뉴 사진·프로필·리뷰)는 민감정보가 아니고 앱·LLM이 반복/직접 표시하므로, 읽기는 **만료 없는 공개 읽기/CDN URL**로 제공한다(추측 불가능한 객체 키로 보호). 업로드된 안정 URL을 **DB에 저장·응답으로 전달**하는 소비 패턴(KB-147 `profileImageUrl` CloudFront 방향과 일치)에 맞춘다. 쓰기만 서명 PUT으로 잠그며, 별도 조회 서명/재발급 엔드포인트는 두지 않는다. (Background의 "버킷을 공개하지 않고도"는 쓰기 보호 취지로 해석 — 읽기 공개는 사용자 확정.)
- **테스트/환경(사용자 확정)**: 발급을 seam 인터페이스로 추상화해 local·테스트는 페이크로 검증하고, 실 S3는 dev/prod 프로파일에서만 접근한다(LocalStack·공용 dev 버킷 불필요).
- **리사이즈/이미지 규격은 클라이언트 책임**: 서버는 presign 정책(크기 상한·Content-Type)으로만 방어하며, 실제 리사이즈(메뉴판 스캔: 긴 변 1024px, JPEG 품질 등)는 클라이언트가 수행한다.
- **용도(purpose) 범위**: 첫 릴리스는 **메뉴판 스캔** 용도를 지원하고, 리뷰 등은 같은 API에 용도 값·prefix를 추가하는 방식으로 확장한다(신규 엔드포인트 불필요).
- **스토리지**: AWS S3를 대상으로 한다(Jira 제목 명시). 실제 버킷·IAM 구성은 plan 단계에서 구체화한다.
- **범위 밖**: 업로드 완료 여부의 서버 추적/후처리(썸네일·재인코딩), 이미지 삭제/수명주기 정책, 업로드된 객체와 도메인 엔티티(회원 프로필·리뷰)의 영속 연결은 각 소비 기능 태스크의 책임이며 본 태스크 범위 밖이다.
- **의존**: KB-147(프로필 이미지 URL)은 이미 URL 문자열을 받는 계약이 있으나, 그 URL의 발급/업로드는 본 API가 담당한다(소비자 연결은 별도).
