# Feature Specification: 홈 조회 커넥션 획득 3회→1회

**Feature Branch**: `fix/kb716-home-single-tx`

**Created**: 2026-10-04

**Status**: Draft

**Jira**: [KB-716](https://simhani1.atlassian.net/browse/KB-716)

**Input**: User description: "KB-716 홈 조회의 북마크·평점 조회를 HomeService 트랜잭션 안으로 옮겨 커넥션 획득을 1회로 줄인다 (Jira KB-716 본문 참조: 현재 컨트롤러 getHome 뒤에 BookmarkService.getBookmarkedFoodIds·ReviewService.getFoodRatings 를 따로 불러 트랜잭션이 3개 열리고 커넥션 획득 3회. HomeResult 가 bookmarkedFoodIds·ratings 를 담고 컨트롤러는 HomeResponse.from 매핑만. 응답 계약 불변, 기존 홈 통합 테스트 무수정 통과)"

## 배경

홈 조회 한 건은 지금 DB 커넥션을 세 번 획득한다. 본문 조회(기피 성분·인기 음식·리뷰 많은 음식·최근 스캔)가 읽기 트랜잭션 하나를 쓰고, 그 뒤 컨트롤러가 북마크 여부 조회와 평점 조회를 따로 불러 각자 새 트랜잭션을 연다(세션 지표: 커넥션 획득 3회, SQL 7개).

dev 에 200 rps 부하를 걸었을 때 요청당 커넥션 획득 대기가 평균 3.5초, 쿼리 실행은 100ms 였다. 풀(태스크당 10)이 꽉 찬 상태에서 요청 하나가 대기 큐에 세 번 줄을 서므로, 큐가 깊을수록 대기가 세 배로 드러난다. 북마크·평점 조회를 본문 조회와 같은 트랜잭션에 넣으면 줄을 한 번만 선다. 두 조회는 1ms 미만이라 커넥션 점유 시간은 거의 늘지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 홈 응답은 그대로이고 커넥션 획득만 1회로 줄어든다 (Priority: P1)

앱 사용자는 이전과 같은 홈 응답(같은 섹션·같은 카드 내용·같은 북마크 여부·같은 평점)을 받는다. 서버는 홈 조회 한 건에 DB 커넥션을 한 번만 획득하므로, 풀이 포화된 부하 상황에서 응답 대기가 줄어든다.

**Why this priority**: 이 작업의 유일한 목적이자 수용 기준이다.

**Independent Test**: 기존 홈 통합 테스트(회원·비회원)가 무수정으로 통과하고, 세션 지표 로그에서 홈 요청 한 건의 커넥션 획득 수가 1이다.

**Acceptance Scenarios**:

1. **Given** 기존 홈 통합 테스트, **When** 변경 후 실행하면, **Then** 한 줄도 고치지 않고 전부 통과한다.
2. **Given** 북마크와 리뷰가 있는 회원, **When** 홈을 조회하면, **Then** 각 음식 카드의 북마크 여부와 평균 평점·리뷰 수가 변경 전과 같다.
3. **Given** 비회원, **When** 홈을 조회하면, **Then** 모든 카드의 북마크 여부는 false 이고 평점은 변경 전과 같다.
4. **Given** 세션 지표 로그가 켜진 dev 환경, **When** 회원 토큰으로 홈을 한 번 호출하면, **Then** 그 요청의 커넥션 획득 수가 1이고 SQL 문 수는 변경 전과 같다(7개).

---

### Edge Cases

- 세 음식 섹션이 모두 비면 북마크·평점 조회는 DB 에 가지 않는다(지금과 같다).
- 비회원은 북마크 조회가 DB 에 가지 않는다(지금과 같다).
- 같은 음식이 여러 섹션에 겹쳐도 카드마다 같은 북마크 여부·평점이 붙는다.
- 리뷰가 없는 음식의 평점 표시는 변경 전과 같다.
- 탈퇴·정지 회원의 홈 조회 오류 동작은 그대로다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 홈 조회 한 건은 DB 커넥션을 1회만 획득해야 한다(회원·비회원 공통).
- **FR-002**: 홈 본문 조회와 카드 장식 조회(북마크 여부·평점)는 하나의 읽기 트랜잭션 안에서 수행되어야 한다.
- **FR-003**: 홈 조회 결과는 본문 네 섹션과 함께 북마크된 음식 id 집합과 음식별 평점을 담아야 한다. 컨트롤러는 그 결과를 응답으로 매핑만 한다.
- **FR-004**: 홈 응답의 구조·필드·값·정렬은 변경 전과 같아야 한다. 기존 홈 통합 테스트는 무수정 통과.
- **FR-005**: 홈 조회의 SQL 문 수는 늘지 않아야 한다.
- **FR-006**: 북마크·평점 조회 기능 자체의 동작과 다른 화면(음식 목록·상세, 북마크 목록)의 호출 방식은 바꾸지 않는다.

### Key Entities

- **홈 조회 결과**: 기피 성분·인기 음식·리뷰 많은 음식·최근 스캔 네 섹션에 더해, 그 섹션에 나온 음식 중 요청자가 북마크한 음식 id 집합과 음식별 평점(평균·리뷰 수)을 담는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 홈 요청 한 건의 DB 커넥션 획득 수가 3에서 1로 줄어든다(dev 세션 지표로 확인).
- **SC-002**: 기존 홈 통합 테스트가 수정 0줄로 100% 통과한다.
- **SC-003**: 홈 응답 JSON 이 같은 데이터에 대해 변경 전후 동일하다(무작위인 인기 음식 구성은 제외).
- **SC-004**: 홈 요청 한 건의 SQL 문 수가 변경 전(회원 7개)보다 늘지 않는다.

## Assumptions

- 범위는 홈 조회뿐이다. 같은 패턴이 있는 음식 목록·상세와 북마크 목록은 홈에서 효과를 확인한 뒤 별도 태스크로 다룬다.
- 북마크·평점 조회는 기존 서비스 메서드를 그대로 재사용한다. 바깥 읽기 트랜잭션에 참여하는 것만으로 커넥션 획득이 합쳐진다.
- 커넥션 획득 수는 자동 테스트로 단언하지 않는다. dev 배포 후 세션 지표 로그(KB-715 에서 켠 쿼리 통계)로 확인한다.
- 풀 크기·타임아웃 등 커넥션 풀 설정은 건드리지 않는다.
- 두 장식 조회는 1ms 미만이라 트랜잭션에 합쳐도 커넥션 점유 시간 증가는 무시할 수준이다.
