# Feature Specification: Firebase 토큰 검증 소셜 로그인 — 자체 JWT 쿠키 발급·재발급·로그아웃

**Feature Branch**: `kb-118-firebase-jwt-auth`

**Created**: 2026-07-10

**Status**: Draft

**Input**: User description: "kb-118의 작업 중 JWT 토큰을 사용하기 위한 작업. 파이어베이스의 토큰을 파싱해서 사용자 이메일과 uid를 꺼낸 후 우리 데이터베이스에 회원 정보를 저장. 우리 서비스 자체 JWT 토큰(access, refresh)를 만들어 쿠키에 포함시켜 클라이언트의 OAuth 인증 요청에 대한 응답으로 내려줌. AccessToken 재발급 로직도 고려." (Jira KB-118 — [BE] Firebase ID 토큰 검증 기반 소셜 로그인·로그아웃 API)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 소셜 계정으로 로그인/가입 (Priority: P1)

사용자가 앱에서 구글·애플 로그인을 마치면 외부 인증 제공자(Firebase)가 발급한 신원 토큰을 서버에 제출한다. 서버는 토큰의 진위(서명·발급자·수신자·만료)를 검증한 뒤 신원 정보(소셜 플랫폼·플랫폼 원본 사용자 id·이메일)를 꺼내, 기존 회원이면 로그인시키고 처음이면 회원으로 가입시킨다. 응답으로 서비스 자체 인증 토큰(access·refresh)을 쿠키에 담아 내려주고, 신규 회원 여부를 함께 알려 클라이언트가 온보딩 화면으로 분기할 수 있게 한다.

**Why this priority**: 로그인 진입점이 없으면 회원 도메인 전체(가입·프로필·탈퇴)가 실사용 불가능하다 — 서비스의 문.

**Independent Test**: 페이크 토큰 검증기로 로그인 유스케이스(신규 가입/기존 재로그인)를 단위 테스트하고, 로그인 API 를 web 테스트로 검증할 수 있다. 이 스토리만으로 "로그인해서 인증된 상태가 된다"는 가치가 완결된다.

**Acceptance Scenarios**:

1. **Given** 유효한 신원 토큰을 가진 미가입 사용자가, **When** 로그인을 요청하면, **Then** 회원으로 가입되고 응답 쿠키에 access·refresh 토큰이 담기며 신규 회원임이 표시된다.
2. **Given** 이미 가입된 회원이, **When** 같은 소셜 계정으로 로그인을 요청하면, **Then** 새 회원이 생기지 않고 기존 회원으로 로그인되며 신규가 아님이 표시된다.
3. **Given** 서명이 위조되었거나 만료된 신원 토큰으로, **When** 로그인을 요청하면, **Then** 인증 실패(401)로 거절되고 회원이 생성되지 않는다.
4. **Given** 정지(SUSPENDED)된 회원이, **When** 로그인을 요청하면, **Then** 로그인이 거부되고 신규 가입으로 오인해 새 회원이 만들어지지 않는다.
5. **Given** 애플 이메일 가리기를 쓰는 사용자(릴레이 주소)가, **When** 로그인을 요청하면, **Then** 릴레이 주소 그대로 저장되고 로그인은 정상 동작한다(신원 판별은 이메일이 아니라 플랫폼 원본 id).

---

### User Story 2 - 토큰 재발급 (Priority: P2)

access 토큰은 수명이 짧아 만료되면, 클라이언트는 보유한 refresh 토큰으로 재발급을 요청한다. 재발급 성공 시 **access 와 refresh 를 모두 새로 발급**해 refresh 의 유효기간도 연장된다(rotation — 활동 중인 사용자는 세션이 계속 늘어난다). 이전 refresh 토큰은 즉시 폐기된다. refresh 마저 만료되었다면 서버는 **강제 로그아웃**(세션 폐기 + 쿠키 제거) 처리하고, 사용자는 재로그인해야 한다.

**Why this priority**: 짧은 수명의 access 토큰 전략이 성립하려면 재발급이 반드시 있어야 한다 — 없으면 사용자가 수십 분마다 재로그인해야 한다.

**Independent Test**: 로그인으로 받은 refresh 토큰으로 재발급 API 를 호출해 두 토큰이 모두 갱신되는지, 이전 refresh 가 폐기되는지, 만료·조작·폐기된 refresh 가 각각 정의된 예외 응답으로 거절되는지 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 유효한 refresh 토큰을 가진 로그인 회원이, **When** 재발급을 요청하면, **Then** 새 access·refresh 토큰이 모두 쿠키로 내려오고 refresh 유효기간이 연장된다.
2. **Given** 재발급을 마친 회원이, **When** 회전 전의 이전 refresh 토큰으로 다시 재발급을 요청하면, **Then** 이미 폐기된 토큰이므로 거절된다(401).
3. **Given** 만료된 refresh 토큰으로, **When** 재발급을 요청하면, **Then** 만료 전용 예외 응답(401)과 함께 강제 로그아웃(쿠키 제거)되어 재로그인이 필요하다.
4. **Given** 서명이 조작되었거나 서버에 저장된 적 없는 refresh 토큰으로, **When** 재발급을 요청하면, **Then** 유효하지 않은 토큰 예외 응답(401)으로 거절된다.

---

### User Story 3 - 로그아웃 (Priority: P3)

사용자가 로그아웃하면 서버는 저장해 둔 refresh 토큰을 폐기한다. 이후 그 refresh 토큰으로는 access 토큰을 재발급받을 수 없다. (이미 발급된 access 토큰은 짧은 수명이 다하면 자연 만료된다.)

**Why this priority**: 세션 종료 수단 — 보안 완결성에 필요하지만 로그인·재발급이 먼저 있어야 의미가 있다.

**Independent Test**: 로그인 → 로그아웃 → 같은 refresh 토큰으로 재발급 시도가 거절되는지 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 로그인된 회원이, **When** 로그아웃을 요청하면, **Then** 서버에 저장된 refresh 토큰이 폐기된다.
2. **Given** 로그아웃한 회원이, **When** 폐기된 refresh 토큰으로 재발급을 요청하면, **Then** 거절된다.

---

### Edge Cases

- 신원 토큰의 페이로드만 디코딩해 위조 신원으로 로그인 시도하면? → 서명·발급자(iss)·수신자(aud)·만료(exp)를 모두 검증하므로 거절된다(401). 디코딩 가능 ≠ 신뢰 가능.
- 지원하지 않는 소셜 플랫폼(구글·애플 외)의 토큰이 오면? → 명시적 오류로 거절한다(조용한 무시 금지).
- 탈퇴한 회원이 같은 소셜 계정으로 다시 로그인하면? → 신규 회원으로 재가입된다(KB-117 탈퇴 정책 — 신원 삭제 표식으로 재가입 개방).
- 같은 회원이 다른 기기에서 또 로그인하면? → 기기별 refresh 토큰을 각각 유지한다(한 기기의 로그아웃이 다른 기기를 끊지 않음).
- 이메일이 없는(null) 신원 토큰이면? → 이메일 없이 그대로 가입·로그인된다(이메일은 신원 키가 아님).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 서버는 클라이언트가 제출한 외부 신원 토큰의 서명·발급자·수신자·만료를 모두 검증해야 하며, 검증 없이 디코딩만으로 신원을 신뢰해서는 안 된다. 검증 실패(만료·서명 불일치·수신자 불일치)는 인증 실패(401)로 응답한다.
- **FR-002**: 검증된 토큰에서 소셜 플랫폼 구분·플랫폼 원본 사용자 id·이메일을 추출한다. 저장하는 식별자는 인증 중개자(Firebase)가 만든 uid 가 아니라 **소셜 플랫폼이 발급한 원본 id** 여야 한다(중개자를 걷어내도 신원 매핑 유지).
- **FR-003**: 이메일은 신원 판별에 사용하지 않는다 — 신원 키는 (플랫폼, 원본 id) 조합뿐이다. 이메일은 null 이거나 릴레이 주소여도 그대로 저장한다.
- **FR-004**: 신원으로 기존 회원을 찾으면 로그인, 없으면 가입 처리한다. 응답에 신규 회원 여부를 담아 클라이언트가 온보딩으로 분기할 수 있게 한다.
- **FR-005**: 로그인 성공 시 서비스 자체 인증 토큰 두 종(access·refresh)을 발급해 **응답 쿠키에 담아** 내려준다. 자체 토큰의 사용자 클레임은 **회원 저장 후 반환된 내부 식별자(PK) 단 하나**이며, 이메일·닉네임 등 **개인정보는 어떤 것도 포함하지 않는다**(KB-102 결정 강화).
- **FR-006**: 외부 신원 토큰은 로그인 시점에 한 번만 검증한다. 이후 모든 요청 인증은 자체 access 토큰으로 처리한다.
- **FR-007**: access 토큰은 짧은 수명을 갖고, 만료 시 refresh 토큰으로 재발급받을 수 있어야 한다. 재발급 성공 시 **access·refresh 를 모두 새로 발급하고 이전 refresh 는 즉시 폐기**한다(rotation — refresh 유효기간 연장, 활동 사용자는 재로그인 없이 지속).
- **FR-007a**: 토큰 이상 상황은 구분된 예외 응답으로 정의한다 — ① 조작(서명 불일치·형식 불량)·위조/폐기(서버 미저장) refresh = "유효하지 않은 토큰"(401) ② **만료된 refresh = 만료 전용 예외(401) + 강제 로그아웃**(서버 세션 폐기·쿠키 제거) — 클라이언트는 재로그인으로만 복귀한다. 모든 예외 응답은 공통 봉투(BaseResponse fail)를 따른다.
- **FR-008**: refresh 토큰은 서버 저장소에 보관하며, 회원별 다중 기기 로그인을 허용한다(기기별 refresh 토큰 각각 유지). 저장소는 토큰 수명과 저장 수명이 자동으로 일치해야 한다(만료된 토큰이 저장소에 잔존하지 않음).
- **FR-009**: 로그아웃 시 서버에 저장된 해당 refresh 토큰을 폐기한다. 외부 인증 제공자에는 아무 통지도 필요 없다(제공자의 로그아웃은 기기 로컬 문제).
- **FR-010**: 정지(SUSPENDED) 회원의 로그인은 거부하며, 이 과정에서 신규 가입으로 오인해 새 회원을 생성해서는 안 된다.
- **FR-011**: 지원하지 않는 소셜 플랫폼의 토큰은 명시적 오류로 거절한다.
- **FR-012**: 외부 인증 제공자 접속에 필요한 비밀 자격(서비스 계정 키)은 저장소에 커밋하지 않으며, 실행 환경(local/dev/staging/prod)별 주입 경로를 문서화한다.

### Key Entities

- **소셜 신원(Social Identity)**: 외부 신원 토큰에서 추출한 (소셜 플랫폼, 플랫폼 원본 사용자 id, 이메일). 회원 판별의 유일한 키는 (플랫폼, 원본 id).
- **자체 인증 토큰(Access Token)**: 서비스가 발급하는 짧은 수명의 요청 인증 수단. 사용자 클레임은 회원 내부 식별자(PK) 하나뿐 — 개인정보(이메일·닉네임 등) 미포함. 상태 비저장 — 만료 전 서버가 무효화할 수 없으므로 수명을 짧게 둔다.
- **갱신 토큰(Refresh Token)**: access 토큰 재발급 전용. 서버 저장소에 보관되어 폐기(로그아웃) 가능. 회원당 기기별로 여러 개 존재할 수 있다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 유효한 소셜 계정 사용자는 첫 로그인 요청 한 번으로 100% 가입·인증 상태가 된다(별도 가입 절차 0단계).
- **SC-002**: 서명·발급자·수신자·만료 검증을 통과하지 못한 신원 토큰의 로그인 성공률은 0% 다(위조 로그인 불가).
- **SC-003**: 같은 소셜 계정의 재로그인에서 중복 회원 생성은 0건이다.
- **SC-004**: access 토큰 만료 후에도 유효한 refresh 토큰 보유자는 재로그인 없이 100% 세션을 이어가고, 재발급 시점마다 refresh 유효기간이 연장된다.
- **SC-005**: 로그아웃 후 또는 rotation 으로 폐기된 이전 refresh 토큰의 재발급 성공률은 0% 다.
- **SC-005a**: refresh 만료 시 강제 로그아웃되어, 만료된 refresh 로 세션을 이어갈 수 있는 경로는 0개다(재로그인 필수).
- **SC-006**: 정지 회원의 로그인 성공률은 0% 이고, 그 과정에서 생성되는 회원 수는 0 이다.
- **SC-007**: 저장소(코드·설정 커밋)에서 외부 인증 비밀 자격이 발견되는 건수는 0 이다.

## Assumptions

- 클라이언트(앱)는 이미 Firebase SDK 로 구글·애플 로그인을 완료하고 신원 토큰을 얻는다 — 소셜 로그인 UI·SDK 연동은 클라이언트 소유, 서버는 토큰 검증부터 담당한다.
- 자체 토큰 전달은 응답 쿠키를 기본으로 한다(사용자 결정). 쿠키 보안 속성(HttpOnly 등)·수명 구체값은 plan 단계에서 정한다 — access 는 짧게(분 단위), refresh 는 길게(주 단위)라는 원칙만 고정.
- 회원별 다중 기기 로그인을 허용한다 — 모바일 서비스에서 복수 기기는 일반적이며, 로그아웃은 해당 기기의 refresh 토큰만 폐기한다.
- refresh 토큰 저장소는 **Redis** 로 한다(사용자 결정 2026-07-10) — TTL 자동 만료로 토큰 수명 = 저장 수명이 보장되고 만료 청소가 불필요하다. **Redis 인프라 도입(로컬 docker 스택·프로필별 접속 설정·의존성)도 이번 작업 범위에 포함**한다. 이슈 DoD 의 "마이그레이션 작성"(RDB 전제)은 이 결정으로 대체된다. 트레이드오프(기록): Redis 유실 시 전체 재로그인 발생 — 세션 재수립으로 복구 가능한 수준으로 수용.
- 모듈 배치(사용자 결정 2026-07-10, 빠른 구현 우선): **Redis 의존성·어댑터는 기존 `:infra:persistence` 모듈 안에서 관리**한다(신규 모듈 없음). **Firebase 토큰 분석 기술(firebase-admin)은 `:application` 모듈에 직접 의존성으로 추가**한다 — 이슈 DoD 의 "infra:firebase 모듈 신설 + port 조립"을 대체하는 의식적 경계 완화이며, 헌법 III(application 은 port 로만 외부 기술 사용) 위반임을 인지하고 수용한다(plan 의 Complexity Tracking 에 정당화 기록). 추후 재사용·교체 필요가 생기면 infra 모듈로 추출한다.
- 자체 토큰의 사용자 클레임은 회원 PK 하나로 한정한다(KB-102 기존 결정 + 사용자 확정 2026-07-10). 이메일 등 개인정보는 DB 회원 레코드에만 저장되고 토큰에는 절대 실리지 않는다.
- 회원 스키마(단일 신원·member_status)는 KB-117 에서 완료된 상태를 전제한다.
- access 토큰의 즉시 무효화(강제 로그아웃·정지 즉시 차단)는 범위 밖 — 정지 회원도 이미 발급된 access 토큰 수명 동안은 요청이 통과할 수 있으며, 짧은 수명으로 창을 최소화한다.
- 계정 연결(한 회원이 복수 소셜 계정)은 KB-117 에서 제외된 상태 그대로 미지원 — 다른 플랫폼으로 로그인하면 별도 회원이 된다.
