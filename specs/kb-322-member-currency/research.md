# Phase 0 Research: 회원 통화 설정

**Feature**: kb-322-member-currency | **Date**: 2026-08-11

## R1. 통화를 무엇으로 표현하는가 — enum vs 문자열

- **Decision**: 식별자 **enum `CurrencyCode`** 를 만든다. 저장은 코드 문자열(3자), 코드상 취급은 enum.
- **Rationale**: 저장소에 이미 같은 패턴이 셋 있다 — `CountryCode`(197개)·`LanguageCode`(10개)·`IngredientCode`(81개). 헌법 원칙 V 의 "고정 reference taxonomy — 식별자 enum" 조항이 이 형태를 규정한다: 운영자 런타임 편집이 없고 고정·읽기 전용인 기준 목록은 식별자 enum 으로 컴파일 타임 안전을 얻는다. 통화는 정확히 그 성격이다.
- **Alternatives considered**: `String` 저장 + 화이트리스트 검증 — 타입 안전이 없어 후속 환산(KB-323)에서 오타가 런타임까지 간다. 기각. / `java.util.Currency` — JDK 로케일 데이터에 의존해 버전마다 목록이 달라지고, 우리가 지원하는 집합을 코드로 못 박을 수 없다. 기각.

## R2. `CurrencyCode` 를 어느 패키지에 두는가

- **Decision**: **`com.kbap.common.domain` 루트**(`LanguageCode` 옆). `member.model` 안에 두지 않는다.
- **Rationale**: 헌법 원칙 II — *"여러 컨텍스트가 공유하는 vocabulary(`LanguageCode` 등)는 소유 도메인이 아니라 공유 도메인 vocabulary(`com.kbap.common.domain` 루트)에 둔다 — 소유 도메인에 두면 참조하는 쪽에 도메인 간 의존이 생긴다."* 후속 작업(KB-323)에서 **scan 이 통화를 읽는다.** member.model 에 두면 scan→member 도메인 의존이 생기고 `ModuleBoundaryTest` 허용 맵을 건드려야 한다.
- **Alternatives considered**: `member.model.CurrencyCode` — 지금은 member 만 쓰므로 자연스러워 보이지만, KB-323 이 곧 scan 에서 참조한다. 그때 옮기는 비용 + 허용 맵 수정을 미리 피한다. 기각.

## R3. 국가→통화 매핑을 어디에 두는가

- **Decision**: `CountryCode` enum 에 **`currency` 필드를 추가**한다 — `KR("대한민국", CurrencyCode.KRW)` 형태.
- **Rationale**: 197개 전수 채움(FR-004)을 **컴파일러가 강제**한다. 별도 `Map<CountryCode, CurrencyCode>` 를 두면 누락돼도 컴파일이 통과하고 런타임에 드러난다. 파일 diff 크기는 어느 쪽이든 197줄로 같으므로, 강제력이 있는 쪽을 택한다.
- **Alternatives considered**: 별도 매핑 객체/테이블 — 누락 검출을 테스트에 의존해야 한다. 기각. / DB 테이블 — 운영자 편집 대상이 아니고(원칙 V) 조회 한 번이 더 늘어난다. 기각.
- **주의**: 여러 국가가 한 통화를 공유한다(유로존 20개국 EUR, 서아프리카 XOF 등). 국가→통화는 1:1 이라 enum 필드로 표현되지만, 역방향 조회가 필요해지면 별도 함수가 필요하다(현재 요구 없음).

## R4. 기존 회원 백필 — 저장값 vs 읽기 시점 유도

- **Decision**: 온보딩 시점에 **실제로 저장**하고, 기존 회원은 **마이그레이션에서 백필**한다. 읽기 시점 유도(`currency ?: mapping(country)`)를 쓰지 않는다.
- **Rationale**: 읽기 시점 유도를 쓰면 통화가 국가에 계속 종속돼, **FR-007(국가를 바꿔도 통화 불변)이 깨진다** — 저장된 값이 없는 회원의 국가를 바꾸면 유도된 통화가 따라 바뀐다. 저장을 해야 "국가와 통화가 독립"이라는 명세가 성립한다.
- **백필 방법**: `UPDATE member SET currency = CASE country_code WHEN ... END WHERE country_code IS NOT NULL` — 197개 분기. 기계적이고 1회성이다.
- **Alternatives considered**: 앱 기동 시 일회성 잡 — 실행 시점·재실행·다중 인스턴스(운영 api 2대) 문제를 새로 만든다. 기각.

## R5. 백필 SQL ↔ enum 매핑의 드리프트를 막는 법

- **문제**: 매핑이 enum(코드)과 마이그레이션(SQL) 두 곳에 존재한다. 한쪽만 고치면 조용히 어긋난다.
- **Decision**: **시드-동기화 테스트**로 강제한다 — 마이그레이션 SQL 을 리소스로 읽어 `CASE` 분기 집합이 `CountryCode` 전수의 (국가, 통화) 쌍과 일치하는지 검증한다.
- **Rationale**: 저장소에 선례가 있다 — `IngredientCatalogSeedSyncTest` 가 같은 방식으로 시드 SQL 과 enum 을 대조한다.
- **함정(CLAUDE.md 경고 그대로)**: 이런 테스트는 **마이그레이션 파일명을 리소스 경로로 하드코딩**한다. 파일명·위치를 바꾸면 파일을 못 찾아 내용이 빈 문자열로 읽히고, "파일 없음"이 아니라 **데이터 불일치 assertion 실패**로 조용히 깨진다. 테스트 설명에 버전 번호를 박지 않는다.

## R6. 검증을 어디서 하는가

- **Decision**: `MemberProfile.updatedWith` 에 `currency` 파라미터를 더하고 `validatedCurrency` 를 둔다. 신규 `ErrorCode.INVALID_CURRENCY_CODE("MEMBER-010", 400)`.
- **Rationale**: `MemberProfile` 은 이미 *"검증 있는 copy — 전달된 필드만 검증 후 교체, null 은 기존 값 유지"* 규약을 갖고 있고, 주석에 **"검증은 updatedWith 경유가 유일 경로(무검증 저장 차단)"** 라고 못박혀 있다. 통화만 다른 경로로 검증하면 그 불변이 깨진다. 미전송=유지(FR-006)도 이 규약이 그대로 준다.
- **에러 코드 번호**: MEMBER 는 001~006·008·009 사용 중이다. **007 은 폐기된 번호라 재사용하지 않는다**(CLAUDE.md 규약) — 다음 번호는 **010**.

## R7. 온보딩 자동 지정이 일어나는 지점

- **Decision**: `Member.completeOnboarding` 안에서 확정된 국가로부터 통화를 파생해 함께 저장한다. API 요청 DTO 에 통화 필드를 두지 않는다.
- **Rationale**: 헌법 원칙 IV — 도메인 로직(상태 전이·정책)은 도메인이 소유한다. "국가가 정해지면 통화가 따라온다"는 정책이므로 컨트롤러·애플리케이션 서비스가 아니라 엔티티의 온보딩 전이 안에 있어야 한다. 요청 DTO 에 필드가 없으면 FR-003(보내도 무시)이 **구조적으로** 성립한다 — 무시 로직을 따로 쓸 필요가 없다.
- **Alternatives considered**: 컨트롤러에서 매핑해 서비스로 넘김 — 정책이 web 계층으로 샌다. 기각.

## R8. API 계약 변경의 성격

- **Decision**: 버전을 올리지 않는다. 프로필 수정 요청에 **선택 필드 추가**, 프로필 조회 응답에 **필드 추가** 둘 다 하위 호환이다.
- **Rationale**: 팀 정책이 *"비호환 변경만 새 버전을 릴리즈한다. 하위 호환 변경(응답 필드 추가·선택 파라미터 추가·새 엔드포인트)은 버전을 올리지 않는다"* 로 규정한다.
- **온보딩 요청은 변경 없음** — 통화 필드를 추가하지 않으므로 계약이 그대로다.

## R9. 환율 출처를 frankfurter 에서 국내 은행 고시로 바꾼 경위 (2026-08-11)

- **처음 선택**: frankfurter(ECB 기준환율) — 무료·키 불필요.
- **문제**: **30종만 지원**한다. 197개 국가를 환산하려면 통화가 146종 필요한데 116종이 비었다. 특히 **베트남(VND)·대만(TWD)·사우디(SAR)·아랍에미리트(AED)** 가 없어 한국 방문객 비중이 큰 나라들이 통째로 빠졌다.
- **정밀도 문제도 있었다**: `base=KRW` 로 부르면 USD 가 `0.00071` — **유효숫자 2자리**다. `amount=1000000` 트릭으로 우회해야 했다.
- **Decision**: **국내 은행 고시 매매기준율** 스냅샷으로 교체한다. 취급 통화 45종 + 원화 = **46종 전부가 환율을 갖는다.**
- **Rationale**: 출처가 하나고 시점이 하나다. 교차 출처 혼합(일부는 ECB, 일부는 은행)보다 일관된다. 매매기준율은 송금·현찰 매매가가 아닌 스프레드 없는 중간값이라 "대략 얼마" 표시에 맞다.
- **감수하는 비용**: 고정 스냅샷이라 시간이 지나면 실제와 벌어진다. 갱신 경로는 KB-323 의 몫이며, 그때까지는 참고용 근사다.
- **Alternatives considered**: 유료 API(openexchangerates 등) — 키 관리·비용·외부 의존이 늘고, 이 티켓의 목표(통화 저장)를 넘어선다. 기각.

## R10. 환율의 단위와 자릿수

- **단위 Decision**: **1단위당 원화 금액**(`krwPerUnit`)으로 저장한다. 은행 고시의 `일본 100엔`·`인도네시아 100루피아`·`베트남 100동` 은 100으로 나눠 정규화하고, 라벨에서도 `100` 을 뗐다.
- **Rationale**: 통화마다 단위가 다르면 환산 코드가 통화별 분기를 갖게 된다. 라벨에 `100` 이 남아 있으면 `JPY("일본 100엔", 8.89)` 를 읽는 사람이 "100엔 = 8.89원"으로 100배 오해한다.
- **자릿수 Decision**: **소수점 4자리 통일**.
- **Rationale**: 처음엔 2자리로 지시받았으나 1원 미만 통화에서 무너진다 — **VND 0.0544 → 0.05 는 −8.09%** 다. 9,000원 요리가 165,441동 대신 180,000동으로 나온다. IDR 도 −0.62%. 전 통화 4자리로 맞춰 통화별 예외를 없앴다.
- **타입 Decision**: `BigDecimal` **문자열 리터럴**. `Double` 은 `1416.00`·`0.0544` 를 정확히 표현하지 못해 금액 계산에서 오차가 누적된다.
- **회귀 방어**: `CurrencyRateSnapshotTest` 가 9,000원 → VND 165,441 을 고정한다. 누가 2자리로 되돌리면 이 테스트가 잡는다.

## R11. 환율을 어느 enum 이 소유하는가

- **Decision**: **`CurrencyCode` 가 소유**한다. `CountryCode` 는 통화만 가리킨다(`country.currency.krwPerUnit`).
- **Rationale**: 국가에 환율을 얹으면 **유로존 국가 전부에 같은 값이 중복**된다. 갱신 때 하나만 고치고 나머지를 놓치는 사고가 구조적으로 가능해진다. 통화에 두면 중복이 0이고 접근 경로 길이만 한 단계 늘어난다.
- **Alternatives considered**: `CountryCode(label, currency, krwPerUnit)` — 국가 하나만 보면 되는 편의는 있으나 중복이 위험을 만든다. 기각.
