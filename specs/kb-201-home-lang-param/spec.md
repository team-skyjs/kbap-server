# Feature Specification: lang 파라미터 정책 통일

**Feature Branch**: `kb-201-home-lang-param`

**Created**: 2026-07-20

**Status**: Draft

**Input**: KB-201 — [BE] lang 파라미터 정책 통일 — 전 API 필수화, 미지원 코드는 영어 폴백

> 브랜치·폴더 slug 는 홈 전용으로 시작한 초기 범위(`home-lang-param`)를 유지한다 — 범위가 5개 엔드포인트로 확장됐으나 브랜치 리네임은 하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 앱 전체가 한 언어로 보인다 (Priority: P1)

사용자가 기기 언어로 앱을 쓰면, 홈·음식 목록·검색·상세·북마크 어느 화면을 가도 같은 언어로 표시된다.

**Why this priority**: 지금은 화면마다 언어 결정 규칙이 달라 같은 세션에서 언어가 바뀐다. 프로필 언어가 일본어인 회원이 홈에서 일본어 음식명을 보고 그걸 탭해 상세로 들어가면 한국어로 바뀐다. 이 스토리가 이 기능의 존재 이유다.

**Independent Test**: 같은 표시 언어로 5개 화면을 차례로 조회해 표시명 언어가 일관되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 일본어 번역명이 있는 음식이 존재하고, **When** 홈·목록·검색·상세·북마크를 모두 일본어로 조회하면, **Then** 다섯 응답의 음식명이 모두 일본어다
2. **Given** 회원이 로그인해 있고, **When** 한국어로 홈을 조회하면, **Then** 프로필 설정과 무관하게 한국어로 응답된다
3. **Given** 같은 표시 언어를 전달하고, **When** 회원과 비회원이 각각 홈을 조회하면, **Then** 두 응답의 표시 언어가 동일하다

---

### User Story 2 - 알 수 없는 언어여도 화면은 열린다 (Priority: P1)

표시 언어를 값과 함께 전달했으나 그 값이 서비스가 지원하지 않는 언어이면, 오류 없이 영어로 표시된다.

**Why this priority**: 기기 언어는 사용자가 고른 값이 아니라 시스템이 주는 값이라 서비스가 통제할 수 없다. 지원하지 않는 기기 언어를 쓰는 사용자에게 오류를 주면 화면이 열리지 않는다. 특히 홈은 앱 진입 화면이라 실패하면 앱이 열리지 않는 것과 같다.

**Independent Test**: 지원 목록에 없는 코드를 5개 엔드포인트에 각각 전달해, 모두 성공 응답이며 표시명이 영어인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 어느 대상 API 든, **When** 지원하지 않는 언어 코드를 전달하면, **Then** 오류 없이 성공 응답이 오고 표시명은 영어다
2. **Given** 지원 언어와 대소문자만 다른 코드를 전달하면, **Then** 지원하지 않는 코드로 보아 영어로 응답한다
3. **Given** 지원 언어에 지역 태그가 붙은 코드를 전달하면, **Then** 영어로 응답한다
4. **Given** 지원 언어 코드 앞뒤에 공백이 붙어 있으면, **Then** 정확히 일치하지 않으므로 영어로 응답한다

---

### User Story 3 - 표시 언어는 반드시 채워서 보내야 한다 (Priority: P1)

클라이언트는 대상 API 를 호출할 때 표시 언어를 항상 값과 함께 전달한다. 빠뜨리거나 빈 값·공백으로 보내면 요청이 거절된다.

**Why this priority**: 표시 언어의 출처를 요청 하나로 고정하는 것이 이 기능의 핵심이다. 기본값을 두면 클라이언트가 언어를 빠뜨린 버그가 정상 응답에 묻혀 드러나지 않는다. 미지원 코드는 조용히 폴백하므로, 최소한 "값을 안 보낸 것"만큼은 시끄럽게 실패해야 한다.

**Independent Test**: 표시 언어를 빠뜨리거나 빈 값·공백으로 각 API 를 조회해 요청이 거절되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 어느 대상 API 든, **When** 표시 언어 파라미터를 넣지 않으면, **Then** 요청이 거절되고 잘못된 요청임을 알리는 오류가 반환된다
2. **Given** 어느 대상 API 든, **When** 표시 언어를 빈 값으로 보내면, **Then** 동일하게 거절된다
3. **Given** 어느 대상 API 든, **When** 표시 언어를 공백 문자로만 채워 보내면, **Then** 동일하게 거절된다
4. **Given** 표시 언어가 비어 있어 거절될 때, **When** 로그인 여부가 어떻든, **Then** 동일하게 거절된다

---

### User Story 4 - 비회원도 기기 언어로 홈을 본다 (Priority: P2)

로그인하지 않은 사용자가 앱을 열면 홈의 인기 음식명·기피 성분명이 기기 언어로 나온다.

**Why this priority**: US1 의 통일 규칙이 적용되면 자동으로 따라오는 결과다. 별도 구현이 아니라 검증 대상으로 남긴다.

**Independent Test**: 인증 없이 지원 언어를 전달해 홈을 조회하고 번역명을 확인한다.

**Acceptance Scenarios**:

1. **Given** 일본어 번역명이 있는 음식이 존재하고, **When** 비회원이 일본어로 홈을 조회하면, **Then** 인기 음식명이 일본어로 응답된다

---

### Edge Cases

- **값이 비어 있는 것과 값이 잘못된 것은 다르게 취급한다** — 빈 값·공백은 아예 안 보낸 것과 같이 보아 거절하고, 값이 채워져 있으면 그것이 지원하지 않는 코드여도 영어로 응답한다.
- 표시 언어 코드 매칭은 **정확 일치**다. 대소문자 보정·지역 태그 제거·앞뒤 공백 제거 같은 정규화를 하지 않는다.
- 표시 언어에 해당하는 번역명이 특정 음식·성분에 없는 경우, 기존 번역명 폴백 동작(한국어 원문)을 그대로 따른다.
- 인증 토큰이 유효하지 않은 경우의 응답은 이 기능이 바꾸지 않는다.
- 로그인 여부에 따른 개인화 섹션 노출 규칙은 그대로다 — 로그인 여부는 **무엇을 보여줄지**를 계속 결정하고, **어떤 언어로 보여줄지**에만 관여하지 않게 된다.
- 스캔 API 는 이 기능의 대상이 아니다 — 표시 언어 파라미터를 받지 않고 회원 프로필을 계속 참조한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 대상 API 는 표시 언어를 **필수로** 받아야 한다. 기본값을 두지 않는다.
- **FR-002**: 표시 언어 파라미터가 없거나 값이 비어 있으면(공백만 있는 경우 포함) 잘못된 요청으로 거절해야 한다.
- **FR-003**: 전달된 표시 언어가 지원 언어와 정확히 일치하면 그 언어로 응답해야 한다. 지원 언어는 한국어를 포함한 10종이다.
- **FR-004**: 전달된 표시 언어가 비어 있지 않으나 지원 목록에 없으면(미지원 코드·대소문자 불일치·지역 변형·앞뒤 공백 포함) 영어로 응답해야 하며, 오류 응답을 반환해서는 안 된다.
- **FR-005**: 외부 입력의 유효성 판정과 거절은 **요청 경계에서** 이뤄져야 하며, 그 뒤의 처리 로직은 이미 확정된 표시 언어를 전달받는다고 가정할 수 있어야 한다.
- **FR-006**: 홈 응답의 표시 언어는 요청에 실린 값만으로 결정되어야 하며, 회원 프로필의 앱 언어를 참조해서는 안 된다.
- **FR-007**: 표시 언어는 각 응답의 번역 대상 전부(음식명·설명·기피 성분명)에 동일하게 적용돼야 한다.
- **FR-008**: 지원하지 않는 언어 코드를 사유로 하는 오류 응답은 서비스에서 제거돼야 한다.
- **FR-009**: API 문서에 표시 언어 파라미터가 필수임, 지원 목록, 미지원 값의 영어 폴백, 누락·빈 값 시의 거절 응답이 대상 API 전부에 기술돼야 한다.
- **FR-010**: 로그인 여부에 따른 개인화 규칙(기피 성분·최근 스캔·북마크 여부)은 그대로 유지돼야 한다.

### Key Entities

- **표시 언어**: 응답의 번역명을 고르는 기준. 요청이 반드시 값과 함께 제공해야 하며, 지원 목록에 있으면 그 언어, 없으면 영어로 확정된다. 결정 규칙은 대상 API 전부에서 동일하다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 지원하는 10개 언어 각각에 대해, 해당 언어를 전달해 대상 API 를 조회하면 번역명이 존재하는 항목은 100% 그 언어로 표시된다.
- **SC-002**: 같은 표시 언어로 5개 대상 API 를 조회하면 응답 언어가 100% 일치한다.
- **SC-003**: 비어 있지 않은 표시 언어를 전달한 요청은 그 값이 무엇이든 100% 성공 응답을 반환한다.
- **SC-004**: 표시 언어가 없거나 비어 있는 요청은 100% 거절된다.
- **SC-005**: 같은 표시 언어로 조회하면 회원과 비회원의 응답 언어가 100% 동일하다.

## Assumptions

- 클라이언트가 기기 설정 언어를 서비스 지원 언어 코드 형식으로 변환해 전달한다. 서버는 코드 정규화를 수행하지 않는다.
- **파괴적 변경 인지**: 현재 배포된 클라이언트는 홈을 표시 언어 없이 호출하고, 음식·북마크도 생략하면 성공 응답을 받아왔다. 이 변경 후 그 호출은 모두 거절된다. **클라이언트 배포 선행 또는 강제 업데이트가 릴리스 조건**이다. 5개가 한 번에 바뀌므로 클라이언트 릴리스는 한 번으로 끝난다.
- **정책 번복 인지**: 미지원 코드에 오류를 반환하던 기존 결정(spec 008)을 뒤집는다. 헌법 원칙 V 개정과 결정 기록이 이 기능의 산출물에 포함된다.
- **감수하는 비용**: 미지원 코드가 조용히 영어로 폴백되므로, 클라이언트가 언어 코드를 잘못 보내도(예: 오타·대소문자) 성공 응답이 와 결함이 QA 에서 드러나지 않을 수 있다. 표시 언어를 필수로 두는 것이 이 위험에 대한 부분적 방어다.
- 신규 API·데이터베이스 스키마 변경·번역 데이터 추가는 이 기능의 범위 밖이다.
- 응답의 필드 구조는 변경하지 않는다(응답 언어와 오류 응답만 달라진다).
- 스캔 API 의 언어 결정 방식(회원 프로필 참조)은 이 기능에서 바꾸지 않는다.
