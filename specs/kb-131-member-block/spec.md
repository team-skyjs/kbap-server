# Feature Specification: 사용자 차단 (Member Block)

**Feature Branch**: `kb-131-member-block`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "KB-131 유저 차단 API — 리뷰나 커뮤니티 등 UGC 보이는 곳에서 공통으로 사용할 예정. 사용자 차단 후에는 리뷰 조회 시 컨텐츠 조회 시점에 내가 차단한 사용자의 것은 보이지 않도록 변경되어야 함."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 불쾌한 회원 차단 후 그 회원의 리뷰가 안 보인다 (Priority: P1)

리뷰를 보다가 특정 회원의 글을 더 이상 보고 싶지 않은 회원이 그 회원을 차단한다. 차단 직후부터 내가 보는 모든 리뷰 목록(음식 리뷰 목록, 음식 상세의 리뷰 섹션)에서 그 회원이 쓴 리뷰가 사라진다. 신고(리뷰 한 건을 가리는 수단)와 달리 차단은 그 사람이 쓴 글 전체를 가리는 수단이며, 앱스토어 UGC 심사에서도 신고와 함께 요구되는 기능이다.

**Why this priority**: 차단의 존재 이유 그 자체 — 차단 등록과 콘텐츠 미노출이 함께 동작해야 사용자 가치가 생기고, 앱스토어 심사 요건을 충족한다.

**Independent Test**: 회원 A 가 회원 B 를 차단한 뒤 B 의 리뷰가 있는 음식의 리뷰 목록을 조회하면 B 의 리뷰가 0건 노출되는 것으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 회원 B 의 리뷰가 있는 음식, **When** 회원 A 가 B 를 차단하고 그 음식의 리뷰 목록을 조회하면, **Then** B 의 리뷰는 목록에 나타나지 않는다.
2. **Given** A 가 B 를 차단한 상태, **When** B 가 같은 음식의 리뷰 목록을 조회하면, **Then** A 의 리뷰는 그대로 보인다(차단은 단방향).
3. **Given** A 가 B 를 차단한 상태, **When** 누구든 그 음식의 평균 별점·리뷰 수를 조회하면, **Then** 집계 값은 차단 전과 동일하다(집계는 전역 값 유지).
4. **Given** 로그인한 회원 A, **When** A 가 자기 자신을 차단 시도하면, **Then** 요청이 거부되고 오류가 반환된다.
5. **Given** 존재하지 않거나 탈퇴한 회원 식별자, **When** A 가 그 식별자로 차단 시도하면, **Then** "회원을 찾을 수 없음" 오류가 반환된다.
6. **Given** A 가 이미 B 를 차단한 상태, **When** A 가 B 를 다시 차단하면, **Then** 오류 없이 성공으로 처리된다(멱등).

---

### User Story 2 - 차단 해제 후 다시 보인다 (Priority: P2)

차단했던 회원과의 관계를 되돌리고 싶은 회원이 차단을 해제한다. 해제 직후부터 그 회원의 리뷰가 목록에 다시 나타나고, 마음이 바뀌면 언제든 같은 회원을 다시 차단할 수 있다.

**Why this priority**: 차단이 영구적이면 실수·변심을 되돌릴 수 없어 기능 자체의 신뢰가 떨어진다. 차단(P1)이 있어야 의미가 생기는 후속 동작.

**Independent Test**: 차단 → 해제 → 리뷰 목록 재조회로 해당 회원의 리뷰가 다시 노출되는 것을 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** A 가 B 를 차단한 상태, **When** A 가 차단을 해제하고 리뷰 목록을 조회하면, **Then** B 의 리뷰가 다시 노출된다.
2. **Given** A 가 B 를 차단한 적 없는 상태, **When** A 가 B 의 차단 해제를 요청하면, **Then** 오류 없이 성공으로 처리된다(멱등).
3. **Given** A 가 B 를 차단했다가 해제한 상태, **When** A 가 B 를 다시 차단하면, **Then** 정상적으로 차단되고 B 의 리뷰가 다시 숨겨진다(재차단).

---

### User Story 3 - 내가 차단한 회원 목록 확인 (Priority: P3)

회원이 자신이 차단한 회원들을 한눈에 확인한다. 목록에는 각 회원의 식별자·닉네임·프로필 이미지가 보이며, 여기서 누구를 해제할지 판단한다.

**Why this priority**: 차단·해제(P1·P2)가 동작한 뒤의 관리 편의 기능. 목록 없이도 차단·해제 자체는 성립한다.

**Independent Test**: 여러 회원을 차단한 뒤 차단 목록을 조회해 차단한 회원 전원이 최신 닉네임·프로필 이미지와 함께 반환되는 것으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** A 가 B·C 를 차단한 상태, **When** A 가 차단 목록을 조회하면, **Then** B·C 가 각자의 식별자·닉네임·프로필 이미지와 함께 전부 반환된다(페이징 없음).
2. **Given** A 가 B 를 차단한 뒤 B 가 닉네임을 변경한 상태, **When** A 가 차단 목록을 조회하면, **Then** B 의 최신 닉네임이 보인다(차단 시점 스냅샷이 아님).
3. **Given** 아무도 차단하지 않은 회원, **When** 차단 목록을 조회하면, **Then** 빈 목록이 반환된다.

---

### Edge Cases

- 차단한 회원이 이후 탈퇴하면? — 차단 목록에는 더 이상 노출되지 않아도 무방하며, 탈퇴 회원의 리뷰는 기존 정책대로 처리된다(차단 여부와 무관).
- 차단·해제·재차단을 빠르게 반복하면? — 각 요청은 멱등하게 처리되어 마지막 상태만 남는다.
- 로그인하지 않은 상태로 차단 관련 기능을 호출하면? — 인증 오류로 거부된다(리뷰 조회를 포함한 관련 화면 전부 인증 필수이므로 조회자 식별자는 항상 존재).
- 차단한 회원 수가 많아지면? — 개인이 차단하는 인원은 소수라는 전제로 목록은 전체 반환하며, 리뷰 목록 필터도 차단 수에 비례해 동작한다.
- 내 리뷰 목록(내가 쓴 리뷰 모아보기)은? — 조회자 본인의 글만 나오므로 차단 필터의 실질 영향은 없지만, 리뷰 목록 조회라는 동일한 규칙(조회 시점에 차단 회원 글 제외)이 일관되게 적용된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 인증된 회원은 다른 회원을 차단할 수 있어야 한다.
- **FR-002**: 시스템은 자기 자신에 대한 차단 요청을 거부하고 오류를 반환해야 한다.
- **FR-003**: 시스템은 존재하지 않거나 탈퇴한 회원에 대한 차단 요청에 "회원을 찾을 수 없음" 오류를 반환해야 한다.
- **FR-004**: 이미 차단 중인 회원을 다시 차단해도 오류 없이 성공으로 처리해야 한다(멱등).
- **FR-005**: 회원은 차단을 해제할 수 있어야 하며, 차단하지 않은 회원에 대한 해제 요청도 오류 없이 성공으로 처리해야 한다(멱등).
- **FR-006**: 차단을 해제했던 회원을 다시 차단할 수 있어야 한다(재차단 시에도 신규 차단과 동일하게 동작).
- **FR-007**: 회원은 자신이 차단한 회원 목록을 조회할 수 있어야 하며, 목록은 각 회원의 식별자·닉네임·프로필 이미지를 포함하고 페이징 없이 전체를 반환한다. 닉네임·프로필 이미지는 조회 시점의 최신 값이어야 한다.
- **FR-008**: 차단은 단방향이어야 한다 — A 가 B 를 차단해도 B 가 보는 화면(A 의 리뷰 노출 포함)에는 어떤 영향도 없다.
- **FR-009**: 리뷰 목록 조회 시 **콘텐츠 조회 시점에** 조회자가 차단한 회원의 리뷰를 제외해야 한다(저장된 데이터를 삭제·변경하지 않는다). 대상: 음식 리뷰 목록 등 다른 회원의 리뷰가 노출되는 모든 지점.
- **FR-010**: 음식의 평균 별점·리뷰 수 등 집계 값은 차단과 무관하게 전역 값을 유지해야 한다(조회자마다 달라지지 않는다).
- **FR-011**: 차단에 의한 노출 제외 규칙은 리뷰에 한정되지 않고, 향후 커뮤니티 등 회원 생성 콘텐츠(UGC)가 노출되는 다른 지점에서도 동일하게 재사용할 수 있는 공통 규칙이어야 한다.
- **FR-012**: 차단 등록·해제·목록 조회는 모두 인증된 회원만 사용할 수 있어야 한다.

### Key Entities

- **차단 관계(Member Block)**: "누가(차단한 회원) 누구를(차단당한 회원) 차단했는가"를 나타내는 단방향 관계. 회원 쌍당 최대 1건이며, 해제되면 비활성 상태로 남고 재차단 시 다시 활성화된다.
- **회원(Member)**: 차단의 주체이자 대상. 차단 목록에는 대상 회원의 최신 닉네임·프로필 이미지가 함께 노출된다.
- **리뷰(Review)**: 차단에 의해 노출이 걸러지는 첫 번째 UGC. 데이터 자체는 변하지 않고 조회자별 노출만 달라진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 차단 완료 직후의 리뷰 목록 조회부터 차단한 회원의 리뷰가 0건 노출된다.
- **SC-002**: 차단 해제 직후의 리뷰 목록 조회부터 해당 회원의 리뷰가 다시 노출된다.
- **SC-003**: 임의 회원을 차단하기 전후로 음식의 평균 별점·리뷰 수 집계가 동일하다.
- **SC-004**: 동일한 차단·해제 요청을 연속 2회 이상 보내도 결과 상태와 응답 성공 여부가 1회 요청과 동일하다.
- **SC-005**: A 의 차단 행위 전후로 B(차단당한 회원)가 보는 리뷰 목록·집계에는 어떤 변화도 없다.
- **SC-006**: 차단 목록 조회 시 차단 중인 회원 전원이 누락 없이 반환되고, 해제한 회원은 포함되지 않는다.

## Assumptions

- 개인이 차단하는 인원은 소수(수십 명 이내)라는 전제로 차단 목록은 페이징 없이 전체 반환하며, 차단 수 상한은 두지 않는다.
- 차단당한 회원에게는 어떤 알림·표시도 하지 않는다(상대는 차단 사실을 알 수 없다).
- 커뮤니티 등 리뷰 외 UGC 노출 지점은 아직 존재하지 않는다 — 이번 범위에서 차단 필터는 리뷰 노출 지점에만 실제 적용하고, 다른 UGC 에 재사용 가능한 공통 규칙으로 만든다(FR-011).
- 선행 이슈 KB-129(신고에 의한 리뷰 제외 필터)는 아직 구현되어 있지 않다 — 차단 필터가 첫 번째 노출 제외 규칙으로 도입되며, 이후 신고 제외 필터가 같은 방식으로 합류한다.
- 리뷰 조회를 포함한 관련 기능은 전부 인증이 필요하므로(KB-132), 목록 조회 시 조회자 회원 식별자는 항상 존재한다.
- 차단이 리뷰 외 회원 간 상호작용(예: 랭킹, 북마크)에 영향을 주는 요구는 없다.
