# Feature Specification: 스프링 컨테이너 메트릭 개선 (Tomcat 스레드풀·HTTP 지연 백분위 노출)

**Feature Branch**: `kb-411-spring-container-metrics`

**Created**: 2026-09-02

**Status**: Draft

**Jira**: [KB-411](https://simhani1.atlassian.net/browse/KB-411) (에픽 KB-379 모니터링 - Grafana·CloudWatch)

**Input**: User description: "411 이제 스프링 컨테이너 메트릭 개선으로 넘어간다"

## 배경

api 앱은 관측 엔드포인트로 내부 지표를 노출하고, 호스트마다 뜬 수집기가 이를 홈서버 시계열 저장소로 밀어 넣는다(KB-380·KB-381). 그런데 대시보드를 짜다 보니 **컨테이너 안에서 정작 봐야 할 두 지표군이 비어 있다**(2026-09-01 확인, 지식 위키 `observability-app-metrics-and-ecs-healthcheck`).

- **웹 서버 스레드풀이 전무하다.** 요청을 처리하는 스레드가 몇 개 바쁘고 상한이 얼마인지 알 수 없어, 트래픽이 몰릴 때 앱이 포화됐는지 판단할 수단이 없다. 프레임워크 기본값이 이 지표를 끄고 있어서다.
- **응답 지연의 백분위(p95·p99)를 계산할 수 없다.** 지금 나오는 건 요청 수·누적 시간·최대값뿐이라 "평균" 과 "최악" 만 보이고, 사용자 대다수가 겪는 지연(p95)은 알 수 없다. 백분위 계산에 필요한 구간별 분포가 노출되지 않아서다.

한편 요청 처리량(req/sec)·GC·힙·DB 커넥션 풀은 이미 노출되고 있어 대시보드 쪽 작업만 남았다. dev·prod 를 묶어 보는 필터도 수집기가 붙이는 환경 라벨이 이미 있어 대시보드 변수로 해결된다(2026-09-02 홈서버 Node Exporter 대시보드에 같은 방식으로 적용 완료).

이 기능은 **앱이 두 지표군을 노출하도록 하는 것**이 핵심이고, 그 위에 대시보드 구성과 기록이 따라온다.

## 범위

- **포함**: api 앱의 웹 서버 스레드풀 지표 노출, HTTP 요청 지연의 구간 분포(백분위 계산용) 노출, 홈서버 앱 대시보드(환경 필터·처리량·p95/p99·DB 풀·GC·스레드풀) 구성, 대시보드 정의와 각 패널 질의의 의미 기록.
- **제외**: 배치 앱(HTTP 트래픽이 없어 스레드풀·지연 지표가 무의미), 알림 규칙, 수집기(Alloy)·홈서버 저장소 설정 변경, 관측 엔드포인트 접근 제어(KB-380 결정 유지), 호스트 이름 개선(별도 작업).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 응답 지연 백분위를 본다 (Priority: P1)

운영자가 홈서버 대시보드에서 api 의 p95·p99 응답 지연을 시간축으로 본다. 특정 시각에 "사용자 대부분이 느렸는가, 소수만 느렸는가" 를 구분할 수 있다.

**Why this priority**: 지연은 사용자 체감과 직결되는 유일한 지표이고, 현재 평균·최대값만으로는 장애 판단이 불가하다. 대시보드의 나머지 패널은 이미 나오는 지표로 구성 가능하므로 앱 변경이 필요한 이 항목이 가장 우선이다.

**Independent Test**: 앱에 요청을 한 번 보낸 뒤 관측 엔드포인트를 읽으면 HTTP 요청 지연의 구간별 누적 분포가 나온다. 이것만으로 백분위 패널이 성립한다.

**Acceptance Scenarios**:

1. **Given** api 앱이 기동돼 있고 HTTP 요청이 한 번 이상 처리됐다, **When** 관측 엔드포인트를 읽는다, **Then** HTTP 요청 지연의 구간별 누적 분포 지표가 포함돼 있다.
2. **Given** 그 분포가 홈서버에 수집되고 있다, **When** 대시보드에서 p95·p99 패널을 본다, **Then** 인스턴스 2대의 분포를 합산한 백분위 값이 시간축으로 그려진다(인스턴스별로 따로 계산한 값이 아니다).
3. **Given** 분포 노출이 켜진 뒤 dev 에 배포됐다, **When** 홈서버 저장소의 시계열 수 증가를 확인한다, **Then** 증가 폭이 예상 범위 안이며(경로×메서드×상태×인스턴스 조합당 구간 수 상한 이내) prod 반영 판단의 근거가 된다.

---

### User Story 2 - 웹 서버 포화 여부를 본다 (Priority: P1)

운영자가 대시보드에서 api 의 요청 처리 스레드 사용량(바쁜 스레드·현재 스레드·최대 스레드)을 본다. 바쁜 스레드가 최대에 붙으면 앱이 포화된 것이고, 그 전이면 병목은 다른 곳(DB·외부 호출)이다.

**Why this priority**: 부하 상황에서 "앱을 늘려야 하는가, DB 를 봐야 하는가" 를 가르는 첫 분기점이다. 현재 이 지표가 하나도 없다.

**Independent Test**: 앱 기동 후 관측 엔드포인트를 읽으면 웹 서버 스레드풀 지표 세 개가 나온다.

**Acceptance Scenarios**:

1. **Given** api 앱이 기동돼 있다, **When** 관측 엔드포인트를 읽는다, **Then** 바쁜 스레드 수·현재 스레드 수·최대 스레드 수 지표가 포함돼 있다.
2. **Given** 그 지표가 수집되고 있다, **When** 대시보드 스레드풀 패널을 본다, **Then** 인스턴스별로 세 값이 한 그래프에 겹쳐 그려져 포화 여부를 한눈에 판단할 수 있다.

---

### User Story 3 - 앱 대시보드 한 장으로 상태를 훑는다 (Priority: P2)

운영자가 홈서버의 앱 대시보드를 열고 상단 환경 필터(dev·prod·전체)를 고르면, 요청 처리량(req/sec)·p95/p99 지연·DB 커넥션 풀·GC·힙·스레드풀 패널이 그 환경 기준으로 한 화면에 나온다.

**Why this priority**: 지표 노출(US1·US2)이 끝나야 완성되는 조립 단계다. 노출 자체보다 후순위지만 KB-411 의 사용자 가치는 여기서 실현된다.

**Independent Test**: 이미 나오는 지표(처리량·GC·힙·DB 풀)만으로도 패널 절반은 독립 구성·검증이 가능하다.

**Acceptance Scenarios**:

1. **Given** 대시보드를 연다, **When** 환경 필터를 prod 로 고른다, **Then** 모든 패널이 prod 인스턴스의 값만 보여 준다.
2. **Given** 환경 필터를 전체로 고른다, **When** 처리량 패널을 본다, **Then** dev·prod 가 구분되는 선으로 함께 그려진다.
3. **Given** 처리량 패널을 본다, **When** 10초 간격으로 수집된 누적 요청 수를 확인한다, **Then** 패널의 y 축은 구간 증가량을 구간 길이로 나눈 초당 평균 요청 수다.

---

### User Story 4 - 대시보드를 기록으로 남긴다 (Priority: P3)

다음 사람이 대시보드가 사라지거나 홈서버가 바뀌어도 복원할 수 있도록, 대시보드 정의를 내보내 저장소에 두고 각 패널의 질의가 무엇을 뜻하는지 한 줄씩 적는다.

**Why this priority**: 홈서버 Grafana 는 백업 대상이 아니다. 질의를 "이해한 상태" 로 만드는 것이 KB-411 의 명시된 목적이라 기록이 그 증거가 된다.

**Independent Test**: 저장소의 대시보드 정의 파일을 새 Grafana 에 가져오면 같은 패널이 재현된다.

**Acceptance Scenarios**:

1. **Given** 대시보드 정의 파일이 저장소에 있다, **When** Grafana 에 가져온다, **Then** 패널·변수가 그대로 재현된다.
2. **Given** 패널 설명 문서를 읽는다, **When** 임의의 패널을 고른다, **Then** 그 패널의 질의가 무엇을 어떻게 계산하는지 한 줄로 적혀 있다.

---

### Edge Cases

- **인스턴스가 2대인데 한 대만 값이 있으면?** 백분위는 있는 만큼만 합산한다. 한 대가 재시작 중이면 그 구간은 남은 한 대의 분포로 계산되며 빈 값이 아니다.
- **트래픽이 0 인 구간의 p95·p99 는?** 분포가 갱신되지 않으므로 값이 없거나 직전 값이 유지된다. 패널은 "0ms" 로 오독되지 않게 값 없음으로 표시한다.
- **지연 분포 노출로 시계열 수가 급증하면?** 구간 범위를 좁혀(하한·상한 지정) 조합당 구간 수를 제한한다. dev 에서 증가 폭을 확인한 뒤 prod 로 올린다.
- **경로 변수(예: `/api/foods/{id}`)가 실제 값으로 풀려 조합이 폭증하면?** 프레임워크가 경로 템플릿으로 집계하므로 기본적으로 발생하지 않는다. 미매칭 경로(404)는 하나의 값으로 묶인다.
- **스레드풀 지표가 켜졌는데 배치 앱에도 영향이 가면?** 배치는 대상이 아니며 배치 설정은 건드리지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: api 앱은 관측 엔드포인트에 웹 서버 스레드풀 지표(바쁜 스레드 수·현재 스레드 수·최대 스레드 수)를 노출해야 한다.
- **FR-002**: api 앱은 HTTP 요청 지연을 **구간별 누적 분포** 형태로 노출해야 한다. 저장소가 질의 시점에 여러 인스턴스를 합산해 백분위를 계산할 수 있어야 하므로, 앱 안에서 계산한 백분위 값(인스턴스 간 합산 불가)으로 대체할 수 없다.
- **FR-003**: 지연 분포의 구간 범위는 하한·상한을 명시해 조합당 구간 수를 제한해야 한다(카디널리티 방어).
- **FR-004**: 위 두 노출은 api 앱의 모든 실행 환경(local·dev·staging·prod)에 동일하게 적용되며, 배치 앱에는 적용하지 않는다.
- **FR-005**: 관측 엔드포인트 노출 범위(health·prometheus)·경로·접근 방식은 바꾸지 않는다(KB-380 결정 유지).
- **FR-006**: 홈서버 앱 대시보드는 환경 필터(dev·prod·전체)를 갖고, 모든 패널이 그 필터를 따라야 한다.
- **FR-007**: 대시보드는 요청 처리량(초당 요청 수, 누적 카운터의 구간 증가율)·p95/p99 지연·DB 커넥션 풀(활성·유휴·대기·최대)·GC(횟수·소요 시간)·힙 사용량·웹 서버 스레드풀 패널을 포함해야 한다.
- **FR-008**: 대시보드 정의는 저장소에 파일로 보관하고, 각 패널 질의의 의미를 한 줄씩 기록한 문서를 함께 둔다.
- **FR-009**: 지연 분포 노출의 검증은 기존 통합 테스트 컨텍스트 안에서 수행한다(새 애플리케이션 컨텍스트를 만들지 않는다 — KB-392 규율).

### Key Entities

- **관측 지표(메트릭)**: 앱이 노출하는 이름·라벨·값의 시계열. 이 기능이 추가하는 것은 스레드풀 지표 3종과 HTTP 지연 분포(구간별 누적 카운트)다.
- **대시보드 정의**: 패널·변수·질의를 담은 내보내기 파일. 저장소에 보관되는 산출물.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 배포 후 관측 엔드포인트 한 번 조회로 스레드풀 지표 3종과 HTTP 지연 분포가 모두 확인된다(누락 0).
- **SC-002**: 대시보드에서 임의 시각의 p95·p99 지연을 5초 안에 읽을 수 있다(패널을 찾아 값을 읽는 데 걸리는 시간).
- **SC-003**: 환경 필터를 바꿀 때 6개 패널 전부가 해당 환경 값으로 바뀐다(필터를 따르지 않는 패널 0).
- **SC-004**: 지연 분포 노출 후 홈서버 시계열 증가가 dev 기준으로 예측 범위(조합당 구간 수 상한 × 조합 수) 안에 든다.
- **SC-005**: 대시보드 정의 파일을 새 Grafana 에 가져와 패널 6종·환경 필터가 그대로 재현된다.

## Assumptions

- 홈서버 수집 경로(호스트별 수집기 → 홈 저장소)와 환경 라벨은 KB-381 대로 동작 중이며 이 기능에서 바꾸지 않는다.
- dev 선반영 → prod 반영 순서는 기존 배포 흐름(develop 머지 = dev 배포, 릴리스 PR = prod 배포)이 자연히 보장하므로 별도 프로필 분기를 두지 않는다. 카디널리티 확인은 dev 배포 후 prod 릴리스 전에 한다.
- 지연 분포의 구간 하한·상한 기본값은 5ms·10s 로 잡는다. 실제 응답 분포를 보고 조정할 수 있다.
- 스레드풀 지표는 실제 웹 서버가 떠야 나오므로, MockMvc 기반 통합 테스트로는 검증하지 않는다. 설정 값 바인딩 확인과 dev 배포 후 관측 엔드포인트 육안 확인으로 대신한다(KB-380 "설정 노출은 자동화 테스트 없음" 결정과 일관).
- 대시보드 정의 파일과 패널 설명 문서는 이 저장소 `docs/` 아래에 둔다(홈서버 설정 저장소가 따로 없음).
- 처리량 패널의 수집 간격은 현재 수집기 설정(15초)을 따르며, 구간 증가율 계산 창은 수집 간격의 2배 이상으로 잡는다.
