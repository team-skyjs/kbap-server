# Feature Specification: 리뷰 신고

**Feature Branch**: `kb-129-review-report`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "KB-129 [BE] 리뷰 신고 API — 리뷰 신고 접수 + 신고자 본인에게 해당 리뷰 숨김"

## Clarifications

### Session 2026-08-01

- Q: 신고 접수 엔드포인트를 어떤 형태로 정의할까요? → A: 신고를 독립 리소스로 일반화 — `POST /api/v1/reports`, body 에 `targetType`(이번 범위는 REVIEW 뿐)·`targetId`·`reason`·`detail`. 신고 대상은 이후 커뮤니티 게시글로 확장될 예정이므로 리뷰 하위 리소스가 아닌 신고 중심 명칭을 쓴다.
- Q: 신고 기록을 어떤 모델로 저장할까요? → A: 일반 신고 모델 — 단일 신고 엔티티에 대상 타입 + 대상 id 를 저장하고 유일성은 (신고자, 대상 타입, 대상 id) 조합. 게시글 신고가 추가돼도 저장 구조는 불변, 타입 값만 늘어난다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 부적절한 리뷰 신고 (Priority: P1)

앱 사용자가 음식 리뷰 목록에서 부적절한 리뷰(스팸·욕설·허위 정보·음란물 등)를 발견하면, 사유를 골라 신고를 접수한다. 서비스는 신고를 저장하고 접수 완료를 알려준다. 리뷰는 사용자 생성 콘텐츠(UGC)이므로 앱스토어 심사에서 신고 수단은 사실상 필수 요건이다.

**Why this priority**: 신고 접수 자체가 이 기능의 존재 이유다. 앱스토어 UGC 심사 요건을 충족하는 최소 단위이며, 이것만 구현해도 배포 가치가 있다.

**Independent Test**: 회원이 다른 회원의 리뷰를 사유와 함께 신고하면 접수가 저장되고 성공 응답을 받는 것으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 다른 회원이 작성한 리뷰가 있을 때, **When** 로그인한 회원이 사유(예: 스팸)를 골라 신고하면, **Then** 신고가 접수되고 성공 응답을 받는다.
2. **Given** 신고 사유를 고를 때, **When** 스팸·광고 / 욕설·혐오 / 허위 정보 / 음란물 / 기타 중 하나를 선택하면, **Then** 선택한 사유 코드가 신고와 함께 저장된다.
3. **Given** 사유가 "기타"처럼 부연이 필요한 경우, **When** 상세 설명(최대 500자)을 함께 적어 신고하면, **Then** 상세 설명이 신고에 함께 저장된다.
4. **Given** 자기가 작성한 리뷰가 있을 때, **When** 그 리뷰를 신고하면, **Then** 신고가 거절되고 잘못된 요청임을 알려준다.
5. **Given** 이미 신고한 리뷰가 있을 때, **When** 같은 리뷰를 다시 신고하면, **Then** 중복 신고로 거절된다.
6. **Given** 존재하지 않거나 삭제된 리뷰가 있을 때, **When** 그 리뷰를 신고하면, **Then** 대상 없음으로 거절된다.
7. **Given** 로그인하지 않은 상태일 때, **When** 신고를 시도하면, **Then** 인증 필요로 거절된다.

---

### User Story 2 - 신고한 리뷰는 나에게 보이지 않음 (Priority: P2)

신고를 마친 사용자가 같은 음식의 리뷰 목록을 다시 열면, 방금 신고한 리뷰가 목록에서 사라져 있다. 불쾌한 콘텐츠를 다시 마주치지 않게 하는 것이 신고 경험의 완성이다. 다른 사용자에게는 그 리뷰가 그대로 보인다.

**Why this priority**: 신고 접수(US1)가 있어야 성립하는 후속 경험이다. 신고만 되고 리뷰가 계속 보이면 사용자는 신고가 무시됐다고 느끼므로 P1 바로 다음으로 중요하다.

**Independent Test**: 회원 A가 리뷰를 신고한 뒤 A의 음식 리뷰 목록 조회에는 그 리뷰가 없고, 회원 B의 조회에는 그대로 있는 것으로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 회원 A가 어떤 리뷰를 신고한 상태일 때, **When** A가 그 음식의 리뷰 목록을 조회하면, **Then** 신고한 리뷰는 목록에 나타나지 않는다.
2. **Given** 회원 A가 어떤 리뷰를 신고한 상태일 때, **When** 다른 회원 B가 같은 음식의 리뷰 목록을 조회하면, **Then** 그 리뷰는 그대로 보인다.
3. **Given** 회원 A가 한 음식에서 여러 리뷰를 신고한 상태일 때, **When** A가 그 음식의 리뷰 목록을 조회하면, **Then** 신고한 리뷰 전부가 제외된다.
4. **Given** 커서 기반 페이지 조회 중일 때, **When** 신고로 제외된 리뷰 때문에 한 페이지가 기준 개수보다 적게 채워지면, **Then** 페이지 개수를 억지로 채우지 않고 다음 페이지 여부·커서 규약은 그대로 유지된다.

---

### Edge Cases

- 자기 리뷰 신고와 중복 신고가 동시에 해당하면(자기 리뷰를 두 번 신고 시도) 자기 리뷰 거절이 우선한다 — 첫 신고 자체가 접수되지 않으므로 중복 상황이 생기지 않는다.
- 같은 리뷰에 대해 두 요청이 동시에 접수돼도 신고는 한 건만 저장된다(중복 방지는 동시 요청에도 유효).
- 신고 상세 설명이 500자를 넘으면 잘못된 요청으로 거절된다.
- 정의되지 않은 사유 값이나 대상 타입 값으로 신고하면 잘못된 요청으로 거절된다.
- 신고된 리뷰가 이후 작성자에 의해 삭제되면 모든 회원의 목록에서 사라진다(기존 삭제 규칙 그대로). 저장된 신고 기록은 남는다.
- 신고 취소 기능은 없다 — 한 번 신고한 리뷰는 그 회원에게 계속 숨겨진다.
- 음식 상세 화면의 평점 요약(평균·개수)은 신고 여부와 무관하게 전체 리뷰 기준을 유지한다(목록 노출만 개인화).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 로그인한 회원은 다른 회원의 리뷰를 사유와 함께 신고할 수 있어야 하며, 서비스는 신고자·대상 타입·대상 id·사유·상세 설명을 저장해야 한다. 신고 접수는 대상 타입을 함께 받는 신고 중심 단일 창구로 노출해 향후 커뮤니티 게시글 등 새 대상이 타입 값 추가만으로 확장되게 한다.
- **FR-002**: 신고 사유는 고정 카테고리 5종 — 스팸·광고(SPAM), 욕설·혐오(ABUSE), 허위 정보(FALSE_INFO), 음란물(SEXUAL), 기타(OTHER) — 의 안정적인 코드값으로 받고 저장·반환해야 한다. 사유의 번역 표시명은 서버가 만들지 않는다(클라이언트 i18n 소관).
- **FR-003**: 신고 상세 설명은 선택 입력이며 최대 500자까지 허용해야 한다. 초과하면 잘못된 요청으로 거절한다.
- **FR-004**: 자기가 작성한 리뷰에 대한 신고는 잘못된 요청으로 거절해야 한다.
- **FR-005**: 같은 회원이 같은 대상(대상 타입 + 대상 id)을 두 번 이상 신고하면 중복으로 거절해야 하며, 동시에 들어온 중복 요청에도 신고는 한 건만 저장돼야 한다.
- **FR-006**: 존재하지 않거나 삭제된 리뷰에 대한 신고는 대상 없음으로 거절해야 한다.
- **FR-007**: 신고 접수와 리뷰 목록 조회는 모두 인증된 회원만 이용할 수 있어야 하며, 미인증 요청은 거절해야 한다.
- **FR-008**: 음식 리뷰 목록 조회는 호출한 회원이 신고한 리뷰를 결과에서 제외해야 한다. 신고하지 않은 다른 회원의 조회 결과에는 영향이 없어야 한다.
- **FR-009**: 신고로 리뷰가 제외돼 한 페이지가 기준 개수보다 적게 채워져도, 개수를 맞추기 위한 재조회 없이 기존 페이지 규약(다음 페이지 여부·커서)을 유지해야 한다.
- **FR-010**: 이번 범위의 신고 대상은 리뷰만이다(커뮤니티 게시글 등은 대상 타입 값 추가로 후속 확장). 회원 신고, 신고 수 임계치에 따른 자동 숨김, 관리자 신고 검토는 이번 범위에 포함하지 않는다.

### Key Entities

- **신고**: 한 회원이 한 콘텐츠에 대해 접수한 신고 기록. 신고자, 대상 타입(이번 범위는 리뷰뿐, 향후 커뮤니티 게시글 등 확장), 대상 id, 사유 카테고리, 상세 설명(선택, 최대 500자), 접수 시각을 가진다. 같은 (신고자, 대상 타입, 대상 id) 조합은 한 건만 존재한다.
- **신고 대상 타입**: 신고 가능한 콘텐츠 종류의 고정 코드값. 이번 범위는 리뷰(REVIEW) 하나이며, 커뮤니티 게시글 등이 값 추가만으로 확장된다.
- **신고 사유 카테고리**: 스팸·광고 / 욕설·혐오 / 허위 정보 / 음란물 / 기타 5종의 고정 코드값.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자는 리뷰 신고를 사유 선택 한 번으로 완료할 수 있다(요청 1회, 추가 단계 없음).
- **SC-002**: 신고 완료 직후의 음식 리뷰 목록 재조회에서 신고한 리뷰가 100% 나타나지 않는다.
- **SC-003**: 신고하지 않은 회원의 리뷰 목록 조회 결과는 신고 전후가 100% 동일하다.
- **SC-004**: 같은 리뷰에 대한 재신고·동시 중복 신고는 100% 거절되고 저장된 신고는 1건을 유지한다.
- **SC-005**: 앱스토어 UGC 심사 요건 중 "부적절 콘텐츠 신고 수단 제공" 항목을 충족한다.

## Assumptions

- 리뷰 목록 경로는 현재 서비스 기준(음식 리뷰 목록 `GET /api/v1/reviews?foodId=`, 내 리뷰 목록 `GET /api/v1/reviews/me`)을 따른다. Jira 본문의 `GET /api/v1/foods/{foodId}/reviews`·`GET /api/v1/members/me/reviews` 는 개편(KB-263) 이전 경로다. 신고 접수는 신고 중심 독립 리소스 `POST /api/v1/reports` 로 노출한다(body: `targetType`·`targetId`·`reason`·`detail`) — 신고 대상이 커뮤니티 게시글로 확장될 예정이라 리뷰 하위 경로를 쓰지 않는다(Jira 본문의 `POST /reviews/{reviewId}/reports` 를 대체, Clarifications 참조). 이번 범위의 `targetType` 은 REVIEW 하나다.
- 신고 제외 필터는 음식 리뷰 목록에만 적용한다. 내 리뷰 목록은 자기 리뷰 신고가 불가능하므로 신고로 제외될 리뷰가 존재할 수 없다.
- 음식 상세의 평점 요약(평균·리뷰 수)은 신고 여부와 무관하게 전체 리뷰 기준을 유지한다 — 개인화 대상은 목록 노출뿐이다.
- 신고 기록은 향후 관리자 검토·자동 숨김 기능이 추가될 때 활용할 수 있도록 보관한다(취소·삭제 기능 없음).
- 선행 의존(KB-128 리뷰 CRUD, 인증 보호 경로)은 이미 서비스에 반영돼 있다. 리뷰 관련 경로는 모두 인증 필수다.
- 특정 회원에게만 콘텐츠를 숨기는 목록 제외 메커니즘은 이후 유저 차단 기능이 재사용할 수 있는 형태로 둔다(이번 범위는 신고 기반 제외만).
