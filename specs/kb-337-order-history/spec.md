# Feature Specification: 주문 내역·주문 음식 이력 저장

**Feature Branch**: `kb-337-order-history`

**Created**: 2026-08-20

**Status**: Draft

**Input**: User description: "337 워크트리 ㄱ" (Jira KB-337 — 주문 내역·주문 음식 이력 저장 기능)

## 맥락 (Jira KB-337·agent-hub·코드 현황)

- 현재 저장되는 이력은 **스캔 이력뿐**이다 — `scan_history` 가 스캔 추출 메뉴를 1건씩(메뉴명·한국어명·가격·foodId) 회원별로 저장하지만, "무엇을 **주문**했는지" 를 기록하는 저장소는 없다.
- **가격은 음식 마스터에 없고 스캔 경로에서만 존재**한다(KB-138 결정 — `scan_history.price` 가 유일한 가격 저장소). 따라서 주문 항목의 가격은 클라이언트가 스캔 결과에서 받아 온 값을 주문 시점에 함께 실어 보내 기록한다.
- 주문 이력이 쌓이면 회원의 취향·재주문 데이터로 활용할 수 있다(기획 피드백, 2026-08-15 멘토링 "주문 메뉴 저장" 안건).
- 음식 썸네일은 음식 마스터의 대표 이미지(`imageRef`)를 재사용한다 — 별도 썸네일 자산 없음.
- **주문의 위치는 식당 태그가 아니라 '주문하기'를 누른 순간의 위치**다(사용자 확정 2026-08-20 — 목업의 식당명 표기는 예시일 뿐). 클라이언트가 **GPS 좌표를 옵셔널로** 보내면 서버가 **도로명 주소로 역지오코딩해 좌표와 주소를 둘 다 저장**하고, 응답에는 **주소만** 노출한다(좌표 미노출). 위치 미동의 회원은 좌표 없이 주문하며 주소도 없다. 이로써 KB-351(주문 좌표 역지오코딩)의 내용이 이 기능에 흡수된다 — 공급자는 **Google Maps(Geocoding) API 로 확정**(사용자 확정 2026-08-20, KB-350 구글 전환과 일관).
- **주문 썸네일은 음식 마스터의 이미지를 표시 시점에 읽는다.** 미등록 음식은 이미지가 없으므로 기존 규칙(KB-343 — 없으면 기본 대체 이미지 URL 로 치환해 응답)을 그대로 재사용한다. **DB 의 음식 이미지 필드에 대체 이미지를 저장하지 않는다** — 이미지 유무가 이미지 생성 배치의 대상 선정 조건이라, 값을 채우면 실사진 생성이 영영 건너뛰어진다(2026-08-20 부작용 분석으로 확정).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔한 메뉴로 주문 내역 저장 (Priority: P1)

회원이 스캔 결과 화면에서 실제로 주문한 메뉴들을 수량과 함께 선택해 '주문하기' 하면, 주문 1건(주문 항목 N개)이 저장된다.

**Why this priority**: 이 기능의 뿌리 — 저장이 없으면 조회도 없다. 조회(US2·US3)와 독립으로 배포해도 데이터가 쌓이기 시작하는 가치가 있다.

**Independent Test**: 메뉴 2종(수량 1·2)으로 주문 저장 호출 → 성공 응답, 저장소에 주문 1건 + 항목 2건(각 가격·수량) 존재.

**Acceptance Scenarios**:

1. **Given** 로그인 회원과 스캔 결과의 메뉴 목록, **When** 메뉴 2종(각 수량·가격 포함)으로 주문을 저장하면, **Then** 주문 1건이 생성되고 각 항목에 메뉴명·수량·단가가 저장된다.
2. **Given** GPS 좌표를 함께 보낸 주문, **When** 저장하면, **Then** 좌표와 역지오코딩된 도로명 주소가 함께 저장된다. 좌표 없이 보내면 위치 정보 없이 저장된다(좌표는 옵셔널).
   - 역지오코딩이 실패해도 주문 저장은 성공한다 — **실패 로그를 남기고** 주소는 null 로 저장, 좌표만 남는다(위치는 부가 정보).
3. **Given** 항목이 0개인 주문 요청, **When** 저장을 시도하면, **Then** 거절된다(빈 주문 금지).
5. **Given** 이미 주문을 저장한 스캔, **When** 같은 스캔으로 다시 주문하면, **Then** 거절된다 — **스캔 1회당 주문 1회**(사용자 확정 2026-08-20). 더블탭 경합도 저장소 유일성 제약이 원자적으로 막는다.
4. **Given** 스캔 결과에 가격이 없던 메뉴(가격 미인식), **When** 그 메뉴를 포함해 주문하면, **Then** 해당 항목은 가격 없이 저장되고 주문은 성공한다.

---

### User Story 2 - 주문 내역 리스트 조회 (Priority: P2)

회원이 자신의 주문 내역을 최근 주문 순으로 본다. 각 주문 카드에는 주문 날짜, 주문한 음식 썸네일(최대 4개), 총 수량, 도로명 주소(있으면)가 보이고, 상단에 총 주문 수가 보인다. (총 그릇 수 합계는 표기하지 않는다 — 사용자 확정으로 제외.)

**Why this priority**: 저장된 데이터를 사용자에게 되돌려주는 첫 화면. US1 없이는 의미가 없어 P2.

**Independent Test**: 주문 3건 저장 후 리스트 조회 → 총 주문 수 3, 최근 순 정렬, 각 카드에 썸네일·총 수량·날짜.

**Acceptance Scenarios**:

1. **Given** 주문 3건을 가진 회원, **When** 리스트를 조회하면, **Then** 총 주문 수 3과 최근 주문 순 목록이 내려간다.
2. **Given** 음식 5종을 담은 주문, **When** 리스트를 조회하면, **Then** 그 주문 카드의 썸네일은 최대 4개까지만 내려간다.
3. **Given** 미등록 메뉴(음식 이미지 없음)를 포함한 주문, **When** 리스트를 조회하면, **Then** 해당 항목의 썸네일은 기본 대체 이미지 URL 로 내려간다 — 항목마다 음식 참조가 항상 있으므로 썸네일은 앞 4개 항목으로 그대로 채워진다.
4. **Given** 주문 날짜, **When** 응답을 확인하면, **Then** 날짜는 숫자 타임스탬프(밀리초, long)로 내려간다.
5. **Given** 주문이 없는 회원, **When** 조회하면, **Then** 총 주문 수 0·빈 목록으로 정상 응답한다.

---

### User Story 3 - 주문 상세 조회 (Priority: P3)

회원이 주문 카드를 눌러 그 주문의 메뉴별 내역(수량·가격)과 주문 총가격을 본다.

**Why this priority**: 리스트에서 한 단계 더 들어가는 화면 — US2 다음.

**Independent Test**: 항목 2개(1,000원×2 + 3,000원×1) 주문 상세 조회 → 항목별 수량·가격과 총가격 5,000원.

**Acceptance Scenarios**:

1. **Given** 저장된 주문, **When** 상세를 조회하면, **Then** 리스트 카드 정보 + 메뉴별 수량·단가 + 주문 총가격이 내려간다.
2. **Given** 가격 없는 항목이 섞인 주문, **When** 상세를 조회하면, **Then** 그 항목의 가격은 비어 있고 총가격은 가격이 있는 항목들의 합이다.
3. **Given** 남의 주문 id, **When** 상세를 조회하면, **Then** 접근이 거절된다(본인 주문만).
4. **Given** 존재하지 않는 주문 id, **When** 조회하면, **Then** 찾을 수 없음으로 거절된다.

---

### Edge Cases

- 같은 메뉴를 두 항목으로 나눠 보내면(중복 메뉴)? — 병합하지 않고 보낸 그대로 저장한다(클라이언트 화면 구성 그대로 보존).
- 수량이 0 이하인 항목? — 거절한다(항목 수량은 1 이상).
- 주문한 음식이 나중에 소프트 삭제되면? — 주문 항목은 저장 시점의 이름·가격 스냅샷을 자체 보유하므로 리스트·상세는 계속 정상이고, 썸네일만 기본 대체 이미지로 바뀔 수 있다.
- 주문 시점과 조회 시점의 음식 이미지가 다르면? — 썸네일은 조회 시점의 음식 대표 이미지를 따른다(이미지는 스냅샷하지 않음). 미등록 음식이 나중에 배치로 실사진을 얻으면 주문 썸네일도 자동으로 바뀐다.
- 역지오코딩 결과가 관할 밖(해외 좌표 등)이면? — 주소 없이 좌표만 저장하고 주문은 성공한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 회원은 **스캔 식별자(imagePath)** 와 메뉴 항목 목록(항목별 메뉴명·수량·음식 참조·선택적 가격), **선택적 GPS 좌표**로 **주문 1건을 저장**할 수 있어야 한다. 빈 항목 목록·0 이하 수량은 거절한다.
- **FR-001b**: **스캔 1회당 주문은 1회만** 저장할 수 있다 — 같은 스캔 식별자로 두 번째 저장은 거절한다. 이 유일성은 저장소 제약으로 강제한다(동시 요청 포함).
- **FR-001a**: 좌표가 오면 서버가 **Google Geocoding 으로 도로명 주소를 변환해 좌표·주소를 모두 저장**한다. 변환 실패는 주문 저장을 막지 않는다 — **실패 사유를 로그로 남기고 주소는 null 로 저장**(좌표는 유지). 응답에는 주소만 노출하고 좌표는 노출하지 않는다.
- **FR-002**: 주문 항목은 저장 시점의 **이름·가격 스냅샷을 자체 보유**한다 — 이후 음식 마스터가 바뀌어도 주문 내역의 표시 값은 변하지 않는다(썸네일 제외).
- **FR-003**: 회원은 자신의 **주문 리스트**를 조회할 수 있어야 한다 — 총 주문 수, 최근 주문 순, 주문별(썸네일 최대 4개·도로명 주소(옵셔널)·주문 날짜(밀리초 long)·총 수량). 총 그릇 수 합계는 제공하지 않는다.
- **FR-004**: 회원은 자신의 **주문 상세**를 조회할 수 있어야 한다 — 리스트 정보 + 메뉴별 수량·가격 + 주문 총가격(가격 있는 항목의 합).
- **FR-005**: 주문 조회는 **본인 것만** 가능하다. 타인 주문 접근은 거절한다.
- **FR-006**: 썸네일은 음식 마스터의 대표 이미지를 표시 시점에 읽고, 이미지가 없으면 **기본 대체 이미지 URL 로 치환해 응답**한다(KB-343 규칙 재사용). **음식 이미지 필드에 대체 이미지를 저장하는 방식은 금지** — 이미지 생성 배치의 대상 선정(이미지 부재 조건)을 깨뜨린다.
- **FR-007**: 신규 조회·저장 API 계약은 API 문서(swagger)에 노출한다.

### Key Entities

- **주문(Order)**: 회원의 1회 주문. 스캔 식별자(유일)·주문 날짜·선택적 위치(좌표 + 역지오코딩된 도로명 주소)를 가진다. 회원에 속한다. 좌표는 저장만 하고 응답에 노출하지 않는다.
- **주문 항목(OrderItem)**: 주문에 속한 메뉴 1종. 메뉴명(스냅샷)·수량·단가(스냅샷, 없을 수 있음)·음식 참조(필수 — 미등록 음식도 스캔 시점에 음식 저장소에 생성되므로 항상 존재)를 가진다.
- **스캔 이력과의 관계**: 주문 항목은 저장 시점 값을 스냅샷하며 스캔 이력 레코드(row)에 대한 참조는 없다. 단 주문은 **스캔 식별자(imagePath)** 를 유일값으로 보유한다 — "스캔 1회당 주문 1회" 강제와 출처 추적용.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 스캔 결과 화면에서 주문 저장까지 API 1회 호출로 완료된다(항목 수 무관).
- **SC-002**: 주문 리스트·상세 조회가 저장된 주문 100% 를 누락·왜곡 없이 반영한다(스냅샷 값 기준).
- **SC-003**: 음식 마스터 변경(이름·가격 정책·소프트 삭제) 후에도 기존 주문 내역의 이름·가격 표시가 변하지 않는다.
- **SC-004**: 주문 없는 회원·썸네일 없는 주문 등 빈 상태에서도 조회 오류율 0.

## Assumptions

- **역지오코딩이 이번 범위에 포함된다**(KB-351 흡수). 공급자는 **Google Geocoding API**(사용자 확정 2026-08-20) — 기존 Google 키 재사용 가능 여부(키의 API 제한에 Geocoding 추가)는 계획 단계에서 확인. 호출은 주문 저장 시 1회·트랜잭션 밖.
- **주문 수정·삭제는 범위 밖** — 이력 성격의 데이터라 저장·조회만 제공한다. 목업의 장소 편집(tag a place/edit)은 식당 태그 개념이었을 때의 것으로, 위치 = 주문 순간 좌표로 확정되며 사라졌다.
- 주문 날짜는 **저장 시점 서버 시각**이다(클라이언트가 보내지 않는다). 응답은 밀리초 epoch(long) — Jira DoD 명시.
- 리스트 조회는 **페이지 단위**로 내려간다(무한 스크롤 대응). 페이지 방식·크기는 기존 목록 API(리뷰 목록 등)의 관례를 따른다 — plan 에서 확정.
- 항목별 가격은 **원화 정수**(스캔 가격과 동일 단위). 통화 환산은 클라이언트 몫(KB-349 계약과 일관).
- 회원 전용 API — 게스트 접근 불가. 신규 경로는 JWT 보호 경로에 등록한다.

## Out of Scope

- 주문 수정·삭제·취소, 재주문 원클릭·장소(식당) 태깅
- 좌표의 응답 노출(저장만 한다)·지도 표시
- 공유 카드(9:16 스토리) 생성 — 클라이언트가 응답 데이터로 렌더링(서버 무관)
- 사용자 사진 업로드·교체(dish photo replace) — 썸네일은 음식 마스터 이미지로 고정
- 주문 기반 추천·통계(취향 분석은 데이터가 쌓인 뒤 별도 기능)
- 스캔 이력 레코드와의 참조 연결
