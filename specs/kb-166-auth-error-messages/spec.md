# Feature Specification: 인증 토큰 에러 메시지 문구 개선

**Feature Branch**: `kb-166-auth-error-messages`

**Created**: 2026-07-17

**Status**: Draft

**Input**: User description: "kb166 바로 시작 — [BE] 인증 토큰 에러 메시지 문구 개선 — 액세스/리프레시 용어 통일·다음 행동 안내"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 토큰 에러 메시지만 보고 다음 행동 파악 (Priority: P1)

앱 사용자(및 이를 다루는 클라이언트 개발자)가 인증 관련 에러를 만났을 때, 에러 메시지가 어떤 토큰(액세스/리프레시)이 왜(만료/무효) 거절됐고 다음에 무엇을 해야 하는지(토큰 갱신/재로그인)를 문장 자체로 알려준다. 현재는 "인증 토큰"·"갱신 토큰"이라는 용어가 액세스/리프레시 토큰과 즉시 매핑되지 않고 소셜 인증 토큰(AUTH-001)과도 어휘가 겹치며, 다음 행동 안내도 없다.

**Why this priority**: 이 스토리가 기능의 전부 — 표시용 메시지 4건의 문구 개선.

**Independent Test**: 각 인증 에러 상황을 재현해 응답 `message` 가 새 문구인지, `code`·HTTP 상태가 기존과 동일한지 확인하면 완결적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 위조/형식 오류 액세스 토큰, **When** 보호 API 를 호출하면, **Then** `AUTH-003` + "유효하지 않은 액세스 토큰입니다. 다시 로그인해 주세요" 를 받는다.
2. **Given** 만료된 액세스 토큰, **When** 보호 API 를 호출하면, **Then** `AUTH-004` + "만료된 액세스 토큰입니다. 토큰을 갱신해 주세요" 를 받는다.
3. **Given** 위조/이미 사용된 리프레시 토큰, **When** 토큰 갱신을 요청하면, **Then** `AUTH-005` + "유효하지 않은 리프레시 토큰입니다. 다시 로그인해 주세요" 를 받는다.
4. **Given** 만료된 리프레시 토큰, **When** 토큰 갱신을 요청하면, **Then** `AUTH-006` + "만료된 리프레시 토큰입니다. 다시 로그인해 주세요" 를 받는다.
5. **Given** 기존 클라이언트, **When** 위 에러들을 받으면, **Then** 분기 기준인 `code`(AUTH-003~006)와 HTTP 상태(401)가 변하지 않아 기존 동작(자동 토큰 갱신·재로그인 유도)이 그대로 동작한다.

---

### Edge Cases

- 클라이언트는 `message` 매칭이 금지돼 있고(`code` 로만 분기하는 규약) 이번 변경은 `message` 만 손대므로 비파괴다 — `code`·`status` 가 하나라도 바뀌면 회귀.
- 소셜 인증 토큰 에러(AUTH-001 "유효하지 않은 소셜 인증 토큰입니다")는 범위 밖 — 변경하지 않지만, 개선 후 "액세스/리프레시" 용어와 더 이상 겹치지 않아 구분이 명확해진다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: AUTH-003 메시지는 "유효하지 않은 액세스 토큰입니다. 다시 로그인해 주세요" 여야 한다.
- **FR-002**: AUTH-004 메시지는 "만료된 액세스 토큰입니다. 토큰을 갱신해 주세요" 여야 한다.
- **FR-003**: AUTH-005 메시지는 "유효하지 않은 리프레시 토큰입니다. 다시 로그인해 주세요" 여야 한다.
- **FR-004**: AUTH-006 메시지는 "만료된 리프레시 토큰입니다. 다시 로그인해 주세요" 여야 한다.
- **FR-005**: 네 에러의 `code` 식별자와 HTTP 상태(401)는 변경되지 않아야 한다.

### Key Entities

- **에러 코드(ErrorCode)**: 코드(클라이언트 분기용 안정 식별자)·HTTP 상태·표시용 메시지의 삼요소. 이번 변경은 인증 계열 4건(AUTH-003~006)의 메시지 요소만 대상.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 인증 토큰 에러 4종의 메시지가 토큰 종류(액세스/리프레시)·상태(만료/무효)·다음 행동(갱신/재로그인)을 모두 담는다 — 4건 중 4건.
- **SC-002**: 기존 클라이언트의 에러 분기(`code` 기반) 회귀 0건 — code·상태 변경 0건.
- **SC-003**: 에러 코드표만 읽고 클라이언트 개발자가 각 코드의 대응 행동을 추가 문의 없이 파악할 수 있다.

## Assumptions

- 문구는 KB-166 DoD 에 확정된 4문장을 그대로 쓴다 (재협의 없음).
- 메시지에 하드 의존하는 테스트가 있으면 새 문구로 함께 갱신한다 — 클라이언트는 message 매칭 금지 규약이라 외부 영향 없음.
- AUTH-001·002·007 등 나머지 인증 에러와 타 도메인 에러 메시지는 범위 밖.
- 국제화(i18n)·다국어 메시지는 범위 밖 — 현행 한국어 단일 메시지 체계 유지.
