# Feature Specification: 주문 상세 응답에 메뉴판 사진 필드 추가

**Feature Branch**: `kb-376-order-detail-scan-image`

**Created**: 2026-08-25

**Status**: Draft

**Input**: User description: 주문 상세(`GET /api/orders/{id}`) 응답에 목록에는 있는 `scanImageUrl`(주문 시점 스캔한 메뉴판 사진)이 빠져 있어 FE가 주문 상세에서 메뉴판 사진을 못 그린다. 목록과 동일한 값(같은 URL)을 상세에도 실어 달라.

## Context & Decision

- **누락은 실수다(의도적 제외 아님).** 주문 목록 응답에는 `scanImageUrl`(주문 시점 스캔한 메뉴판 사진)이 이미 실려 있고, 주문 상세 응답에는 같은 값이 빠져 있다. 목록·상세 모두 같은 주문 데이터에서 나오며 상세 응답을 만들 때 이 값의 원본이 이미 손에 있으므로, 상세만 이 필드를 뺄 근거가 없다.
- 따라서 FE 우회(목록 값을 상세로 넘겨 그리기)는 불필요하며, 상세 응답에 목록과 **동일한 의미·동일한 값**의 필드를 그대로 추가한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 주문 상세에서 메뉴판 사진 보기 (Priority: P1)

사용자가 주문 내역에서 특정 주문을 눌러 상세 화면에 들어가면, 그 주문을 만들 때 스캔했던 메뉴판 사진이 함께 표시된다. 지금은 상세 응답에 사진 URL 자체가 없어 항상 사진이 안 뜬다.

**Why this priority**: 이 기능의 유일한 목적이자 전부다. 필드가 없으면 상세 화면의 메뉴판 사진은 어떤 경우에도 표시되지 못한다.

**Independent Test**: 주문 하나를 만든 뒤 그 주문의 상세를 조회해, 응답에 목록 응답과 동일한 메뉴판 사진 URL이 담겨 오는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 어떤 회원이 스캔을 거쳐 만든 주문이 있고, **When** 그 회원이 해당 주문의 상세를 조회하면, **Then** 응답에 그 주문의 메뉴판 사진 URL이 포함된다.
2. **Given** 같은 주문에 대해, **When** 목록 조회와 상세 조회를 각각 수행하면, **Then** 두 응답의 메뉴판 사진 URL 값이 서로 같다.
3. **Given** 상세 응답의 기존 필드들(주문 식별자·주문 시각·도로명 주소·총 수량·총가격·메뉴별 내역)이 있는 상태에서, **When** 이 변경을 적용하면, **Then** 기존 필드는 이름·의미·값이 그대로 유지되고 메뉴판 사진 URL 필드만 새로 추가된다.

---

### Edge Cases

- **도로명 주소는 미동의·변환 실패 시 없을 수 있으나(기존 계약), 메뉴판 사진은 주문이 스캔을 전제로 생성되므로 항상 존재한다** — 목록 응답이 이미 이 값을 "반드시 있는 값"으로 다루고 있으므로, 상세도 동일하게 항상 채워진 값으로 취급한다. 별도의 "없음" 표현은 두지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 주문 상세 응답은 그 주문의 "주문 시점 스캔한 메뉴판 사진" URL을 포함해야 한다.
- **FR-002**: 상세 응답의 이 사진 URL은 같은 주문의 목록 응답이 제공하는 사진 URL과 의미가 같고 값이 동일해야 한다.
- **FR-003**: 이 필드는 목록 응답과 동일하게 "항상 존재하는 값"으로 제공되어야 한다(없음 상태를 별도로 표현하지 않는다).
- **FR-004**: 기존 상세 응답 필드(주문 식별자·주문 시각·도로명 주소·총 수량·총가격·메뉴별 내역)의 이름·의미·값은 이 변경으로 달라지지 않아야 한다.
- **FR-005**: 목록 응답의 계약(필드 구성·의미)은 이 변경으로 달라지지 않아야 한다.

### Key Entities *(include if feature involves data)*

- **주문(Order)**: 회원이 스캔을 거쳐 생성한 주문. 주문 시점의 메뉴판 사진을 가리키는 정보를 보유하며, 이 정보로부터 목록·상세 양쪽의 사진 URL이 만들어진다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 주문 상세를 조회하면 100%의 경우에 메뉴판 사진 URL이 응답에 포함된다(주문이 존재하는 한 누락 0건).
- **SC-002**: 같은 주문에 대해 목록과 상세가 반환하는 메뉴판 사진 URL이 100% 일치한다.
- **SC-003**: FE는 이 변경 이후 추가 코드 없이(기존 조건부 렌더 로직 그대로) 주문 상세에서 메뉴판 사진을 표시할 수 있다.
- **SC-004**: 기존 상세·목록 응답을 소비하던 클라이언트가 이 변경으로 깨지지 않는다(기존 필드 회귀 0건).

## Assumptions

- 이 변경은 백엔드 응답 계약에 필드를 **추가**하는 것으로, 기존 필드 제거·이름 변경·의미 변경은 없다(하위 호환).
- dev 기준 실측이며 prod 계약도 동일하다고 본다 — 별도 prod 전용 작업 없이 다음 배포에 함께 반영되면 충분하다(급하지 않음).
- 목록 응답이 이미 이 사진 URL을 "반드시 존재하는 값"으로 제공하고 있으므로, 상세도 같은 성질(항상 존재)로 맞춘다. 목록과 상세가 서로 다른 null 허용 규칙을 갖지 않는다.
- 이 사진 URL을 만드는 데 필요한 원본 정보는 상세 응답을 조립하는 시점에 이미 확보되어 있어, 추가적인 외부 조회나 별도 저장이 필요하지 않다.
