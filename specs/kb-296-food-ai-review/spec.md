# Feature Specification: 음식 AI 검수 파이프라인 연동 준비

**Feature Branch**: `kb-296-food-ai-review`

**Created**: 2026-08-04

**Status**: Draft

**Input**: KB-296 — 음식 콘텐츠 AI 검수 파이프라인을 도입한다. 검수 배치는 별도 레포(kbap-langchain, LangGraph CLI)가 홈서버에서 실행하며 DB 직접 접근 없이 kbap 어드민 API로만 읽고 쓴다. 이 태스크는 스프링(kbap) 측 선행 작업만 다룬다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 검수 대상 음식 목록 받아가기 (Priority: P1)

외부 AI 검수 파이프라인이 "지금 검수할 음식"을 한 번의 호출로 받아간다. 응답에는 검수 판단에 필요한 콘텐츠 필드(한국어명·설명·이름 번역·설명 번역·기피 물질·매움 정도·이미지)가 모두 들어 있어, 파이프라인이 추가 조회 없이 각 노드에서 기준치를 판정할 수 있다.

**Why this priority**: 검수 결과를 되돌려 보내려면 대상을 먼저 받아야 한다. 이 스토리만 있어도 파이프라인이 오프라인으로 품질을 계측·리포팅하는 가치가 나온다.

**Independent Test**: PENDING_REVIEW 음식 몇 건과 다른 상태 음식을 섞어 두고 조회 API를 호출해, PENDING_REVIEW 건만 콘텐츠 필드 전부와 함께 반환되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** PENDING_REVIEW 음식 3건과 INCOMPLETE·READY 음식이 섞여 있을 때, **When** 검수 대상 조회를 호출하면, **Then** PENDING_REVIEW 3건만 반환된다.
2. **Given** 검수 대상이 반환될 때, **When** 응답을 확인하면, **Then** 각 항목에 음식 식별자·한국어명·설명·이름 번역·설명 번역·기피 물질·매움 정도·이미지 참조·현재 검수 시도 횟수가 포함된다.
3. **Given** PENDING_REVIEW 음식이 한 건도 없을 때, **When** 조회를 호출하면, **Then** 빈 목록으로 성공 응답한다.
4. **Given** 대상이 요청한 최대 건수보다 많을 때, **When** 조회를 호출하면, **Then** 지정한 건수까지만 반환된다.

---

### User Story 2 - 검수 통과 결과 반영 (Priority: P1)

파이프라인이 모든 판정 노드를 통과시킨 음식에 대해 "통과"를 알리면, 서버가 상태를 REVIEWED로 올리고 사람 승인 대기열에 남긴다.

**Why this priority**: 검수 결과가 되돌아오지 않으면 대상이 영원히 PENDING_REVIEW에 머무른다. 통과 경로가 파이프라인 왕복의 최소 단위다.

**Independent Test**: PENDING_REVIEW 음식에 통과 결과를 반영하고 상태가 REVIEWED로 바뀌는지, 콘텐츠 필드는 그대로인지 확인한다.

**Acceptance Scenarios**:

1. **Given** PENDING_REVIEW 음식이 있을 때, **When** 통과 결과를 반영하면, **Then** 상태가 REVIEWED가 되고 콘텐츠 필드·검수 시도 횟수는 변하지 않는다.
2. **Given** 이미 REVIEWED인 음식에, **When** 다시 통과 결과를 반영하면, **Then** 상태 변화 없이 성공 응답한다(멱등).
3. **Given** 존재하지 않는 음식 식별자로, **When** 결과를 반영하면, **Then** 음식 없음 오류 코드로 실패한다.

---

### User Story 3 - 검수 탈락 결과 반영과 재시도 롤백 (Priority: P1)

파이프라인의 최종 판단 노드가 기준을 못 넘긴 필드를 지목해 "탈락"을 알리면, 서버가 재시도 여력에 따라 두 갈래로 처리한다. 여력이 있으면 지목된 필드만 비우고 INCOMPLETE로 되돌려 콘텐츠 채움 배치가 그 필드만 다시 생성하게 하고, 여력이 없으면 값을 그대로 둔 채 REVIEW_REJECTED로 보내 사람이 직접 판단하게 한다.

**Why this priority**: 자동 재생성 루프가 이 기능의 본질이다. 여기가 없으면 AI 검수는 통과/보류만 가능한 반쪽이다.

**Independent Test**: 검수 시도 횟수가 0인 음식과 2인 음식에 각각 같은 탈락 결과를 반영해, 앞은 필드 초기화+INCOMPLETE+시도 1, 뒤는 값 유지+REVIEW_REJECTED+사유 저장으로 갈리는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검수 시도 횟수 0인 PENDING_REVIEW 음식에 설명·설명 번역이 문제로 지목될 때, **When** 탈락 결과를 반영하면, **Then** 그 두 필드만 미채움 상태로 되돌아가고 나머지 필드는 유지되며 상태는 INCOMPLETE, 시도 횟수는 1이 된다.
2. **Given** 검수 시도 횟수 1인 음식이 다시 탈락할 때, **When** 결과를 반영하면, **Then** 시도 횟수가 2가 되고 상태는 INCOMPLETE로 롤백된다.
3. **Given** 검수 시도 횟수가 이미 2인 음식이 탈락할 때, **When** 결과를 반영하면, **Then** 어떤 콘텐츠 필드도 비워지지 않고 상태가 REVIEW_REJECTED가 되며 탈락 사유가 저장된다.
4. **Given** 이미지가 문제로 지목되고 재시도 여력이 있을 때, **When** 결과를 반영하면, **Then** 이미지 참조가 비워지고 나머지 텍스트 콘텐츠가 온전하면 상태는 PENDING_IMAGE가 된다.
5. **Given** 탈락 사유가 10줄 또는 1000자를 넘을 때, **When** 결과를 반영하면, **Then** 한도까지만 잘려 저장된다.
6. **Given** 탈락으로 INCOMPLETE·PENDING_IMAGE로 롤백된 음식을, **When** 콘텐츠 채움 배치가 다시 채우면, **Then** 정상적으로 PENDING_REVIEW까지 재진입한다.
7. **Given** REVIEWED·REVIEW_REJECTED 상태의 음식을, **When** 콘텐츠 채움 배치가 훑으면, **Then** 상태가 임의로 되돌려지지 않는다.

---

### Edge Cases

- 탈락인데 문제 필드가 하나도 지목되지 않으면? → 요청 검증 실패로 거절한다(무엇을 비울지 서버가 추측하지 않는다).
- 통과인데 문제 필드나 사유가 함께 오면? → 무시하고 통과로 처리한다.
- PENDING_REVIEW가 아닌 상태(INCOMPLETE 등)에 검수 결과가 오면? → 잘못된 상태 전이로 거절한다.
- 같은 음식에 같은 탈락 결과가 중복 도착하면? → 각 호출이 시도 횟수를 올린다. 파이프라인이 재전송을 삼가는 것을 전제로 한다.
- 소프트 삭제된 음식은? → 조회 대상에서 빠지고, 결과 반영 시 음식 없음으로 거절된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 음식 콘텐츠 상태에 `REVIEWED`(AI 검수 통과, 사람 승인 대기)와 `REVIEW_REJECTED`(재시도 소진 후 탈락, 사람 판단 필요) 두 값이 추가되어야 한다.
- **FR-002**: 음식은 AI 검수 시도 횟수를 0부터 누적 보관해야 하며, 기존 음식은 0으로 시작한다.
- **FR-003**: 음식은 최종 탈락 사유를 최대 10줄·1000자까지 보관해야 하며, 넘치는 입력은 잘라서 보관한다(저장 실패로 검수 결과를 잃지 않는다).
- **FR-004**: 관리자는 검수 대상(PENDING_REVIEW) 음식 목록을, 검수 판단에 필요한 콘텐츠 필드 전부와 함께 조회할 수 있어야 한다.
- **FR-005**: 검수 대상 조회는 한 번에 가져갈 최대 건수를 지정할 수 있어야 하며, 지정하지 않으면 기본 상한을 적용한다.
- **FR-006**: 관리자는 음식 한 건에 대한 검수 결과(통과 여부, 문제 필드 목록, 탈락 사유)를 반영할 수 있어야 한다.
- **FR-007**: 통과 결과는 상태를 `REVIEWED`로 전이시키고 콘텐츠 필드와 시도 횟수를 변경하지 않아야 한다.
- **FR-008**: 탈락 결과는 시도 횟수가 2 미만이면 지목된 필드만 미채움 상태로 되돌리고 시도 횟수를 1 증가시킨 뒤, 남은 콘텐츠 완성도에 따라 `INCOMPLETE` 또는 `PENDING_IMAGE`로 전이시켜야 한다.
- **FR-009**: 탈락 결과는 시도 횟수가 2 이상이면 콘텐츠 필드를 그대로 둔 채 `REVIEW_REJECTED`로 전이시키고 탈락 사유를 저장해야 한다.
- **FR-010**: 지목 가능한 문제 필드는 설명·이름 번역·설명 번역·기피 물질·매움 정도·이미지로 한정되며, 알 수 없는 필드 값은 요청 검증 실패로 거절해야 한다.
- **FR-011**: 탈락 결과에 문제 필드가 하나도 없으면 요청 검증 실패로 거절해야 한다.
- **FR-012**: 검수 대상이 아닌 상태의 음식에 결과를 반영하면 거절해야 한다. 단 통과 결과를 이미 `REVIEWED`인 음식에 반영하는 것은 성공으로 취급한다.
- **FR-013**: 콘텐츠 채움 배치는 `REVIEWED`·`REVIEW_REJECTED` 상태의 음식 상태를 임의로 되돌리지 않아야 한다.
- **FR-014**: 두 API는 기존 어드민 API와 동일한 인가(ADMIN 역할 토큰)로 보호되어야 하며, 일반 사용자 토큰은 거절된다.
- **FR-015**: 기존 저장 데이터의 상태·의미는 이번 변경으로 달라지지 않아야 한다(무중단 확장).

### Key Entities

- **음식(Food)**: 검수 대상. 콘텐츠 상태, AI 검수 시도 횟수, 최종 탈락 사유를 함께 보유한다.
- **콘텐츠 상태(FoodContentStatus)**: `INCOMPLETE` → `PENDING_IMAGE` → `PENDING_REVIEW` → `REVIEWED` → `READY`(사람 승인). 탈락 시 재시도 여력에 따라 앞단으로 롤백하거나 `REVIEW_REJECTED`로 빠진다.
- **검수 결과**: 통과 여부, 문제 필드 목록, 탈락 사유로 구성되는 외부 파이프라인의 판정.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 외부 검수 파이프라인이 DB에 직접 접근하지 않고 두 번의 API 호출(대상 조회 → 결과 반영)만으로 한 음식의 검수 왕복을 완결한다.
- **SC-002**: 검수 탈락 음식 중 재시도 여력이 있는 건은 100% 자동으로 콘텐츠 재생성 대기열(`INCOMPLETE`/`PENDING_IMAGE`)로 되돌아간다.
- **SC-003**: 같은 음식이 자동 재생성 루프를 3회를 넘겨 돌지 않는다(최초 검수 + 재시도 2회).
- **SC-004**: 사람이 직접 봐야 하는 음식은 `REVIEW_REJECTED` 하나로만 모여, 검수 실패 원인 확인에 다른 화면·조회가 필요 없다.
- **SC-005**: 기존에 저장된 음식 데이터가 이번 변경 이후에도 동일한 상태·콘텐츠로 조회된다.

## Assumptions

- 재시도 한도는 2회로 고정한다(설정값으로 빼지 않는다). 운영하며 조정이 필요해지면 별도 태스크로 뺀다.
- 문제 필드 판정은 전적으로 외부 파이프라인 몫이다. 서버는 지목받은 필드를 비울 뿐, 자체 품질 판정을 하지 않는다.
- 검수 결과 반영은 음식 1건 단위다. 일괄 반영은 필요해질 때 추가한다.
- 검수 대상 조회는 정렬·커서 없이 상한 건수만 받는다. 파이프라인이 처리한 건은 상태가 바뀌어 대상에서 빠지므로 페이징이 필요 없다.
- 어드민 화면의 승인 큐를 `REVIEWED` 기준으로 바꾸는 작업은 이번 범위 밖이다(후속 태스크). 이번 태스크 이후 화면은 여전히 `PENDING_REVIEW`만 보므로, AI 파이프라인이 실제로 붙기 전까지 상태 전이는 기존과 동일하게 흐른다.
- 탈락 사유는 사람이 읽는 자유 텍스트이며 기계 파싱 대상이 아니다.
- 외부 파이프라인(kbap-langchain)의 노드 구성·모델 선택·실행 스케줄은 이 스펙 범위 밖이다.
