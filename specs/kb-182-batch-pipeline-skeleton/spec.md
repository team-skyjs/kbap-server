## User Scenarios & Testing *(mandatory)*

### User Story 1 - 음식 READY 전이 규칙 (Priority: P1)

서비스 운영 관점에서, 음식은 콘텐츠 4작업(사진·설명·이름 번역·기피성분 매핑)이 **모두** 완료됐을 때만 사용자에게 노출 가능한 READY 상태가 된다. 하나라도 비어 있으면 INCOMPLETE 로 남아 사용자에게 불완전한 정보(특히 기피성분 공백 — 안전 직결)가 노출되지 않는다.

**Why this priority**: 파이프라인의 존재 이유가 "완성된 음식만 노출"이라는 안전 보장이다. 이 규칙이 없으면 나머지 골격은 의미가 없다.

**Independent Test**: 콘텐츠 필드 조합(전부 채움 / 하나씩 비움)별로 전이 시도를 수행해, 전부 채워진 경우에만 READY 가 되는지 단위 수준에서 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사진·설명(원문+번역)·이름 번역·기피성분 매핑이 모두 채워진 INCOMPLETE 음식, **When** 전이를 시도하면, **Then** READY 로 전이된다.
2. **Given** 4작업 중 하나라도 비어 있는 INCOMPLETE 음식, **When** 전이를 시도하면, **Then** INCOMPLETE 로 남는다.
3. **Given** 이미 READY 인 음식, **When** 전이를 다시 시도하면, **Then** 상태가 변하지 않고 오류도 발생하지 않는다(멱등).

### User Story 2 - 음식 단위 처리 러너 골격 (Priority: P1)

배치 실행 시 INCOMPLETE 음식을 일정 건수씩 가져와 **음식 1건 단위**로 처리한다. 한 음식에 대해 필요한 작업을 한 번에 수행하고, 완료되면 그 자리에서 READY 전이를 시도한다. 특정 음식 처리가 실패해도 그 실패는 해당 음식 1건에 격리되고, 같은 청크의 다른 음식 처리는 계속된다.

**Why this priority**: 후속 태스크(이름 번역·설명 KB-183, 사진 KB-184, 기피성분 KB-209)가 전부 이 골격에 스텝으로 꽂힌다. 실패 격리 구조가 없으면 1건 실패가 배치 전체를 무너뜨린다.

**Independent Test**: 처리 스텝을 페이크로 대체해, N건 중 1건이 실패하는 시나리오에서 나머지 (N-1)건이 정상 처리·전이되고 실패 건만 INCOMPLETE 로 남는지 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** INCOMPLETE 음식 여러 건, **When** 배치를 실행하면, **Then** 설정된 청크 크기만큼 조회되어 1건씩 순서대로 처리된다.
2. **Given** 청크 내 특정 음식의 작업이 실패, **When** 배치가 계속 실행되면, **Then** 실패 음식은 INCOMPLETE 로 남고 나머지 음식은 정상 처리·전이된다.
3. **Given** 청크 크기 설정값 변경, **When** 배치를 재실행하면, **Then** 코드 수정 없이 변경된 건수로 조회된다.

---

### User Story 3 - 레거시 배치 코드 제거 (Priority: P2)

개발자 관점에서, 초기 개발 중 중단된 회피성분 스코어링 배치와 research 도메인 모듈(3모델 앙상블·합의 집계 등 현재 요구에 맞지 않는 추상화)을 걷어낸다. 제거 후에도 전체 빌드·테스트는 그린을 유지한다.

**Why this priority**: 새 골격을 레거시 위에 얹으면 두 구조가 공존해 혼란을 만든다. 다만 제거 자체는 사용자 가치가 아니라 골격 작업의 전제 정리다.

**Independent Test**: 제거 커밋 후 전체 빌드·테스트가 통과하고, 배치 앱이 정상 부팅되는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 구 스코어링 배치·research 모듈 코드가 존재하는 상태, **When** 재사용하지 않는 코드를 제거하면, **Then** 전체 빌드와 테스트가 통과한다.
2. **Given** 제거 완료 상태, **When** 배치 앱을 실행하면, **Then** 정상 부팅된다.

---

### Edge Cases

- INCOMPLETE 대상이 0건일 때 배치를 실행하면? → 아무 것도 처리하지 않고 정상 종료한다.
- 일부 작업만 완료된 음식(예: 설명만 채워짐)이 다음 실행에서 다시 조회되면? → 남은 작업을 마저 수행할 수 있어야 하며, 전이 규칙이 미완성 노출을 막는다.
- 처리 도중 배치가 중단되면? → 완료·전이된 음식은 READY 로 유지되고, 미처리 음식은 INCOMPLETE 로 남아 다음 실행에서 재처리된다.
- 청크 크기 설정이 없으면? → 합리적 기본값으로 동작한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 콘텐츠 4작업 산출물(사진, 설명 원문·번역, 이름 번역, 기피성분 매핑)이 **모두** 존재할 때만 음식을 READY 로 전이해야 한다.
- **FR-002**: 4작업 중 하나라도 미완성인 음식은 전이 시도 후에도 INCOMPLETE 로 남아야 한다.
- **FR-003**: READY 전이 판정 규칙은 도메인(음식 모델)이 소유해야 하며, 배치 실행 코드가 판정 로직을 중복 보유하지 않아야 한다.
- **FR-004**: 배치는 INCOMPLETE 상태 음식을 설정된 청크 크기만큼 조회하는 단일 창구를 가져야 한다.
- **FR-005**: 배치는 음식 1건 단위로 처리→전이를 수행해야 하며, 1건의 실패가 다른 음식의 처리·전이에 영향을 주지 않아야 한다.
- **FR-006**: 청크 크기는 코드 수정 없이 조정 가능한 외부 설정값이어야 하며, 미설정 시 기본값으로 동작해야 한다.
- **FR-007**: 구 회피성분 스코어링 배치와 research 모듈에서 재사용하지 않는 코드는 제거되어야 하고, 제거 후 전체 빌드·테스트가 통과해야 한다.
- **FR-008**: 골격은 후속 4작업 스텝(이름 번역·설명 생성, 사진 생성, 기피성분 매핑)이 개별 태스크로 꽂힐 자리를 제공해야 한다(이번 범위에서 실제 스텝 구현은 제외).

### Key Entities

- **음식(Food)**: 콘텐츠 상태(INCOMPLETE/READY)를 가지며, 사진 참조·설명(원문+번역)·이름 번역·기피성분 매핑의 완성 여부로 READY 전이 가능 여부가 판정된다.
- **기피성분 매핑**: 음식과 기피성분 카탈로그의 연결. 존재 여부가 READY 전이의 필수 조건 중 하나다(상세 구현은 KB-209).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 4작업이 모두 완료되지 않은 음식이 READY 로 전이되는 사례가 0건이다(필드 조합 전수 테스트로 검증).
- **SC-002**: 청크 내 1건이 실패하는 시나리오에서 나머지 건의 처리·전이 성공률이 100%다.
- **SC-003**: 레거시 제거 후 전체 빌드·테스트가 통과하고 배치 앱이 정상 부팅된다.
- **SC-004**: 청크 크기 변경이 코드 수정·재빌드 없이 설정만으로 반영된다.
- **SC-005**: 후속 스텝 태스크(KB-183·184·209)가 골격 코드 구조 변경 없이 각자의 스텝 구현만 추가하면 되는 상태다.

## Assumptions

- READY 전이에 필요한 콘텐츠는 사진 참조, 설명(원문+대상 언어 번역), 이름 번역, 기피성분 매핑 4종이다(KB-182 본문 기준 — 기피성분 스텝 구현은 KB-209).
- 이번 범위는 골격(정리·조회 창구·전이 규칙·러너·청크 설정)까지이며, 실제 콘텐츠 생성 스텝(LLM 호출·사진 생성)은 후속 태스크(KB-183·184·209) 범위다. 골격 검증은 페이크 스텝으로 수행한다.
- 청크 크기 기본값은 운영 중 조정을 전제로 한 임시값이며, 최적값 산정은 범위 밖이다.
- 신규 INCOMPLETE 음식의 적재(외국인 인기 메뉴 선정)는 KB-186 범위로, 이 골격은 이미 존재하는 INCOMPLETE 음식을 입력으로 가정한다.
- 배치 실행 스케줄(주기·트리거)은 범위 밖이며, 수동 실행 기준으로 검증한다.
