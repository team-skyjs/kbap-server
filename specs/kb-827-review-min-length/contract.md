# KB-827 리뷰 본문 최소 10자 — API 계약

대상: `POST /api/reviews`(작성), `PATCH /api/reviews/{reviewId}`(수정). 버전 헤더 무관(전 버전 동일 규칙).

> **운영 릴리스 순서 제약 (R-98 공부 세션 결정 (a))**: 서버 운영 배포는 앱 PR #304(KB-828 — 본문 카운터·REVIEW-005 처리)가 **production OTA로 나간 뒤**(ota-prod-2026102x 포함)에 한다. 구버전 앱은 본문 없는/짧은 리뷰를 보내면 400 을 받는다. 버전 게이트(헤더 버전별 규칙)는 두지 않는다. develop 머지·dev 배포는 순서 제약 없음.

## 규칙

- 본문(`content`)은 **필수**다. 판정은 `content.trim()` 의 **유니코드 코드 포인트 수 ≥ 10**.
  - 이모지 한 개(서로게이트 쌍, UTF-16 2단위)는 1자로 센다. 결합 문자(예: 피부색 수식자)는 각각 1자다.
  - 앞뒤 공백은 세지 않는다. 가운데 공백은 센다.
- 상한은 기존대로 1000자(Bean Validation `@Size` — **UTF-16 단위** 기준이라 이모지는 2자로 센다. 하한(코드 포인트)과 세는 단위가 다르다는 점을 클라 카운터가 알아야 한다. 초과는 기존 400 COMMON 검증 실패 그대로).
- 스키마상 `content` 는 required 지만 Kotlin 필드는 nullable 로 둔다 — 누락을 Bean Validation 공통 오류가 아니라 같은 REVIEW-005 로 돌려주기 위해서다.
- trim 은 Kotlin `trim()`(유니코드 공백) 기준이다. BOM(U+FEFF)·제로폭 문자는 공백이 아니라 글자로 센다(알려진 한계 — 클라 입력에서 거의 안 나옴).
- 사진·별점만 있는 리뷰는 더 이상 만들 수 없다(정책 변경).
- 저장 값은 보낸 원문 그대로다(trim 해서 저장하지 않는다).

## 실패 응답

| 경우 | HTTP | code | payload |
|---|---|---|---|
| `content` 없음·`""`·공백만·trim 후 10자 미만 | 400 | `REVIEW-005` | `{"minLength": 10}` |

메시지(표시용, 분기 금지): "리뷰 본문은 10자 이상이어야 해요".

판정 순서: 작성은 음식 존재(FOOD-001)·사진 소유(REVIEW-003) 다음, 수정은 리뷰 존재(REVIEW-001)·본인(REVIEW-002) 다음 사진 소유 전에 본문을 본다. 실패하면 리뷰·카운터·랭킹 이벤트 모두 바뀌지 않는다.

## 영향 없음

- 기존 리뷰(본문 없음·10자 미만 포함)는 그대로 남고 조회 응답도 같다. 수정할 때만 새 규칙을 탄다.
- 리뷰 봇: 생성물 필터(`ReviewBotContentGuard`)가 20자 미만에 더해 trim 후 코드 포인트 10자 미만도 버려 재생성(최대 2회)한다. 재생성까지 못 미치면 그 건을 건너뛴다(카운터 불변). 저장 단계 검사는 같은 규칙의 마지막 방어선이다.
