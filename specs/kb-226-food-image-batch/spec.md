## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자 이미지 일괄 제출 (Priority: P1)

관리자가 이미지가 준비되지 않은 음식들을 한 번의 요청으로 외부 이미지 생성 서비스에 일괄 제출한다. 제출 요청은 생성 완료를 기다리지 않고 즉시 응답하며, 제출 이력은 시스템 내부 메타 테이블에 기록된다.

**Why this priority**: 제출이 없으면 회수할 것도 없다. 비동기 구조의 시작점이며, 이것만 있어도 "제출됨" 상태 확인이라는 최소 가치를 준다.

**Independent Test**: 이미지 없는 음식 N건이 있는 상태에서 관리자 제출을 호출하면, 생성 서비스에 배치가 만들어지고 메타 테이블에 SUBMITTED 배치와 PENDING 항목이 기록되는지 페이크 클라이언트로 검증.

**Acceptance Scenarios**:

1. **Given** 이미지가 없는 음식 25건, **When** 관리자가 일괄 제출을 호출하면, **Then** 음식이 배치 단위로 분할 제출되고 각 배치·항목이 메타 테이블에 SUBMITTED/PENDING으로 기록되며 응답은 생성 완료를 기다리지 않는다
2. **Given** 진행 중 배치에 이미 포함된 음식, **When** 관리자가 제출을 다시 호출하면, **Then** 해당 음식은 제출 대상에서 제외된다 (중복 제출 없음)
3. **Given** 이미지가 필요한 음식이 0건, **When** 제출을 호출하면, **Then** 아무 배치도 생성되지 않고 정상 응답한다

---

### User Story 2 - 완료 배치 자동 회수 (Priority: P1)

시스템이 주기적으로(3시간, 하루 8회) 제출된 배치의 완료 여부를 확인하고, 완료된 배치의 결과 이미지를 스토리지에 저장한 뒤 음식의 이미지 참조를 갱신하고 배치를 마감한다. 운영 서버 2대 환경에서 한 주기에 한 번만 실행된다.

**Why this priority**: 제출과 함께 비동기 구조의 반쪽. 회수가 없으면 이미지는 영원히 도착하지 않는다.

**Independent Test**: SUBMITTED 배치가 있는 상태에서 회수를 실행하면, 완료된 배치의 결과가 스토리지에 저장되고 food 이미지 참조가 갱신되며 배치가 COLLECTED로 마감되는지 페이크 생성 서비스·페이크 스토리지로 검증.

**Acceptance Scenarios**:

1. **Given** 생성이 완료된 SUBMITTED 배치, **When** 회수가 실행되면, **Then** 결과가 줄 단위 스트리밍으로 파싱되어 스토리지에 저장되고 각 음식의 이미지 참조가 갱신되며 배치는 COLLECTED가 된다
2. **Given** 아직 진행 중인 배치, **When** 회수가 실행되면, **Then** 해당 배치는 건드리지 않고 다음 주기로 넘긴다
3. **Given** 회수 도중 시스템이 중단된 배치, **When** 다음 주기 회수가 실행되면, **Then** 미처리(PENDING) 항목만 다시 회수되어 결과가 유실되지 않는다 (멱등)
4. **Given** 운영 인스턴스 2대, **When** 같은 주기가 도래하면, **Then** 회수는 한 인스턴스에서만 실행된다

---

### User Story 3 - 실패·만료 항목 자동 재제출 (Priority: P2)

생성에 실패했거나 기한 만료된 항목은 실패로 마킹되고, 다음 관리자 제출 시 자동으로 다시 포함된다. 별도의 복구 작업 없이 "다시 제출 버튼"만으로 빠진 것이 채워진다.

**Why this priority**: 멱등 원칙의 완성. 없어도 P1 두 개로 정상 경로는 동작하지만, 실패 건이 수동 복구 대상으로 쌓인다.

**Independent Test**: failed/expired 배치를 만들어 회수를 실행한 뒤 제출을 다시 호출하면, 실패 항목의 음식이 새 배치에 포함되는지 검증.

**Acceptance Scenarios**:

1. **Given** 생성 서비스에서 failed/expired 처리된 배치, **When** 회수가 실행되면, **Then** 해당 항목들은 실패로 마킹되고 배치는 마감된다
2. **Given** 실패로 마킹된 항목의 음식, **When** 관리자가 제출을 다시 호출하면, **Then** 그 음식이 새 배치에 자동 포함된다

---

### User Story 4 - 콘텐츠 배치와 이미지의 분리 (Priority: P2)

기존 콘텐츠 배치는 텍스트 3작업(번역·설명·기피성분)만 전담하고, 이미지만 남은 음식을 매 배치마다 무한 재선정하지 않는다. 이미지는 회수 시점에 사후 갱신된다.

**Why this priority**: 이것을 반영하지 않으면 콘텐츠 배치가 이미지 미보유 음식을 영원히 재처리하는 낭비가 생긴다.

**Independent Test**: 텍스트 3작업이 끝났고 이미지만 없는 음식이 콘텐츠 배치 재실행 시 선정되지 않음을 검증.

**Acceptance Scenarios**:

1. **Given** 텍스트 3작업 완료·이미지 미보유 음식, **When** 콘텐츠 배치가 실행되면, **Then** 해당 음식은 처리 대상으로 선정되지 않는다

---

### Edge Cases

- 관리자가 제출 버튼을 연속 두 번 누르면? → 선정 조건(이미지 참조 부재 + 진행 중 배치 미포함)이 가드를 겸해 재제출 없음
- 결과 파일이 수십 MB(base64 이미지 포함)라면? → 줄 단위 스트리밍 파싱, 전체 메모리 적재 금지
- 배치 내 일부 항목만 실패하면? → 성공 항목은 저장·갱신, 실패 항목만 실패 마킹 후 재제출 경로로
- 회수 주기를 놓치면(배포·재시작)? → 다음 주기가 회수. 상태의 원천은 내부 메타 테이블이므로 유실 없음
- 24시간을 넘겨 만료된 배치의 미처리 건은? → 실패 마킹 → 다음 제출에 자연 포함
- 동일 음식이 삭제된 뒤 결과가 도착하면? → 이미지 참조 갱신 대상 부재 시 항목만 마감하고 건너뜀

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 이미지 배치와 배치 항목을 기록하는 메타 테이블을 가져야 하며, 배치 상태(SUBMITTED/COLLECTED/FAILED)와 항목 상태(PENDING/DONE/FAILED)의 원천은 외부 서비스가 아닌 이 테이블이다
- **FR-002**: 관리자 제출은 이미지 참조가 없고 진행 중 배치에 미포함인 음식만 선정하여, 항목 식별자(custom_id)로 음식 PK를 사용해 배치를 생성·기록하고 즉시 응답해야 한다
- **FR-003**: 제출을 재실행하면 빠진 것만 다시 제출되어야 한다 (멱등 — 어떤 단계에서 중단되어도 성립)
- **FR-004**: 회수는 api 서버의 스케줄 실행(3시간 주기, 하루 8회) + ShedLock(JDBC, lockAtMostFor 30분)으로 트리거되며, 운영 2대 환경에서 한 주기 한 번만 실행됨을 보장해야 한다. 람다 등 외부 워커는 두지 않는다 (부하 실측 전 선지불 금지 — 회수 서비스는 상태 조회/바이트 이동/DB 전이 seam을 갈라두어 향후 분리에 대비)
- **FR-005**: 회수는 SUBMITTED 배치의 완료 여부를 확인하여, 완료분 결과를 줄 단위 스트리밍으로 파싱·디코딩해 스토리지에 저장하고 음식의 이미지 참조를 갱신한 뒤 항목·배치 상태를 마감해야 한다
- **FR-006**: failed/expired 배치의 항목은 실패로 마킹되어 다음 관리자 제출에 자동 포함되어야 한다
- **FR-007**: 콘텐츠 배치는 텍스트 3작업만 전담하며, 이미지만 남은 음식을 재선정하지 않아야 한다 — 음식 상태에 PENDING_IMAGE(텍스트 완료·이미지 대기)를 신설하고, 상태 전이는 칼럼 상태(텍스트 4조건 × imageRef)로 목표 상태를 계산하는 수렴 함수 하나로 통일한다. 콘텐츠 배치와 이미지 회수가 같은 함수를 호출하므로 텍스트/이미지 어느 쪽이 먼저 끝나도 안전하다: 텍스트 미완이면 INCOMPLETE 유지(이미지가 먼저 오면 imageRef만 세팅), 텍스트 완료+이미지 없음이면 PENDING_IMAGE, 텍스트 완료+이미지 있음이면 PENDING_REVIEW(PENDING_IMAGE 건너뜀). 검수자는 이미지를 포함해 검수한다
- **FR-008**: 이미지는 원본 그대로 저장·서빙한다 — 512px 축소본은 스코프에서 제외 (확정)
- **FR-009**: 제출·회수·상태 전이는 페이크(외부 생성 서비스·스토리지)로 자동 검증 가능해야 한다

### Key Entities

- **이미지 배치(image_batch)**: 외부 제출 단위. 외부 배치 식별자(unique), 배치 상태, 프롬프트 버전, 모델, 제출/회수 시각
- **배치 항목(image_batch_item)**: 배치 내 음식 1건. 배치 참조(id 값 참조), 음식 식별자(= custom_id), 항목 상태, 결과 파일명, 오류 메시지
- **음식(food)**: 기존 엔티티. 이미지 참조(image_ref)가 "이미지 필요" 판단과 회수 결과 반영의 대상

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자 제출 응답은 이미지 생성 완료를 기다리지 않는다 (생성에 5분이 걸리든 24시간이 걸리든 제출 UX 불변)
- **SC-002**: 제출 버튼을 연속으로 눌러도 중복 제출 0건
- **SC-003**: 생성 완료된 이미지는 완료 시점으로부터 최대 1주기(3시간) 안에 회수·반영된다
- **SC-004**: 운영 2대 환경에서 회수는 주기당 정확히 1회 실행된다
- **SC-005**: 어떤 단계에서 중단 후 재실행해도 결과가 수렴한다 — 유실 0건, 중복 저장 0건
- **SC-006**: 콘텐츠 배치가 이미지만 남은 음식을 재선정하는 건수 0건
- **SC-007**: 대용량 결과 처리 중 상주 메모리는 이미지 1장 수준을 유지한다 (전체 파일 메모리 적재 없음)

## Assumptions

- 배치당 항목 수 기본값은 100건 — 한 번에 제작·회수(운영 결정). 배치 단위 실패/만료 손실은 부분 완료분 회수로 흡수
- 장당 원가는 항목 테이블 컬럼이 아니라 기존 원가 장부(KB-155, llm_call_cost)에 이미지 1장당 1행으로 기록한다 (이중 장부 방지 — research R6)
- 프롬프트는 코드 상수로 관리(설정 아님 — PROMPT_TEMPLATE·PROMPT_VERSION 이 같은 파일에서 함께 이동)하고 배치에 prompt_version 을 기록만 한다 — 버전 불일치 기반 재생성 트리거는 후속 티켓 (research R7)
- 기존 동기식 이미지 생성 구현(KB-224)은 이 구조로 대체된다 (빈 조립 주석 처리 상태에서 정리)
- 스토리지 저장은 기존 StorageObjectStore 경로를 재사용한다
- 람다가 외부 서비스를 직접 폴링하는 안은 기각됨 (상태 원천 원칙 위배 — Jira Background 참조), 재논의 대상 아님
