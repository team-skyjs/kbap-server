# Feature Specification: 회원 알림 설정 API — 활동 푸시·K-Bap 소식 두 그룹 재편

**Feature Branch**: `kb-466-notification-settings-api`

**Created**: 2026-09-07

**Status**: Draft

**Input**: User description: "466 워크트리. 변경할 내용은 알림의 타입을 아래와 같이 나눈다. 1. 활동 푸시 하위 항목으로 활동/소식(리뷰 좋아요, 리뷰 작성 리마인더) 2. 광고성 푸시 하위 항목으로 마케팅 목적의 개인정보 수집 및 이용 동의(선택)을 동의해야만 점심, 저녁 푸시알림을 받도록" — Jira KB-466 「[BE] 회원 알림 설정 API GET/PATCH /api/members/me/notification-settings」. 에픽 KB-463 의 세 번째 태스크. 명확화 답변(2026-09-07): 활동/소식은 토글 하나로 도움됨·리마인더를 함께 관리한다. 광고성 그룹의 이름은 「K-Bap에서 보내는 소식」이며 「마케팅 목적 개인정보 수집·이용 동의(선택)」와 「광고성 정보 수신 동의」 **둘 다** 동의해야 켜진다. 그 하위 토글은 「식사 시간 알림」(점심·저녁을 하나로 관리) 하나뿐이다.

## 배경

앱의 알림 설정 화면은 지금 기기 로컬에만 저장된다. 서버가 회원 설정의 정본을 갖지 않으면 발송 배치(KB-468 이후)는 누구에게 무엇을 보내도 되는지 판단할 수 없다. 또 광고성 알림은 법적 동의가 전제라, "켰다" 는 사실만이 아니라 "어떤 문구에 언제 동의했는지" 를 서버가 남겨야 한다.

이 기능은 회원의 알림 설정을 서버가 읽고 쓰는 통로를 열면서, 설정의 구조를 두 그룹으로 재편한다.

| 그룹 | 켜는 조건 | 하위 토글 |
|---|---|---|
| **활동 푸시** | 없음 | 활동/소식 — 리뷰 도움됨, 리뷰 작성 리마인더 (기본 켜짐) |
| **K-Bap에서 보내는 소식** (광고성) | 「마케팅 목적 개인정보 수집·이용 동의(선택)」 + 「광고성 정보 수신 동의」 둘 다 동의 | 식사 시간 알림 — 점심·저녁 "식사할 때 스캔해 보세요" 넛지 |

KB-464 가 만든 저장 기반(선호 2개 컬럼·광고성 동의 원장 1종)은 이 구조에 맞춰 조정된다. 조정의 "어떻게" 는 plan 에서 정한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원이 자신의 알림 설정을 조회한다 (Priority: P1)

회원이 알림 설정 화면을 열면 서버가 보관한 현재 설정이 그대로 보인다. 아직 아무것도 설정한 적 없는 회원은 기본값(활동/소식 켜짐, K-Bap 소식 꺼짐·동의 없음)을 본다. K-Bap 소식이 켜져 있으면 두 동의 각각의 동의 시각과 문구 버전, 그리고 식사 시간 알림 토글 상태가 함께 보인다.

**Why this priority**: 조회가 있어야 앱이 서버 정본으로 화면을 그릴 수 있다. 쓰기(P2)보다 먼저 있어야 앱 팀이 연동을 시작한다.

**Independent Test**: 설정을 한 번도 안 만든 회원으로 조회 → 기본값. 저장소에 설정·동의를 직접 심은 회원으로 조회 → 심은 값이 그대로 보임.

**Acceptance Scenarios**:

1. **Given** 설정 기록이 없는 회원, **When** 설정을 조회하면, **Then** 활동/소식 켜짐, K-Bap 소식 꺼짐, 식사 시간 알림 꺼짐, 두 동의 모두 없음(시각·버전 비어 있음)으로 응답한다.
2. **Given** 활동/소식을 끈 회원, **When** 조회하면, **Then** 활동/소식 꺼짐이 보이고 나머지는 저장된 값대로다.
3. **Given** 두 동의를 모두 한 회원(식사 시간 알림 꺼짐), **When** 조회하면, **Then** K-Bap 소식 켜짐, 두 동의 각각의 시각·버전, 식사 시간 알림 꺼짐이 보인다.
4. **Given** 한쪽 동의만 유효한 회원(다른 쪽은 철회됨), **When** 조회하면, **Then** K-Bap 소식은 꺼짐으로 보이고 유효한 동의 하나의 시각·버전만 채워진다.
5. **Given** 인증 없는 요청(게스트), **When** 조회하면, **Then** 인증 오류로 거절된다.

### User Story 2 - 회원이 활동/소식·식사 시간 알림 토글을 켜고 끈다 (Priority: P2)

회원은 활동/소식 토글 하나로 리뷰 도움됨·리뷰 작성 리마인더 알림을 함께 켜고 끈다. K-Bap 소식이 켜진 상태에서는 식사 시간 알림을 켜고 끌 수 있다. 식사 시간 알림은 점심·저녁을 따로 고르지 않고 하나로 켜고 끈다. 부분 수정이라 보낸 항목만 바뀌고 나머지는 그대로다.

**Why this priority**: 설정 화면의 기본 상호작용. 동의(US3)와 독립적으로 검증 가능하다.

**Independent Test**: 활동/소식 off → 조회하면 off, 나머지 불변. K-Bap 소식 켜진 회원이 식사 시간 알림 off → 그것만 바뀜.

**Acceptance Scenarios**:

1. **Given** 설정 기록이 없는 회원, **When** 활동/소식 끄기를 보내면, **Then** 설정 기록이 생기고 활동/소식 꺼짐, 나머지는 기본값이다.
2. **Given** 활동/소식이 꺼진 회원, **When** 켜기를 보내면, **Then** 켜짐으로 바뀐다.
3. **Given** K-Bap 소식이 켜진 회원(식사 시간 알림 켜짐), **When** 식사 시간 알림 끄기만 보내면, **Then** 식사 시간 알림만 꺼지고 활동/소식·동의는 그대로다.
4. **Given** K-Bap 소식이 꺼진 회원, **When** 식사 시간 알림 켜기를 보내면, **Then** 요청은 거절되고(동의 선행 필요) 설정은 바뀌지 않는다.
5. **Given** 어떤 회원, **When** 빈 요청(항목 없음)을 보내면, **Then** 아무것도 바뀌지 않고 현재 설정을 응답한다.

### User Story 3 - 회원이 K-Bap 소식을 켜며 두 가지 동의를 남기고, 끄며 철회한다 (Priority: P2)

회원이 K-Bap 소식을 켜려면 「마케팅 목적 개인정보 수집·이용 동의(선택)」와 「광고성 정보 수신 동의」 둘 다에 동의해야 한다. 앱은 두 동의의 문구 버전을 함께 보내고, 서버는 종류별로 "언제 어떤 버전에 동의했는지" 를 원장에 남긴다. 켜는 순간 식사 시간 알림은 기본 켜진다. K-Bap 소식을 끄면 두 동의의 열린 기록이 모두 철회 시각과 함께 닫히고, 식사 시간 알림 값은 보존되지만 발송에는 쓰이지 않는다. 문구가 바뀐 뒤 다시 켜면 이전 동의는 닫히고 새 버전의 동의가 남아 최초 동의 시각이 이력으로 보존된다.

**Why this priority**: 광고성 알림은 법적 동의 없이는 한 건도 나갈 수 없다. 원장이 정확해야 "누가 언제 무엇에 동의했나" 를 답할 수 있다.

**Independent Test**: K-Bap 소식 on(두 버전 포함) → 원장에 종류별 열린 기록 1개씩, 식사 시간 알림 on → 같은 버전으로 다시 on → 무변화 → 한쪽 버전만 올려 on → 그 종류만 닫고 새 기록 → off → 두 종류 열린 기록 모두 닫힘, 기록 보존.

**Acceptance Scenarios**:

1. **Given** 동의 기록이 없는 회원, **When** K-Bap 소식 켜기를 두 동의의 문구 버전과 함께 보내면, **Then** 종류별 열린 동의 기록이 하나씩 생기고(서버 시각 스탬프), 식사 시간 알림이 켜지며, 조회 시 K-Bap 소식 켜짐이 보인다.
2. **Given** 회원, **When** K-Bap 소식 켜기를 보내는데 두 버전 중 하나라도 없거나 양의 정수가 아니면, **Then** 요청은 거절되고 원장·설정은 바뀌지 않는다.
3. **Given** 같은 버전들로 이미 열린 두 동의가 있는 회원, **When** 같은 버전들로 다시 켜기를 보내면, **Then** 원장·설정 모두 바뀌지 않는다.
4. **Given** 두 동의가 열린 회원, **When** 광고성 정보 수신 동의 버전만 올려 켜기를 보내면, **Then** 수신 동의는 이전 기록이 닫히고 새 버전 기록이 생기며, 개인정보 동의 기록은 그대로다.
5. **Given** 두 동의가 열린 회원(식사 시간 알림 꺼짐), **When** K-Bap 소식 끄기를 보내면, **Then** 두 종류의 열린 기록 모두 철회 시각이 찍혀 닫히고 기록은 남으며, 식사 시간 알림 값은 보존되고, 조회 시 K-Bap 소식 꺼짐·동의 없음으로 보인다.
6. **Given** 동의 기록이 없는 회원, **When** 끄기를 보내면, **Then** 아무 변화 없이 성공한다.
7. **Given** 회원, **When** 켜기 요청에 클라이언트가 동의 시각을 실어 보내면, **Then** 그 값은 무시되고 서버 시각이 기록된다.
8. **Given** K-Bap 소식을 껐다가 다시 켠 회원(이전에 식사 시간 알림 꺼짐), **When** 다시 켜면, **Then** 식사 시간 알림 꺼짐이 그대로 복원된다(기본값으로 되돌리지 않음).

---

### Edge Cases

- 회원에게 같은 종류의 열린 동의가 두 건 이상 있을 때(재시도 등) 끄기는 전부 닫고, 켜기는 최신 버전 기준으로 판단한다. 한 건만 남기지 않는다.
- 개인정보 동의는 열려 있고 수신 동의만 철회된 상태(직접 조작·과거 데이터)는 "K-Bap 소식 꺼짐" 으로 취급하고, 발송 대상에서 제외한다.
- 게스트 시절 기기에서 남긴 동의가 로그인 때 회원에게 이어진 경우(KB-465), 그 기록도 종류별로 이어져야 한다. KB-465 의 게스트 동의는 종류 1개(광고성 수신)뿐이었으므로, 이 기능 이후 게스트 등록 시에도 두 종류를 함께 남기도록 토큰 등록 계약을 맞춘다.
- 식사 시간 알림을 끈 채 K-Bap 소식이 켜져 있으면 동의는 유효하지만 광고성 알림은 한 건도 나가지 않는다. 허용한다.
- 활동/소식 하나로 도움됨·리마인더를 관리하므로 둘 중 하나만 끄는 조합은 존재하지 않는다. 식사 시간 알림도 점심만·저녁만 끄는 조합은 존재하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 회원 본인의 알림 설정을 한 번의 조회로 돌려줘야 한다: 활동/소식 on/off, K-Bap 소식 on/off(= 두 동의 모두 유효), 식사 시간 알림 on/off, 두 동의 각각의 동의 시각·문구 버전(없으면 비어 있음).
- **FR-002**: 시스템은 설정 기록이 없는 회원에게 기본값(활동/소식 켜짐, K-Bap 소식 꺼짐, 식사 시간 알림 꺼짐, 동의 없음)을 돌려줘야 하며, 조회만으로 기록을 만들지 않는다.
- **FR-003**: 시스템은 부분 수정을 지원해야 한다: 보낸 항목만 바꾸고 나머지는 유지하며, 빈 요청은 무변화로 성공한다.
- **FR-004**: 시스템은 활동/소식 토글 하나로 리뷰 도움됨·리뷰 작성 리마인더 알림 수신을 함께 제어해야 한다.
- **FR-005**: 시스템은 식사 시간 알림 토글 하나로 점심·저녁 넛지 수신을 함께 제어해야 한다. 시간대별 개별 설정은 두지 않는다.
- **FR-006**: 시스템은 K-Bap 소식 켜기 요청에 두 동의(마케팅 목적 개인정보 수집·이용, 광고성 정보 수신)의 문구 버전(양의 정수)이 모두 있을 때만 받아들이고, 하나라도 없으면 거절해야 한다.
- **FR-007**: 시스템은 K-Bap 소식 켜기 시 동의 종류별로 원장에 기록을 남겨야 한다: 같은 종류의 열린 기록이 같은 버전이면 무변화, 다른 버전이면 그 기록을 닫고 새 기록을 남긴다. 동의 시각은 서버가 찍고 클라이언트 값은 무시한다.
- **FR-008**: 시스템은 K-Bap 소식 켜기 시 식사 시간 알림이 한 번도 설정된 적 없으면 켜야 하고, 이전 값이 있으면 그 값을 유지해야 한다.
- **FR-009**: 시스템은 K-Bap 소식 끄기 시 두 종류의 열린 동의 기록을 모두 닫되(철회 시각 기록) 어떤 기록도 삭제하지 않아야 하며, 식사 시간 알림 값은 보존해야 한다.
- **FR-010**: 시스템은 K-Bap 소식이 꺼진(두 동의 중 하나라도 유효하지 않은) 회원의 식사 시간 알림 켜기 요청을 거절해야 한다.
- **FR-011**: 시스템은 "K-Bap 소식 켜짐" 을 두 동의가 모두 유효할 때로만 판정해야 한다. 발송 대상 판정도 같은 기준을 따르며, 그 위에 식사 시간 알림 토글을 적용한다.
- **FR-012**: 시스템은 이 설정을 회원 전용으로 노출해야 한다. 게스트 요청은 인증 오류다.
- **FR-013**: 시스템은 게스트의 토큰 등록 시 동의(KB-465)도 같은 두 종류로 남기도록 계약을 맞춰야 한다. 게스트는 동의하면 식사 시간 알림을 받는다.
- **FR-014**: 시스템은 이 API 를 기존 규약(공통 응답 봉투·버전 헤더 필수·보호 경로 등록)에 맞춰 노출하고 API 문서에 실어야 한다.

### Key Entities *(include if data involves)*

- **회원 알림 선호(NotificationSetting)**: 회원 1 : 기록 1. 활동/소식 on/off, 식사 시간 알림 on/off. KB-464 의 도움됨·리마인더 두 항목을 활동/소식 하나로 합치고 식사 시간 알림을 더한다.
- **동의 기록(NotificationConsent)**: 동의 1회의 생애. 주체(회원 또는 기기)·**동의 종류**(마케팅 목적 개인정보 수집·이용 / 광고성 정보 수신)·문구 버전·동의 시각·철회 시각. KB-464 의 원장에 "종류" 축이 추가된다.
- **알림 유형**: 활동 푸시 → 활동/소식(리뷰 도움됨, 리뷰 작성 리마인더). K-Bap 소식 → 식사 시간 알림(점심·저녁 넛지). 유형과 토글의 대응은 고정이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 앱 팀이 개발 서버의 API 문서만 보고 설정 화면(활동 그룹 토글 1개, K-Bap 소식 그룹 동의 + 토글 1개)을 서버 정본으로 연동할 수 있다.
- **SC-002**: 회원 한 명이 "K-Bap 소식 켜기 → 식사 시간 알림 끄기 → K-Bap 소식 끄기 → 다시 켜기" 를 수행한 뒤, 조회 결과가 각 단계의 기대값과 일치하고 식사 시간 알림 꺼짐이 복원된다.
- **SC-003**: 위 시나리오 후 동의 원장에는 삭제된 행 없이 종류별 동의·철회·재동의 이력이 시각·버전과 함께 남아, 특정 회원이 어떤 동의에 언제 동의·철회했는지 원장만으로 답할 수 있다.
- **SC-004**: 두 동의 중 하나라도 철회된 회원은 발송 대상 조회(KB-464 정의 질의를 이 기준으로 갱신)에서 식사 시간 알림 대상으로 잡히지 않는다.
- **SC-005**: 위 시나리오 전부가 자동화 통합 테스트로 재현되어 회귀 시 실패한다.

## Assumptions

- 광고성 그룹의 이름은 「K-Bap에서 보내는 소식」으로 확정했다(2026-09-07). 하위 토글은 「식사 시간 알림」(리텐션 목적의 "식사할 때 스캔해 보세요" 넛지, 기존 유형 NUDGE) 하나뿐이다. 점심·저녁은 발송 시각 구분일 뿐 사용자가 따로 고르지 않는다.
- 기존 유형 NOTICE(공지)는 이 설정 화면에 토글이 없다. 공지를 광고성으로 보낼지, 동의 없이 보낼 필수 고지로 볼지는 발송 배치 태스크에서 정한다.
- 두 동의는 각각 별도 문구 버전을 가진다(구 문구 = 1). 서버는 "현재 최신 버전" 을 검증하지 않고 받은 값을 기록한다.
- K-Bap 소식 켜기 요청은 두 동의를 한 번에 보낸다. 한 종류만 따로 켜는 요청은 없다(앱 화면이 하나의 스위치로 두 동의를 받는다).
- 식사 시간 알림의 발송 시각(점심·저녁)·문구는 배치(KB-468 이후)가 정한다.
- 활동/소식이 켜져 있어도 리뷰 도움됨·리마인더의 실제 발생 조건(누가 도움됨을 눌렀나, 주문 후 며칠인가)은 발송 배치가 판단한다.
- 게스트 동의 계약 조정(FR-013)은 KB-465 로 이미 머지된 토큰 등록 API 의 요청 형식을 바꾸는 일이라, 앱 팀에 계약 변경을 통지한다. 아직 앱이 연동 전이라 호환 유지 없이 교체한다.
- 동의 원장에 "종류" 를 더하는 것과 선호 항목 재편은 KB-464 마이그레이션이 공유 DB 에 이미 적용됐으므로 새 마이그레이션으로 처리한다(기존 파일 수정 금지).
- 요청 기기 식별 헤더가 있으면 회원 동의 기록에 "동의 받은 기기" 로 함께 남긴다(KB-464 설계). 없어도 회원 동의 기록은 남는다.
