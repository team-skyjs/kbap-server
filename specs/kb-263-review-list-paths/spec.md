# Feature Specification: 리뷰 목록 조회 엔드포인트 경로를 /reviews 리소스 아래로 통일

**Feature Branch**: `kb-263-review-list-paths`

**Created**: 2026-07-30

**Status**: Draft

**Input**: User description: "리뷰 API 중 내 리뷰 목록과 음식별 리뷰 목록 엔드포인트를 변경한다. 각각 reviews/me, reviews?foodId= 이렇게" (Jira KB-263)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 음식별 리뷰 목록을 리뷰 리소스 경로로 조회 (Priority: P1)

클라이언트 개발자가 특정 음식의 리뷰 목록을 조회할 때, 음식 리소스 하위 경로가 아니라 리뷰 리소스 경로에 음식 식별자를 조건으로 넘겨 조회한다.

**Why this priority**: 목록의 주체가 리뷰이므로 리뷰 리소스 아래로 통일해야 API 가 일관된다. 두 변경 중 파라미터 형태(경로 변수 → 쿼리 파라미터)까지 바뀌는 더 큰 변경.

**Independent Test**: 새 경로로 음식 리뷰 목록을 요청해 기존과 동일한 목록·페이지 응답을 받는 것으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 리뷰가 있는 음식, **When** 새 경로에 음식 식별자를 조건으로 목록을 요청하면, **Then** 기존 경로와 동일한 형식·내용의 리뷰 목록이 반환된다
2. **Given** 음식 식별자 조건 없이 새 경로로 요청, **When** 목록을 요청하면, **Then** 요청 오류로 응답한다
3. **Given** 기존 경로(음식 리소스 하위), **When** 목록을 요청하면, **Then** 더 이상 제공되지 않는다

---

### User Story 2 - 내 리뷰 목록을 리뷰 리소스 경로로 조회 (Priority: P2)

로그인한 회원이 자신이 작성한 리뷰 목록을 회원 리소스 하위 경로가 아니라 리뷰 리소스의 "내 것" 경로로 조회한다.

**Why this priority**: 같은 통일 원칙의 적용이지만 경로 이동만 있고 파라미터 형태 변화가 없어 P1 보다 단순.

**Independent Test**: 로그인 상태로 새 경로를 요청해 기존과 동일한 내 리뷰 목록을 받는 것으로 단독 검증 가능.

**Acceptance Scenarios**:

1. **Given** 리뷰를 작성한 로그인 회원, **When** 새 "내 리뷰" 경로로 목록을 요청하면, **Then** 기존 경로와 동일한 형식·내용의 목록이 반환된다
2. **Given** 미로그인 상태, **When** 새 "내 리뷰" 경로로 요청하면, **Then** 인증 오류로 응답한다
3. **Given** 기존 경로(회원 리소스 하위), **When** 목록을 요청하면, **Then** 더 이상 제공되지 않는다

---

### Edge Cases

- 음식 식별자 조건이 없거나 형식이 잘못된 경우(비어 있음·숫자 아님) 요청 오류로 구분해 응답하는가?
- "내 리뷰" 경로(`/reviews/me`)가 개별 리뷰 식별자 경로(`/reviews/{reviewId}`)와 충돌 없이 해석되는가?
- 기존 두 경로에 대한 인증 보호 설정이 새 경로로 옮겨져, 새 경로에서도 동일한 인증 규칙이 적용되는가?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 음식별 리뷰 목록은 `GET /api/v1/reviews?foodId={foodId}` 로 조회할 수 있어야 한다. `foodId` 는 필수 조건이며, 누락 시 요청 오류로 응답한다.
- **FR-002**: 내 리뷰 목록은 `GET /api/v1/reviews/me` 로 조회할 수 있어야 한다(로그인 필수).
- **FR-003**: 기존 경로 `GET /api/v1/foods/{foodId}/reviews` 와 `GET /api/v1/members/me/reviews` 는 제거한다(하위 호환 유지 없음).
- **FR-004**: 커서·국적 필터 등 기존 쿼리 파라미터와 응답 형식·내용은 두 엔드포인트 모두 변경 전과 동일하게 유지한다.
- **FR-005**: 인증 규칙은 변경 전과 동일하다 — 두 목록 조회 모두 로그인한 회원만 사용할 수 있다.
- **FR-006**: API 문서(Swagger)와 인증 보호 경로 설정이 새 경로를 반영해야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새 경로 2개로 조회한 결과가 변경 전 경로의 결과와 100% 동일하다(목록 내용·페이지 커서·오류 응답).
- **SC-002**: 제거된 기존 경로 2개는 어떤 요청에도 목록을 반환하지 않는다.
- **SC-003**: 관련 자동화 테스트 전체가 새 경로 기준으로 통과한다.

## Assumptions

- 이 API 는 아직 출시 전이라 외부에 배포된 클라이언트가 없어, 기존 경로를 리다이렉트·병행 유지 없이 즉시 제거해도 된다(KB-263 DoD 명시).
- 서비스 내부 로직·데이터 모델은 변경하지 않는다 — HTTP 경계(경로·파라미터 바인딩)와 문서·보호 경로 설정만 이동한다.
- 음식별 리뷰 목록의 인증 정책(로그인 필수)은 현행 동작을 그대로 유지한다.
