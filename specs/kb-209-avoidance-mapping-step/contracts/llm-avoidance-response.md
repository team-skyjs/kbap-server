# Contract: 기피성분 조사 LLM 응답 (모델별 단건)

외부 인터페이스는 web API 가 아니라 **LLM 모델 3사에 강제하는 응답 JSON 계약**이다. `FoodAvoidanceInvestigator` 가 프롬프트로 지시하고 파서가 검증한다.

## 요청(프롬프트) 입력

- 음식 한국어 이름 1건 (`food.koreanName`)
- 기피성분 카탈로그: `[{code, korean_name}]` 81종 (DB 단일 출처)
- 지시: 카탈로그 코드 중 이 음식에 포함될 수 있는 성분과 포함 확률(0~100), 맵기(0~10)를 JSON 으로만 응답

## 응답 JSON (모델별)

```json
{
  "spiciness": 7,
  "substances": [
    { "code": "EGG", "inclusion_percent": 90 },
    { "code": "WHEAT", "inclusion_percent": 100 }
  ]
}
```

| 필드 | 타입 | 제약 | 위반 시 |
|---|---|---|---|
| `spiciness` | int | 0~10 | 그 모델 응답 전체 탈락 |
| `substances` | array | 빈 배열 허용(무성분 판단). 코드 중복은 dedup(1표) | — |
| `substances[].code` | string | 카탈로그 code 집합 내 | **해당 항목만 폐기 + 경고 로그**(응답은 유지) |
| `substances[].inclusion_percent` | int | 1~100 | 0~100 밖 → 그 모델 응답 전체 탈락. **0 은 "미포함 판단"으로 항목 폐기**(투표 아님, 응답 유지) |
| (형식) | JSON object | 코드펜스·전후 잡문은 제거 후 파싱 | 파싱 불가 시 그 모델 응답 탈락 |

## 합의(3모델 종합) 계약

- 성공(파싱까지 통과) 응답 **2개 미만 → 음식 실패**(INCOMPLETE 유지, 재시도).
- 투표는 **모델 1개당 코드 1표**(응답 내 중복 코드 dedup). 성분 채택: 성공 모델 중 **2개 이상이 지목한 code** 만. `inclusion_percent` = 지목 모델 평균(반올림).
- `spiciness` = 성공 응답 **중앙값**(성공 2개면 평균 반올림) — 결과는 0~10 안에 있음(입력이 모두 0~10).
- **빈 결과의 성공 조건 (false-safe 방지)**: 채택 코드가 없을 때 "무성분 조사완료(`[]`)"로 확정하는 것은 **성공 모델 2개 이상이 각각 명시적으로 빈 `substances` 를 반환한 경우뿐**이다. 모델들이 서로 다른 성분을 지목해 교집합이 빈 경우·유효 항목이 전량 폐기(미지 코드 등)된 경우는 **합의 미성립 → 음식 실패**(재시도). 성분 불일치가 "무성분"으로 저장돼 READY 되는 경로를 차단한다.

## 실패 의미론 (배치 관점)

| 상황 | 처리 |
|---|---|
| 합의 성립 | `assessAvoidance` 반영 + `saveProgress`(독립 커밋) |
| 합의 미성립·전 모델 실패 | 그 음식의 기피성분 작업만 미완 — 예외 전파 없이 다음 작업/음식 진행, 다음 실행 재시도 |
| 미지 코드 | 항목 폐기 + `warn` 로그(code·foodId·modelId 포함) |
