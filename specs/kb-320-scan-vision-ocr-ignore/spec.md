# Feature Specification: 스캔 v2 경로 분리 · 비전 모델 교체 · LLM 단일 벤더 정리

**Feature Branch**: `kb-320-scan-vision-ocr-ignore`

**Created**: 2026-08-11 (2026-08-11 범위 재정의)

**Status**: Draft

**Input**: User description: "KB-320 [BE] 스캔 비전 LLM 5.6 luna 교체 및 클라이언트 OCR 무시 프롬프트로 정확도 개선"

## 범위 변경 이력 (중요)

이 기능은 작업 중 두 번 범위가 바뀌었다. 지금의 spec 은 **최종 산출물 기준**이다.

| 시점 | 내용 |
|------|------|
| 초안 | v1 스캔의 프롬프트를 고쳐 클라이언트 OCR 을 판단에서 배제하고, 요청 계약(`items` 필수)은 유지한다 |
| 1차 변경 | 구버전 앱 동작 보존 요구 → `X-API-Version` 헤더로 프롬프트를 두 벌 분기 |
| **최종** | **KB-319(PR #141)가 이미 같은 목표를 `X-API-Version` + 서버 OCR 로 구현·머지**한 사실을 발견. 헤더 분기를 걷어내고 **URL 경로로 v1/v2 를 분리**한다. 프롬프트 자체는 이 브랜치에서 바꾸지 않는다 |

**"클라이언트 OCR 을 판단에 쓰지 않는다"는 목표는 프롬프트가 아니라 구조가 달성한다** — v2 는 `items` 를 아예 받지 않으므로 OCR 이 개입할 경로가 없다. 지라 DoD 의 프롬프트 항목은 KB-319 의 `SERVER_OCR_SYSTEM_PROMPT` 가 충족한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 신규 앱은 사진만 보내고 정확한 결과를 받는다 (Priority: P1)

신규 클라이언트는 메뉴판 사진 경로만 보낸다. 기기 OCR 을 돌리지도, 보내지도 않는다. 서버가 사진에서 직접 메뉴명·가격을 읽어 위험도를 돌려주므로 기기 성능이 결과에 영향을 주지 않는다.

**Why this priority**: 정확도 개선의 본체다. 기기 OCR 품질과 스캔 정확도의 연결을 끊는다.

**Independent Test**: 사진 경로만 담은 요청으로 `POST /api/v2/scans` 를 호출해 메뉴·위험도가 돌아오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 검증된 사진 경로만 보낼 때, **When** v2 로 스캔하면, **Then** 서버가 추출한 메뉴별 위험도·가격이 돌아온다.
2. **Given** 요청 본문에 `items` 가 섞여 들어올 때, **When** v2 로 스캔하면, **Then** 무시되고 서버 OCR 결과만 쓰인다.
3. **Given** `imagePath` 를 누락했을 때, **When** v2 로 스캔하면, **Then** 400(COMMON-002)으로 거절한다.
4. **Given** 메뉴판이 아닌 사진일 때, **When** v2 로 스캔하면, **Then** 빈 결과의 정상 응답이다(실패 아님).

---

### User Story 2 - 배포된 구버전 앱은 아무 영향도 받지 않는다 (Priority: P1)

이미 배포된 앱은 계속 `POST /api/v1/scans` 에 `items` 를 담아 보내고, 예전과 똑같은 모양의 응답을 받는다.

**Why this priority**: 앱 스토어 배포 주기와 서버 배포가 분리돼 있어 v1 계약이 깨지면 곧 장애다.

**Independent Test**: v1 회귀 시나리오 전량이 **테스트 수정 없이** 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 현행 v1 요청 본문일 때, **When** 스캔하면, **Then** 응답 필드 구성이 이전과 같다.
2. **Given** `items` 를 비우거나 누락했을 때, **When** v1 으로 스캔하면, **Then** 종전대로 400(COMMON-002)이다.
3. **Given** 임의의 v1 응답일 때, **When** 필드를 확인하면, **Then** `similarFood` 필드 자체가 없다(v2 전용).
4. **Given** v1 요청일 때, **When** 헤더를 어떻게 보내든, **Then** 동작이 달라지지 않는다(헤더를 보지 않는다).

---

### User Story 3 - 화면의 박스에 위험도가 겹쳐 그려지지 않는다 (Priority: P2)

v1 사용자가 스캔했을 때, 모델이 같은 OCR 항목을 두 메뉴에 물려도 한 박스에 위험도가 겹쳐 그려지지 않는다.

**Why this priority**: v1 전용 결함 방어다. 발생 확률은 낮지만 발생하면 화면이 눈에 띄게 깨진다.

**Independent Test**: 같은 `matchedIdx` 를 가진 추출 결과 2건을 넣고 뒤 항목의 `idx` 가 비는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 두 추출 메뉴가 같은 OCR `idx` 를 물고 올 때, **When** v1 으로 스캔하면, **Then** 먼저 나온 결과만 `idx` 를 갖고 뒤 결과는 비며 **두 메뉴 모두 응답에 남는다**.
2. **Given** 요청 `idx` 집합 밖의 값을 모델이 줄 때, **When** 스캔하면, **Then** 그 결과의 `idx` 는 비어 있다(기존 방어 유지).

---

### User Story 4 - 스캔 비용이 새 모델 기준으로 집계된다 (Priority: P2)

운영자는 관리자 대시보드에서 모델별 일일 비용을 본다. 비전 모델을 교체해도 새 모델 이름과 올바른 단가로 기록돼야 한다.

**Why this priority**: 사용자 가치가 아니라 운영 가치. 단가를 반영하지 않으면 비용 지표가 조용히 틀린다.

**Independent Test**: 스캔 1회 후 비용 기록의 모델 이름·금액이 새 단가 기준인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 새 모델로 스캔했을 때, **When** 비용 기록을 조회하면, **Then** 새 모델 이름으로 기록돼 있다.
2. **Given** 새 단가가 설정돼 있을 때, **When** 비용을 계산하면, **Then** 이전 모델 단가가 아니라 새 단가가 적용된다.

---

### User Story 5 - 쓰지 않는 LLM 경로가 코드에 남지 않는다 (Priority: P2)

개발자가 LLM 코드를 열었을 때, 실제로 호출되는 경로만 보인다. 벤더가 하나이고 죽은 클라이언트가 없다.

**Why this priority**: 사용자에게 보이지 않지만, 남은 죽은 코드가 다음 작업자를 오도한다(이번 작업에서 실제로 그랬다).

**Independent Test**: LLM 모듈에서 살아있는 소비처가 없는 클래스가 0개인지 확인하고 전체 빌드가 통과하는지 본다.

**Acceptance Scenarios**:

1. **Given** 전 채팅 모델이 한 벤더로 통일됐을 때, **When** 설정을 보면, **Then** 벤더별 분기 설정이 없다.
2. **Given** 배치 콘텐츠 생성이 외부로 이관됐을 때, **When** LLM 모듈을 보면, **Then** 그 경로의 클라이언트·seam 이 남아 있지 않다.
3. **Given** 환경변수를 설정할 때, **When** 목록을 보면, **Then** 같은 값을 담는 변수가 둘 이상 존재하지 않는다.

---

### Edge Cases

- v2 요청에 `items` 가 섞여 들어옴 — 무시하고 서버 OCR 결과만 쓴다(400 아님).
- v2 에서 미등록 메뉴가 나옴 — 유사 음식 폴백이 붙거나, 임계 미달·검색 장애면 해당 항목만 `similarFood` 없이 정상 응답한다(부분 성공).
- v1 요청에 `X-API-Version` 헤더가 실려 옴 — 무시한다. 경로가 계약을 결정한다.
- 새 모델이 응답 형식(JSON)을 못 지킴 — 기존 판독 실패 경로(503 SCAN-002)로 흐른다.
- 새 모델의 응답 지연 증가 — 기존 vision 타임아웃(60초) 안에서 실패 처리된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `POST /api/v2/scans` 는 사진 경로만으로 성립해야 하며 클라이언트 OCR 항목을 요구하지 않아야 한다.
- **FR-002**: v2 응답에는 클라이언트 화면 매칭 키(`idx`)가 없어야 한다 — 서버는 클라이언트가 그릴 박스를 알지 못한다.
- **FR-003**: v2 는 미등록 메뉴에 유사 음식 대체 결과를 제공해야 하며, 제공 불가 시 해당 항목만 비우고 스캔은 성공해야 한다.
- **FR-004**: `POST /api/v1/scans` 의 요청·응답 계약과 검증 규칙·오류 코드는 KB-319 이전 상태로 유지돼야 한다(`items` 필수, `similarFood` 없음).
- **FR-005**: 두 엔드포인트 모두 `X-API-Version` 헤더로 동작이 갈리지 않아야 한다 — 계약은 경로가 결정한다.
- **FR-006**: v1 응답에서 하나의 `idx` 는 최대 하나의 결과에만 부여돼야 한다.
- **FR-007**: v1 응답의 `idx` 는 그 요청이 보낸 OCR 항목 식별자 집합 안의 값이어야 한다.
- **FR-008**: 스캔 비전 모델은 OpenAI `gpt-5.6-luna` 여야 한다.
- **FR-009**: 새 모델의 입력·출력 단가(1M 토큰당 USD 0.2 / 1.2)가 설정에 명시돼야 하며 비용 기록에 반영돼야 한다.
- **FR-010**: 채팅·비전 모델은 단일 벤더여야 하며 다중 벤더 fan-out 코드가 남지 않아야 한다.
- **FR-011**: 살아있는 소비처가 없는 LLM 클라이언트·seam 은 제거돼야 한다.
- **FR-012**: 같은 값을 담는 환경변수가 중복 정의되지 않아야 하며, 신규 기능 전용 환경변수는 기존 변수로 대체 가능하면 만들지 않아야 한다.
- **FR-013**: 신규 인증 필요 경로는 보호 경로 목록에 등록돼야 한다.

### Key Entities

- **스캔 v1 요청**: 사진 경로 + 클라이언트 OCR 항목 목록(식별자 + 원문). 동결 계약.
- **스캔 v2 요청**: 사진 경로만.
- **스캔 결과 항목(내부)**: 메뉴명·한국어명·가격·위험도·매칭 여부에 더해 v1 전용 `idx` 와 v2 전용 유사 음식을 함께 들고, 각 응답이 필요한 것만 노출한다.
- **모델 호출 비용 기록**: 모델 이름·토큰·비용. 모델 교체 시 이름과 단가가 함께 바뀐다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: v2 는 클라이언트 OCR 없이 동작하므로, 같은 사진에 대해 기기 OCR 품질과 무관하게 동일한 추출 결과가 나온다.
- **SC-002**: v1 회귀 시나리오가 **테스트 수정 0건**으로 전량 통과한다.
- **SC-003**: v1 응답 한 건 안에서 `idx` 중복은 0건이다.
- **SC-004**: 스캔 1회당 기록되는 비용이 새 모델의 공시 단가와 일치한다.
- **SC-005**: 스캔 응답 시간이 기존 타임아웃 정책 안에 머무른다.
- **SC-006**: LLM 모듈에서 살아있는 소비처가 없는 클래스가 0개다.
- **SC-007**: 배포 환경변수 목록에 같은 값을 담는 변수가 0쌍이다.

## Assumptions

- v1 은 신규 클라이언트가 v2 로 옮겨가면 자연 소멸하는 경로다. 정확도 개선을 v1 에 소급 적용하지 않는다 — 그것이 v1 을 "동결"한다는 말의 의미다.
- 프롬프트는 이 브랜치에서 바꾸지 않는다. v1·v2 프롬프트 모두 KB-319 가 develop 에 넣은 상태를 그대로 쓴다.
- `gpt-5.6-luna` 는 이미지 입력과 구조화된 JSON 응답을 지원하므로 현행 호출 형태를 그대로 쓸 수 있다.
- luna 는 추론 토큰을 사용한다 — 출력 토큰이 늘어 스캔 1회 비용·지연이 단가 배수 이상으로 증가할 수 있다. 배포 전 실측으로 확인한다.
- 이미지 생성(`gpt-image-2`)·임베딩(Bedrock Titan)은 채팅 모델이 아니라 단일 벤더 통일 대상이 아니다.
- 배치의 주석 처리된 콘텐츠 파이프라인 파일 자체는 KB-302 가 정리한다 — 이번엔 LLM 쪽만 걷어낸다.
