# Feature Specification: 스캔 비전 모델 교체 및 사진 단독 판독

**Feature Branch**: `kb-320-scan-vision-ocr-ignore`

**Created**: 2026-08-11

**Status**: Draft

**Input**: User description: "KB-320 [BE] 스캔 비전 LLM 5.6 luna 교체 및 클라이언트 OCR 무시 프롬프트로 정확도 개선"

## 배경

메뉴판 스캔은 사용자가 찍은 사진과 **클라이언트 기기가 자체 OCR 로 읽은 메뉴 텍스트 목록(`items`)** 을 함께 받아, 사진 속 각 메뉴의 기피 성분 위험도를 돌려준다. 응답의 각 결과는 클라이언트 OCR 항목의 식별자(`idx`)를 달고 오며, 클라이언트는 그 `idx` 로 자기 화면의 어느 글자 박스에 위험도를 그릴지 정한다.

현재는 이 OCR 목록이 **판단 근거**로도 쓰인다 — 오탈자 교정의 기준선이자 "무엇이 메뉴인가"의 후보 목록이다. 저가 기기·어두운 조명에서 OCR 품질이 낮으면 잘못 읽힌 텍스트가 판독을 오염시켜 스캔 정확도가 떨어진다.

이 기능은 (1) 스캔에 쓰는 비전 모델을 상위 모델로 교체하고, (2) 판독의 진실 출처를 **사진 하나로 좁혀** 클라이언트 OCR 품질과 스캔 정확도를 분리한다. 클라이언트와의 요청/응답 계약은 그대로 둔다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 저품질 OCR 기기에서도 정확한 스캔 (Priority: P1)

OCR 품질이 낮은 기기를 쓰는 사용자가 메뉴판을 찍는다. 기기가 "되지불고기", "삼겹사", "5징어볶음" 처럼 잘못 읽어 보내더라도, 서버는 사진에 실제로 인쇄된 글자만으로 메뉴명과 가격을 판독해 위험도를 돌려준다. 사용자는 기기 성능과 무관하게 같은 결과를 본다.

**Why this priority**: 이 기능의 존재 이유다. OCR 오염 제거가 정확도 개선의 본체이고, 나머지는 이를 뒷받침한다.

**Independent Test**: 같은 사진에 대해 (a) 정확한 OCR 목록, (b) 오탈자·환각이 섞인 OCR 목록을 각각 보내고, 추출된 메뉴명·가격·위험도가 동일한지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사진에는 "돼지불고기"가 인쇄돼 있고 클라이언트 OCR 은 "되지불고기"로 보냈을 때, **When** 스캔을 요청하면, **Then** 결과의 메뉴명은 사진 기준 "돼지불고기"다.
2. **Given** 사진에 없는 메뉴가 OCR 목록에만 들어 있을 때(환각), **When** 스캔을 요청하면, **Then** 그 메뉴는 결과에 나타나지 않는다.
3. **Given** 사진에 분명히 인쇄됐지만 클라이언트 OCR 이 아예 놓친 메뉴가 있을 때, **When** 스캔을 요청하면, **Then** 그 메뉴도 결과에 포함된다.
4. **Given** 동일한 사진에 대해 OCR 목록만 다르게(정확본 / 오염본) 두 번 요청할 때, **When** 두 응답을 비교하면, **Then** 추출된 메뉴명·가격·위험도 집합이 같다.

---

### User Story 2 - 화면의 박스에 위험도가 그대로 붙는다 (Priority: P1)

사용자가 스캔 결과를 볼 때, 위험도 배지는 자기 화면에서 인식된 메뉴 글자 위에 정확히 얹혀야 한다. 판독 근거가 사진으로 바뀌어도 응답의 `idx` 는 계속 클라이언트가 보낸 OCR 항목을 정확히 가리켜야 한다.

**Why this priority**: P1 이 정확해져도 배지가 엉뚱한 글자에 붙으면 사용자에겐 오히려 퇴행이다. 두 스토리는 같은 릴리스에서 함께 성립해야 한다.

**Independent Test**: 알려진 사진 + OCR 목록으로 스캔해 각 결과의 `idx` 가 같은 메뉴를 가리키는 OCR 항목인지 사람 눈으로 대조한다. 중복 `idx` 가 없는지도 확인한다.

**Acceptance Scenarios**:

1. **Given** 사진과 OCR 목록에 같은 메뉴가 있을 때, **When** 스캔하면, **Then** 그 결과의 `idx` 는 해당 OCR 항목의 `idx` 다.
2. **Given** 사진에는 있으나 OCR 목록에 대응 항목이 없는 메뉴일 때, **When** 스캔하면, **Then** 그 결과의 `idx` 는 비어 있다(박스 없음).
3. **Given** 한 메뉴가 OCR 에서 여러 조각으로 쪼개졌을 때, **When** 스캔하면, **Then** 결과는 하나이고 `idx` 는 조각 중 하나만 갖는다.
4. **Given** 임의의 스캔 응답일 때, **When** 결과 목록을 훑으면, **Then** 같은 `idx` 가 두 결과에 나타나지 않는다.

---

### User Story 3 - 기존 클라이언트가 수정 없이 계속 동작한다 (Priority: P1)

이미 배포된 앱은 바뀐 것을 모른 채 지금과 똑같은 요청을 보내고 똑같은 모양의 응답을 받는다.

**Why this priority**: 앱 스토어 배포 주기와 서버 배포가 분리돼 있어 계약 변경은 곧 장애다. 릴리스 가능 조건이다.

**Independent Test**: 현재 앱이 보내는 것과 동일한 요청 본문으로 스캔을 호출해 응답 필드 구성과 검증 규칙(필수 필드, 최대 항목 수, `idx` 중복 금지, 오류 코드)이 변하지 않았는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 현행 요청 본문 형식 그대로일 때, **When** 스캔을 호출하면, **Then** 요청은 정상 처리되고 응답 필드 구성은 이전과 같다.
2. **Given** OCR 항목을 비운 요청일 때, **When** 스캔을 호출하면, **Then** 지금과 동일하게 거절된다(검증 규칙 불변).
3. **Given** 비전 판독이 실패했을 때, **When** 스캔을 호출하면, **Then** 지금과 동일한 실패 응답(코드·상태)을 받는다.

---

### User Story 4 - 스캔 비용이 계속 집계된다 (Priority: P2)

운영자는 관리자 대시보드에서 모델별 일일 비용을 본다. 모델이 바뀌어도 새 모델 이름과 올바른 단가로 비용이 기록돼야 한다.

**Why this priority**: 정확도와 무관하지만 모델 교체는 곧 단가 변경이고, 단가를 반영하지 않으면 비용 지표가 조용히 틀린다. 사용자 가치가 아니라 운영 가치라 P2.

**Independent Test**: 스캔 1회 후 비용 기록의 모델 이름과 금액이 새 모델 단가 기준으로 계산됐는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 새 모델로 스캔 1회를 수행했을 때, **When** 비용 기록을 조회하면, **Then** 새 모델 이름으로 기록돼 있다.
2. **Given** 새 모델의 입력/출력 단가가 설정돼 있을 때, **When** 비용을 계산하면, **Then** 이전 모델 단가가 아니라 새 단가가 적용된다.

---

### Edge Cases

- OCR 목록의 모든 항목이 사진과 무관한 환각일 때 — 사진에서 추출된 메뉴는 정상 반환되고 `idx` 는 모두 비어 있어야 한다.
- 사진이 흐리거나 메뉴판이 아닐 때 — 결과가 빈 목록이거나 판독 실패 응답이며, OCR 목록의 텍스트를 결과로 대신 채우지 않는다.
- 사진에는 메뉴가 30개인데 OCR 은 5개만 읽었을 때 — 30개가 모두 결과에 나오고 그중 5개만 `idx` 를 갖는다.
- 한 OCR 항목에 여러 메뉴가 뭉쳐 있거나 사이즈별로 나뉠 때 — 결과는 분리되되 그 `idx` 는 한 결과만 사용한다.
- 사진에서 확실히 판독되지 않는 흐린 글자 — OCR 을 근거로 삼지 않으므로 추측해 채우지 않고 제외하거나 사진에서 읽히는 만큼만 반환한다.
- 새 모델이 응답 형식(JSON)을 지키지 못할 때 — 기존 판독 실패 경로와 동일하게 처리되며 사용자에게 부분 손상된 결과를 내보내지 않는다.
- 새 모델의 응답 지연이 기존보다 클 때 — 기존 타임아웃 정책 안에서 실패 처리되고 응답 없이 매달리지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 스캔의 메뉴명·가격 판독은 **사진만을 진실의 출처**로 삼아야 한다. 클라이언트가 보낸 OCR 텍스트는 오탈자 교정 기준·메뉴 후보 목록·존재 판정 근거로 사용되지 않는다.
- **FR-002**: 사진에서 판독된 메뉴는 클라이언트 OCR 목록에 대응 항목이 없더라도 결과에 포함돼야 한다.
- **FR-003**: 클라이언트 OCR 목록에만 존재하고 사진에 근거가 없는 항목은 결과에 포함되지 않아야 한다.
- **FR-004**: 각 결과는 대응하는 클라이언트 OCR 항목의 식별자(`idx`)를 계속 제공해야 하며, 대응 항목이 없으면 비워 둔다. 이 매칭은 **판독이 끝난 뒤 텍스트 내용 기준으로 수행**하는 별도 단계이며, 판독 자체에 영향을 주지 않는다.
- **FR-005**: 하나의 `idx` 는 최대 하나의 결과에만 부여돼야 한다(중복 금지).
- **FR-006**: 응답에 실린 `idx` 는 그 요청이 보낸 OCR 항목의 식별자 집합 안의 값이어야 한다.
- **FR-007**: 스캔 요청 본문 계약(필드 구성, 필수 여부, 항목 수 상한, `idx` 중복 금지 검증)과 응답 본문 계약은 변경되지 않아야 한다.
- **FR-008**: 스캔 비전 판독에 사용하는 모델을 OpenAI `gpt-5.6-luna` 로 교체해야 한다. 제공자·엔드포인트는 현행(OpenAI 호환)과 동일하며 모델 지정만 바뀐다.
- **FR-009**: 새 모델의 단가(입력 1M 토큰당 USD 0.2, 출력 1M 토큰당 USD 1.2)가 설정에 명시돼야 하며, 비용 기록은 이전 모델 단가(0.15/0.60)가 아닌 새 단가로 계산돼야 한다.
- **FR-010**: 판독 실패·형식 오류 시의 사용자 응답(오류 코드·HTTP 상태)은 현행과 동일하게 유지돼야 한다.
- **FR-011**: OCR 무시 동작(FR-001~FR-003)이 자동화된 테스트로 검증돼야 하며, 기존 스캔 테스트는 모두 통과해야 한다.

### Key Entities

- **스캔 요청**: 메뉴판 사진의 위치와 클라이언트 OCR 항목 목록(각 항목은 식별자 + 원문 텍스트)으로 구성된다. 이번 변경에서 구성은 그대로이나, OCR 항목의 **역할이 "판단 근거"에서 "박스 매칭용 참조표"로 축소**된다.
- **추출된 메뉴**: 사진에서 판독된 메뉴명(표기 그대로), 표준 한국어 메뉴명, 가격, 그리고 선택적으로 매칭된 OCR 식별자.
- **스캔 결과 항목**: 추출된 메뉴에 기피 성분 위험도와 DB 매칭 여부를 얹은 응답 단위. 클라이언트는 식별자로 화면 위치를 찾는다.
- **모델 호출 비용 기록**: 호출한 모델 이름, 입력/출력 토큰, 산정된 비용. 모델 교체 시 이름과 단가가 함께 바뀐다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 동일한 사진에 정확한 OCR 목록과 오염된(오탈자·누락·환각 포함) OCR 목록을 각각 보냈을 때, 추출되는 메뉴명·가격 집합이 100% 동일하다.
- **SC-002**: 사진에 인쇄된 메뉴 중 클라이언트 OCR 이 놓친 메뉴도 결과에 포함되어, 검증용 메뉴판 표본에서 메뉴 커버리지가 현행 대비 하락하지 않는다.
- **SC-003**: 검증용 메뉴판 표본에서 사진 기준 메뉴명 판독 정확도가 현행 대비 개선된다(오탈자 그대로 반환되는 사례 감소).
- **SC-004**: OCR 대응 항목이 있는 결과 중 `idx` 가 올바른 항목을 가리키는 비율이 현행 대비 하락하지 않으며, 한 응답 안에서 `idx` 중복은 0건이다.
- **SC-005**: 기존 클라이언트 앱을 수정하지 않고도 스캔이 정상 동작한다(요청 거절·응답 파싱 실패 0건).
- **SC-006**: 스캔 1회당 기록되는 비용이 새 모델의 공시 단가와 일치한다(오차 없음).
- **SC-007**: 스캔 응답 시간이 기존 타임아웃 정책 안에 머무르며 사용자 체감 대기가 눈에 띄게 늘지 않는다.

## Assumptions

- 클라이언트 OCR 목록은 **계속 필수**로 받는다. 없애면 화면의 글자 박스에 위험도를 얹을 수 없어 스캔 UX 가 성립하지 않는다. 요청 계약 불변 요구도 이를 강제한다.
- "OCR 을 무시한다"는 **판독(무엇이 메뉴이고 어떤 글자인가)에서 배제한다**는 뜻이며, 판독이 끝난 결과를 클라이언트 화면 좌표에 이어 붙이는 **매칭 용도로는 계속 참조**한다는 뜻으로 해석했다. 매칭까지 없애면 모든 `idx` 가 비어 사용자 화면에 아무 배지도 그려지지 않는다.
- 사진은 기존과 동일한 경로(업로드된 이미지 위치)로 모델에 전달되며 전달 방식은 이번 범위 밖이다.
- 스캔 이후 단계(메뉴명 정규화, DB 매칭, 기피 성분 위험도 산정, 스캔 이력 기록)는 변경하지 않는다.
- 모델 교체는 스캔 비전 경로에만 적용하며, 배치의 기피 성분 판정·이미지 생성·임베딩 등 다른 모델 사용처는 건드리지 않는다.
- 정확도 개선 검증은 자동화 지표가 아니라 검증용 메뉴판 표본에 대한 수동 비교로 판정한다(현재 정확도 회귀 스위트가 없다).
- `gpt-5.6-luna` 는 이미지 입력과 구조화된 JSON 응답을 모두 지원하므로 현행 호출 형태(사진 + JSON 객체 응답)를 그대로 쓸 수 있다.
