# Feature Specification: 배치 콘텐츠 4작업 LLM 호출 인터페이스 사전 선언

**Feature Branch**: `kb-182-llm-client-interface`

**Created**: 2026-07-22

**Status**: Draft

**Input**: User description: "kb-182에 대하여 4가지 작업에서 실제 llm api를 호출해야 하는데, 이때 배치쪽에서 외부 클라이언트 호출과 강결합을 피하고자 인터페이스를 선언하고 실제 구현을 infra모듈에서 할 수 있도록 사전작업을 하려고 함. 즉 인터페이스를 선언해두는 작업을 할 것임"

## Clarifications

### Session 2026-07-22

- 범위 확장(사용자 지시): 계약 선언에 그치지 않고, LLM 호출 후 원하는 응답 포맷과 **데이터베이스 적재에 적합한 형태의 DTO 까지** 이번 범위에서 모두 정의한다.
- Q: 번역(이름·설명) 호출·응답 단위는? → A: 일괄 — 호출 1번에 전 대상 언어(9종)를 언어코드→텍스트 맵으로 반환. DTO 는 DB 의 번역 맵 컬럼 형태와 일치시킨다.
- Q: 설명 생성 DTO 에 맵기(spiciness)를 포함하나? → A: 포함 — 설명 생성 호출 1번으로 설명과 맵기(정수)를 함께 산출해 맵기 센티널(-1)을 해소한다.
- Q: 사진 생성 계약의 출력 형태는? → A: 스토리지 참조 키 — 호출자(배치)가 저장할 키를 입력으로 지정하고, 구현이 그 위치에 저장까지 완료한 뒤 키를 반환한다(예: Lambda 가 S3 에 직접 저장). 절대 URL 은 반환·적재하지 않는다(CDN 키 관례 유지). 같은 키 재호출은 덮어쓰기로 멱등이다.
- 기피성분 매핑 출력 DTO 는 기존 DB 적재 형태와 동일한 "성분 코드 + 포함 가능성(%)" 목록으로 정의한다(질문 없이 확정 — DB 형태가 이미 고정).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 콘텐츠 4작업 호출 계약 선언 (Priority: P1)

배치 파이프라인(KB-182 골격)의 콘텐츠 4작업 — 이름 번역, 설명 생성(원문+번역), 사진 생성, 기피성분 매핑 — 이 외부 LLM 호출을 필요로 한다. 각 작업이 "무엇을 주고 무엇을 받는지"를 계약(인터페이스)으로 먼저 선언해, 배치 쪽 코드는 계약만 알고 외부 제공자의 구체 기술은 전혀 모르게 한다.

**Why this priority**: 이 계약이 있어야 후속 태스크(KB-183·184·209)의 실제 구현과 배치 스텝 개발이 서로를 기다리지 않고 병렬로 진행될 수 있다. 계약이 없으면 배치 코드가 외부 클라이언트에 직접 묶여 교체·테스트가 어려워진다.

**Independent Test**: 4작업 각각의 계약이 입력·출력·실패 표현을 갖춰 선언되어 있고, 배치 모듈이 외부 연동 기술 없이 계약만 참조해 컴파일되는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** KB-182 배치 골격, **When** 콘텐츠 4작업 각각에 대응하는 호출 계약을 찾으면, **Then** 이름 번역·설명 생성·사진 생성·기피성분 매핑 4종의 계약이 모두 선언되어 있다.
2. **Given** 선언된 계약, **When** 각 계약의 입출력을 확인하면, **Then** 입력(대상 음식 정보)과 출력(생성된 콘텐츠), 실패 시 표현이 계약만 읽고 파악 가능하다.
3. **Given** 배치 모듈, **When** 의존 관계를 검사하면, **Then** 외부 LLM 연동 기술에 대한 직접 의존 없이 계약만 참조한다.

---

### User Story 2 - 대체 구현(페이크)으로 배치 검증 가능 (Priority: P2)

배치 골격의 테스트는 실제 외부 호출 없이 진행되어야 한다. 계약이 선언되어 있으므로 테스트에서는 페이크 구현을 꽂아 스텝 흐름(성공·실패 격리·READY 전이)을 검증할 수 있다.

**Why this priority**: KB-182 스펙의 "골격 검증은 페이크 스텝으로 수행한다"는 전제를 계약 수준에서 실현한다. P1(계약 선언)이 선행되어야 의미가 있다.

**Independent Test**: 계약의 페이크 구현을 테스트에서 주입해, 외부 네트워크 없이 배치 스텝 시나리오가 실행되는지로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 계약의 페이크 구현, **When** 배치 스텝 테스트에 주입하면, **Then** 외부 호출 없이 스텝 흐름이 검증된다.
2. **Given** 페이크가 실패를 반환하는 시나리오, **When** 배치 스텝이 실행되면, **Then** 실패가 계약의 실패 표현대로 전달되어 해당 음식 1건에 격리된다.

---

### Edge Cases

- 실제 구현이 아직 없는 상태에서 배치 앱을 부팅하면? — 계약 선언만으로는 부팅이 깨지지 않아야 한다(계약을 필수 주입으로 강제하지 않거나, 후속 구현 전까지 배선하지 않는다).
- 외부 호출이 실패(시간 초과·제공자 오류)하면? — 계약은 실패를 호출자에게 전달 가능한 형태로 표현해야 하며, 실패 처리 정책(재시도 등)은 계약이 아닌 호출자(배치 스텝) 책임이다.
- 하나의 음식에 4작업 중 일부만 필요한 경우? — 각 작업 계약은 독립적으로 호출 가능해야 한다(전부 호출을 강제하지 않는다).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 콘텐츠 4작업(이름 번역·설명 생성·사진 생성·기피성분 매핑) 각각에 대응하는 외부 호출 계약을 선언해야 한다.
- **FR-002**: 각 계약은 입력(대상 음식 식별·원문 정보)과 출력(생성된 콘텐츠)을 DTO 로 명시해야 하며, 출력 DTO 는 데이터베이스 적재 형태(음식의 콘텐츠 필드)와 직접 대응해 변환 없이 적재 가능해야 한다.
- **FR-002a**: 이름 번역·설명 번역 계약은 호출 1번에 전 대상 언어(9종)를 언어코드→텍스트 맵으로 일괄 반환해야 한다.
- **FR-002b**: 설명 생성 계약의 출력 DTO 는 설명(원문+번역 맵)과 함께 맵기(정수)를 포함해, 한 호출로 맵기 미정 상태(-1)를 해소할 수 있어야 한다.
- **FR-002c**: 사진 생성 계약은 호출자가 지정한 스토리지 참조 키를 입력으로 받아, 구현이 해당 위치에 이미지 저장까지 완료한 뒤 그 키를 반환해야 한다. 절대 URL 을 반환하거나 적재해서는 안 된다. 같은 키로의 재호출은 덮어쓰기로 멱등이어야 한다.
- **FR-002d**: 기피성분 매핑 계약의 출력 DTO 는 "성분 코드 + 포함 가능성(%)" 항목의 목록으로, 기존 음식 기피성분 적재 형태와 동일해야 한다.
- **FR-003**: 각 계약은 외부 호출 실패를 호출자에게 전달 가능한 형태로 표현해야 한다.
- **FR-004**: 배치 모듈은 외부 LLM 연동 기술에 직접 의존하지 않고 계약만 참조해야 한다(의존 방향 검사로 검증 가능).
- **FR-005**: 계약의 실제 구현은 외부 연동 전담 모듈에서 후속 태스크(KB-183·184·209)로 제공될 수 있어야 하며, 이번 범위에서는 구현 없이도 전체 빌드·배치 부팅이 유지되어야 한다.
- **FR-006**: 계약은 테스트에서 페이크 구현으로 대체 가능해야 한다.

### Key Entities

- **콘텐츠 생성 계약**: 배치가 외부 지능형 서비스에 위임하는 작업 1종의 입력·출력·실패 표현. 4작업 각각 존재하며, 출력 DTO 는 DB 적재 형태와 직접 대응한다:
  - 이름 번역 → 언어코드→텍스트 맵(9개 언어 일괄)
  - 설명 생성 → 설명 원문 + 언어코드→텍스트 맵(9개 언어 일괄) + 맵기(정수)
  - 사진 생성 → 저장 완료된 스토리지 참조 키(호출자가 키 지정)
  - 기피성분 매핑 → "성분 코드 + 포함 가능성(%)" 목록
- **음식(Food)**: 계약 호출의 대상. 계약 입력은 음식의 원문 정보(한국어 이름 등)를, 출력은 해당 작업의 산출 콘텐츠를 담는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 콘텐츠 4작업 전부에 대해 호출 계약과 입·출력 DTO 가 선언되어 있다(4/4). 각 출력 DTO 는 음식의 대응 콘텐츠 필드에 변환 로직 없이 적재 가능하다.
- **SC-002**: 배치 모듈에서 외부 LLM 연동 기술로의 직접 의존이 0건이다(의존 검사 통과).
- **SC-003**: 실제 구현이 하나도 없는 상태에서 전체 빌드와 배치 앱 부팅이 성공한다.
- **SC-004**: 후속 태스크(KB-183·184·209)가 계약 변경 없이 구현 추가만으로 진행 가능한 상태다.

## Assumptions

- "4가지 작업"은 KB-182 골격 스펙의 콘텐츠 4작업 — 이름 번역, 설명 생성(원문+번역), 사진 생성, 기피성분 매핑 — 을 가리킨다. 사진 생성도 외부 지능형 API 호출로 본다.
- 이번 범위는 계약 선언 + 입·출력 DTO 정의(+페이크 대체 가능성)까지이며, 실제 외부 호출 구현·배치 스텝 본문 구현은 후속 태스크(KB-183·184·209) 범위다. 사진 생성 구현 방식(예: Lambda 가 S3 에 직접 저장)은 KB-184 에서 결정하되, 어떤 방식이든 이 계약(키 지정 입력 → 저장 완료 키 반환)을 만족해야 한다.
- 계약 선언 위치는 기존 외부 client seam 관례(공유 커널의 seam 선언, 전담 모듈 구현)를 따른다.
- 호출 실패의 재시도·건너뛰기 정책은 KB-182 골격의 실패 격리 규칙을 따르며 이번 범위 밖이다.
- LLM 호출 비용 기록(KB-155 원장)과의 연동은 구현 태스크 범위로, 계약 선언 단계에서는 다루지 않는다.
