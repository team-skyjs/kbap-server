# Feature Specification: LLM 스코어링 호출 비용 절감 — 호출당 ₩1 미만 (프롬프트 압축·텍스트 역할 분리)

**Feature Branch**: `kb-93-llm-scoring-cost-reduction`

**Created**: 2026-07-07

**Status**: Draft

**Input**: Jira KB-93 — "[BE] LLM 스코어링 호출 비용 절감 — 호출당 ₩1 미만 (프롬프트 압축·텍스트 역할 분리)"

## 개요

KB-53 은 조사 대기열 음식을 10개 청크로 3개 LLM(OpenAI·Upstage·Gemini)에 병렬 호출해 기피성분 81종 포함 신뢰도를 종합하는 스코어링 파이프라인을 만들었다. **1차 실측 결과 호출 비용이 목표(청크당·모델당 ₩1 미만)를 크게 초과**했다 — OpenAI 약 ₩10, Gemini 약 ₩6.3, Upstage 약 ₩0.9. 원인을 분석하니 **출력 토큰의 80% 이상이 음식 설명(한국어 + 9개 언어 번역) 텍스트**였고, 스코어링 판단(key-value JSON)·이름 번역(언어키 객체)의 포맷 오버헤드도 컸다.

이 기능은 **스코어링의 산출물·정확도는 유지**하면서 **호출 비용만** 목표 이하로 낮춘다. 세 갈래로 접근한다: (1) 프롬프트·응답 **포맷 압축**(인덱스 매칭·배열 판단·지시문 축약), (2) **텍스트 역할 분리**(음식명 번역은 한 모델 단독, 음식 설명 생성·번역은 스코어링 호출에서 제외), (3) **모델·옵션 튜닝**(더 싼 모델·추론 최소화·출력 상한·프리픽스 캐싱 정렬). **청크당 모델별 API 호출은 1회로 유지**한다.

스코어링 도메인 로직(프롬프트·파싱·앙상블)은 KB-53 과 동일하게 `:core:research` 순수 서비스에 있고, 조율은 `:app:batch` 잡, 벤더 호출은 `:infra:llm` 이다. 이 기능은 **주로 프롬프트 생성·응답 파싱 계약을 압축 포맷으로 교체**하고 배치 조율에서 모델별 프롬프트 구성을 분기한다. 최종 신뢰도 산출 의미(`inclusionConfidence` 정수 1~100)·3모델 전량 취합 확정 규칙·앙상블 공식은 **바꾸지 않는다**.

## Clarifications

### Session 2026-07-07

- Q: 이 기능이 스코어링 결과값(신뢰도·앙상블 공식·확정 규칙)을 바꾸나? → A: 아니오. 결과 산출의 의미·범위·집계 공식·3모델 전량 취합 확정은 **KB-53 그대로 유지**한다. 이 기능은 **동일 산출을 더 싸게 얻는** 포맷·역할·모델 최적화만 한다.
- Q: 음식 설명(한국어 생성 + 9개 언어 번역)은 어떻게 되나? → A: **스코어링 호출에서 완전히 제외**한다(출력 토큰의 최대 비중). 설명 생성·번역은 **별도 티켓으로 분리**하며 이 기능의 범위 밖이다. 저장(KB-54) 시 설명이 비어 있어도 파이프라인은 정상 동작해야 한다.
- Q: 음식명 9개 언어 번역은 계속 받나? → A: 예. 단 **한 모델(Gemini) 단독**으로만 받는다(3모델 중복 수신 제거). 나머지 두 모델은 번역을 요청·수신하지 않는다. 청크당 모델별 호출은 1회를 유지하므로, Gemini 의 그 1회 호출이 스코어링 판단 + 이름 번역을 함께 담는다.
- Q: 청크당 API 호출 횟수는? → A: **모델별 1회로 유지**한다(KB-53 과 동일). 역할 분리는 호출을 늘리지 않고 **각 모델 호출의 요청·응답 내용을 줄이는** 방식으로 한다.
- Q: 이름 번역이 일부 언어 누락되면 청크를 확정 못 하나? → A: 아니오. **청크 확정은 스코어링 판단(3모델 전량 취합)** 으로만 게이트한다. 이름 번역은 KB-53 과 같이 **best-effort 병합**이며 누락 언어는 확정을 막지 않는다(후속 보완 대상). 단 번역 담당 모델(Gemini) 호출 자체가 실패하면 그 청크의 스코어링도 미취합이라 어차피 미확정된다.
- Q: 비용 목표의 판정 단위는? → A: **청크(음식 10개) 1개를 스코어링할 때 3개 모델 각각의 1회 호출 비용**이 ₩1 미만이어야 한다. 실측은 실행 시 남는 토큰/비용 로그(입력·출력 토큰 + USD/KRW)로 확인한다.

### Amendment 2026-07-07 (실측 스모크 반영 — US2 부분 개정)

실 API 키 스모크에서 **이름 번역을 Gemini 스코어링 호출에 얹은 구조(US2)가 문제**로 드러났다: Gemini 가 번역 배열(`t`) 직렬화를 틀어(닫는 대괄호 누락) 응답 JSON 전체가 malformed 가 되며 **개선된 스코어링 판단까지 통째로 폐기**됐다(청크 미확정). 안전 직결인 스코어링을 부가 텍스트(번역)의 직렬화 안정성에 인질로 잡는 구조다.

- **결정**: 스코어링 호출에서 **이름 번역을 완전히 제거**하고 3모델을 모두 **스코어링 전용**으로 통일한다. 음식명 번역은 음식 설명과 함께 **별도 배치([KB-94](https://simhani1.atlassian.net/browse/KB-94))** 로 이관한다.
- **영향**: 아래 **FR-005·SC-003 은 본 개정으로 대체**된다(US2 의 "번역 Gemini 단독 수신"은 더 이상 유효하지 않음). FR-006(모델별 1회 호출)·비용 목표(SC-001)·설명 제거(FR-004/SC-002)·확정 게이트(FR-008)는 불변. 스코어링-전용 통일로 파싱 견고성이 오히려 향상됐다(스모크에서 scored=10/10 확인).
- **미사용 잔존**: 번역 프롬프트/파싱 기계(`ScoringPromptFactory.includeNameTranslations`·파서 `t`·`LlmFanoutClient.generate(requestFor)`)는 스코어링에서 미사용으로 남기며, KB-94 재사용 또는 후속 정리 대상이다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스코어링 프롬프트·응답을 압축 포맷으로 교체 (Priority: P1)

음식 10개 청크와 기피성분 81종 후보를 입력하면, 시스템은 이를 **압축 포맷** 프롬프트로 구성한다 — 음식과 후보 성분을 각각 **인덱스로 열거**하고, 후보 성분은 코드만 제시(한국어 라벨 제거)하며, 지시문은 축약한다. 모델은 포함으로 판단한 (음식, 성분) 조합만 **`[음식인덱스, 성분인덱스, score, probability]` 형태의 배열**로 응답하고, 시스템은 그 배열을 인덱스로 되짚어 (음식 → 성분 → {score, probability}) 구조로 파싱한다.

**Why this priority**: 판단(스코어링) 자체가 매 모델·매 청크 호출에 항상 들어가는 공통 비용이며, key-value JSON·한국어 라벨·장문 지시문의 오버헤드를 없애는 것이 절감의 토대다. 압축 포맷 계약(프롬프트 생성 + 응답 파서)만으로도 입력·출력 토큰이 줄어 그 자체로 가치 있는 슬라이스다. 역할 분리·모델 튜닝은 이 계약 위에 얹힌다.

**Independent Test**: 대표 음식 청크·후보에 대해 압축 포맷 프롬프트가 인덱스 열거·코드 전용 후보·축약 지시문·배열 응답 스키마를 담는지 골든 테스트로 검증하고, 페이크 모델의 배열 응답을 파서가 인덱스로 올바르게 되짚어 유효 범위(score 0/1/2, probability 1~100) 조합으로 파싱하며, 범위이탈·형식오류·인덱스이탈·중복 응답을 KB-53 과 동일한 규칙으로 처리하는지 검증한다(실 네트워크 불요).

**Acceptance Scenarios**:

1. **Given** 음식 10개 청크와 81종 후보가 주어지고, **When** 시스템이 압축 프롬프트를 구성하면, **Then** 프롬프트는 음식·후보를 인덱스로 열거하고, 후보는 코드만(한국어 라벨 없이) 제시하며, 기대 응답을 `[음식인덱스, 성분인덱스, score, probability]` 배열 스키마로 지시한다.
2. **Given** 모델이 일부 조합만 배열 항목으로 응답하고, **When** 응답을 파싱하면, **Then** 각 배열 항목은 인덱스로 음식·성분에 되짚어져 score(0/1/2)·probability(1~100)로 구조화되고, 응답에 없는 성분은 미포함으로 처리된다.
3. **Given** 모델이 범위이탈 probability·형식 오류·인덱스 이탈·중복 인덱스를 반환하고, **When** 파싱하면, **Then** 정의된 규칙(부분 스킵 또는 모델 실패 처리)이 KB-53 과 동일 의미로 일관 적용된다.
4. **Given** 압축 파서로 교체되고, **When** 동일 입력·동일 판단을 KB-53 포맷과 압축 포맷으로 각각 파싱하면, **Then** 최종 (음식,성분)별 판단 결과는 동일하다(포맷만 바뀌고 산출은 불변).

### User Story 2 - 텍스트 역할 분리 (이름 번역 단일 모델·설명 제외) (Priority: P1)

시스템은 스코어링 호출에서 **음식 설명(한국어 생성 + 9개 언어 번역)을 완전히 제거**하고, **음식명 9개 언어 번역은 한 모델(Gemini) 호출에서만** 요청한다. 나머지 두 모델(OpenAI·Upstage) 프롬프트는 스코어링 판단만 요청한다. `FoodContentSelector` 는 단일 소스(Gemini)로 줄어든 이름 번역을 기존 병합 규칙으로 정상 결합하고, 설명이 없어도 후속 조립·저장이 깨지지 않는다.

**Why this priority**: 설명 텍스트가 출력 토큰의 80% 이상을 차지해 **포맷 압축만으로는 목표 미달**이다. 설명 제외가 비용 절감의 최대 지렛대이고, 이름 번역을 3모델 중복에서 단일 모델로 줄이면 나머지 두 모델의 출력이 판단만 남아 급감한다. US1 과 함께 P1 인 이유다.

**Independent Test**: OpenAI·Upstage 프롬프트에는 이름 번역·설명 지시문이 없고 Gemini 프롬프트에만 이름 번역 지시문이 있는지(설명 지시문은 어느 모델에도 없음) 검증하고, 페이크 3모델 응답(Gemini 만 이름 번역 포함, 설명은 전무)에 대해 `FoodContentSelector` 가 이름 번역을 단일 소스로 병합하고 설명은 없음(null/빈값)으로 안전 처리하는지, 청크 확정이 스코어링 취합으로만 게이트되고 번역 누락으로는 막히지 않는지 검증한다.

**Acceptance Scenarios**:

1. **Given** 3개 모델용 프롬프트를 구성하고, **When** 각 모델 프롬프트를 확인하면, **Then** 어떤 모델 프롬프트에도 음식 설명 생성·번역 지시문이 없고, 이름 번역 지시문은 Gemini 프롬프트에만 있다.
2. **Given** Gemini 만 이름 번역을 응답하고 세 모델 모두 설명을 응답하지 않으며, **When** `FoodContentSelector` 가 콘텐츠를 선정하면, **Then** 이름 번역은 Gemini 결과로 채워지고 설명은 비어 있으며(null), 후속 조립·저장 경로가 예외 없이 진행된다.
3. **Given** Gemini 의 스코어링 판단은 정상이나 이름 번역 일부 언어가 누락되고, **When** 청크 확정 여부를 판정하면, **Then** 스코어링 3모델 전량 취합이 충족되면 청크는 확정되고 누락 언어는 확정을 막지 않는다.

### User Story 3 - 모델·옵션 튜닝 + 프리픽스 캐싱 정렬 + 비용 실측 (Priority: P2)

시스템은 OpenAI 모델을 **gpt-5-nano**(입력 $0.05 / 출력 $0.40 per 1M)로 쓰고 **추론 노력을 최소(minimal)** 로, 전 모델에 **출력 토큰 상한(maxTokens)** 을 둔다. 프롬프트는 **[정적: 시스템 지시 + 후보 81종] → [동적: 음식 청크]** 순서로 배치해 벤더의 프리픽스 캐싱 할인을 활용한다. 실행 시 호출마다 입력·출력 토큰과 USD/KRW 비용을 로그로 남겨 **청크당 모델별 ₩1 미만**을 실측으로 확인한다.

**Why this priority**: 포맷 압축·역할 분리(P1)로 토큰이 줄어든 위에서, 단가·옵션·캐싱을 맞춰 목표선을 확실히 통과시키고 검증한다. 결과 정확도에는 영향이 없어 P2 다.

**Independent Test**: 압축·역할 분리가 적용된 프롬프트가 정적 프리픽스(시스템+후보) 다음에 동적 음식 청크를 두는 순서인지 검증하고, gpt-5-nano 단가·추론 최소·출력 상한 설정이 반영됐는지 확인하며, 대표 청크(음식 10개)를 실행해 3개 모델 각각의 호출 비용이 토큰/비용 로그상 ₩1 미만인지 실측한다.

**Acceptance Scenarios**:

1. **Given** 스코어링 프롬프트를 구성하고, **When** 프롬프트 순서를 확인하면, **Then** 청크마다 변하지 않는 시스템 지시·후보 81종이 앞에 오고 청크별로 달라지는 음식 목록이 뒤에 온다.
2. **Given** gpt-5-nano·추론 최소·출력 상한이 설정되고, **When** 청크 10개를 실제 실행하면, **Then** 3개 모델 각각의 1회 호출 비용이 ₩1 미만으로 로그에 기록된다.
3. **Given** 출력 상한에 걸려 응답이 잘려 유효 JSON 이 아니게 되면, **When** 파싱하면, **Then** 해당 모델은 실패로 처리되고 청크는 확정되지 않으며(재조사로 남김) 그 실패가 별도 로깅된다.

### User Story 4 - 음식 설명 생성·번역 분리 티켓 등록 (Priority: P3)

스코어링에서 제외한 음식 설명 생성·번역 책임을 **별도 Jira 티켓**으로 등록해 후속 작업으로 추적한다.

**Why this priority**: 산출물이 아니라 후속 작업 관리다. 코드 변경과 독립적이며 마지막에 처리한다.

**Independent Test**: 설명 생성·번역을 다루는 별도 티켓이 KB 프로젝트에 등록돼 있고 KB-93 과 연결(또는 참조)되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 설명이 스코어링에서 제외되면, **When** 후속 작업을 정리하면, **Then** 음식 설명 생성·번역 티켓이 등록되고 이 기능 문서에서 참조된다.

---

### Edge Cases

- **응답 배열 항목의 인덱스가 청크 크기·후보 수를 벗어남** → 해당 항목만 스킵(모델 전체 실패로 보지 않음). 단 이로 인해 모델별 음식 커버리지 게이트를 못 채우면 그 모델은 미취합.
- **모델이 압축 배열 대신 예전 key-value 포맷으로 응답** → 파서는 유효 배열 항목만 취하며, 유효 판단을 추출하지 못하면 그 모델은 실패 처리(청크 미확정).
- **중복 인덱스 조합**(같은 음식·성분을 두 번) → 첫 항목만 채택, 이후 중복은 스킵(KB-53 중복 코드 처리와 동일 의미).
- **출력 상한(maxTokens) 초과로 JSON 절단** → 파싱 실패 → 모델 실패 → 청크 미확정 + 실패 로깅.
- **Gemini(번역 담당) 호출 실패** → 스코어링도 미취합이라 청크 미확정. 이름 번역은 그 청크에서 부재.
- **Gemini 스코어링 성공 + 이름 번역 일부/전부 누락** → 스코어링 취합 충족 시 청크 확정, 이름 번역은 부분/부재로 저장 대상(후속 보완).
- **세 모델 모두 설명 없음이 정상** → `FoodContentSelector` 의 설명 병합은 항상 null 을 산출하며 후속 조립·저장이 이를 허용해야 한다.
- **프리픽스 캐싱 미적용(벤더 미지원·캐시 미스)** → 비용은 캐싱 할인 없이도 압축·역할 분리만으로 목표를 만족해야 한다(캐싱은 추가 마진).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 스코어링 프롬프트에서 음식·후보 성분을 **인덱스로 열거**하고, 모델 응답을 **인덱스 기반 배열**(`[음식인덱스, 성분인덱스, score, probability]` 형태)로 받아 인덱스를 통해 음식·성분에 되짚어 파싱해야 한다.
- **FR-002**: 시스템은 후보 성분을 **코드만**으로 제시해야 한다(한국어 라벨 제거). 지시문은 의미를 유지한 채 축약해야 한다.
- **FR-003**: 압축 포맷 파서는 KB-53 파서와 **동일한 판단 결과**를 산출해야 한다 — 유효 범위(score 0/1/2, probability 1~100)·미포함 해석·미지/이탈 처리 규칙의 의미가 보존돼야 한다.
- **FR-004**: 시스템은 스코어링 호출에서 **음식 설명(한국어 생성 + 번역) 생성·수신을 완전히 제거**해야 한다 — 어떤 모델 프롬프트에도 설명 지시문이 없어야 한다.
- **FR-005**: ~~시스템은 **음식명 9개 언어 번역을 한 모델(Gemini) 호출에서만** 요청·수신해야 한다.~~ **(Amendment 2026-07-07 로 대체)** 시스템은 스코어링 호출에서 **이름 번역을 요청·수신하지 않는다** — 3모델 모두 스코어링 판단만 요청한다. 음식명 번역은 별도 배치(KB-94)로 이관한다.
- **FR-006**: 청크당 **모델별 API 호출은 정확히 1회**를 유지해야 한다(역할 분리가 호출 수를 늘리지 않는다).
- **FR-007**: `FoodContentSelector` 는 이름 번역을 **단일 소스(Gemini)** 기준으로 기존 병합 규칙에 따라 결합하고, 설명이 없을 때 null(빈 콘텐츠)을 안전하게 산출해야 한다.
- **FR-008**: 청크 확정은 **스코어링 판단의 3모델 전량 취합**으로만 게이트해야 한다 — 이름 번역의 언어 누락은 확정을 막지 않는다.
- **FR-009**: 시스템은 OpenAI 모델을 **gpt-5-nano** 로, **추론 노력을 최소**로 설정하고, **전 모델에 출력 토큰 상한**을 두어야 한다. 단가(입력 $0.05 / 출력 $0.40 per 1M)를 비용 계산에 반영해야 한다.
- **FR-010**: 프롬프트는 **정적(시스템 지시 + 후보 81종)을 앞**에, **동적(음식 청크)을 뒤**에 배치해 프리픽스 캐싱을 활용해야 한다.
- **FR-011**: 시스템은 호출마다 입력·출력 토큰과 USD/KRW 비용을 로그로 남겨 청크당 모델별 비용을 **실측 검증 가능**하게 해야 한다.
- **FR-012**: 압축 포맷 프롬프트·파서는 **골든 테스트를 갱신**해 TDD 로 전환해야 한다(프롬프트 문자열·파싱 결과 검증).
- **FR-013**: 음식 설명 생성·번역을 다루는 **별도 티켓을 등록**하고 이 기능 문서에서 참조해야 한다. → **[KB-94](https://simhani1.atlassian.net/browse/KB-94)** 등록·연결(Relates KB-93).

### Key Entities *(include if feature involves data)*

- **압축 스코어링 프롬프트**: 인덱스로 열거된 음식 목록·후보 성분(코드 전용)·축약 지시문·배열 응답 스키마로 구성된, 모델 호출용 정적+동적 프롬프트. 모델별로 이름 번역 지시문 포함 여부가 다르다.
- **인덱스 기반 판단 항목**: 응답 배열의 한 원소 — 음식 인덱스·성분 인덱스·score(0/1/2)·probability(1~100). 파서가 인덱스로 원래 음식/성분에 되짚는다.
- **모델 스코어링 결과**(기존 `ModelScoring` 유지): (음식 → 포함 판단 목록) + (음식 → 이름 번역) + 커버리지. 설명은 더 이상 담기지 않는다.
- **음식 콘텐츠 선정 결과**(기존 `FoodContent` 유지): 병합된 이름 번역 + 설명(이번 범위에서는 항상 없음).
- **호출 비용 로그**: 모델·입력 토큰·출력 토큰·USD·KRW. 청크당 모델별 ₩1 미만 실측의 근거.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 대표 청크(음식 10개)를 실제 실행할 때 **3개 모델 각각의 1회 호출 비용이 ₩1 미만**임이 토큰/비용 로그로 확인된다.
- **SC-002**: 스코어링 호출의 **출력 토큰에 음식 설명 텍스트가 0** 이다(설명 지시문·수신 완전 제거).
- **SC-003**: ~~음식명 9개 언어 번역은 **정확히 한 모델**에서만 수신된다.~~ **(Amendment 2026-07-07 로 대체)** 스코어링 호출의 **어떤 모델 응답에도 이름 번역이 없다**(3모델 스코어링 전용). 이름 번역은 KB-94 로 이관.
- **SC-004**: 청크당 **모델별 API 호출 수가 정확히 1회**로 유지된다(KB-53 대비 증가 없음).
- **SC-005**: 압축 포맷 전환 후에도 (음식,성분)별 **최종 판단 결과가 KB-53 과 동일**하다(동일 입력·동일 모델 판단 기준, 포맷만 변경).
- **SC-006**: 압축 프롬프트·파서·역할 분리·selector 병합에 대한 단위/골든 테스트가 통과한다.
- **SC-007**: 음식 설명 생성·번역 후속 티켓이 등록되어 추적된다. → **[KB-94](https://simhani1.atlassian.net/browse/KB-94)**.

## Assumptions

- 스코어링의 **결과 의미·범위(`inclusionConfidence` 1~100)·앙상블 공식·3모델 전량 취합 확정 규칙**은 KB-53 그대로이며 이 기능에서 바꾸지 않는다.
- **이름 번역은 best-effort** 다 — 단일 소스(Gemini)에서 일부 언어가 누락돼도 청크 확정을 막지 않으며, 누락은 후속 보완 대상이다(저장은 KB-54).
- **음식 설명 생성·번역은 이 기능의 범위 밖**이며 별도 티켓에서 다룬다. 이 기능은 스코어링 호출에서 설명을 제거하는 데까지만 책임진다.
- 비용 목표(₩1 미만)의 환율 기준은 기존 배치 설정의 **1 USD = 1,500 KRW 고정 추정**을 따른다.
- **번역 담당 모델은 Gemini** 로 고정한다(3모델 중 이름 번역 품질·비용 균형상). 향후 담당 모델 변경은 별도 결정 사항이다.
- 프리픽스 캐싱은 **추가 마진**이며, 벤더가 미지원하거나 캐시 미스여도 압축·역할 분리만으로 목표를 만족해야 한다.
- 파서의 인덱스 이탈·형식 오류·중복 처리 정책은 **KB-53 의 부분 스킵 + 모델별 음식 커버리지 게이트**와 동일한 의미를 유지한다.
- 위험도 판정(KB-9)·DB 영속(KB-54)은 KB-53 과 동일하게 이 기능의 범위 밖이다.
