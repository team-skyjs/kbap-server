# Research: 스캔 2.0 — 메뉴판 아닌 사진의 빈 결과 처리

## R1. 처리 방식 — 프롬프트 규칙으로 빈 결과 수렴 (서버 코드 무변경)

- **Decision**: `SERVER_OCR_SYSTEM_PROMPT` 에 "메뉴판으로 추정되지 않거나 메뉴를 확인할 수 없으면 빈 배열 `[]` 반환 + 사진에서 읽히지 않는 메뉴 날조 금지" 규칙을 추가한다. 서버 코드는 바꾸지 않는다.
- **Rationale**: 1.0 의 주 경로가 바로 이것이다 — 1.0 프롬프트의 환각 제외 규칙(근거 없는 OCR 제외·메뉴 아닌 텍스트 제외) 덕에 비메뉴판 사진이 빈 목록(200)으로 수렴한다. 파서(`MenuBoardResultParser`)는 빈 배열을 이미 빈 목록으로 처리하고, `ScanService` 는 빈 추출을 200 + 빈 items 로 반환하며 히스토리도 기록하지 않는다(기존 코드 확인). 사용자 결정(2026-08-13, KB-330 개정).
- **Alternatives considered**: ①명시 신호(`notMenuBoard` 플래그) + 서버에서 SCAN-002 변환 — KB-330 초안이었으나 1.0 의 실제 주 경로는 503 이 아니라 빈 목록 200 이라 "1.0 과 동일한 처리"가 아니어서 폐기. ②사전 분류 LLM 호출 추가 — 호출 2배 비용, 과설계.

## R2. 규칙 문안 방향 — 판정 기준을 모델에 위임

- **Decision**: 프롬프트에는 "메뉴판(음식 이름과 가격이 나열된 판·차림표)으로 추정되지 않으면 빈 배열만 출력"과 "사진에서 확실히 읽히는 메뉴만 포함, 추측·보완 금지" 수준의 규칙을 넣는다. 신뢰도 임계값·카테고리 열거 같은 세밀한 판정 기준은 넣지 않는다.
- **Rationale**: 1.0 규칙도 같은 위임 수준("사진에 근거가 없는 항목 제외")으로 충분히 동작해 왔다. 과도한 기준 열거는 정상 메뉴판 회귀(과잉 거부) 위험을 키운다 — US2(무회귀)가 우선.
- **Alternatives considered**: 판정 예시 목록(영수증·간판·셀카…) 열거 — 예시 밖 케이스에서 오히려 혼란, 1.0 프롬프트의 "예시는 원칙의 예시일 뿐" 관례에 따라 최소화.

## R3. 검증 전략 — 결정 경로는 자동, 프롬프트 실효성은 수동

- **Decision**: 자동 테스트는 결정적인 서버 경로만 고정한다 — 파서의 "빈 배열 → 빈 목록" 계약(`MenuBoardResultParserTest`, 케이스 없으면 추가)과 기존 `FakeMenuBoardVisionExtractor` 기반 통합 테스트(빈 추출 → 200 빈 items). 프롬프트 실효성(실제 비메뉴판 사진에서 빈 배열이 나오는가)은 dev 환경에서 비메뉴판 표본(풍경·셀카·영수증·간판)과 정상 메뉴판 표본을 수동 스캔해 확인한다.
- **Rationale**: LLM 출력은 비결정적이라 CI 에서 실모델 호출 테스트는 플레이키 + 비용. 헌법 I 은 "테스트 가능한 단위"에 적용 — 프롬프트 문자열 자체의 단위 테스트(문구 포함 검사)는 회귀 방지 가치가 없어 만들지 않는다.
- **Alternatives considered**: LLM eval 하네스 구축 — 표본 수십 장 자동 평가는 kbap-langchain 쪽 자산이며 이 태스크(SP 1) 범위 밖.

## R4. 1.0 프롬프트 무변경

- **Decision**: `SYSTEM_PROMPT`(1.0, 클라이언트 OCR 매칭)는 건드리지 않는다.
- **Rationale**: 1.0 은 이미 환각 제외 규칙을 갖고 있고 스펙 범위 밖(Edge Cases 명시). 두 프롬프트를 같이 만지면 무회귀 검증 면적만 넓어진다.
