# Feature Specification: 아키텍처 단순화 — persistence 모듈 해체·port 폐기·JPA 연관관계 제거

**Feature Branch**: `kb-134-architecture-simplification`

**Created**: 2026-07-13

**Status**: Draft

**Input**: KB-134 — "[BE] 아키텍처 단순화 — persistence 모듈 해체·port 폐기·JPA 연관관계 제거" (KB-101 클린아키텍처 폐기 결정 흡수)

## User Scenarios & Testing *(mandatory)*

이 기능의 사용자는 **이 코드베이스를 만지는 개발자**다. 최종 사용자(앱)는 아무 변화도 느끼지 못해야 한다 — 순수 구조 리팩토링이며 동작 변경은 없다.

### User Story 1 - 도메인 하나를 고칠 때 한 모듈만 열면 된다 (Priority: P1)

개발자가 회원 기능을 수정한다. 지금은 회원 하나를 다루는 데 도메인 모델(Member)·port 인터페이스(MemberRepository)·JPA 엔티티(MemberJpaEntity)·Spring Data 리포지토리(MemberJpaRepository)·어댑터(MemberRepositoryAdapter) 다섯 조각이 두 모듈(:core:member·:infra:persistence)에 흩어져 있다. 변경 후에는 도메인 모듈 하나 안에 도메인 모델·도메인 서비스·영속 코드가 함께 있어, 그 모듈만 열면 된다. port 인터페이스와 어댑터는 사라진다.

**Why this priority**: 이 리팩토링의 존재 이유다. 얻는 것(계층 교체 가능성)에 비해 유지 비용(조각 수·폴더 뎁스·보일러플레이트)이 크다는 판단이 이슈의 출발점이다.

**Independent Test**: 임의 도메인(예: member)의 영속 코드가 해당 도메인 모듈 안에 있고, `:infra:persistence` 모듈과 리포지토리 port·어댑터가 존재하지 않음을 확인하면 단독 검증된다.

**Acceptance Scenarios**:

1. **Given** 리팩토링 완료 상태, **When** 임의 도메인의 코드를 찾으면, **Then** 도메인 모델·도메인 서비스·JPA 엔티티·Spring Data 리포지토리가 모두 그 도메인 모듈 하나 안에 있다.
2. **Given** 리팩토링 완료 상태, **When** 저장소를 검색하면, **Then** `:infra:persistence` 모듈·리포지토리 port 인터페이스·`RepositoryAdapter` 가 하나도 없다.
3. **Given** 리팩토링 완료 상태, **When** 도메인 모델과 JPA 엔티티를 보면, **Then** 둘은 여전히 분리돼 있고 변환(toDomain/from)은 엔티티 안에 그대로 있다 — 위치만 도메인 모듈로 옮겨졌다.

---

### User Story 2 - 도메인 경계는 모듈 밖에서 컴파일러가 지킨다 (Priority: P1)

각 도메인 모듈은 도메인 서비스(MemberService·FoodService 같은) 하나를 공개 창구로 두고, 영속 코드(엔티티·Spring Data 리포지토리)는 모듈 밖에서 접근할 수 없게 감춘다. application 계층은 도메인 서비스만 조합해 유스케이스를 만들고, 컨텍스트 간 조합은 application 에서만 한다는 규약은 그대로다.

**Why this priority**: port 를 폐기해도 경계가 무너지면 리팩토링이 아니라 퇴보다. 모듈이 컴파일 단위라 접근 제한(internal)을 컴파일러가 강제하므로, port 없이도 경계가 지켜진다는 것이 이 설계의 핵심 전제다.

**Independent Test**: 도메인 모듈 밖(application·app)에서 엔티티나 Spring Data 리포지토리를 참조하는 코드를 작성하면 컴파일이 실패하는지, 자동화된 경계 검증(ArchUnit)이 새 규칙으로 통과하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 리팩토링 완료 상태, **When** 도메인 모듈 밖에서 엔티티·Spring Data 리포지토리를 참조하려 하면, **Then** 컴파일이 실패한다(internal 경계).
2. **Given** 리팩토링 완료 상태, **When** 유스케이스 코드를 보면, **Then** 도메인 서비스만 호출하며 영속 코드를 직접 만지지 않는다.
3. **Given** 리팩토링 완료 상태, **When** 자동화된 경계 검증을 실행하면, **Then** 새 구조의 규칙(도메인 모듈 간 직접 의존 금지, 엔티티는 도메인 모듈에만, JPA 연관관계 애너테이션 전면 금지, 컨트롤러 매핑은 /api/v 시작, app:api 는 엔티티 미참조)이 전부 통과한다.

### User Story 3 - N+1 이 구조적으로 발생할 수 없다 (Priority: P2)

엔티티 간 JPA 연관관계(@OneToMany·@ManyToOne·@OneToOne·@ManyToMany)를 전부 끊는다. 엔티티는 참조를 id 값으로만 들고, 연관 데이터가 필요하면 도메인 서비스에서 id(또는 id 목록)로 명시적으로 조회한다. 지연 로딩 자체가 없으니 N+1 과 LazyInitializationException 이 구조적으로 불가능해진다. 데이터 정합성(외래키 제약)은 코드가 아니라 DB 스키마가 계속 강제한다.

**Why this priority**: 단순화의 두 번째 축이다. US1·US2(모듈 재배치)와 독립적으로 검증 가능하지만, 같은 파일들을 만지므로 함께 수행한다.

**Independent Test**: 전체 엔티티에서 연관관계 애너테이션이 0건인지 검색으로 확인하고, 외래키 제약이 DB 스키마(마이그레이션)에 존재하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 리팩토링 완료 상태, **When** 전체 엔티티를 검색하면, **Then** JPA 연관관계 애너테이션이 0건이고 참조는 id 값 컬럼뿐이다.
2. **Given** 연관 데이터가 필요한 조회, **When** 도메인 서비스가 처리하면, **Then** id 목록으로 한 번에 조회한다(건별 반복 조회로 N+1 을 재현하지 않는다).
3. **Given** 연관관계 제거 후, **When** DB 스키마를 보면, **Then** 기존 외래키 제약은 그대로 유지된다(제약 강제 주체가 ORM 이 아니라 스키마).

### User Story 4 - 모듈 이름이 역할을 그대로 말한다 (Priority: P2)

모듈 명칭을 개편한다 — 도메인 컨테이너 `core/` → `domain/`(`:domain:food` 등), 공통 모듈 `:core:kernel` → `:core`. 패키지·컨벤션 플러그인·경계 검증·문서 표기가 모두 새 명칭을 따른다. 모든 도메인 모듈이 상속해야 하는 영속 공통 코드(BaseEntity·EntityStatus)는 공통 모듈로 옮긴다.

**Why this priority**: KB-101 에서 흡수한 결정이다. 재배치(US1)와 함께하지 않으면 대규모 이동을 두 번 하게 된다.

**Independent Test**: 새 모듈 경로(`:domain:*`·`:core`)로 전체 빌드가 성공하고, 옛 경로(`:core:*`·`:infra:persistence`)가 남아 있지 않음을 확인한다.

**Acceptance Scenarios**:

1. **Given** 리팩토링 완료 상태, **When** 모듈 트리를 보면, **Then** 도메인은 `:domain:<이름>`, 공통은 `:core` 이고 옛 명칭은 없다.
2. **Given** 리팩토링 완료 상태, **When** 영속 공통 코드(BaseEntity·EntityStatus)를 찾으면, **Then** 공통 모듈에 있고 모든 도메인 모듈의 엔티티가 이를 상속한다.

---

### User Story 5 - 쓰지 않는 것은 남기지 않는다 (Priority: P3)

실제 코드가 한 줄도 없는 MongoDB 잔재(의존성·설정 블록·로컬 컨테이너)를 제거한다.

**Why this priority**: 죽은 설정은 새로 온 개발자를 오도하고 로컬 환경을 무겁게 한다. 위험이 없는 정리라 우선순위는 낮다.

**Independent Test**: 저장소에서 MongoDB 관련 의존성·설정·컨테이너 정의가 0건인지 검색으로 확인하고, 두 앱이 정상 부팅하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 리팩토링 완료 상태, **When** 저장소를 검색하면, **Then** MongoDB 의존성·yml 설정 블록·로컬 컨테이너 정의가 없다.
2. **Given** MongoDB 제거 후, **When** 두 앱(api·batch)을 부팅하면, **Then** 정상 기동한다.

---

### Edge Cases

- **페이크 port 에 의존하던 테스트**: port 가 사라지면 유스케이스 테스트의 페이크 리포지토리도 사라진다. 도메인 서비스를 스텁하거나 통합 테스트로 옮겨 다시 쓴다 — 이 태스크에서 비용이 가장 큰 부분이며, 테스트가 검증하던 **의미**(시나리오)는 보존해야 한다.
- **배치 앱**: api 와 같은 도메인·영속을 공유하므로 동일하게 새 구조를 따른다. 배치 잡이 port 를 직접 쓰던 자리도 도메인 서비스 호출로 바뀐다.
- **placeholder 도메인(review)**: 코드가 비어 있어도 모듈 명칭 개편과 새 컨벤션을 함께 따른다. 후속 리뷰 기능(KB-128·KB-129·KB-131)이 새 구조 위에서 시작한다.
- **마이그레이션 파일명을 하드코딩해 읽는 테스트**(시드 동기화 테스트): 파일 위치·이름이 바뀌면 조용히 깨진다. 이번 변경으로 기존 마이그레이션 파일을 옮기거나 리네임하지 않는다.
- **이미 적용된 DB 스키마**: 이 리팩토링은 코드 구조만 바꾼다. 기존 테이블·컬럼·제약은 변경하지 않으며, 스키마에 외래키 제약이 빠져 있던 곳이 발견되면 새 마이그레이션으로 추가만 한다.
- **LLM 어댑터 모듈(:infra:llm)**: 해체 대상이 아니다. 그대로 둔다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `:infra:persistence` 의 엔티티·Spring Data 리포지토리를 각 도메인 모듈로 옮기고 모듈을 삭제해야 한다. 어댑터 클래스는 옮기지 않고 폐기한다.
- **FR-002**: 리포지토리 port 인터페이스를 전부 제거해야 한다.
- **FR-003**: 각 도메인 모듈은 영속 접근의 공개 창구를 도메인 서비스로 한정하고(member 는 `RefreshTokenStore` 구체 클래스를 포함), 엔티티·Spring Data 리포지토리는 모듈 밖에서 접근 불가(internal)여야 한다.
- **FR-004**: 도메인 모델과 JPA 엔티티의 분리, 엔티티 내 변환(toDomain/from) 방식은 그대로 유지해야 한다 — 위치만 도메인 모듈로 이동한다.
- **FR-005**: 모든 엔티티에서 JPA 연관관계 애너테이션(@OneToMany·@ManyToOne·@OneToOne·@ManyToMany)을 제거하고 참조를 id 값으로만 들어야 한다.
- **FR-006**: 연관관계 제거 후에도 외래키 제약은 DB 스키마(마이그레이션)로 유지해야 한다. ON DELETE 정책은 소프트 삭제 구조라 두지 않는다.
- **FR-007**: 영속 공통 코드(BaseEntity·EntityStatus)를 공통 모듈로 옮겨 모든 도메인 모듈이 상속할 수 있어야 한다.
- **FR-008**: 모듈 명칭을 개편해야 한다 — 도메인 컨테이너 `core/` → `domain/`, `:core:kernel` → `:core`. 패키지·컨벤션 플러그인·경계 검증·문서 표기를 함께 갱신한다.
- **FR-009**: 컨벤션 플러그인과 각 모듈 빌드 구성을 새 구조에 맞게 고쳐야 한다(도메인 모듈에 Spring·JPA 의존 추가, runtimeOnly 어댑터 조립 제거, 부트앱이 도메인 모듈 직접 의존).
- **FR-010**: `:application:client` 유스케이스는 도메인 서비스를 조합하도록 바뀌어야 하며, 트랜잭션 경계와 "컨텍스트 간 조합은 application 에서만" 규약은 유지한다.
- **FR-011**: MongoDB 의존성·설정 블록·로컬 컨테이너 정의를 제거해야 한다.
- **FR-012**: 자동화된 경계 검증(ArchUnit)을 새 구조 기준으로 다시 써야 한다 — 도메인 모듈 간 직접 의존 금지, 엔티티는 도메인 모듈에만, JPA 연관관계 애너테이션 전면 금지, 컨트롤러 매핑은 /api/v 로 시작, app:api 는 엔티티 미참조.
- **FR-013**: 페이크 port 에 의존하던 테스트를 새 구조로 다시 쓰되 기존 시나리오의 검증 의미를 보존해야 하며, 전체 테스트가 통과해야 한다.
- **FR-014**: 기존 API 의 요청·응답 계약과 동작은 하나도 바뀌지 않아야 한다(순수 구조 리팩토링).
- **FR-015**: 새 구조를 ADR 로 기록하고(기존 ADR-0006·ADR-0008 대체) CLAUDE.md 의 모듈 구조·컨벤션 절을 갱신해야 한다.

### Key Entities

- **도메인 모듈(`:domain:<이름>`)**: 도메인 모델(불변) + 도메인 서비스(공개 창구) + JPA 엔티티·Spring Data 리포지토리(비공개). food·member·scan·avoidance·research·review.
- **공통 모듈(`:core`)**: 공통 타입·예외·값 객체 + 영속 공통(BaseEntity·EntityStatus). 모든 도메인 모듈이 의존한다.
- **유스케이스 모듈(`:application:client`)**: 도메인 서비스를 조합. 트랜잭션 경계. 컨텍스트 간 조합의 유일한 자리.
- **부트앱(`:app:api`·`:app:batch`)**: 도메인 모듈을 직접 의존해 조립. 엔티티는 보이지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 도메인 하나를 다루는 조각 수가 다섯(모델·port·엔티티·리포지토리·어댑터)에서 셋 이하(모델·서비스·엔티티+리포지토리)로 줄고, 그 조각이 모두 한 모듈 안에 있다.
- **SC-002**: 리포지토리 port·어댑터·`:infra:persistence` 모듈·JPA 연관관계 애너테이션·MongoDB 잔재가 저장소에서 0건이다.
- **SC-003**: 기존 API 응답이 변경 전과 100% 동일하다(회귀 0건).
- **SC-004**: 전체 테스트와 자동화된 경계 검증이 새 구조에서 전부 통과한다.
- **SC-005**: 도메인 모듈 밖에서 영속 코드에 접근하는 시도는 100% 컴파일 단계에서 차단된다.
- **SC-006**: 후속 리뷰 기능(KB-128·KB-129·KB-131)은 새 구조 위에서 영속 코드를 한 번만 작성한다(이중 작업 0건).

## Assumptions

- **이 태스크는 KB-101 을 대체·흡수한다.** 모듈 명칭 개편, 스키마 주도 외래키 제약, id 값 클래스 검토가 KB-101 에서 넘어온 결정이다.
- **참조 id 의 표현(값 클래스 vs Long)은 구현 시 선택한다.** 값 클래스를 쓰면 id 혼동을 컴파일 단계에서 막지만 타입별 컨버터 등록이 필요하고, 실익이 없다고 판단되면 Long 을 그대로 써도 동작은 동일하다 — 이슈가 명시적으로 구현 단계 선택으로 남겼다.
- **리뷰 기능(KB-128·KB-129·KB-131)보다 먼저 수행한다.** 나중에 하면 리뷰 영속 코드를 두 번 쓴다. 리뷰 태스크 본문은 새 구조 기준으로 갱신한다.
- **DB 스키마는 변경하지 않는다.** 코드 구조만 바꾸며, 예외는 누락된 외래키 제약을 추가하는 마이그레이션뿐이다.
- **`:infra:llm` 과 통합 이벤트 공유 모듈(`:common`)은 이번 개편의 대상이 아니다.**
- **테스트 스타일·응답 봉투·경로 규약 등 기존 컨벤션은 그대로다.** 바뀌는 것은 모듈 구조와 영속 접근 방식뿐이다.

## Out of Scope

- **리뷰 기능 구현(KB-128·KB-129·KB-131)** — 이 리팩토링의 후속이며 여기 포함하지 않는다.
- **도메인 모델과 JPA 엔티티의 통합** — 분리를 유지한다. 통합은 이슈가 명시적으로 배제했다.
- **`:infra:llm` 재배치** — 그대로 둔다.
- **기존 마이그레이션 파일 이동·리네임** — 하지 않는다(시드 동기화 테스트 결합·checksum 파손 위험).
- **API 계약 변경** — 어떤 엔드포인트의 요청·응답도 바꾸지 않는다.
