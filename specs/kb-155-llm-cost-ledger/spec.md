# Feature Specification: 메뉴 스캔 LLM 호출 비용 기록 원장 (관리자용 총비용 집계)

**Feature Branch**: `kb-155-llm-cost-ledger`

**Created**: 2026-07-17

**Status**: Draft

**Input**: User description: "kb-155 — 메뉴 스캔 LLM 호출 비용 기록 테이블(관리자용 총비용 집계). 토큰 출력 비용 기록은 비즈니스 로직과 별개이므로 비동기/이벤트 발행으로 DB에 기록한다."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 누적 LLM 비용을 집계한다 (Priority: P1)

서비스 운영자(관리자)는 메뉴판 스캔 기능이 외부 LLM(vision)을 호출할 때마다 발생하는 비용을 누적 집계하고 싶다. 지금은 비용이 애플리케이션 로그로만 남아 총비용을 계산할 수 없다. 호출 1건마다 사용 모델명·입력 토큰 수·출력 토큰 수·USD 비용·KRW 비용이 기록 원장에 1행씩 쌓이면, 관리자는 기간·모델별 총비용을 언제든 합산할 수 있다.

**Why this priority**: 이 기능의 존재 이유 그 자체 — 기록이 쌓이지 않으면 아무 가치가 없다.

**Independent Test**: 메뉴판 스캔을 1회 수행한 뒤 기록 저장소를 조회하면 모델명·토큰 수·USD/KRW 비용이 채워진 행이 정확히 1행 존재한다.

**Acceptance Scenarios**:

1. **Given** 메뉴판 사진이 업로드 완료된 상태, **When** 사용자가 메뉴판 스캔을 요청해 vision 호출이 성공하면, **Then** 비용 기록 원장에 모델명·input 토큰·output 토큰·USD 비용·KRW 비용이 담긴 행이 1행 추가된다.
2. **Given** 스캔이 여러 번 수행된 상태, **When** 관리자가 원장의 KRW 비용을 합산하면, **Then** 호출별 비용의 총합(누적 총비용)을 얻는다.
3. **Given** vision 이 응답했지만 응답 해석(파싱)이 실패한 경우, **When** 스캔이 오류로 종료되어도, **Then** 비용 행은 추가된다 — 과금은 응답을 받은 시점에 이미 발생했다.
4. **Given** vision 호출 자체가 실패해 응답을 받지 못한 경우(네트워크·타임아웃), **When** 스캔이 오류로 종료되면, **Then** 비용 행은 추가되지 않는다.

---

### User Story 2 - 비용 기록 실패가 스캔 기능을 방해하지 않는다 (Priority: P2)

비용 기록은 부가(관측) 기능이다. 기록 저장이 실패하더라도(저장소 장애 등) 사용자의 메뉴판 스캔 결과 응답은 정상 반환되어야 한다. 또한 기록 작업이 스캔 응답 경로와 분리되어(비동기), 기록에 걸리는 시간이 사용자 응답 시간에 더해지지 않아야 한다.

**Why this priority**: 부가 기능이 핵심 사용자 기능을 깨뜨리면 안 된다는 안전 요건 — P1 기록이 존재해야 의미가 있으므로 P2.

**Independent Test**: 비용 기록 저장을 강제로 실패시킨 상태에서 스캔을 요청해도 스캔 응답이 정상(성공) 반환됨을 확인한다.

**Acceptance Scenarios**:

1. **Given** 비용 기록 저장이 실패하도록 만든 상태, **When** 사용자가 메뉴판 스캔을 요청하면, **Then** 스캔 결과는 정상 반환되고 실패는 로그로만 남는다.
2. **Given** 정상 상태, **When** 스캔 응답이 반환된 시점, **Then** 비용 기록은 응답 경로 밖(비동기)에서 수행되며 응답 지연에 기여하지 않는다.

---

### Edge Cases

- LLM 응답에 토큰 사용량 정보가 없으면(usage 누락) 토큰 수는 0으로 기록하고 경고 로그를 남긴다 — 호출 사실 자체는 남기되, 0 이 "무료"가 아니라 "측정 불가"일 수 있음을 로그로 식별한다.
- 가격표가 등록되지 않은 모델(단가 0)의 호출은 비용 0 으로 기록되고 경고 로그를 남긴다(총비용 과소 집계 식별용).
- 비동기 기록 특성상 앱 프로세스가 기록 완료 전에 종료되면 해당 행은 유실될 수 있다 — 관리 지표 용도이므로 허용한다(회계 수준 정합성 불요).
- 스캔 응답 반환 직후 원장을 조회하면 아직 행이 없을 수 있다(비동기 지연) — 집계는 실시간성이 필요 없는 관리자 작업이므로 허용한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 메뉴 스캔 vision 호출이 응답을 반환할 때마다(이후 파싱·스캔 처리 실패와 무관하게) 비용 기록 원장에 1행을 추가해야 한다. 원장은 append-only — 시스템은 기록의 생성만 제공하고 수정·삭제 기능은 노출하지 않는다.
- **FR-002**: 각 기록 행은 사용 모델명(예: `gpt-4o-mini`), input 토큰 수, output 토큰 수, USD 비용, KRW 비용을 포함해야 한다.
- **FR-003**: KRW 비용은 기존 비용 산식과 동일하게 환율 1 USD = 1,500 KRW 로 계산해 저장해야 한다(기존 산식 재사용 — 로그와 원장의 금액이 일치).
- **FR-004**: 비용 기록 경로의 어느 단계(기록 요청 전달·비동기 처리·저장)가 실패해도 스캔 요청 처리 결과에 영향을 주지 않아야 한다(스캔 응답 정상 반환, 실패는 로그로 남김).
- **FR-005**: 비용 기록은 스캔 응답 경로와 분리(비동기)되어 수행되어야 한다 — 기록 소요 시간이 사용자 응답 시간에 합산되지 않는다.
- **FR-006**: 기록 저장 구조는 관리자가 표준 질의(합산·기간 필터)로 총비용을 집계할 수 있어야 한다.
- **FR-007**: 저장 금액의 정밀도는 고정한다 — USD 는 소수 6자리, KRW 는 소수 2자리(반올림 HALF_UP). 기존 로그 표기(USD 6자리·KRW 2자리)와 같은 자릿수라 금액 대조가 가능하다.

### Key Entities

- **LLM 호출 비용 기록(원장 행)**: 외부 LLM 1회 호출의 과금 근거 스냅샷 — 모델명, input 토큰 수, output 토큰 수, USD 비용, KRW 비용, 기록 시각. 다른 엔티티와 관계 없음(독립 원장).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 정상 운영 상태(기록 경로 장애 없음)에서 vision 응답 N회당 원장에 N행이 존재하고, 행별 KRW 비용 합산으로 누적 총비용을 산출할 수 있다.
- **SC-002**: 비용 기록 저장이 100% 실패하는 상황에서도 메뉴판 스캔 성공률은 기록 기능 도입 전과 동일하다.
- **SC-003**: 기록 1행의 금액은 기존 로그로 남던 금액과 동일하다(동일 산식·동일 환율).
- **SC-004**: 관리자 조회/집계 화면·API 없이도(범위 밖) 저장소 직접 질의만으로 총비용 집계가 가능하다.

## Assumptions

- 대상은 **메뉴 스캔 vision 호출**만이다 — 배치(음식 스코어링) LLM fan-out 호출 기록은 이 기능 범위 밖이다(단, 원장 구조는 특정 기능에 종속되지 않게 일반적으로 둔다).
- 관리자 조회/집계 API·화면은 범위 밖이다(KB-155 DoD). 집계는 DB 직접 질의로 수행한다.
- 비용 기록은 best-effort 관리 지표다 — 프로세스 종료·저장 실패로 인한 소량 유실을 허용하며, 회계 수준의 정합성(재시도·보상 트랜잭션)은 요구하지 않는다.
- 기존 비용 산식(`LlmPricing.costUsd/costKrw`, 환율 상수 1500)은 이미 검증되어 있으며 그대로 재사용한다.
- vision 이 응답을 반환하지 못한 실패(네트워크·타임아웃)만 미과금으로 간주해 기록하지 않는다 — 응답을 받은 뒤의 실패(파싱 등)는 과금이 발생했으므로 기록한다.
- 기록 시각은 저장 시각(생성 시각 컬럼)으로 충분하다 — 비동기 지연은 밀리초 수준이라 기간 집계에 무의미하다.
