## User Scenarios & Testing *(mandatory)*

### User Story 1 - 음식 상세를 볼 때마다 조회 이력이 한 줄 남는다 (Priority: P1)

앱 사용자가 음식 상세 화면을 열면, 서비스는 "언제, 어느 회원이(게스트면 회원 없음), 어느 음식을" 봤는지를 이력 한 줄로 남긴다. 사용자는 이 기록을 의식하지 못하며 상세 화면은 이전과 똑같은 속도로 뜬다.

**Why this priority**: 인기순 음식 조회의 근거가 조회수다. 이 이력이 없으면 후속 기능을 시작할 수 없다.

**Independent Test**: 회원·게스트로 상세 조회를 각각 한 번씩 호출한 뒤, 조회 이력에 음식·회원(또는 없음)·시각이 담긴 행이 정확히 하나씩 늘었는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 준비된(노출 가능한) 음식과 로그인한 회원, **When** 그 음식의 상세를 조회하면, **Then** 상세 응답은 이전과 동일하게 성공하고, 잠시 뒤 그 음식·그 회원·조회 시각이 담긴 조회 이력 1행이 존재한다.
2. **Given** 준비된 음식과 게스트(비로그인) 사용자, **When** 상세를 조회하면, **Then** 회원 정보가 비어 있는 조회 이력 1행이 남는다.
3. **Given** 같은 회원이 같은 음식 상세를 연속 3번 조회, **When** 각 조회가 성공하면, **Then** 조회 이력은 3행 남는다(중복 제거 없음).
4. **Given** 존재하지 않거나 노출 불가 상태의 음식, **When** 상세를 조회해 실패 응답이 나가면, **Then** 조회 이력은 남지 않는다.

---

### User Story 2 - 이력 기록이 실패해도 사용자는 영향을 받지 않는다 (Priority: P2)

이력 저장이 어떤 이유로든 실패하거나 느려져도, 상세 조회 응답은 성공 여부·내용·응답 시간이 달라지지 않는다. 실패는 운영자가 나중에 확인할 수 있게 서버 로그에만 남는다.

**Why this priority**: 통계용 부가 기능이 본 기능을 깨뜨리면 안 된다. P1 의 안전 전제이지만, 정상 경로가 먼저 있어야 검증할 수 있어 P2 다.

**Independent Test**: 이력 저장을 강제로 실패시킨 상태에서 상세 조회를 호출해, 응답이 성공이고 내용이 정상이며 서버 로그에 실패 기록이 남는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이력 저장이 실패하도록 만든 환경, **When** 상세 조회를 호출하면, **Then** 상세 응답은 정상 성공이고 서버 로그에 저장 실패가 기록된다.
2. **Given** 정상 환경, **When** 상세 조회 응답이 사용자에게 반환되면, **Then** 응답 완료는 이력 저장 완료를 기다리지 않는다(저장은 응답 뒤에 끝나도 된다).

---

### User Story 3 - 운영자가 비동기 저장 실패 로그를 원 요청과 연결한다 (Priority: P3)

운영자가 서버 로그에서 이력 저장 실패를 발견하면, 그 로그에 원 요청의 식별자(요청 id·회원 id·앱/OS 버전)가 함께 찍혀 있어 어느 요청에서 비롯됐는지 바로 찾을 수 있다. 지금은 응답 스레드에서만 이 식별자가 붙고, 별도 스레드에서 처리되는 작업의 로그에는 붙지 않는다. 이 문제는 이력 저장뿐 아니라 이미 있는 비동기 작업(푸시 발송·비용 기록)에도 똑같이 있으므로 한 번에 고친다.

**Why this priority**: 정상 동작(US1)·안전(US2)이 먼저다. 이 스토리는 장애 추적 편의이며, 없어도 이력 자체는 쌓인다.

**Independent Test**: 로컬 실행에서 상세 조회의 이력 저장 실패를 유도해 서버 로그에 요청 식별자가 붙는지, 이어지는 다른 비동기 로그에 앞 요청의 식별자가 남지 않는지 확인한다(자동 테스트 없음 — 2026-09-23 결정).

**Acceptance Scenarios**:

1. **Given** 요청 식별자가 채워진 요청 스레드, **When** 비동기 작업을 넘기면, **Then** 작업 스레드 안에서 같은 식별자를 읽을 수 있다.
2. **Given** 식별자 없이 넘긴 비동기 작업, **When** 작업이 실행되면, **Then** 이전 작업이 남긴 식별자가 보이지 않는다(스레드 재사용에 의한 오염 없음).
3. **Given** 비동기 작업이 끝난 스레드, **When** 다음 작업이 같은 스레드에서 돌면, **Then** 앞 작업의 식별자가 남아 있지 않다.

---

### Edge Cases

- 회원 탈퇴 후에도 그 회원이 남긴 조회 이력은 그대로 남는다(통계 원본 보존). 회원을 식별하는 값만 담고 개인정보(이름·이메일 등)는 담지 않는다.
- 음식이 나중에 삭제·비노출 처리돼도 과거 조회 이력은 남는다. 인기순 집계 쪽이 노출 가능한 음식만 골라 쓰는 것은 후속 태스크의 몫이다.
- 서버가 종료·재시작되는 순간에 아직 저장되지 않은 이력은 유실될 수 있다. 통계 용도라 유실을 감수하며, 재전송·보장 큐를 두지 않는다.
- 짧은 시간에 같은 사용자가 같은 음식을 반복 조회해도 전부 그대로 남긴다. 어뷰징 필터링·중복 제거는 집계 단계의 책임이다.
- 이력 테이블이 계속 커진다. 보존 기간·정리 정책은 이 태스크 범위 밖이며, 집계 기능을 만들 때 함께 정한다.
- 비동기 작업 스레드는 풀에서 재사용된다. 식별자 복사 뒤 복원을 빠뜨리면 다음 작업 로그에 남의 요청 id 가 찍힌다 — 전파는 반드시 "작업 전 설정·작업 후 원복" 쌍으로 한다.
- 검색·둘러보기·스캔 등 어느 경로로 상세에 왔는지는 이번에 기록하지 않는다. 필요해지면 이력에 선택 컬럼(유입 경로)을 추가하는 후속 태스크로 다루며, 과거 행은 "경로 미상"으로 남는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 음식 상세 조회가 성공 응답으로 끝날 때마다 조회 이력 1행을 남겨야 한다. 이력에는 조회된 음식, 조회한 회원(게스트면 없음), 조회 시각이 담긴다.
- **FR-002**: 실패 응답(음식 없음, 노출 불가 등)으로 끝난 상세 조회에는 이력을 남기지 않아야 한다.
- **FR-003**: 이력 저장은 사용자 응답과 분리해 응답 이후에 처리해야 하며, 응답 완료가 이력 저장 완료를 기다려서는 안 된다.
- **FR-004**: 이력 저장의 실패·지연은 상세 조회 응답의 성공 여부·내용에 영향을 주어서는 안 되며, 실패는 서버 로그에 남겨야 한다.
- **FR-005**: 이력은 추가만 되는(append-only) 기록이어야 한다. 기존 행을 갱신하거나 집계 컬럼을 증가시키는 방식으로 대체하지 않는다.
- **FR-006**: 이력에는 회원·음식을 식별하는 값만 담고, 이름·이메일 같은 개인정보나 음식 표시 정보를 복제해 담지 않아야 한다.
- **FR-007**: 이력은 회원·음식이 나중에 삭제·탈퇴·비노출되어도 그대로 보존되어야 한다.
- **FR-008**: 이력은 후속 인기순 집계가 "특정 기간의 음식별 조회 수"를 뽑을 수 있는 형태로 저장되어야 한다.
- **FR-009**: 기존 상세 조회 요청·응답 계약은 바뀌지 않아야 한다. 클라이언트 변경은 없다.
- **FR-010**: 요청 스레드의 로그 식별자(요청 id·회원 id·앱/OS 버전)는 그 요청이 넘긴 비동기 작업의 로그에도 그대로 붙어야 하며, 작업이 끝나면 작업 스레드에서 제거되어야 한다. 이 전파는 이력 저장뿐 아니라 서비스의 모든 비동기 작업에 공통 적용된다.

### Key Entities *(include if feature involves data)*

- **음식 조회 이력**: 상세 조회 1회를 나타내는 사건 기록. 대상 음식, 조회한 회원(없을 수 있음), 발생 시각. 갱신되지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 성공한 상세 조회 요청의 100% 에 대해 응답 후 5초 이내에 대응하는 이력 1행이 존재한다(정상 환경 기준).
- **SC-002**: 이력 기록을 켠 뒤 상세 조회 응답 시간의 p95 가 기록 전 대비 5% 이상 늘지 않는다.
- **SC-003**: 이력 저장을 강제로 실패시킨 상태에서도 상세 조회 요청의 성공률은 100% 로 유지된다.
- **SC-004**: 후속 인기순 집계 담당자가 추가 스키마 변경 없이 "최근 N일 음식별 조회 수 상위 K개"를 이력만으로 뽑을 수 있다.
- **SC-005**: 비동기 작업(이력 저장·푸시 발송·비용 기록)의 서버 로그 100% 에 원 요청의 요청 id 가 붙는다(요청 스레드에 요청 id 가 있었던 경우).

## Assumptions

- 검색 횟수는 수집하지 않는다(2026-09-23 결정). 키워드 검색 로그는 음식 단위로 귀속되지 않아 인기순 음식의 근거가 못 되며, 검색 → 상세 조회 흐름의 결과는 조회 이력이 잡는다. 인기 검색어가 필요해지면 별도 태스크로 다룬다.
- 유입 경로(검색/둘러보기/스캔 등)는 이번에 기록하지 않는다. 다만 이력 테이블에 **용도 미정 예비 컬럼 3개(빈 값 허용)** 를 미리 둔다(2026-09-23 결정) — 유입 경로 등을 담게 되면 이 자리를 쓰고, 클라이언트가 진입점에서 값을 싣는 것은 후속 태스크다.
- 게스트(비로그인) 사용자의 조회도 남긴다. 회원 식별값만 비어 있다. 게스트를 기기 식별자(installation id) 등으로 대신 식별하지 않는다(2026-09-23 결정 — 비회원 조회를 개인화까지 잇지 않는다. 인기순은 총 조회수만 쓴다).
- 이력은 통계용이므로 서버 종료 순간의 소량 유실을 감수한다. 전송 보장·재시도 큐는 두지 않는다.
- 보존 기간·삭제 정책·어뷰징 필터는 이 태스크 범위 밖이다. 인기순 집계 기능(별도 태스크)을 설계할 때 함께 정한다.
- 인기순 정렬·집계 API 자체는 이 태스크에서 만들지 않는다. 이 태스크는 데이터 축적까지다.
- 로그 식별자 전파(2026-09-23 추가 결정)는 서비스 공통 비동기 실행기에 한 번 적용한다. 기존 비동기 작업(푸시 발송·비용 기록)도 자동으로 혜택을 받으며, 그쪽 코드는 손대지 않는다.
