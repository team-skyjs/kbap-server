# Feature Specification: 홈 인기 음식 목록 캐시

**Feature Branch**: `feat/kb725-popular-food-cache`

**Created**: 2026-10-08

**Status**: Draft

**Jira**: [KB-725](https://simhani1.atlassian.net/browse/KB-725)

**Input**: User description: "홈 인기 음식 조회를 프로세스 내 캐시로 — DB 집계 1회/TTL, 동시 갱신 방지. 홈 API 는 요청마다 최근 30일 조회 로그(dev 약 10만 건)를 집계해 인기 음식 10건을 고르는데, 결과는 사용자와 무관한 전역 값인데도 캐시가 없어 매 요청 집계를 돌린다. 2026-10-08 dev 부하 테스트(홈 동시 1,000명)에서 이 쿼리가 DB 시간의 56% 를 차지하며 RDS CPU 를 1분 만에 100% 로 올렸고, 커넥션 풀이 전부 물려 성공률 30% 였다. 인기 음식 id 목록·순서만 짧은 TTL 로 캐시하고, 사용자별 값(기피 성분 안전 여부·북마크·평점)은 요청마다 계산한다. TTL 만료 순간의 동시 미스(스탬피드)는 한 요청만 집계하고 나머지는 결과를 기다리게 한다. 리뷰 인기·최근 스캔은 범위 밖."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 홈을 여는 사람이 많아져도 인기 음식 때문에 홈이 느려지지 않는다 (Priority: P1)

홈 화면을 여는 사용자(회원·비회원)는 동시 접속자가 많은 시간대에도 홈을 평소와 같은 속도로 본다. 인기 음식 목록은 모든 사용자에게 같은 값이므로, 서버는 짧은 유효 기간 동안 한 번 만든 목록을 재사용하고 유효 기간이 지나면 다시 만든다. 사용자가 보는 홈 응답의 내용·구조는 지금과 같다.

**Why this priority**: 기능의 본체이자 부하 테스트에서 드러난 장애 원인(DB 집계가 요청마다 반복)을 없앤다. 이것만 구현해도 홈의 DB 비용이 요청당 집계 1회에서 유효 기간당 1회로 내려간다.

**Independent Test**: 인기 음식을 두 번 연속 조회하면 두 번째 조회는 조회 기록 집계를 수행하지 않고 첫 번째와 같은 목록을 돌려준다. 유효 기간이 지난 뒤 조회하면 집계를 다시 수행한다.

**Acceptance Scenarios**:

1. **Given** 인기 음식 목록이 아직 만들어지지 않았을 때, **When** 홈을 조회하면, **Then** 조회 기록을 집계해 인기 음식 목록을 만들고 돌려준다.
2. **Given** 유효 기간 내에 만들어진 인기 음식 목록이 있을 때, **When** 홈을 다시 조회하면, **Then** 집계를 수행하지 않고 같은 목록(같은 음식·같은 순서)을 돌려준다.
3. **Given** 인기 음식 목록의 유효 기간이 지났을 때, **When** 홈을 조회하면, **Then** 집계를 다시 수행해 새 목록을 만들고 돌려준다.
4. **Given** 캐시된 목록이 있을 때, **When** 홈을 조회하면, **Then** 홈 응답의 필드·레일 크기·정렬 규칙(KB-714: 최근 30일 조회수 내림차순, 동률 id 내림차순, 최대 10건)은 캐시가 없을 때와 동일하다.

---

### User Story 2 - 사용자마다 다른 정보는 캐시와 무관하게 정확하다 (Priority: P1)

인기 음식 목록은 모두에게 같지만, 각 음식이 **내** 기피 성분 기준으로 안전한지, **내가** 북마크했는지, 현재 평점이 얼마인지는 사용자·시점마다 다르다. 이 값들은 목록이 캐시에서 왔든 새로 집계됐든 요청마다 그 사용자 기준으로 계산된다.

**Why this priority**: 캐시 도입이 개인화 정보를 다른 사용자 것으로 섞거나 오래된 값으로 보여주면 기능 자체가 틀린 것이 된다. US1 과 같은 릴리스에서 반드시 함께 보장돼야 한다.

**Independent Test**: 기피 성분이 서로 다른 회원 A·B 가 연속으로 홈을 조회하면(두 번째는 캐시 히트) 인기 음식 목록은 같지만 안전 여부 표시는 각자의 기피 성분 기준으로 다르게 나온다.

**Acceptance Scenarios**:

1. **Given** 회원 A 가 홈을 조회해 인기 음식 목록이 캐시됐을 때, **When** 기피 성분이 다른 회원 B 가 홈을 조회하면, **Then** 인기 음식 목록은 같고 각 음식의 안전 여부는 B 의 기피 성분 기준으로 평가된다.
2. **Given** 인기 음식 목록이 캐시됐을 때, **When** 회원이 인기 음식 중 하나를 북마크한 뒤 홈을 다시 조회하면, **Then** 그 음식은 북마크됨으로 표시된다.
3. **Given** 인기 음식 목록이 캐시됐을 때, **When** 비회원이 홈을 조회하면, **Then** 인기 음식 목록은 같고 안전 여부·북마크는 비회원 규칙(기존과 동일)으로 나온다.
4. **Given** 인기 음식 목록이 캐시됐을 때, **When** 표시 언어가 다른 사용자가 홈을 조회하면, **Then** 같은 음식들이 요청한 언어의 이름으로 나온다.

### User Story 3 - 유효 기간이 끝나는 순간 몰린 요청도 집계는 한 번만 한다 (Priority: P2)

유효 기간이 만료된 직후 수백 명이 동시에 홈을 열어도 조회 기록 집계는 한 번만 수행되고, 나머지 요청은 그 결과를 받아 응답한다. 캐시가 없던 때의 부하가 만료 순간마다 순간적으로 재현되지 않는다.

**Why this priority**: 부하 테스트 조건(동시 1,000명)에서 US1 만으로는 만료 순간마다 집계가 수백 번 겹칠 수 있다. 피크 보호의 완성이지만, US1·US2 없이 단독으로는 의미가 없어 P2 다.

**Independent Test**: 캐시가 비어 있거나 만료된 상태에서 N 개 요청을 동시에 보내면 집계는 1회만 수행되고 N 개 요청 모두 같은 목록을 받는다.

**Acceptance Scenarios**:

1. **Given** 인기 음식 목록이 비어 있거나 만료됐을 때, **When** N 개의 홈 요청이 동시에 들어오면, **Then** 조회 기록 집계는 1회만 수행되고 N 개 요청 모두 같은 목록을 돌려받는다.
2. **Given** 한 요청이 집계를 수행 중일 때, **When** 다른 요청이 들어오면, **Then** 그 요청은 집계를 중복 수행하지 않고 완성된 결과를 기다렸다가 돌려받는다.

---

### Edge Cases

- 집계 중 오류가 나면 그 요청은 기존과 동일하게 실패하고, 빈 목록이나 실패 결과를 캐시에 남기지 않는다. 다음 요청이 다시 집계를 시도한다.
- 최근 30일 조회 기록이 없어 인기 음식이 0건이면 빈 목록도 유효 기간 동안 캐시한다(빈 결과를 매 요청 재집계하지 않는다).
- 캐시 유효 기간 안에 조회수가 바뀌어 순위가 달라져도 목록은 유효 기간이 끝날 때까지 갱신되지 않는다 — 최대 유효 기간만큼의 지연을 감수한다.
- 캐시 유효 기간 안에 목록의 음식이 삭제되거나 비공개로 바뀐 경우, 삭제된 음식은 노출하지 않는다. 비공개 전환은 최대 유효 기간만큼 늦게 반영될 수 있다.
- 서버 인스턴스가 여러 대면 인스턴스마다 각자 목록을 만든다. 인스턴스 간 목록이 짧은 시간 다를 수 있고, 집계 횟수는 유효 기간당 인스턴스 수만큼이다(허용).
- 서버 재시작 직후 첫 요청은 집계를 수행한다(워밍업 없음).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 홈의 인기 음식 목록(어떤 음식 id 가 어떤 순서인지, 최대 10건)은 서버 프로세스 안에서 고정된 유효 기간 동안 재사용된다. 같은 유효 기간 안의 홈 요청은 조회 기록 집계를 다시 수행하지 않는다.
- **FR-002**: 인기 음식 목록 캐시는 사용자·언어와 무관한 전역 단일 항목이다. 회원 id·비회원 여부·표시 언어는 캐시 키에 포함되지 않는다.
- **FR-003**: 유효 기간이 지난 뒤의 첫 요청은 조회 기록을 다시 집계해 목록을 갱신한다.
- **FR-004**: 캐시가 비어 있거나 만료된 상태에서 여러 요청이 동시에 들어와도 집계는 1회만 수행되고, 나머지 요청은 그 결과를 받는다.
- **FR-005**: 사용자별 값 — 기피 성분 기준 안전 여부·북마크 여부·평점 — 은 캐시하지 않고 캐시 히트 여부와 무관하게 요청마다 요청 사용자 기준으로 계산한다. 음식 이름은 요청 언어로 표시한다.
- **FR-006**: 캐시 히트 시 홈 응답의 필드·레일 크기·정렬 규칙(KB-714)은 캐시 미스 때와 동일하다. 기존 홈 통합 테스트는 검증 본문 수정 없이 통과한다.
- **FR-007**: 집계가 실패하면 실패 결과를 캐시하지 않는다. 빈 목록(인기 음식 0건)은 정상 결과로 캐시한다.
- **FR-008**: 캐시 유효 기간 안에 삭제된 음식은 인기 음식에 노출하지 않는다.
- **FR-009**: 리뷰 인기 음식·최근 스캔 레일은 이 기능의 대상이 아니다(동작 불변).
- **FR-010**: 다음 규칙은 구현보다 먼저 실패하는 테스트로 고정한다(Test-First): 두 번째 호출은 집계를 수행하지 않는다 / 유효 기간 경과 후 재집계한다 / 동시 N 요청이 미스를 만나도 집계는 1회다 / 캐시 히트 시에도 사용자별 평가가 수행된다.

### Key Entities

- **인기 음식 목록**: 최근 30일 조회수 순 공개 음식 id 의 순서 있는 목록(최대 10건). 전역 값이며 유효 기간을 가진다. 이 기능이 새로 도입하는 임시 보관 단위.
- **음식(Food)**: 목록의 대상. 공개 상태·삭제 여부가 노출 조건(KB-714 와 동일).
- **음식 조회 기록(food_view_log)**: 집계의 원천. 이 기능은 읽기만 하며 기록 방식은 바꾸지 않는다.
- **사용자별 평가**: 기피 성분 안전 여부·북마크 여부·평점. 목록과 분리돼 요청마다 계산되며 캐시 대상이 아니다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 서버 인스턴스에서 유효 기간 하나 동안 조회 기록 집계는 최대 1회 수행된다(홈 요청 수와 무관).
- **SC-002**: 캐시가 비어 있거나 만료된 상태에 동시에 들어온 N 개 요청(N ≥ 100)에 대해 집계 수행 횟수는 1회다.
- **SC-003**: 캐시 히트 시 홈 응답의 인기 음식 목록·순서는 직전 집계 결과와 100% 같고, 안전 여부·북마크·평점은 요청 사용자 기준 값과 100% 일치한다.
- **SC-004**: 기존 홈 통합 테스트가 검증 본문 변경 없이 전부 통과한다.
- **SC-005**: dev 환경 부하 테스트(홈 동시 1,000명, 타임아웃 30초) 재실행에서 인기 음식 집계 쿼리 호출 수가 유효 기간당 인스턴스별 1회 수준으로 떨어지고, DB CPU 사용률과 요청 성공률이 2026-10-08 1차 결과(성공률 30%) 대비 개선돼 Notion 부하 테스트 페이지에 기록된다.

## Assumptions

- 캐시 유효 기간은 **2일**로 고정한다(2026-10-08 사용자 지시). 설정값으로 노출하지 않는다. 운영 중 조정이 필요해지면 그때 상수를 바꾼다. 서버 재배포·재시작 시 캐시는 비워지므로 실제 갱신 주기는 2일 또는 배포 간격 중 짧은 쪽이다.
- 캐시는 API 프로세스 내부에 둔다. 외부 공유 캐시는 쓰지 않는다 — 인스턴스 2대가 각자 집계해도 유효 기간당 2회뿐이라 비용이 미미하고 Jira 원문이 명시적으로 배제했다.
- 캐시 보관 단위는 "인기 음식 id 목록·순서"다. 사용자별 평가와 언어별 이름은 요청마다 기존 로직으로 조립한다. id 목록을 보관하고 요청 시 음식을 다시 읽는지, 음식 자체를 보관하는지는 설계 단계에서 정한다(FR-008 삭제 음식 비노출은 어느 쪽이든 만족해야 한다).
- 조회수 변동에 따른 순위 변경과 비공개(READY 해제) 전환은 최대 2일 늦게 반영된다. 이를 감수한다 — 인기 레일은 "최근 추세"면 충분하고, 음식을 비공개로 돌리는 일은 드물다. 삭제된 음식은 기간과 무관하게 노출하지 않는다(FR-008).
- 집계 중 대기하는 요청은 집계가 끝날 때까지 기다린다. 별도 대기 시간 상한은 두지 않는다 — 집계 자체가 유휴 시 0.2초 수준이고, 타임아웃 분기를 추가하는 것은 요청되지 않은 방어 기능이다.
- 워밍업·사전 갱신(만료 전 백그라운드 재집계)은 범위 밖이다. 서버 기동 직후 첫 요청이 집계를 맡는다.
- 리뷰 인기 음식 레일은 같은 패턴의 후속 태스크로 분리한다(Jira 원문). 이 기능의 테스트·변경 범위에 넣지 않는다.
- dev 부하 테스트 재실행(SC-005)은 구현 완료 후 사용자가 수행·기록한다. 이 스펙의 자동화 테스트 범위는 SC-001~SC-004 다.
