**Feature Branch**: `feat/kb726-review-count-denormalize`

**Created**: 2026-10-08

**Status**: Draft

**Jira**: [KB-726](https://simhani1.atlassian.net/browse/KB-726)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 홈을 여는 사람이 많아져도 리뷰 인기 음식 때문에 홈이 느려지지 않는다 (Priority: P1)

홈 화면을 여는 사용자(회원·비회원)는 동시 접속자가 많은 시간대에도 "리뷰가 많은 음식" 레일을 평소 속도로 본다. 서버는 음식마다 미리 유지하는 리뷰 수를 읽어 상위 10개를 고르며, 홈 요청 때마다 전체 리뷰를 다시 세지 않는다. 사용자가 보는 홈 응답의 내용·구조는 지금과 같다.

**Why this priority**: 2026-10-08 부하 테스트 2차(동시 1,000명 홈)에서 이 레일의 집계 하나가 DB 시간의 93% 를 차지해 성공률이 55% 에 그쳤다. 리뷰가 쌓일수록 비용이 선형으로 느는 구조라 캐시가 아닌 데이터 구조 변경이 필요하다. 이것이 기능의 본체다.

**Independent Test**: 음식마다 리뷰 수가 유지된 상태에서 홈을 조회하면, 리뷰 수 내림차순(동률은 음식 id 내림차순)으로 최대 10개의 공개 음식이 나오고, 그 조회는 리뷰 테이블을 읽지 않는다.

**Acceptance Scenarios**:

1. **Given** 음식 A 에 리뷰 3개, 음식 B 에 리뷰 1개가 있을 때, **When** 홈을 조회하면, **Then** 리뷰 인기 음식은 A, B 순서로 나온다.
2. **Given** 리뷰 수가 같은 음식 두 개(id 1, id 2)가 있을 때, **When** 홈을 조회하면, **Then** id 가 큰 음식(2)이 먼저 나온다.
3. **Given** 리뷰가 하나도 없을 때, **When** 홈을 조회하면, **Then** 리뷰 인기 음식은 빈 배열이다.
4. **Given** 리뷰가 있지만 공개 상태가 아니거나 삭제된 음식이 있을 때, **When** 홈을 조회하면, **Then** 그 음식은 리뷰 인기 음식에 나오지 않는다.
5. **Given** 리뷰 수가 유지된 상태일 때, **When** 회원과 비회원이 각각 홈을 조회하면, **Then** 레일의 음식·순서는 같고 사용자별 값(안전 여부·북마크·평점)은 각자 기준으로 나온다(기존과 동일).

### User Story 2 - 리뷰를 쓰거나 지우면 그 음식의 리뷰 수가 즉시 정확히 바뀐다 (Priority: P1)

회원이 어떤 음식에 리뷰를 작성하면 그 음식의 리뷰 수가 1 늘고, 본인이 리뷰를 삭제하거나 관리자가 신고 처리로 리뷰를 삭제하면 1 줄어든다. 이 변경은 리뷰 작성·삭제와 한 몸으로 처리된다 — 리뷰 작성이 실패(롤백)하면 리뷰 수도 바뀌지 않고, 리뷰 작성이 성공하면 리뷰 수 반영도 반드시 성공한다.

**Why this priority**: 리뷰 수가 리뷰 테이블과 어긋나면 레일 순서가 틀린 채로 영구히 남는다(드리프트). US1 과 같은 릴리스에서 반드시 함께 보장돼야 한다.

**Independent Test**: 리뷰 수 0인 음식에 리뷰를 작성하면 1, 본인 삭제하면 0, 다른 회원이 작성 후 관리자 삭제하면 다시 0 이 된다. 같은 음식에 여러 회원이 동시에 리뷰를 작성해도 충돌·실패 없이 리뷰 수가 작성 건수만큼 는다.

**Acceptance Scenarios**:

1. **Given** 리뷰 수 0인 공개 음식이 있을 때, **When** 회원이 리뷰를 작성하면, **Then** 그 음식의 리뷰 수는 1 이다.
2. **Given** 회원 본인의 리뷰로 리뷰 수가 1인 음식이 있을 때, **When** 본인이 그 리뷰를 삭제하면, **Then** 리뷰 수는 0 이다.
3. **Given** 리뷰 수가 1인 음식이 있을 때, **When** 관리자가 신고 처리로 그 리뷰를 삭제하면, **Then** 리뷰 수는 0 이다.
4. **Given** 작성자 회원이 이미 탈퇴해 존재하지 않는 리뷰가 있을 때, **When** 관리자가 신고 처리로 그 리뷰를 삭제하면, **Then** 음식의 리뷰 수는 1 줄어든다(회원 통계는 건드리지 않는 기존 분기 그대로).
5. **Given** 이미 삭제된 리뷰가 있을 때, **When** 관리자가 다시 신고 처리하면, **Then** 리뷰 수는 변하지 않는다(중복 감소 없음).
6. **Given** 한 음식에 여러 회원이 동시에 리뷰를 작성할 때, **When** 모두 처리되면, **Then** 어느 작성도 충돌로 실패하지 않고 리뷰 수는 작성 건수만큼 늘어 있다.
7. **Given** 리뷰 작성 처리 중 뒤쪽 단계가 실패할 때, **When** 작성이 롤백되면, **Then** 리뷰 수도 늘지 않는다.
8. **Given** 리뷰를 수정만 할 때(평점·내용 변경), **When** 수정이 완료되면, **Then** 리뷰 수는 변하지 않는다.

### User Story 3 - 기존 리뷰가 있는 상태로 배포해도 리뷰 수가 처음부터 맞는다 (Priority: P2)

이미 리뷰가 쌓인 환경(dev 약 4만 건, prod)에 이 기능을 배포하면, 배포 과정에서 음식마다 현재 유효한(삭제되지 않은) 리뷰 수가 채워진다. 배포 직후 첫 홈 요청부터 레일이 지금과 같은 음식·순서(동률 규칙만 변경)를 보여준다.

**Why this priority**: 초기값이 0 이면 배포 직후 레일이 비거나 엉뚱한 순서가 된다. 그러나 US1·US2 와 독립적으로 "스키마 변경 + 백필"만으로 검증할 수 있는 단위라 P2 다.

**Independent Test**: 리뷰가 미리 들어 있는 DB 에 마이그레이션을 적용하면 각 음식의 리뷰 수가 그 음식의 유효 리뷰 건수와 같다. 리뷰가 없는 음식은 0 이다.

**Acceptance Scenarios**:

1. **Given** 마이그레이션 전 음식 A 에 유효 리뷰 3개·삭제된 리뷰 1개가 있을 때, **When** 마이그레이션을 적용하면, **Then** A 의 리뷰 수는 3 이다.
2. **Given** 마이그레이션 전 리뷰가 없는 음식 B 가 있을 때, **When** 마이그레이션을 적용하면, **Then** B 의 리뷰 수는 0 이다.
3. **Given** 마이그레이션이 적용된 뒤, **When** 애플리케이션이 기동하면, **Then** 엔티티와 스키마 정합 검증을 통과해 정상 부팅한다.

---

### Edge Cases

- 리뷰 수가 0인 음식에서 감소가 호출되면(정합이 이미 깨진 경우) 음수로 내려가지 않게 할 필요는 없다 — 정합 복구는 백필과 같은 재집계를 수동 재실행해 바로잡는다. 자동 복구 배치는 두지 않는다.
- 리뷰 작성 대상 음식이 공개 상태가 아니면 기존대로 작성 자체가 거부되므로 리뷰 수도 변하지 않는다.
- 음식이 삭제(소프트)되거나 비공개로 바뀌어도 그 음식의 리뷰 수 값은 유지된다. 레일 노출은 공개·활성 조건이 거른다.
- 통합 테스트가 리뷰를 SQL 로 직접 심는 경우(홈 테스트 시드) 음식의 리뷰 수도 함께 맞춰 심어야 레일 순서가 기대와 같다 — 리뷰 수는 리뷰 작성 경로를 거칠 때만 자동으로 는다.
- 회원 리뷰 작성 경로에서 음식의 리뷰 수 갱신이 0건(대상 음식 없음)이면 이는 선행 검증(공개 음식 확인)이 통과한 뒤라 발생하지 않는 상태다. 별도 예외 분기는 두지 않는다.
- 조회수 인기 레일(KB-725 캐시)·최근 스캔 레일은 변경하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 음식은 "현재 유효한(삭제되지 않은) 리뷰 수"를 자기 속성으로 유지한다. 기본값은 0 이다.
- **FR-002**: 홈의 리뷰 인기 음식 레일은 음식이 유지하는 리뷰 수를 기준으로 공개·활성 음식 중 리뷰 수 내림차순, 동률은 음식 id 내림차순으로 최대 10개를 고른다. 이 조회는 리뷰 테이블을 읽거나 집계하지 않는다.
- **FR-003**: 회원이 리뷰를 작성하면 같은 처리 단위 안에서 그 음식의 리뷰 수가 1 증가한다. 리뷰 작성이 실패해 되돌려지면 리뷰 수 증가도 함께 되돌려진다.
- **FR-004**: 리뷰가 삭제되면(본인 삭제·관리자 신고 처리 모두, 작성자 회원 존재 여부와 무관) 같은 처리 단위 안에서 그 음식의 리뷰 수가 1 감소한다. 이미 삭제된 리뷰의 재삭제 요청은 리뷰 수를 바꾸지 않는다.
- **FR-005**: 리뷰 수 증감은 음식 행을 통째로 읽어 다시 쓰는 방식이 아니라 "현재 값 ± 1" 한 줄 갱신으로 수행해, 같은 음식에 동시에 리뷰가 작성돼도 어느 작성도 버전 충돌로 실패하지 않는다. 음식의 기존 버전 관리(낙관적 잠금)에 영향을 주지 않는다.
- **FR-006**: 리뷰 수 갱신은 리뷰 작성·삭제와 동기로 같은 처리 단위에서 수행한다. 비동기 이벤트·지연 처리·별도 보정 배치로 갱신하지 않는다.
- **FR-007**: 리뷰 수정(평점·내용·사진·장소 변경)은 리뷰 수를 바꾸지 않는다.
- **FR-008**: 배포 시 스키마 변경 한 번으로 (a) 리뷰 수 속성 추가(기본 0), (b) 레일 조회를 위한 정렬 보조 구조 추가, (c) 기존 음식의 유효 리뷰 수 백필을 함께 수행한다. 백필 이후 음식의 리뷰 수는 그 음식의 유효 리뷰 건수와 같다.
- **FR-009**: 홈 응답의 필드·레일 크기·사용자별 값(안전 여부·북마크·평점) 계산 방식은 변하지 않는다. 바뀌는 것은 레일 선정 근거(유지되는 리뷰 수)와 동률 규칙(최신 리뷰 id 내림차순 → 음식 id 내림차순)뿐이다.
- **FR-010**: 조회수 인기 레일의 프로세스 내 캐시(KB-725)는 그대로 둔다. 리뷰 인기 레일에는 캐시를 두지 않는다 — 인덱스 순서 읽기로 충분하다.
- **FR-011**: 음식 속성 추가에 따라 음식 행을 직접 심는 테스트 시드·손스텁 스키마가 있으면 함께 갱신해 전체 빌드가 통과한다.
- **FR-012**: 다음 규칙은 구현보다 먼저 실패하는 테스트로 고정한다(Test-First): 작성 후 리뷰 수 +1 / 본인 삭제 후 -1 / 관리자 삭제 후 -1(회원 있음·없음 두 분기) / 재삭제 시 불변 / 수정 시 불변 / 홈 리뷰 인기 순서가 리뷰 수 내림차순·동률 id 내림차순·리뷰 0건 제외. 백필(FR-008c)은 빈 DB 에 도는 테스트 스키마에서 검증할 수 없어 로컬·dev 에서 드리프트 점검 질의로 확인한다(quickstart).

### Key Entities

- **음식(Food)**: 레일의 대상. 공개 상태·삭제 여부가 노출 조건. 이 기능으로 "유효 리뷰 수"를 자기 속성으로 갖게 된다.
- **리뷰(Review)**: 회원이 음식에 남긴 평가. 작성·삭제가 음식의 리뷰 수를 ±1 한다. 소프트 삭제 모델(삭제돼도 행은 남음)이라 "유효"는 삭제되지 않은 상태를 뜻한다.
- **리뷰 인기 음식 목록**: 음식의 리뷰 수 기준 상위 10개 공개 음식의 순서 있는 목록. 저장하지 않고 요청마다 읽는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 홈 요청 1건당 리뷰 인기 레일을 위해 읽는 행 수는 리뷰 총 건수와 무관하게 상위 10개 음식 수준으로 고정된다(리뷰 테이블 접근 0회).
- **SC-002**: 리뷰 작성·삭제 직후 그 음식의 리뷰 수는 해당 음식의 유효 리뷰 건수와 100% 일치한다(동시 작성 N 건 포함, 충돌 실패 0건).
- **SC-003**: 기존 리뷰가 있는 DB 에 배포한 직후 모든 음식의 리뷰 수가 유효 리뷰 건수와 100% 일치한다.
- **SC-004**: 기존 홈·리뷰 통합 테스트가 시드 보정 외 검증 본문 변경 없이 전부 통과하고, 전체 빌드가 통과한다.
- **SC-005**: dev 배포 후 부하 테스트 3차(홈 동시 1,000명)에서 리뷰 인기 조회가 슬로우 로그 상위에서 사라지고, 홈 1건당 DB 시간이 2차(1.44초) 대비 약 0.1초 수준으로 내려가 Notion 부하 테스트 페이지에 기록된다.

## Assumptions

- 동률 규칙 변경(최신 리뷰 id 내림차순 → 음식 id 내림차순)은 Jira 원문의 명시 결정이다. 인기 10개 안의 동률 순서라 사용자 체감 차이는 없다고 본다. 기존 홈 테스트의 기대 순서는 이 규칙으로도 그대로 성립한다(리뷰 수가 다른 음식만 비교).
- 리뷰 수의 정합이 어긋났을 때의 복구는 백필과 같은 재집계 갱신을 수동으로 재실행하는 것으로 한다. 주기 배치·자동 보정·음수 방지 가드는 요청되지 않은 방어 기능이라 두지 않는다.
- 통합 테스트에서 리뷰를 SQL 로 직접 심는 홈 시드는 음식의 리뷰 수를 함께 맞춰 심도록 보정한다(리뷰 작성 경로를 타지 않으므로). 검증 본문은 바꾸지 않는다.
- Jira 원문이 언급한 "scan 통합 테스트의 손스텁 CREATE TABLE" 은 코드베이스에 없다(설계 단계 확인 — 테스트 스키마는 운영 마이그레이션 + 엔티티 정합 검증으로 만든다). 음식 행을 직접 심는 시드는 전부 컬럼 명시형이라 기본값 0 컬럼 추가에 영향이 없고, 리뷰를 직접 심는 홈 시드만 보정한다.
- 리뷰 수는 공개 여부와 무관하게 모든 음식에 유지한다. 레일 노출만 공개·활성 조건으로 거른다.
- 리뷰 봇(자동 리뷰 작성)은 일반 리뷰 작성 경로를 그대로 쓴다(설계 단계 확인) — 별도 작업 없이 FR-003 이 적용된다.
- dev 부하 테스트 3차(SC-005)는 구현 완료·배포 후 사용자가 수행·기록한다. 이 스펙의 자동화 테스트 범위는 SC-001~SC-004 다.
