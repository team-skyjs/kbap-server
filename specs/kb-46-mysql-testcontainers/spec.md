# Feature Specification: MySQL Testcontainers 도입 (프로덕션-동등 통합 테스트)

**Feature Branch**: `kb-46-mysql-testcontainers`

**Created**: 2026-07-05

**Status**: Draft

**Input**: User description: "테스트를 돌릴 때 H2 를 사용하지 않고 프로덕션에서 사용할 MySQL 테스트 컨테이너를 도입하여 실제 환경과 유사하게 동작하는지를 검증한다 (KB-46)."

## User Scenarios & Testing *(mandatory)*

이 기능의 "사용자"는 서비스 최종 사용자가 아니라 **개발팀과 CI 파이프라인**이다. 통합 테스트가 실제 운영 DB 엔진과 동등한 환경에서 실행되도록 만들어, 배포 전에 DB 관련 결함을 잡아내는 것이 목적이다.

### User Story 1 - 테스트가 실제 마이그레이션으로 만든 스키마 위에서 돈다 (Priority: P1)

테스트용 스키마가 `ddl-auto` 자동 생성이 아니라 **운영에 적용되는 것과 동일한 Flyway 마이그레이션**으로 만들어진다. 그 결과 마이그레이션 SQL 자체(문법·타입·제약·시드 데이터)가 테스트 실행 시 함께 검증되어, 지금까지 테스트로 전혀 검증되지 않던 마이그레이션 결함을 잡는다.

**Why this priority**: 코드 검증 결과 이 작업의 **실질 가치가 여기 집중**된다. 현재 테스트는 Flyway 를 끄고(`flyway.enabled=false`) `ddl-auto: create-drop` 으로 스키마를 만들어, **마이그레이션 SQL 은 테스트에서 한 줄도 실행되지 않는다**. 게다가 실제 마이그레이션은 `JSON_OBJECTAGG`·`JSON_SET`·`MODIFY COLUMN`·`ADD COLUMN … AFTER` 같은 **MySQL 전용 함수·DDL 방언**으로 가득해 H2 로는 문법상 실행 자체가 불가능하다. 즉 운영 스키마를 만드는 경로 전체가 검증 사각지대이며, 잘못된 마이그레이션이 로컬/운영 DB 를 실제로 띄워 보기 전까지 발견되지 않는다. 이 사각지대를 없애는 것이 핵심 가치다.

**Independent Test**: 컨테이너 위에서 Flyway 마이그레이션이 전부 적용되어 스키마가 만들어지고, 그 스키마 위에서 기존 테스트가 통과하는지로 단독 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** MySQL 테스트 컨테이너가 준비되고, **When** 테스트 컨텍스트가 기동하면, **Then** 운영과 동일한 Flyway 마이그레이션이 순서대로 적용되어 스키마와 시드 데이터가 생성된다.
2. **Given** 새로 추가된 마이그레이션 SQL 이 MySQL 문법상 오류가 있고, **When** 테스트를 실행하면, **Then** 마이그레이션 적용 단계에서 테스트가 실패해 결함이 조기에 드러난다.

---

### User Story 2 - 영속 계층 테스트가 실제 MySQL 엔진에서 검증된다 (Priority: P2)

개발자가 리포지토리/영속 어댑터 테스트를 실행하면, 임베디드 H2 가 아니라 **운영과 동일한 MySQL 엔진**을 상대로 쿼리·매핑·제약이 실행된다. 그 결과 앞으로 추가될 MySQL 방언 의존 코드(타입·길이·함수·예약어·인덱스/제약 동작, 네이티브 JSON 쿼리 등)의 차이를 배포 전에 잡을 수 있는 **기반**이 마련된다.

**Why this priority**: 현재 테이블 기준으로는 이 항목의 즉각적 결함 검출력은 낮다 — JSON 컬럼은 Hibernate 의 `@JdbcTypeCode(SqlTypes.JSON)` 가 Java 레벨에서 직렬화를 추상화하고, 리포지토리에 네이티브 SQL(`JSON_EXTRACT`·`->>`)이 없어, 엔진만 바꿔도 대부분 동일하게 통과한다. 다만 프로젝트 규약이 이미 "컬럼 정의를 MySQL 기준으로 고정하고 H2 호환은 고려하지 않는다"이므로, 엔진을 운영과 일치시켜 두면 **향후 MySQL 전용 쿼리·제약이 추가될 때 자동으로 실환경에서 검증**된다. 그래서 P1(마이그레이션 검증)의 부수 효과이자 미래 대비 기반으로 P2 에 둔다.

**Independent Test**: 영속 어댑터 테스트(리포지토리 계층) 하나만 MySQL 컨테이너로 전환해도, 그 테스트가 실제 MySQL 엔진에서 통과하는지 단독으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** DB 를 직접 사용하는 통합 테스트가 있고, **When** 테스트 스위트를 실행하면, **Then** 테스트는 운영과 동일한 MySQL 엔진(동일 메이저 버전) 인스턴스를 상대로 실행된다.
2. **Given** MySQL 에서만 유효하고 H2 에서는 다르게 동작하거나 실패할 컬럼 정의/쿼리가 있고, **When** 테스트가 그 경로를 실행하면, **Then** 그 차이가 테스트 결과에 실제로 드러난다(운영과 동일하게 동작하거나, 문제라면 실패한다).

---

### User Story 3 - 컨테이너 재사용으로 반복 실행이 실용적으로 유지된다 (Priority: P3)

DB 컨테이너가 테스트 클래스마다 새로 뜨지 않고 **모듈 테스트 실행 내에서 재사용**되어, MySQL 도입으로 인한 반복 기동 오버헤드가 억제된다. 로컬 개발과 CI 양쪽에서 동일하게 동작한다.

**Why this priority**: 재사용/공유 전략이 없으면 컨테이너가 클래스마다 재기동되어 개발자가 테스트를 회피하게 되고, 이 기능의 가치가 훼손된다. 기능적 정확성(P1·P2)이 확보된 뒤 실용성으로 마무리한다.

**Independent Test**: 여러 DB 테스트 클래스를 한 번에 실행했을 때 컨테이너가 한 번만 기동되고 재사용되는지, 그리고 전체 스위트 시간이 목표 범위 내인지로 검증한다.

**Acceptance Scenarios**:

1. **Given** DB 를 사용하는 테스트 클래스가 여러 개 있고, **When** 스위트를 한 번 실행하면, **Then** MySQL 인스턴스는 실행당 한 번만 기동되어 클래스 간 재사용된다.
2. **Given** CI 환경에서 스위트를 실행하면, **When** 테스트가 돌면, **Then** 로컬에서 별도 DB 를 수동 기동하지 않아도 컨테이너가 자동 프로비저닝되어 통과한다.

---

### Edge Cases

- **Docker 미가용 환경**: 컨테이너 런타임(Docker 등)이 없는 로컬/CI 에서 DB 테스트를 돌리면, 원인 불명 오류가 아니라 "컨테이너 런타임이 필요하다"는 **명확하고 실행 가능한 실패 메시지**가 나와야 한다.
- **순수 도메인 단위 테스트**: DB·Spring 이 필요 없는 도메인 단위 테스트는 컨테이너를 띄우지 않고 기존과 동일하게 빠르게 실행되어야 한다(불필요한 프로비저닝 금지).
- **컨테이너 기동 지연/실패**: 컨테이너 기동이 느리거나 실패할 때 테스트가 무한정 대기하지 않고 합리적 시간 내 실패한다.
- **테스트 간 상태 격리**: 컨테이너를 재사용할 때 앞선 테스트가 남긴 데이터가 뒤 테스트에 새지 않도록 격리(정리/트랜잭션 롤백 등)가 보장되어야 한다.
- **버전 드리프트**: 운영 MySQL 메이저 버전이 올라가면 테스트 컨테이너 버전도 함께 따라가야 한다(불일치 방지).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: DB 를 직접 사용하는 모든 통합 테스트(영속 어댑터 테스트 및 DB 를 기동하는 web 통합 테스트)는 임베디드 H2 대신 **운영과 동일한 MySQL 엔진(동일 메이저 버전)** 인스턴스를 상대로 실행되어야 한다.
- **FR-002**: 테스트용 스키마는 `ddl-auto` 자동 생성이 아니라 **운영에 적용되는 것과 동일한 Flyway 마이그레이션**으로 생성되어야 한다(마이그레이션 SQL 이 테스트에서 실제 실행되어 검증됨).
- **FR-003**: MySQL 테스트 인스턴스는 개발자가 DB 를 **수동으로 기동하지 않아도 테스트 실행 시 자동 프로비저닝**되어야 한다.
- **FR-004**: MySQL 컨테이너는 **동일 Spring 테스트 컨텍스트당 한 번만** 기동되어(컨텍스트 캐싱으로 **클래스 간 재사용**) 클래스마다 재기동되지 않아야 한다. (한 모듈에 서로 다른 테스트 컨텍스트가 여러 개면 컨텍스트 수만큼 기동될 수 있으며, 모듈당 단일 컨테이너는 별도 최적화 대상이다.)
- **FR-005**: DB·Spring 컨텍스트가 필요 없는 **순수 도메인 단위 테스트는 컨테이너 없이** 기존과 동일하게 실행되어야 한다.
- **FR-006**: 재사용되는 인스턴스에서 **테스트 간 데이터 상태가 격리**되어야 한다(앞선 테스트의 잔여 데이터가 뒤 테스트 결과에 영향을 주지 않음).
- **FR-007**: 컨테이너 런타임을 사용할 수 없을 때 테스트는 **원인과 조치를 알 수 있는 명확한 메시지로 실패**해야 한다.
- **FR-008**: 통합 테스트 경로에서 **H2 의존은 더 이상 사용되지 않아야** 한다(DB-backed 테스트에서 H2 를 제거).
- **FR-009**: 테스트가 사용하는 MySQL 버전은 **운영 DB 버전과 일치**해야 하며, 운영 버전 변경 시 함께 갱신 가능한 단일 지점에서 관리되어야 한다.

### Key Entities

이 기능은 데이터 모델을 새로 도입하지 않는다. 기존 도메인/엔티티/스키마는 변경하지 않으며, **테스트가 실행되는 데이터베이스 환경만** H2 → MySQL(컨테이너)로 대체한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 운영 Flyway 마이그레이션 전체가 **테스트 스위트 실행 시 실제로 적용·검증**된다(현재 마이그레이션은 테스트에서 전혀 실행되지 않음 — 0% → 100%). *(이 작업의 핵심 성과 지표)*
- **SC-002**: DB 를 사용하는 통합 테스트의 **100% 가 운영과 동일한 MySQL 엔진(동일 메이저 버전)** 을 상대로 실행된다(현재 0%).
- **SC-003**: MySQL 컨테이너가 **동일 테스트 컨텍스트 내 클래스 간 재사용**되어(클래스마다 재기동되지 않음) 프로비저닝 오버헤드가 상각된다 — 재사용 동작을 **컨테이너 기동 횟수**로 검증한다.
- **SC-004**: DB 테스트를 통과시키기 위한 **H2 전용 우회/호환 코드가 0 건**이다(운영 기준 정의를 그대로 검증).
- **SC-005**: 새 마이그레이션이나 MySQL 전용 스키마/쿼리 결함이 **로컬/운영 DB 를 수동으로 띄우기 전, 테스트 단계에서** 검출된다.

## Assumptions

- 운영 DB 는 MySQL 이며, 로컬 개발 스택 기준 **MySQL 8.4** 를 운영 대상 버전으로 가정한다(운영 버전 확정 시 단일 지점에서 조정).
- 테스트 실행 환경(로컬 개발 머신 및 CI)에서 **컨테이너 런타임(Docker 또는 호환 런타임)을 사용할 수 있다**고 가정한다. 사용 불가 시 DB 통합 테스트는 실행되지 않는 것으로 본다(FR-007 의 명확한 실패).
- 이 작업의 범위는 **DB 를 사용하는 테스트의 실행 환경 교체**로 한정한다. 기존 테스트의 검증 로직/단언, 도메인/엔티티/스키마, 운영 런타임 설정은 변경하지 않는다.
- 순수 도메인 단위 테스트(Spring·DB 무관)는 이 변경의 영향 밖이며 계속 인메모리로 빠르게 실행된다.
- 향후 추가되는 DB 통합 테스트도 동일한 MySQL 컨테이너 기반 경로를 재사용한다(H2 로 회귀하지 않음).
