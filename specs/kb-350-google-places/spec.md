# Feature Specification: 장소 검색을 Google Places API (New) 로 전환

**Feature Branch**: `kb-350-google-places`

**Created**: 2026-08-19

**Status**: Draft

**Input**: User description: "KB-350 — 장소 검색을 카카오 로컬 API 에서 Google Places API (New) 로 전환 (8/15 기획: 지도 API 구글 전환). 화면 진입 시 현재 좌표 기준 근처 식당 20건, 그 외에는 검색 키워드+좌표로 20건 단일 응답 — 페이징 없음."

## 맥락 (Jira KB-350·agent-hub·사용자 확정)

- 8/15 기획: 지도 API 를 구글로 전환(현재 Kakao — `common.port.place`). 후속으로 스캔 위치 자동 태깅(위치+메뉴명 검색 → 첫 식당 기본 태그)이 예정돼 있으나 **이 태스크는 검색 제공자 전환까지만** 다룬다.
- 사용자 확정(2026-08-19): **페이징 제거 — 단일 응답 최대 20건.** 구글 Places (New) 는 페이지당 최대 20건·토큰(nextPageToken) 방식·검색당 총 60건 상한인데, 식당 태그 화면에서 20건이면 충분하다는 기획 판단. 토큰은 요청·응답·서버 내부 어디에도 등장하지 않는다.
- 화면 흐름: **장소 태그 화면 진입 시** 현재 좌표로 주변 식당 20건 목록(Nearby) → 사용자가 검색어를 입력하면 **키워드+좌표 검색** 20건(Text Search).
- 현재 구조: seam `PlaceSearchClient`(searchNearby·searchPage) 뒤에 카카오 어댑터. 소비자는 장소 API(주변·검색)와 리뷰 작성의 식당 선택(place 저장, 출처 `KAKAO_PLACE`).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 화면 진입 시 주변 식당 목록 (Priority: P1)

회원이 리뷰 작성에서 장소 태그 화면에 진입하면, 현재 좌표 기준 **근처 식당 최대 20건**이 구글 데이터로 내려간다.

**Why this priority**: 태그 화면의 첫 화면 — 검색 없이 바로 고르는 기본 경로.

**Independent Test**: 좌표로 주변 조회 → 구글 기반 식당 목록(이름·주소·좌표) 최대 20건.

**Acceptance Scenarios**:

1. **Given** 유효한 좌표, **When** 주변 조회를 호출하면, **Then** 근처 식당 최대 20건이 기존 응답 형태(이름·주소·좌표)로 내려간다.
2. **Given** 주변에 식당이 없는 좌표, **When** 조회하면, **Then** 빈 목록(200)이다.
3. **Given** 좌표 누락·범위 밖 값, **When** 조회하면, **Then** 기존과 동일하게 400 이다.

---

### User Story 2 - 키워드 장소 검색 (Priority: P1)

사용자가 검색어를 입력하면 **키워드+좌표** 기준으로 구글 검색 결과 **최대 20건이 단일 응답**으로 내려간다. 페이징 파라미터는 없다.

**Why this priority**: 기본 목록에 원하는 식당이 없을 때의 유일한 경로.

**Independent Test**: 검색어+좌표로 검색 호출 → 20건 이하 단일 응답, page 파라미터 없음.

**Acceptance Scenarios**:

1. **Given** 검색어와 좌표, **When** 검색을 호출하면, **Then** 관련 식당 최대 20건이 단일 응답으로 내려간다(더보기·페이지 없음).
2. **Given** 결과가 없는 검색어, **When** 검색하면, **Then** 빈 목록(200)이다.
3. **Given** 기존 클라이언트가 보내던 `page` 파라미터, **When** 함께 보내면, **Then** 무시된다(400 아님 — 미지원 파라미터는 관대 수용, 전환기 호환).

---

### User Story 3 - 리뷰의 장소 출처 구분 (Priority: P2)

전환 후 작성되는 리뷰의 장소는 **구글 출처**로 저장·노출되고, 기존 카카오 출처 리뷰는 그대로 보존된다.

**Why this priority**: 데이터 정합 — 과거 리뷰를 깨지 않으면서 신규 출처를 구분.

**Independent Test**: 전환 후 검색 결과로 리뷰 작성 → place 출처가 구글. 기존 리뷰 조회 → 카카오 출처 그대로.

**Acceptance Scenarios**:

1. **Given** 구글 검색 결과로 식당을 골라 리뷰 작성, **When** 저장하면, **Then** 장소 출처가 구글로 저장되고 조회 응답에 그 출처가 내려간다.
2. **Given** 전환 전 작성된 카카오 출처 리뷰, **When** 조회하면, **Then** 기존 출처·식당 정보가 그대로 내려간다.
3. **Given** 수동 입력(MANUAL)·작성자 좌표(AUTHOR_LOCATION) 출처, **When** 작성·조회하면, **Then** 기존과 동일하게 동작한다.

---

### Edge Cases

- 구글 API 장애·타임아웃 — 기존 카카오 어댑터의 실패 처리 방식과 동일 수준(전파되는 오류 응답)을 유지한다. 폴백(카카오 재시도)은 두지 않는다 — 전환이지 이중화가 아님.
- 응답 언어 — 검색 결과 식당명·주소는 서비스 사용자 다수가 한국 소재 식당을 찾으므로 한국어 우선으로 요청한다(구글 언어 파라미터). 세부는 plan 에서.
- 검색당 20건 초과 결과 — 절단되며 안내 없음(기획 확정). 총량 확장(40·60건)은 서버 내부 변경만으로 가능(클라이언트 계약 불변).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 주변 조회는 좌표 기준 구글 데이터로 최대 20건을 반환해야 한다 — 기존 응답 형태(이름·주소·좌표) 유지.
- **FR-002**: 키워드 검색은 검색어+좌표 기준 구글 데이터로 **최대 20건 단일 응답**이어야 한다 — 페이징 파라미터·hasNext·토큰 없음.
- **FR-003**: 기존 `page` 파라미터는 계약에서 제거하되, 전환기 동안 보내는 클라이언트를 400 으로 거절하지 않는다(무시).
- **FR-004**: 전환 후 작성 리뷰의 장소 출처는 구글로 저장·노출되어야 하며, 기존 카카오·수동·작성자좌표 출처 데이터와 동작은 불변이다.
- **FR-005**: 카카오 연동(어댑터·설정)은 제거한다 — 폴백 없음.
- **FR-006**: 장소 API 의 인증·경로 등 그 외 계약은 불변이다.

### Key Entities

- **장소 검색 결과**: 이름·주소·좌표 — 기존 응답 형태 유지(제공자 전환이 계약 형태를 바꾸지 않음, 페이징 제거 제외).
- **리뷰 장소 출처**: 기존 카카오/수동/작성자좌표에 **구글** 추가 — 저장된 과거 값은 불변.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 태그 화면 진입 시 좌표 기반 주변 식당 목록(≤20건)이 구글 데이터로 내려온다.
- **SC-002**: 키워드 검색이 단일 응답(≤20건)으로 완결된다 — 페이징 요청 0건.
- **SC-003**: 전환 후 신규 리뷰의 장소 출처는 100% 구글로 기록되고, 기존 리뷰의 장소 표시 회귀 0건.
- **SC-004**: 카카오 API 호출 0건(전환 완료) — 관련 설정·키 제거.

## Assumptions

- 스캔 위치 자동 태깅(위치+메뉴명 → 첫 식당 기본 태그)은 별도 후속 태스크 — 이 기능은 검색 제공자 전환까지.
- 구글 API 키는 서버 환경변수로 공급되며 발급·과금 설정은 운영 작업으로 별도 진행.
- 리뷰 장소 출처의 기존 값(카카오)은 마이그레이션하지 않는다 — 신규만 구글.
- 20건 상한은 기획 확정값 — 확장(≤60) 시 서버 내부 변경만으로 대응 가능.
