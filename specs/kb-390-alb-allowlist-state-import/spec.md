# Feature Specification: 인프라 제어권 복구 — terraform state 를 이 컴퓨터에 마련하고, prod 에 수집기를 붙이고, 공개 진입점에서 관리 경로를 막는다

**Feature Branch**: `kb-390-alb-allowlist-state-import`

**Created**: 2026-08-28

**Status**: Draft

**Input**: User description: "390 진행. state는 import를 dev, prod 환경 대상으로 진행하여 현재 컴퓨터에 마련한다. 이후 prod 쪽에 alloy를 붙여 홈서버 그라파나에서 잘 나오는지 확인하는 작업도 한다" — Jira KB-390(ALB 허용 목록) + KB-381 DoD 잔여(prod Alloy) + prod terraform state 복구(미등록, 이 spec 에서 다룸)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 운영자가 이 컴퓨터에서 dev·prod 인프라를 terraform 으로 다시 다룰 수 있다 (Priority: P1)

지금 dev 인프라의 장부(state)는 집 맥미니에만 있고, prod ECS 의 장부는 어디에도 없다(만든 뒤 사라짐). 그래서 prod 에는 아무것도 terraform 으로 추가할 수 없고, dev 도 맥미니 앞에 앉아야만 바꿀 수 있다. 이 기능이 끝나면 운영자가 **이 컴퓨터(맥북)에서** dev·prod 둘 다 `plan` 을 떠서 "변경 없음"을 확인하고 필요한 것만 추가할 수 있다. 장부는 두 컴퓨터가 같은 것을 보도록 공유 저장소에 둔다.

**Why this priority**: 이게 없으면 US2·US3 모두 prod 에는 적용할 수 없다. 이번 세션에서 두 번 벽에 부딪힌 근본 원인.

**Independent Test**: 이 컴퓨터에서 dev·prod 각각 `plan` 을 떴을 때 **"변경 없음(0 add / 0 change / 0 destroy)"** 이 나오고, 맥미니에서 같은 plan 을 떠도 같은 결과면 통과.

**Acceptance Scenarios**:

1. **Given** prod ECS 리소스가 AWS 에 실제로 돌고 있고 장부가 없다, **When** 운영자가 이 컴퓨터에서 prod 를 terraform 으로 읽어들이면, **Then** 실제 리소스 전부가 장부에 잡히고 `plan` 이 변경 없음을 보고한다 — 어떤 운영 리소스도 재생성·교체되지 않는다.
2. **Given** dev 장부가 맥미니에 있다, **When** 공유 저장소로 옮기면, **Then** 이 컴퓨터와 맥미니 어디서 `plan` 을 떠도 변경 없음이고, 두 곳에서 동시에 apply 를 시도하면 한쪽이 잠금으로 거부된다.
3. **Given** 장부가 공유 저장소에 있다, **When** 운영자가 `dev.tfvars`·`prod.tfvars` 없이 `plan` 을 시도하면, **Then** 명확한 오류로 멈추며(조용히 기본값으로 진행하지 않음), 두 파일의 정확한 값은 문서로 복원 가능하다.
4. **Given** 이 컴퓨터의 로컬에 옛 장부 사본이 남아 있다, **When** 마이그레이션이 끝나면, **Then** 로컬 사본이 다시 쓰일 수 없게 정리되거나 문서에 "쓰지 말 것"이 명시된다.

### User Story 2 - prod 앱·호스트 메트릭이 홈서버 Grafana 에 나온다 (Priority: P1)

dev 에서 검증된 수집기(KB-381)를 prod 에도 똑같이 붙여, 운영자가 홈서버 Grafana 에서 `env=prod` 로 api 의 내부 상태와 호스트 자원을 본다. prod 배치는 현재 꺼져 있어 배치 호스트에서는 호스트 자원만 나온다.

**Why this priority**: 모니터링 에픽의 목적이 prod 관측이다. dev 만으로는 반쪽.

**Independent Test**: 홈서버 Grafana 에서 `up{env="prod", job="prometheus.scrape.ecs_apps"}` 가 prod api 태스크 수(2)만큼 1 이고, 호스트 타깃이 prod 인스턴스 수만큼 보이면 통과.

**Acceptance Scenarios**:

1. **Given** US1 로 prod 장부가 복구됐다, **When** 수집기를 prod 에 적용하면, **Then** 추가되는 것은 수집기 관련 3개뿐이고(로그 저장소·수집기 정의·서비스) 기존 prod 리소스는 변경 0 이다.
2. **Given** 수집기가 prod 에 떴다, **When** Grafana 에서 `env="prod"` 를 조회하면, **Then** api 태스크 2개의 JVM·커넥션 풀·요청 메트릭과 호스트별 메모리·디스크가 15초 간격으로 보인다.
3. **Given** prod 수집기가 홈서버로 보내고 있다, **When** dev 와 prod 를 같은 대시보드에서 `env` 로 전환하면, **Then** 서로 섞이지 않는다.
4. **Given** prod 토큰이 dev 토큰과 다르다, **When** 한쪽 토큰을 폐기하면, **Then** 다른 환경 수집에는 영향이 없다.

### User Story 3 - 공개 도메인에서 관리 경로가 보이지 않는다 (Priority: P2)

지금 `https://dev.kbap.site/actuator/prometheus` 로 누구나 내부 지표를 읽을 수 있다. 공개 진입점(로드밸런서 계층)에서 **앱이 실제로 내놓는 경로(API·관리자 페이지·정적 자원·문서)만 통과**시키고 나머지는 존재하지 않는 것으로 응답한다. 경로를 변형한 요청(`//actuator/…`, 퍼센트 인코딩)도 새지 않아야 한다. 카나리 배포(구·신 버전 전환)는 지금처럼 동작해야 한다.

**Why this priority**: 노출되는 건 내부 지표(자격증명 아님)라 P1 뒤. 그러나 KB-380 에서 "후속으로 막는다"고 약속한 항목이라 이번에 닫는다.

**Independent Test**: dev 적용 후 `/actuator/prometheus`·`//actuator/prometheus`·`/%61ctuator/prometheus` → 404, `/api/app-version`·`/admin/login`·Swagger → 200, 로드밸런서 타깃 healthy 유지, 카나리 배포 1회가 정상 전환.

**Acceptance Scenarios**:

1. **Given** dev 에 적용됐다, **When** 공개 도메인으로 관리 경로를 원문·변형 형태로 호출하면, **Then** 모두 404 다.
2. **Given** 같은 적용, **When** 앱이 내놓는 경로(API·관리자 페이지·정적·문서)를 호출하면, **Then** 이전과 동일하게 응답한다.
3. **Given** 같은 적용, **When** api 를 카나리로 1회 배포하면, **Then** 구→신 전환이 이전과 같이 완료되고 전환 후 신버전이 응답한다(경로 규칙이 전환을 방해하지 않음).
4. **Given** 같은 적용, **When** 로드밸런서 헬스체크와 호스트 안의 수집기를 보면, **Then** 둘 다 영향 없다(헬스체크 통과, `up` 유지).
5. **Given** dev 에서 통과했다, **When** prod 에 같은 규칙을 적용하면, **Then** prod 는 문서(Swagger) 경로를 허용 목록에서 뺀 채로 동일하게 동작한다.

### Edge Cases

- prod 장부 복구 중 실제 리소스와 코드가 조금 다르면(태그·기본값)? → apply 하지 않고 차이를 문서화한 뒤, 코드를 실제에 맞추거나 무해함을 확인한 후에만 진행. "변경 없음"이 나올 때까지 apply 금지.
- 복구 도중 prod 에 CI 배포가 일어나면? → 태스크 정의·서비스는 terraform 이 무시하도록 돼 있어(ignore) 영향 없음. 그 외 리소스는 CI 가 건드리지 않는다.
- 공유 저장소 잠금이 남아 있으면(이전 apply 가 중단)? → 잠금 해제 절차를 문서에 둔다.
- 두 컴퓨터에서 동시에 apply? → 잠금으로 한쪽 거부(US1-2).
- 허용 목록에 없는 새 경로를 앱에 추가하면? → 공개 도메인에서 404 가 난다. README 에 "새 공개 경로 = 허용 목록도 수정" 을 명시. 관리자 페이지·Swagger 는 이미 포함.
- 경로 규칙이 카나리 전환을 따라가지 못하면? → 전환 후 신버전이 아닌 구버전이 응답하거나 404 — dev 카나리 1회로 반드시 확인(US3-3).
- prod 배치를 나중에 켜면? → 수집기는 이미 그 호스트에 떠 있어 자동으로 배치 앱 타깃이 추가된다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: dev·prod 인프라 장부(state)가 두 컴퓨터(맥북·맥미니)에서 같은 것을 보는 공유 저장소에 있어야 하며, 동시 apply 는 잠금으로 막혀야 한다.
- **FR-002**: prod ECS 의 실제 리소스 전부가 장부에 잡혀 `plan` 이 "변경 없음"을 보고해야 한다. 복구 과정에서 어떤 prod 리소스도 재생성·교체·삭제되지 않는다.
- **FR-003**: dev 장부는 맥미니의 기존 것을 옮겨 이어받아야 하며(다시 만들지 않음), 옮긴 뒤 `plan` 이 변경 없음이어야 한다.
- **FR-004**: `dev.tfvars`·`prod.tfvars` 의 정확한 값(예시 파일과 다른 항목)이 복원 가능하도록 문서화되어야 한다. 값 자체를 git 에 넣지 않는다.
- **FR-005**: prod 에 수집기가 dev 와 동일 구성으로 적용되어야 하며, 적용 시 추가되는 것은 수집기 관련 3개뿐이다.
- **FR-006**: 홈서버 Grafana 에서 `env=prod` 앱 메트릭(api 태스크 2)과 호스트 메트릭(인스턴스 수만큼)이 15초 간격으로 조회되어야 한다.
- **FR-007**: 공개 진입점은 앱이 내놓는 경로(API·관리자 페이지·정적 자원·dev 한정 문서)만 통과시키고 그 외는 404 로 응답해야 한다. 경로 변형(중복 슬래시·퍼센트 인코딩·대소문자)으로 관리 경로에 도달할 수 없어야 한다.
- **FR-008**: 경로 규칙은 카나리 배포의 구→신 전환을 방해하지 않아야 하며, dev 에서 배포 1회로 실증한다.
- **FR-009**: 경로 규칙은 로드밸런서 헬스체크와 호스트 안 수집기에 영향을 주지 않아야 한다.
- **FR-010**: 인프라 문서에 (a) 장부 위치·잠금·복원 절차, (b) tfvars 복원 값, (c) 허용 목록과 "새 공개 경로 추가 시 규칙도 수정" 규칙이 기록되어야 한다.

### Key Entities *(include if feature involves data)*

- **인프라 장부(state)**: 환경별 1개(dev·prod). 공유 저장소에 저장, 잠금 동반. 코드 블록 ↔ 실제 리소스 id 대응표.
- **환경 변수 파일(tfvars)**: 환경별 1개. git 밖. 예시 파일 대비 차이 항목만 문서화.
- **허용 경로 목록**: 환경별(dev 는 문서 경로 포함, prod 는 제외). 공개 진입점 규칙의 입력.
- **수집기(prod)**: KB-381 과 동일 — 호스트당 1개, `env=prod` 토큰 별도.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 이 컴퓨터와 맥미니 양쪽에서 dev·prod `plan` 이 모두 "0 add / 0 change / 0 destroy" 다.
- **SC-002**: prod 장부 복구 전후로 prod 리소스의 생성 시각이 하나도 바뀌지 않는다(재생성 0).
- **SC-003**: prod 수집기 적용 plan 이 정확히 3 add 이고, 적용 후 5분 안에 Grafana `up{env="prod"}` 가 api 태스크 수와 일치한다.
- **SC-004**: 공개 도메인에서 관리 경로 원문·변형 3종 호출이 100% 404, 허용 경로 호출은 적용 전과 동일 응답.
- **SC-005**: 규칙 적용 후 dev 카나리 배포 1회가 이전과 같은 시간 안에 완료되고 전환 후 신버전이 100% 응답한다.
- **SC-006**: 이 기능으로 인한 월 추가 비용은 공유 저장소(스토리지 수 KB)와 — 규칙을 로드밸런서 밖 서비스로 구현할 경우 그 서비스 요금 — 뿐이며, 새 서버·로드밸런서·고정 IP 는 0 이다.

## Assumptions

- "현재 컴퓨터에 마련한다"는 **맥북에서 apply 할 수 있게 한다**로 해석하고, 두 컴퓨터가 서로 다른 장부를 갖는 사고를 막기 위해 **공유 저장소(S3 백엔드, 잠금 포함)** 를 전제로 한다. 코드에 이미 주석으로 준비된 구성을 켠다.
- dev 는 맥미니의 기존 장부를 **옮기는 것(migrate)** 이지 다시 읽어들이는 것(import)이 아니다 — 결과(맥북에서 dev 를 다룰 수 있음)는 같고 위험이 훨씬 작다. import 는 장부가 없는 prod 에만 한다.
- prod 의 태스크 정의·서비스는 CI 가 이미지 교체 리비전을 만들어 왔으므로 코드와 "초기값"이 다르다 — 이는 `ignore_changes` 로 무시되는 항목이라 변경 없음 판정에 영향이 없다. 그 외 드리프트(사람이 콘솔에서 바꾼 것)가 있으면 코드를 실제에 맞춘다.
- prod Alloy 의 전제(Cloudflare Access prod 토큰, SSM `/kbap/prod/CF_ACCESS_*`)는 KB-381 에서 이미 준비됐다.
- 경로 규칙의 구현 계층은 계획 단계에서 정한다 — 로드밸런서 리스너 규칙만으로는 카나리 전환(배포 도구가 리스너의 기본 동작만 바꿈)과 경로 정규화를 둘 다 만족 못 할 수 있어, 로드밸런서 앞단의 요청 필터(경로 정규화 지원)까지 후보에 둔다. 앱 코드로 막지는 않는다(사용자 결정, KB-380).
- prod 는 문서(Swagger) 경로를 공개하지 않는다. dev 는 공개한다.
- 자동화 테스트는 작성하지 않는다(인프라 작업, KB-380/381 과 동일). 검증은 plan 출력·curl·Grafana 조회·카나리 1회.
- 실행 위치: 장부 복구는 맥미니의 dev 장부를 읽어야 하므로 맥미니 세션과 협업한다(맥북이 주도, 맥미니는 마이그레이션 명령 실행).
