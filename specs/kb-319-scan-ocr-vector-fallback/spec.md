**Feature Branch**: `kb-319-scan-ocr-vector-fallback`

**Created**: 2026-08-10

**Status**: Draft

**Jira**: KB-319 (선행: KB-318 — 유사 음식 검색 저장소 구축, 인프라 완료)

**Input**: User description: "documentdb로 벡터 db는 만들어놓은 상태임. 따라서 ocr를 위한 llm api 설계, 그리고 db miss난 음식들을 벡터디비에서 찾는 로직, 그 후 응답으로 내려주는 로직을 구현하면 돼. 기존 api와 다르게 동작하도록 버저닝 헤더를 동일한 정책으로 붙이면 됨."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 사진 업로드만으로 스캔 완료 (Priority: P1)

신버전 앱 사용자는 메뉴판 사진을 업로드하기만 하면 스캔 결과를 받는다. 기존 플로우와 달리 클라이언트가 기기에서 글자를 읽어(OCR) 항목 목록을 만들어 보낼 필요가 없다 — 서버가 사진에서 텍스트를 추출하고, 음식 이름·가격 쌍으로 정제한 뒤, 등록된 음식이면 저장된 음식 정보(위험도 포함)를 내려준다.

**Why this priority**: 이 기능의 존재 이유다. 클라이언트 OCR 의존을 제거해 스캔 품질을 서버가 통제하고, 등록 음식 hit 경로만으로도 신규 플로우가 완결된 가치를 낸다.

**Independent Test**: 등록(READY) 음식이 적힌 메뉴판 사진 경로로 신규 계약 버전 헤더와 함께 스캔을 요청하면, 항목 목록 없이도 해당 음식의 저장된 정보가 응답에 담긴다.

**Acceptance Scenarios**:

1. **Given** 업로드 완료된 메뉴판 사진과 등록된 음식 "김치찌개", **When** 신규 계약 버전 헤더로 사진 경로만 보내 스캔하면, **Then** 서버가 추출·정제한 "김치찌개"가 등록 음식 정보(이름·위험도 등 기존 스캔과 동일한 정보)로 응답된다.
2. **Given** 메뉴판이 아닌 사진(음식 텍스트 없음), **When** 신규 계약으로 스캔하면, **Then** 오류가 아니라 빈 결과가 정상 응답된다.
3. **Given** 텍스트 추출은 됐지만 가격이 없는 메뉴, **When** 스캔하면, **Then** 가격 없이 음식 이름만으로 정제·조회가 진행된다.

---

### User Story 2 - 미등록 음식은 유사 음식으로 대체 응답 (Priority: P2)

정제된 음식 이름이 등록 음식에 없으면(miss), 시스템은 미리 구축된 유사 음식 검색 저장소에서 가장 비슷한 음식을 찾아 그 음식의 이름·설명·사진 경로를 **유사 대체 결과임을 구분할 수 있는 형태로** 내려준다. 사용자는 모르는 메뉴를 찍어도 "정보 없음" 대신 비슷한 음식의 정보로 힌트를 얻는다.

**Why this priority**: miss 경로는 hit 경로가 있어야 의미가 있다. 미등록 메뉴에서 빈 화면 대신 유사 정보를 주는 것이 이 기능의 차별점이지만, P1 없이 단독으로는 성립하지 않는다.

**Independent Test**: 등록 음식에 없는 이름이 적힌 메뉴판을 신규 계약으로 스캔하면, 응답 항목에 유사 음식의 이름·설명·사진 경로와 "정확 매칭 아님" 구분자가 담긴다.

**Acceptance Scenarios**:

1. **Given** 등록 음식에 없는 메뉴 "할머니손맛찌개"와 유사 음식 "김치찌개"가 검색 저장소에 존재, **When** 신규 계약으로 스캔하면, **Then** 해당 항목은 유사 음식의 이름·설명·사진 경로를 담고 유사 대체 결과임이 응답에서 구분된다.
2. **Given** 유사 대체로 내려간 음식, **When** 클라이언트가 그 음식의 식별자로 상세 조회를 호출하면, **Then** 정상적으로 상세 정보가 조회된다(유사 음식은 등록 음식 중에서만 선정되므로 식별자가 항상 유효).
3. **Given** 검색 저장소에서 충분히 비슷한 음식을 찾지 못한 미등록 메뉴, **When** 스캔하면, **Then** 유사 대체 없이 미등록(미조사) 상태로 응답된다 — 비슷하지 않은 음식을 억지로 보여주지 않는다.

---

### User Story 3 - 기존 스캔 플로우 무영향 (Priority: P3)

기존 앱 사용자는 아무 변화를 겪지 않는다. 클라이언트 OCR 항목을 보내는 기존 스캔 요청은 계약 버전 헤더가 없거나 이전 버전이면 종전과 완전히 동일하게 동작한다.

**Why this priority**: 회귀 방지는 필수 제약이지만 새 가치를 만들지는 않는다. P1·P2 구현의 전제 조건으로 검증한다.

**Independent Test**: 계약 버전 헤더 없이 기존 형식(사진 경로 + 항목 목록)으로 스캔하면 종전과 동일한 검증·응답·부수 동작이 수행된다.

**Acceptance Scenarios**:

1. **Given** 기존 앱의 스캔 요청(헤더 없음, 항목 목록 포함), **When** 스캔하면, **Then** 종전과 동일한 응답 형식·오류 코드로 동작한다(회귀 0건).
2. **Given** 신규 계약 버전 미만 또는 형식이 잘못된 헤더, **When** 스캔하면, **Then** 기존 계약으로 동작한다.

---

### Edge Cases

- 텍스트 추출(OCR) 또는 이름·가격 정제 단계가 실패하면? → 기존 스캔의 추출 실패 처리와 동일하게 서비스 오류로 응답하고, 구조가 깨진 결과만 오류로 취급한다(빈 결과는 정상).
- 정제 결과에 같은 음식 이름이 중복되면? → 중복 이름은 하나의 항목으로 합치지 않고 메뉴판에 나타난 대로 응답한다(기존 스캔과 동일).
- 유사 음식 검색 저장소가 일시적으로 응답하지 않으면? → 스캔 전체를 실패시키지 않고, 해당 miss 항목만 유사 대체 없이 미등록 상태로 응답한다(부분 성공).
- 유사 검색이 반환한 음식이 등록 음식에서 삭제·비공개 상태로 바뀌었다면? → 응답에서 제외하고 미등록 상태로 응답한다.
- 한 사진에서 hit 과 miss 가 섞여 나오면? → 항목별로 독립 판정한다 — hit 항목은 등록 정보, miss 항목은 유사 대체.
- 남의 이미지 경로로 스캔을 요청하면? → 기존 스캔과 동일한 소유 검증 정책을 따른다(현행 유예 상태 포함 — 정책 변경은 이 기능 범위 밖).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 스캔 요청의 계약 버전 헤더(`X-API-Version`, 선택)로 신·구 동작을 분기해야 한다. 버전 표기·비교·폴백 규칙은 기존 버저닝 정책(캘린더 표기 `yyyy.mm.sprint차수`, 이상이면 신동작, 미전송·이전·형식 오류는 종전 계약)과 동일해야 한다.
- **FR-002**: 신규 계약 요청은 사진 경로만으로 성립해야 하며, 클라이언트 OCR 항목 목록을 요구하지 않아야 한다.
- **FR-003**: 시스템은 신규 계약 요청에서 사진의 텍스트를 서버 측에서 추출하고, 추출 텍스트에서 음식 이름·가격 쌍을 정제해야 한다. 가격이 없는 항목은 이름만으로 진행한다.
- **FR-004**: 시스템은 정제된 음식 이름을 기존 스캔과 동일한 이름 정규화 규칙으로 등록 음식과 대조해야 한다.
- **FR-005**: 등록 음식과 일치(hit)한 항목은 기존 스캔 응답과 동등한 수준의 저장된 음식 정보(이름·조사 상태·기피 위험도 판정 포함)로 응답해야 한다.
- **FR-006**: 등록 음식에 없는(miss) 항목은 유사 음식 검색 저장소에서 정제된 이름으로 유사 음식을 검색해, 유사 음식의 이름·설명·사진 경로를 대체 응답으로 내려야 한다.
- **FR-007**: 유사 대체 결과는 응답에서 정확 매칭 결과와 명확히 구분되어야 한다 — 클라이언트가 "정확 매칭 아님" 주의 표시를 그릴 수 있는 명시적 구분자를 포함한다.
- **FR-008**: 유사 대체 결과는 등록 음식의 유효한 식별자를 포함해야 하며, 그 식별자로 기존 음식 상세 조회가 가능해야 한다(유사 음식 선정 대상을 등록 음식으로 한정).
- **FR-009**: 유사도가 기준에 미달하거나 검색 저장소 장애 시, 해당 항목은 유사 대체 없이 미등록(미조사) 상태로 응답해야 하며 스캔 전체를 실패시키지 않아야 한다.
- **FR-010**: 신규 계약 스캔도 기존 스캔의 부수 동작(스캔 이력 기록, 스캔 횟수 증가)을 동일하게 수행해야 한다.
- **FR-011**: 계약 버전 헤더가 없거나 이전 버전·형식 오류인 요청은 기존 스캔 계약(요청 형식·검증·응답·오류 코드)과 완전히 동일하게 동작해야 한다 — 기존 API 회귀 0건.
- **FR-012**: 유사 대체 응답의 표시 방식과 상세 조회 연동 방안(FR-007·FR-008)은 결정 근거와 함께 문서화되어야 한다.

### Key Entities

- **스캔 요청(신규 계약)**: 업로드 완료된 메뉴판 사진 경로. 항목 목록 없음.
- **정제 메뉴 항목**: 서버가 추출·정제한 음식 이름·가격 쌍. 가격은 선택.
- **등록 음식**: 서비스가 보유한 음식 마스터. 이름·설명·사진·조사 상태·성분(위험도 판정 근거)을 가진다.
- **유사 음식 후보**: 유사 음식 검색 저장소의 검색 결과. 등록 음식의 식별자·이름·설명·사진 경로와 유사도 정보를 가지며, 수록 대상은 등록 음식으로 한정된다.
- **스캔 이력**: 신규·기존 계약 공통으로 기록되는 스캔 결과(매칭 실패 항목 포함, 가격 보존).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 신버전 앱 사용자는 사진 업로드 외의 입력 없이 스캔 결과를 받는다 — 클라이언트 측 문자 인식 절차가 플로우에서 완전히 제거된다.
- **SC-002**: 등록 음식이 적힌 메뉴판 스캔에서, 신규 계약 응답의 음식 정보는 기존 계약으로 같은 음식을 스캔했을 때와 동등하다.
- **SC-003**: 미등록 음식 항목의 90% 이상이 "정보 없음" 대신 유사 음식 정보(이름·설명·사진)를 포함해 응답된다(검색 저장소 정상 가동 기준).
- **SC-004**: 유사 대체 결과는 100% 구분자를 포함하며, 그 식별자로 상세 조회 시 실패율 0%.
- **SC-005**: 기존 계약 스캔의 요청·응답·오류 동작이 배포 전후 동일하다(회귀 0건).
- **SC-006**: 사용자는 스캔 요청 후 합리적 대기 시간(기존 스캔과 동등한 수준) 안에 결과를 받는다 — 서버 측 추출·정제가 추가되어도 사용자 체감 흐름이 유지된다.

## Assumptions

- **계약 버전 값은 현행 스프린트의 캘린더 버전(`2026.08.07`)을 사용한다** — 온보딩 v2 와 같은 릴리즈 스프린트이므로 같은 버전 값을 공유한다(엔드포인트별 임계값 비교는 독립).
- 신규 플로우는 **기존 스캔 엔드포인트에 계약 버전 헤더로 공존**한다 — 별도 경로를 만들지 않는다(버저닝 정책 문서의 "같은 리소스의 동작 분기는 헤더" 기준).
- 이미지 업로드 플로우(presign → 직접 업로드 → 완료 신고)는 기존 것을 그대로 사용하며 이 기능 범위 밖이다.
- 유사 음식 검색 저장소(벡터 저장소)와 그 데이터 적재는 **이미 구축 완료**(KB-318·인프라)이며, 이 기능은 검색·응답 연동만 담당한다. 텍스트 임베딩 수단은 기존에 도입된 것을 재사용한다.
- 유사 대체는 **miss 항목당 최유사 1건**을 기본으로 한다(복수 후보 노출은 클라이언트 UX 결정 시 후속 확장).
- miss 항목의 **조사 대기 음식 자동 등록(수요 파악용)은 기존 스캔과 동일하게 유지**한다 — 유사 대체 응답과 별개로 동작한다.
- 유사도 기준값(임계)은 구현 단계에서 실데이터로 튜닝하며, 스펙은 "기준 미달 시 대체 없음" 동작만 고정한다.
- 이미지 소유 검증의 현행 유예 상태는 이 기능에서 바꾸지 않는다(별도 결정 사항).
- 신규 계약의 언어 파라미터(`lang`) 동작은 기존 스캔과 동일하다.
