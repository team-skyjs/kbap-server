## User Scenarios & Testing *(mandatory)*

### User Story 1 - 전체 리뷰 피드 조회 (Priority: P1)

로그인한 사용자가 특정 음식을 고르지 않고도 서비스 전체에 올라온 최신 리뷰를 피드처럼 둘러본다. 화면을 아래로 스크롤하면 다음 리뷰 묶음이 이어서 로드된다(무한 스크롤).

**Why this priority**: 현재는 음식을 먼저 선택해야만 그 음식의 리뷰를 볼 수 있어, 서비스 전체의 생생한 리뷰를 탐색하는 진입점이 없다. 전체 피드는 이 기능의 핵심 가치이며 이것 하나만으로도 독립적인 화면이 성립한다.

**Independent Test**: 여러 음식에 걸쳐 리뷰를 여러 건 등록한 뒤, 음식 지정 없이 전체 리뷰 목록을 요청하면 최신순으로 반환되고, 응답에 포함된 커서로 다음 페이지를 이어서 받을 수 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 서로 다른 음식에 리뷰가 여러 건 등록되어 있을 때, **When** 사용자가 음식 지정 없이 전체 리뷰 목록을 요청하면, **Then** 음식과 무관하게 모든 리뷰가 최신순으로 반환된다.
2. **Given** 첫 페이지 응답에 다음 커서가 포함되어 있을 때, **When** 그 커서로 다음 페이지를 요청하면, **Then** 이전 페이지와 중복·누락 없이 이어지는 리뷰가 반환된다.
3. **Given** 등록된 리뷰가 하나도 없을 때, **When** 전체 리뷰 목록을 요청하면, **Then** 오류 없이 빈 목록이 반환된다.

---

### User Story 2 - 리뷰 카드에 음식 정보 표시 (Priority: P2)

사용자가 리뷰 목록(전체 피드·음식별·내 리뷰)을 볼 때, 각 리뷰에 "어떤 음식에 대한 리뷰인지"가 음식 이름 등으로 바로 보인다. 클라이언트가 리뷰마다 음식 상세를 따로 다시 조회하지 않아도 리뷰 카드 하나를 완성할 수 있다.

**Why this priority**: 전체 피드에서는 음식 맥락이 없으므로 음식 정보가 없으면 리뷰를 이해할 수 없다. 다만 P1 피드가 먼저 존재해야 의미가 커지므로 P2로 둔다.

**Independent Test**: 기존 음식별 리뷰 조회·내 리뷰 조회 응답만으로도 검증 가능 — 응답의 각 리뷰에 음식 식별자 외에 음식 이름 등 표시용 정보가 포함되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 어떤 음식에 리뷰가 등록되어 있을 때, **When** 리뷰 목록을 조회하면, **Then** 각 리뷰에 음식 식별자뿐 아니라 음식 이름 등 카드 표시에 필요한 음식 정보가 함께 반환된다.
2. **Given** 리뷰 목록을 조회할 때, **When** 응답을 받으면, **Then** 기존 작성자 정보(닉네임·랭킹·국적)는 종전과 동일한 구조로 유지된다.
3. **Given** 전체 피드·음식별 조회·내 리뷰 조회 세 경로가 있을 때, **When** 각각을 조회하면, **Then** 세 경로 모두 동일한 리뷰 응답 구조(음식 정보 + 작성자 정보)를 반환한다.

---

### Edge Cases

- 리뷰가 달린 음식이 삭제(소프트 삭제)된 경우 그 리뷰를 피드에 노출할 것인가? → 음식 정보를 그릴 수 없으므로 전체 피드에서 제외한다.
- 작성자가 탈퇴한 리뷰는 목록(피드·음식별)에서 제외한다. (2026-08-11 개정 — 종전 "작성자 비움 노출 유지"를 대체)
- 사용자가 차단한 회원의 리뷰는 기존 음식별 조회와 동일하게 전체 피드에서도 제외되어야 한다.
- 잘못되었거나 만료된 커서로 요청하면 오류 없이 처리 가능한 기존 커서 규칙(무시 또는 명확한 실패 응답)을 그대로 따른다.
- 페이지를 넘기는 사이 새 리뷰가 등록되어도 커서 기준으로 중복·누락이 생기지 않아야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 음식을 지정하지 않은 전체 리뷰 목록 조회를 제공해야 한다(로그인 사용자 대상).
- **FR-002**: 전체 리뷰 목록은 최신 작성순으로 정렬되어야 한다.
- **FR-003**: 전체 리뷰 목록은 기존 리뷰 목록과 동일한 커서 기반 페이지네이션 방식을 재사용해야 한다(응답에 다음 커서 포함, 커서로 이어서 조회).
- **FR-004**: 리뷰 목록 응답의 각 리뷰에는 음식 식별자 외에 음식 이름 등 리뷰 카드 표시에 필요한 음식 정보가 포함되어야 한다.
- **FR-005**: 음식 정보 보강은 전체 피드뿐 아니라 기존 음식별 리뷰 조회·내 리뷰 조회 응답에도 동일하게 적용되어야 한다.
- **FR-006**: 기존 작성자 정보(닉네임·랭킹·국적, 탈퇴 회원은 비어 있음)와 좋아요 정보는 종전 응답 구조를 그대로 유지해야 한다.
- **FR-007**: 사용자가 차단한 회원의 리뷰는 전체 피드에서도 제외되어야 한다(기존 음식별 조회와 동일 규칙).
- **FR-008**: 삭제된 음식에 달린 리뷰는 전체 피드에 노출되지 않아야 한다.

### Key Entities

- **리뷰**: 회원이 음식에 남긴 별점·본문·사진. 이번 기능에서 새로 만들어지지 않고 조회 범위와 응답 표현만 확장된다.
- **음식**: 리뷰의 대상. 리뷰 응답에 이름 등 표시용 정보가 함께 실리게 된다.
- **작성자(회원)**: 리뷰를 남긴 회원. 응답 내 작성자 표현은 기존 구조를 유지한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 음식을 먼저 선택하지 않고도 한 번의 요청으로 서비스 전체 최신 리뷰를 볼 수 있다.
- **SC-002**: 리뷰 목록 화면에서 리뷰 카드 하나(음식 이름·작성자·별점·본문·사진·좋아요)를 그리는 데 목록 응답 외 추가 조회가 0회다.
- **SC-003**: 전체 피드에서 페이지를 연속으로 넘겨도 리뷰가 중복되거나 누락되지 않는다.
- **SC-004**: 기존 리뷰 목록 클라이언트(음식별·내 리뷰)는 기존 필드가 그대로 유지되어 응답 구조 변경으로 깨지지 않는다.

## Assumptions

- 응답에 보강하는 음식 정보는 리뷰 카드 표시에 필요한 최소한(음식 이름 중심, 필요 시 대표 이미지)으로 하고, 구체 필드 구성은 계획 단계에서 확정한다.
- 전체 피드도 기존 리뷰 조회와 동일하게 로그인 사용자를 전제로 한다(좋아요 여부·차단 필터가 조회 회원 기준이므로).
- 정렬 기준은 최신 작성순 하나만 제공하며 인기순 등 추가 정렬은 이번 범위 밖이다.
- 리뷰 응답의 음식 정보는 기존 필드를 제거하지 않고 필드를 추가하는 방식으로 확장한다(하위 호환 유지).
- 별도 검색·필터(국가·별점 등)는 이번 범위 밖이다.
