# Feature Specification: 메뉴판 스캔 신규 메뉴의 유사 음식 대체 응답

**Feature Branch**: `feat/kb787-scan-similar-substitute`

**Created**: 2026-10-14

**Status**: Draft

**Input**: User description: "KB-787 메뉴판 스캔 신규 등록 메뉴를 벡터 유사 음식으로 대체 응답. Jira KB-787 본문(Background·DoD)을 그대로 요구사항으로 삼는다. 요지: 스캔 2.0 에서 DB miss 로 새로 저장된 메뉴만 메뉴명을 임베딩해 S3 Vectors 검색(limit 1), 스코어 0.6 이상이고 그 foodId 가 READY 면 항목을 그 음식으로 대체해 matched=true 로 응답한다. 응답 항목에 substituted(Boolean)·originalScannedName(대체 전 스캔 메뉴명, 비대체는 null) 을 추가하고, 1.0 응답은 무변경. 임계값은 kbap.vector.similarity-threshold(기본 0.6). 대체 불가(미달·비READY·빈 미설정·검색 실패)·기존 PENDING/FAILED 음식은 현재 준비중 응답 그대로. 스캔 이력은 대체 음식 id 로 기록. KB-343(PR #180)에서 제거된 SimilarFoodResolver 를 git 이력에서 복원해 재사용한다." (입력 일부가 인코딩 깨짐 — Jira 본문을 원문으로 삼음)

## 배경

메뉴판 스캔은 사진에서 추출한 메뉴명을 한국어명으로 음식 목록에서 찾고, 없으면 "미완성 음식"으로 먼저 등록해 두고 응답한다. 매칭 판정은 음식이 **완성(READY)** 상태인지로 하므로, 방금 등록된 신규 음식은 매칭 실패(`matched=false`)·위험도 UNKNOWN·기본 이미지로 내려가 앱에서는 "준비중" 카드로 보인다.

신규 음식을 등록해 두고 나중에 콘텐츠를 채우는 구조는 유지한다. 문제는 **응답 시점**이다. 거의 같은 음식(예: "김치찌개" vs "김치 찌개", "돼지국밥" vs "돼지 국밥")이 이미 완성 상태로 있어도 사용자는 준비중 카드를 보고, 스캔의 핵심 가치인 위험도·회피 성분 판정을 받지 못한다.

유사 음식을 찾는 부품(음식 벡터 색인·검색·질의 임베딩)은 이미 운영 중이다. 과거 KB-319 에서 비매칭 항목 **옆에** 유사 음식을 덧붙이는 방식(임계값 없음)을 넣었다가 KB-343 에서 제거했다. 이번에는 **항목 자체를 유사 음식으로 대체**하되 유사도 임계값 0.6 을 둔다. 대체 사실을 알리는 필드는 **스캔 API 버전 3.0** 에서 채운다(2.0 은 대체는 하되 필드는 null).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 신규 메뉴를 유사한 완성 음식으로 대체해 판정 제공 (Priority: P1)

외국인 사용자가 스캔 2.0 이상(2.0·3.0)으로 메뉴판을 찍었을 때, 음식 목록에 없던 메뉴("김치 찌개")라도 충분히 유사한 완성 음식("김치찌개")이 있으면 준비중 카드 대신 그 음식의 위험도·회피 성분·이미지·번역명을 즉시 받는다.

**Why this priority**: 이 기능의 존재 이유다. 스캔의 핵심 가치(위험도 판정)를 표기 차이 때문에 놓치는 경우를 없앤다.

**Independent Test**: 완성 음식 "김치찌개"가 벡터 색인에 있는 상태에서 메뉴판에 "김치 찌개"만 있는 사진을 스캔 2.0 또는 3.0 으로 올리면, 응답 항목이 `matched=true` 이고 foodId·위험도·이미지·번역명이 "김치찌개"의 것과 같다.

**Acceptance Scenarios**:

1. **Given** "김치 찌개"가 음식 목록에 없고 완성 음식 "김치찌개"가 벡터 색인에 있으며 유사도가 임계값 이상, **When** 스캔 2.0 또는 3.0 으로 "김치 찌개"를 스캔, **Then** 응답 항목은 "김치찌개"의 foodId·`matched=true`·사용자 회피 성분 기준 위험도·대표 이미지·요청 언어 번역명을 담는다(정상 매칭 항목과 동일한 내용).
2. **Given** 위와 동일, **When** 스캔 완료, **Then** "김치 찌개"는 기존과 동일하게 미완성 음식으로 등록돼 있다(대체는 응답에만 영향, 등록 구조는 유지).
3. **Given** 위와 동일, **When** 대체된 항목에 대해 스캔 이력을 조회, **Then** 이력의 음식은 대체된 완성 음식("김치찌개")이다 — 최근 스캔·북마크 흐름이 정상 매칭과 동일하게 동작한다.
4. **Given** 한 사진에 신규 메뉴 여러 개가 있고 그중 일부만 유사 완성 음식이 있음, **When** 스캔 2.0 또는 3.0, **Then** 유사 음식이 있는 항목만 대체되고 나머지는 준비중 응답이다. 항목 순서는 추출 순서 그대로다.

---

### User Story 2 - 대체 사실을 앱이 식별 (Priority: P1)

앱(프론트)은 대체된 항목을 정상 매칭과 구분해 "원래 스캔된 메뉴는 ○○ 였고 유사 음식으로 보여준다"는 안내를 할 수 있어야 한다.

**Why this priority**: 대체 항목을 정상 매칭과 똑같이 보여주면 사용자가 다른 음식의 판정을 자기 메뉴 판정으로 오인한다. 대체 기능과 분리할 수 없는 신뢰 장치다.

**Independent Test**: 스캔 3.0 응답의 각 항목에 `substituted` 와 `originalScannedName` 이 있고, 대체 항목만 `substituted=true` + 원래 스캔 메뉴명을 갖는지 확인한다. 같은 요청을 2.0 으로 보내면 두 필드가 null 인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 대체가 일어난 항목, **When** 스캔 3.0 응답 수신, **Then** 그 항목은 `substituted=true`, `originalScannedName`="김치 찌개"(대체 전 비전이 정제한 한국어 메뉴명), `koreanName`·`name` 은 대체된 음식 기준이다.
2. **Given** 정상 매칭 항목(DB 에 완성 음식으로 바로 조회됨), **When** 스캔 3.0 응답 수신, **Then** `substituted=false`, `originalScannedName=null`.
3. **Given** 준비중 항목(대체 불가), **When** 스캔 3.0 응답 수신, **Then** `substituted=false`, `originalScannedName=null` 이고 나머지 필드는 현재 준비중 응답과 동일하다.
4. **Given** 스캔 2.0 클라이언트, **When** 대체가 일어난 항목을 포함한 스캔 2.0 응답 수신, **Then** 항목은 대체 음식 기준으로 채워지되(`matched=true` 등 3.0 과 동일) `substituted=null`, `originalScannedName=null` 이다. 비대체 항목도 두 필드는 null 이다.
5. **Given** 스캔 1.0 클라이언트, **When** 스캔 1.0 응답 수신, **Then** 응답 스키마·내용 모두 현재와 동일하다(새 필드 없음, 대체 없음).

### User Story 3 - 대체 불가 시 현재 동작 유지·전체 실패 전파 금지 (Priority: P2)

유사 음식이 없거나, 있어도 완성 상태가 아니거나, 벡터 검색이 꺼져 있거나 실패해도 스캔은 지금과 똑같이 성공하고 해당 항목은 준비중으로 내려간다.

**Why this priority**: 보조 기능이 핵심 기능(스캔)을 깨뜨리면 안 된다. 로컬·일부 환경은 벡터 검색이 꺼져 있다.

**Independent Test**: 벡터 검색을 끈 환경과 검색이 오류를 내는 환경 각각에서 신규 메뉴 스캔이 현재와 동일한 준비중 응답으로 성공하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 가장 유사한 음식의 스코어가 임계값 미만, **When** 스캔 2.0 또는 3.0, **Then** 항목은 현재의 준비중 응답과 동일하다(`matched=false`·UNKNOWN·기본 이미지·`substituted` 는 3.0 이면 false, 2.0 이면 null).
2. **Given** 가장 유사한 음식이 완성(READY) 상태가 아님(PENDING/FAILED 등), **When** 스캔 2.0 또는 3.0, **Then** 대체하지 않고 준비중 응답이다. 차순위 후보를 찾지 않는다(검색 결과는 1건만 본다).
3. **Given** 임베딩 또는 벡터 검색이 비활성화된 환경, **When** 스캔 2.0 또는 3.0, **Then** 대체 단계를 조용히 건너뛰고 스캔은 정상 응답한다.
4. **Given** 임베딩 호출 또는 벡터 검색이 오류·타임아웃, **When** 스캔 2.0 또는 3.0, **Then** 스캔 전체는 실패하지 않고 해당 항목만 준비중 응답이다(부분 성공). 실패는 운영 로그로 남긴다.
5. **Given** 메뉴가 음식 목록에 이미 있으나 완성 상태가 아님(PENDING/FAILED), **When** 스캔 2.0 또는 3.0, **Then** 대체 대상이 아니다 — 현재의 준비중 응답 그대로(벡터 검색을 시도하지 않는다).

### Edge Cases

- 같은 사진에 같은 신규 메뉴명이 두 번 나오면: 음식 등록은 한 번(현재 동작)이고, 두 항목 모두 같은 음식으로 대체된다.
- 유사 음식이 대체 판정 직후 완성 상태에서 벗어난(관리자 수정 등) 극히 드문 경합은 감수한다 — 응답 시점 조회 결과를 따른다.
- 벡터 색인에는 있으나 음식 목록에서 삭제(소프트)된 음식이 최상위로 나오면: 재조회 실패이므로 대체하지 않는다(차순위 탐색 없음).
- 벡터 검색이 자기 자신(방금 등록된 미완성 음식)을 돌려주는 경우: 미완성이므로 완성 조건에 걸려 대체하지 않는다.
- 임베딩 대상 문자열은 대체 전 비전이 정제한 표준 한국어 메뉴명(원본 표기)이다.
- 신규 메뉴가 없는 스캔(전부 정상 매칭 또는 전부 기존 미완성)은 벡터 검색을 한 번도 호출하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 스캔 2.0 이상(2.0·3.0, 이하 "스캔 2.0+")은 한국어명으로 음식 목록에 없는 메뉴를 기존과 동일하게 미완성 음식으로 먼저 등록한다(변경 없음).
- **FR-002**: 스캔 2.0+ 은 **이번 스캔에서 새로 등록된 메뉴만** 대상으로, 메뉴명(대체 전 표준 한국어명)으로 유사 음식을 **1건** 조회한다. 이미 등록돼 있던 미완성(PENDING/FAILED) 음식과 정상 매칭 음식은 대상이 아니다.
- **FR-003**: 조회된 유사 음식의 유사도 스코어가 임계값 **이상**이고, 그 음식을 재조회했을 때 **완성(READY)** 상태면 해당 항목을 그 음식으로 대체한다.
- **FR-004**: 대체된 항목은 정상 매칭 항목과 동일하게 채운다 — `matched=true`, 대체 음식의 foodId, 사용자 회피 성분 기준 위험도·회피 성분 겹침 정보, 대표 이미지, 요청 언어 번역명(`name`), 한국어명(`koreanName`).
- **FR-005**: 스캔 2.0+ 응답 항목에 `substituted`(Boolean, nullable)와 `originalScannedName`(문자열, nullable)을 추가한다. **3.0 요청**에서 대체 항목은 `substituted=true` + `originalScannedName`=대체 전 비전이 정제한 한국어 메뉴명, 비대체 항목(정상 매칭·준비중 모두)은 `substituted=false` + `originalScannedName=null`.
- **FR-005a**: **2.0 요청**에서는 대체는 동일하게 수행하되 두 필드는 모든 항목에서 항상 null 이다. 2.0 과 3.0 의 응답 스키마는 같고 두 필드의 값만 다르다.
- **FR-005b**: 스캔 API 에 버전 3.0 을 지원 버전으로 추가한다. 3.0 의 요청 계약(헤더·파라미터·본문)은 2.0 과 동일하다.
- **FR-006**: 스캔 1.0 의 응답 스키마와 동작은 변경하지 않는다(새 필드 없음, 대체 없음).
- **FR-007**: 대체 불가 — 스코어 미달, 완성 상태 아님, 재조회 실패, 임베딩/벡터 검색 비활성, 외부 호출 실패·타임아웃 — 인 경우 항목은 현재의 준비중 응답과 완전히 동일하다(두 필드 추가 외 차이 없음 — 3.0 은 `substituted=false`, 2.0 은 null).
- **FR-008**: 임베딩·벡터 검색 호출 실패는 스캔 전체 실패로 번지지 않는다(해당 항목만 준비중). 실패는 운영 로그에 남긴다.
- **FR-009**: 유사도 임계값은 코드 상수 **0.6** 으로 고정한다(설정·환경변수 노출 없음).
- **FR-010**: 대체된 항목의 스캔 이력(`scan_history.food_id`)은 **대체된 완성 음식의 id** 로 기록한다. 비대체 항목은 현재대로(신규 등록된 미완성 음식 id).
- **FR-011**: 벡터 검색 결과는 id 와 스코어만 사용하고, 표시 내용은 항상 음식 목록 재조회로 얻는다(기존 원칙 유지).
- **FR-012**: 스캔 2.0+ API 문서(Swagger)에 새 필드의 의미와 2.0 에서는 null 인 점을 기술한다.

### Key Entities

- **스캔 항목 응답(2.0+)**: 사진에서 추출된 메뉴 1건의 판정. 기존 필드(matched·foodId·riskLevel·name·koreanName·price·imageRef·회피 성분 겹침 등)에 `substituted`·`originalScannedName` 이 추가된다(3.0 에서 값, 2.0 에서 null).
- **음식(Food)**: 매칭·대체의 대상. 콘텐츠 상태(READY/PENDING_IMAGE/PENDING_REVIEW/FAILED)를 가지며 완성(READY)만 매칭/대체 가능.
- **유사 음식 조회 결과**: 벡터 검색이 돌려주는 (foodId, 스코어) 1건.
- **스캔 이력(ScanHistory)**: 회원·음식 id 기록. 대체 항목은 대체 음식 id.
- **유사도 임계값**: 코드 상수 0.6 (`SimilarFoodService` 소유).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 완성 음식과 표기만 다른 신규 메뉴(띄어쓰기·조사 차이 수준)를 스캔 2.0 또는 3.0 으로 올리면 100% 준비중 카드가 아닌 위험도 판정이 내려간다(벡터 검색 활성 환경).
- **SC-002**: 3.0 응답에서 대체 항목은 예외 없이 `substituted=true` + 원래 스캔 메뉴명을 담고, 비대체 항목은 예외 없이 `substituted=false` + null 이다. 2.0 응답은 모든 항목에서 두 필드가 null 이다.
- **SC-003**: 벡터 검색을 끄거나 검색이 실패해도 스캔 2.0+ 성공률은 변경 전과 동일하다(대체 단계로 인한 스캔 실패 0건).
- **SC-004**: 스캔 1.0 응답은 변경 전후 바이트 단위로 동일하다.
- **SC-005**: 대체된 항목을 포함한 스캔 직후 최근 스캔 목록에 대체된 완성 음식이 나타난다.
- **SC-006**: 임계값은 코드 한 곳(`SimilarFoodService` 상수)에만 존재한다 — 설정 파일·환경변수에 중복 정의가 없다.

## Assumptions

- **대체는 스캔 2.0 이상(2.0·3.0)에 적용하고, 대체 사실 필드의 값은 3.0 에서만 채운다.** 2.0 과 3.0 은 같은 응답 스키마를 쓰며 요청 버전에 따라 두 필드의 값만 달라진다(2.0 은 null). 스캔 1.0 은 응답에 대체 사실을 알릴 필드가 없어 대체하면 사용자가 오인하므로 동작·스키마 모두 현재 그대로 둔다(FR-006).
- 유사 음식 검색은 **최상위 1건만** 본다. 1건이 완성 상태가 아니면 차순위를 찾지 않고 준비중으로 둔다(Jira 본문 "limit 1").
- 임베딩 입력은 대체 전 비전이 정제한 표준 한국어 메뉴명이며, `originalScannedName` 도 같은 값이다.
- 유사도 비교는 "임계값 이상(≥)"으로 한다.
- 기존 KB-343 에서 제거된 유사 음식 조회 부품은 git 이력(PR #180 직전)에서 복원해 재사용한다 — 설계 상세는 플랜 단계.
- 상세 조회에서 "원래 스캔된 메뉴는 ○○ 였고…" 식 LLM 보충 설명은 **범위 밖**이다(후속 과제).
- 벡터 색인에 신규 등록 음식이 즉시 반영되지 않는 것(배치 적재)은 정상이며, 이 기능은 색인에 있는 완성 음식만 대체 후보로 본다.
- 대체 여부·원래 메뉴명은 응답에만 담고 별도 저장하지 않는다(스캔 이력에는 대체 음식 id 만).
- 테스트는 사용자 요청 또는 스펙 명시가 있을 때만 작성한다(헌법 원칙 I).
