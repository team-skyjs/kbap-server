# Feature Specification: 환율을 고정 스냅샷에서 실시간 조회로 전환

**Feature Branch**: `kb-349-realtime-exchange-rate`

**Created**: 2026-08-19

**Status**: Draft

**Input**: User description: "349 워크트리. 실시간 환율 api 조회로 태스크에 적힌 api가 지원하는 통화에 대해서만 응답으로 전달. 그 외 국가라면 usd를 기본으로. 따라서 하드코딩된 환율 정보를 제거하고 api 호출로 변경하는것. 그런데 이 환율 api를 매번 호출할 필요는 없으니 캐시를 고려한다. 너무 사소하다고 판단되면 우선 캐시도 생각하지 않고 그냥 구현부터 해보고 나중에 고민한다."

## 맥락 (Jira KB-349·agent-hub·사용자 확정)

- 현재 환율은 **코드에 박힌 고정 스냅샷**이다 — 통화 46종(국내 은행 고시 45종 + 원화)에 "1단위당 원화" 값을 하드코딩. 갱신 경로가 없어 시간이 지날수록 실제 시세와 벌어진다.
- 소비자는 **2.0 스캔 응답**(`currency { code, krwPerUnit }`) 하나 — 서버는 환산하지 않고 코드+환율만 내리고, 환산·반올림은 클라이언트가 한다. 응답 계약은 이번에 바뀌지 않는다.
- 회원 통화는 온보딩에서 국가로부터 자동 지정되고 이후 독립이며, 취급 통화 밖 국가는 이미 USD 로 대체한다.
- 8/15 기획·8/18 스프린트 확정: **실시간 환율 제공처(무료·공개, 약 30종 지원)를 호출하고, 지원 통화만 취급하며 그 밖은 USD.** 이 제공처는 KB-322 때 커버리지 부족(베트남·대만·사우디·아랍에미리트 미지원)으로 한 번 기각했던 것이고, 이번엔 **시세 신선도를 얻는 대가로 커버리지 축소(USD 대체)를 받아들이는** 결정이다.
- 사용자 확정(2026-08-19): **캐시 없이 스캔 요청마다 제공처를 호출한다.** 캐시(인스턴스 로컬 / Redis 공유)는 검토 후 전부 범위 밖 — 구현을 먼저 두고 필요해지면 후속.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 스캔 응답에 최신 환율이 실린다 (Priority: P1)

지원 통화를 쓰는 회원이 2.0 스캔을 하면, 응답의 환율 값이 코드에 박힌 옛 값이 아니라 **외부 제공처의 최신 고시값**이다.

**Why this priority**: 이 기능의 존재 이유 — 스냅샷이 낡아 환산 금액이 틀리는 문제를 없앤다.

**Independent Test**: 지원 통화(예: JPY) 회원으로 2.0 스캔 → 응답 `currency.krwPerUnit` 이 제공처의 당일 고시값과 일치(하드코딩 상수와 무관).

**Acceptance Scenarios**:

1. **Given** 통화 JPY 회원, **When** 2.0 스캔을 호출하면, **Then** `currency = { code: "JPY", krwPerUnit: <제공처 당일 고시값> }` 이 내려간다.
2. **Given** 통화 KRW 회원, **When** 2.0 스캔을 호출하면, **Then** `{ code: "KRW", krwPerUnit: 1 }` 이 내려간다(기준 통화는 항상 1).
3. **Given** 통화 미설정 회원, **When** 2.0 스캔을 호출하면, **Then** `currency = null` 로 스캔이 정상 성공한다(기존과 동일).

---

### User Story 2 - 미지원 통화 국가는 USD 로 (Priority: P1)

제공처가 지원하지 않는 통화(베트남 동·대만 달러·사우디 리얄 등)를 쓰던 국가의 회원은 통화가 **USD** 로 취급되고, 스캔 응답도 USD 환율로 내려간다.

**Why this priority**: 지원 목록 축소가 기존 회원·온보딩에 직접 영향을 준다 — 이 규칙 없이는 폐기 통화를 가진 회원의 스캔이 깨진다.

**Independent Test**: 베트남 국적으로 온보딩 → 통화 USD 자동 지정. 기존에 VND 를 갖고 있던 회원 → 프로필 조회·스캔에서 USD 로 보인다.

**Acceptance Scenarios**:

1. **Given** 통화가 제공처 미지원인 국가(예: VN)로 온보딩, **When** 완료하면, **Then** 회원 통화는 USD 다.
2. **Given** 전환 전 미지원 통화(예: VND)를 가진 기존 회원, **When** 프로필을 조회하거나 스캔하면, **Then** 통화가 USD 로 보이고 오류가 나지 않는다.
3. **Given** 프로필 수정에서 미지원 통화 코드를 보내면, **When** 저장을 시도하면, **Then** 지원하지 않는 통화로 거절된다(기존 `INVALID_CURRENCY_CODE` 규칙 유지).

---

### User Story 3 - 제공처가 느리거나 죽어도 스캔은 된다 (Priority: P2)

외부 환율 제공처가 응답하지 않거나 오류를 내도, 사용자의 **스캔은 실패하지 않는다.**

**Why this priority**: 환율은 부가 정보다. 부가 정보 때문에 핵심 기능(스캔)이 막히면 안 된다.

**Independent Test**: 제공처를 차단한 상태에서 2.0 스캔 → 스캔 결과는 정상, `currency = null`.

**Acceptance Scenarios**:

1. **Given** 제공처 장애, **When** 2.0 스캔을 호출하면, **Then** 스캔 결과(항목·위험도)는 정상이고 `currency = null` 이다.
2. **Given** 제공처 응답 지연, **When** 2.0 스캔을 호출하면, **Then** 짧은 대기 한도 안에서 포기하고 `currency = null` 로 스캔을 돌려준다(환율 때문에 스캔이 수 초 이상 늘어지지 않는다).

---

### Edge Cases

- 제공처가 지원 통화 목록을 바꾸면(추가/삭제)? — 우리 취급 목록은 코드로 고정한다. 제공처 응답에서 우리 통화가 빠지면 `currency = null`(FR-006).
- 제공처 고시가 하루 한 번(주말·공휴일 미갱신)이면? — 정상. "최신 = 제공처의 가장 최근 고시"이지 실시간 틱이 아니다. 사용자에게 "실시간"이라 표기하지 않는다.
- 제공처가 KRW 기준으로 유효숫자가 적게 오면(예: 0.00071)? — 정밀도 손실 없이 "1단위당 원화 4자리"로 변환돼야 한다(KB-322 R9 에서 발견된 함정).
- 폐기 통화를 백필로 USD 전환한 뒤 그 회원이 프로필에서 다시 통화를 고르면? — 지원 목록 안에서만 선택 가능.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 스캔 응답의 환율 값을 **외부 환율 제공처에서 조회한 값**으로 내려야 하며, 코드에 하드코딩된 환율 상수를 더 이상 갖지 않아야 한다.
- **FR-002**: 취급 통화는 **제공처가 지원하는 통화 전부 + 원화**로 한정한다. 이 목록은 시스템이 소유하는 고정 목록이며(제공처 응답으로 동적으로 늘리지 않는다), 목록 밖 통화 코드는 프로필 수정에서 거절한다.
- **FR-003**: 국가→통화 자동 지정에서 취급 목록 밖 통화를 쓰는 국가는 **USD** 로 지정한다.
- **FR-004**: 전환 시점에 취급 목록에서 빠지는 통화를 가진 **기존 회원의 통화는 USD 로 일괄 전환**한다. 전환 후 조회·스캔·프로필 수정이 오류 없이 동작해야 한다.
- **FR-005**: 환율은 "**해당 통화 1단위당 원화 금액**, 소수 4자리" 의미를 유지한다. 제공처의 기준 통화·정밀도와 무관하게 이 의미로 변환해 내린다. KRW 는 항상 1.
- **FR-006**: 제공처 조회 실패(오류·타임아웃·해당 통화 누락) 시 스캔은 실패하지 않아야 하며, `currency = null` 로 내린다(스캔 본문은 정상).
- **FR-007**: 제공처 호출은 **스캔 요청마다 1회** 발생한다(캐시 없음 — 사용자 확정). 호출에는 짧은 대기 한도를 두어 스캔 응답을 수 초 이상 지연시키지 않는다.
- **FR-008**: 2.0 스캔 응답 계약(`currency { code, krwPerUnit } | null`)과 1.0 응답은 변경하지 않는다.

### Key Entities

- **취급 통화 목록**: 시스템이 환율을 제공하는 통화 코드의 고정 집합(제공처 지원 통화 + KRW). 프로필 통화 선택·국가→통화 매핑·스캔 응답의 유효 범위를 정한다.
- **환율(1단위당 원화)**: 요청 시점에 제공처에서 받은 값. 코드 상수가 아니고 저장하지도 않는다.
- **국가→통화 매핑**: 온보딩 자동 지정 규칙. 취급 목록 밖 통화의 국가는 USD.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 지원 통화 회원의 2.0 스캔 응답 100% 에서 환율이 제공처의 가장 최근 고시값과 일치한다(하드코딩 값과 무관).
- **SC-002**: 취급 목록 밖 통화를 가진 회원이 전환 후 0명이며(전부 USD), 이들의 스캔·프로필 조회 오류율 0.
- **SC-003**: 제공처를 완전히 차단해도 2.0 스캔 성공률이 차단 전과 같다.
- **SC-004**: 제공처가 정상일 때 2.0 스캔 응답 시간 증가가 제공처 왕복 1회(수백 ms 이내)를 넘지 않고, 제공처가 무응답일 때도 대기 한도(수 초) 안에서 스캔이 돌아온다.

## Assumptions

- **제공처는 KB-322 때 검토했던 무료·공개 환율 제공처(ECB 기준환율, 약 30종)** 다. Jira/기획의 "30개국 통화"가 이것을 가리킨다. 지원 목록은 계획 단계에서 최신 문서로 확정하며, 대략 현재 46종 중 **약 28종 유지 · 약 18종(AED·BDT·BHD·BND·EGP·FJD·JOD·KHR·KWD·KZT·MNT·NPR·PKR·QAR·RUB·SAR·TWD·VND) 이 USD 로 대체**되고, 제공처가 지원하지만 지금 없는 소수(BGN·ISK·RON 등)는 **추가**한다("제공처 지원 통화 전부"가 규칙이라 선별하지 않는다).
- **커버리지 축소는 의도된 트레이드오프다** — 방한 관광객 상위권인 베트남·대만 사용자가 자국 통화 대신 USD 를 보게 된다. 8/15 기획·8/18 스프린트에서 확정된 방향이며 이 스펙은 그것을 뒤집지 않는다.
- **캐시를 두지 않는다**(사용자 확정 2026-08-19). 검토 경위: 인스턴스 로컬(JVM) 캐시는 다중 인스턴스 운영이라 호출 N배·인스턴스 간 환율 불일치로 부적합, Redis 공유 캐시는 가능하나 지금 단계에선 과하다고 판단 → 구현만 먼저. 스캔은 LLM 호출로 수 초 걸리는 경로라 제공처 왕복 1회(수백 ms)는 감수한다. 제공처 호출량이 문제 되면 그때 Redis 공유 스냅샷(하루 1회 갱신)을 후속으로 붙인다.
- 환율 갱신 시각·"기준 시각" 노출은 범위 밖. 응답에 `asOf` 같은 필드를 추가하지 않는다(계약 불변).
- 기존 회원 통화 백필은 **1회성 데이터 마이그레이션**으로 처리한다(스키마 변경 없음 — 값만 USD 로).
- 제공처 장애 동안은 모든 2.0 스캔이 `currency = null` 로 나간다(이전 성공값 보관 없음). 클라이언트는 이미 nullable 계약이라 환산 UI 만 숨기면 된다.

## Out of Scope

- 서버 환산·항목별 환산 금액 (클라이언트 소관 유지)
- 환율 기준 시각 응답 노출, 환율 이력 저장, 관리자 수동 갱신
- 캐시 일체(인스턴스 로컬·Redis 공유·선갱신 스케줄러) — 호출량이 문제 될 때 후속
- 취급 목록 밖 통화의 별도 제공처 보강(예: VND 를 다른 API 로 채우기)
