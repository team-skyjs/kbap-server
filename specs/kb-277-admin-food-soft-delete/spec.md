## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 잘못 시드된 음식을 삭제한다 (Priority: P1)

관리자는 음식 상세 화면에서 잘못 등록된 음식(이름 오탈자, 음식이 아닌 텍스트 등)을 발견하면, 삭제 버튼을 눌러 확인 단계를 거친 뒤 그 음식을 삭제한다. 삭제 후에는 보고 있던 목록 페이지로 돌아가 나머지 정리 작업을 이어간다. 지금은 삭제 수단이 없어 DB에 직접 접근해야만 정리할 수 있다.

**Why this priority**: 이 기능의 존재 이유 자체. 관리자가 운영 도구 안에서 데이터 정리를 끝낼 수 있게 하는 핵심 여정이다.

**Independent Test**: 관리자 음식 상세 패널에서 삭제 버튼 → 확인 → 삭제 실행 후, 해당 음식이 목록에서 사라지고 현재 페이지가 유지되는지 확인하면 단독으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 관리자 음식 상세 패널이 열려 있을 때, **When** 삭제 버튼을 누르면, **Then** 실수 방지를 위한 확인 단계가 표시되고 즉시 삭제되지 않는다.
2. **Given** 확인 단계가 표시된 상태에서, **When** 관리자가 삭제를 확정하면, **Then** 음식이 삭제(소프트)되고 보고 있던 목록 페이지(현재 페이지 번호 유지)로 돌아간다.
3. **Given** 확인 단계가 표시된 상태에서, **When** 관리자가 취소하면, **Then** 아무 변경 없이 상세 화면이 유지된다.
4. **Given** 존재하지 않거나 이미 삭제된 음식에 대해, **When** 삭제를 요청하면, **Then** 삭제는 실행되지 않고 음식을 찾을 수 없다는 실패 응답을 받는다.

---

### User Story 2 - 삭제된 음식은 어디에도 노출되지 않는다 (Priority: P2)

관리자가 음식을 삭제하면, 그 음식은 관리자 목록뿐 아니라 앱 사용자가 보는 모든 조회 경로(검색, 상세 조회, 북마크 목록, 리뷰 목록)에서도 더 이상 보이지 않아야 한다.

**Why this priority**: 삭제의 실질 효과. 잘못된 데이터가 사용자에게 계속 노출되면 삭제 기능의 목적이 무의미해진다. 다만 P1이 없으면 검증할 대상 자체가 없으므로 P1 다음이다.

**Independent Test**: 음식을 삭제한 뒤 관리자 목록·검색·상세·북마크·리뷰 목록 각각을 조회해 해당 음식이 나타나지 않음을 확인하면 단독으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 삭제된 음식이 있을 때, **When** 관리자 음식 목록을 조회하면, **Then** 해당 음식은 목록에 나타나지 않는다.
2. **Given** 삭제된 음식이 있을 때, **When** 앱 사용자가 검색하거나 상세를 조회하면, **Then** 해당 음식은 결과에 없고 상세 조회는 찾을 수 없음으로 처리된다.
3. **Given** 삭제된 음식을 북마크했거나 리뷰를 남긴 사용자가 있을 때, **When** 북마크 목록·리뷰 목록을 조회하면, **Then** 해당 음식 항목은 노출되지 않고 목록 조회 자체는 오류 없이 동작한다.

---

### User Story 3 - 동명 재시드 제약을 삭제 화면에서 안내한다 (Priority: P3)

관리자가 음식을 삭제할 때, 삭제된 음식의 이름이 계속 점유되어 같은 이름을 다시 등록(시드)하면 조용히 누락된다는 기존 동작을 삭제 확인 화면에서 안내 문구로 알려준다.

**Why this priority**: 데이터 정리 후 재등록을 시도하는 관리자가 "왜 등록이 안 되지"를 겪지 않게 하는 예방 장치. 핵심 흐름을 막지는 않으므로 P3.

**Independent Test**: 삭제 확인 단계 화면에 동명 재시드 누락 안내 문구가 표시되는지 확인하면 단독으로 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** 삭제 확인 단계가 표시될 때, **When** 관리자가 안내 영역을 보면, **Then** 삭제된 음식의 이름이 계속 점유되어 동명 음식 재시드가 누락된다는 문구가 표시된다.

---

### Edge Cases

- 존재하지 않는 음식 id로 삭제를 요청하면 찾을 수 없음 실패로 응답한다(무해한 no-op가 아니라 명시적 실패).
- 이미 삭제된 음식을 다시 삭제하려 하면 동일하게 찾을 수 없음으로 처리된다(삭제된 데이터는 조회에서 제외되므로).
- 목록 마지막 페이지의 유일한 항목을 삭제한 경우에도 삭제 후 이동한 목록 페이지가 오류 없이 표시된다(빈 페이지 허용).
- 삭제된 음식을 참조하는 기존 데이터(북마크, 리뷰, 스캔 이력)는 그대로 보존되며, 이를 포함한 목록 조회가 오류를 일으키지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 관리자 음식 상세 패널은 삭제 버튼을 제공해야 한다.
- **FR-002**: 삭제 실행 전 실수 방지를 위한 확인 단계를 반드시 거쳐야 하며, 확인 없이 삭제가 실행되어서는 안 된다.
- **FR-003**: 삭제는 데이터를 물리적으로 제거하지 않는 소프트 삭제여야 하며, 삭제된 음식을 참조하는 기존 데이터(북마크·리뷰·스캔 이력)는 보존된다.
- **FR-004**: 삭제 성공 후 관리자는 삭제 직전에 보던 목록 페이지(동일 페이지 번호)로 돌아가야 한다.
- **FR-005**: 삭제된 음식은 관리자 음식 목록·앱 사용자 검색·상세 조회·북마크 목록·리뷰 목록 어디에도 노출되지 않아야 한다.
- **FR-006**: 존재하지 않거나 이미 삭제된 음식에 대한 삭제 요청은 음식을 찾을 수 없다는 실패로 처리해야 한다.
- **FR-007**: 삭제 확인 화면은 소프트 삭제된 음식의 이름이 계속 점유되어 같은 이름의 음식을 다시 시드하면 등록이 누락된다는 사실을 안내 문구로 명시해야 한다.
- **FR-008**: 삭제 성공 경로와 미존재 음식 삭제 시도 경로는 자동화된 테스트로 검증되어야 한다.

### Key Entities

- **음식(Food)**: 관리자가 관리하는 음식 항목. 활성/삭제 상태를 가지며, 삭제 시 상태만 전환되고 데이터는 보존된다. 이름은 유일해야 하며 삭제 후에도 이름 점유가 유지된다.
- **음식 참조 데이터(북마크·리뷰·스캔 이력)**: 음식을 참조하는 사용자 활동 기록. 음식 삭제 후에도 보존되지만, 삭제된 음식 항목은 목록 화면에 노출되지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자가 잘못 시드된 음식 1건을 발견부터 삭제 완료까지 관리 화면 안에서 30초 이내에 처리할 수 있다(DB 직접 접근 불필요).
- **SC-002**: 삭제 후 어떤 조회 경로(관리자 목록·검색·상세·북마크·리뷰 목록)에서도 삭제된 음식이 노출되는 사례가 0건이다.
- **SC-003**: 확인 단계 없이 삭제가 실행되는 경로가 존재하지 않는다(모든 삭제는 확인을 거친다).
- **SC-004**: 미존재·기삭제 음식 삭제 시도는 100% 명시적 실패로 응답하며 시스템 오류를 일으키지 않는다.

## Assumptions

- 삭제 권한은 기존 관리자 화면 접근 권한과 동일하다 — 별도의 세분화된 권한(역할별 삭제 권한)은 이번 범위 밖이다.
- 삭제 취소(복구) 기능은 이번 범위 밖이다. 소프트 삭제라 데이터는 보존되지만 복구 UI는 제공하지 않는다.
- 동명 재시드 누락 동작 자체(등록 시 경고 로그 후 조용히 건너뜀)는 기존 동작을 그대로 유지하며, 이번 작업은 안내 문구 추가에 한정한다.
- 삭제된 음식을 참조하는 화면(북마크·리뷰 목록)의 노출 제외는 기존 조회 규칙(활성 데이터만 조회)에 의해 자동으로 달성된다고 가정하되, 실제 노출 여부는 확인 대상이다.
- 대상 사용자는 내부 운영 관리자 소수이며 대량 일괄 삭제·동시 삭제 경합은 고려 범위 밖이다.
