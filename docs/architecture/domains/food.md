# food Context

## 1. 역할

`food` 컨텍스트는 **검수된 음식 카탈로그**를 관리한다. 음식명, 설명, 대표 이미지, 재료, 알러지 유발 성분, 종교/비건 관련 주의 성분, 9개국어 번역, 데이터 상태가 이 컨텍스트의 책임이다.

`food`는 **LLM 조사·종합을 직접 하지 않는다.** 캐시 미스 메뉴를 LLM으로 조사하고 응답을 종합하는 일은 `research` 컨텍스트(배치)의 책임이며([ADR-0004](../../adr/0004-research-bounded-context.md)), `food`는 그 종합 결과(`SynthesizedFoodProfile`)를 받아 `Food`/`FoodIngredient`로 영속하고 자신을 만든 research를 **ID로만** 참조한다. (지식 획득 = `research`, 검수된 지식 = `food`.)

`food`는 사용자가 이 음식을 먹어도 되는지 최종 판단하지 않는다. 최종 위험도 판정은 `assessment` 컨텍스트의 책임이다.

MVP에서는 음식 카탈로그와 재료 지식베이스를 같은 `food` 컨텍스트 안에 둔다. 다만 재료, 알러지 매핑, 종교/비건 매핑이 커지면 `ingredient` 또는 `food-knowledge` 컨텍스트로 분리할 수 있다.

## 2. 포함 기능

- 음식 기본 정보 관리
- 다국어 음식명 관리 (한국어 원문 + 9개 언어 번역)
- 음식 별칭 관리
- 음식 설명 관리
- 대표 이미지 정보 관리
- 음식별 주요 재료 관리
- 재료별 포함 비율(`inclusionPercent`) 관리
- 재료 정보 관리
- 알러지 유발 성분 매핑 관리
- 종교/비건 주의 성분 매핑 관리
- `research`가 종합한 결과를 받아 음식 데이터로 영속(생성/보강)
- 음식 데이터 상태(검수)와 갱신 이력 관리, 만든 research를 ID로 참조
- 메뉴명 기반 음식 캐시 조회

## 3. 제외 기능

- 사용자별 위험도 최종 판정
- 사용자 알러지 프로필 관리
- 메뉴판 스캔 요청 상태 관리
- **LLM 조사·3개 응답 종합·조사 대기열 소유**(= `research` 컨텍스트)
- 음식별 리뷰/평점 관리
- 식당별 메뉴 관리
- 지도/식당 위치 관리

## 4. 핵심 개념

### Food

음식의 기준 정보다. 김치찌개, 불고기, 비빔밥 같은 음식 단위를 의미한다.

필드 판단 기준:

- 음식 식별에 필요한 값
- 표시명 (한국어 원문 + 9개 언어 번역)
- 음식 설명 (한국어 원문 + 9개 언어 번역)
- 음식 카테고리 또는 분류
- 대표 이미지 참조
- 데이터 상태
- 생성/갱신 시각
- 데이터 출처

도메인 로직 판단 기준:

- 음식명이 비어 있으면 안 된다.
- 음식 콘텐츠는 **한국어 원문을 기준으로 관리하고, 9개 대상 언어 번역을 함께 보관한다**(ADR-0003). 9개 언어: `zh-Hans`/`en`/`ja`/`zh-Hant`/`vi`/`id`/`th`/`ru`/`es`.
- 각 언어 설명은 외국인이 음식을 이해할 수 있는 수준이어야 하며, 과도하게 길지 않아야 한다.
- 번역은 `research`(배치)가 LLM으로 생성하며, 원문/번역 모두 LLM 생성물과 내부 검수 데이터를 구분할 수 있어야 한다.

### FoodName / FoodAlias

음식의 이름과 별칭을 표현한다. 메뉴판에는 같은 음식이 다양한 이름으로 등장할 수 있다.

필드 판단 기준:

- 원문 이름
- 정규화된 이름
- 언어
- 별칭 여부
- 우선 표시 여부

도메인 로직 판단 기준:

- 메뉴명 매칭은 원문 메뉴명과 정규화 이름을 모두 고려한다.
- 별칭은 음식 식별을 돕기 위한 값이지, 별도 음식으로 취급하지 않는다.
- `언어` 필드로 다국어 표시명을 표현한다 — 한국어(`ko`) 원문 + 9개 대상 언어 번역이 음식별로 존재한다(ADR-0003). 매칭은 한국어 원문·정규화 기준이고, 번역명은 표시용이다.

### Ingredient

재료를 표현한다. 간장, 새우젓, 돼지고기, 고춧가루 같은 단위다.

필드 판단 기준:

- 재료 식별자
- 다국어 재료명 (한국어 원문 + 9개 언어 번역)
- 재료 별칭
- 재료 분류
- 알러지 유발 성분 매핑
- 종교/비건 주의 성분 매핑

도메인 로직 판단 기준:

- 재료는 여러 음식에서 공유된다.
- 음식이 재료 객체 전체를 직접 소유하지 않도록 한다.
- 음식과 재료의 관계는 별도 관계 모델로 둔다.

### FoodIngredient

음식과 재료의 관계다. “김치찌개에 새우젓이 들어갈 수 있다” 같은 정보를 표현한다.

필드 판단 기준:

- 음식 ID
- 재료 ID
- 포함 비율(`inclusionPercent`) — **표시·저장값**
- 표시 순서(`displayOrder`)
- 포함 근거
- 데이터 출처
- 신뢰도 또는 검수 상태

포함 비율(`inclusionPercent`) — 표시·저장값:

- `0~100`의 **연속 비율**로, 여러 레시피 기준 해당 재료의 포함 확률을 나타낸다(UI 의 `~50%` 표기 원천).
- 이 슬라이스(001)에서 도메인·영속·응답이 다루는 값은 이 **`inclusionPercent` 하나**다.

후속 LLM per-recipe 스코어(`0/1/2`) — 별개 개념(이번 범위 밖):

- `0`: 일반적으로 포함되지 않음 / `1`: 매장·레시피에 따라 포함될 수 있음 / `2`: 일반적으로 포함됨.
- 이 `0/1/2` 는 **`inclusionPercent`(연속 %)를 산출하기 위한 후속 LLM per-recipe 스코어링의 입력값**이며, 표시·저장값이 아니다. `inclusionPercent` 와 혼동하지 않는다(둘은 별개).

도메인 로직 판단 기준:

- 포함 비율은 위험도 판정의 참고 입력이다.
- 이 컨텍스트는 음식·재료·포함 비율을 저장·관리하지만, 사용자별 `SAFE`, `CAUTION`, `DANGER`, `UNKNOWN`은 결정하지 않는다.

### AllergenMapping

재료와 알러지 유발 성분의 연결이다.

필드 판단 기준:

- 재료 ID
- 알러지 코드
- 매핑 근거
- 매핑 신뢰도

도메인 로직 판단 기준:

- 알러지 코드는 사용자 프로필에서도 참조하므로 공통 코드 체계가 필요하다.
- 재료와 알러지 성분의 연결은 음식보다 재료 쪽에 가깝다.

### DietaryRestrictionMapping

재료와 종교/비건 제한 조건의 연결이다.

필드 판단 기준:

- 재료 ID
- 제한 유형
- 제한 코드
- 매핑 근거

도메인 로직 판단 기준:

- 돼지고기, 소고기, 해산물, 젓갈, 육수, 동물성 성분처럼 종교/비건 제한과 연결되는 재료를 표현한다.
- 사용자별 종교/비건 여부와 직접 비교하는 일은 `assessment`에서 수행한다.

### 데이터 출처 참조 (research 이관)

> LLM 제공자·각 응답 요약·종합 결과·실패 사유 같은 **provenance(`FoodSource`/`FoodInference`)는 `research` 컨텍스트로 이관**했다([ADR-0004](../../adr/0004-research-bounded-context.md)). `food`는 그 세부를 들고 있지 않는다.

`food`가 보관하는 것은 다음으로 한정한다:

- **데이터 상태** — `생성됨` / `LLM 생성됨` / `검수 필요` / `검수 완료` / `비활성`(§5).
- **출처 참조** — 이 음식을 만든 `research` 결과를 **ID로만** 참조한다(컨텍스트 간 전체 객체 비참조).

도메인 로직 판단 기준:

- LLM 원본 응답·종합 메타데이터는 `research`가 소유한다. `food`는 종합 결과(`SynthesizedFoodProfile`)를 받아 영속하고, LLM 생성물과 내부 검수 데이터를 상태로 구분한다.
- 캐시 미스 메뉴의 조사·종합·저장은 `research`(배치)가 수행하며, 스캔 응답 경로에서는 생성하지 않는다(ADR-0003).

## 5. 상태

음식 데이터에는 상태가 필요하다.

후보 상태:

- 생성됨
- LLM 생성됨
- 검수 필요
- 검수 완료
- 비활성

상태 판단 기준:

- LLM으로 처음 생성된 음식은 내부 검수 여부를 구분할 수 있어야 한다.
- 사용자에게 이미 제공된 음식 데이터는 추적 가능해야 한다.
- 음식 데이터를 삭제하기보다 비활성 처리하는 방식을 우선 고려한다.

## 6. 다른 컨텍스트와의 관계

- `member`: 직접 의존하지 않는다. 사용자의 식이 제한 정보는 `assessment`가 조합한다.
- `scan`: 메뉴명 매핑을 위해 food ID와 음식명 정보를 제공한다(캐시 조회).
- `assessment`: 음식 재료, 알러지 매핑, 종교/비건 매핑 정보를 제공한다.
- `research`: 캐시 미스 메뉴의 종합 결과(`SynthesizedFoodProfile`)를 `research`에서 받아 `Food`/`FoodIngredient`로 영속한다. `food`는 만든 research를 ID로만 참조한다.
- `review`: 현재 구현 범위에서는 제외한다. 추후 리뷰 기능이 확정되면 음식 ID를 기준으로 연결된다.

## 7. 구현 시 주의사항

- 음식은 식당에 귀속되지 않는다.
- 음식 데이터는 한국어 원문 + 9개 언어로 사전 번역해 저장한다(ADR-0003). 번역·재료 종합은 `research`(배치)가 생성하고 `food`는 그 결과를 영속한다.
- 사용자별 위험도를 Food에 저장하지 않는다.
- Food와 Ingredient를 하나의 Aggregate로 묶지 않는다.
- 재료 지식베이스가 커지면 `Ingredient`, `AllergenMapping`, `DietaryRestrictionMapping`은 별도 컨텍스트 분리 후보로 본다.
- LLM 응답 원본·종합 메타데이터는 `food`가 아니라 `research`가 소유한다 — `food`는 데이터 상태와 research ID 참조만 둔다.
- 메뉴판 원문 메뉴명은 `scan`의 책임이고, 음식의 정규 정보는 `food`의 책임이다.
