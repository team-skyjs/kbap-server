# member Context

## 1. 역할

`member` 컨텍스트는 사용자와 사용자의 식이 제한 정보를 관리한다. Kbap에서 위험도 판정은 개인화되어야 하므로, `member`는 알러지, 종교상 먹지 못하는 음식, 비건 여부를 정확히 보관해야 한다.

`member`는 음식 재료를 해석하거나 위험도를 계산하지 않는다. 사용자의 조건을 보관하고 제공하는 책임만 가진다.

인증/인가와 이메일 인증은 MVP에서 별도 Bounded Context로 분리하지 않고 `member` 내부 하위 영역으로 둔다. 단, 프로필/식이 제한 관리와 인증 코드는 패키지와 책임을 분리한다.

## 2. 포함 기능

- 회원 기본 정보 관리
- 이메일 인증 상태 관리
- 닉네임 관리
- 국적 관리
- 알러지 정보 관리
- 종교상 먹지 못하는 음식 관리
- 비건 여부 관리
- 매운맛 허용 정도 관리
- 관심 음식 관리
- 사용자 랭킹 상태 관리

## 3. 제외 기능

- 음식 재료 정보 관리
- 재료와 알러지 유발 성분 매핑 관리
- 사용자별 위험도 계산
- 음식별 리뷰 본문 관리
- 메뉴판 스캔 결과 관리

## 4. 핵심 개념

### Member

서비스 사용자다.

필드 판단 기준:

- 회원 식별자
- 이메일
- 이메일 인증 상태
- 닉네임
- 회원 상태
- 가입 시각
- 탈퇴 시각

도메인 로직 판단 기준:

- 이메일 인증이 필요한 기능과 그렇지 않은 기능을 구분할 수 있어야 한다.
- 탈퇴 또는 비활성 사용자는 스캔 요청 같은 주요 기능이 제한될 수 있다. 추후 리뷰 기능을 구현하면 리뷰 작성도 제한 대상이 될 수 있다.

### Identity / Auth

회원 인증과 인가에 필요한 정보다.

필드 판단 기준:

- 이메일
- 이메일 인증 상태
- 인증 제공자
- 로그인 식별자
- 권한 또는 역할
- 마지막 로그인 시각

도메인 로직 판단 기준:

- 인증/인가 정보는 사용자 프로필과 같은 컨텍스트 안에 있어도 책임을 섞지 않는다.
- 이메일 인증 상태는 가입 완료와 주요 기능 사용 가능 여부에 영향을 줄 수 있다.
- 토큰 발급, 세션 관리, 보안 필터 구현은 도메인 로직이 아니라 API/security 계층 책임이다.

### MemberProfile

사용자 표시 정보와 기본 설정이다.

필드 판단 기준:

- 닉네임
- 국적
- 프로필 이미지 여부

도메인 로직 판단 기준:

- 국적은 사용자 표시와 개인화에 사용된다. 추후 리뷰 기능을 구현하면 리뷰 필터와 동일 국적 평점 계산에도 사용할 수 있다.
- 표시 언어는 프로필이 보관하지 않는다 — 어느 번역본을 내려줄지는 요청 `lang` 파라미터가 정한다(KB-229 · ADR-0014).

### DietaryProfile

위험도 판정에 필요한 사용자 식이 제한 프로필이다.

필드 판단 기준:

- 사용자 ID
- 알러지 목록
- 종교상 제한 조건
- 비건 여부
- 갱신 시각

도메인 로직 판단 기준:

- MVP 위험도 판정에는 알러지, 종교, 비건만 포함한다.
- 식이 제한 정보는 비어 있을 수 있지만, 그 경우 위험도 판정 결과에 영향을 준다.
- 사용자가 식이 제한 정보를 수정하면 이후 판정 결과는 달라질 수 있다.
- 과거 스캔 당시 결과는 `scan`의 스냅샷으로 보존한다.

### MemberAllergen

사용자가 가진 알러지 성분이다.

필드 판단 기준:

- 알러지 코드
- 알러지 표시명
- 심각도
- 메모

도메인 로직 판단 기준:

- 알러지 코드는 `food`의 알러지 매핑과 비교 가능한 공통 코드여야 한다.
- 심각도는 MVP에서 위험도 단계에 직접 반영할지 여부를 별도 결정해야 한다.
- 알러지 메모는 판정 로직보다 사용자 표시 또는 고객지원용에 가깝다.

### ReligiousRestriction

종교상 먹지 못하는 음식 또는 재료 조건이다.

필드 판단 기준:

- 제한 유형
- 제한 코드
- 사용자 선택 여부

도메인 로직 판단 기준:

- 돼지고기, 소고기, 특정 육류, 해산물 등 제한 코드는 재료 매핑과 비교 가능해야 한다.
- 종교 자체를 저장할지, 종교에 따른 제한 조건만 저장할지는 구현 단계에서 결정할 수 있다.
- 위험도 판정에는 “이 사용자가 피해야 하는 재료 조건”만 필요하다.

### VeganPreference

비건 또는 채식 관련 조건이다.

필드 판단 기준:

- 비건 여부
- 채식 유형
- 제외 동물성 성분

도메인 로직 판단 기준:

- MVP에서는 비건 여부만 필수 기준으로 둔다.
- 락토, 오보, 페스코 같은 세부 채식 유형은 확장 가능성으로 남길 수 있다.
- 비건 여부는 `avoidance`에서 재료의 동물성 여부와 비교된다.

### SpiceTolerance

사용자의 매운맛 허용 정도다.

필드 판단 기준:

- 0~10 단계 값
- 갱신 시각

도메인 로직 판단 기준:

- MVP 위험도 `SAFE`, `CAUTION`, `DANGER`, `UNKNOWN`에는 직접 포함하지 않는다.
- 추천, 홈 피드, 음식 상세 표시에서 보조 정보로 사용할 수 있다.
- 단계 기준은 콘텐츠 정책에 따라 바뀔 수 있으므로 코드에 하드코딩하지 않는다.

### InterestedFood

사용자가 관심 있거나 먹어본 한국 음식이다.

필드 판단 기준:

- 음식 ID
- 선택 시각
- 관심/먹어봄 구분

도메인 로직 판단 기준:

- 추천과 온보딩 개인화에 사용한다.
- 음식의 상세 정보는 `food`에서 관리한다.

### MemberRanking

사용자의 서비스 활동 기반 랭킹이다.

필드 판단 기준:

- 랭킹 등급
- 랭킹 계산 기준값
- 마지막 계산 시각

도메인 로직 판단 기준:

- 랭킹의 소유권은 `member`가 가진다.
- 리뷰 기능이 확정되면 리뷰 활동은 랭킹 계산의 입력이 될 수 있다.
- 현재 도메인 설계에서는 리뷰 컨텍스트를 구현하지 않으므로 랭킹 계산은 보류하거나 단순 상태로 둔다.

## 5. 상태

회원 상태 후보:

- 가입 대기
- 정상
- 정지
- 탈퇴

식이 제한 프로필 상태 후보:

- 입력 전
- 입력 완료
- 수정 필요

상태 판단 기준:

- 식이 제한 프로필이 없으면 위험도 판정은 제한 조건이 없는 사용자로 처리될 수 있다.
- 단, 알러지 서비스의 특성상 온보딩에서 식이 제한 입력은 필수로 두는 것이 제품 방향에 맞다.

## 6. 다른 컨텍스트와의 관계

- `food`: 직접 의존하지 않는다.
- `avoidance`: DietaryProfile을 제공한다.
- `scan`: 스캔 요청자 ID를 제공한다.
- `review`: 현재 구현 범위에서는 제외한다. 추후 리뷰 기능이 확정되면 작성자 ID, 국적, 랭킹 표시용 정보를 제공할 수 있다.

## 7. 구현 시 주의사항

- member가 음식 재료 상세를 알면 안 된다.
- 사용자 식이 제한 정보는 위험도 판정의 입력이지 판정 결과가 아니다.
- 과거 스캔 결과를 사용자 프로필 변경에 맞춰 덮어쓰지 않는다.
- 음식 데이터 저장 언어 정책과 요청 표시 언어(`lang`)를 혼동하지 않는다.
- 랭킹은 `member` 소유로 둔다. 리뷰 활동 기반 랭킹은 리뷰 기능 재개 시점에 다시 설계한다.
