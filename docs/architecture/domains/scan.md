# scan Context

## 1. 역할

`scan` 컨텍스트는 사용자가 메뉴판을 스캔한 사건과 그 결과를 관리한다. 서버는 OCR을 직접 수행하지 않는다. 클라이언트가 추출한 메뉴명 목록을 서버로 보내고, 서버는 그 메뉴명이 어떤 음식 데이터로 매핑되었는지(또는 **DB에 없어 결과 없음**인지)와 당시 사용자에게 어떤 결과를 반환했는지를 기록한다.

`scan`은 음식 재료를 해석하지 않고, 위험도 정책도 직접 계산하지 않으며, **LLM을 호출하지 않는다**. 캐시 미스 메뉴의 조사·종합은 `research` 컨텍스트(배치)의 책임이다([ADR-0003](../../adr/0003-pretranslated-batch-menu-pipeline.md)·[ADR-0004](../../adr/0004-research-bounded-context.md)). scan은 "미스였다"는 사실만 스냅샷으로 남긴다.

## 2. 포함 기능

- 메뉴판 스캔 요청 생성
- 스캔 요청자 기록
- 클라이언트가 전달한 원문 메뉴명 저장
- 메뉴명 표시 순서 저장
- 클라이언트 OCR 보조 메타데이터(바운딩 박스 등) 저장
- 원문 메뉴명과 Food 매핑 결과 저장(히트 / 미스=결과없음)
- 매핑 상태와 매핑 신뢰도 관리
- 사용자에게 반환한 위험도 결과 스냅샷 저장
- 스캔 상태 관리
- **스캔 이력 조회**(사용자가 과거 스캔 내역을 다시 열람)
- **스캔 횟수 제한**(rate limit) 관리

## 3. 제외 기능

- 서버 OCR 수행
- 이미지 인식
- 음식 사진 판별
- 가공식품 분석
- 음식 재료 생성
- 알러지 위험도 계산
- 회원 식이 제한 정보 관리
- **LLM 호출·미스 메뉴 조사/종합·조사 대기열 소유**(= `research` 컨텍스트)
- **음식 데이터(카탈로그) 영속**(= `food` 컨텍스트)

## 4. 핵심 개념

### MenuScan

사용자가 메뉴판을 스캔한 하나의 요청이다.

필드 판단 기준:

- 스캔 ID
- 요청자 ID
- 스캔 상태
- 이미지 참조값
- 생성 시각
- 완료 시각
- 실패 사유

도메인 로직 판단 기준:

- 스캔은 여러 메뉴 항목을 가진다.
- 스캔 상태는 처리 흐름을 표현해야 한다.
- 일부 메뉴가 캐시 미스(결과 없음)이거나 매핑 실패여도 스캔 전체는 부분 완료일 수 있다(스캔 경로에 LLM 호출은 없다).

### ScannedMenuItem / RecognizedMenuItem

클라이언트가 추출해 서버로 보낸 메뉴판의 메뉴 항목이다.

필드 판단 기준:

- 원문 메뉴명
- 정규화 메뉴명
- 표시 순서
- 클라이언트 OCR 신뢰도
- 클라이언트 화면 위치 메타데이터
- 매핑된 음식 ID
- 매핑 상태
- 매핑 신뢰도

도메인 로직 판단 기준:

- 원문 메뉴명은 반드시 보존한다.
- 한국어 질문 화면에 표시할 메뉴명은 실제 메뉴판의 메뉴명과 같아야 한다.
- 클라이언트 화면 위치는 도메인 핵심 규칙이 아니라 결과 재현용 메타데이터다.
- 같은 메뉴명이 여러 번 등장할 수 있으므로 표시 순서나 항목 ID가 필요하다.

### FoodMapping

원문 메뉴명이 어떤 Food로 해석되었는지를 표현한다.

필드 판단 기준:

- 원문 메뉴명
- 정규화 메뉴명
- 매핑된 food ID
- 매핑 방식
- 매핑 신뢰도
- 매핑 상태

매핑 상태 후보:

- 매핑 완료(캐시 히트)
- 결과 없음(캐시 미스 — DB에 음식 데이터 없음, `research` 조사 대기)
- 매핑 실패
- 알 수 없음(`UNKNOWN` — 음료·세트·상품명 등 재료 판정 비대상)

도메인 로직 판단 기준:

- 스캔 시점에는 **캐시 히트 / 결과 없음(미스)** 두 결과뿐이다 — 스캔은 LLM을 호출해 음식을 생성하지 않는다.
- "결과 없음(미스)"과 "알 수 없음(`UNKNOWN`)"을 구분한다 — 전자는 아직 DB에 없을 뿐 후속 배치로 채워지고, 후자는 애초에 재료 판정 대상이 아니다.
- 매핑 실패가 전체 스캔 실패를 반드시 의미하지는 않는다.
- 매핑된 Food가 나중에 갱신되어도 당시 매핑 결과는 추적 가능해야 한다.

### ScanAssessmentSnapshot

스캔 당시 사용자에게 반환한 위험도 결과다.

필드 판단 기준:

- 메뉴 항목 ID
- food ID
- 표시한 음식명
- 위험도
- 위험 사유 요약
- 주의 재료 목록
- 사장님 질문 생성에 필요한 값
- 생성 시각

도메인 로직 판단 기준:

- 스냅샷은 과거 사용자 경험을 재현하기 위한 값이다.
- 사용자 프로필이나 Food 데이터가 바뀌어도 과거 스냅샷을 자동 변경하지 않는다.
- 현재 기준 위험도 재계산은 `avoidance`를 다시 호출하는 별도 흐름이다.

### ClientScanMetadata

클라이언트가 오버레이 UI를 복원하거나 디버깅하기 위해 넘긴 보조 정보다.

필드 판단 기준:

- bounding box
- OCR confidence
- display order
- 원본 이미지 참조

도메인 로직 판단 기준:

- bounding box는 핵심 도메인 규칙이 아니다.
- 다만 스캔 결과 화면을 다시 열어야 하거나, 사용자 제보/검수 화면에서 원본 메뉴 위치를 보여줘야 한다면 저장할 수 있다.
- 이 값은 위험도 판정에 사용하지 않는다.

## 5. 상태

스캔 상태 후보:

- 생성됨
- 처리 중
- 부분 완료
- 완료
- 실패

상태 판단 기준:

- 일부 메뉴만 캐시 미스(결과 없음)거나 매핑 실패해도 스캔 전체는 부분 완료일 수 있다.
- 캐시 미스(결과 없음)와 매핑 실패(오류)를 구분한다. 스캔 경로에 LLM 호출은 없으므로 LLM 실패 상태는 스캔에 없다.
- 스캔 완료는 사용자에게 반환 가능한 결과가 만들어졌다는 뜻이다.

## 6. 다른 컨텍스트와의 관계

- `member`: 요청자 ID를 가진다. 사용자 식이 제한 상세는 직접 알지 않는다.
- `food`: 원문 메뉴명을 Food로 매핑하기 위해 사용한다(캐시 조회).
- `avoidance`: 사용자에게 반환할 위험도 결과를 만들기 위해 사용한다.
- `research`: 직접 의존하지 않는다. 캐시 미스 적재는 `:application`이 스캔 유스케이스에서 `research`에 등록한다 — scan은 미스를 스냅샷으로 기록만 하고 조사 대기열을 소유하지 않는다.
- `review`: 직접 관련 없다.

## 7. 구현 시 주의사항

- scan은 OCR 도메인이 아니다.
- scan은 “무엇을 찍었는가”보다 “어떤 메뉴명이 어떤 음식으로 해석되었는가(또는 결과 없음인가)”를 저장한다.
- bounding box는 도메인 핵심 필드가 아니라 UI 재현용 메타데이터다.
- 위험도 계산 로직을 scan에 넣지 않는다. **LLM 호출·미스 메뉴 조사 대기열도 scan에 두지 않는다**(= `research`).
- Food 재료 정보를 scan에 복제하지 않는다. 필요한 것은 당시 결과 스냅샷이다.
- 현재 기준 재판정 결과와 과거 스캔 스냅샷을 구분한다.
- 스캔 이력 조회·횟수 제한은 scan의 책임이다 — 이것이 scan을 (단순 미스 적재가 아니라) 독립 컨텍스트로 유지하는 이유다.
