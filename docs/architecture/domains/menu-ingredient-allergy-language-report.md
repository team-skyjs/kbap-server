# 메뉴·재료·알러지·다국어 도메인 의사결정 보고서

> **다국어·캐시미스·LLM 처리 위치 결정은 [ADR-0003](../../adr/0003-pretranslated-batch-menu-pipeline.md)으로 갱신됐다.** 음식 콘텐츠는 9개 언어로 사전 번역해 저장하고, 캐시 미스는 실시간 LLM 없이 결과 없음으로 처리하며, 재료 조사·번역은 `meogo-batch`가 하루 1회 수행한다. (초안의 "한·영만 저장" 결정은 이 ADR이 대체.)

## 1. 배경

Meogo는 외국인 사용자가 한국 음식 메뉴를 보고 자신의 알러지, 종교상 제한, 비건 조건과 충돌하는지 빠르게 판단하도록 돕는 서비스다. 따라서 도메인 설계의 핵심은 "메뉴판에서 본 이름", "서비스가 관리하는 음식 기준 정보", "음식에 포함될 수 있는 재료", "사용자별 위험도 판정"을 서로 섞지 않는 것이다.

이번 설계에서는 다음 네 가지 결정을 중심으로 도메인을 나눴다.

- 메뉴판 스캔 결과는 `scan` 컨텍스트가 사건과 스냅샷으로 관리한다.
- 음식과 재료 지식은 `food` 컨텍스트가 관리한다.
- 사용자별 알러지/식이 제한과 음식의 충돌 여부는 `assessment` 컨텍스트가 판정한다.
- 음식 콘텐츠 데이터는 한국어 원문 + 9개 대상 언어로 사전 번역해 저장하고(ADR-0003), 정적 UI 다국어 문구와 분리한다.

## 2. 메뉴명과 음식 기준 정보 분리

메뉴판에서 사용자가 보는 이름은 항상 정규 음식명과 같지 않다. 같은 음식도 식당마다 다른 이름으로 적힐 수 있고, 메뉴판에는 약어, 외래어 표기, 세트명, 수식어가 섞일 수 있다. 그래서 원문 메뉴명과 음식 기준 정보를 분리했다.

`scan` 컨텍스트는 사용자가 보낸 메뉴명 목록과 처리 결과를 기록한다. 여기서 중요한 값은 원문 메뉴명, 정규화 메뉴명, 표시 순서, 음식 매핑 결과, 당시 사용자에게 반환한 위험도 스냅샷이다. 서버는 OCR을 직접 수행하지 않고, 클라이언트가 추출한 메뉴명 목록을 입력으로 받는다.

`food` 컨텍스트는 김치찌개, 불고기, 비빔밥 같은 음식 기준 정보를 관리한다. 음식의 이름·설명(한국어 원문 + 9개 언어 번역), 대표 이미지, 카테고리, 데이터 상태, 출처가 여기에 속한다. 메뉴판 원문은 `scan`의 책임이고, 음식의 정규 정보는 `food`의 책임으로 나눴다.

이렇게 분리한 이유는 과거 스캔 경험을 안정적으로 재현하기 위해서다. 나중에 음식 데이터가 수정되더라도 과거 사용자가 본 메뉴명과 그때 받은 결과는 `scan`의 스냅샷으로 남아야 한다. 반대로 최신 음식 정보 기준으로 다시 판정해야 할 때는 `assessment`를 다시 호출하는 별도 흐름으로 처리한다.

## 3. 음식과 재료 모델링

`food` 컨텍스트의 주요 Aggregate Root는 `Food`와 `Ingredient`다. 두 모델은 같은 컨텍스트 안에 있지만 같은 Aggregate는 아니다.

`Food`는 음식 하나의 기준 정보를 나타낸다. `Ingredient`는 간장, 새우젓, 돼지고기, 고춧가루처럼 여러 음식에서 공유될 수 있는 재료 단위다. 예를 들어 간장은 불고기에도 들어갈 수 있고 비빔밥 양념에도 들어갈 수 있으므로, 음식이 재료 객체 전체를 직접 소유하지 않도록 했다.

음식과 재료의 관계는 `FoodIngredient`로 표현한다. `FoodIngredient`는 특정 음식에 특정 재료가 들어갈 수 있는지를 나타내며, `foodId`, `ingredientId`, 포함 가능성 스코어, 포함 근거, 데이터 출처, 검수 상태를 가진다.

포함 가능성 스코어는 세 단계다.

- `0`: 일반적으로 포함되지 않음
- `1`: 매장 또는 레시피에 따라 포함될 수 있음
- `2`: 일반적으로 포함됨

음식 단위의 포함 가능성 요약은 관련 재료 스코어의 평균을 소수점 한 자리까지 반올림해 표시할 수 있다. 다만 이 평균은 표시용 요약 지표이며, 사용자별 최종 위험도를 낮추는 산식으로 쓰지 않는다. 이 스코어는 사용자별 위험도 판정의 입력일 뿐, `food` 컨텍스트가 직접 `SAFE`, `CAUTION`, `DANGER`, `UNKNOWN`을 결정하지 않는다.

이 구조의 장점은 재료 지식의 중복을 줄이고, 음식별 포함 가능성은 별도로 표현할 수 있다는 점이다. 같은 `Ingredient`라도 음식마다 포함 가능성 스코어가 다를 수 있다. 예를 들어 돼지고기는 제육볶음에서는 일반적으로 포함될 수 있지만, 김치찌개에서는 식당이나 레시피에 따라 달라질 수 있다.

## 4. 알러지 포함 여부와 위험도 판정

알러지 포함 여부는 단순히 음식 이름만 보고 결정하지 않는다. 음식이 어떤 재료를 가질 수 있는지, 그 재료가 어떤 알러지 코드와 연결되는지, 사용자가 어떤 알러지를 가지고 있는지를 조합해야 한다.

이를 위해 `food` 컨텍스트에는 재료와 알러지 유발 성분을 연결하는 `AllergenMapping`을 둔다. 알러지 코드는 `member` 컨텍스트의 사용자 알러지 정보와 비교 가능한 공통 코드 체계로 관리한다. 같은 방식으로 종교/비건 제한은 `DietaryRestrictionMapping`으로 재료와 제한 코드를 연결한다.

사용자의 실제 조건은 `member` 컨텍스트의 `DietaryProfile`에 저장된다. 여기에는 알러지 목록, 종교상 제한 조건, 비건 여부가 포함된다. 하지만 `assessment`는 `DietaryProfile`이나 `FoodIngredient` 같은 다른 컨텍스트의 영속 모델을 직접 받지 않는다.

대신 `:meogo-api:application`이 `food`와 `member`의 데이터를 판정에 필요한 값만 담은 `AssessmentInput`으로 변환한다. 이 입력에는 사용자 제한 조건, 음식 재료 목록, 포함 가능성 스코어, 알러지/종교/비건 매핑, 원문 메뉴명이 들어간다.

`assessment` 컨텍스트는 이 입력을 바탕으로 위험도를 계산한다.

- 포함 가능성 스코어 `2`인 재료가 사용자 제한 조건과 충돌하면 `DANGER` 후보가 된다.
- 포함 가능성 스코어 `1`인 재료가 사용자 제한 조건과 충돌하면 `CAUTION` 후보가 된다.
- 식별된 음식의 재료 정보가 부족하면 `CAUTION` 후보가 된다.
- 판정 가능한 음식이고 충돌하는 주요 재료가 확인되지 않으면 `SAFE`가 될 수 있다.
- 음료, 세트/코스명, 상품명, 식별 불가 메뉴처럼 음식/재료 판정 대상이 명확하지 않으면 `UNKNOWN`이 된다.

최종 위험도는 먼저 `UNKNOWN` 대상인지 확인한 뒤, 판정 가능한 음식에서는 가장 높은 위험도를 채택한다. 판정 가능한 음식의 우선순위는 `DANGER` > `CAUTION` > `SAFE`다. 알러지 서비스 특성상 확실하지 않은 경우 `SAFE`로 낮추지 않고 `CAUTION`으로 남기는 것을 원칙으로 했다.

## 5. 조회 시점 판정과 스냅샷 구분

음식 상세나 음식 리스트 조회에서 사용자 알러지 프로필과 특정 음식의 상관관계를 내려줘야 할 수 있다. 이 경우 현재 설계에서는 조회 시점에 `assessment` 판정 정책을 호출하는 방식이 맞다.

흐름은 다음과 같다.

1. `food`에서 음식 기준 정보와 음식-재료 관계를 조회한다.
2. `member`에서 사용자의 식이 제한 프로필을 조회한다.
3. `:meogo-api:application`에서 두 데이터를 `AssessmentInput`으로 변환한다.
4. `assessment`가 사용자별 위험도와 사유를 계산한다.
5. API 응답 DTO에서 음식 정보와 사용자별 판정 결과를 조합해 내려준다.

이렇게 하면 `Food`에 사용자별 위험도를 저장하지 않아도 된다. 위험도는 음식 자체의 속성이 아니라 사용자 조건과 음식 재료의 조합 결과이기 때문이다.

반면 스캔 결과처럼 과거 사용자 경험을 재현해야 하는 경우에는 `ScanAssessmentSnapshot`으로 당시 결과를 저장한다. 사용자의 알러지 프로필이나 음식 재료 데이터가 나중에 바뀌어도 과거 스냅샷을 자동 변경하지 않는다.

## 6. 다국어 지원 의사결정

음식 콘텐츠 데이터는 한국어(`ko`) 원문 + 9개 대상 언어로 사전 번역해 저장한다(ADR-0003). 여기서 음식 콘텐츠는 음식명, 설명, 재료명, 알러지/종교/비건 주의 성분을 의미한다.

9개 대상 언어: 중국어 간체(`zh-Hans`), 영어(`en`), 일본어(`ja`), 중국어 번체(`zh-Hant`), 베트남어(`vi`), 인도네시아어(`id`), 태국어(`th`), 러시아어(`ru`), 스페인어(`es`).

이 결정을 내린 이유는 다음과 같다.

- 한국 음식의 원문 정보는 한국어가 기준이므로 한국어를 원문으로 관리한다.
- 서비스 대상이 다양한 국적의 외국인이므로, 메뉴를 스캔하면 사용자 언어로 즉시 읽히도록 9개 언어를 미리 번역해 둔다.
- 응답 시점에 번역하면 매 요청마다 번역 비용·지연이 생기고 캐시 이점이 사라진다. 사전 번역·저장이 읽기 비용을 낮춘다.
- 음식 데이터 번역 정책과 앱의 정적 UI 문구 번역 정책은 성격이 다르므로 분리한다(둘 다 사전 번역·저장 모델을 쓰되 트랙은 별개).

번역은 `research`(배치)가 LLM으로 생성하고 `food`가 저장한다(§7). 사용자의 `사용 언어`는 어떤 사전 번역본을 내려줄지와 정적 UI 문구 제공에 사용한다. 버튼, 안내 문구, 법적 고지 같은 정적 문구는 `:meogo-api:core` 또는 별도 supporting resource에서 관리하고, 음식 지식 데이터와 섞지 않는다.

모든 언어로 음식 데이터를 저장하면 검수·품질 관리 비용이 커지는 점은 9개 언어로 범위를 한정해 통제한다. 특히 알러지/식이 제한처럼 안전 직결 데이터는 검수 상태로 구분한다(§7).

사장님에게 보여줄 질문은 도메인 값으로 필요한 재료명, 원문 메뉴명, 사용자 제한 조건을 생성하되, 질문 문구 자체의 다국어 처리는 UI 문구 정책과 분리한다.

## 7. LLM 데이터와 검수 정책

캐시 미스 메뉴는 그 스캔에서 결과 없음으로 응답하고, 미스 메뉴명을 `research` 조사 대기열에 적재한다. 적재된 메뉴는 `research` 컨텍스트가 LLM을 호출해 음식 데이터 후보(재료 + 9개 언어 번역)를 만들고, `meogo-batch`가 하루 1회 트리거한다(ADR-0003·ADR-0004). 하지만 LLM 원본 응답을 그대로 도메인 판단에 쓰지 않는다. `research` 종합 정책(순수 도메인 서비스)이 여러 응답을 종합하고, 도메인에서 쓸 수 있게 정리한 결과만 `food`가 `Food`, `FoodIngredient`에 반영한다.

음식 데이터에는 생성됨, LLM 생성됨, 검수 필요, 검수 완료, 비활성 같은 상태가 필요하다. 특히 알러지와 식이 제한은 사용자 안전과 직결되므로, LLM이 만든 데이터와 내부 검수된 데이터를 구분할 수 있어야 한다. 9개 언어 번역 역시 LLM 생성물이므로 같은 검수 정책을 적용한다.

## 8. 설계의 효과와 한계

이 설계의 가장 큰 효과는 책임 분리다. `food`는 음식과 재료 지식을 관리하고, `member`는 사용자 조건을 관리하고, `assessment`는 사용자 조건과 음식 재료를 조합해 판정한다. `scan`은 과거 스캔 사건과 당시 응답을 기록한다.

이렇게 나누면 음식 데이터가 바뀌어도 사용자 프로필과 스캔 이력을 안전하게 분리할 수 있다. 또한 음식 리스트, 음식 상세, 메뉴판 스캔처럼 화면이 달라도 같은 `assessment` 정책을 재사용할 수 있다.

다만 리스트 조회처럼 여러 음식을 한 번에 판정해야 하는 경우에는 성능을 고려해야 한다. 음식마다 개별적으로 판정하면 조회 비용이 커질 수 있으므로, Application 계층에서 여러 음식의 재료 정보와 사용자 프로필을 모아 batch 형태로 판정하는 유스케이스를 두는 것이 좋다.

추후 재료 지식베이스가 커지면 `Ingredient`, `AllergenMapping`, `DietaryRestrictionMapping`을 별도 `ingredient` 또는 `food-knowledge` 컨텍스트로 분리할 수 있다. 현재 MVP에서는 복잡도를 낮추기 위해 `food` 컨텍스트 안에 함께 둔다.

## 9. 결론

이번 도메인 설계는 메뉴명, 음식, 재료, 알러지 판정, 다국어 정책을 한 모델에 몰아넣지 않고 역할별로 분리했다.

- 메뉴판 원문과 스캔 결과는 `scan`이 관리한다.
- 음식 기준 정보와 재료 지식은 `food`가 관리한다.
- 사용자 조건은 `member`가 관리한다.
- 사용자별 위험도는 `assessment`가 조회 또는 스캔 시점에 계산한다.
- 음식 콘텐츠는 한국어 원문 + 9개 언어로 사전 번역해 저장하고(ADR-0003), 정적 UI 다국어와 분리한다.
- 캐시 미스 메뉴의 재료 조사·번역은 `meogo-batch`가 하루 1회 처리하고, 스캔 응답 경로는 LLM을 호출하지 않는다(ADR-0003).
