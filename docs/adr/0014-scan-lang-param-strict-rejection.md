# 0014. 스캔 표시 언어 — `lang` 파라미터 전환 + 미지원 코드 거절(en 폴백 예외)

- **상태**: Accepted
- **날짜**: 2026-07-23
- **관련**: specs/kb-229-scan-lang-param · Jira KB-229 · ADR-0013(범위 한정 예외 추가, supersede 아님) · 헌법 v4.0.0 원칙 V

## Context

ADR-0013(KB-201)이 표시 언어를 받는 전 API 를 `lang` 필수 + 미지원 코드 en 폴백으로 통일했지만, **스캔 API(`POST /api/v1/scans`)는 대상에서 빠졌다** — `lang` 파라미터가 없고 회원 프로필 `appLanguage`(미설정 시 `ko`)로 응답 언어를 정했다. ADR-0013 은 이를 "프로필 기반 언어 결정이 남은 유일한 지점이며 통일 여부는 별도로 판단한다" 로 남겨 두었다.

그 결과 두 문제가 있었다.

1. **앱 표시 언어와 스캔 결과 언어가 어긋난다.** 사용자가 앱 언어를 바꿔도 프로필을 갱신하지 않으면 스캔 결과는 옛 언어로 나온다.
2. **프로필이 언어를 계속 보관해야 한다.** 서버가 기억하는 언어와 요청이 싣고 오는 언어라는 두 출처가 공존한다.

통일을 결정하면 미지원 코드 처리를 ADR-0013 과 같이 갈지가 남는다. ADR-0013 이 en 폴백을 택한 근거는 **"`lang` 은 기기 설정에서 흘러드는 값이라, 미지원 기기 언어 사용자에게 400 을 주면 화면(특히 진입 화면인 홈)이 열리지 않는다"** 였고, 그 대가로 **"클라이언트의 코드 오타·대소문자 오류가 200 으로 조용히 나간다"** 를 명시적으로 감수했다.

## Decision

1. 스캔 API 는 표시 언어를 **`lang` 쿼리 파라미터로 받는다**(필수). 회원 프로필은 응답 언어에 관여하지 않는다.
2. 누락·빈 값·공백은 **400 `COMMON-002`** 로 거절한다(ADR-0013 과 동일).
3. **지원 목록에 없는 코드는 en 으로 폴백하지 않고 400 `COMMON-002` 으로 거절한다** — ADR-0013 결정 3번에서 스캔에 한해 이탈한다. 매칭은 정확 일치이며 관대한 정규화(trim·대소문자 보정)를 하지 않으므로 `EN`·`ko-KR`·`" ko"` 도 거절 대상이다.
4. **에러코드를 새로 채번하지 않는다** — 다른 API 들이 요청 검증 실패에 공통으로 쓰는 기존 `INVALID_REQUEST("COMMON-002")` 를 그대로 쓴다. 클라이언트 입장에서 "lang 을 안 보냄" 과 "lang 값이 잘못됨" 은 같은 대응(요청 수정)이라 분기를 나눌 이유가 없다. 프로필 언어 제거로 미사용이 된 `UNSUPPORTED_APP_LANGUAGE("MEMBER-007")` 는 삭제하고 번호는 재사용하지 않는다.
5. 확정 로직은 **컨트롤러가 소유**한다. `:core` 의 `LanguageCode.from`(관용 lookup, en 폴백)은 그대로 두고 스캔 컨트롤러가 정확 일치로 해석한다 — ADR-0013 의 "엔드포인트별 정책은 각 컨트롤러가 소유한다" 를 따른다.
6. 회원 프로필에서 `appLanguage` 를 전면 제거하고, 기존 row 의 폐기 키는 Flyway 마이그레이션(`JSON_REMOVE`)으로 지운다.

**이 ADR 은 ADR-0013 을 supersede 하지 않는다.** 나머지 5개 엔드포인트(홈·음식 목록/검색/상세·북마크)의 en 폴백은 그대로 유지되며, 이 결정은 스캔 엔드포인트에만 적용되는 범위 한정 예외다.

## Alternatives Considered

- **스캔도 en 폴백(ADR-0013 전면 준수)** — 일관성은 최선이지만, ADR-0013 이 감수한 "조용한 실패" 비용을 스캔에서는 받아들이지 않기로 했다. 스캔 결과는 사용자가 먹을 것을 고르는 화면이라, 요청과 다른 언어의 메뉴명이 조용히 내려가면 사용자가 어긋남을 알아채지 못한다. 또 en 폴백의 근거였던 "진입 화면이 안 열린다" 는 홈 기준 논리이며, 스캔은 사용자가 명시적으로 실행하는 후속 동작이라 400 을 받아도 앱이 잠기지 않는다. 기각.
- **전 API 를 다시 fail-fast 로 되돌린다(ADR-0013 을 supersede)** — 홈이 다시 열리지 않는 문제가 재발한다. ADR-0013 의 핵심 근거가 그대로 유효하므로 기각.
- **전용 에러코드 신규 채번(`SCAN-003` 등)** — 클라이언트가 얻는 정보가 늘지 않는 반면 코드 표는 길어진다. 누락·공백과 미지원 코드는 대응이 같으므로 기존 `COMMON-002` 로 충분해 기각.
- **`MEMBER-007` 재사용** — 스캔 엔드포인트에서 `MEMBER-` 접두 코드가 나가면 클라이언트 분기가 오독한다. 기각.
- **`:core` 에 엄격 lookup(`strictFrom`) 추가** — 엔드포인트 정책이 `:core` 로 새어 들어간다. ADR-0013 이 명시적으로 피한 구조라 기각.

## Consequences

**좋은 점**

- 서버가 표시 언어를 저장·기억하는 경로가 0개가 된다. 프로필 모델이 단순해지고 언어 출처가 요청 하나로 고정된다.
- 클라이언트의 언어 코드 오류가 스캔에서는 즉시 드러난다 — ADR-0013 이 후속으로 남긴 "미지원 코드 유입 탐지" 문제를 이 엔드포인트에 한해 해소한다.
- 스캔 결과 언어가 앱 표시 언어와 항상 일치한다.

**감수하는 트레이드오프**

- **정책이 엔드포인트별로 갈린다.** 같은 `lang` 값이 홈에서는 200(영어), 스캔에서는 400 이다. 클라이언트는 지원 목록을 벗어난 코드를 스캔에 보내지 않도록 관리해야 한다.
- 미지원 기기 언어 사용자는 클라이언트가 지원 언어로 매핑해 보내지 않으면 스캔을 쓸 수 없다. 클라이언트가 폴백 언어를 정해 보내는 것으로 해소한다.

**파괴적 변경 (릴리스 조건)**

- 스캔 API 는 `lang` 없이 호출하면 400 이다. **클라이언트 배포 선행 또는 강제 업데이트가 전제**다.
- 온보딩·프로필 수정의 `appLanguage` 는 보내도 무시되므로 구버전 앱이 그 경로에서 깨지지는 않는다.

**후속**

- 이 예외를 유지할지, 다른 엔드포인트로 확대해 ADR-0013 을 개정할지는 운영 데이터(미지원 코드 유입률)를 보고 판단한다.
- 헌법 원칙 V 는 개정하지 않았다 — 이탈 근거는 specs/kb-229-scan-lang-param 의 plan.md Complexity Tracking 에 기록돼 있다.
