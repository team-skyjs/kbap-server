# 0013. 표시 언어(lang) — 필수화 + 미지원 코드 영어 폴백

- **상태**: Accepted
- **날짜**: 2026-07-20
- **관련**: specs/kb-201-home-lang-param · Jira KB-201 · specs/008-unsupported-language-error(supersede) · 헌법 v4.0.0

## Context

표시 언어 결정 규칙이 API 마다 달랐다.

| API | 언어 결정 | 미지정 | 미지원 코드 |
|---|---|---|---|
| 홈 | 회원 프로필 `appLanguage`(비회원은 고정) | `en` | (파라미터 없음) |
| 음식 목록·검색·상세, 북마크 | `lang` 쿼리 파라미터 | `ko` | 400 `COMMON-001` |

그 결과 두 문제가 있었다.

1. **같은 세션에서 화면별 언어가 어긋난다.** 프로필 언어가 `ja`인 회원이 홈에서 일본어 음식명을 보고 그걸 탭해 상세로 들어가면, 클라이언트가 `lang`을 붙이지 않는 한 한국어로 바뀐다.
2. **비회원은 기기 언어를 전달할 방법이 없다.** 홈이 요청 파라미터를 받지 않아, 클라이언트가 기기 언어를 알아도 항상 영어를 봤다.

규칙을 하나로 합치려면 미지정·미지원 처리를 어느 쪽으로 통일할지 정해야 했다. 특히 미지원 코드의 400 fail-fast 는 spec 008 에서 명시적으로 결정하고 헌법 원칙 V 에 박아둔 계약이라, 바꾸려면 헌법 개정이 필요했다.

핵심 제약: **`lang` 은 사용자가 고르는 값이 아니라 기기 설정에서 흘러드는 값**이다. 서비스가 지원 언어를 늘리기 전까지 그 목록 밖의 기기 언어를 쓰는 사용자는 계속 존재한다.

## Decision

표시 언어를 받는 전 API(`GET /home`·`/foods`·`/foods/search`·`/foods/{id}`·`/bookmarks`)에서 다음으로 통일한다.

1. **`lang` 은 필수다.** 기본값을 두지 않는다. 파라미터 누락·빈 값·공백은 **400 `COMMON-002`** 로 거절한다.
2. 값이 지원 10종(`ko` 포함)과 **정확히 일치**하면 그 언어로 응답한다.
3. 그 외 값(미지원 코드·대소문자 불일치·지역 변형·앞뒤 공백)은 거절하지 않고 **`en`(영어)으로 폴백**한다.
4. **홈은 회원 프로필 `appLanguage` 를 참조하지 않는다** — 같은 `lang` 이면 회원과 비회원의 응답 언어가 같다.
5. **유효성 검증과 `LanguageCode` 확정은 요청 경계(컨트롤러)가 소유한다.** 요청 DTO 의 `@field:NotBlank` 가 빈 값을 쳐내고, 컨트롤러가 `LanguageCode` 를 확정해 서비스에 넘긴다.

즉 **거절 지점이 "값이 틀렸을 때"에서 "값을 안 채웠을 때"로 이동**한다.

그 결과 `LanguageCode.from` 은 검증 책임을 전부 잃고 순수 lookup 이 된다.

```kotlin
fun from(code: String): LanguageCode = entries.firstOrNull { it.code == code } ?: EN
```

`ErrorCode.UNSUPPORTED_LANGUAGE`(`COMMON-001`)는 삭제한다. 언어 코드 **값**을 사유로 하는 400 은 더 이상 존재하지 않는다.

trim 을 하지 않으므로 `" ko "` 는 미지원으로 보아 영어로 폴백한다 — 헌법의 "정확 일치, 관대한 정규화 금지"에 부합한다.

## Alternatives Considered

- **미지원 코드도 400 유지(spec 008 그대로)** — 지원하지 않는 기기 언어(예: `fr`) 사용자에게 화면이 열리지 않는다. 홈은 앱 진입 화면이라 앱 자체가 열리지 않는 것과 같다. 기각.
- **`ko` 로 폴백** — 비한국어권 외국인 대상 서비스의 목적에 정면으로 반한다. 원칙 V 의 원래 fail-fast 근거도 "조용히 **한국어로** 응답되면 오인·디버깅을 어렵게 한다"였다. 기각.
- **클라이언트가 지원 목록을 알고 미지원이면 `lang` 을 생략** — 지원 목록을 클라이언트에 이중으로 유지해야 하고, 서버가 언어를 추가할 때마다 앱 배포가 필요하다. `lang` 필수화와도 양립하지 않는다. 기각.
- **`lang` 을 선택으로 두고 미지정 시 기본값(ko 또는 en)** — 클라이언트가 언어를 빠뜨린 버그가 정상 응답에 묻혀 드러나지 않는다. 미지원 코드를 조용히 폴백하기로 한 이상, 결함 탐지 경로를 최소 하나는 남겨야 한다. 기각.
- **홈만 예외로 두고 나머지는 기존 유지** — 원래 문제(화면별 언어 불일치)가 그대로 남는다. 또 엔드포인트마다 정책이 갈릴 때마다 파서가 늘어난다(초기 설계안은 `fromOrNull` 을 `from` 과 병존시켰다). 기각.

## Consequences

**좋은 점**

- 표시 언어 결정 경로가 요청 하나로 고정된다. 클라이언트는 기기 언어를 모든 요청에 실으면 되고, 화면마다 다른 규칙을 익힐 필요가 없다.
- `:core` 의 `LanguageCode` 가 vocabulary 고유 책임(문자열→enum)만 갖는다. 엔드포인트별 정책은 각 컨트롤러가 소유하므로, 새 정책이 필요해도 `:core` 를 건드리지 않는다.
- 도메인·애플리케이션 서비스가 확정된 `LanguageCode` 를 받아 언어 관련 분기가 사라진다. 타입이 계약을 강제한다.
- 미지원 코드의 400 → 200 완화는 클라이언트를 깨지 않는다.

**감수하는 트레이드오프**

- **조용한 실패.** 클라이언트의 코드 오타(`jp`)나 대소문자 오류(`EN`)가 200 영어로 나가 QA 에서 드러나지 않을 수 있다. 특히 `EN` → 영어는 "우연히 맞아 보이는" 결과라 결함이 오래 남을 수 있다. `lang` 필수화가 부분적 방어일 뿐이다.
- 완화책으로 서버 로그에 미지원 코드 유입을 남기는 것을 후속으로 검토한다(이번 범위 밖).

**파괴적 변경 (릴리스 조건)**

5개 엔드포인트가 동시에 깨진다. 현재 배포된 클라이언트는 홈을 `lang` 없이 호출하고, 음식·북마크도 생략하면 200(`ko`)을 받아왔다. 변경 후 그 호출은 전부 400 이다. **클라이언트 배포 선행 또는 강제 업데이트가 전제**이며, 5개가 한 번에 바뀌므로 클라이언트 릴리스는 한 번으로 끝난다.

**후속**

- ~~스캔 API 는 이 결정의 대상이 아니다~~ → **KB-229 에서 스캔 API 도 `lang` 필수 파라미터로 전환하고 회원 프로필 `appLanguage` 를 제거했다**(specs/kb-229-scan-lang-param). 프로필 기반 언어 결정 지점은 0개다.
- 쿼리 파라미터 검증을 요청 DTO 로 올린 첫 사례다. 이후 신규 API 와 기존 API 이행은 이 패턴을 따른다.
