# ADR-0012: 미완성 음식 candidate 스테이징 → 완성 시 food 승격 파이프라인

- **상태**: Proposed (2026-07-07) <!-- P1 구현·검증 시 Accepted 승격 -->
- **관련**: Jira KB-94(음식 설명 생성·번역)·KB-54(스코어링 영속) · [ADR-0004](./0004-research-bounded-context.md)(research 배치 컨텍스트) · [ADR-0009](./0009-food-avoidance-direct-mapping.md)(food↔기피성분) · [ADR-0013](./0013-batch-bulk-persistence-io-exposed.md)(영속·IO 전략)

## Context

음식 콘텐츠는 **서로 다른 잡·시점에서 부분적으로** 완성된다 — 기피성분 스코어링(KB-54)이 성분 매핑을, 설명 배치(KB-94)가 9개 언어 설명 번역을 채운다. 두 조각은 독립적으로 완성되고, 순서도 정해지지 않는다(성분 먼저일 수도, 설명 먼저일 수도).

`food` 테이블은 API 음식 상세 **서빙 테이블**이다. 여기에 미완성 음식(성분만 있고 설명 없음, 또는 반대)이 섞이면 사용자에게 불완전한 데이터가 노출된다. 특히 **성분 매핑이 없는 음식**이 노출되면 회피 성분 정보가 공백이 되는데, 이는 외국인 대상 서비스에서 **안전 직결** 데이터라 치명적이다.

지금은 스코어링 결과 영속(KB-54)도 설명 생성(KB-94)도 **아직 `food` 에 직접 쓰지 않는다**(현재 `ScoringJobRunner` 는 로그만, 설명 잡은 미구현). 즉 어느 잡도 food 에 쓰기 시작하기 전이라, **저장 구조를 정할 적기**다.

추가 제약: 배치는 청크 순차 처리라 대량이면 실행 시간이 음식 수에 비례해 길어진다(수천 건 → 수 시간). 잡을 새벽 시간대로 분리해도(스코어링 1시·설명 5시) 오버런하면 겹칠 수 있어, **정합성을 실행 타이밍에 의존할 수 없다.**

## Decision

**미완성 음식은 별도 candidate 스테이징 테이블에 쌓고, 완성된 것만 승격 배치가 `food` 로 적재한다.**

- **candidate 테이블은 `:core:research` 가 소유**한다(미스 메뉴 조사·종합 파이프라인 — ADR-0004). enrichment 잡들은 candidate 의 **자기 컬럼만** 채운다(스코어링 → 성분 매핑, 설명 잡 → 설명 번역).
- **승격 배치**(`:app:batch` 독립 러너)가 **완성 조건**을 만족한 candidate 만 `food`(+`food_avoidance_substance`)로 적재한다. 완성 조건 = 성분 매핑 有 && ko 설명 有 && 9개 언어 번역 완비 && 미승격. 적재는 **멱등** — `korean_name` 기준 업서트 + candidate 의 `published_food_id` 링크로 재실행·부분 실패에 안전하며, 음식 1건 = 트랜잭션 1개다.
- **`food` 엔 완성본만 존재**하므로, API 서빙은 별도 publish 플래그·게이트 없이 `food` 조회만으로 완성본만 본다.
- **컨텍스트 경계**(원칙 II): 승격은 배치가 `FoodCandidateRepository`(research) + `FoodRepository`(food) 두 포트를 조합해 수행한다. 두 도메인 객체를 서로 import 하지 않고 **스냅샷 값**(korean_name·설명 텍스트·성분 코드+percent)으로만 옮긴다.
- **정합성은 실행 타이밍에 의존하지 않는다** — 잡 스케줄이 겹쳐도 컬럼-스코프 부분 업데이트 + 멱등으로 안전하다(구체 규칙은 [ADR-0013](./0013-batch-bulk-persistence-io-exposed.md)).

## Alternatives Considered

- **`food` 에 nullable 컬럼을 두고 제자리(in-place) 점진 채움 + `is_published` 플래그.** 빠르게 만들 수 있으나 **서빙 테이블에 미완성 행이 섞이고**, 모든 서빙 조회에 publish 필터를 달아야 하며, 부분 업데이트 실수 한 번에 미완성 음식이 노출될 위험이 있다(안전 직결). 스테이징 분리는 서빙 테이블을 구조적으로 깨끗하게 유지해 "완성본만"을 데이터 배치로 보장한다.
- **잡 실행 시간대 분리(1시/5시)로 동시성 회피.** 청크 순차 처리라 대량이면 오버런해 겹칠 수 있어 **정합성을 보장하지 못한다.** 타이밍은 부차적 최적화로만 두고, 컬럼-스코프 + 멱등으로 타이밍 무관하게 안전을 확보한다.
- **승격 없이 스코어링 잡이 완성 음식을 곧장 food 에 씀.** 설명·성분 완성 시점이 어긋나 "성분만 있는 food"가 생긴다. 두 enrichment 를 한 잡에 묶으면 KB-93 이 없앤 비용(설명을 스코어링 호출에 얹음)이 되살아난다. 분리 + 승격 게이트가 비용·정합성 양쪽을 만족.

## Consequences

**+**
- `food` 서빙 테이블은 항상 완성본 — 안전 직결 데이터(회피 성분) 공백 노출을 구조적으로 차단.
- enrichment 잡들이 candidate 위에서 **독립·병렬**(서로 다른 컬럼) — 스케줄 조율 코드가 필요 없다.
- 승격은 증분·멱등 — 언제 돌든 그 시점 완성분만 흘려보내고 미완성은 다음 실행으로 미룬다.

**−**
- candidate 가 `food` 스키마를 상당 부분 미러링해 **데이터 구조가 중복**되고, candidate→food **매핑·승격 코드**가 필요하다.
- 파이프라인 조각(candidate 생성 · 스코어링→candidate · 설명→candidate · 승격)이 **여러 티켓(P1 골격 · KB-54 · KB-94)에 걸친다** — candidate 테이블·포트·승격 골격(P1)이 나머지의 선행이라 직렬 병목이 된다.

## 후속

- candidate **생성**(메뉴 발견 → 행 + ko 설명 확보)의 소스·시점, 완성 조건의 정확한 술어, candidate 성분 매핑의 저장 형태(JSON 스냅샷 vs 자식 테이블)는 P1 스펙에서 확정한다.
- 스테이징 방식 채택으로 "food = 완성본만"이 자동 충족되어 별도 publish 플래그·서빙 게이트는 두지 않는다(불필요해짐).
