# 0003. 메뉴 데이터 파이프라인 — 사전 번역 배치(9개국어) + 캐시 미스 결과 없음

- **상태**: Accepted
- **날짜**: 2026-06-27
- **관련**: [meogo-data-ai-pipeline](../architecture/meogo-data-ai-pipeline.md), [menu-ingredient-allergy-language-report](../architecture/domains/menu-ingredient-allergy-language-report.md), [ADR-0001](./0001-multi-app-modular-layout.md)

## Context

기존 설계(ADR-0001 이후의 아키텍처 문서)는 메뉴판 스캔을 다음 전제로 잡았다.

- **음식 콘텐츠는 한국어·영어만** DB에 저장한다(그 외 언어는 정적 UI 문구만 사전 번역).
- **캐시 미스 메뉴는 API 서버가 즉시 LLM 3개 모델을 병렬 호출**해 동기적으로 음식 데이터를 만들고, "스캔 API에서 바로 결과를 반환하는 UX"를 우선한다(`meogo-api-module-structure.md` §17).

이후 제품 기획에서 두 전제를 모두 바꾸기로 합의했다.

- **다국어 응답 확대** — 외국인 사용자 대상 서비스이므로, 메뉴를 스캔하면 음식 콘텐츠가 **9개 대상 언어로 미리 번역된 상태**로 내려와야 한다.
- **실시간 LLM 호출 제거** — 스캔 API 응답을 외부 LLM latency·실패에서 분리한다. 캐시 미스는 즉시 "결과 없음"으로 처리하고, 무거운 LLM 처리(재료 조사 + 다국어 번역)는 **하루 1회 배치**로 모아서 돌린다.

이 변경은 강제 규칙(`meogo-conventions.md`의 언어/데이터 정책·외부 호출 규칙)과 데이터/AI 파이프라인 문서를 동시에 뒤집으므로 ADR로 남긴다.

## Decision

메뉴 데이터 파이프라인을 **사전 번역 배치 모델**로 전환한다.

1. **다국어 저장 — 한국어 원문 + 9개 대상 언어.** 음식 콘텐츠(음식명·설명·재료명·알러지/종교/비건 주의 성분)를 한국어(`ko`) 원문 기준으로 관리하고, 9개 언어로 번역해 DB에 저장한다: 중국어 간체(`zh-Hans`) · 영어(`en`) · 일본어(`ja`) · 중국어 번체(`zh-Hant`) · 베트남어(`vi`) · 인도네시아어(`id`) · 태국어(`th`) · 러시아어(`ru`) · 스페인어(`es`). 이 결정은 기존 "음식 콘텐츠는 한·영만 저장" 정책을 대체한다.

2. **캐시 미스 = 결과 없음.** 클라이언트가 보낸 메뉴명이 DB에 없으면(캐시 미스), 그 메뉴는 그 스캔에서 **조회 불가(결과 없음)**로 응답한다. 스캔 API는 캐시 미스 메뉴에 대해 LLM을 **실시간 호출하지 않는다**. 미스 메뉴명은 후속 배치 처리를 위해 적재한다.

3. **하루 1회 배치가 재료 조사 + 9개국어 번역을 수행한다.** 적재된 미스 메뉴를 `meogo-batch`가 하루 한 번 처리한다. 배치는 LLM API 3개 모델(OpenAI · Upstage · Gemini)을 **병렬 호출**하고 응답을 종합하여, 음식 정보·재료 스코어·9개 언어 번역을 만들어 DB에 저장한다. 제품 정책상 이 종합 결과를 신뢰해 사용자에게 제공한다. (3개 응답을 종합하는 정확한 알고리즘은 여전히 미결정.)

4. **LLM 병렬 호출/종합 책임이 API 서버에서 `meogo-batch`로 이동한다.** 기존 §17의 "MVP에서는 API 서버가 LLM 병렬 호출까지 담당한다" 결정을 대체한다. `meogo-api`의 스캔 유스케이스는 캐시 조회 + 위험도 판정만 동기로 수행한다. LLM client(`meogo-infra`)와 응답 종합 로직은 그대로 두되, 이를 트리거하는 주체가 `meogo-batch`다(ADR-0001대로 배치는 `:meogo-api:application` 유스케이스를 트리거하고 `:meogo-api:infra`를 조립한다).

## Alternatives Considered

- **실시간 LLM 유지 + 응답 시 9개국어 즉석 번역** — 첫 스캔에서도 신규 메뉴 결과를 본다. 그러나 스캔 API가 외부 LLM latency·실패·비용에 그대로 노출되고, 9개 언어 번역까지 동기로 하면 응답이 더 느려진다. 기획이 "즉시 결과"보다 "응답 속도·안정성·다국어"를 택해 비채택.
- **온디맨드 비동기(미스 시 큐 적재 후 즉시 워커 처리)** — 배치보다 신선하지만 상시 워커·중복 제어·스케일링이 필요. 트래픽이 적은 MVP에선 하루 1회 배치가 비용·운영상 단순. 필요 시 후속에서 주기를 좁힐 수 있게 열어둔다.
- **9개 언어를 응답 시 번역(저장은 한·영)** — 저장 비용은 줄지만 매 응답마다 번역 비용·지연이 발생하고 캐시 이점이 사라진다. 사전 번역·저장이 읽기 비용을 낮춰 채택.

## Consequences

- **좋음**: 스캔 API 응답이 외부 LLM latency·실패에서 분리돼 빠르고 예측 가능하다. 음식 콘텐츠가 9개 언어로 사전 번역돼 있어 다국어 사용자가 즉시 읽는다. LLM 비용·검수를 배치에서 일괄 처리해 통제하기 쉽다. 배치는 ADR-0001의 "API application 유스케이스를 트리거하는 위성 앱" 구조를 그대로 활용한다(신규 시스템 추가 없음).
- **트레이드오프**: 신규(미등록) 메뉴는 **첫 스캔에서 결과를 볼 수 없고**, 배치가 돈 뒤(최대 ~1일 지연) 재스캔해야 한다 — 이 지연을 클라이언트 UX(예: "조회 중/준비 중" 안내)로 다뤄야 한다. 9개 언어 사전 번역은 저장량·검수·번역 비용을 늘린다.
- **후속/리스크**: ① 미스 메뉴명 적재 저장소·정규화·중복 제거 설계. ② 배치 스케줄·재시도·실패 처리·부분 성공 정책. ③ 9개 언어 번역 품질 검수 플로우(특히 알러지/식이 제한은 안전 직결). ④ LLM 3개 응답 종합 알고리즘은 여전히 미결정(`meogo-data-ai-pipeline.md` §관련 미결정). ⑤ 캐시된 음식 정보의 재번역·갱신 주기.
