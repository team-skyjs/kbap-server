# 최근 스캔 조회가 홈 쿼리 중 가장 무거운 이유와 설계안

2026-10-04, dev 200 rps 부하 측정(RDS 슬로우 로그 `long_query_time=0`) 기준.

## 한 줄 요약

스캔 이력은 "스캔할 때마다 한 줄씩 쌓이는 로그"인데, 홈과 내 스캔 목록은 그 로그에서 "음식별 마지막 스캔 시각 기준 최신 10개"를 매번 새로 계산한다. 10개를 보여 주려고 그 회원의 스캔 행 전부를 읽어 묶고 정렬하는 구조라, 스캔을 많이 한 회원일수록 비례해서 느려진다. 지금은 요청당 8ms 라 병목이 아니지만, 홈 DB 시간의 절반을 혼자 쓰고 있고 성장 방향이 나쁘다.

## 측정값

| 홈 쿼리 (200 rps 부하 중, 4,813회) | DB 평균 | p95 | 최대 | 검사 행 |
|---|---|---|---|---|
| **최근 스캔** (`scan_history` join `food`, group by) | **7.8 ms** | 24.2 | 426 | 964 |
| 인기 음식 | 2.2 ms | 5.3 | 286 | 100 |
| 최다 리뷰 | 1.3 ms | 2.8 | 75 | 41 |
| 나머지 4개 합 | 3.1 ms | | | |

- 홈 DB 시간 14.4 ms 중 54% 가 최근 스캔이다.
- 측정 회원(id 3)은 스캔 행 477개, 음식 213종이다. 10개를 돌려주기 위해 964행을 봤다.
- 요청 전체(2.9초)에서는 0.3% 라 지금의 병목은 커넥션 대기(2.6초)이고 이 쿼리가 아니다.

## 데이터가 쌓이는 방식

`scan_history` 는 **스캔 이벤트 로그**다.

- 메뉴판을 한 번 스캔하면 인식된 메뉴 항목 수만큼 행이 들어간다 (`ScanService.recordHistory` → `saveAll`). 행 하나 = (회원, 음식, 가격, 시각).
- 같은 음식을 다시 스캔하면 또 한 줄이 쌓인다. 갱신이 아니라 **누적**이다. 삭제도 없다(소프트 삭제).
- dev 분포: 31명, 11,667행, 평균 376행/명. 상위 회원은 4,071행에 음식은 19종 — 같은 음식을 평균 214번 스캔한 테스트 데이터다.

이 설계 자체는 맞다. 가격 추이·일별 스캔 수·"이 음식을 언제 마지막으로 봤나" 같은 질문엔 로그가 필요하다.

## 홈이 묻는 질문은 로그와 모양이 다르다

홈이 원하는 건 "**이 회원이 최근에 본 음식 10개, 음식별로 한 번씩, 마지막 스캔 시각 순**"이다. 로그에서 이걸 구하려면 피할 수 없는 단계가 있다.

```sql
select f.*, max(sh.created_at)
from scan_history sh join food f on f.id = sh.food_id
where sh.member_id = ? and sh.status = 'ACTIVE'
  and f.status = 'ACTIVE' and f.content_status = 'READY'
group by f.id
order by max(sh.created_at) desc
limit 10
```

MySQL 이 실제로 하는 일(회원 3, EXPLAIN ANALYZE):

1. 인덱스 `(member_id, food_id, created_at)` 로 회원 3의 행 **477개 전부**를 읽는다.
2. 행마다 `food` 를 조인해 READY·ACTIVE 인지 본다 (477회 조회).
3. 음식별로 묶기 위해 **임시 테이블**을 만들고(213개 그룹) 각 그룹의 `max(created_at)` 을 계산한다.
4. 그 213개를 시각 순으로 **정렬**(filesort)한다.
5. 그제야 앞 10개를 자른다.

`limit 10` 은 5단계에서야 적용된다. 1~4단계는 회원의 스캔 행 수에 비례한다. 즉 **비용 = 회원의 스캔 행 수**이고, 10개라는 결과 크기와 무관하다.

### 인덱스가 못 돕는 이유

`idx_scan_history_member_food_recent (member_id, food_id, created_at)` 은 2026-09-30 에 (member_id, created_at) 을 대체해 들어왔다. 이 인덱스는

- "회원의 행 찾기"(1단계)와 "회원+음식의 마지막 스캔"(`findLastScannedAt`)에는 딱 맞는다.
- 그러나 "마지막 스캔 시각 **순**"은 인덱스에 없는 값이다. `max(created_at)` 은 그룹을 다 묶은 뒤에야 나오는 집계 결과라 어떤 인덱스로도 정렬을 대신할 수 없다. 그래서 임시 테이블과 filesort 가 항상 붙는다.

### 조인이 더하는 비용

`food` 를 조인하는 이유는 READY 아닌 음식(사진·설명 준비 중)과 삭제된 음식을 빼기 위해서다. 필터를 위해 477회 조인하고, 최종 10개는 `f.*` 전체(JSON 컬럼 3개 포함)를 하이드레이션한다. 회원 35 처럼 음식 수가 적은 경우엔 옵티마이저가 반대로 READY 음식 590개를 먼저 훑고 음식마다 스캔 인덱스를 찍는 플랜을 고르기도 한다. 어느 쪽이든 "10개 결과를 위해 수백 행"이다.

## 성장 모델

| 회원 유형 | 스캔 행 | 예상 DB 시간 |
|---|---|---|
| 측정 회원 (dev) | 477 | 8 ms (부하 중), 2~3 ms (무경합) |
| 하루 2회 × 메뉴 5개 × 1년 | 3,650 | 수십 ms |
| 헤비 유저 (수만 행) | 20,000+ | 100 ms 이상 |

홈은 앱의 첫 화면이라 회원이 들어올 때마다 이 계산을 다시 한다. 캐시도 없다(회원별·시각별로 다르니 캐시 효율도 낮다).

## 같은 구조가 세 곳에 있다

| 기능 | 리포지토리 메서드 | 모양 |
|---|---|---|
| 홈 최근 스캔 | `findRecentScannedFoods` | 위 쿼리 그대로 |
| 내 스캔 목록 페이지 | `findScannedFoodPageIds` | 같은 group by 를 서브쿼리로 만든 뒤 커서로 자른다. **페이지를 넘길 때마다 전체 group by 를 다시 한다** |
| 내 스캔 검색 | `findScannedFoodIds` | 같은 group by + 음식명 LIKE |

내 스캔 목록 페이지가 더 나쁘다. 홈은 한 번이지만 목록은 스크롤마다 전체를 다시 계산한다.

## 설계안

### A. 회원별 "본 음식" 읽기 모델 (권장, 다음 성능 라운드)

```
member_scanned_food
  member_id        bigint   ─┐ PK
  food_id          bigint   ─┘
  last_scanned_at  datetime
  scan_count       int
  index (member_id, last_scanned_at desc)
```

- 스캔을 저장할 때 같은 트랜잭션에서 `insert ... on duplicate key update last_scanned_at = now(), scan_count = scan_count + 1`. 음식당 한 행이라 회원 35 는 4,071행 대신 19행이다.
- 홈: `where member_id = ? order by last_scanned_at desc limit 10` → 인덱스로 **10행만** 읽는다. 임시 테이블·정렬 없음. 스캔을 1만 번 해도 비용이 같다.
- 목록 페이지: 커서 `(last_scanned_at, food_id)` 로 그대로 넘긴다. 검색은 이 테이블과 `food` 를 조인하되 회원의 "본 음식" 수(수십~수백)만 본다.
- READY 필터는 그대로 `food` 조인으로 한다. 조인 대상이 10~수백 행이라 문제없다.
- `scan_history` 로그는 그대로 둔다. 가격·통계·"마지막 스캔 시각" 조회는 로그가 맡는다.
- 마이그레이션 때 로그에서 한 번 백필한다(`insert ... select member_id, food_id, max(created_at), count(*) ... group by`).
- 비용: 테이블 1개, 엔티티 1개, 스캔 저장 경로에 upsert 1줄, 조회 3곳 교체. 변경 중 블루/그린 공존은 두 테이블을 같이 쓰므로 안전하다.

### B. 최소안: 앱에서 최신 N행만 보고 거르기

인덱스를 `(member_id, created_at desc)` 로 되돌리고 "최신 행부터 읽다가 서로 다른 음식 10개가 모이면 멈춘다"로 바꾼다. 보통 회원은 수십 행만 읽는다. 그러나 같은 음식을 반복 스캔하는 회원(35 처럼)은 10개를 모으려고 수천 행을 읽게 돼 상한이 없다. 목록 페이지 커서와도 맞추기 어렵다.

### C. 그대로 두기 (지금)

8ms 는 요청 2.9초의 0.3% 다. 지금 홈을 느리게 만드는 건 태스크 CPU 와 커넥션 대기이고, 그걸 풀고 처리량이 200 rps 를 넘어 RDS 가 병목이 되는 시점에 이 쿼리가 가장 먼저 커진다. 그때 A 로 간다.

## 참고

- dev 의 회원 35(4,071행/19음식) 는 부하 테스트가 만든 데이터라 실제 분포를 과장한다. 설계 판단은 "회원당 스캔 행 수는 시간에 비례해 늘고 상한이 없다"는 사실에만 기대면 된다.
- 측정 방법: RDS 슬로우 로그(`kbap-dev-mysql84` 파라미터 그룹, `long_query_time=0`) → CloudWatch `/aws/rds/instance/kbap-db-devstg/slowquery` → 문장 정규화 후 집계. Hibernate `HHH000117` 로그는 네이티브 쿼리의 DB 시간을 포함하지 않아 쓰지 않았다.
